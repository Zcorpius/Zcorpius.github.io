Android 系统启动：system_server

源码基线：本笔记以当前工作区 Android 15 frameworks/base、frameworks/base/core/jni 为准。system_server 不是由 init 直接 exec 出来的进程；它是 Zygote fork 出的第一个 Java 子进程。Zygote 的启动、预加载和 socket 轮询见《03-Zygote进程》。

1. 角色、边界与总链路

system_server 以 system UID 和 SELinux u:r:system_server:s0 域运行，是 Java framework 服务的宿主。AMS、ATMS、PMS、WMS 等服务大多在同一个进程内；它们之间可以直接调用 Java 对象，也会将 Binder 接口发布给其他进程。

启动主线如下：

init 启动 primary zygote → ZygoteInit.main() 预加载 → forkSystemServer() → native fork() 与特权收缩 → 子进程执行 SystemServer.main() → SystemServer.run() 创建上下文与服务管理器 → 按依赖顺序启动服务、推进 boot phase → AMS systemReady() 后允许第三方应用启动。

不要把以下三件事混为一谈：

  • 进程创建：Zygote fork() 得到 system_server；
  • 服务构造/启动：SystemServiceManager 构造 SystemService 并调用 onStart()；
  • Binder 可见：服务自行通过 ServiceManager.addService() 发布 Binder。onStart() 并不必然等于已发布 Binder。

2. Zygote fork system_server

2.1 ZygoteInit 构造固定启动参数

Zygote 在自身完成预加载、GC 和 native 初始化后调用 forkSystemServer()。参数包含 system UID/GID、补充 group、能力集及 Java 入口 com.android.server.SystemServer。

pid == 0 是子进程分支；父 Zygote 得到子 PID 后继续 runSelectLoop()。在双 Zygote 设备上，子进程会先等待 secondary zygote，以降低 ABI 环境未就绪时 system_server 过早启动的风险。

2.2 Java 到 JNI：fork 前后 Hook

Zygote.forkSystemServer() 与普通应用的 forkAndSpecialize() 共享大部分 fork 机制。Java 在 fork 前调用 ART Hook；子进程恢复线程优先级并进行 fork 后公共初始化。

2.3 native fork：system_server 死亡会连带杀死 Zygote

native 层记录 system_server PID。SIGCHLD 处理逻辑发现该 PID 死亡时会 SIGKILL Zygote；这样 init 观察到 zygote 退出，可按其服务规则恢复一整套 Java 运行时，而不是留下失去核心服务的 Zygote。

2.4 特权收缩与安全域

ForkCommon() 负责停用/恢复信号和 fork 相关的通用动作；子分支 SpecializeCommon() 才真正把“预加载时的 root Zygote”转为“system_server 身份”。其关键工作包括关闭不应继承的 FD、设置 cgroup/调度策略、资源限制、挂载隔离、setgroups/setresgid/setresuid、能力集、SELinux context、seccomp 等。

这里不能概括成“fork 后设置 UID”。安全域与凭据切换的顺序、FD 清理、挂载和 seccomp 共同组成进程隔离；任何一个环节缺失都可能造成权限或资源泄漏。

3. 子进程进入 SystemServer.main

handleSystemServerProcess() 处理可选 wrapper，然后交给 ZygoteInit.zygoteInit()。后者完成 app 级 Runtime 初始化、启动 Binder 线程池，并反射找到 SystemServer.main(String[])；Runnable 的返回结构用于清除 Zygote 调用栈。

4. SystemServer.run()：进程级地基

run() 的前半段不是“启动 AMS”那么简单：它先配置 system_server 自身的 Binder、主线程 Looper、native 库、系统 Context、诊断对象和并行初始化线程池。

几点容易误解：

  • system_server 已经在 zygoteInit() 中启动了 Binder 线程池；setMaxThreads() 是调整该进程 Binder 线程池上限，不是首次启动 Binder。
  • Looper.prepareMainLooper() 只为 system_server 主线程准备消息循环；Binder 调度与这个 Looper 是两套协作机制。
  • SystemServerInitThreadPool 用于可并行的初始化任务，不能随意把有严格依赖的服务丢进去。

5. 四个服务启动批次与依赖关系

Android 15 明确按四个方法编排，而不是过去常见的“只分 bootstrap/core/other”三段：

批次 目的与代表服务 依赖特点
startBootstrapServices Installer、ATMS、AMS、PMS 前置项、Power 等 建立最基础的系统调度、安装与包管理能力
startCoreServices Battery、UsageStats、WebViewUpdate、SystemConfig 等 依赖核心服务已存在
startOtherServices WMS、Input、Alarm、Network、Notification、Location 等 大量硬件能力/特性/属性条件分支
startApexServices APEX 中声明的 system-server jar 服务 模块化服务，排序与类加载由配置决定

5.1 Bootstrap 中的 AMS/ATMS 关系

ATMS 与 AMS 是两套对象、强协作但不等价。Android 15 中 ATMS 通过 SystemServiceManager 启动；AMS 由其 Lifecycle.startService() 创建，并注入同一个管理器与 Installer。

5.2 SystemServiceManager 的通用启动协议

它只管理继承 SystemService 的生命周期：反射构造（或指定类加载器）、加入已启动列表、调用 onStart()，随后在每一个 boot phase 回调所有已启动服务。服务是否发布 Binder、是否注册 LocalServices，由服务自身决定。

5.3 APEX 服务不是普通 Java 类名硬编码列表

startApexServices() 通过 ApexManager 获取 APEX 声明的服务信息，按其 name/jarPath 启动。它必须是最后一类启动的服务，随后 SystemServiceManager 被 seal；因而 OEM 或 Mainline 模块中服务是否存在、排序如何，不能只根据 SystemServer.java 中的硬编码行号判断。

6. Boot phase：服务启动后仍需“就绪”

onStart() 仅表示服务已被创建并接受启动回调。系统以递增 phase 通知服务满足更高层前提，例如默认 Display、传感器、锁设置、系统服务、设备专属服务、AMS ready、可启动第三方应用、开机完成。

Android 15 SystemServer 中可见的关键推进点包括：

  • PHASE_WAIT_FOR_DEFAULT_DISPLAY：PMS 初始化前，需要默认 Display；
  • PHASE_WAIT_FOR_SENSOR_SERVICE：WMS 创建前等待 sensor service；
  • PHASE_LOCK_SETTINGS_READY、PHASE_SYSTEM_SERVICES_READY；
  • PHASE_DEVICE_SPECIFIC_SERVICES_READY；
  • PHASE_ACTIVITY_MANAGER_READY：放在 AMS systemReady() 回调中；
  • PHASE_THIRD_PARTY_APPS_CAN_START：允许第三方代码真正运行；
  • PHASE_BOOT_COMPLETED：完成后关闭初始化线程池。

相同 phase 会回调“截至此刻已启动”的所有服务；因此服务若在较晚阶段才启动，不会自动补收早期 phase，启动顺序是设计的一部分。

7. AMS systemReady() 与允许应用启动

SystemServer 不能在“服务都 new 完”后立即认为 Android 已可用。它先让 PMS、WMS、Display 等完成各自 systemReady()；再进入 ActivityManagerService.systemReady()，在其回调中继续推进服务、启动 SystemUI 等关键组件，并最终到达“第三方应用可启动”阶段。

systemReady() 中还涉及用户、设置、存储解锁、广播、provider、应用启动等状态切换；其内部细节随分支和设备形态变化很大。阅读时应沿 ActivityManagerService.systemReady() 与 SystemServer 回调两端一起追，不应把它误写成“AMS 启动 Launcher 的单一步骤”。

8. 调试与阅读路径

  • 性能时间线：atrace / Perfetto 中查看 SystemServer、StartServices、StartService *、OnBootPhase_*；代码使用 TimingsTraceAndSlog 写入相应 trace。
  • 日志：logcat -b system -s SystemServer SystemServiceManager ActivityManager；启动失败会在 SystemServer.run() 的 StartServices catch 中抛出。
  • Binder 服务：service list、dumpsys <service>；这观察的是已发布 Binder，不等于 mServices 的完整列表。
  • 启动状态：getprop sys.boot_completed 与 dumpsys activity 可辅助确认 AMS 的后续状态，但不同设备的属性时序可能受厂商服务影响。

9. 小结

  1. system_server 是 Zygote 的特殊子进程；其死亡会触发 Zygote 自杀，交给 init 重建 Java 世界。
  2. native specialize 不只是改 UID，而是落实 FD、挂载、capability、SELinux、seccomp 等隔离边界。
  3. SystemServer.run() 先搭建进程基础设施，再按 bootstrap → core → other → APEX 启动服务。
  4. SystemServiceManager.onStart()、Binder 发布、onBootPhase() 是三个不同层次；不要混用“服务启动完成”。
  5. PHASE_THIRD_PARTY_APPS_CAN_START 才是“可以真正运行第三方应用”的关键门槛，AMS systemReady() 是其中的枢纽。
