Android 系统启动——SystemServer进程

发表于 2025-09-30 | 分类于 Android ， StartUp
字数统计: 10.1k | 阅读时长 ≈ 39

1. 从“进程出现了”到“系统可以用了”

启动 Android 时，ps 已经能看到 system_server，service list 也能找到 power，为什么系统仍可能停在开机画面？因为这两个现象分别只能证明进程存在和Binder 接口已发布。服务依赖是否齐备、应用是否允许启动、开机是否完成，还由后续状态决定。

system_server 是 Java framework 核心服务的宿主。ActivityManagerService（AMS）、ActivityTaskManagerService（ATMS）、PackageManagerService（包管理服务）和 WindowManagerService（WMS）等主要对象在这里协作。本文从 Zygote 创建它开始，追到服务初始化、boot phase 和主线程消息循环；重点不是背服务名单，而是回答四个问题：

  1. Zygote fork 出来的子进程，怎样进入 SystemServer.main()？
  2. startService()、publishBinderService()、onBootPhase() 各改变什么？
  3. 系统怎样按依赖推进启动，而不是把所有服务一次性 new 出来？
  4. 开机停住时，怎样区分进程问题、服务初始化问题和后续应用启动问题？

贯穿全文的例子是 PowerManagerService（电源管理服务）：观察它从对象构造，到发布 power，再到获得显示、窗口策略、电池等运行依赖，最后接收开机完成阶段。为避免与包管理服务混淆，本文不把这两个服务都缩写成 PMS。

Note

源码范围：以本地 LineageOS 目录为准。manifest 默认分支为 lineage-22.2，vendor/lineage/config/version.mk 标识 22.2，构建目录的 Android 15 版本配置与之对应。本文主要依据 frameworks/base 的本地提交 f8d852aaaa843b9d74db780bb11d4691b3ceebc0（核对时为 detached HEAD）；它是本地实现依据，不能等同于某个未经核对的 AOSP 发布标签。本文摘录的启动、生命周期、电源管理文件无未提交修改。

下文代码均为源码节选，添加中文讲解注释；... 表示省略非关键实现，不能作为独立编译单元。路径相对于用户提供的源码根。

前一篇 《Zygote 进程》 解释了预加载和应用创建请求。本篇从其中的特殊分支 forkSystemServer() 接续。

2. Zygote 怎样把执行权交给 SystemServer

2.1 fork 之后，父子进程走不同的路

fork() 之后，父子进程都会从返回位置继续执行，但返回值不同：父进程得到子 PID，子进程得到 0。因此，下面这张图不是“Zygote 依次调用完所有框”，而是存在一次真正的进程分流。

图 1：绿色箭头表示创建子进程，橙色箭头表示各自进程内的执行顺序；图示采用未配置 wrapper 的正常路径。

Zygote 使用一组固定参数指定子进程身份和 Java 入口。与普通应用启动相比，这里没有先等 AMS 发送创建请求：启动主 Zygote 时的 startSystemServer 参数决定是否走这条特殊路径。

Zygote.forkSystemServer() 的 Java 包装负责 ART 的 fork 前后 Hook，再进入 JNI 的 nativeForkSystemServer()。后者用 ForkCommon() 创建子进程，并在子分支执行 SpecializeCommon()。

这里的“特化”是把从 Zygote 继承来的运行环境收束为目标进程的身份和资源边界。system_server 使用 system UID/GID（1000），不是 root；它保留所需的能力集，并进入 u:r:system_server:s0 安全域。UID、Linux capabilities 和 SELinux 是不同层面的约束，不能仅凭 UID 判断它是否能完成某项操作。

所在位置 本文需要理解的作用
ForkCommon() 完成 fork 相关的公共准备及子进程 FD 处理，避免把不该继承的通信端点带入新进程
SpecializeCommon() 按目标身份处理补充组、资源限制、GID、seccomp、调度、UID、capabilities 和 SELinux 等
handleSystemServerProcess() 设置文件创建掩码、进程名，准备 system_server ClassLoader，选择正常入口或 wrapper 分支

这些动作有先后约束。例如本地实现先 setresgid()、安装 seccomp 过滤器并设置调度策略，再 setresuid()，之后设置 capabilities 和安全域。不能把这一阶段压缩成“改一下进程名”，也不应把其中所有 app 专用隔离分支一概说成 system_server 必定执行。

2.2 Runnable 是入口包装，不是新线程

子进程需要用 system-server classpath 加载 SystemServer 及相关代码。正常路径取得专用 ClassLoader 后，调用 zygoteInit()；如果配置了 mInvokeWith，则改走 WrapperInit.execApplication()，本节不把这个调试分支画入主线。

applicationInit() 解析目标类名；findStaticMain() 用 ClassLoader 找到 public static main(String[])，再把反射方法和参数封装成 MethodAndArgsCaller。这个对象实现 Runnable，但 Runnable.run() 只是一段可调用的代码；只有交给线程或执行器，才涉及新的调度。这里的调用者仍是子进程当前线程：

让 Runnable 逐层返回，再调用它，会使中间的入口准备函数先退栈；它不表示“已经退掉了整个 Zygote Java 主入口”。本地 RuntimeInit.findStaticMain() 附近还留有提到 throw/catch 的历史注释，判断当前机制应以实际的 return new MethodAndArgsCaller(...) 与 r.run() 为准。

2.3 system_server 死亡为什么会牵动 Zygote

native 父分支把新 PID 保存为 gSystemServerPid，并额外用一次非阻塞 waitpid() 检查子进程是否已经过早退出。正常运行后，Zygote 的 SIGCHLD 处理逻辑也会识别这个 PID：

因此，排查一次 framework 运行时重启时，可能同时看到 system_server 和 Zygote 的 PID 改变。这个联动不等于每次都重启内核；init 的重启规则、故障次数及恢复策略还会影响最终结果。本文只确认这里的死亡联动，具体服务恢复机制接回 init 与 Zygote 篇。

3. run() 先给服务准备运行环境

SystemServer.main() 只有一个关键动作：new SystemServer().run()。它创建的是一个 Java 对象，进程早在上一章的 fork 位置就存在了。

3.1 Context、Looper 和 Binder 分别解决什么问题

服务需要访问资源和系统环境，需要处理本地异步消息，也需要接收其他进程的调用。这三种需求分别对应 Context、Looper/Handler 和 Binder；它们互相协作，但不是同一套机制。

这里有几个需要连接起来理解的事实：

  • Binder 线程池先于 run() 启动。 nativeZygoteInit() 经 AndroidRuntime 到 app_process 的 AppRuntime::onZygoteInit()，在那里调用 ProcessState::startThreadPool()。这里的 setMaxThreads() 是后续配置；本地 sMaxBinderThreads 为 31，不代表此刻已经创建了 31 个线程。
  • prepareMainLooper() 不会立即处理消息。 启动流程仍在当前线程向下执行，直到末尾 Looper.loop() 才进入主线程消息分发。服务若在这段同步初始化里等待“自己发给主线程的消息执行完”，就可能让启动无法前进。
  • Binder 请求也不必一律先经过主 Looper。 来自其他进程的 Binder 请求由 Binder 工作线程接收；服务是否再转交 Handler，由具体实现决定。服务发布接口后，必须考虑启动中途收到请求的情况。

Binder.setWarnOnBlocking(true) 也不能解释成“同步调用从此被禁止”。它启用的是阻塞调用相关的警告机制；设计上仍需避免关键线程被慢调用拖住。

3.2 ActivityThread.systemMain() 不会另起一个应用进程

系统服务同样需要 Android 的资源、配置、包上下文等能力。createSystemContext() 借助 ActivityThread 建立系统侧上下文：

ActivityThread 的类名容易让人以为这里在启动 Activity。实际的 systemMain() 是 new ActivityThread()、attach(true, 0) 并返回对象；本段没有 fork，也没有发起 HOME。这里的 systemUiContext 是供系统侧使用的 Context，取得它不等于启动了 SystemUI 应用。

3.3 临时初始化线程池与长期工作线程

SystemServerInitThreadPool 用于可以并行的初始化任务。提交任务只表示安排执行，后续消费者仍要在依赖点等待结果。例如 WebView 准备可以先在池中运行，推进 phase 600 前再等待对应 Future；这一等待会在第 6 章看到。

它不取代 Binder 线程池，也不是所有服务的长期线程池。到 phase 1000 的回调分发结束后，SystemServiceManager 才调用其关闭逻辑；关闭过程还会等待任务退出并检查未完成任务。

另一方面，Watchdog 在 bootstrap 的早期启动，用于监视系统关键线程和锁的健康状态。耗时初始化、死锁监测和 Binder 线程调度各有职责，不能把它们都归到一个“主循环”里。

4. 一个服务对象，三种不同的管理关系

4.1 先分清谁管理生命周期，谁保存接口

如果只看名字，SystemServiceManager、ServiceManager 和 LocalServices 很容易混在一起。它们回答的其实是三个不同的问题：

对象或机制 保存、管理什么 PowerManagerService 的对应例子
SystemServiceManager 本进程内的 SystemService 实例及生命周期，核心列表是 mServices 构造电源服务，调用 onStart()，随后分发阶段回调
Java ServiceManager → native servicemanager 通过 Binder 注册、查询名字对应的 Binder 接口 向外发布名为 power 的接口
LocalServices 当前进程中的 Class<?> → Object 映射 用 PowerManagerInternal.class 取得内部 Java 接口

system_server 是服务宿主进程；SystemServer 是入口和启动编排类；SystemService 是参与这套生命周期协议的基类。它也不同于应用组件 android.app.Service：对 SystemService 调用 startService()，不意味着创建一个 APK 进程。

图 2：橙色实线表示生命周期调用，蓝色虚线表示接口注册。phase 500 的回调由管理器在后续阶段发起，不是 onStart() 自行调用。

同一服务可以同时发布 Binder 接口和本地接口，也可以只提供其中一种。LocalServices 中保存的是 Java 对象引用，获取后可在同一进程直接调用；它不会因为名字里有 Service 就自动经过 Binder 驱动。Binder 名字表的详细实现见 《Servicemanager 进程》。

4.2 startService() 完成构造和 onStart()，不自动发布 Binder

startService(PowerManagerService.class) 传入的是类对象，管理器用反射找到公开的 Context 构造器。泛型中的 <T extends SystemService> 约束 T 必须是该基类的子类，并使返回值保持具体服务类型。

列表登记发生在 onStart() 之前。onStart() 抛异常时，这段实现会向上抛出启动失败，并没有先回滚列表再继续下一个服务。因此，“出现在 started services 列表里”也不是服务已成功完成全部初始化的充分证据。

还要注意查重的范围：查重在接收实例的重载里。如果重复调用接收 Class 的重载，反射构造已经先发生，随后才发现类名重复。不要把这里理解成一个保证“绝不重复构造”的通用依赖注入容器。

从保留代码可以直接看到：管理器没有通用的 addService() 语句。Binder 是否发布、用什么名字、允许谁访问，仍要阅读服务自己的 onStart()。

4.3 PowerManagerService 为什么先发布，再补齐依赖

电源能力很早就可能被其他系统组件使用。本地 SystemServer 在启动它的注释中明确要求：注册后必须能够立即处理进入的 Binder 调用，包括权限检查。与此同时，完整的电源状态协调还依赖稍后才准备好的显示、窗口策略、电池等对象。

这就形成了“两段初始化”：先建立可被访问的服务与接口，再在合适的系统阶段取得运行依赖。

publishBinderService() 最终调用 ServiceManager.addService()，publishLocalService() 则调用 LocalServices.addService()；这两个辅助方法定义在 SystemService.java 中。

回到开头的场景：service list 查到 power，说明外部能查询到这个 Binder 名字；它不证明电源服务已经执行完 systemReady()，更不证明它已收到 phase 1000。反过来，也不能说 phase 500 前电源接口“一律不能调用”：提前发布正是为了让需要早期工作的接口能够被访问，各方法必须按自身状态和权限规则处理请求。

5. 服务启动批次与 boot phase 是两条交错的轴

5.1 四个方法编排创建顺序

SystemServer.run() 依次调用四个服务启动方法。它们是源码组织方式，不是四个线程，也不是四个公开的系统就绪状态。

启动方法 本地实现中的代表内容 读代码时关注什么
startBootstrapServices() Installer、ATMS、AMS、Power、Display、PackageManager 等 基础依赖紧密耦合，顺序与对象注入直接影响后续初始化
startCoreServices() SystemConfig、Battery、UsageStats、WebViewUpdate 等 依赖已有基础能力；如 WebView 服务受设备 feature 条件控制
startOtherServices() WMS、输入、网络、通知等服务及多个 ready 调用 大量条件分支；这里同时推进多个 boot phase
startApexServices() APEX 声明的 system-server 服务 按 APEX 信息选择类加载路径，最后封存服务集合

例如，ATMS 负责 Activity/任务相关的管理，AMS 还承担进程、应用组件与系统运行协调。它们是互相协作的不同对象。Lifecycle 包装类使不直接继承 SystemService 的核心服务也能接入统一生命周期：

这段顺序体现了两种依赖处理：把已经创建的对象直接注入后续服务，以及在继续初始化前推进一个明确的阶段并等待相应条件。

并非所有核心服务都走 SystemServiceManager.startService()。WMS 在 startOtherServices() 中通过 WindowManagerService.main(...) 创建，再由 ServiceManager.addService(Context.WINDOW_SERVICE, wm, ...) 发布。因此，生命周期列表与 Binder 名字表不应被期待为一一对应。

5.2 boot phase 是依赖通知，也可以成为等待点

如果在构造函数里就要求所有其他服务可用，很容易遇到循环依赖：A 的构造需要 B，B 的构造又需要 A。boot phase 的作用是把“建立对象和接口”与“依赖满足后完成某部分工作”分开。

SystemServiceManager 保存当前阶段 mCurrentPhase。推进阶段时，它直接遍历当时的服务列表，调用每个服务的 onBootPhase()：

由此可以推导出四条规则，而不必把 phase 想象成某种隐含的后台广播：

  1. 阶段只能严格增大。 重复推进同一个值也会抛异常；这段代码没有要求数字连续。
  2. 同一次分发按列表顺序同步调用。 一个回调尚未返回，后面的回调和调用者的后续语句就不能继续。callback 这个名字本身不代表异步。
  3. 晚加入的服务不会自动补收旧阶段。 方法没有保存和重放历史阶段，startService() 也没有补发逻辑。
  4. 异常不是被记录后忽略。 某个回调抛异常会中断这次分发；mCurrentPhase 却已经更新。因此只看 Current phase: 500，不能断言所有服务都完成了 500 的工作。

在本文从 SystemServer.run() 展开的启动路径上，这些同步分发由 system_server 主线程发起。判断其他调用入口的执行线程时仍应追调用者；startBootPhase() 自身不负责切换到某个线程。

5.3 关键阶段怎样嵌进启动过程

下面的数值和语义来自 SystemService.java，推进位置来自本地 SystemServer.java 与 AMS。它们是阶段编号，不是进度百分比。

phase 常量去掉 PHASE_ 后的名称 本地推进位置与含义

200 WAIT_FOR_SENSOR_SERVICE other 内，创建 WMS 前等待 SensorService 可用
480 LOCK_SETTINGS_READY other 内，锁设置准备好后通知依赖方

520 DEVICE_SPECIFIC_
SERVICES_READY		 other 内，设备专属服务准备之后

需要区分“调用点开始推进一个 phase”与“该 phase 的前提全部满足”。phase 100 就是一个直观例子：DisplayManager 的回调本身承担等待工作。

因此，“DisplayManagerService 的 onStart() 已执行”不能替代 phase 100 的条件检查。若默认显示仍没准备好，主启动流程会停在这里等待；超时抛异常时，正常路径不会继续完成后面的 PackageManager 初始化。

这也是为什么需要把启动批次和就绪阶段放在同一张时间线上：phase 100 发生在 bootstrap 尚未结束时；480～600 发生在 other 内；APEX 这批服务则在 other 返回后才创建。不存在“先把四批服务全启动，再统一从 100 通知到 1000”的过程。

6. AMS 的 systemReady() 怎样接住后半程

6.1 一个同步回调把启动编排接回 SystemServer

到 startOtherServices() 后段，SystemServer 已经推进 500、520，并调用了 WMS、PackageManager、Display 等服务各自的 ready 方法。接下来需要 AMS 建立允许启动应用的内部状态，同时给其他服务一次收尾机会。

这里的参数 goingCallback 是 Runnable。AMS 先准备自己的状态，然后直接调用 goingCallback.run()；回调返回后，AMS 再继续初始应用相关逻辑。

这段代码的意义不是“给 AMS 发了一条消息，等它将来再答复”。在正常启动调用栈中，SystemServer 调 AMS，AMS 又同步执行 SystemServer 提供的 lambda，结束后才返回继续。把回调里的慢操作挪到线程池后，如果仍在回调中等待 Future，其等待依赖也没有消失。

6.2 600 前要等待什么，600 后还要做什么

看回调两端，才能准确理解“第三方应用可以启动”这句话：

phase 600 通知服务可以启动或绑定第三方应用，但并不保证每个应用都立刻可运行。权限、用户状态、组件可用性、存储解锁等各自的条件仍然存在。更不能把它当成“所有开机工作已经完成”。

当前源码中的 SystemUI 顺序尤其值得单独记住：它位于 AMS 回调之外，且在 600 之后。startSystemUi() 取得 SystemUI 服务组件，用 context.startServiceAsUser(..., UserHandle.SYSTEM) 发起启动请求，再通知 WMS。发请求返回不等于 SystemUI 已完成绘制；这也与第 3.2 节创建 systemUiContext 是两件事。

6.3 APEX 最后启动，为什么不能依赖补发旧阶段

APEX 可以携带模块化的系统服务。这里读取的是 ApexManager 提供的服务信息，再根据是否有独立 jar 路径选择启动方式：

源码注释要求这批服务最后启动，以降低 APEX 独立更新时带来的稳定性与依赖问题。sealStartedServices() 将已启动服务列表转成不可修改的列表；它约束这套生命周期登记，不能解释成“此后系统里任何对象、Binder 接口或应用组件都不能再创建”。

结合第 5.2 节，可以得到一个实际的模块设计约束：在此处才加入列表的服务，不会自动收到已过去的 500、550、600。如果把必要的初始化只写在 if (phase == 500) 分支，而又直到 APEX 阶段才启动，就不能期待框架替它补做。应按该服务真实的启动时机安排初始化和后续阶段处理。

6.4 Looper.loop() 与 phase 1000 的边界

四批服务启动完成后，主线程进入 Looper.loop()，持续处理自己的消息。Binder 工作线程和各服务专用线程继续承担各自任务；“SystemServer 启动代码走到末尾”是进入长期运行阶段，不是让进程退出。

phase 1000 则在后续 AMS finishBooting() 路径推进。该函数开头会检查 mBootAnimationComplete，尚未满足时设置 mCallFinishBooting 并返回；因此它不是一个忽略显示链路、按固定延迟自动触发的通知。

对 PowerManagerService 而言，这时才执行第 4.3 节中的 mBootCompleted = true 和相关电源状态更新。对 SystemServiceManager 而言，这一阶段的回调完成后还要关闭初始化线程池。

phase 1000、sys.boot_completed 属性、各用户收到 BOOT_COMPLETED 广播、桌面实际可见，是相关但不能互换的观察点。 HOME、开机动画、启屏以及用户广播的后续链路，继续阅读 《07-开机界面与完成》；本文不展开它们的完整时序。

7.1 沿电源服务走完一次正常启动

7.2 三个场景，先预测再定位

场景 A：power 已在 Binder 名字表中，但开机还没完成。

这并不矛盾。电源服务在 bootstrap 的 onStart() 就发布接口，500、600、1000 都是后续的工作。下一步应看当前 phase、dumpsys power 的状态，以及服务初始化日志。如果稳定停在 100，则应优先追默认显示等待路径，不能因为查到了 power 就把焦点直接跳到 Launcher。

场景 B：日志显示 Starting phase 500，随后某服务抛异常。

mCurrentPhase 已在循环前写成 500。假设列表顺序为 A、B、C，A 的回调返回，B 抛异常，则本次分发不会继续执行 C。应从异常中读出服务类名和阶段，再检查对应的 onBootPhase()。仅凭“Starting phase 500”或 dump 中的 500，都不能宣称这一阶段成功完成。

场景 C：一个在 APEX 阶段创建的服务，把关键初始化只放在 onBootPhase(500)。

从正常顺序看，此时 500 已过去。新对象会得到 onStart()，管理器却不会回放旧阶段，所以那段初始化不会因“加入了服务列表”而自动执行。排查时应把该类出现在 started services 中的事实，与它的实际创建位置一起看，而不是只检查 phase 常量拼写。

8. 记忆分层与折叠自测

8.1 L0：先抓住四个状态

进程存在 → 服务对象已建立 → 接口已发布 → 相应依赖与启动阶段已满足。 它们是可以分别观察的事实，不能互相替代；具体服务的发布与准备过程还要看实现。

system_server 从 Zygote 的子分支进入 SystemServer.main()，由 run() 组织基础设施和服务，随后依靠主 Looper、Binder 线程池及专用线程长期运行。

8.2 L1：应当能自己展开的主干

  • 入口链：forkSystemServer() → native fork／specialize → handleSystemServerProcess() → zygoteInit() → 返回 Runnable → r.run() → SystemServer.main()。
  • 服务链：SystemServiceManager.startService() → 构造 → 列表登记 → onStart()；服务自身决定 Binder／LocalServices 的发布。
  • 依赖链：四个启动批次之间穿插 boot phase；startBootPhase() 同步遍历，当前值先更新，迟到服务不补收旧阶段。
  • 后半程：AMS 准备状态 → 同步回调推进 550、600 → AMS 后续启动逻辑 → 返回后请求 SystemUI → APEX 与 seal → 主 Looper；1000 另由后续 finishBooting() 推进。

8.3 L2：按问题查细节，不必背完整服务名单

遇到的问题 优先定位
system_server 的 UID、能力集或 ClassLoader 不符 ZygoteInit.forkSystemServer()、handleSystemServerProcess()、native SpecializeCommon()
某服务为什么早／晚启动 SystemServer 四个批次里的调用点、feature／属性条件及依赖等待
有 Binder 名字却没进入预期状态 服务的 onStart()、onBootPhase() 与内部状态检查
phase 日志停在某个值 SystemServiceManager.startBootPhase() 的当前回调、异常和等待对象
APEX 服务加载失败 startApexServices()、startServiceFromJar() 和 ApexManager 提供的信息
最终阶段、开机动画、用户广播不一致 AMS finishBooting() 及开机界面与完成篇

8.4 基础自测

1. new SystemServer().run() 创建了 system_server 进程吗？

展开参考答案

没有。进程在 Zygote 的 native fork 位置创建；这句话在子进程里构造 Java 对象并同步执行方法。回看第 2.1、3 章，区分进程、对象与线程。

2. 为什么 Runnable 和 ActivityThread.systemMain() 都不能直接当作“创建线程”的证据？

展开参考答案

Runnable 只是可执行代码的接口，这里调用的是 r.run()；ActivityThread.systemMain() 在当前进程中创建 ActivityThread 并执行 attach(true, 0)。判断新线程要找到实际线程启动或调度入口，不能从类型名推断。回看第 2.2、3.2 节。

3. 为什么查 service list 不能替代查询 SystemServiceManager？

展开参考答案

前者观察 Binder 名字表，后者保存 SystemService 生命周期实例。一个服务可以只发布本地接口，也可以用包装类接入生命周期；WMS 则有直接创建和发布路径。两张列表表达的关系不同。回看第 4.1、5.1、7.3 节。

4. onStart() 结束后，PowerManagerService 是否已经收到开机完成通知？

展开参考答案

不能这样判断。onStart() 负责发布 Binder 和内部接口等；500 才调用其 systemReady()，1000 才在相应分支设置 mBootCompleted 并更新状态。回看第 4.3、7.1 节。

8.5 场景推理

5. phase 100 的 DisplayManager 回调持续等待，PackageManager 能沿当前正常启动路径先初始化完吗？怎样验证？

展开参考答案

不能。startBootPhase() 同步调用回调；bootstrap 在这个调用返回后才继续 PackageManager 初始化。应检查默认逻辑显示与 VirtualDisplayAdapter 条件、等待超时异常，以及 phase 100 对应的 trace，而不只看 DisplayManager 已经创建。回看第 5.1～5.3、7.4 节。

6. A、B、C 顺序接收 phase 500，B 抛异常；dump 仍显示 500，能说 C 已执行吗？

展开参考答案

不能。当前阶段在遍历前就更新；B 的异常被包装后向外抛出，本次循环不会继续到 C。应结合异常中的服务类名和阶段定位，dump 的数字不是所有回调成功的证明。回看第 5.2、7.2 节。

7. APEX 阶段新启动的服务，把全部必要工作放在 if (phase == 500) 中，框架会自动补发吗？

展开参考答案

不会。本地 APEX 批次在 other 返回后执行，500、600 已经经过；startService() 只执行启动协议，没有历史阶段重放。需要按实际创建时机安排初始化，不能等待一个已经过去的通知。回看第 5.2、6.3 节。

8. 已看到 phase 600，为什么还不能断言 SystemUI 可见或所有应用已收到开机广播？

展开参考答案

600 表示服务可以启动／绑定第三方应用的阶段。本地实现随后还会执行 AMS 后续逻辑，返回后才请求 SystemUI，之后还有 APEX 服务等工作；请求启动与完成绘制又是两回事。phase 1000 和用户广播也有各自后续条件。应分别观察对应链路。回看第 6.2～6.4、7.3 节。
