Android 系统启动——概述

发表于 2025-09-12 | 分类于 Android ， StartUp
字数统计: 9.1k | 阅读时长 ≈ 34

1. 从按下电源，到能够打开一个应用

如果只背“init → Zygote → SystemServer → Launcher”，遇到真实问题时仍然很难判断：动画已经出现，为什么还没有桌面？system_server 有 PID，为什么某个服务查不到？应用进程创建成功，为什么 Activity 还没有执行？

这些问题来自同一个边界：进程出现、接口发布、业务准备完成、界面可用，并不是同一件事。 Android 启动是在逐步建立这些条件，同时保留一套常驻机制，用于之后启动应用、响应请求和处理进程死亡。

本文用一条贯穿场景建立全局认识：一台普通手机冷启动，系统建立显示与 framework 服务，启动 HOME；用户首次解锁后，从桌面打开一个尚无进程的示例笔记应用。笔记应用只用于讲解，没有在本次设备上安装或启动。

读完后应能回答：谁真正创建进程，谁只发请求；不同的“服务”由谁管理；启动顺序靠哪些条件推进；遇到卡点应去后续哪一篇查实现。这里保留决定边界的代码，不展开每个子系统的全部实现。

1.1 先看一张全局地图

图中绿线表示进程创建，橙色虚线表示 system_server 发给 Zygote 的应用创建请求。图是一张简化进程关系图，竖直位置不表示严格启动顺序。 例子选择 64 位主 Zygote；辅 Zygote、USAP 和专用 Zygote 是否存在，取决于产品 ABI、配置和实际用途。

沿这张图，可以把一次启动读成三条互相协作的线：

  • native 基础设施：init 建立属性与服务调度，启动 servicemanager、SurfaceFlinger 等进程。它们为后续服务发现与显示提供基础。
  • Java 运行环境与 framework：init 运行 app_process 建立 Zygote，Zygote 创建 system_server；SystemServer 在这个进程中组织系统服务，随后由 AMS/ATMS 发起应用组件启动。
  • 画面与完成状态：动画在独立进程里播放；HOME、锁屏和系统窗口陆续准备。WMS 协调显示交接，AMS 推进设备级完成，用户控制器继续处理按用户安排的广播。

这三条线有依赖和等待，也存在重叠。启动性能分析要找到“当前哪项工作阻塞了下一项条件”，不能把各进程的耗时简单相加。

2. 读启动源码，先把四种对象分开

2.1 进程、程序入口和 Java 对象

进程是 Linux 调度与资源隔离的容器，有 PID、UID、地址空间和线程。可执行文件是磁盘上的程序，例如 /system/bin/app_process64。入口函数或类决定进程开始执行哪些逻辑。一个进程内还可以创建许多 Java 服务对象。

例如 init 启动 app_process64，这个 native 程序建立 ART 后进入 ZygoteInit.main()，运行中的进程被命名为 Zygote。它 fork 出另一个进程后，子进程再进入 SystemServer.main()。ActivityManagerService、WindowManagerService 等对象随后都在 system_server 的地址空间内创建，不能因为名字带 Service 就各画一个 Linux 进程。

容易混用的名称 实际是什么 读源码时该问什么
zygote init service 名；也常用来泛指 Zygote 进程 rc 在什么条件下启动它？对应哪个 ABI？
app_process64 native 可执行文件 哪个参数让它进入 Zygote 模式？
SystemServer framework 启动编排类 当前代码在 system_server 的哪个线程执行？
system_server Linux 进程 谁 fork 它？当前 UID、PID、PPID 是什么？
ActivityThread 应用运行时入口与调度对象 当前方法运行在主线程还是 Binder 线程？

ActivityThread 的名字尤其容易误导：它不是通过 new ActivityThread() 就新建的一条 Java Thread。普通应用的主线程早已作为进程执行流存在，main() 再在这条线程上准备 Looper、创建对象并回连系统。

2.2 同一个“服务”，可能属于不同管理体系

管理者 管理的对象 代表入口
init rc 中声明的 service 进程 start、class_start、进程回收与重启
servicemanager 名称到 Binder 对象的映射与访问控制 addService、查询、通知
SystemServiceManager system_server 内的 SystemService 生命周期 onStart()、onBootPhase()
AMS 应用进程记录、组件运行与生命周期协调 进程创建请求、attach、Service/广播等调度

此外，Java android.os.ServiceManager 是访问 Binder 服务目录的工具类；LocalServices 保存同一进程内按 Java 类型索引的对象。它们都不能与独立的 servicemanager 进程混为一谈。

后面的 power 例子会贯穿这几层：init 没有为每个 PowerManagerService 对象单独创建进程；SystemServiceManager 管它的生命周期；它自行发布名为 power 的 Binder 接口；客户端经 servicemanager 找到接口后，向真正的服务宿主发起调用。

3. init：把一次引导变成长期运行的系统

3.1 从引导层进入 PID 1

更早的 Boot ROM、Bootloader 与内核负责把硬件从复位状态带到能运行用户空间程序的状态。Bootloader 的典型工作包含内存准备、启动镜像与完整性检查、选择启动目标并加载内核和 ramdisk；具体阶段与分区布局由设备决定，可参照 AOSP Bootloader 概述。

进入本文的普通 Android 启动路径后，内核将执行权交给用户空间的 /init，其主进程为 PID 1。本地 init 使用三段主入口：first stage 准备早期文件系统等条件，SELinux setup 准备安全策略与域切换，second stage 建立长期运行的服务管理机制。

FirstStageMain() 最后执行 /system/bin/init selinux_setup，SetupSelinux() 再执行 /system/bin/init second_stage。这两次使用的是 exec：在同一个进程里替换程序映像，成功后不会回到旧调用点，PID 不因此变成三个。与此同时，init 也可以另外创建 subcontext 等辅助进程；不能把“主路径保持 PID 1”误读为系统中只能有一个名字包含 init 的进程。

操作 是否创建新进程 启动中的例子
普通函数调用 否 SystemServer.run() 调服务启动方法
exec 否，替换当前进程的程序映像 init 自身切换阶段；service 子进程执行目标程序
fork / 相应 clone 路径 是，产生新的进程执行流 init 创建服务进程，Zygote 创建 Java 子进程
Handler post 否，把工作交给消息队列 应用绑定任务从 Binder 接收侧转到主线程

3.2 rc 是调度规则，不是一份从头执行到尾的脚本

second stage 通过 LoadBootScripts() 解析主 rc 与分区中的配置，分别保存 action 和 service：action 回答“什么事件下执行哪些命令”，service 回答“用什么程序、身份和选项运行一个服务”。

随后，QueueEventTrigger() 将事件放入队列，主循环在未被属性等待或同步 exec service 阻塞时，调用 ActionManager::ExecuteOneCommand() 消费工作。这意味着 trigger 入队与对应命令执行之间存在调度过程。

下面两处入口体现了不同依赖：

late-init action 会按本地顺序排队文件系统、数据准备等事件，再排入 zygote-start。但这不代表到了该事件就立刻获得 Zygote PID；上面还有属性等待和同步服务执行。start zygote 则查找已经解析的 service 定义，再由 Service::Start() 创建子进程、准备身份与 FD，并在子进程里执行目标文件。

init 把服务记为 running，只是生命周期状态，不能保证目标进程已经发布 Binder 或完成业务初始化。开机之后，这个事件循环还要处理属性变化、服务控制、子进程退出与重启，并不会在“启动完所有服务”后退出。

要进一步解释 action 排队、属性等待、class、disabled/oneshot 与回收机制，阅读 《init 进程》。

4. servicemanager：让跨进程接口能够按名字被找到

建立系统服务不仅需要进程，还需要一种发现接口的方法。客户端不知道 power 当前对应的 Binder 对象在哪里，服务端则需要把可供访问的引用登记出去。servicemanager 就管理这种命名关系。

本地入口选择 /dev/binder 作为默认驱动，将自身设为这个 Binder 域的 context manager，再通过 Looper 处理 Binder 工作：

context manager 为客户端提供一个约定的初始入口，通常以 handle 0 表达。之后服务端注册名称，客户端取得目标 Binder 引用；业务事务由 Binder 驱动送到目标服务进程，不需要 servicemanager 逐次转发业务调用。

它解决“怎样找到接口”，没有替目标服务完成所有初始化。即使 service check power 返回 found，电源服务也可能尚未执行后续阶段逻辑。反过来，进程存在而服务名不存在，也可能是尚未注册、注册失败或客户端没有访问条件，需要继续查对应证据。

这里讨论 /dev/binder 域；HIDL 的 hwservicemanager、vendor Binder 域及 AIDL HAL 的具体归属不能拼成一张无差别服务表。完整注册、查找、访问控制和懒启动流程见 《Servicemanager 进程》。

5. Zygote：把运行环境准备与应用身份分开

5.1 从 native 启动器进入 Java 父进程

init 依据 ro.zygote 选择相应 rc。以 64 位主 Zygote 为例，service 命令执行 /system/bin/app_process64，带上 --zygote、--start-system-server 和 socket 参数。主辅 Zygote 的含义是支持的 ABI 和启动职责，不是“主线程与子线程”。

frameworks/base/cmds/app_process/app_main.cpp 解析参数，创建 AppRuntime 并调用 AndroidRuntime::start()。后者在 frameworks/base/core/jni/AndroidRuntime.cpp 中创建虚拟机、注册 JNI，再经 JNI 调入 ZygoteInit.main()。到这一步，仍然是在 init 创建的那个进程里执行，并没有因 native 进入 Java 而再创建一个进程。

Zygote 预先加载一部分公共类、资源等内容，随后 fork 子进程。Copy-on-Write 让可共享且未被写入的页面暂时由父子共享；写入相关页面后才发生必要的复制。它减少重复准备的成本，但不是让所有应用共享同一份可随意修改的 Java 对象状态，也不是把所有应用业务代码都提前执行一遍。

5.2 fork 之后，同一份代码开始走父子分支

forkSystemServer() 内部通过 Zygote.forkSystemServer() 进入 native 创建路径。父分支返回 null，子分支关闭不该保留的服务 socket，再由 handleSystemServerProcess() 准备入口。这里的 Runnable 是可执行入口包装，直接 run() 不会自动再起一条线程。

子进程还要特化 UID/GID、能力、SELinux 身份、FD 与其他运行环境。普通应用不会因为继承了 Zygote 的运行时，就拥有 Zygote 的 root 身份。创建新地址空间与赋予正确身份是同一条启动链上的不同责任。

父 Zygote 留在请求循环中，为之后的应用创建、查询、预加载和池管理服务。开启且允许使用 USAP 时，可以提前 fork 出尚未绑定具体应用身份的进程，收到请求后再特化；它提前了 fork 的时间，并未让 AMS 变成应用的 fork 父进程。App Zygote、WebView Zygote 等专用分支按实际用途选择，细节见 《Zygote 进程》。

6. system_server：把对象创建变成分阶段可用的服务

6.1 SystemServer 编排服务，主线程最终进入长期循环

system_server 子进程经运行时入口包装进入 SystemServer.main()，再执行 run()。主线程先准备 Looper、native 服务库、系统 Context 与生命周期管理器，然后组织四批服务启动。

这四个方法是组织服务创建的批次，不是四个独立线程，也不是四个公开的就绪状态。boot phase 则是 SystemServiceManager 向当时已登记的服务发送的阶段回调，两者交错发生。

本地代码中，等待默认显示的 phase 100 就发生在 bootstrap 内；500、550、600 等阶段嵌在 other 的后半程，APEX 服务随后才启动。不能画成“四批服务全部创建后，再从 100 一路广播到 1000”。

6.2 用 power 看清“有对象”与“可查接口”

SystemServiceManager 负责把服务加入列表并调用 onStart()，但不会替每个服务自动发布 Binder。是否发布、以什么名称发布，由具体服务决定。PowerManagerService 就在自己的 onStart() 中发布两种不同接口：

蓝线表示这个具体服务在正常启动中的推进顺序，不是所有服务都必须采用的固定模板。图中 PID 为示意值，真实设备采样见第 9.1 节。服务对象始终在 system_server 内；发布接口没有把它搬到 servicemanager 进程。

这张图也给排障提供了四层问题：进程存在吗？接口已经发布吗？服务进入了需要的 ready 阶段吗？完成阶段是否已处理？即使某个 mSystemReady 字段为真，也要核对它在方法中的写入位置，不能忽略同一方法后面的工作或异常。

6.3 systemReady、600 和 1000，分别放在哪里

SystemServer 在 startOtherServices() 后段调用 AMS 的 systemReady(goingCallback, t)。AMS 准备自身状态后，直接执行这个 Runnable，再继续初始应用相关工作。这里的回调是同步方法调用，不是向另一个“AMS 进程”发消息。

阶段或入口 本地实现中的作用 不代表什么
phase 100 等待默认显示等早期依赖 所有窗口已绘制
phase 500 让已登记服务处理 system services ready 所有应用可任意运行
AMS 回调内的 phase 550 推进 ActivityManager ready 阶段 HOME 已经可见
同一回调内的 phase 600 在应用数据、必要的 WebView 准备等依赖之后，通知可启动第三方应用 用户已解锁、应用业务已完成
后续 AMS finishBooting() 的 phase 1000 处理 framework 完成阶段 所有用户的开机广播都处理完毕

这张表只列主线节点，省略其他阶段，不应据此推导所有服务都经历完全相同的回调历史。阶段回调本身也可能等待、抛异常或安排异步工作；一个服务的慢回调会影响后面的编排。

本地版本在 AMS systemReady() 返回后才请求启动 SystemUI；创建 SystemUI 所用 Context 与真正启动 SystemUI 组件是两件事。随后 APEX 批次完成、主线程进入 Looper，后面的窗口与完成事件继续在系统中推进。详细时序和服务登记规则见 《SystemServer 进程》。

7. 从 HOME 到笔记应用：系统怎样交付一个能运行组件的进程

7.1 AMS 发请求，Zygote 执行创建

AMS/ATMS 发起 HOME 后，会先解析组件、寻找任务和可用宿主进程。有合适进程就复用；没有时，AMS 的 ProcessList 才准备创建请求。用户之后打开笔记应用，也会复用这套按需创建机制，区别是触发的组件和相关策略。

普通路径经过 Process.start()、ZygoteProcess，按 ABI 连接相应 Zygote socket；特定用途可选择 App Zygote 或 WebView Zygote，USAP 也有独立准入条件。system_server 决定需要什么进程并追踪记录，Zygote 一侧实际产生或特化子进程。

不要把进程当成包名的同义词：一个包可以按配置使用多个进程，服务或 Provider 也可以在没有 Activity 界面的情况下拉起进程。我们的笔记例子仅假设主进程尚不存在，并要启动一个 Activity。

7.2 PID 返回之后，还有应用绑定与组件派发

普通应用入口是 ActivityThread.main()：

startSeq 用于关联一次具体的创建请求，不能仅凭 PID 猜测回连身份。Zygote 向系统返回 PID，与子进程执行 main() 并回连，可以并发推进；系统侧需要核对这两份信息，处理先后竞态。

阶段 谁做什么 笔记应用此时获得了什么
创建与特化 Zygote 一侧建立进程身份和运行环境 能执行应用运行时入口；尚不等于 Application 已初始化
attach ActivityThread 向 AMS 提供应用侧 Binder 接口和 startSeq 系统能关联 ProcessRecord 并联系该进程
bindApplication AMS 发绑定请求，应用 Binder 接收侧转交主线程 Handler 开始准备包、Context、Application、Provider 等
同步应用初始化 主线程安装适用的 Provider，执行 Instrumentation 与 Application 回调等 逐步形成应用运行环境；后台工作仍可能未结束
finishAttachApplication 应用回报绑定阶段完成，系统按配置继续派发 默认等待路径可接回此前待启动的组件
Activity 生命周期与绘制 客户端处理事务，创建与恢复 Activity，再推进窗口和帧 才逐步获得界面，而不是 fork 时立即显示

本地版本里，ActivityThread.handleBindApplication() 在相应条件下先安装 Provider，随后调用 Application.onCreate()；完成这段同步绑定及后续准备后，再调用 finishAttachApplication()。因此“Application 回调一定早于所有 Provider 初始化”也不成立。

AMS 的 mEnableWaitForFinishAttachApplication 默认是 true，可由 DeviceConfig 更新。开启时，后续组件派发要等完成回报；关闭时，系统侧较早进入继续处理分支，但应用侧的绑定与生命周期消息仍由自己的线程机制执行。这个开关改变等待点，不会让 Application 初始化自动换到 Binder 线程。

如果笔记应用在 Provider 初始化里做耗时工作，PID 可以早已存在，绑定与 Activity 派发却仍未完成。分析应从最早缺失的阶段证据往前追。请求身份、线程交接、Provider 顺序和 Activity 创建见 《App 进程》。

8. 启动画面与故障恢复，把整张地图接起来

8.1 动画、桌面和完成广播各有条件

SurfaceFlinger 和 bootanimation 是 init 管理的 native 进程。SurfaceFlinger 设置 ctl.start=bootanim，请求 init 启动动画；动画通过自己的 Surface 生产画面，所以不必等 Launcher 的 Activity 初始化完成。

应用启动侧促成收尾请求后，WMS 仍独立检查显示策略和应等待的窗口，再设置 service.bootanim.exit=1。正常路径还要等动画服务不再运行，并成功通知 SurfaceFlinger，才继续显示启用与输入协作。WMS 的 mDisplayEnabled 是自己的启动显示状态，不能理解为物理面板此时才第一次亮起。

AMS 的 finishBooting() 若先于显示完成通知到达，就记录待续办状态并返回。之后收到 bootAnimationComplete() 再继续：推进 phase 1000，设置设备级属性，再由 UserController 处理用户解锁与广播。这些状态共同组成后半程，但不能压缩成一个“桌面出现”时间戳。

因此在有锁屏凭据的冷启动场景里，设备完成属性已为 1、锁屏已经可见、前台用户 CE 存储却尚未解锁，是可能同时成立的状态。BOOT_COMPLETED 还有相应用户的条件；首次解锁与之后普通亮灭屏锁定也不能混同。窗口门槛、超时边界和广播流程详见 《开机界面与完成》。

8.2 启动后继续运行，死亡也沿这些边界传播

init、Zygote、servicemanager 和 system_server 在开机后都还有长期循环。init 管 service 生命周期，Zygote 接受后续创建请求，servicemanager 处理名字与引用管理，system_server 的主线程、Binder 线程与专用线程继续提供系统功能。

“创建者是谁”也决定了恢复链。system_server 不是 init rc 中一项独立的普通 service；本地 Zygote 的子进程回收逻辑明确检查 system_server 的死亡：

对应的典型恢复链是：system_server 终止，父 Zygote 检测到后退出，init 回收 Zygote service 并按配置重启，新 Zygote 再创建 system_server。它可以属于 Android runtime 的重启过程，不能只凭动画重新出现就断言 Linux 内核也重新启动了。

出问题的位置 优先追踪的责任方 不应直接推断
普通应用死亡 AMS 的进程与组件策略、应用崩溃记录 所有应用死亡都会重启整个系统
system_server 死亡 Zygote 子进程回收、init 的 Zygote service 恢复 init 直接执行一个名为 system_server 的 service
Zygote 反复退出 init service 状态、crash 计数、rc onrestart 每次退出都会触发整机重启
servicemanager 退出 其 rc 的重启和依赖 class 联动、Binder 发现错误 只重建进程就能保留所有旧引用的有效性

不要把所有子进程的命运都归因于“父进程死亡”：Linux 父子关系、进程组清理和 Android 服务联动是不同机制，需要各自的证据。本地 Zygote rc 的 critical window=${zygote.critical_window.minute:-off} 默认还可能关闭该保护；critical、重启节流与 onrestart 不能靠一个关键字概括。

10. 两个场景，检验是否真正读懂全局关系

10.1 “服务查得到，界面没出来”为什么没有矛盾

假设 power 已发布，笔记应用的 PID 也已出现，但其 Provider 在主线程初始化时长时间阻塞。第 6 章只能告诉我们电源接口已登记，不能替应用完成第 7 章的绑定工作。

此时继续搜 servicemanager 的业务转发没有帮助，因为它不负责把每一次应用启动事务串到界面。应检查应用是否已 attach、主线程停在哪里、是否完成 finishAttachApplication()，再查待派发 Activity 和窗口绘制。观察入口之所以这样排序，是因为它们分别对应前文的创建、绑定、组件和显示边界。

10.2 “又看到开机动画”为什么还需要确认重启范围

假设 system_server 因异常退出，Zygote 与相关运行时服务随后重建。显示侧再次进入启动画面，并不直接证明内核重启。

应对照系统 uptime、boot ID、相关进程 PID 的变化和 init/Zygote 日志，区分内核启动与 runtime 恢复；同一次采样的单个 PID 或一张屏幕照片不够。只读入口可使用 adb shell cat /proc/uptime、adb shell cat /proc/sys/kernel/random/boot_id，但本次未采集一组故障前后的对照数据。

恢复过程中，旧的 Binder 引用、应用进程和窗口还涉及各自的死亡通知与清理，不能用“父进程没了”概括全部后果。沿实际 service 配置与系统管理记录继续追踪，才能说明这台设备为什么恢复或持续重启。

12. 折叠自测

12.1 基础关系

问题 1：为什么 system_server 要求启动应用，应用的 PPID 却通常指向某个 Zygote？

展开参考答案

system_server 做创建决策并发送请求，真正 fork 的一方是相应 Zygote。USAP 只是把 fork 提前，应用请求与父子关系仍不是一回事。回看第 1.1、5.2、7.1 节。

问题 2：init 的三段入口意味着创建了三个 PID 1 吗？

展开参考答案

不是。主路径通过两次 exec 替换同一个进程的程序映像，PID 保持不变；另外创建的辅助进程需要独立分析。回看第 3.1 节。

问题 3：SystemServiceManager 和 servicemanager 各管理什么？发布 Binder 会把对象搬到注册中心吗？

展开参考答案

前者管理 system_server 内 SystemService 的生命周期，后者管理 Binder 名字与对象引用。发布接口后，服务实现仍留在原宿主进程。回看第 2.2、4、6.2 节。

问题 4：SystemServer 四批服务启动与 boot phase，是前后分开的两个完整阶段吗？

展开参考答案

不是，二者交错。phase 100 在 bootstrap 内，500～600 等节点位于 other 后段，APEX 批次随后才启动，1000 由后续 AMS 收尾推进。回看第 6.1、6.3 节；表中并未列全所有阶段。

12.2 场景推理

问题 5：笔记应用已有 PID，但 Provider 初始化很慢。下一步应优先看 servicemanager，还是应用主线程与绑定阶段？

展开参考答案

优先看后者。PID 只证明创建阶段，Provider 的同步初始化可以阻塞应用绑定以及默认等待路径上的后续组件派发。需要 attach、主线程堆栈、finishAttachApplication 和组件事务等证据。回看第 7.2、10.1 节。

问题 6：sys.boot_completed 为 1，但用户仍在首次解锁前，普通开机广播没到，能判定系统启动失败吗？

展开参考答案

不能。设备级完成与用户 CE 解锁、广播投递有不同条件。先确认目标用户状态及接收器条件，再查广播。回看第 8.1、9.3 节，并继续阅读第 7 篇。

问题 7：系统重新出现开机动画，怎样判断是内核重启还是运行时恢复？

展开参考答案

比较故障前后的 uptime、boot ID、进程身份与 init/Zygote 日志。system_server 死亡可以经 Zygote 退出触发 runtime 恢复；仅凭动画或一次 PID 快照不足以判断。回看第 8.2、10.2 节。本次没有实际触发这类故障实验。
