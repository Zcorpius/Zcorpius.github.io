Android 系统启动总览

本章是《Android 系统启动》的总导航。源码基线为当前工作区 Android 15 AOSP；它只建立端到端的进程、服务与权限边界，不替代后续章节的逐行分析。

1. 先建立正确的全局模型

从 Linux 内核切入 Android 用户空间之后，启动不是一条“init 依次启动所有应用”的直线，而是两条彼此协作的主线：

native 基础设施线：init 启动并监管 native daemon（含 servicemanager）；

Java 运行时线：init 启动 Zygote → Zygote 预加载并 fork system_server → system_server 建立系统服务 → AMS 请求 Zygote 创建应用进程。

完整因果链可以写成：

Boot ROM / Bootloader → Linux kernel → /init (PID 1) → rc action/service → servicemanager 与 Zygote → system_server → AMS/ATMS/PMS/WMS 等系统服务 → Zygote / USAP → 应用进程 ActivityThread → AMS bindApplication() → Application / Activity / Service / Provider。

其中 servicemanager 与 Zygote 并不是父子关系：二者通常都由 init 启动；system_server 虽然向 servicemanager 注册 Binder 服务，但它是 Zygote 的子进程；普通 Java app 也由 Zygote（或 USAP、App/WebView Zygote）创建，而不是由 system_server fork()。

2. 进程、父子关系与职责

对象 创建/监管者 核心职责 后续章节
init (PID 1) kernel 首次执行 /init rc action、属性、服务生命周期、SELinux、子进程回收 02-init进程
servicemanager init service /dev/binder 的 context manager；命名服务注册、查找和访问控制 05-Servicemanager进程
Zygote init service，经 app_process 建立 ART 预加载、Zygote socket、fork system_server / app / USAP 03-Zygote进程
system_server Zygote fork framework 系统服务宿主、SystemServer boot phase、AMS 04-SystemServer进程
app 进程 Zygote / USAP / 专用 Zygote 执行 ActivityThread，向 AMS attach，承载应用组件 06-App进程

常见但错误的两种画法：

  • 把所有 app 画成 system_server 的 Unix 子进程；实际上 app 的 fork 父进程是相应 Zygote。
  • 把 servicemanager 画在 system_server 内；它是独立 native 进程，system_server 只是其大客户与服务注册者之一。

3. 从 kernel 到 init：用户空间的起点

Boot ROM、Bootloader、verified boot、kernel 驱动初始化属于更靠前的引导层。kernel 切入用户空间时启动 /init；init 的首次执行从 FirstStageMain() 开始，随后 init 会 两次自 exec：一次进入 SELinux setup，一次进入 second stage。不要写成“init 被 kernel 执行三次”。

second stage 才承担属性服务、rc 导入和 action/service 调度等常驻职责。它不是按一个固定顺序“读完 init.rc 后依次启动所有服务”：属性触发器、class、disabled/oneshot、依赖条件和 service state 都会参与调度。

4. init 同时拉起 servicemanager 与 Zygote

4.1 servicemanager：先有 Binder 服务目录

init 启动 /system/bin/servicemanager。它将自己设为 /dev/binder 的 context manager，才使后续 system_server 和 app 能按名字发现 framework Binder 服务。

setThreadPoolMaxThreadCount(0) 并不表示不处理 Binder；Android 15 将 Binder FD 接到 Looper，由 polling 回调接收命令。servicemanager 仅管理服务的命名、权限、死亡与懒启动协作，拿到目标 Binder 后的业务事务不会再经它转发。

4.2 Zygote：通过 rc 启动的 Java 父进程

app_process64 不是 Zygote 逻辑本身；它是 native 启动器。它建立 ART/JNI 后反射进入 Java ZygoteInit.main()。

5. Zygote：把“昂贵初始化”变成可共享父进程

Zygote 在 fork 前预加载 framework 类、资源、图形相关对象等。fork 使用 Copy-on-Write：只读或未写入的页面可在父子间共享；子进程写入后才复制页面。因此预加载可降低冷启动耗时和内存总量，但也会把不适合共享的状态带入每一个 child，源码对此严格限制线程与 FD。

r != null 只会出现在刚 fork 出的子进程；父 Zygote 留在 socket 的 select/poll 循环中，持续处理 app 创建、USAP pool、预加载及查询命令。

6. system_server：第一个关键 Java 子进程

Zygote 以 system UID/GID、系统能力集和 com.android.server.SystemServer 为入口 fork system_server。native 子分支完成 FD 清理、UID/GID/capability、SELinux u:r:system_server:s0、seccomp、挂载与调度等 specialize；这不等价于简单的 setuid(1000)。

子进程经 zygoteInit()、RuntimeInit.applicationInit() 反射进入 SystemServer.main()。SystemServer.run() 先建立 system context、native server 库、主线程 Looper 和 SystemServiceManager，再按 bootstrap、core、other、APEX 四批启动服务，并推进 boot phase。

服务“构造并调用 onStart()”、服务“向 servicemanager 发布 Binder”、服务“在某 boot phase 真正就绪”是三件不同的事。AMS systemReady() 回调中推进 PHASE_ACTIVITY_MANAGER_READY，最终到 PHASE_THIRD_PARTY_APPS_CAN_START，才是三方代码可以实际运行的关键门槛。

7. App：由 AMS 决策，交给 Zygote 创建

当活动、服务、广播或 Provider 需要目标进程时，AMS 的 ProcessList 根据 HostingRecord 选择常规 Zygote、App Zygote 或 WebView Zygote；常规路径调用 Process.start()，不是 system_server 自己 fork。

ZygoteProcess 根据请求 ABI 选择 primary/secondary Zygote socket；USAP pool 可用并满足策略时会优先尝试 USAP，通信失败才回退普通 Zygote。无论走哪条路径，fork 后 child 都需经过 native specialize，不能继承 Zygote 的控制 socket 和 root 身份。

常规应用入口是 ActivityThread.main()。它准备应用主线程 Looper，并通过 attachApplication(mAppThread, startSeq) 回连 AMS；AMS 验证 ProcessRecord 后异步调用 bindApplication()。此时才开始 LoadedApk / Context / Provider / Instrumentation / Application.onCreate() 等应用初始化，而不是 fork 的瞬间。

8. 关键依赖关系：服务名、Binder 与启动顺序

可以用以下关系理解启动的“横向依赖”：

init 负责 创建/重启进程；
servicemanager 负责 让 Binder 服务按名称被发现；
system_server 负责 创建多数 framework 服务并协调其 boot phase；
AMS 负责 决定何时需要 app 进程并追踪其状态；
Zygote 负责 实际创建 Java 子进程。

一个 framework 服务典型会经历：

SystemServer / SystemServiceManager 创建 → onStart() → ServiceManager.addService(name, binder)（若它是对外 Binder 服务）→ 后续 onBootPhase() / systemReady() → 客户端通过 ServiceManager.getService(name) 获取 Binder。

不要把 service list 的结果误解为“SystemServiceManager 已启动的全部服务”：前者只显示 servicemanager 中已发布且可列出的 Binder 名称，后者的 Java 生命周期服务列表更大。

9. 失败传播与 runtime restart

失败对象 直接后果 典型恢复链
app 进程 进程死亡，Binder death 通知相关方 AMS 依据组件/重要性/崩溃策略决定是否再次启动
system_server Zygote 的 SIGCHLD 逻辑检测到 system_server PID 死亡 Zygote 自杀 → init 重启 Zygote → 重新 fork system_server
Zygote Java 父进程消失，子进程通常随之失去生命周期基础 init 根据 service 规则重启，并执行 rc onrestart 联动
servicemanager Binder 命名服务目录丢失 init 重启它，并按 rc 重启依赖服务 class

“system_server 死亡后 init 直接重启 system_server”是不准确的。init 监管的是 Zygote service；Zygote 特意将 system_server 死亡升级为自身退出，进而触发完整 runtime restart。critical 只是 init 服务的额外崩溃保护策略，并非每次死亡都立即重启整机。

10. 推荐阅读顺序与排障入口

  1. 02-init进程：先理解 rc、property、service state、SIGCHLD，才能解释进程为何被拉起或重启。
  2. 05-Servicemanager进程：理解 Binder 服务发现、SELinux add/find、lazy AIDL，避免把“服务不存在”误判为“进程没启动”。
  3. 03-Zygote进程：理解 app_process、ART 预加载、socket、普通 fork 与 USAP。
  4. 04-SystemServer进程：理解 system_server 特化、服务批次、boot phase 与 AMS systemReady()。
  5. 06-App进程：从 ProcessList 到 ActivityThread.bindApplication()，串起真正的应用进程启动。

排障时建议先定位故障落在哪个边界：

  • 进程根本没出现：看 init service/rc/property 与 Zygote socket；
  • 进程出现又退出：看 Zygote specialize、SELinux、崩溃栈和 SIGCHLD；
  • 服务找不到：看 servicemanager 注册、SELinux add/find、lazy service 声明；
  • app fork 后卡住：看 attachApplication、bindApplication、Provider、主线程初始化和启动超时。

Perfetto/atrace 中可按 StartServices、StartService *、OnBootPhase_*、Start proc:*、PostFork、ActivityThreadMain 串时间线；日志可从 init、servicemanager、Zygote、SystemServer、ActivityManager 五个 tag/进程边界分段查看。

11. 本章小结

  1. init 是用户空间 PID 1 和生命周期监管者；servicemanager、Zygote 多为 init 直接启动的同级服务。
  2. Zygote 是 Java 进程父体：预加载后 fork system_server 和 app；system_server 不是 init 直接启动的服务。
  3. servicemanager 管命名 Binder 服务，system_server 管 framework 服务生命周期，AMS 管 app 进程记录与调度；三者职责互补而不重叠。
  4. fork 只创建进程；app 还必须 attach AMS 并收到 bindApplication()，系统服务也还要经过 Binder 发布和 boot phase。
  5. 后续五章按上述边界展开，遇到启动/重启/服务发现问题应先判断它跨越了哪一个边界。
