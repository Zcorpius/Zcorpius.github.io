Android 系统启动——Zygote进程

发表于 2025-09-23 | 分类于 Android ， StartUp
字数统计: 11.1k | 阅读时长 ≈ 44

1. 从 init 启动一个程序，到 Android 拥有一套进程工厂

上一章中，init 已经根据 rc 配置启动了 app_process。但此时还没有回答一个更重要的问题：为什么 Android 不让每个应用都重新启动一次虚拟机，而要先运行一个长期存在的 Zygote？

Zygote 把许多进程都会使用的运行环境提前准备好：创建 ART、注册 framework JNI、加载常用类与资源。随后，它用 fork() 产生子进程，让子进程继承这些状态，再按目标进程的身份和隔离要求完成特化（specialization）。父 Zygote 则继续等待下一次请求。

本文沿着一个连续场景展开：设备开机，primary Zygote 创建 system_server；系统运行后，system_server 请求创建一个普通应用进程。读完后应能回答：

  • app_process、ART、ZygoteInit 和 ZygoteServer 分别是什么，哪些转换没有创建新进程？
  • 预加载能共享什么，为什么共享并不等于几个应用共用一份可变 Java 状态？
  • 一次创建请求由谁发出、谁接收，父子进程在哪里分开？
  • USAP 提前做了哪一步，收到 PID 又能证明什么？
  • system_server 死亡时，为什么恢复路径会回到 init？

本文衔接 《init 进程》，重点是 Zygote 的运行机制。系统服务的启动批次见 《SystemServer 进程》；应用 attach、bindApplication 和组件启动见 《App 进程》。WebView Zygote、App Zygote 和 wrapper 在这里仅交代边界，不展开各自完整流程。

1.2 先分清程序、运行时、入口与服务端

图中的蓝色实线表示同一进程内的调用或继续执行，橙色箭头表示创建新进程。跨过 C++ 与 Java 的边界，本身不会改变 PID。

名称 负责什么 容易混淆的边界
app_process native 可执行程序，解析参数并启动运行时 不是另一个名为 ART 的进程
AndroidRuntime / AppRuntime 在当前进程中创建 VM、注册 JNI、调用 Java 入口 JNI 调用不是 Binder，也不是 fork
ZygoteInit Java 启动入口，组织预加载、创建 system_server、进入服务循环 main() 与子进程使用的 zygoteInit() 是两个方法
ZygoteServer / ZygoteConnection 管理监听 socket、连接和命令处理 Java 对象，不是每个连接创建一个服务进程
ZygoteProcess 通常由 system_server 使用的客户端，选择 ABI 并发送创建请求 名字带 Process，但这个对象不等于 Zygote 进程

Zygote 是普通 Android 应用进程的重要祖先进程，也创建 system_server。它不是所有 Linux 进程的父进程：init 直接启动的 native daemon，以及 app_process 的普通工具模式，都不能套进同一条应用孵化路径。

2. init 交给 app_process 的，不只是一个类名

2.1 rc 决定二进制、启动角色和 socket

以本地 init.zygote64.rc 为例，关注可执行文件、两个不同含义的 zygote 参数，以及 socket 声明：

-Xzygote 是交给运行时的选项；--zygote 是 app_process 自身解析的模式选项；--start-system-server 则要求 Java 启动流程创建系统服务进程。它们不能因为都含有 zygote 或 start 就当作同一层参数。

init 在启动 service 时创建、绑定 socket，设置权限，并通过 ANDROID_SOCKET_<name> 环境变量传递 FD 数字；真正跨过 exec 保留下来的是子进程已继承的描述符。Zygote 用这个 FD 构造 LocalServerSocket 并开始监听，不会重新按路径创建和 bind 同一个 socket。

primary 与 32/64 位是两个维度。在本地配套配置中，名为 zygote 的 primary 负责创建 system_server；zygote_secondary 服务于另一组 ABI。Java 主入口按 socket 名识别 isPrimaryZygote，是否调用 forkSystemServer() 则由 startSystemServer 标记控制，正常 rc 将二者配套设置。

配置 primary secondary 本地配置中的预加载差别
zygote64 64 位 无 primary 默认立即预加载
zygote64_32 导入 init.zygote64.rc，为 64 位 app_process32 secondary 明确带 --enable-lazy-preload

因此，“primary 必定是 64 位”和“secondary 天生就延迟预加载”都不准确。前者取决于产品配置，后者取决于实际启动参数。本次设备的 ro.zygote=zygote64_32 与第二行对应。

2.3 AndroidRuntime 怎样从 native 进入 Java？

创建虚拟机和注册 JNI 是两件事。前者让当前进程能执行 Java；后者建立 framework Java native 方法与 C/C++ 实现之间的对应关系。

startVm() 把堆、GC、JIT、boot image 等属性与已有 VM 参数整理进 JavaVMInitArgs，最终调用 JNI_CreateJavaVM()。startReg() 遍历 gRegJNI 注册 framework native 方法，其中包含 Zygote 的 JNI 桥接。这里使用的“Dalvik”属性名是历史命名，不代表当前运行时仍是 Dalvik。

方法签名 ([Ljava/lang/String;)V 表示“参数为 String[]，返回值为 void”。JNI 要同时凭类、方法名和签名定位入口。由于参数数组第 0 项是类名，ZygoteInit.main() 从下标 1 开始解析自己的参数。

3. 先准备可继承的运行环境，再允许它产生孩子

3.1 ZygoteInit.main 的顺序约束

这里不是一串可以随意交换的初始化调用。预加载发生在常规首次 fork 之前；父子分流后，只有父进程留在长期服务循环中。

Zygote.initNativeState() 准备 Zygote 自身的 native 状态。后文的 ZygoteInit.nativeZygoteInit() 则用于 fork 后目标进程的初始化，并会接到 Binder 线程池。两者名字接近、执行身份不同，不能互换。

3.2 为什么要管住线程，而不只是保证 Java 代码没报错？

fork() 后，子进程保留调用 fork 的线程，其他线程不会一起复制成仍可运行的线程；但内存里的锁状态会被继承。如果一把锁由另一个线程持有，子进程可能留下“锁着，但原持有者已不存在”的状态。

因此有两层不同的约束：

  1. 启动预加载阶段用 startZygoteNoThreadCreation() 打开限制窗口。ART 的 Thread_nativeCreate() 检查该状态并抛出 InternalError，防止类初始化器随意启动 Java 线程。
  2. 真正执行每次 fork 前，还要经过 ZygoteHooks.preFork() 等运行时协调。不能因为预加载窗口已经关闭，就认为此后可以不处理线程状态直接 fork。

这不支持“Zygote 从出生到死亡永远只有一个线程”的结论。应记住的是：fork 的关键时刻需要满足运行时规定的线程状态；父、子在 fork 后还有各自的恢复工作。本地源码缺少 libcore 仓库，本文不补造 ZygoteHooks Java 层内部实现；这里的依据是已读取的 framework 调用点与 ART 接收端。

3.3 preload 具体准备了什么？

预加载的目标是准备多个后续进程可能复用的基础状态，而不是提前执行每个应用的 Application.onCreate()。本地实现的主要步骤如下；其中 HTTP 引擎预加载带开关与兼容性处理，不能把它遗漏后仍称为“完整固定顺序”。

preloadClasses() 打开设备上的 /system/etc/preloaded-classes，跳过空行与注释，执行 Class.forName(line, true, null)。true 要求执行类初始化，null 使用 boot class path 的加载器。因此预加载不只是把类名登记到一张表中，静态初始化器确实可能运行。

为限制这段初始化的权限，在真实 UID/GID 都为 root 时，代码暂时把 effective UID/GID 降到 9999，执行完成后恢复。它并没有永久把 Zygote 降权，否则后续无法按不同目标身份创建进程。预加载结束后的 GC/finalization 清理启动临时对象；ART 的 fork 前准备还会调整共享空间和方法状态。不能把共享收益全部归因于一次 GC。

本地 init.zygote64_32.rc 的 secondary 带延迟预加载参数，因此其 main() 跳过上述启动时预加载。ZygoteConnection.handlePreload() 处理 --preload-default，通过 lazyPreload() 完成一次预加载；客户端有 ZygoteProcess.preloadDefault()。延迟的是准备工作的时机，不是让应用永久缺少这套运行环境。

3.4 COW：共享物理页，不共享应用之间的写入

蓝色虚线表示虚拟页到物理页的映射；右图的橙色箭头表示写时复制。图只展示一个可按 COW 共享的页，不表示所有映射都使用同一种策略。

fork 后，父子已经拥有各自的虚拟地址空间。对于符合共享条件的私有页，可以先指向相同物理页；某一方写入时，再分离出副本。共享以页为单位，不以一个 Java 对象为单位。一个小对象的写入，也可能影响它所在的整页是否继续共享。

用一个教学例子推演：某预加载类的静态字段最初为 counter=0，随后从同一 Zygote 创建应用 A、B。A 在自己的进程中执行 counter++，不会让 B 或父 Zygote 自动看到 1。它们继承了初始状态，不共享此后的可变 Java 状态。static 的作用域不能跨进程解释。

预加载因此同时服务于启动时间和内存利用：子进程不用从零完成相同初始化，仍未修改的页有机会保持共享。但启动成本仍包括页表、特化、运行时恢复、应用代码加载等工作，也不能保证所有预加载内容都永久共享。Android 官方的内存管理说明同样把 Zygote fork 与共享公共代码、资源联系起来；本文具体初始化顺序以本地代码为准。

4. 第一个特殊孩子：system_server 从哪里来？

4.1 它不需要先向自己的父进程发送启动请求

普通应用创建通常由 system_server 发起；但 system_server 尚未存在时，显然无法由它发请求创建自己。因此 primary Zygote 在启动阶段内部构造参数，直接调用 forkSystemServer()。

这组参数指定 UID/GID 1000、补充组、经过当前 capability 集合过滤的权限、进程名 system_server 和入口 com.android.server.SystemServer。它不是 init rc 中另一个独立的 service system_server。

一次成功 fork 会产生两个执行分支：父进程收到大于 0 的子 PID，子进程收到 0。这个数值不是“当前进程的 PID 变成了 0”，只是 fork 的返回值。子进程从调用点继续走，普通路径不会再次从 app_process.main() 创建一台新 VM。

hasSecondZygote() 比较设备 ABI 总列表与当前 Zygote 的列表；需要另一 Zygote 时，子进程通过连接等待它可用。它不是固定睡眠若干秒，也不是证明所有系统服务都已就绪。

4.2 从专用参数到 SystemServer.main

Java 的 Zygote.forkSystemServer() 经过 JNI，先执行 ForkCommon()；只有 pid == 0 的子进程进入 SpecializeCommon(..., is_system_server=true, ...)。身份切换和运行时 post-fork 工作完成后，才返回 Java。

handleSystemServerProcess() 设置 umask、进程名，处理 system server classpath，并在普通无 wrapper 路径中取得专用 ClassLoader，调用 ZygoteInit.zygoteInit(...)。最终得到调用 SystemServer.main() 的 Runnable，返回第 3.1 节，由子进程执行 r.run()。

父 Zygote 此时拿到的是 null，继续运行 runSelectLoop()。所以从图上应画出“父进程继续服务”和“子进程进入系统服务”两个分支，不能画成父 Zygote 顺序调用完 SystemServer.main() 后再回来接收请求。

如果配置了 invoke-with，handleSystemServerProcess() 会走 WrapperInit.execApplication()，这属于显式 wrapper 分支。本文“继承 VM 后继续运行、不重新 exec”的主线限定于普通无 wrapper 情况。

5.1 客户端先选 ABI，再发送参数

ZygoteProcess.startViaZygote() 把 UID/GID、补充组、运行标记、target SDK、SELinux 的 seInfo、进程名、目录隔离信息和入口类等整理为参数列表。普通应用入口通常是 android.app.ActivityThread，不是 APK 中任意一个 Activity 的类名。

openZygoteSocketIfNeeded(abi) 先检查 primary 返回的 ABI 列表；不匹配时再尝试 secondary，仍不匹配就失败。它不是“64 位 system_server 只能创建 64 位 app”：客户端所在位数不替代目标 ABI 的选择。

协议本身很简单：第一行是参数数量，随后每行一个参数。参数中禁止换行、回车和 NUL，避免把一项拆成多项。普通通道的响应则是一个整数 PID 和一个 usingWrapper 布尔值：

5.2 服务端怎样区分新连接与新命令？

ZygoteServer 从 init 传来的 FD 构造监听 socket。它保留两类不同对象：一个监听入口，以及每次 accept 得到的会话连接。可 accept 表示有客户端连接到来；会话可读 才表示可以从已建立的连接读取命令。

runSelectLoop() 虽然名字含 select，当前实现使用 Os.poll()。USAP 未启用时主要监听服务 socket 和会话 socket；启用时还加入池 eventfd 和各 USAP 的报告 pipe。

这里由循环串行管理连接，不是“每 accept 一个连接就创建一条业务线程”。它既能处理进程创建，也能处理 ABI 查询、PID 查询、预加载、boot-completed、USAP 开关与 hidden API 配置等管理命令。

forkSimpleApps() 是符合条件的简单请求连续 fork 优化：无 wrapper、不是 child Zygote，并且 multipleOK 允许，才可能进入。multipleOK 又取决于 USAP 池未启用以及运行时允许相应线程暂停。native 端不能继续处理的命令会返回上层，而不是跳过管理命令。

5.5 native 边界：复制运行环境，整理继承资源

ForkCommon() 不是只包了一行 fork()。它在复制前建立 FD 检查基线，在子进程中处理不该继续持有的描述符：

应用不能继承后继续使用父 Zygote 的命令连接与监听入口。经典路径通过 fdsToClose 传入相关 FD，native 层将它们脱离；一些描述符位置会以 /dev/null 替换，避免 Java 对象随后 close 时误操作一个已被复用的 FD 数字。Java 层仍需关闭对应包装对象。

fds_to_ignore 也不是“随便保留任意资源”的许可，它表示从这次通用 FD 表检查中排除、由特定路径管理的描述符。其他文件依类型和规则重新打开或分离，避免不合适地共享文件偏移等状态。权限检查、FD 检查和子进程清理共同构成继承边界。

7. USAP 把 fork 提前，但没有跳过特化

7.1 从“收到请求才创建”改成“先准备一个尚未定身份的孩子”

USAP 是 Unspecialized App Process，意为尚未特化的应用进程。它已经是 Zygote fork 出来的独立进程，但尚未绑定到某个具体应用。

图中从“USAP 等待”到“应用入口”的括号表示同一个进程。特化不产生新的 PID，应用退出后也不会退回池里重新服务另一应用；池缺少成员时，Zygote 创建新的 USAP 补充。

ZygoteServer.fillUsapPool() 在 pre-fork hook 后调用 Zygote.forkUsap()。父进程保存 USAP PID 与报告 pipe 的读端；子进程关闭读端，进入 childMain(null, usapPoolSocket, writeFD)。子进程在这个方法里等待请求，并非必须先返回一个“等待任务”才开始 accept。

7.2 收到请求后，USAP 怎样变成应用？

与普通通道由父 Zygote 接收请求不同，USAP 自己在继承的池 socket 上 accept。下面保留决定执行身份与响应时机的部分：

这里存在一个很强的反例：USAP 已向 system_server 回写 PID 时，specializeAppProcess() 还没有执行完，甚至尚未开始调用。所以 PID 响应不承诺特化成功，更不承诺 Activity 已显示；后续失败仍要靠进程死亡、attach 超时等机制处理。

客户端的 USAP 分支只读取整数 PID，usingWrapper 固定为 false。它与普通 Zygote 通道“整数加布尔值”的响应格式不同，不能混用读取方式。

7.3 谁选 USAP，谁维护池？

是否尝试 USAP，由客户端 shouldAttemptUsapLaunch() 同时检查：池受支持、开关已启用、启动策略允许、参数被 USAP 支持。wrapper、特定管理请求等不能直接塞给一个等待特化的池成员。

zygoteSendArgsAndGetResult() 在 USAP 通信发生 IOException 时尝试普通 Zygote 通道。这是代码中明确捕获的回退条件，不能扩写成“USAP 任意失败都会自动回退”。例如返回负 PID 会抛出另外的启动失败异常。

池的控制与数据由父 Zygote 管理：

情况 通知路径 父 Zygote 的动作
USAP 被应用请求占用 该成员的报告 pipe 从池表移除对应成员，再按池策略补充
池成员意外退出 SIGCHLD handler 清理表项并写 eventfd poll 醒来后重新评估池数量
池不足 runSelectLoop() 的事件或超时 紧急补到 min，延迟补到 max，取决于当前状态
影响已继承状态的配置更新 对应管理命令处理逻辑 相关路径先清空旧池、更新状态，再补池

runSelectLoop() 把池 pipe/eventfd 放在后面的索引，倒序处理，以便先校正池状态再处理普通命令。这里的 pipe 用于成员报告，eventfd 用于池变化通知；它们不是传送应用启动参数的 socket。

本地 ZygoteConfig 的代码默认值为：开关 false，min 1、max 3、补充阈值 1、延迟 3000 ms，max 上限 100。getBool() / getInt() 优先读取非空的 persist.device_config.runtime_native.<name>，否则读取 dalvik.vm.<name>，最后才使用默认值。默认值、设备属性和运行中的池状态是三层证据，不能仅看常量就宣称某台设备一定有三个 USAP。

8. 一个孩子死亡，为什么有时只是回收，有时要重建系统？

普通应用死亡和 system_server 死亡的影响不同。Zygote 的 native SigChldHandler() 循环执行非阻塞 waitpid(-1, ..., WNOHANG)，回收已退出的直接子进程并报告退出信息；是否退出自己，还要检查死者是不是记录的 system_server PID。

父分支的 nativeForkSystemServer() 会保存 gSystemServerPid，并立即再做一次 waitpid(pid, ..., WNOHANG) 检查：孩子可能在 PID 尚未登记前就已经死亡，这一步用于覆盖该时间窗口。它解释了为什么不能只看 signal handler 就认为所有时序都已覆盖。

退出者 直接后果 不应推导出的结论
普通 app 子进程 回收并向系统报告，后续是否重建由更高层策略决定 不是每个 app 崩溃都会重启 Zygote
尚在池中的 USAP 清理池记录，必要时触发补池 不等于一个已绑定应用又退回池中
system_server primary Zygote 杀死自己，init 按 service 规则接手 不等于必定进行硬件重启

沿正常恢复分支推演：system_server 退出 → primary Zygote 退出 → init 回收并处理 zygote service → 满足重启条件时重新启动 app_process → 新 primary 创建新的 system_server。onrestart 还会影响 rc 中指定的其他服务；critical 的行为取决于属性和故障条件，可能进入更强的故障处理。因此不能把整个恢复承诺简化成“永远只重启两个进程”。

本地 zygote64_32 的 secondary 还配置了 onrestart restart zygote，需要分析双 Zygote 联动时应回到 rc 核对。本文只读设备状态，没有通过杀死 Zygote 或 system_server 验证恢复链。

10. 分层记忆与折叠自测

10.1 L0：先记住三种工作

Zygote 的工作可以压缩为三件事：提前准备可继承的运行环境；在合适的线程与资源状态下产生孩子；让孩子按目标身份继续运行，自己留下服务。

init 负责启动和监管 Zygote；system_server 通常决定何时需要普通应用进程；Zygote 落实创建和特化。不要把这三者的决策与执行职责揉成一个“启动应用”动作。

10.2 L1：应能自己展开的主干

  1. init rc → app_process → AndroidRuntime → ZygoteInit.main：只有 init 创建 service 子进程的地方产生了新的 PID，native/Java 切换仍在该进程中。
  2. preload → GC / ART 准备 → fork：预初始化提供可复用状态，COW 共享不传递应用之间的后续写入。
  3. forkSystemServer → 父返回 null / 子返回 Runnable：父留下接收请求，子进入 SystemServer.main。
  4. ZygoteProcess → socket → 校验 → fork / 特化 → Runnable：PID 响应不是入口完成或业务就绪通知。
  5. 提前 fork → USAP 等待 → 收请求 → 特化：创建时机提前，PID 不变，特化后不回池复用。
  6. system_server 死亡 → Zygote 自退 → init 监管：恢复政策仍受 rc 和故障条件约束。

10.3 L2：需要时去哪里查？

要找的细节 源码位置与符号
ABI、primary/secondary、lazy 参数 system/core/rootdir/init.zygote*.rc；app_main.cpp 的 ABI_LIST_PROPERTY

预加载与 system_server 参数 core/java/com/android/internal/os/ZygoteInit.java

USAP 与简单 fork 共用后半段 Zygote.java：forkUsap()、forkSimpleApps()、childMain()

10.4 基础自测

1. app_process 调入 ZygoteInit.main 时，是否又产生了一个 Java 进程？

展开参考答案

没有。AndroidRuntime 在当前进程中创建 VM，再经 JNI 调用 Java main；跨语言不等于跨进程。新进程来自 init 启动 service 时的创建动作，以及后续 Zygote 的 fork。回看第 1.2、2.3 节。

2. primary 是不是“64 位 Zygote”的别名？

展开参考答案

不是。primary 的启动角色与位数分开；本地 zygote32 也由 primary 创建 system_server。客户端按目标 ABI 匹配可用 Zygote，不能只看 system_server 自己的位数。回看第 2.1、5.1 节。

3. 为什么不能在预加载类的静态初始化器里随意开启工作线程？

展开参考答案

fork 只保留调用线程，其他线程留下的锁状态可能使子进程无法继续。预加载窗口在受检查的 Java 线程入口禁止创建线程，真正 fork 前还要通过运行时协调与单线程检查。它不意味着 Zygote 全生命周期永远只有一个线程。回看第 3.2 节。

4. 当前版本通过抛出 MethodAndArgsCaller 来进入应用 main 吗？

展开参考答案

不是。findStaticMain() 返回实现 Runnable 的对象，调用链返回到 ZygoteInit.main() 后执行 run()。附近旧注释仍可能谈到 throw，阅读时必须核对实际类型与控制流。回看第 6.1 节。

10.5 场景推理

5. A、B 都继承了预加载静态字段，A 把它从 0 改成 1，B 会跟着变化吗？

展开参考答案

不会因为共同来自 Zygote 就自动同步。父子地址空间独立，COW 保留初始共享页；写入导致相应页分离。要让 B 获知变化，需要另外的跨进程共享或通信机制。回看第 3.4 节；测试时应比较各进程各自读到的值，而不是只比较类名。

6. trace 中出现 Zygote.childMain，能断定用了 USAP 吗？

展开参考答案

不能。forkSimpleApps() 也进入它，只是传入已有 argBuffer，不会在池 socket 上等待。应结合是否预先存在 USAP、fork 相对请求的时间、实际分支或参数来源判断。回看第 5.4、7.2、9.3 节。

7. 客户端已经拿到 PID，随后一直没有首帧，是否说明 Zygote 的工作必定全部成功？

展开参考答案

不能。普通路径中父进程返回与子进程初始化独立；USAP 更是在调用特化之前就回写 PID。应继续区分特化、入口执行、attach、应用绑定与绘制，结合死亡或超时记录定位。回看第 5.1、6.2、7.2 节。

8. 设备属性显示 USAP 关闭，且没有 usap64 行，能证明某个现存应用历史上没用过 USAP 吗？

展开参考答案

不能。当前属性和进程快照只反映采样时刻；已特化的进程不再以 USAP 名称留在池中。需要启动前后的时间证据、配置记录或分支 trace。回看第 7.3、9.1、9.3 节。

9. 普通应用崩溃与 system_server 崩溃，为什么不能套用同一条恢复推理？

展开参考答案

退出回收路径会比较 pid == gSystemServerPid，只有该特殊孩子触发这里的 Zygote 自退。普通 app 的后续重建由上层决定；system_server 的恢复则回到 init 的 service 管理，而且还受 critical 等条件约束。回看第 8 节。

10. 能从设备读取到 zygote service 的 running 属性，却不能列出 socket 标签，这两件事矛盾吗？

展开参考答案

不矛盾。它们是不同对象和不同权限下的观察。running 反映 init 管理的服务状态；目录读取被拒绝只能说明当前 shell 无法完成检查，不能推出 socket 不存在，也不能把源码配置当作标签实测。回看第 2.1、9.1、9.2 节。
