Android 系统启动：Zygote 进程

基于当前工作区的 AOSP Android 15 源码，梳理 Zygote 从 init service 启动、进入 ART/Java，到 fork system_server 与应用进程的完整链路。

本文涉及代码：system/core/rootdir/init.zygote64.rc、frameworks/base/cmds/app_process/app_main.cpp、frameworks/base/core/jni/AndroidRuntime.cpp、frameworks/base/core/java/com/android/internal/os/ZygoteInit.java、ZygoteServer.java、ZygoteConnection.java、Zygote.java、frameworks/base/core/jni/com_android_internal_os_Zygote.cpp。

一、定位与全景

Zygote 是 Android 普通 Java 进程的共同父进程。它不是一个单纯的“fork 服务器”：启动后会创建 ART VM、注册 framework JNI、预加载常用类/资源/库，并维持一个 socket 服务端。随后 system_server 和大多数 app 进程从它 fork 出来，通过写时复制（COW）复用这些已初始化的内存页。

这带来两个直接收益：

  1. 避免每个新进程重复初始化 ART 与 framework 基础设施；
  2. fork 后先继承完整运行时，再由 native 层按目标进程收敛 UID/GID、capability、SELinux domain、mount namespace 与文件描述符。

主启动路径如下：

init → app_process[32|64] --zygote → AndroidRuntime.start(ZygoteInit) → 创建 ART VM/JNI → ZygoteInit.main() → preload + GC → 接管 init socket → primary zygote fork system_server → poll 命令 → 常规 fork 或 USAP 特化。

  • socket 由 init 在 Service::Start() 时创建，并通过 ANDROID_SOCKET_zygote、ANDROID_SOCKET_usap_pool_primary 环境变量传给子进程；Zygote 不会重新 bind 这两个 socket。

zygote service 崩溃后由 init 重启。更关键的是，若它 fork 的 system_server 死亡，Zygote 的 native SIGCHLD handler 会主动 SIGKILL 自己，交由 init 重新拉起整条链路。

三、ZygoteInit：预加载后再开始 fork

3.1 主流程与“禁止创建线程”窗口

预加载到首次 fork 之间需要尽量保持单线程。fork 复制的是调用线程，其余线程的锁状态却会留在内存中；若子进程继承了一个由“不存在的线程”持有的锁，极易死锁。startZygoteNoThreadCreation() 让这段窗口中新建 Java 线程直接失败；initNativeState() 完成后才解除限制并建立服务端。

gcAndFinalize() 在 fork 前回收启动期间产生的临时对象，尽量减少将来 COW 被写脏的页。

4.3 native fork 与特化

Java 调用最终落入 com_android_internal_os_Zygote.cpp：

ForkCommon() 在 fork 前执行的重点是：设置 SIGCHLD/SIGHUP 处理策略、临时阻塞 SIGCHLD、关闭日志 fd、建立或校验打开 fd 白名单、fork()；在子进程中立即关闭不应继承的描述符、清空 USAP 表、重新打开/分离其余 fd。

SpecializeCommon() 才把“zygote 子进程”变成目标进程，核心动作包括：

  • 创建目标 cgroup，设置 supplemental groups、rlimit、capability、scheduler policy；
  • 建立应用 mount namespace，按请求挂载外部存储并隔离 app/JIT profile 数据目录；
  • 设定 seccomp、setresgid()、setresuid()；
  • 依据 UID、seinfo、nice name 调用 selinux_android_setcontext()；
  • 清除子进程继承的 SIGCHLD handler，执行 ART post-fork hooks，并把 nice 降回默认值；
  • 对 system_server 额外执行 post-fork system-server hooks，并显式切至 u:r:system_server:s0。

因此，fork 的本质不是“复制后立即跑 app”：复制只保留运行时状态；安全身份、namespace 和 fd 继承边界由特化步骤决定。

5.3 USAP：预 fork，收到请求后再特化

USAP（Unspecialized App Process）是由 Zygote 预先 fork、尚未绑定到具体应用的进程：

USAP 流程：zygote --forkUsap()--> usap32/usap64 --accept(usap_pool)--> 校验参数 → specializeAppProcess()。

它减少了启动关键路径上的 fork 等待，但不会跳过特化：USAP 收到请求后仍调用 specializeAppProcess()，完成 UID/GID、SELinux、namespace 等收敛。

USAP 子进程改名、等待 usap_pool 连接、执行参数校验，然后才进行特化：

池功能默认关闭，ZygoteConfig.USAP_POOL_ENABLED_DEFAULT 为 false；大小、阈值和延迟可由 system property/DeviceConfig 配置。默认 max=3、min=1、refill threshold=1，但设备配置可覆盖，max 还有 100 的硬上限。启用池时 Zygote 先补满；池内进程退出时 native SIGCHLD handler 从 USAP 表删除该 pid，并写 eventfd 唤醒 poll loop 决定立即或延迟补池。

涉及全局 Zygote 状态的命令（例如 hidden API 配置变更）会先清空 USAP 池，更新状态后再补池，避免旧 USAP 继承过时配置。

六、总结

总结：init service → app_process（ART/JNI）→ ZygoteInit（preload/GC）→ ZygoteServer（init socket）→ primary fork system_server；父 Zygote 持续 poll，按请求走 forkAndSpecialize 或 USAP 特化。

记住以下结论：

  1. Zygote 的价值是“预初始化运行时 + COW 共享 + 统一特化”，而非单纯调用 fork()。
  2. init 创建并持有服务生命周期；Zygote 只接管传入的监听 socket。
  3. primary 的定义是“fork system_server”，与 32/64 位不是同一概念。
  4. 所有子进程都从同一个高权限运行时副本开始，但必须经 native SpecializeCommon() 才获得目标身份与隔离边界。
  5. system_server 死亡会使 Zygote 主动退出，最终由 init 恢复整条 Java 系统服务链路。
  6. USAP 是“先 fork、后特化”的延迟优化；它不会绕开安全检查或 specialization。
