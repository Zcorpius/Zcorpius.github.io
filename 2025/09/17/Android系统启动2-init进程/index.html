Android 系统启动——init进程

发表于 2025-09-17 | 分类于 Android ， StartUp
字数统计: 13.1k | 阅读时长 ≈ 51

1. 从一个问题开始：谁把 Zygote 启动起来？

内核已经进入用户空间，手机却还不能运行 Android 应用。此时需要有人准备文件系统和安全环境，读懂“哪些程序在什么条件下启动”，并在它们退出后继续照看整个系统。承担这些工作的就是 init，PID 为 1 的用户空间进程。

本文用一个场景串起这些职责：系统正常开机，init 读到 Zygote 的 service 定义，等启动条件满足后创建进程；如果这个 Zygote 之后异常退出，init 再决定怎样清理和重启它。 沿途重点回答：

  • init 为什么有 first stage、SELinux setup 和 second stage？这是不是三个进程？
  • rc 文件已经解析，为什么 Zygote 还没有启动？trigger 到底做了什么？
  • start zygote 怎样跨过进程边界？socket、身份和环境变量怎样交给子进程？
  • 属性变化、服务退出和重启请求怎样进入同一个调度循环？
  • 怎样通过设备上的 PID、属性和日志，区分“规则存在”“进程已启动”和“业务已就绪”？

上一章 《Android 系统启动——概述》 负责端到端导航。本章止于 init 把控制权交给 app_process，以及之后的服务监管；ART 初始化、Zygote 预加载和 system_server 的创建留给 《Zygote进程》。

1.2 先看两种完全不同的进程边界

图中的橙色箭头表示 exec 替换当前进程映像，绿色箭头表示 fork/clone 创建子进程。上方整个框始终是 PID 1；只有下方服务框是新进程。

fork() 成功后，父子进程各自继续执行：父进程得到子 PID，子进程得到返回值 0。execv() 则把调用者的代码、数据和用户态执行环境换成目标程序；成功时不会回到旧程序的下一行，PID 保持不变。先分清这两件事，后面的源码才不会被误读成“init 把自己变成了 Zygote”。

所谓“两阶段 init”指 first stage 和 second stage 的职责划分，中间穿插 SELinux setup。内核首次执行 /init，随后 init 自己 exec 两次，形成三段入口；不是内核创建三个 init，也不是 fork 三次。

2.2 First stage：先有最小环境，才有完整用户空间

刚进入用户空间时，不能假定 /dev 的节点、属性共享区、安全策略和普通服务都已经存在。First stage 先建立后续工作依赖的最小环境，再根据启动配置准备设备、加载模块、完成首阶段挂载。

准备工作 后续为什么需要它
挂载 /dev、/proc、/sys 等基础文件系统 访问设备节点、内核信息和 sysfs 接口
创建 /dev/kmsg 等必要节点 普通日志服务尚未启动，也能记录早期故障
加载所需内核模块、创建首阶段挂载设备 让承载后续系统文件的设备可访问
按首阶段挂载规则挂载必要分区 访问后续 init、SELinux 策略和系统运行所需文件

这里的“必要分区”取决于设备 fstab 和启动布局，不表示所有分区、所有用户数据都在 first stage 挂载完。Recovery 会走不同分支，不能用正常启动路径覆盖它。

2.3 SELinux setup：准备策略，并在 exec 边界切换域

SELinux 的 domain 是进程所处的安全域，文件 label 则描述被访问文件的安全类型。二者不能混用：对 init 文件执行 restorecon 是恢复文件标签，真正的进程域转换依赖随后执行该文件时的策略规则。

本地实现明确说明，这时希望从 kernel domain 转入 init domain。不要把“加载策略”“启用 enforcing”“进程域转换”合并成一个动作；例如仅调用 restorecon 并不等价于进程已经切换到 u:r:init:s0。

2.4 Second stage：准备长期运行的调度器

二阶段的任务从“让环境可用”转为“持续管理用户空间”。其关键先后关系是：

  1. PropertyInit() 建立属性区域，加载启动属性。之后解析 rc 中的 ${ro.zygote} 才有数据可用。
  2. 建立 epoll；注册子进程退出处理和用于唤醒主线程的 eventfd。
  3. StartPropertyService() 启动属性服务线程。
  4. 准备内建命令映射、挂载命名空间和 vendor 子上下文，然后 LoadBootScripts()。
  5. 把早期 action 和启动事件加入队列，进入常驻循环。

epoll 可以理解为“等一组文件描述符中谁有事发生”。signalfd 把指定信号转成可读 FD；eventfd 用来通知主线程“有新工作了”。这些 FD 不负责保存 rc 规则，规则和待执行内容在 init 自己的数据结构中。

init 的核心日志使用 KernelLogger 写入内核日志通道，不依赖稍后才由 init 启动的 logd。一阶段在基础节点准备后也会建立这一日志通道；上节自 exec 前的 dup2 是另一个标准流衔接动作。普通 service 的 stdout/stderr 是否进入 kmsg 还取决于其配置，不能据此推断所有守护进程日志都在 dmesg 中。

3. rc 解析：把文本变成规则和服务对象

3.1 三个问题，三类对象

假设我们只保留一条“到了 zygote-start 就启动 Zygote”的规则。init 至少需要记住三件事：什么时候执行、执行什么命令、命令指向哪个服务。因此 rc 中的 on 和 service 必须分开理解。

rc 内容 运行时承载者 保存什么 不代表什么
on <条件> 及其命令 Action，由 ActionManager 管理 触发条件、有顺序的命令列表、来源位置 条件此刻已经满足
service <名称> <程序> ... 及其选项 Service，由 ServiceList 管理 可执行文件、参数、身份、socket、class 和生命周期状态 已经存在一个同名进程
start、trigger、setprop 等 Command 与内建函数映射 命令参数和对应执行函数 一行 shell 脚本

Parser 识别 section，ActionParser 和 ServiceParser 在 section 完成时分别调用 AddAction()、AddService()。因此，rc 解析完成时可以只有一个 Service 对象，而完全没有对应的子进程。

rc 使用自己的语言：空白拆分参数，# 引入注释，反斜线可续行，${属性名} 可参与展开。on 和 service 开启 section，后续行分别是命令或选项。import 是解析期导入指令，不是等 action 执行时运行的普通命令。需要 shell 语法时，必须由配置显式执行 shell，不能默认 start 后面支持管道和命令替换。

3.3 读懂 Zygote 的 service 定义

这里有四种不同的名字：zygote 是 init 的服务标识；app_process64 是磁盘上的可执行文件；main 是分组名；/dev/socket/zygote 是通信端点。它们分别用于查找服务、exec 程序、批量控制和建立连接，不能互相代替。

常用选项也要和触发时机一起读：

选项 对行为的影响
class main 把服务加入 main 分组；未指定 class 时默认是 default
disabled class_start 不自动启动它；仍可显式 start
oneshot 普通退出后不自动重启；不表示“整个设备生命周期只能启动一次”
user / group 规定子进程的 UID、主 GID 和补充组
socket 规定 Unix socket 的名称、类型、权限与属主
onrestart 进入自动/请求重启处理路径时执行指定命令，具体位置见第 7 章
restart_period 从上次启动时刻计算下一次重启时间，默认周期 5 秒
critical 符合条件的反复异常退出可能升级为系统级故障处理

critical 这一行尤其不能只读关键词：${zygote.critical_window.minute:-off} 使用 off 作为缺省值；ServiceParser::ParseCritical() 读到 window=off 会直接返回，不设置 SVC_CRITICAL。存在这行配置，不等于所有设备都已启用 Zygote 的 critical 保护。

  • current_command_：当前 Action 执行到了第几条命令？

决定顺序的代码在 ExecuteOneCommand()，重点是第一个 while 的条件与最后的命令游标：

std::visit 是对 variant 中实际存储的类型做分发：同一个事件队列可以保存字符串事件、属性变化、内建 Action 指针，然后分别调用对应的 CheckEvent()。无需记住这一语法的所有细节，只需知道它没有把所有事件混成一种匹配规则。

一次事件出队时，匹配的 Action 按 actions_ 的已有顺序进入执行队列。每次调用推进一条命令，当前 Action 的所有命令完成后才换下一个；这一批 Action 全部完成后，才处理下一个事件。若事件没有匹配项，while 可以继续取后续事件，但不会因此多执行一条命令。

4.3 事件条件和属性条件不是同一种触发

可以把常见条件读成下面几种形式：

条件示例 在本地实现中的含义
on boot 当 boot 事件被消费并匹配时，把 Action 加入执行队列
on property:demo.ready=1 属性触发启用后的相关变化，或启动期全量属性扫描，可以使它匹配
on boot && property:demo.ready=1 只在 boot 事件匹配时检查 ready；boot 过去后 ready 才变为 1，不会补跑
on property:demo.a=1 && property:demo.b=1 相关属性变化时，同时检查组合条件；还参与启动期全量扫描

一个 Action 可以有一个事件条件和多个属性条件，通过 && 连接；不能写两个独立事件条件要求它们“先后都发生”。对于属性变化，CheckPropertyTriggers() 使用事件中携带的变化值检查该属性，其余属性读取检查时的当前值。

这也解释了为什么“条件曾经满足”不总等于“Action 将会执行”。事件与属性组合条件在事件被消费时匹配；它不是持续监听这个条件直到满足的等待器。匹配完成后，已排队的 Action 也不是每执行一条命令就重新检查全部触发条件。

启动早期已经存在的属性同样需要处理。queue_property_triggers_action() 会安排启用属性触发，再通过 QueueAllPropertyActions() 加入一次全量扫描。这样纯属性 Action 不必只等下一次写入；这不意味着所有带 boot 等事件名的规则都会被补触发。

因此，调试“为什么 Zygote 没有出现”时，不能只检查是否加载了 init.zygote64.rc。还要确认是否消费到 zygote-start，是否停在 odsign.verification.done，以及 update_verifier 是否已经结束。

两种等待不会让整个 init 进程停止处理所有事情：主循环仍有 epoll、退出回收、控制消息等路径，属性线程也仍可接收写请求；否则等待的属性和 exec 子进程退出根本没有机会解除等待。另一方面，普通内建命令本身也可能耗时，不能把“每轮一条”理解成固定时间片或实时调度保证。

Zygote 虽然属于 main class，这条启动路径使用的却是显式 start zygote。class_start main 通过 StartIfNotDisabled() 遍历该 class 的服务；显式 start 直接调用 Start()。Start() 对已经运行的普通服务会返回成功，而不是再 fork 一份，所以重复触达启动路径也不等价于产生重复 Zygote。

5.3 Service::Start()：父进程管理，子进程换程序

内建 do_start() 先用服务名在 ServiceList 查找对象，再调用 Service::Start()。开始前会检查可执行文件、SELinux 执行上下文等条件；需要命名空间创建标志时走 clone，普通路径走 fork。

父进程记录 PID，准备 cgroup 并通知子进程；子进程在 RunService() 中进入命名空间、准备环境、发布 FD，等待 cgroup 准备，再设置 task profiles、UID/GID、能力和安全上下文，最终通过 ExpandArgsAndExecv() 执行目标程序。

这是“fork 后父子进程协作”的具体例子：父分支的记录与资源控制，和子分支的权限收敛、exec，可能交错推进，不能画成两条互不相关的简单函数调用。

5.4 socket 怎样穿过 exec？

socket zygote stream 660 root system 使 init 在启动准备阶段创建 /dev/socket/zygote。fork 让子进程继承已经打开的文件描述符，而 RunService() 中的 Descriptor::Publish() 解决两个后续问题：新程序去哪里找这个 FD，以及 exec 会不会关闭它。

对于 Zygote，环境变量是 ANDROID_SOCKET_zygote。变量值是 FD 编号，不是 socket 路径，也不是把 socket 内容序列化进字符串。子进程通过这个编号接管继承的 socket；后续 listen/accept 和 Java 层包装属于 Zygote 的初始化过程。

把这条链连起来就是：rc 给出 socket 规格 → init 创建并绑定 → fork 继承 FD → 子进程清除 close-on-exec 标记并发布编号 → app_process/Zygote 接管。

5.5 running 到底证明了什么？

NotifyStateChange("running") 把监管状态发布为 init.svc.zygote=running。第一次进入 running 时，它还会尝试写入 ro.boottime.zygote，记录基于 boot clock 的启动时刻；该值不会在每次重启时覆盖更新。

观察结果 可以支持的结论 尚不能支持的结论
找到 rc 的 service zygote 存在可供解析的启动定义 规则已加载、事件已执行或进程已创建
init.svc.zygote=running init 已走到相应启动状态发布点 exec 后程序一定成功完成初始化、socket 已可接受请求
ps 中存在 Zygote PID 采样时这个进程存在 预加载、system_server 启动和桌面展示全部完成
sys.boot_completed=1 采样时系统发布了 boot completed 状态 此后所有后台任务均已结束，或所有硬件服务都可用

服务自身仍可能在启动后很快失败，因此取一次属性只能得到一个时间点的状态。业务就绪应结合目标服务的协议、专用就绪信号或后续可观察行为判断。

6. 属性服务：把写入请求接到 init 的调度机制

6.1 为什么读属性和写属性走不同的路？

Android property 是全局命名的键值状态。例如 ro.zygote 选择启动配置，init.svc.zygote 表达监管状态，odsign.verification.done 让某个启动等待解除。属性既是数据，也是跨组件协调的一种信号来源。

普通客户端通过属性区域读取允许访问的值，不需要每次向 init 发起 socket 请求。写入则要经属性服务，统一校验调用者身份、属性规则和 SELinux 权限。共享内存解决读路径的效率问题，受控写入口维护全局状态的权限和一致性。

PropertyInit() 在二阶段早期创建 /dev/__properties__，建立属性信息和共享区域，处理设备树、内核命令行与 bootconfig 中的启动信息，加载默认属性与派生属性。它早于 LoadBootScripts()，因此 rc 的属性展开有了基础。

6.2 属性服务线程和 init 主线程怎样分工？

图中的两列 init 都属于同一个 PID 1 进程。蓝色虚线表示跨线程入队；它没有表示“属性线程直接执行 rc Action”。队列画在主线程一侧，表示由主线程消费，不表示内存只能由这一线程访问。

本地 StartPropertyService() 创建 system 专用与全局两个 property socket，并分别启动服务线程；每个线程有自己的 epoll。还存在用于 init 与属性服务内部管理消息的 socketpair，例如加载持久属性的请求。普通属性变化在这里通过受锁保护的队列传递，并使用 eventfd 唤醒主循环，不是把每次变化塞进这条 socketpair。

ro.property_service.version=2 表达的是属性服务协议版本，不能用这个数字推出“必然有两个线程”。线程结构应以该分支的 StartThread() 调用为证据。

外部写请求的处理链是：接收 socket 连接 → 用 SO_PEERCRED 取得 UID/GID/PID → 读取协议、名称和值 → 获取调用者 SELinux context → 权限检查与分流。

CheckPermissions() 对普通属性依据 property context 检查 SELinux 写权限和声明的值类型；对 ctl.* 则检查控制动作与目标服务对应的权限。能连接 socket 不等于能写任意属性，UID 为 root 也不能代替 SELinux 的判断。

6.4 ctl.* 是控制通道，不是普通状态值

具备权限的客户端请求 ctl.start=zygote 时，SendControlMessage() 调用 QueueControlMessage()，把动作、服务名、调用者信息等加入单独的控制队列，并唤醒主线程。主线程在 HandleControlMessages() 中每轮最多取一条，经 HandleControlMessage() 查找服务，再走 Start()、Stop() 或 Restart()。

这条路径与 on property:某属性=某值 不同：它不先写一个名叫 ctl.start 的常驻属性，也不需要找到对应的 rc Action。因此应通过 init.svc.<服务名>、实际 PID 和日志观察结果，不应通过 getprop ctl.start 判断服务是否启动。

现代协议下，部分控制请求还会把应答 FD 交给主线程，在处理控制消息后回报结果；兼容路径存在差异。即便控制调用成功，仍不等价于第 5.5 节中的业务就绪。

7. Zygote 退出之后：先回收，再决定是否重启

7.1 为什么退出事件也要放进主循环？

内核在子进程退出时通知父进程。init 是它所启动的 service 的父进程，也可能回收被重新托管给它的孤儿进程。system_server 的直接父进程通常是 primary Zygote；不能把所有 Android 进程的退出画成“先由 init 处理”。

子进程退出后，如果父进程尚未读取退出状态，内核还会保留必要的进程记录，即常说的僵尸进程。回收负责领取退出状态、释放这份记录；重启则是创建新进程的策略，两者不是同一个动作。

本地实现先在单线程阶段屏蔽 SIGCHLD，再通过 signalfd 交给 epoll。这样退出处理可以和服务控制、状态更新放在主线程的正常执行上下文里，避免在普通异步信号处理器中展开复杂业务。

InstallSignalFdHandler() 注册这个 FD，同时使用 SA_NOCLDSTOP 避免把停止/继续当作所需的退出通知。fork 子进程的信号屏蔽则通过注册的 atfork 子处理函数解除。

7.3 Service::Reap() 决定进入 stopped 还是 restarting

回到 Zygote：它不是普通 oneshot，进入重启路径时会执行 rc 中的 onrestart，例如请求相关媒体服务重启。这些命令发生在 Reap() 阶段，不是等新 Zygote 已就绪后才执行的回调。

手动 stop 会让服务走停止路径；它不适合拿来模拟崩溃后自动拉起。反过来，一个没有 oneshot 的普通守护进程即使以退出码 0 结束，也仍可能按重启策略再次启动；“正常退出”主要还影响周期下限与故障计数，不自动等价于停止监管。

7.5 什么时候从“重启一个服务”升级为“处理系统故障”？

本地 Service::Reap() 对 critical 服务和满足条件的可更新组件进程维护崩溃计数。主要条件包括：不是显式 SVC_RESTART，上次退出不正常，并且处于配置的崩溃窗口内或尚未 boot completed。

源码判断是 ++crash_count_ > 4：进入该判断的计数超过 4，即第 5 次满足条件的异常退出，才走升级路径。不能被日志里的 “exited 4 times” 字样误导，也不能把它简化成“任意四次退出都会重启手机”。

  • critical 分支还检查 init.svc_debug.no_fatal.<name>，并以 persist.init.svc.last_fatal_reboot_epoch 做 24 小时节流，再设置 fatal 目标。
  • 非 critical、但符合可更新组件条件的进程，设置 sys.init.updatable_crashing* 通知后续处理，不在这一分支直接执行同样的整机重启。
  • Zygote 的 critical 是否启用、窗口多长，要回到第 3.3 节的属性展开；本次设备读到 zygote.critical_window.minute=10，这只是配置观察，未进行崩溃升级实验。

日常定位先确认普通的“退出 → 回收 → restarting → 新 PID”链路，再按日志与 flags 判断是否进入上述保护分支，避免一开始就把所有服务重启归因于 critical。

10. 分层记忆与折叠自测

10.1 L0：先记住完整角色

init 先准备自身运行环境，再把 rc 规则变成事件驱动的服务管理。它以 PID 1 长期存在，启动子进程、接收属性与控制请求、回收退出状态，并按策略决定下一步。

看到一个服务问题，先分清它停在哪一层：定义是否加载、触发条件是否满足、命令是否执行、进程是否创建、业务是否就绪、退出后是否允许重启。

10.4 基础自测

问题 1：first stage、SELinux setup 和 second stage 是三个不同 PID 吗？为什么 exec 后还能叫 init？

展开参考答案

正常主干中它们属于同一个 PID 1。两次 execv() 替换执行映像，并带不同参数回到 init 的 main() 分发；成功时不返回旧函数。程序文件和入口阶段变化不等于创建新进程。回看第 1.2、2.1 节。

问题 2：解析完成 service zygote ... 后，为什么 ps 中仍可能没有 Zygote？

展开参考答案

解析只注册 Service 对象。还需要到达启动路径，解除 wait_for_prop 和 exec service 等等待，并且 Start() 成功创建进程。应逐层检查事件、等待与启动错误，不能把对象存在等同于进程存在。回看第 3.1、5.2 节。

问题 3：class main、service 名 zygote、进程名 zygote64 和 app_process64 分别是什么？

展开参考答案

分别是批量控制分组、init 查找服务的标识、ps 观察到的进程名称、启动时 exec 的程序。Zygote 可以由 start zygote 显式启动；不用等看到某个 class_start main 才判断它能启动。回看第 3.3、5.2、9.1 节。

问题 4：ANDROID_SOCKET_zygote 保存什么？为什么只有继承环境变量还不够？

展开参考答案

它保存 FD 编号。socket 对象要先由 init 创建，再通过 fork 继承；还要清除这个 FD 的 FD_CLOEXEC，使它在 exec 后保留。只有字符串而没有有效描述符，无法凭空接管 socket。回看第 5.4 节。

10.5 场景推理

问题 5：Action A 第一条命令 trigger B，第二条命令修改状态。B 能先于 A 的第二条命令执行吗？

展开参考答案

在本文普通事件调度路径中不会。trigger B 只把事件加入队尾，当前已匹配 Action 队列尚未清空，消费者不取 B 来匹配。A 的后续命令先推进；如果还有同一事件匹配出的其他 Action，也要继续处理完。可对照第 4.2 节的教学示例预测最终属性值。

问题 6：on boot && property:demo.ready=1 在 boot 被匹配时 ready=0，稍后 ready 变为 1。该 Action 会补跑吗？

展开参考答案

不会仅因这次属性变化补跑。带事件名的 Action 要由对应事件匹配，CheckEvent(PropertyChange) 要求 event_trigger_ 为空。它也不同于 wait_for_prop 的显式等待。需要重新发生并匹配相应事件，或按实际需求改写触发设计。回看第 4.3、6.3 节。

问题 7：服务默认重启周期为 5 秒，启动 20 秒后崩溃。是否还要从崩溃时刻再等 5 秒？

展开参考答案

不是。到期点是上次启动时刻加有效周期，此时早已过去。回收设置 SVC_RESTARTING 后，后续主循环可尝试启动。实际仍受调度和启动处理影响，不能保证立即完成。要用启动、退出、新 PID 的日志时间线验证，不能只看第一次的 ro.boottime.<name>。回看第 7.4、9.2、9.3 节。

问题 8：init.svc.zygote=running，但请求 Zygote 失败，是否足以说明属性服务撒谎？

展开参考答案

不足以。running 是 init 发布的生命周期状态，不是 Zygote 业务就绪握手。程序可能尚未完成初始化，也可能在采样后退出。应同时观察实际 PID、Zygote 自身日志和通信状态，分清时间点与责任边界。回看第 5.5 节。

问题 9：init 正在 wait_for_prop，另一个服务恰好退出。回收是否也必须等这个属性满足？

展开参考答案

不需要。等待使主循环跳过普通 ExecuteOneCommand()，但 epoll 和退出回收仍可运行。exec service 退出还会通过回收解除同步 exec 等待。注意这不保证能抢占正在执行的耗时内建命令。回看第 5.2、7.3、8 章。

问题 10：设备读到 ro.boottime.init.first_stage 为空，同时没有读到早期日志，能否断言跳过了 first stage？

展开参考答案

不能。需要先确认属性与日志的访问条件、设备实现、缓冲区保留情况。本次只有当前进程关系与安全域的有效采样，启动时间线缺少实测材料。源码主干、预期输出和实际观测应分别标明。回看第 9.1、9.2 节。
