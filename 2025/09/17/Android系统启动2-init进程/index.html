1. 前言

Note

源码与摘录约定：本系列以本地 LineageOS 22.2 / Android 15 源码快照为准，具体实现可能与其他 AOSP 标签不同。代码块首行标出源码相对路径，保留函数或 rc section 及关键分支；... 表示省略的非关键实现，摘录不作为可独立编译的完整代码。

本文分析 init 从内核入口、两次自 exec，到 rc 调度、服务监管和属性服务的完整过程。

源码位置 本篇关注点

init 是 Linux 内核启动的第一个用户空间进程（PID 1），主要负责：

  1. 解析并执行 rc 文件，按 trigger 启动和管理系统服务；
  2. 监听子进程退出信号 SIGCHLD，负责回收与重启；
  3. 提供属性（property）服务；
  4. 监听 keychord、/proc/mounts 变化等事件，并协调关机、服务控制和重启。

本地 Android 15 的 init 采用两阶段架构。内核首次启动 /init 进入一阶段；随后同一进程映像再经两次 exec，依次进入 SELinux 设置阶段和二阶段主流程。因此，从“执行映像”看会经历三段，但 init 自己只调用两次 execv()；入口 main() 通过 argv 分发角色。

为什么要分两阶段?内核刚起来时 SELinux 策略尚未装载，/system 等分区也可能尚未挂载，init 此时运行在 kernel domain。一阶段（运行在 ramdisk 上）负责准备最小文件系统、加载内核模块、创建首阶段挂载所需设备节点并挂载早期分区；SELinux 阶段装载策略、设置 enforcing 状态，并对 /system/bin/init 执行 restorecon。随后 exec 才能触发到受限的 u:r:init:s0 域；二阶段再解析 rc、启动服务并进入事件循环。

3. 子进程退出与信号处理

init 是由它直接启动的 rc service 的父进程，也会接管失去父进程的孤儿进程。其直接子进程退出时，内核向 init 发送 SIGCHLD；init 回收退出状态，并对匹配的 service 决定是否重启。system_server 与普通应用的退出首先由对应父 Zygote 处理。AOSP 15中这部分代码在 sigchld_handler.cpp 与 service.cpp(SIGCHLD在任何线程创建之前被block并转成signalfd,信号变成了可读的fd)。

5.2 服务启动

Service::Start(service.cpp)的关键步骤:

子进程 Service::RunService() 依次进入 namespace、设置环境变量、发布已创建的描述符、写 PID 文件、等待父进程完成 cgroup 设置、应用 task profiles、设置身份与能力集，最后调用 ExpandArgsAndExecv()。这里的“发布 socket”是把 FD 编号放进 ANDROID_SOCKET_<name> 并允许它跨 exec 继承；socket 路径已在父进程准备阶段创建，不是把 FD 转成路径。

即init采用fork + exec创建服务:exec 替换的是 fork 后子进程中的 init 映像，PID 1 的父 init 继续调度；子进程从服务自己的 main() 开始运行。父进程收尾:记录pid与start_order_、创建进程组、NotifyStateChange("running")——写入 init.svc.zygote=running、ro.boottime.zygote=<ns>。

服务退出后由 Service::Reap(service.cpp)决策:

Important

回收与重启分开执行：Reap() 清理退出状态、执行 onrestart 并标记待重启；HandleProcessActions() 根据上次启动时间和 restart_period() 决定真正重启的时刻。

重启不在Reap里立即做,而是由主循环 HandleProcessActions()(init.cpp)按时间点拉起:

restart_period()(service.h)的规则：异常退出或超时被杀时，实际 period 取 max(配置值, 5s)；正常退出（状态码 0）则尊重 rc 配置。要注意，重启时刻是 time_started + restart_period()，不是“退出后再等待 5 秒”：服务若已经运行了 4.8 秒才异常退出，默认情况下约 0.2 秒后即可重启。

崩溃风暴保护:

critical 服务在配置的崩溃窗口内（默认 4 分钟，或 boot 完成前）异常退出超过 4 次时，即第 5 次满足条件的异常退出，才进入 fatal 处理；还要满足未启用 init.svc_debug.no_fatal.<name>，且距上次该类重启超过 24 小时等条件。critical window=off 等配置也会改变保护是否启用。另一个细节是：默认 mount namespace 中、包含可更新 APEX 组件的非 critical 服务发生同类崩溃风暴时，init 不直接重启整机，而是设置 sys.init.updatable_crashing* 属性通知 update_verifier/apexd。另外，setprop ctl.start/stop/restart <name> 控制消息经 HandleControlMessage(init.cpp)入队，主循环每轮消化一条。

6. 属性服务

属性(property)是 Android 全局的键值对系统：普通客户端通过共享内存高效只读访问；写入请求必须经 property socket 由 init 的属性服务处理。socket 文件权限并不等于写权限，最终还要通过 caller 的 SELinux 上下文、property context 与属性名规则校验。属性还承担“跨进程事件”的角色：on property:k=v 触发器、ctl.* 控制消息、wait_for_prop 同步都建立在它之上。

7. 记忆与检验

7.1 记忆总结

  • init 是用户空间第一个进程。内核首次启动 init 后，init 再自发 exec 两次，形成三个执行映像：一阶段（准备最小文件系统、挂载分区、创建设备、加载模块）→ SELinux 阶段（装载策略、设置 enforcing、切入 init 域）→ 二阶段（解析 rc、启动服务、进入主循环）；
  • rc 语法 = Action（on + trigger + commands）+ Service（可执行文件 + options）+ Import；trigger 分事件触发与属性触发。基础 rc 解析后，APEX 激活还可能带来额外 rc；
  • init用fork + exec创建服务(zygote即 execv("/system/bin/app_process64", ...)),socket由init预创建并经环境变量传递fd;
  • SIGCHLD 经 signalfd 转成 fd 事件，ReapAnyOutstandingChildren 收尸 → Service::Reap 执行 onrestart 并标记 RESTARTING → 主循环按“上次启动时刻 + restart_period”重启；异常退出的 period 下限为 5 秒；critical 服务第 5 次满足条件的异常退出才会触发整机重启；
  • 属性系统：普通客户端经共享内存只读，写入经 socket 由 init 的属性线程处理并受 SELinux/property context 管控；属性变化可触发 action，ctl.* 前缀转为服务控制消息；
  • 二阶段主循环(init.cpp)最终形态：在非同步等待状态下每轮最多执行一条 rc 命令，并消化一条 ctl 消息、处理到点服务重启；epoll 上挂着 SIGCHLD signalfd、唤醒 eventfd、keychord、/proc/mounts 监听等 fd，无事时无限期休眠。

7.2 自测问题

问题 回答要点
init 为什么有两个阶段，却会经过三段入口？ 首次执行 FirstStageMain，随后自 exec 进入 SELinux setup 和 SecondStageMain。
服务退出后会立即在 Reap 中 fork 吗？ 不会。Reap 设置重启状态，主循环到达重启时刻后调用 Start。
ctl.start 是普通的持久属性吗？ 不是。通过属性服务做权限校验后，转成 init 的服务控制消息。
