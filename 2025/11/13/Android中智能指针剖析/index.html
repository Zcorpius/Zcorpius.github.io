1. 前言

阅读 Binder 源码时，经常会遇到 sp<IBinder>、sp<IInterface> 和 wp<DeathRecipient>。要读懂它们，既要知道强弱引用怎样增减，也要知道指针指向哪个对象、对象之间怎样持有、最后一份引用消失时会调用谁。

本文以仓库中的 IResultReceiver 为例：先认识 sp/wp/RefBase 与 Binder 的继承关系，再跟随一次代理创建、接口转换、调用和释放，最后用 AudioTrack 的死亡通知与共享缓冲区操作验证这些规则。先给全程主线，后面每节展开一段：

这条链中的 BpResultReceiver 和 BpBinder 是两个本地对象。前者提供 send() 这样的业务方法，后者负责 handle 与事务传输；它们各有自己的引用计数，通过 BpRefBase 建立持有关系。

本文涉及的关键角色：

角色 一句话职责
sp<T> 管理一份强引用，复制时增加，析构或清空时归还。
wp<T> 管理一份弱引用，通过 promote() 尝试取得临时强引用。
RefBase / weakref_impl 保存计数和生命周期策略，在关键时刻调用派生类回调。

IInterface / BnInterface / BpInterface 将业务接口接入本地 Binder 或客户端代理。
BpRefBase 管理类型化代理对底层 IBinder 的强弱持有。

2. 对象关系与核心结构

2.1 sp 与 wp 保存了什么

sp<T> 是一个模板类。它把复制、移动、析构等 C++ 操作转成目标对象的引用计数操作；最关键的成员只有一个 T* m_ptr：

wp<T> 则保存两部分：目标对象地址 m_ptr，以及独立控制块的地址 m_refs：

这两个地址的职责不同：

  • m_ptr 记录对象地址。 在默认生命周期下，对象已经析构后，这个地址仍可能保留在 wp 中。
  • m_refs 保存提升所需的计数状态。 只要这份 wp 还在，控制块就仍然存在，可以用它判断是否允许取得强引用。
  • promote() 才是访问入口。 成功后返回一个 sp<T>，用这份局部强引用保证接下来的操作期间对象仍存活。

3.2.1 复制增加一份，移动转交原来的一份



复制构造使两个 sp 同时持有对象，因此调用 incStrong()；移动构造则把源 m_ptr 置空，原有计数不变，之后由目标 sp 负责归还。

这里的顺序有实际意义：先 otherPtr->incStrong()，再 oldPtr->decStrong()，最后替换 m_ptr。即使新旧指针指向同一个对象，也不会因为先减引用而把对象提前销毁。

  1. 增加计数需要原子性。 单纯增加一份持有，不需要把每次操作都变成完整的跨线程同步点。
    2. 

  2. 归还计数使用 release。 使用者必须先结束这份持有所覆盖的对象访问，再归还引用。
    3. 

  3. 最后释放配合 acquire fence。 通过计数上的原子读改写与释放序列，让前面持有者的访问在最终销毁之前完成。
    4. 



这里有一个前提：指针必须已经通过正确的跨线程发布方式交给使用者。原子引用计数不会自动修复同一个 sp 变量上的数据竞争，也不会替业务字段补锁；promote() 成功只能据此建立生命期保护。


5.6.3 回调也要先取得局部强引用
普通回调也有同样的“弱转强”操作：




processAudioBuffer() 在锁内提升 mCallback，失败就停止本次处理；成功后局部 callback 延长接收者生命。后续路径释放 mLock 再调用回调，保活由这份局部 sp 承担。


5.7 析构顺序：先停止使用者，再归还资源
AudioTrack 析构的资源清理主线是：




stopAndJoinCallbacks() 会请求回调线程退出、打断等待并等待线程结束，然后清掉线程对象的强引用。之后才解除死亡通知、清空 Binder 接口和共享内存。


这说明智能指针与线程退出协议需要配合：引用计数负责最后何时销毁，业务代码仍需安排何时停止继续访问资源。

7.2 基础自测
对象与继承
    

  1. sp、目标对象、weakref_impl 是同一块内存吗？
    
 
    答案展开


     不是。sp 实例保存目标地址，目标对象的 RefBase 在构造时单独分配控制块。默认模式最后强引用可先销毁对象，控制块继续被弱引用保留（2.1、2.2）。
    
 
    

    2. 

  2. BnResultReceiver 为什么只有一份 RefBase？
    
 
    答案展开


     两条路径分别经 IResultReceiver → IInterface 和 BBinder → IBinder，而 IInterface/IBinder 都虚继承 RefBase，所以完整对象共享同一个基类子对象（2.3）。
    
 
    

    3. 

  3. BpResultReceiver 是 BpBinder 的子类吗？
    
 
    答案展开


     不是。它继承 BpInterface<IResultReceiver>，后者组合业务接口和 BpRefBase；BpRefBase 持有另一个 IBinder，远端路径中通常是 BpBinder。两层对象各有计数（2.3、4.4）。
    
 
    4. 



引用与生命周期
    

  1. 有 2 份 sp 和 1 份显式 wp，为什么普通对象稳定弱计数是 3？
    
 
    答案展开


     每份强引用都会增加一份配套弱引用，因此弱计数包含 2 份隐含弱份额加 1 份显式弱份额。Binder 内部还可能增加其他临时引用，不能把实际现场计数直接套进这个简化模型（2.2、3.7、4.2）。
    
 
    

    2. 

  2. OBJECT_LIFETIME_WEAK 是否保证 promote() 成功？
    
 
    答案展开


     不保证。它允许对象由弱引用继续保留；从零恢复还要看 onIncStrongAttempted()。当前源码 BpBinder 的内核分支最终调用一个返回 INVALID_OPERATION 的实现，RPC 分支也返回失败（3.6、4.7）。
    
 
    

    3. 

  3. 复制一份 sp<IResultReceiver> 会再次给 mRemote 加强引用吗？
    
 
    答案展开


     普通复制增加上层类型化代理的计数。BpRefBase 已在构造时取得下层强引用，首次回调只标记责任转交；直到上层最后强引用归还，才向下执行 decStrong()（4.4、4.8）。
    
 
    4. 



回调与并发
    

  1. linkToDeath() 接受 sp<DeathRecipient>，为什么业务层仍要保存接收者？
    
 
    答案展开


     入参被保存到 Obituary 的 wp<DeathRecipient> 中。登记不会长期强持有接收者，业务层必须自行保活它，并持有被监听的 Binder（5.1、5.2）。
    
 
    

    2. 

  2. binderDied() 中应提升哪个弱引用？
    
 
    答案展开


     如果接收者弱回指一个仍可能存活的业务对象，可以像 DeathNotifier 一样提升该业务对象。参数 who 标识已死亡的 Binder，IBinder.h 明确要求不要尝试提升它。两者不能混淆（5.1、5.4）。
    
 
    

    3. 

  3. sp 使用原子计数，为什么 AudioTrack 还要在锁内复制成员？
    
 
    答案展开


     原子计数保证不同持有者增减计数的安全；同一个成员指针的替换与读取，以及相关对象状态的一致性仍需锁。取得局部强引用后，才可让生命期保护跨越解锁区间（5.5、5.6）。
    
 
    

    4. 

  4. releaseBuffer() 为什么先声明临时 sp，再声明锁？
    

    答案展开


    局部变量逆序析构，后声明的锁先释放，随后临时 sp 才归还引用。若这触发对象析构，析构发生在锁外（5.5.2）。
    

    5. 



7.3 场景追问
    

  1. 本地还持有 sp<IBinder>，为什么仍收到死亡通知？
    
 
    答案展开


     sp 管理本进程代理，无法阻止远端进程退出。死亡通知更新远端状态；本地 BpBinder 可以继续存在，用于处理清理与错误返回（5.1、5.3）。
    
 
    

    2. 

  2. BpResultReceiver 已无强引用，下层 BpBinder 仍被另一个变量强持有，此时上层 wp 是否还能提升？
    
 
    答案展开


     可以有成功路径。上层由弱引用保留，其 BpRefBase::onIncStrongAttempted() 尝试取得下层强引用；下层强计数为正时走 CAS 快路径，不需要进入不受支持的 handle 恢复慢路径。最终仍以实际并发状态和返回结果为准（4.7.3）。
    
 
    

    3. 

  3. 代理只剩弱引用，wp.promote() 失败，为什么同一 handle 再次到达时 ProcessState 仍可能返回强代理？
    
 
    答案展开


     缓存命中时，ProcessState 在专用锁协议中先取得临时弱引用，然后执行 force_set → forceIncStrong；旧强计数为 0 时调用 onFirstRef()。它没有走普通 wp 的慢路径。如果旧代理已不可用，则创建新的代理（4.1、4.7.2）。
    
 
    

    4. 

  4. 给 DeathNotifier 增加一个 sp<AudioTrack> 回指，为什么可能导致双方无法析构？
    
 
    答案展开


     AudioTrack 已经强持有 DeathNotifier，反向再强持有就构成环。外部引用离开后，两边计数仍被对方保留。保留 wp<AudioTrack> 并在回调时提升，可以让业务对象的外部生命期自然结束（5.4）。
