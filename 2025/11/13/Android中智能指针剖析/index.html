2. 对象关系与核心结构

2.1 sp 与 wp 保存了什么

2.1.1 用一个 C++ 对象代表一份持有责任

智能指针首先是一个普通 C++ 对象。RAII 把资源的取得与归还绑定到构造、析构等语言操作：复制一份持有，就增加引用；持有者离开作用域，就自动归还引用。实际资源可能由多个持有者共享，最终释放发生在协议规定的最后一次归还处。

因此，sp 自身可以是局部变量；它管理的 RefBase 目标对象则应独立分配在堆上。局部智能指针离开作用域，与目标对象当场析构，不是同一件事，还要看是否存在其他持有者及采用哪种生命周期策略。

sp<T> 是一个模板类。它把复制、移动、析构等 C++ 操作转成目标对象的引用计数操作；最关键的成员只有一个 T* m_ptr：

wp<T> 则保存两部分：目标对象地址 m_ptr，以及独立控制块的地址 m_refs：

这两个地址的职责不同：

  • m_ptr 记录对象地址。 在默认生命周期下，对象已经析构后，这个地址仍可能保留在 wp 中。
  • m_refs 保存提升所需的计数状态。 只要这份 wp 还在，控制块就仍然存在，可以用它判断是否允许取得强引用。
  • promote() 才是访问入口。 成功后返回一个 sp<T>，用这份局部强引用保证接下来的操作期间对象仍存活。

2.1.2 sp 依赖的是协议，不是固定的基类

sp<T> 的普通复制和析构只要求 T 提供 incStrong()、decStrong()；使用 fromExisting() 等额外接口时，还需要对应的 incStrongRequireStrong() 等协议。模板并没有规定 T 必须继承 RefBase。

这也解释了为什么同一个 sp 可以配合两套基础设施：

“侵入式”说的是目标类型参与引用协议，而不是所有计数一定直接内嵌在对象内。RefBase 把计数单独分配，仍然属于侵入式设计：目标对象知道并提供自己的引用管理接口。

这里有四个相互配合的设计：

  1. 从 0 开始计数。 LightRefBase 没有弱提升和首次引用回调，不需要区分“从未取得强引用”与“强引用已经归零”。
  2. 由原子减法选出最后一个持有者。 fetch_sub() 返回旧值；旧值为 1 的调用负责删除对象，不是先读计数再决定要不要减。
  3. 用 CRTP 恢复删除类型。 对于 class Foo : public LightRefBase<Foo>，this 被转换成 const Foo* 后删除，可以调用 Foo 的析构函数，不要求这个析构函数是虚函数。若继续把 Foo 当作其他派生对象的多态删除入口，则仍要另外保证正确的析构设计。
  4. 计数是 mutable。 incStrong/decStrong 可以是 const 方法，改变的是持有状态，不代表业务数据获得了线程安全保护。

基类析构函数的 protected 限制了外部直接经 LightRefBase<T>* 销毁对象，但不会自动禁止所有派生类的栈分配或手动删除。若派生类暴露公有构造、析构，语言层面仍可能允许这些操作；一旦由 sp 管理，就必须遵守同一套释放协议。

3.1.3 make() 还把所有权入口写清楚
传统的 sp<Foo> p = new Foo(...) 依赖裸指针隐式转换。它的问题不只是写法：如果一个对象由另一套机制管理，却意外传给接受 sp<Foo> 的函数，可能在调用边界建立一份临时强引用，并在调用返回时销毁对象。


危险情形是这个对象此前从未建立过强引用：临时 sp 取得首份强引用，随后归还最后一份。若原本已有一份正确的强持有，临时复制正常执行的是 1 → 2 → 1，不会仅因这一来一回就删除对象。

5.6.2 为什么增加用 relaxed，最后释放还需要 acquire
再看第 3.3、3.6 节的源码：增加引用一般使用 memory_order_relaxed；减少引用使用 memory_order_release；进入最后一次释放时，再执行 memory_order_acquire 的 fence。RefBase.cpp 开头专门解释了这组安排：


    

  1. 增加计数需要原子性。 单纯增加一份持有，不需要把每次操作都变成完整的跨线程同步点。
    2. 

  2. 归还计数使用 release。 使用者必须先结束这份持有所覆盖的对象访问，再归还引用。
    3. 

  3. 最后释放配合 acquire fence。 通过计数上的原子读改写与释放序列，让前面持有者的访问在最终销毁之前完成。
    4. 



这里有一个前提：指针必须已经通过正确的跨线程发布方式交给使用者。原子引用计数不会自动修复同一个 sp 变量上的数据竞争，也不会替业务字段补锁；promote() 成功只能据此建立生命期保护。


把这组内存序放进一个只有两份强引用的例子，更容易看出 acquire fence 在保护什么。假设线程 A、B 已通过正确同步各自取得一份独立 sp，且对业务字段的访问本身没有数据竞争：




A 的 release 减计数发布此前的访问；B 最后一次原子读改写读取前一次更新的计数值，随后 acquire fence 建立到最终销毁的同步关系。引用计数上的连续原子读改写还可以把更早的 release 纳入释放序列，所以不止“倒数第二个持有者”的访问受到覆盖。对应规则见 C++ 工作草案的原子操作与 acquire fence 同步条件。


这里没有要求 A、B 对每一次增加引用都执行 acquire，也没有把每次减少都写成 acq_rel。源码把 acquire 放在将执行最终释放的分支，减少其他归还路径的同步约束；具体性能收益仍取决于编译器与硬件，不能当作固定倍数的优化。


再区分两个容易混淆的结果：


    

  • 最终销毁的顺序有保证： 各持有者先结束本份引用覆盖的访问，再归还引用，析构线程通过协议完成同步。
    •

  3. 两个线程同时提升同一对象，是否只能一个成功？
    

    答案展开


    不是。一个线程把强计数从 1 加到 2 后，另一个可以重试并加到 3，各有一份强持有。真正需要避免的是默认模式下计数已归零后仍错误取得引用；WEAK 模式的慢路径还需要许可和可能的并发补偿（3.5.2、3.5.3）。
    

    

    4. 

  4. WEAK 对象提升失败，是否可以认为析构函数已经执行？
    

    答案展开


    不可以。对象可以仍由弱引用保留，只是 onIncStrongAttempted() 拒绝恢复。第 3.8 节 WEAK-DENY 用例会先输出提升失败，直到最后 wp 清空才析构（3.6～3.8）。
    

    

    5. 

  5. release() 返回裸指针后，再用 fromExisting() 包起来，是否自动完成了原引用的接管？
    

    答案展开


    没有。release() 留下一份尚未归还的强引用；fromExisting() 又增加一份，不能抵消原先的持有责任。普通持有转移应优先使用 sp 的移动操作（6.4.2）。

7.3 场景追问
    

  1. 本地还持有 sp<IBinder>，为什么仍收到死亡通知？
    
 
    答案展开


     sp 管理本进程代理，无法阻止远端进程退出。死亡通知更新远端状态；本地 BpBinder 可以继续存在，用于处理清理与错误返回（5.1、5.3）。
    
 
    

    2. 

  2. BpResultReceiver 已无强引用，下层 BpBinder 仍被另一个变量强持有，此时上层 wp 是否还能提升？
    
 
    答案展开


     可以有成功路径。上层由弱引用保留，其 BpRefBase::onIncStrongAttempted() 尝试取得下层强引用；下层强计数为正时走 CAS 快路径，不需要进入不受支持的 handle 恢复慢路径。最终仍以实际并发状态和返回结果为准（4.7.3）。
    
 
    

    3. 

  3. 代理只剩弱引用，wp.promote() 失败，为什么同一 handle 再次到达时 ProcessState 仍可能返回强代理？
    
 
    答案展开


     缓存命中时，ProcessState 在专用锁协议中先取得临时弱引用，然后执行 force_set → forceIncStrong；旧强计数为 0 时调用 onFirstRef()。它没有走普通 wp 的慢路径。如果旧代理已不可用，则创建新的代理（4.1、4.7.2）。
    
 
    

    4. 

  4. 给 DeathNotifier 增加一个 sp<AudioTrack> 回指，为什么可能导致双方无法析构？
    
 
    答案展开


     AudioTrack 已经强持有 DeathNotifier，反向再强持有就构成环。外部引用离开后，两边计数仍被对方保留。保留 wp<AudioTrack> 并在回调时提升，可以让业务对象的外部生命期自然结束（5.4）。
