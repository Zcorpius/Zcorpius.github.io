Android 架构学习之旅

发表于 2025-11-11 | 分类于 Android
字数统计: 4.7k | 阅读时长 ≈ 18

Important

这是一篇 Android 系统的全景导读，不试图替代每个子系统的源码分析。行文借鉴了 Gityuan 的 Android 架构开篇 所采用的“启动链路 + 进程视角 + 通信机制”学习方式；文中的结论、图和组织均重新梳理，并以现代 AOSP 的 Treble / Mainline / 稳定 AIDL 架构为准。具体代码、进程名和启动项会随 Android 版本与设备产品配置变化，阅读源码时必须以目标分支为准。

1. 先建立正确的全景图

Android 不是一组按目录叠放的库，而是一套由 Linux 内核调度、由多个进程共同运行、通过稳定接口协作的系统。

传统的“五层架构”仍然有用：Kernel、HAL、Native/ART、Framework、App。但如果只用这张静态图来学习，很容易回答不了三个真正关键的问题：

  1. 谁在什么时刻被创建？
  2. 这段代码运行在哪个进程、哪个分区、什么权限域中？
  3. 它跨越进程或语言边界时，用什么协议、由谁做权限校验？

因此本文采用两张互补的地图：

  • 静态地图回答“代码和接口在哪一层”；
  • 动态地图回答“开机和一次功能请求时，进程怎样协作”。

官方 AOSP 对现代软件栈的划分包含 App、Android Framework、系统服务、ART、HAL、Native 守护进程/库与 Kernel；这比早期只强调 Java Framework 与 Native 的视角多了分区、模块化和硬件接口稳定性的约束。AOSP Architecture overview

1.1 分层不是调用栈

下图中的层表示职责边界，而不是“上层只能调用相邻一层”。例如应用经 Binder 调用 system_server，而 system_server 可以通过稳定 AIDL 调用 Vendor 分区中的 HAL；真正的数据面还可能采用共享内存、DMA 或 socket。

flowchart TB
    App["App / 特权 App<br/>Android API、System API"] --> FW["Android Framework<br/>android.*、JNI 桥接"]
    FW --> SS["系统服务进程群<br/>system_server / SurfaceFlinger / audioserver ..."]
    FW --> ART["ART Runtime<br/>DEX、JIT/AOT、GC"]
    SS --> N["Native 库与守护进程<br/>libbinder、liblog、init、logd ..."]
    SS --> HAL["稳定 HAL 接口<br/>优先 Stable AIDL"]
    HAL --> Vendor["Vendor / ODM 实现<br/>厂商硬件服务"]
    N --> Kernel["Linux Kernel<br/>调度、内存、驱动、Binder Driver"]
    Vendor --> Kernel
区域 典型内容 最该记住的职责
App 第三方 App、系统 App、特权 App 面向 SDK/API 编程；每个应用默认拥有独立 UID 和进程边界
Framework android.app、android.view、android.media 等 API 实现 将应用请求转换为系统服务调用；一部分代码运行在 App 进程内
System services system_server 与 SurfaceFlinger、媒体、网络等原生服务 管理全局状态、策略和资源仲裁；通常通过 Binder 对外暴露能力
ART / Native ART、JNI、libbinder、libutils、init、logd 承接 Java/Native 执行与系统守护能力，直接使用 Linux 能力
HAL / Vendor Audio、Camera、Sensors、Power 等硬件实现 把稳定的系统接口落到具体 SoC 与设备硬件，隔离平台与厂商实现
Kernel 调度、内存、文件系统、Binder 驱动、设备驱动 提供进程隔离与硬件访问的最终基础

Tip

遇到一个类或一个进程时，先回答“它属于哪个分区、哪个进程、对谁提供服务”，再追踪函数调用。这样不会把 Java 包名、代码目录和运行时进程混为一谈。

1.2 现代 Android 相对旧图新增了什么

早期文章常把 HAL 描述为 Framework 通过 hw_module_t 动态加载的一组 .so。这个模型对理解历史代码有帮助，但已不足以描述现代设备：

  • Android 8 起，Treble 为 HAL 引入可独立演进的标准化接口和分区边界；
  • Android 11 起可使用稳定 AIDL 描述 HAL；
  • HIDL 仍可在存量设备上看到，但官方已将它标为弃用，新的 HAL 应优先使用 AIDL；
  • Mainline/APEX 让部分系统模块能够独立于整包系统映像演进，其服务也可携带自己的 init 配置。

也就是说，今天分析 Camera、Audio、Sensors 等问题时，不仅要看 frameworks/，还要看接口定义、VINTF 声明、vendor 实现与 SELinux 策略。HAL overview 与 AIDL for HALs 是更可靠的入口。

2. 用启动链路把静态层连起来

开机过程不是单线程脚本，而是一条不断扩展的进程树。下面的图省略了设备专有守护进程，保留理解 Framework 所需的主干。

flowchart TB
    ROM[Boot ROM] --> BL[Boot Loader]
    BL --> K[Linux Kernel]
    K --> INIT1["first-stage init<br/>挂载必要分区、准备 SELinux"]
    INIT1 --> INIT2["second-stage init<br/>解析 rc、属性与 service"]
    INIT2 --> SM["servicemanager<br/>Binder 名字服务"]
    INIT2 --> Native["Native 系统服务<br/>SurfaceFlinger / audioserver / logd ..."]
    INIT2 --> Z[zygote / zygote64]
    Z --> ART["启动 ART、预加载类和资源"]
    ART --> SS[fork system_server]
    SS --> Services["Bootstrap / Core / Other Services<br/>AMS、WMS、PMS、IMS ..."]
    Services --> Launch["AMS 请求 Zygote 创建应用进程"]
    Z --> App["App 进程<br/>ActivityThread.main"]
    App -->|Binder 请求| Services
    Services -->|Binder 回调| App

2.1 Boot ROM、Boot Loader 与 Kernel：把“系统”带到用户空间门口

  1. 芯片固化的 Boot ROM 运行最初代码，并验证/加载下一阶段；
  2. Boot Loader 初始化足以启动内核的硬件环境，并加载 Kernel、ramdisk 等启动镜像内容；
  3. Kernel 建立调度、内存管理、中断、驱动与 Binder 驱动，随后创建用户空间的第一个进程：init（PID 1）。

这一阶段属于设备启动链路，具体分区、验证链和厂商实现差异很大。学习 Framework 时不必陷入 Boot Loader 细节，但应记住：Java 世界的一切，都是 Kernel 和 init 创建的用户空间进程。

2.2 init：不是一个 init.rc，而是一套服务编排器

init 是用户空间的 1 号进程，也是系统服务的直接或间接祖先。现代 Android 把服务定义分散在对应分区的 etc/init/*.rc 中，而不是维护一个巨大的单体 init.rc：

  • /system/etc/init/：核心系统服务；
  • /vendor/etc/init/：SoC 厂商服务；
  • /odm/etc/init/：设备厂商服务；
  • /apex/*/etc/*rc：随 Mainline/APEX 模块携带的服务定义。

init 负责解析 action、service、property trigger 与 import；再根据 class、依赖、属性和重启策略拉起进程。不要把“某服务由 init 启动”误解成“它和其他服务没有依赖”：例如 servicemanager 必须尽早可用，Zygote 之后才可以孵化 system_server，而许多服务还会等待系统属性或分区就绪。Android Init Language

2.3 ServiceManager：Binder 世界的名字服务

Binder 驱动只能识别对象和句柄，业务代码却需要用诸如 activity、window、package 这样的名字找到服务。servicemanager 解决的正是“名字 → Binder 服务”的注册与查询问题。

典型时序是：服务端将 Binder 实体注册到名字服务，客户端查询后拿到代理对象，之后双方的业务事务经 Binder 驱动直接完成；名字服务不参与每一笔业务数据转发。

sequenceDiagram
    participant Server as 系统服务 / Native 服务
    participant SM as servicemanager
    participant Client as 客户端进程
    participant Driver as Binder Driver

    Server->>Driver: 创建 Binder 实体
    Server->>SM: addService(name, binder)
    Client->>SM: getService(name)
    SM-->>Client: 返回 Binder 引用/代理
    Client->>Driver: transact()
    Driver->>Server: 分发事务
    Server-->>Client: reply / oneway 回调

完整的启动、注册、查询与驱动路径可继续阅读：

  • Binder 启动：从 Zygote 与 Binder 线程池切入；
  • servicemanager 启动：init 配置、上下文管理者与事件循环；
  • servicemanager 获取：应用/Framework 如何取得代理；
  • setService 注册服务 与 getService 获取服务：从 API 到 Native 的完整链路。

Note

历史资料中经常同时出现 servicemanager、hwservicemanager 和 vndservicemanager。阅读时要先确认接口是旧 HIDL 还是 AIDL、服务位于 system 还是 vendor 侧，再决定应追踪哪个名字服务；不要把它们粗暴地当作完全等价的三个进程。新 HAL 的首选路径是稳定 AIDL，而不是继续以 HIDL 为起点。

2.4 Zygote：预加载一次，再 fork 多次

init 启动 Zygote 后，Zygote 通过 app_process 进入 ART 与 ZygoteInit：

  1. 创建 ART 运行环境；
  2. 注册 Unix Domain Socket，等待创建进程的请求；
  3. 预加载常用类、资源、库与 dex cache；
  4. 先 fork 出 system_server；
  5. 之后继续接受 AMS 等发来的创建应用进程请求。

fork 的价值在于 Copy-on-Write：子进程初始共享 Zygote 已准备好的内存页，只有写入时才复制，从而降低冷启动的准备成本。它不是“所有 Android 进程的父亲”这种绝对结论——Native 守护进程通常由 init 直接启动，某些命令行工具也可直接通过 app_process 运行；但常规 Java App 与 system_server 的确由 Zygote 孵化。

从源码角度，重点观察三个动作：preload()、startSystemServer() 和 Zygote socket 的 select loop；后者接到请求后才真正 fork 新应用。ZygoteInit

2.5 system_server：Java Framework 的服务容器，而非“整个 Framework”

system_server 是 Zygote 的首个关键子进程。它运行 com.android.server.SystemServer，按启动阶段装载 Bootstrap、Core 和 Other Services，例如：

  • AMS/ATMS：组件、任务与进程生命周期；
  • WMS：窗口、焦点、层级与显示协作；
  • PMS：包扫描、组件解析、权限与安装状态；
  • IMS：输入系统的 Java 侧管理入口；
  • PowerManagerService、DisplayManagerService、BatteryService 等全局策略服务。

很多 API 表面上是普通 Java 方法，实质是 App 进程中的 Framework 客户端通过 Binder 进入 system_server。但图形、音频等能力并不都“塞在 system_server 内”：SurfaceFlinger、audioserver、cameraserver 等具有 Native 服务进程和自己的线程模型。分析问题时应先用 ps、dumpsys 和 trace 确认边界。

3. 通信机制：先分清跨进程与跨线程

Android 的模块之所以可以拆成许多进程，是因为它有清晰的通信边界。最常见的误解是把 Handler 也视为 IPC，或者以为 Binder 是唯一的跨进程方案。

机制 边界 Android 中的典型位置 关键认识
Binder / AIDL 跨进程 App ↔ system_server；Framework ↔ Native 服务；系统 ↔ HAL 带身份信息、对象引用和权限校验，是系统服务的主干
Unix Domain Socket 跨进程 Zygote 进程孵化协议、部分守护进程控制面 协议直观，适合连接/命令模型；不等于 Binder 的替代品
共享内存 / FMQ 跨进程数据面 音频、图形、部分 HAL 的高吞吐路径 常用 Binder 建立控制关系，再用共享缓冲承载大数据
Handler / Looper 同进程、跨线程 App 主线程、system_server 服务线程 是消息调度模型，不是跨进程机制；底层等待通常会落到 native Looper/epoll
信号、pipe、eventfd、epoll 内核事件与线程协作 init、servicemanager、EventHub、Looper 是更底层的 Linux 工具，不应和 Binder 的对象模型混淆

3.1 Binder：控制面与身份边界

一笔同步 Binder 调用中，客户端线程向驱动提交事务；驱动把事务交给目标进程的 Binder 线程；服务端处理并返回 reply。内核记录调用方 UID/PID，服务端可据此做权限检查，必要时通过 clearCallingIdentity() 切换为服务自身身份执行内部操作。

Binder 很适合控制面与小对象传递，但不应拿它连续搬运大块媒体数据。AudioTrack、图形 Buffer 等场景会用 Binder 建链、用共享内存/BufferQueue 等路径传输数据。

3.2 Socket：Zygote 的控制通道

Zygote 的 socket 并不是“应用之间任意通信”的公共通道。它承载受控的进程创建协议：AMS 等系统侧组件请求 Zygote 按参数 fork/专用化子进程。Zygote 通过 select loop 等待连接与命令，因此分析应用进程创建时必须同时看 AMS 与 Zygote，而非只在某一侧找 fork()。

3.3 Handler：线程把任务交回所属 Looper

Handler 的 MessageQueue 属于一个进程地址空间；线程之间共享 Handler 对象和堆内存，因此能把工作投递给拥有该 Looper 的线程。最典型的是后台线程投递消息给 UI 线程。跨进程时，双方并不共享这份内存，必须先通过 Binder、socket 等 IPC 抵达目标进程，再由其内部 Handler 切换线程。

Handler → MessageQueue → native Looper → epoll 是理解“Java 消息循环如何等到 fd 事件”的一条纵向线；相关底座见 Android 中的 I/O 复用。

4. 以一个真实请求穿过全栈

下面用“用户触摸屏幕后，窗口收到事件”把架构从静态词汇变成运行时协作。细节会随版本变化，但进程边界和职责分工稳定：

sequenceDiagram
    participant Driver as 触摸驱动
    participant EH as EventHub / InputReader
    participant ID as InputDispatcher
    participant WMS as WMS / IMS
    participant App as 目标 App 进程
    participant UI as App 主线程

    Driver->>EH: /dev/input 事件
    EH->>ID: 规范化后的 RawEvent / Notify
    ID->>WMS: 查询焦点、窗口与策略
    WMS-->>ID: 目标窗口 / 拦截结果
    ID->>App: Binder 输入通道事务
    App->>UI: 入队到应用 Looper
    UI-->>App: View 分发与界面更新

这个案例同时揭示了四件事：

  1. 硬件事件从 Kernel 的字符设备进入用户空间；
  2. InputReader 与 InputDispatcher 是 native 输入流水线，不等于 App 的 onTouchEvent；
  3. WMS 参与焦点、窗口与策略判断；
  4. 最后一次跨进程后，事件仍要回到目标 App 的主线程完成 View 分发。

对应的深入阅读顺序是：Input 系统框架 → Input 构造流程 → Input 启动流程。

5. 阅读源码时的现代边界

5.1 system、vendor、odm 与 APEX

目录路径不只是工程组织：它往往意味着发布与兼容性边界。

  • system / system_ext / product：平台与产品侧组件；
  • vendor / odm：SoC 与设备厂商实现，须遵守兼容性约束；
  • APEX：可模块化更新的系统组件，可能提供库、服务与 init rc。

所以同样是一个 C++ 服务，不能只看“它链接了 libbinder”。还要问它在哪个分区：跨分区的稳定接口使用 AIDL 时，vendor 侧通常应使用 NDK/Rust/Java 后端，而不是依赖不稳定的 C++ libbinder ABI。Stable AIDL 的构建约束

5.2 权限不只发生在 API 层

一个调用能否成功，通常经过多层约束：

因此“反射拿到隐藏 API”不意味着一定能访问硬件服务；同样，能拿到 Binder 也不代表服务端会授权。调试权限问题时，dumpsys、logcat、avc: denied 日志与服务端的 enforceCallingPermission 往往要结合观察。

5.3 代码目录、进程名、服务名是三套坐标

以音频为例，frameworks/av 的代码不必然全在一个名为 mediaserver 的进程中；应用 API、system_server 的 AudioService、audioserver、Audio HAL 和内核驱动分别处于不同坐标。不要根据一个目录名猜运行位置。

音频的数据流与控制流已经单独梳理在 Android Audio 学习之旅 和 AudioTrack 剖析 中。

7. 常用观测命令

最后一条 Perfetto 命令只展示入口，不建议直接在生产设备上盲目执行：先明确要观察的时间窗口、数据源和输出路径，再用版本匹配的配置抓取。

8. 总结

理解 Android 架构的目标不是背出五层图或几十个服务名，而是形成下面这套可迁移的判断框架：

  1. 静态上：它属于 App、Framework、系统服务、Native、HAL 还是 Kernel？
  2. 动态上：它由 init、Zygote、system_server，还是某个服务按需创建？
  3. 边界上：它跨的是线程、进程、语言、分区还是硬件边界？
  4. 验证上：能否用源码、进程状态、日志、Binder 服务和 trace 证明链路？

带着这四个问题去读 Binder、Input、Audio 或任一系统服务，看到的就不再是孤立函数，而是一条在真实设备上运行的系统协作链路。
