Android 系统启动：servicemanager

源码基线：frameworks/native/cmds/servicemanager 与 frameworks/base/core/java/android/os/ServiceManager.java。本篇讲的是 /dev/binder 上的 framework servicemanager；不要把它和 Binder 驱动、hwservicemanager 或 vndservicemanager 混为一个对象。

1. 它解决什么问题

Binder 能把一次事务从进程 A 送到进程 B，但客户端首先要拿到服务的 Binder handle。servicemanager 是 /dev/binder 命名服务的上下文管理者（context manager）：

服务进程 addService(name, binder) → servicemanager 保存 name → binder → 客户端 get/check/waitForService(name) → 获得 Binder 引用 → 后续业务事务直接发往目标服务。

它不是“所有服务的执行中心”，也不转发后续业务调用；它只处理服务注册、查找、声明/懒启动、通知、死亡清理与访问控制。

1.1 四个概念的边界

名称 所在位置 职责
Binder driver 内核 /dev/binder 事务、对象引用、线程等待和死亡通知的内核传输层
servicemanager /system/bin/servicemanager framework Binder context manager，维护命名服务
hwservicemanager 独立 native 进程 历史 HIDL 服务注册中心；不要与 AIDL framework 服务混写
vndservicemanager 变体/厂商 Binder 上下文 vendor Binder 域中的服务管理；源码通过编译宏复用部分实现

因此，ServiceManager.addService("activity", ...) 是向 framework servicemanager 注册，service list 看到的也是这一域的服务；它不代表 HAL 的全部服务。

2. init 启动与重启语义

init 的 rc 将它置于很早的 core / animation 类，标为 critical；若它反复异常退出，init 的关键服务保护会使设备进入恢复路径。重启时还会停止就绪属性并重启一批依赖服务。

这解释了为什么它的稳定性极重要：重启 servicemanager 不只是清空一个 map，很多 system 服务必须随之重新建立 Binder 可发现性。

3. 取得 context-manager 身份

3.1 main() 的初始化顺序

默认 Binder driver 是 /dev/binder。进程把 Binder 线程池上限设为 0，并非“完全不处理 Binder”；Android 15 的 servicemanager 采用 Looper + setupPolling() 将 Binder FD 接入事件循环，而非普通 Binder 线程池模型。

becomeContextManager() 最终通过 Binder driver 的 context-manager 操作占据这个 Binder 域的唯一角色。它失败应直接 fatal：同一 driver 上不能有两个 framework servicemanager。

FATAL_IF_NOT_ONEWAY 是对自身发起 Binder 调用的约束：servicemanager 不应进行可能阻塞的同步 Binder 调用。它降低“服务注册中心又被服务端卡住”的风险，不是对外部客户端事务一刀切的限制。

3.2 Binder FD 进入 Looper

Binder 有输入时，Looper 调回 handlePolledCommands()，从 Binder driver 读取并分发事务到 ServiceManager 的 AIDL 实现；timerfd 的 client callback 也在同一 Looper 体系中处理。

4. 数据、注册与权限

4.1 服务表不是简单的 Map<String, IBinder>

Android 15 的 Service 条目至少包含 Binder、是否允许 isolated UID、dump 优先级、client 状态以及注册调用者的 UID/SID/PID 上下文。这样既能做访问判定，也能做延迟服务的 client 回调和故障诊断。

4.2 注册：调用者、SELinux、名称、VINTF、死亡通知

客户端 app UID 不允许注册系统服务；随后服务名要通过 SELinux add 权限，Binder 不能为空、服务名必须合法。framework servicemanager 还检查 VINTF 声明要求（适用时）。远端 Binder 注册 linkToDeath()，使服务进程死亡时能清表。

注意 addService 的成功不表示任何进程都能获取它；查询方还要经过独立的 find SELinux 判定。

5. 查找、懒启动与通知

5.1 getService、checkService 的区别

  • checkService()：不触发启动，立即查询；
  • getService()：服务不存在时可请求按 lazy AIDL service 尝试启动；
  • waitForService()：Java native 辅助层等待服务可用，适合明确需要它才能继续的场景。

getService() 并不保证立即得到非空 Binder；服务启动仍是异步过程。Android 15 的实现会先看内存表与 isolated 限制，再做 SELinux find 判定，最后在缺失且允许时请求懒服务启动。

5.2 注册可用通知

需要等待某服务出现的客户端可使用 registerForNotifications()。servicemanager 会先校验 find 权限、拒绝 isolated 调用者、将 callback 链到 death；如果服务已在表中，则立即通知。服务后来 addService() 时也会遍历回调。

5.3 服务死亡

Binder driver 通知 DeathRecipient 后，servicemanager 删除对应服务条目以及已死 callback。它并不替目标服务“重启进程”：服务如何重启由 init、system_server、懒 AIDL 控制或更上层策略负责。

6. Java 客户端如何抵达 native 服务管理器

Java android.os.ServiceManager 先取 Binder driver 的 context object，再转换为 IServiceManager 代理并缓存。每个具体系统服务也可以进入 sCache；缓存命中时不必再找 servicemanager。

这里的 Binder.allowBlocking() 是 Java 侧对“这个 Binder 可能同步阻塞”的显式标记，和 native servicemanager 自己的 FATAL_IF_NOT_ONEWAY 约束不是同一件事。

7. 排障阅读路径

  • service list：看 framework servicemanager 中当前可列出的 Binder 服务；无权限或其他 Binder 域的服务不会得到同样结果。
  • dumpsys servicemanager / dumpsys -l：检查可枚举服务和 dump 能力；SELinux 会影响 list/find/add。
  • logcat -b system -s servicemanager：查注册、权限拒绝、VINTF 声明、死亡与 lazy 启动日志。
  • SELinux 拒绝：首先区分是 add 还是 find；注册方能 add 并不自动授予客户端 find。
  • Binder driver 状态：需要从 /sys/kernel/debug/binder 或对应 debugfs 节点观察时，应注意用户版本访问限制以及 /dev/binder、/dev/vndbinder 的域差异。

8. 小结

  1. servicemanager 是 /dev/binder 上命名服务的 context manager，不是 Binder driver，也不代理每一次业务 Binder 调用。
  2. Android 15 主进程用 Looper + setupPolling() 处理 Binder FD，线程池最大数设为 0 不等于停止接收事务。
  3. 注册和查找分别有 SELinux add / find 控制；服务名、UID、VINTF、isolated UID、死亡通知共同构成约束。
  4. getService、checkService、waitForService 的启动/等待语义不同；懒 AIDL 服务尤其不能把它们当作等价 API。
  5. system service 的 Binder 死亡只会让条目被清理；服务重启由更上层的生命周期管理承担。
