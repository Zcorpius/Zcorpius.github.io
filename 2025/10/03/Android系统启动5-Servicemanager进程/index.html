Android 系统启动——Servicemanager进程

发表于 2025-10-03 | 分类于 Android ， StartUp
字数统计: 9.3k | 阅读时长 ≈ 37

1. 从名字到 Binder：谁告诉客户端服务在哪里

上一篇 SystemServer 进程 讲到：PowerManagerService.onStart() 发布了名为 power 的 Binder 服务。服务对象仍在 system_server 里，另一个进程却能通过这个名字取得它的引用。中间是谁保存名字，又是谁把引用交给客户端？

这就是 servicemanager 的位置。Binder 驱动负责跨进程传递事务与对象引用；servicemanager 在这个传输机制之上维护命名服务目录。服务端先注册，客户端再发现；拿到目标 Binder 后，业务事务直接发往目标服务进程。

本文沿 power 服务回答四个问题：

  1. servicemanager 自己还没有注册中心可用时，客户端如何找到它？
  2. power 注册成功，具体改变了什么状态？
  3. 查询、等待、缓存命中分别走哪条路？
  4. 找不到服务或服务死亡时，谁通知、谁清理、谁负责启动？

图中橙色实线表示注册、查询等控制调用，蓝色虚线表示返回或通知，绿色实线表示业务事务。跨进程箭头都经过 Binder 驱动，图中省去了驱动的内部传输细节。power 对应的是目标服务的 Binder 引用；handle 0 指向注册中心自身。

1.1 先分清名字相近的对象

名称 在哪里 管什么
servicemanager 独立 native 进程 /dev/binder 域里的命名服务、发现权限和注册通知
native ServiceManager 上述进程中的 C++ 对象 实现 BnServiceManager，持有服务表
Java android.os.ServiceManager 客户端进程中的静态工具类 注册、查找服务的 Java 入口及启动时预装的引用缓存
SystemServiceManager system_server 内 创建 SystemService，推进 onStart()、boot phase 等生命周期
LocalServices 单个进程内 按 Java 类型保存本地对象，不经过 servicemanager
Binder driver 内核 传递事务、维护跨进程引用、报告 Binder 死亡

本文讲 /dev/binder 上的 servicemanager。hwservicemanager 管理的是另一套 HIDL 服务发现机制；vndservicemanager 是 vendor Binder 域的管理器，不能把几者的服务表拼成一张。使用 /dev/binder 的 AIDL HAL 也可能出现在本文这张目录里，因此它既不只包含 Java 系统服务，也不代表设备上全部 HAL。

2. 注册中心如何先启动起来

2.1 init 明确启动它，class 只是分组

servicemanager.rc 定义进程身份、分组和重启行为；真正的早期启动入口还要沿 action 查到 system/core/rootdir/init.rc。本地文件在 on init 中显式执行 start servicemanager，不能仅凭 class core animation 推断它要等到 class_start core 才启动。

start 让 init 启动进程，不保证命令返回时该进程已完成初始化。servicemanager.ready 则由 servicemanager 自己在建立接收机制后设置，这两种状态要分开。

critical 表示 init 对反复异常退出有专门保护。当前 Service::Reap() 还检查崩溃次数、时间窗口、开机是否完成、调试开关和重启节流；不宜概括成“退出一次就重启整机”或“固定进入 recovery”。shutdown critical 是关机阶段的另一个选项，也不能与崩溃保护混为一谈。

2.2 handle 0 解决“先去哪里找注册中心”

普通服务通过名字发现，注册中心则使用 Binder 域提供的特殊入口。客户端的 handle 是本进程使用的 Binder 引用编号，不是目标 PID，也不是可以跨进程直接使用的内存地址。handle 0 对应当前 Binder 域的 context manager，客户端无需先按字符串查询它。

服务端要完成两件事：把用户态的入口对象交给 IPCThreadState，再向驱动申请 context-manager 身份。

becomeContextManager() 先发出 BINDER_SET_CONTEXT_MGR_EXT ioctl，失败时回退到旧的 BINDER_SET_CONTEXT_MGR；两者都失败，main() 就 fatal。同一 Binder context 的管理者角色不能由两个进程同时占据。

addService("manager", ...) 是向自己的命名表放入一个条目，它不是获得 handle 0 身份的原因。客户端取得 context object 的关键证据在 libbinder：

普通外部客户端由此取得代理；驱动把事务送到管理者后，IPCThreadState::executeCommand() 的 context-object 分支调用 the_context_object->transact()，再进入 AIDL 分发。这里建立的是“客户端怎样抵达服务管理器”，还没有查找 power。

2.3 线程池上限为 0，事务由谁处理

setThreadPoolMaxThreadCount(0) 不能读成“这个进程没有线程接收 Binder”。本地 servicemanager 选择把 Binder FD 接入主线程的 Looper，使用事件驱动的 polling 路径。

ClientCallbackCallback 还注册了一个每 5 秒触发的 timerfd，回调中执行 handleClientCallbacks() 并重新检查 Binder FD。它服务于客户端引用状态管理，不是每 5 秒才处理一次注册或查询；Binder FD 就绪时有自己的回调。

FATAL_IF_NOT_ONEWAY 限制的是servicemanager 自己向外发起的非 oneway Binder 调用。它可以接收客户端的同步查询并返回结果。结合单主线程分发方式看，避免注册中心主动陷入同步等待，有助于防止其他注册、查询一起被拖住；这也解释了后文注册通知使用 oneway 接口。

addService() 不是一次无条件的 map 赋值。它先获取 Binder 调用上下文，再检查调用者、服务名、对象和声明要求。下面保留会改变注册结果的分支：

Access::getCallingContext() 取得调用者 UID、PID、SID。SID 用于 SELinux 判断；setRequestingSid(true) 与驱动的安全上下文支持，让注册中心能依据事务来源检查，而不是相信请求参数里的自报身份。

canAddService() 最终要过 Access::canAdd()。Access 用服务名查询 service_contexts 的目标标签，再检查 service_manager 类上的 add 权限；查找时则检查 find。本地 power 的标签是 u:object_r:power_service:s0。名字、标签、允许哪些调用者访问的策略规则，是三个不同层次；登记了标签不等于自动授予权限。

VINTF 检查也有适用条件：meetsDeclarationRequirements() 先看 Stability::requiresVintfDeclaration(binder)，不要求声明的 Binder 直接通过；要求声明的才继续核对 manifest。不能据此要求所有普通 Java 系统服务都加一份 HAL manifest。

回到 power：onStart() 注册成功后，服务表出现条目，符合查询条件的客户端可以取得其引用；但 PowerManagerService.systemReady() 是后续 boot phase 推进的状态。目录中可发现，与服务所有业务能力已完成初始化，并非同一个时刻。

4.2 get、check、wait 必须连同所属层一起读

入口与所属层 目标服务缺失时的行为
Java ServiceManager.getService() / checkService() 本地快照最终走 check 路径；查询不到可返回 null，不在这里等待目标服务注册
native 客户端 IServiceManager::getService()
具体实现 CppBackendShim		 先 check；缺失后在约 5 秒的重试窗口内反复 check，不等于服务端 get

servicemanager 服务端 checkService() startIfNotFound=false；不请求启动缺失服务
Java / native 客户端 waitForService() 经 native 的真实 get 路径请求启动，注册可用通知，并在客户端等待与重试

“即时查询”仅表示不等待目标服务未来注册，不表示整个函数绝不会阻塞：查询本身有同步 Binder 往返；native 适配层首次初始化时，在适用的 Bionic 非 VNDK 构建下还会等待 servicemanager.ready，随后取得 context object。CppBackendShim 的约 5 秒窗口也不是对每次底层 IPC 耗时的硬截止。

当前返回值包含 Service 联合类型，普通路径携带 ServiceWithMetadata；其中 service 才是 Binder，isLazyService 是附带状态。RPC accessor 是另一种返回分支，由适配层处理，本文不把它硬套成普通 Binder 服务条目。

4.4 普通应用获取 power，通常有一条更短的路

把场景还原到应用启动。AMS 的 getCommonServicesLocked(false) 会准备常用服务引用，其中包含 Context.POWER_SERVICE；这些引用随 bindApplication() 传给应用，ActivityThread 再调用 ServiceManager.initServiceCache(services)。

所以普通应用第一次调用 getSystemService(PowerManager.class)，也可能已经命中 power 的 Binder 缓存。SystemServiceRegistry 的工厂取出 powerBinder，执行 IPowerManager.Stub.asInterface(powerBinder)，再构造 PowerManager；该工厂还会取得 thermalservice，本文只追踪其中的 power 依赖。

这里至少有三种不能混称的缓存：Java ServiceManager.sCache 保存 Binder 引用；SystemServiceRegistry 缓存客户端的 PowerManager 包装对象；BackendUnifiedServiceManager 还存在由构建选项控制的 native 引用缓存。仅凭源码中有 native 缓存代码，不能断言目标设备启用了它。

拿到 IPowerManager 后，后续真正需要 IPC 的电源业务调用发往 system_server。例如 WakeLock.acquireLocked() 在满足本地计数条件时调用 mService.acquireWakeLock()，不会先把业务请求交给 servicemanager 转发；PowerManagerService.BinderService.acquireWakeLock() 仍会检查 WAKE_LOCK 等权限。能发现服务，不等于获得它所有业务操作的权限。

isolated 应用也不会直接收到这批普通应用的完整预装引用：AMS 在 getCommonServicesLocked(true) 中走单独分支。不能用普通应用的缓存路径推导 isolated 进程也能访问 power。

5.2 waitForService 等在客户端，不占住注册中心

Java 与 native 客户端共用一套等待逻辑。Java 方法先经过 JNI 桥接，再调用 native 默认服务管理器的等待接口，桥接实现见 android_os_ServiceManager.cpp。

普通 Binder 路径落在 CppBackendShim::waitForService()，其流程如下：

  1. realGetService() 经统一适配层调用真正的 getService2()；若已有引用，立即返回；缺失时可请求 init 启动。
  2. 若仍为空，建立 Waiter，调用 registerForNotifications(name, waiter)。
  3. 客户端线程在条件变量上等待；Binder 回调线程收到 onRegistration() 后写入 mBinder，唤醒等待线程。
  4. 每等待一秒仍无结果，就再执行一次 realGetService()；它既能补查，也能重新请求启动，覆盖 init 与服务死亡通知之间的竞态。
  5. 返回时用局部 Defer 对象注销通知。权限或事务错误可以提前返回空引用；源码循环没有一个“所有情况等满 5 秒就退出”的总超时。

因此客户端需要能处理注册回调的 Binder 线程；如果把相关线程都堵住，即便服务发布了，等待者也可能无法及时收到通知。这与 servicemanager 自己采用 Looper 接收 Binder 是两个进程中的两套执行安排。

图中给出“监听先登记，服务后注册”的一条时序；启动请求由工作线程发送，与客户端返回后的监听登记可以交错。若服务更早注册，也不会因为错过一条瞬间事件就永远等不到，关键在下一段。

6. 服务死亡后，清表和重启是两项工作

注册 power 时，servicemanager 对远端 Binder 建立了 linkToDeath()。如果它所在的 system_server 死亡，Binder 驱动会报告对象死亡，servicemanager 再删除指向这个 Binder 的条目：

清理回调表时删除的是与这个死亡 Binder 对应的回调，并不是一概删掉所有仍存活的等待者。同名服务被新 Binder 替换后，迟到的旧 Binder 死亡通知也不能仅凭名字把新条目删掉，代码中的对象身份比较正是这条边界。

清表不会修复其他进程已经保存的旧 Binder 引用，也不会在这里 fork 一个新的 system_server。客户端再次调用旧引用可能得到死亡或远程异常；如何重新获取引用、是否退出重启，要由相应客户端和进程生命周期策略处理。native 适配层的可选缓存有自己的死亡失效机制，不能因此推断 Java sCache 也自动执行同一套刷新。

对于由 init 管理的懒服务，后续有权限的真实 get 请求可以再次触发启动；对于 system_server 内的系统服务，则要沿 Zygote 与系统恢复链路追踪。另一个方向上，servicemanager 自身死亡会丢失整张进程内目录，所以其 rc 设置了一组依赖重启动作；它与“某一个普通服务条目死亡”影响范围不同。

7. 把源码结论变成可观察的证据

以下是尚未在设备执行的验证方案，不包含虚构的日志或 dump。先记录设备版本，再对照本地源码；量产 user 构建、SELinux 和日志权限会影响可见结果。

7.1 先分别确认进程、注册中心、条目和业务状态

service check power Service power: found 本次 shell 身份能取得 power 引用；不能证明任意应用身份都能取得
service list 中的 power 名称及可取得的接口描述符 目录与描述符查询结果；service list 还会逐项 check，空描述符可能需要继续查 find 权限或服务状态
dumpsys power 中的 mSystemReady 完成相应初始化后通常为 true 电源服务自己的状态；与目录是否包含 power 是两层证据

listServices() 检查的是管理器的 list 权限，并按 dump 标志筛选，不是逐条替调用者做 find 后才返回名字。本地 service list 先取名字，再逐项 checkService() 获取描述符；dumpsys -l 则会略过 check 不到的条目。于是“名单里有名字”“我能取得 Binder”“我有权执行 dump”可能出现不同结果。

dumpsys power 也有自己的 dump 权限与服务响应前提。若它失败，应保留原始错误，不直接把失败解释成 servicemanager 没启动。

7.2 沿失败发生的位置缩小范围

main() 调用了 InitLogging(..., KernelLogger)，而相关源码还使用 ALOG 和 SELinux 审计回调，不能把 logcat -b system -s servicemanager 当作覆盖全部证据的唯一入口。内核日志能否被 logd 转收、早期日志是否保留，需要结合设备构建判断；没有搜到一行日志，不等于没有执行对应代码。

现象 下一步查什么 源码指向
注册端收到拒绝 appId、服务名标签、SELinux add、VINTF 要求、死亡通知建立结果 ServiceManager::addService()、Access
power 已注册但某调用者查询为空 查询者 UID/SID、isolated 身份、find；区分是否已有缓存 tryGetBinder()、Java/native 缓存入口
getService() 返回空却没有启动进程 先确认究竟是 Java、native 客户端 shim，还是服务端 get 第 4.2 节的入口对照
出现懒启动尝试但一直没有条目 rc 的 interface 名称是否一致、init 是否找到并启动服务、服务端是否执行成功注册 tryStartService()、HandleControlMessage()、服务自己的入口
已发布却仍有客户端在 wait 通知登记结果、客户端 Binder 线程可用性、一秒重试日志 CppBackendShim::waitForService()
目录中消失或反复出现同名服务 目标进程退出、binderDied()、同名覆盖日志、init 重启策略 第 3.2、6 节

看到 avc: denied 时，重点保留 { add } / { find } / { list }、scontext、tcontext、tclass=service_manager 以及可用的服务名、PID、UID。它们分别回答“谁对哪个标签申请了哪种操作”。dumpsys 或业务方法自身的权限失败要按其错误继续追踪，不能都归结成 find。

7.3 两个适合在测试构建里补做的对照实验

这些实验需要已有测试服务和客户端程序，本文没有构建或运行它们。不要通过杀死 servicemanager 或 system_server 来代替服务级实验。

实验 操作与记录 预期差异与结论边界
check 与 wait 为一个有独立名称、正确策略和 lazy rc 配置的测试 native 服务准备客户端；服务尚未启动时分别调用 check 与 wait，记录调用入口、开始/返回时间、服务 PID、init 控制日志和注册日志 check 本身不请求懒启动；wait 走真实 get 路径并等待引用。名称、权限、接收线程都正确才有成功条件，不能预设固定启动耗时
订阅时的服务已存在 先让测试服务完成注册，再让有权限的客户端登记注册通知；记录 onRegistration() 到达与 Binder 引用 即使没有“新的注册事件”，登记时的当前表检查也会发通知。另做先订阅后注册，确认第二条路径；若回调缺失还需排查客户端线程

gsid 在第 5 节仅用于核对真实配置，不要求为了学习主动启动或操作设备的动态系统安装服务。测试服务能更清楚地控制初始状态，也能避免把设备其他启动活动误当成自己的实验结果。

8. 分层记忆与自测

8.1 L0：记住三段关系

注册中心先取得 handle 0 的入口身份；服务把“名字 → Binder 引用”登记到目录；客户端取得目标引用后直接进行业务 IPC。 缓存可以省去重复发现，权限与业务就绪仍各有自己的检查位置。

8.2 L1：能顺着问题展开的主干

  • 怎样活起来：init 的 start → native main() → context object 与 context manager → Binder FD 接入 Looper → 设置 ready → 持续分发。
  • 怎样发布：onStart() → publishBinderService() → Java/native 代理 → 身份与策略校验 → 死亡通知 → 写服务表 → 注册通知。
  • 怎样取得：先看实际语言入口和缓存；普通查找还要经过 isolated 限制与 find，返回元数据里的 Binder。
  • 怎样等待：真实 get 请求懒启动；init 创建进程；客户端登记监听并等待；已存在和后来注册两条通知路径一起覆盖。
  • 怎样失效：Binder 死亡触发按对象身份清表；旧引用不会因此自动变成新引用，恢复由各自生命周期策略继续处理。

8.3 L2：按需回到源码定位

需要查阅的细节 入口
主循环、timerfd、调用限制、ready 属性 cmds/servicemanager/main.cpp
handle 0、context-manager ioctl、polling 与事务分发 libs/binder/ProcessState.cpp、IPCThreadState.cpp
服务名规则、同名覆盖、VINTF、isolated、通知、死亡清理 cmds/servicemanager/ServiceManager.cpp

8.4 基础题：先回答，再展开

1. power 的 Binder handle 是 0 吗？为什么查询注册中心不需要另一个注册中心？

展开参考答案

不是。handle 0 是当前 Binder 域 context manager 的特殊入口，客户端通过 getContextObject() 得到它，再按名字查找 power。返回的目标引用由 Binder 机制在接收进程中管理，不能把它与管理器入口混为一个编号。回看第 2.2 节。

2. servicemanager 线程池上限是 0，为什么还能处理同步查询？

展开参考答案

主线程通过 setupPolling() 把 Binder FD 加入 Looper，FD 就绪时执行 handlePolledCommands()。FATAL_IF_NOT_ONEWAY 限制它主动向外发起同步调用，不禁止它接收查询并回复。回看第 2.3 节。

3. addService("power", binder) 成功，能推出所有应用都能获取并调用它吗？

展开参考答案

不能。注册检查的是注册者与对象能否入表；查询还有 find 和 isolated 限制，业务方法还有自己的权限与状态要求。power 的发布还早于后续 systemReady()。回看第 3.2、4.3、4.4 节。

4. Java getService()、native 客户端 getService() 和服务端 getService() 是同一种等待行为吗？

展开参考答案

不是。本地 Java 路径转到 check；native CppBackendShim::getService() 在约 5 秒窗口内重试 check；服务端 get 使用 startIfNotFound=true 请求懒启动，但不等待新条目。真正的通知等待在客户端 waitForService() 中。回看第 4.2、5.2 节。

8.5 场景题：预测结果，并说明如何验证

5. 普通应用第一次创建 PowerManager，trace 中却没有对应的 servicemanager 查询。它一定没有取得 power 吗？

展开参考答案

不能这样判断。AMS 可能已在绑定应用时传入 power 引用，由 ActivityThread 初始化 Java sCache，第一次创建包装对象也能命中它。先核对该进程是否为普通应用、传入的 services 是否含 power，再检查 Java 和可选 native 缓存路径。业务 IPC 与名称查询也要分开观察。回看第 4.4 节。

6. 第一次 get 返回空之后、登记监听之前，懒服务已经注册。wait 是否会永久错过通知？

展开参考答案

在本文普通 Binder 路径、权限与回调线程正常的前提下，不会仅因这个空隙漏掉通知：registerForNotifications() 保存监听后检查当前表，已存在就发送 onRegistration()；若注册发生在监听之后，则由 addService() 通知。可按第 7.3 节做先注册后订阅的对照，并记录回调到达时间。回看第 5.3 节。

7. service list 有某名称，查询该名称却为空，是否只能说明服务刚刚死了？

展开参考答案

不只能这样解释。list 与 find 是不同权限检查；服务端列名并不逐条按 find 过滤，调用者身份和观察时刻也可能不同。应检查 service list 中描述符是否为空，核对同一身份下的 check、SELinux 审计与进程状态。dumpsys -l 又会略过 check 不到的条目。回看第 7.1、7.2 节。

8. 名称被新 Binder 覆盖后，旧 Binder 的死亡通知才到达，会把新条目删掉吗？旧客户端引用会自动更新吗？

展开参考答案

binderDied() 比较的是死亡 Binder 与当前条目保存的 Binder；新旧对象不同，就不会仅因名字相同删除新条目。但旧客户端引用仍然指向旧对象，不会被目录覆盖操作自动替换。分别观察重新查询取得的引用与旧引用上的调用结果，才能区分目录恢复和客户端恢复。回看第 3.2、6 节。

读到这里，可以把上一章的“发布服务”补成完整路径，再到 App 进程启动 追踪常用 Binder 引用如何随着应用绑定传入新进程。init 的 action 与服务启动调度可回看 init 进程。
