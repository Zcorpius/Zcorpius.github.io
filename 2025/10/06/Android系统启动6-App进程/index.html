Android 系统启动——App进程

发表于 2025-10-06 | 分类于 Android ， StartUp
字数统计: 11.9k | 阅读时长 ≈ 46

1. 点击图标以后，什么才算“应用启动了”？

点击一个应用图标，日志已经出现 Start proc，界面却还没有出来。这时进程可能已经存在，但仍在连接系统、创建 Application、初始化 Provider，或者执行首个 Activity 的生命周期。把这些阶段统称为“Zygote 启动应用”，很容易把卡顿定位到错误的地方。

本文用一个贯穿场景说明它们的关系：示例笔记应用 com.example.notes 的主进程尚不存在，用户打开 NotesActivity；该进程还声明了一个普通的 NotesProvider。 这些名称只用于推演，不代表下面真机采样中的应用。

我们从 framework 已经选定目标 Activity、准备为它寻找宿主进程开始，追到 Application 初始化完成和首个 Activity 的创建、恢复。Launcher 点击处理、Intent 解析和完整任务栈策略不在本篇展开；绘制与合成只说明观察边界。重点回答：

  1. 谁判断需要新进程，创建请求为什么要经过两次消息调度？
  2. Zygote 返回 PID 与应用回连 AMS，为什么可能出现先后竞态？
  3. Application、Provider 和 Activity 分别在什么线程、什么时刻初始化？
  4. 本地版本新增的 finishAttachApplication()，怎样影响后续组件派发？

图中选择按需 fork 的常规路径，并假设系统开启等待 finishAttachApplication。橙线表示跨进程通信，绿线表示子进程创建，蓝线表示进程内推进。PID 回包与子进程回连可以并发，不要把图上的排版顺序当成两者必然的先后关系。USAP 改变创建阶段，后面仍要进入应用绑定流程。

《Zygote 进程》 已经解释预加载、fork 和特化；《SystemServer 进程》 解释系统服务如何进入可用阶段。本篇把重点放在新进程怎样成为可接收组件任务的应用进程。

2. 一个包、一个进程和一个 Activity，不是同一个对象

2.1 先分清系统侧记录与应用侧对象

Android 需要同时管理两件事：哪个界面应该启动，以及哪个 Linux 进程能够承载它。它们的状态不同，所以分别由任务管理和进程管理对象保存。

对象 所在位置 在本次启动中的职责
ATMS、ActivityTaskSupervisor system_server 管理 Activity、任务和启动决策，寻找目标进程
ActivityRecord system_server 表示系统侧的一次 Activity 实例及其启动状态，不是应用里的 Activity 对象
AMS、ProcessList system_server 组织进程创建参数、管理待启动记录、接收应用回连
ProcessRecord system_server 保存进程名、UID、PID、启动序号及应用 Binder 接口等
WindowProcessController system_server 进程在窗口/任务管理侧的状态与接口
ActivityThread 应用进程 Java 运行入口和主线程事务处理的组织者；它继承 ClientTransactionHandler，不是 Thread
ApplicationThread / IApplicationThread 应用中的 Binder 实现 / 跨进程接口 接收系统派发的绑定、组件及事务请求
LoadedApk、ContextImpl 应用进程 提供包的代码加载、资源及运行上下文
Application、Activity 应用进程 应用级回调对象与具体界面对象

ApplicationThread 这个名字也容易误导。它是 ActivityThread 的内部类，继承 IApplicationThread.Stub，并不是又一个 Java 主线程。系统经 Binder 调用它后，很多工作还要投递给主线程的 H。

在普通非隔离路径中，系统按进程名与 UID寻找进程。包默认进程名通常等于包名，但组件的 android:process 可以改变宿主。一个进程能承载多个 Activity；同一 APK 的不同进程也各自运行初始化代码，不能把 Application 当成跨进程共享单例。

2.2 有可用进程，就不必再次 fork

笔记应用冷启动时，目标 NotesActivity 已有系统侧记录，但还没有应用侧对象。startSpecificActivity() 先找进程；只有无法走已有进程路径时，才继续请求创建。

因此，“打开 Activity”并不等于“创建进程”。从后台返回已有界面、在已有进程中新建 Activity，都可能绕过 fork；realStartActivityLocked() 本身还要处理暂停和可见性条件，也不是调用后立刻进入应用的 onCreate()。

ProcessList.startProcessLocked() 还会进一步检查已有记录。存在 PID、进程正在启动但尚未 attach 时，可以继续等待这次启动，避免因多个组件同时请求而反复创建。不能仅用“当前没有 IApplicationThread”判断必须再 fork 一次。

2.3 ATMS 到 AMS：同一进程，也需要异步转交

本地 ActivityTaskManagerService.startProcessAsync() 把 Activity 放进 mStartingProcessActivities，随后向 mH 发送一条调用 ActivityManagerInternal.startProcess 的消息。源码明确说明这样做是为了避免持有 ATMS 锁时直接进入 AMS 带来的潜在死锁。

这里要分清两种“跨边界”：

  • ATMS 与 AMS 都在 system_server；ActivityManagerInternal 是本地服务接口。这一步通过 Handler 转交执行，不是向 Zygote 发 Binder 请求。
  • 后面 Process.start() 与 Zygote 通信，才会跨到另一个进程，而且使用 Unix domain socket。

HostingRecord 随请求记录“为什么需要这个进程”：本例是 Activity，其他情况可能是 Service、Provider 或广播接收器。这个原因影响策略和日志，但不会把 Linux 进程变成只能承载某一种组件的进程。

3. ProcessList 怎样发起“一次可核对身份的创建”

3.1 在 fork 之前，先登记 startSeq

如果只保存 PID，就无法表示“已经请求创建但还没拿到 PID”的阶段。进程退出后 PID 还可能被复用，因此启动过程还需要一个属于本次请求的序号。

本地实现先分配 startSeq，建立 mPendingStarts，再提交真正的创建工作。

FLAG_PROCESS_START_ASYNC 的本地默认值为 true。AMS 构造时创建 ActivityManager:procStart 对应的 ServiceThread 和 Handler；handleProcessStart() 有意不一直持有全局 AM 锁，创建完成后再进入锁内登记结果。如果前一个同名进程正在退出，还可能等待前任清理后再执行创建工作。

这就是第二次异步转交：第 2.3 节是 ATMS 把工作交给 AMS；这里是进程管理把实际创建交给专用线程。异步路径返回成功，不能用来证明 ProcessRecord 已经有 PID，更不能证明 Application 已经存在。

3.2 请求中既有入口，也有身份与隔离参数

普通应用的入口类在 ProcessList 中指定为 android.app.ActivityThread。Process.start() 是转发到 ZYGOTE_PROCESS 的 Java 门面，不会在 system_server 中直接调用目标 main。

参数组 例子 为什么需要
执行入口 entryPoint、seq=<startSeq> 选择子进程 Java 入口，并让回连能够对应本次启动
身份 UID、GID、补充组、seInfo 建立 Linux 权限与 SELinux 等安全上下文
代码与运行环境 ABI、instruction set、target SDK、runtime flags 选择合适的 Zygote 和运行时行为
数据与存储 包数据映射、挂载隔离开关 为目标进程准备可访问的数据视图
调度与创建策略 isTopApp、zygotePolicyFlags 影响创建策略和初始调度提示

seInfo 是后续安全上下文选择的输入，不应直接等同于最终 SELinux domain。ABI 决定应连接哪个能承载该指令集的 Zygote；primary/secondary 的含义来自配置，不能固定翻译成 64/32 位。

App Zygote、WebView Zygote 的选择由 HostingRecord 决定；单凭组件有 isolatedProcess 就断言一定使用 App Zygote，会漏掉其他条件。它们的预加载内容和进程组创建位置也不同。本篇不展开 SDK sandbox、App/WebView Zygote 与 isolated entry point 的完整分支。

存储准备的位置还有一个实际影响：Start proc: <进程名> 这段 trace 包含的工作不只是 fork 系统调用。即使它很长，也要继续区分 socket 等待、进程组处理和存储准备，不能直接归因为“内核 fork 慢”。

3.3 从 socket 参数到子进程 main

ZygoteProcess.startViaZygote() 把配置编码成参数列表，再按 ABI 选择连接。普通创建协议是“参数个数 + 等量的换行分隔参数”；发送前拒绝换行、回车与 NUL，避免参数破坏报文边界。

普通 socket 路径返回 PID 和 usingWrapper。ProcessStartResult 不包含 UID 或 startSeq；这些身份信息来自系统已有记录和后续 Binder 回连。USAP 仅在配置和请求策略都允许时尝试；这里捕获的是 IOException，不能扩大成“USAP 的任何失败都会自动回退”。

Zygote 侧仍须检查连接身份与命令参数。本地 ZygoteConnection 构造器只允许 system UID 的对端连接；“能组织同样的参数”不等于普通应用就有权启动任意 UID 的进程。

创建之后还有特化：设置身份、权限、运行时状态和挂载隔离，并按规则清理继承的 FD。常规请求既可能走 forkAndSpecialize()，也可能走简单 fork 分支；USAP 则预先 fork，收到请求后再特化。USAP 的 PID 回包甚至位于特化之前，因此“收到 PID”不能当成后续步骤全部完成的屏障。

普通应用子进程最后进入 ZygoteInit.zygoteInit()，经 RuntimeInit.applicationInit() 找到入口。当前实现返回一个 Runnable，外层执行它，再进入 ActivityThread.main()；不是靠抛出 MethodAndArgsCaller 异常切换到 main，也不是重新 exec 一个 Java 程序。有关父子分流与 native 特化的细节可回看 《Zygote 进程》第 5～7 节。

4. 子进程怎样向 AMS 证明“这次创建的是我”

4.1 ActivityThread.main 先准备 Looper，再回连

新进程已经有从 Zygote 继承并完成调整的运行时环境，但还不知道完整的应用绑定信息。它先准备主线程的消息机制，再把自己的 Binder 接收端交给 AMS。

这里没有 new Thread(...).start()。当前执行 main 的线程成为应用主线程，ActivityThread 对象组织它的消息和回调。prepareMainLooper() 建立队列与 Looper，loop() 才开始持续取消息，两者之间还要完成 attach。

IActivityManager.attachApplication 没有 oneway 修饰，应用主线程会等待这次 Binder 调用返回。此时 Binder 接收能力已经由子进程的 runtime/native 初始化建立，所以 AMS 可以回调 mAppThread，让它先把绑定消息入队；主线程随后进入 Looper 再消费。

ActivityManager.getService() 获取的是系统服务接口。应用自己的 IApplicationThread 是这次 attach 的参数，不是让每个 App 都去 servicemanager 注册一个包名服务。服务查找机制可参考 《Servicemanager 进程》。

4.2 PID 回包与 attach，没有固定先后

fork 后，Zygote 父进程向创建方回包，应用子进程则独立向前执行。系统的进程创建线程要登记结果，AMS 的 Binder 线程也可能同时收到 attach；两个入口都必须关联到正确的 ProcessRecord。

startSeq 标识一次启动请求，不是 PID，也不是可以单独证明身份的秘密。AMS 还要取得 Binder 提供的真实调用方 PID、UID，并与记录中的启动 UID、序号匹配。

外层 attachApplication() 在清除调用身份之前，通过 Binder.getCallingPid() 和 Binder.getCallingUid() 取得这些参数，调用者不能通过传入一个同名包来替代它们。handleProcessStartedLocked() 还会检查进程记录是否仍有效，例如启动期间是否已被系统杀掉、记录是否被替换。

这段实现允许两种正常时序：

  1. 创建结果先登记：PID 表已经有记录，attach 按 PID 找到它，再核对 UID 和序号。
  2. 应用先回连：PID 表未命中，attach 从 mPendingStarts[startSeq] 找到待启动记录，核对后补齐 PID 登记。

第二种情况并不表示系统丢失了进程。它正是启动序号要解决的并发窗口。

4.3 迟到的创建结果怎样避免重复登记

负责真正登记的重载会移除 pending 项、验证记录、设置 PID、清除 pendingStart 并加入 PID 表。若 procAttached 为 false，才安排等待 attach 的进程启动超时；先回连的路径传 true，不再为一个已经 attach 的进程重复安排这段等待。

到这里，系统可以把一个实际 PID、一次启动请求和应用提供的 Binder 端点关联起来了。但 Application 的创建还在下一段流程中。

5.2 LoadedApk、Context 和 Instrumentation 各准备什么

handleBindApplication() 会配置进程运行参数、资源和包加载环境，并准备 Instrumentation。在普通应用路径中，没有测试用 Instrumentation，也会创建框架默认的 Instrumentation；它承担 Application、Activity 的实例化与生命周期调用，不是“只有测试才用到”的对象。

LoadedApk 保存这个包在当前进程里的加载信息，包括 ClassLoader、资源以及已创建的 Application。ContextImpl 则提供访问资源、系统服务和应用环境的上下文。三者不是三份 Application，而是让 Application 能正确构造和运行的支撑对象。

5.3 为什么 Provider 可能早于 Application.onCreate

回到笔记应用：NotesProvider 若被列入本次绑定的 Provider 列表，会在主线程的绑定处理期间初始化。它并不是等到 NotesActivity.onCreate() 才创建。

这张图表示常规绑定且存在待安装 Provider 的情况。受限备份模式、开机解锁状态、组件启用状态和 Provider 所属进程，都会影响实际列表；它不是“APK 内所有 Provider 在任何时候都先执行”的规则。

installContentProviders() 逐一调用 installProvider()，本地 Provider 的 attachInfo() 会进入 ContentProvider.onCreate()，随后把创建好的 Provider 接口发布给系统。顺序可以写成：

创建 Application 对象 → Application.attachBaseContext() → 安装本次 Provider 并调用其 onCreate() → Application.onCreate()。

这也符合 Application.onCreate 官方说明 中对 ContentProvider 的例外约定。

它能解释一个常见故障：如果 NotesProvider.onCreate() 读取一个只在 Application.onCreate() 中赋值的字段，那个字段此时可能仍未初始化。解决问题需要重新安排依赖，例如把该 Provider 必需的轻量初始化放到更早且合适的位置，或让它按需初始化；不能仅凭“Application 是全局对象”假设所有回调已经执行。

5.4 初始化慢和初始化失败，要沿不同证据追踪

Provider、Application 初始化都在主线程上，它们耗时会直接推迟绑定流程以及首个 Activity 的执行。本地主线还要经过第 6 节的完成回连；Application 自己启动了后台任务，并不意味着系统会等待这些后台任务全部结束。

如果构造或 onCreate() 抛出异常，相关 Instrumentation 没有接管时，流程会抛出运行时异常，不会正常走到最后的完成回报。另一种情况是没有崩溃但长期阻塞，此时需要检查主线程栈、调度与绑定超时，而不是把“没看到 Activity”统一归类成 fork 失败。

等待 attach 的超时与等待绑定完成的超时也不同。本地 AMS 在发出 bindApplication() 后移除 PROC_START_TIMEOUT_MSG，安排绑定阶段的超时；绑定软超时还会结合进程可运行却未获 CPU 的等待量决定是否延后一次硬超时，最终可能报告启动 ANR。这些判断说明“已经 attach”并未结束系统对启动进度的管理。

6. finishAttachApplication：何时允许继续派发组件

6.1 makeActive 与初始化完成之间，还有一个状态

AMS 发送 bindApplication() 后，会把应用 Binder 接口装入进程记录，使系统能够向该进程发送请求。但本地实现同时标记 pendingFinishAttach，明确区分“有接收接口”和“完成绑定阶段”。

ProcessRecord.isThreadReady() 的本地判断是 mThread != null && !mPendingFinishAttach。这个方法很好地说明了两个状态的区别，但不能据此假定所有调用点都统一通过它检查；具体派发路径仍须看各自实现。

mEnableWaitForFinishAttachApplication 的本地默认值为 true，可由 activity_manager 命名空间下的 DeviceConfig 键 enable_wait_for_finish_attach_application 更新。默认值和设备当前值要分别核对，第 9 节给出本次实际读取结果。

6.2 应用回报后，系统怎样继续等待中的工作

应用完成第 5 节的同步绑定工作后，会调用 finishAttachApplication()。它同样是同步 Binder 方法；参数里的时间戳是在 Application 回调开始前采集的，而“调用到了这个完成接口”才说明执行流已经走过前面的回调和后续绑定步骤。

finishAttachApplicationInner() 再次根据 PID 查进程记录，核对启动 UID 和 startSeq；通过后移除绑定超时，清除 pendingFinishAttach。接下来：

  • 系统允许正常启动应用时，交给 ATMS 检查等待该进程的 Activity。
  • 若前面没有失败，继续处理等待的 Service、广播和备份代理等。
  • 派发失败可能引发初始化失败处理；没有需要派发的工作也不等于进程创建失败。

笔记应用的 NotesActivity 在第一项中接回主线。若这次进程实际上由 Provider 请求拉起，就不一定有待启动 Activity，更不会凭空创建一个界面。

开启 应用调用 finishAttachApplication() 后进入完成处理 主线程先走完前面的绑定工作，再处理后续消息
关闭 AMS 的 attachApplicationLocked() 内直接进入完成处理 绑定和组件请求仍由应用侧相应消息处理，发出请求不等于立即执行回调

配置关闭并不把 Application 初始化搬到 Binder 线程，也不使 Activity 的 onCreate() 可以任意绕过主线程正在执行的绑定处理。它改变的是系统派发工作的等待点。

7. 进程就绪之后，Activity 怎样真正被创建

7.1 系统找回的仍是 ActivityRecord

第 2.3 节保存了 mStartingProcessActivities。在完成回连后的 ATMS 路径里，RootWindowContainer.attachApplication() 按进程 UID 和进程名匹配这批记录；还会排除已经 finishing、失去任务容器、已经关联进程或不应向当前用户显示等情况。

符合条件的 ActivityRecord 才交给 realStartActivityLocked()。因此从冷启动请求到进程准备好之间，如果用户切换界面、任务发生变化，不能假设所有最初等待的 Activity 都会无条件启动。

服务端记录仍然在 system_server；应用侧将另外创建 ActivityClientRecord 和真正的 NotesActivity。它们通过 token、Intent、ActivityInfo 和配置等信息对应，不共享同一个 Java 对象。

7.2 LaunchActivityItem 与生命周期目标一起发送

本地实现把“创建 Activity”与“最终走到哪个生命周期状态”放入事务项。普通前台场景通常是 LaunchActivityItem 加 ResumeActivityItem；可见性和是否需要恢复会改变最后一项。

这里的 true 表示要求生命周期管理器立即派发这批事务，便于及时发现发送失败，不表示远端已经执行完。最终仍经 IApplicationThread.scheduleTransaction() 这个 oneway Binder 方法到达应用。

7.3 从客户端记录到 Activity.onCreate

handleLaunchActivity() 进一步调用 performLaunchActivity()。它借助 ClassLoader 和 Instrumentation 实例化 Activity，取得已有 Application，绑定上下文、token、Window 等信息，最后调用 Activity 的创建回调。

对于正常前台、从新建状态走向 RESUMED 的事务，执行器还会补齐启动阶段，再由 ResumeActivityItem 驱动恢复。这就把本例连接成了应用可见的回调顺序：

Application/Provider 绑定初始化 → NotesActivity.onCreate() → onStart() → onResume()。

这条顺序描述本例的正常主线。恢复旧 Activity、已有进程中新建界面、状态保存与多窗口等情形，需要结合实际客户端状态和服务端目标分析，不能从一张冷启动图推出全部生命周期组合。

7.4 onResume 与首帧，仍然是不同观察点

Activity 生命周期推进后，窗口还要经历视图遍历、绘制、缓冲区提交和显示合成等工作。本文没有展开这条渲染管线，因此不把某个生命周期返回值当成首帧已显示的证明。

观察点 可以支持的结论 仍不能保证
Zygote 返回正 PID 创建请求获得了一个进程结果 特化、attach、绑定或界面已完成
AMS 完成 attach 身份匹配 记录与应用 Binder 接口关联起来 Application 的主线程回调已完成
等待开启时收到完成回连 执行流走过前面的绑定步骤 应用自建后台任务全部结束
Activity 的 onResume() 已返回 该生命周期阶段已经执行 首帧已经显示、内容已加载完
首帧显示指标 已到达初次显示观察点 列表数据、图片等异步内容全部就绪
应用报告完全绘制 应用声明达到所定义的可用状态 所有应用都有统一且正确的报告口径

官方启动性能文档将初次显示时间称为 TTID，将完全显示时间称为 TTFD；后者需要应用在合适时机报告，不能只看 Displayed 就认定业务数据已经准备好。见 App startup time。

8. 用同一个笔记应用推演四种变化

8.1 再次打开界面，为什么没有 Start proc

假设 com.example.notes 已经初始化完成并仍驻留，用户再次进入它。若目标进程可用，就可能直接进入已有进程的 Activity 调度，不再经过 Zygote 创建和 Application 绑定。

接下来是否调用 NotesActivity.onCreate()，还取决于 Activity 是否仍存在、Intent 标志、launch mode 和任务栈状态。进程复用与 Activity 复用是两个判断，不能因为 PID 没变就断言不会创建新 Activity，也不能因为 Activity 重建就断言 Application 一定重建。

8.2 Provider 中做耗时工作，会卡在哪里

假设 NotesProvider.onCreate() 在主线程同步读取一个很大的数据库。Application 对象虽然已经存在，Application.onCreate() 仍要等待 Provider 安装步骤返回。

等待完成回连开启时，AMS 还没有收到正常的 finishAttachApplication()，后续 Activity 启动继续等待；即使关闭这项等待，应用主线程也不能在正在执行的绑定处理尚未返回时，凭空同时消费 Activity 启动消息。

因此应检查应用主线程的 bindApplication 区间及 Provider 内部 trace。只调整 Zygote 预加载，无法直接消除这段应用自己的同步工作。

8.3 将一个 Service 放入 :sync 进程，会发生什么

假设笔记同步 Service 声明在 :sync，而当前只有默认主进程存在。系统寻找的是 com.example.notes:sync 对应的进程记录；默认进程中的 Application 不会自动充当新进程中的那个对象。

新进程通常仍从 ActivityThread.main() 进入，并建立自己的应用运行环境，但后续派发目标是 Service，不要求创建 NotesActivity。默认进程的静态字段和单例对象也不会因为属于同一个 APK 就与它共享。

本次绑定的 Provider 列表要按实际进程与模式看。不能把默认进程中观察到的 Provider 初始化顺序，直接解释成另一个进程中必然存在同一 Provider 实例。

8.4 Application 启动后台任务，系统会等它结束吗

假设 Application.onCreate() 只启动一个下载任务然后返回。正常绑定继续向前，应用可以完成回连并开始 Activity 生命周期；后台下载是否完成，不是 finishAttachApplication() 的承诺。

如果 Activity 首帧先显示占位界面，随后才显示笔记列表，这可能是正常的异步内容加载。判断“首帧慢”与“内容准备慢”需要不同观察点，不能仅拿 Application.onCreate() 的耗时或一个 PID 来替代。

  2. 强停目标应用，确认目标进程不在，再发起启动。
  3. 保存进程与 Activity 日志，记录新 PID；在应用存活时返回桌面，再启动同一组件，比较 PID 和回调是否重复。

验证 Provider 顺序时，确认测试 Provider 的确位于同一进程且被本次绑定安装。预期能看到 Application 对象构造与上下文绑定先发生，Provider 初始化居中，随后才是 Application 的 onCreate()。若结果不同，先检查进程、模式和采样覆盖，而不是直接归因于“系统乱序”。

10. 分层记忆：主线与查阅细节分开

10.1 L0：先记住三个层次

创建进程让 Linux 进程和运行时存在；绑定应用让它具有应用上下文并完成必要的同步初始化；派发组件才让 Activity、Service 等执行具体任务。首帧显示和业务可用，还需要各自的观察证据。

10.2 L1：应当能自己展开的主干

对本文笔记应用的正常冷启动，应能用自己的话说明：

  1. ATMS 先找可用进程，找不到才向 AMS 转交进程创建请求。
  2. ProcessList 先登记 startSeq 与 pending 记录，再经创建线程把入口、身份和环境交给 Zygote。
  3. 子进程进入 ActivityThread.main()，准备 Looper，带着序号和 IApplicationThread 回连。
  4. AMS 按真实 PID/UID 与序号关联记录，处理“创建结果先到”或“应用回连先到”。
  5. bindApplication 先经过 Binder 接收端，再由主线程创建 Application、安装本次 Provider、调用 Application 回调。
  6. 等待开启时，应用完成回连后系统才继续处理待启动组件；Activity 事务仍要排到应用主线程执行。
  7. Activity 创建与恢复之后，还要用显示和业务指标判断用户看到的结果。

10.3 L2：需要细节时去哪里查

以下路径均位于 frameworks/base。表中 am/、wm/ 分别指 services/core/java/com/android/server/am/ 和 services/core/java/com/android/server/wm/；app/、os/ 指 core/java/android/ 下对应目录。

11. 折叠自测

11.1 基础关系

1. ActivityThread 和 ApplicationThread 分别是不是 Java Thread？

展开参考答案

都不是。前者继承 ClientTransactionHandler，组织应用主线程的入口、消息与事务处理；后者继承 IApplicationThread.Stub，是系统向应用发命令的 Binder 接收实现。执行 main 的线程、Binder 接收线程与这两个 Java 对象要分开理解。回看第 2.1、4.1、5.1 节。

2. 同一个 APK 启动另一个进程，能直接复用默认进程中的 Application 单例吗？

展开参考答案

不能。不同进程有独立的运行环境与对象状态。系统按进程名和 UID 寻找宿主；:sync 进程通常要建立自己的 Application 等上下文，不会共享默认进程的静态字段。回看第 2.1、8.3 节。

3. 异步 startProcessLocked() 返回 true，是否已经有 PID？

展开参考答案

没有这个保证。它可以在把工作投递给 procStart Handler 后立即返回。pending 记录和启动序号已经建立，实际创建结果与 PID 登记在后续路径中完成。回看第 3.1 节。

4. startSeq 是 Zygote 回包中的字段吗？能单独证明回连身份吗？

展开参考答案

不是。普通 Zygote 创建回包携带 PID 和 usingWrapper；startSeq 由 ProcessList 分配，经启动参数进入应用，再随 attach 返回。AMS 还核对 Binder 提供的 PID、UID 与记录状态，序号不是身份密钥。回看第 3.3、4.2 节。

5. bindApplication() 返回，为什么不能证明 Application.onCreate() 已执行？

展开参考答案

因为它属于 oneway Binder 接口，应用接收端还要把 BIND_APPLICATION 投递给主线程。事务提交、入队和业务执行是不同阶段。本地等待配置开启时，还有完成回连来接续后续组件工作。回看第 5.1、6.1 节。

11.2 场景推理

6. 应用 attach 已到达，但 PID 表里没有它，应当直接认定创建失败吗？

展开参考答案

不能。可能是子进程跑得快于创建结果登记。AMS 可按 startSeq 找 pending 记录，核对 UID、序号及有效性后补齐 PID；迟到的结果避免重复登记。如果无法找到合法记录，才进入丢弃回连等失败处理。回看第 4.2、4.3 节。

7. Provider 初始化读到 Application 字段为空，是不是说明 Application 对象尚未创建？

展开参考答案

不一定。常规绑定路径先构造 Application 并绑定上下文，再安装本次 Provider，最后才调用 Application.onCreate()。如果字段只在这个回调里赋值，Provider 可以拿到 Application 对象却仍读到未初始化字段。回看第 5.2、5.3 节。

8. 等待完成回连关闭后，AMS 提前派发 Activity，是否会让它在 Binder 线程上抢先执行 onCreate？

展开参考答案

不会因此改变生命周期回调的执行线程。配置改变系统继续派发的时机，事务到达应用后仍进入主线程消息队列；正在进行的绑定处理不会因为接收到 Binder 请求就自动完成或被生命周期回调并发替代。回看第 5.1、6.2、7.2 节。

9. Application 启动下载任务后正常返回，finishAttach 是否表示笔记列表数据已经下载完成？

展开参考答案

不表示。完成回连只说明执行流走过前面的同步绑定步骤，不等待应用任意创建的后台任务。要分别测量生命周期、首帧和业务内容准备，必要时在合适时机报告完全绘制。回看第 7.4、8.4 节。

10. Settings 的 dump 中 startSeq=14、thread=ApplicationThreadDeferred@...，能推出第 14 次点击时主线程已完成初始化吗？

展开参考答案

不能。序号对应系统记录的一次进程启动，不是点击次数；thread 字段是服务端保存的应用接口包装对象，不是 Linux TID，也不是初始化完成证明。需要结合等待配置、完成回连、主线程 trace 和实际回调判断。回看第 6.1、9.1 节。
