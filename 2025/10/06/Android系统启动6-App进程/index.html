Android 系统启动——App进程

发表于 2025-10-06 | 分类于 Android ， StartUp
字数统计: 3.4k | 阅读时长 ≈ 16

1. 前言

Note

源码与摘录约定：本系列以本地 LineageOS 22.2 / Android 15 源码快照为准，具体实现可能与其他 AOSP 标签不同。代码块首行标出源码相对路径，保留函数或 rc section 及关键分支；... 表示省略的非关键实现，摘录不作为可独立编译的完整代码。

本文涉及：frameworks/base/services/core/java/com/android/server/am、frameworks/base/core/java/android/os、frameworks/base/core/java/com/android/internal/os、frameworks/base/core/java/android/app 与 Zygote JNI。本文从 AMS 决定“需要一个进程”开始，到该进程向 AMS 回连并收到 bindApplication() 为止；Activity、Service、Provider 的具体生命周期由各自的调度路径继续驱动。

这里有三个很重要的分界：

  • 请求创建发生在 system_server 的 ProcessList，不是“ActivityThread 自己启动自己”；
  • fork 成功只说明拿到了 PID，应用还没有 Application、也没有 Activity；
  • attachApplication() 与 bindApplication() 才把新 Java 进程纳入 AMS 管理并赋予应用运行上下文。

2. 谁决定创建：ProcessList.startProcess()

Android 15 的进程创建入口位于 AMS 的 ProcessList。它会根据 hosting 目的、ABI、uid/gid、runtime flags、SELinux seInfo、挂载隔离信息、兼容性变更等组织参数；并不是仅传一个包名或 main class。

2.1 三类 Zygote 路径

路径 选择条件 说明
常规 Zygote 大多数 app Process.start()，走 primary/secondary Zygote 或 USAP pool
App Zygote HostingRecord.usesAppZygote()，如显式启用 App Zygote 的隔离服务 为特定应用创建的子 Zygote；已有 app 相关预加载/隔离边界
WebView Zygote WebView 渲染相关进程 独立的 WebView Zygote，避免污染常规 Zygote

仅声明 android:isolatedProcess 并不能推出一定使用 App Zygote，还需满足 App Zygote 相关配置与托管条件。三者最终都产生应用子进程，但预加载内容、父 Zygote、隔离能力和 process group 创建细节不同。分析 ANR 或启动耗时时必须先确认 HostingRecord 选中了哪条路径。

2.2 数据与存储隔离参数

pkgDataInfoMap、allowlist、bindMountAppsData、bindMountAppStorageDirs 会传给 Zygote native 层，用于应用数据/存储目录的隔离挂载。源码也明确将可能较慢的 prepareStorageDirs() 放在 Process.start() 之后，以避免它阻塞 fork 发起。

这意味着“应用 fork 时一定已完成所有存储目录准备”并不成立；冷启动与 FUSE/用户解锁状态会影响实际时序。

3. system_server 发给 Zygote 的请求

3.1 Process.start() 只是 Java 门面

Process.start() 将大量安全与运行参数转发给单例 ZYGOTE_PROCESS。真正的 socket 通信与参数编码在 ZygoteProcess。

3.2 startViaZygote() 构造 argv

ZygoteProcess 将每项配置显式编码成 Zygote 参数。--runtime-args、--setuid、--setgid、--setgroups 的位置有约束；最后才放入真正 Java 入口。普通 Android 应用的入口通常是 android.app.ActivityThread，后面附加 seq=<startSeq> 用于 AMS 与新进程匹配。

3.3 ABI 选择与 Zygote socket

primary Zygote socket 先被连接并询问 ABI；不匹配才会尝试 secondary socket。primary 不是“永远 64 位”、secondary 也不是“必然 32 位”的源码保证，实际匹配取决于 init 配置和它们回复的 ABI list。

3.4 协议与 USAP fallback

wire protocol 是“参数个数 + 多行参数”。发送前拒绝换行、回车、NUL，避免突破报文边界。USAP pool 启用且策略允许时先尝试 USAP socket；I/O 失败会记录错误并回退到普通 Zygote socket，而不是直接视为应用创建失败。

4. Zygote 接收命令与安全检查

Zygote 的 ZygoteConnection.processCommand() 解析参数后，会处理查询/预加载/USAP 配置等控制命令；普通创建请求不能由客户端自行携带 capabilities，并必须过 UID 与 invoke-with 安全策略。一般 app 由 system_server 发起，满足 fast path 条件时可能批量 forkSimpleApps()；带 wrapper、child zygote 等情形走普通 forkAndSpecialize()。

5. native fork 与进程特化

5.1 Java Hook 与 JNI 入口

5.2 fork 前 FD 表与子进程清理

fork 之前 native 层会检查开放 FD 表；child 关闭 Zygote/USAP 相关 FD，重开或脱离剩余 FD，避免子进程继承 Zygote 的控制 socket 或意外共享描述符。

5.3 SpecializeCommon()：子进程特化

nativeForkAndSpecialize() 计算 capabilities、拼入 USAP/system-server/preload FD 的关闭或忽略列表，然后 child 调用 SpecializeCommon()。后者才执行 UID/GID、SELinux domain、capability、seccomp、挂载和调度等专属化；它不是一个只设置 setuid() 的薄封装。

6. 子进程从 Zygote 栈切换到应用入口

子进程关闭连接 socket，设置进程名；无 wrapper 时由 ZygoteInit.zygoteInit() 完成 runtime 初始化并反射入口。RuntimeInit.applicationInit() 设置 targetSdk 和兼容性变更，再用 findStaticMain() 得到可执行 Runnable，避免把 Zygote 调用链带进应用 main。

7. ActivityThread.main() 回连 AMS

ActivityThread.main() 创建应用主线程 Looper，解析 seq=<startSeq>，创建 ActivityThread，随后由 attach(false, startSeq) 通过 Binder 调用 AMS。还没有调用 Application.onCreate()。

AMS 利用调用方 PID/UID 与 startSeq 验证并找到对应 ProcessRecord，再通过新进程暴露出来的 IApplicationThread 发起 bindApplication()。AMS 发出这次 oneway Binder 调用后，会将记录标为 active、更新 LRU 与 OOM 调整，并继续派发等待中的 Activity/Service 等。

8. bindApplication() 后发生什么

bindApplication() 是 AMS → app 的异步 Binder 回调。ActivityThread 的 ApplicationThread.bindApplication() 将参数封装为 AppBindData，投递 H.BIND_APPLICATION，由主线程 handleBindApplication() 处理。它先准备 LoadedApk、Context 与 Instrumentation，再创建 Application 对象、安装本进程需要的 Provider，最后调用 Application.onCreate()。AMS/ATMS 或 ActiveServices 还会继续发送待启动组件的调度请求。

Important

Application 对象创建与 Application.onCreate() 是两个时刻：常规绑定路径先得到 Application 对象，再安装 Provider，随后调用 Application 的 onCreate()。因此 Provider 初始化可能先于 Application.onCreate()；bindApplication() 的 oneway Binder 调用返回，也不代表应用主线程已经完成初始化。

这里同样不能把“进程启动”简化为 ActivityThread.main()：

  • provider 进程可能先因 ContentProvider 请求被拉起；
  • service、broadcast receiver、instrumentation 的后续调度目标不同；
  • 共享 UID、isolated process、SDK sandbox、App/WebView Zygote 都会改变传入 bind 参数或限制；
  • 启动过程中 OOM adj、进程组、冻结/后台限制等由 AMS 持续调整，fork 时的状态不是终态。

9. 调试路径

  • logcat -b system -s ActivityManager ActivityTaskManager：关注 Start proc、attach、进程死亡、启动超时；应用侧可看 AndroidRuntime、目标进程 tag。
  • Perfetto：查看 Start proc: <name>、PostFork、ActivityThreadMain 与 bindApplication 时间戳，区分“请求到 fork 慢”还是“fork 后绑定慢”。
  • dumpsys activity processes：确认 ProcessRecord、PID、OOM adj 与 pending 状态；dumpsys meminfo <pid> 可辅助检查新进程。
  • ps -A -o PID,PPID,UID,NAME,ARGS：可验证 PPID/UID/进程名，但不能仅凭 PPID 判定必然使用哪种 Zygote 路径。
  • 启动失败应分段定位：socket/ABI/USAP、Zygote 安全策略与 fork、native specialize、attachApplication 匹配、bindApplication 及应用初始化。

10. 记忆与检验

10.1 记忆总结

  1. AMS 的 ProcessList 根据 hosting 类型决定常规、App 或 WebView Zygote 路径；Process.start() 只是常规路径的 Java 门面。
  2. Zygote 参数携带 UID/GID、SELinux、runtime flags、挂载与兼容性配置，远不止入口类名；协议对换行/NUL 有边界校验。
  3. Android 15 允许 USAP 与 fast-fork；USAP I/O 失败会回退普通 Zygote，不要假设每次都由主 Zygote 直接 fork。
  4. native ForkCommon() 管理 FD 与 fork 安全，SpecializeCommon() 完成权限和隔离；fork 成功时应用仍未初始化。
  5. ActivityThread.attach() → AMS bindApplication() 才让进程成为可调度应用，Application.onCreate() 位于其后的应用绑定处理流程。

10.2 自测问题

问题 回答要点
收到 PID，是否已有 Application？ 没有这个保证。还要经过 ActivityThread.main、attach 和 bind。
bindApplication 调用返回，初始化就结束了吗？ 没有。它是 oneway Binder 调用，应用主线程仍需处理绑定消息。
Provider 与 Application.onCreate 谁先执行？ 常规绑定路径先创建 Application 对象，再安装 Provider，最后调用 Application.onCreate。
