Android 系统启动——从开机动画到桌面就绪

发表于 2025-10-08 | 分类于 Android ， StartUp
字数统计: 8.7k | 阅读时长 ≈ 33

1. 动画还在转，系统到底在等什么？

手机冷启动时，开机动画已经播放，Launcher 进程也可能已经出现，屏幕却迟迟没有切到桌面。另一台设备已经显示锁屏，应用仍没有收到 BOOT_COMPLETED。这两种现象都不能只用“启动还没完成”解释：画面生产、窗口就绪、framework 完成和用户解锁，是不同参与者推进的状态。

本篇沿着一个场景展开：一台采用文件级加密、已设置锁屏凭据的普通手机冷启动，系统用户也是前台用户，系统先显示动画，随后允许锁屏或 HOME 画面接管，用户之后再首次解锁。场景用于源码推演；第 8 章另列本次设备采样，二者不混为一次实测。

我们要回答四个问题：

  1. system_server 尚未完成初始化，动画为什么已经能播放？
  2. HOME 启动、Activity idle、窗口绘制完成，分别提供什么信息？
  3. 谁请求动画退出，谁确认它结束，超时又能跳过哪些检查？
  4. PHASE_BOOT_COMPLETED、sys.boot_completed 和开机广播为什么有不同的完成时刻？
《SystemServer 进程》 介绍服务创建与阶段通知；《App 进程》 介绍进程创建、应用绑定和组件派发。本篇从这些机制接到画面交接与启动收尾，不展开 GPU 合成算法、完整 Activity 任务栈策略或厂商 Bootloader 的 Logo 实现。

Note

源码范围：依据本地 LineageOS 源码目录。manifest 默认分支为 lineage-22.2，vendor/lineage/config/version.mk 标识 22.2，build/release/flag_values/ap3a/RELEASE_PLATFORM_VERSION_LAST_STABLE.textproto 标识 Android 15。主要仓库提交为：frameworks/base：f8d852aaaa843b9d74db780bb11d4691b3ceebc0；frameworks/native：a73b37862118479e83dd99ead0b7e48f657d452b；system/core：bcb8623207cf6e7a51876a891d8b7ad3d04fd8c2，核对时均为 detached HEAD。DisplayContent.java、RootWindowContainer.java 有显示容器初始化处的本地日志与注释改动，不涉及本文使用的窗口等待与 HOME 启动方法。

下文代码均为源码节选，添加中文讲解注释；... 表示在原位置省略非关键内容，不能作为独立编译单元。路径相对于上述源码根。版本与设备条件变化时，应重新核对分支，不能把本地实现等同于所有 Android 15 产品。

2. 先分清：谁画动画，谁管理窗口，谁宣布完成

2.1 动画进程和系统服务处在不同位置

绿线表示进程创建，橙色虚线表示属性控制，蓝线表示动画画面提交。图中 AMS、ATMS、WMS 三格都在 system_server 内；surfaceflinger 和 bootanimation 则是 init 管理的独立 native 进程。SurfaceFlinger 发出启动动画的请求，真正创建动画进程的是 init。

参与者 负责的事情 在本篇中的观察点
init 解析 service 定义，处理启动请求，维护服务进程状态 init.svc.surfaceflinger、init.svc.bootanim
SurfaceFlinger 接收图层内容并组织合成、显示提交；发起动画启动请求 Binder 服务、图层、bootFinished()
bootanimation 创建自己的 Surface，用 native 图形接口播放动画 退出属性、动画线程、服务是否仍在运行
ATMS / WMS 前者组织 Activity 与任务，后者管理窗口和显示启用条件 HOME 解析、Activity idle、窗口绘制、mDisplayEnabled
AMS / UserController 前者推进 framework 启动收尾，后者按用户状态推进广播与解锁 完成属性、用户运行状态、广播投递

bootanimation 不需要先成为 Launcher，也不经过 ActivityThread 创建一个 Activity。它只需要显示服务等 native 依赖已经可用，就能建立自己的绘制通路。这解释了为什么动画可以与 system_server 的大量初始化并行。

更早的静态厂商 Logo 可能来自 Bootloader 或其他显示阶段；仅凭屏幕上有一个 Logo，不能判定 bootanim 已经运行。以下“开机动画”专指本地 frameworks/base/cmds/bootanimation 的这条路径。

2.2 “启用显示”不是屏幕第一次通电

动画播放时，显示设备已经能够呈现画面。因此 WMS 后面的 mDisplayEnabled=true 应理解为：WMS 的启动显示门槛已经通过，可以继续正常的窗口与输入协作。它不是物理面板从未亮过到首次点亮的唯一时刻。

同样，HOME 是一种 Activity 入口与任务角色，Launcher 是通常承担这一角色的应用实现。Keyguard 是锁屏界面，SystemUI 承担许多系统界面职责；三者不能合并成一个“桌面进程”。冷启动后先看到锁屏，并不说明 HOME 启动失败。

3.2 动画线程是画面生产者

进程入口先检查是否应禁用动画，再准备 Binder、等待 SurfaceFlinger，最后运行动画线程。

waitForSurfaceFlinger() 在本地实现里通过 servicemanager 查询名为 SurfaceFlinger 的服务，未找到就间隔重试。服务可查到之后，BootAnimation::readyToRun() 查询显示信息、创建 Surface 和 EGL 资源；动画线程向自己的 Surface 提交帧，SurfaceFlinger 再参与合成与显示。

动画文件由 findBootAnimationFile() 按本地配置寻找，不应把网上某个固定路径当成所有设备的唯一来源。threadLoop() 在没有动画文件路径时走内置 Android 动画，否则进入 movie()。本文只跟踪其生命周期，不展开 ZIP 内容格式。

还有两层开关需要分清：SurfaceFlinger 的 debug.sf.boot_animation 决定是否发起这项启动请求；动画程序的 bootAnimationDisabled() 又检查 debug.sf.nobootanimation 及静默启动相关属性。因此“没有动画”既可能是故障，也可能是配置结果，要先核对设备条件。

WMS 不能在画面刚好切换一半时，把“设置退出属性”理解成“进程已经消失”。动画在播放循环中检查该属性：

requestExit() 设置线程退出意愿，并不在这一行直接销毁进程。动画段是否要求完整播放、是否还要淡出、进度段是否走到可结束的位置，都会影响收尾。以 shouldStopPlayingPart() 为例，判断同时包含 exitPending()、!part.playUntilComplete、淡出帧数和进度条件。

4. HOME 启动与 Activity idle，怎样接到显示收尾

4.1 systemReady 发起的是启动工作

AMS 的 systemReady() 在完成启动前准备与 SystemServer 回调后，启动必要的 persistent 应用，再推进初始 Activity。普通非 headless 系统用户走到以下入口：

mAtmInternal 是 system_server 内的本地接口；这一步不是 AMS 跨 Binder 调用另一个“ATMS 进程”。不过后面真正启动应用组件时会跨进程，已有进程可复用，不一定再次 fork。

4.2 HOME 要经过解析和显示区域条件

RootWindowContainer.startHomeOnAllDisplays() 遍历显示屏，再遍历可启动 HOME 的任务显示区域。主 HOME 的常规 Intent 使用 ACTION_MAIN 与 CATEGORY_HOME；次级显示区域可能使用 SECONDARY_HOME。解析结果、用户、设备策略决定具体组件。

这里说明三件事。第一，系统不是把某个 Launcher 类名硬编码为所有产品的首页。第二，startHomeOnAllDisplays() 的名字不保证每个显示屏都能成功启动同一 HOME。第三，返回 true 表示这条路径已提交启动工作，不表示 HOME 已经绘制或响应输入。

首次设置向导、用户选择的桌面、电视或车机的产品实现都会改变实际结果。headless system user 模式下，系统用户通常不承担前台交互，启动用户与前台 HOME 的关系另有编排，不能照搬本篇手机场景的用户 0 假设。

4.3 idle 是应用回报，绘制是另一道检查

Activity 恢复后，ActivityThread 将相关记录加入待报告集合，并通过主线程消息队列的 IdleHandler 回报 activityIdle()。这里的 idle 表示消息队列走到了一个空闲回调点；它不证明后台线程都空闲、网络数据已加载或显示面板已呈现首帧。

服务端 ActivityTaskSupervisor.activityIdleInternal() 会把对应记录的 idle 设为 true。存在有效 Activity 记录时，启动期间所有 resumed Activity 已 idle，或者该次处理来自 idle 超时，会继续检查启动收尾。

5. WMS 的显示门槛：什么条件没过，就继续等

5.1 enableScreenAfterBoot 只是开始尝试

enableScreenAfterBoot() 在锁内将 mSystemBooted 置为 true、隐藏启动消息，并安排 BOOT_TIMEOUT。本地延时是 30 * 1000 * Build.HW_TIMEOUT_MULTIPLIER 毫秒，从这次显示收尾入口计时，不是从按下电源键计时。然后通知策略 systemBooted()，调用 performEnableScreen()。

如果条件暂时不满足，方法可以返回。后续窗口变化通过 enableScreenIfNeededLocked() 向 WMS Handler 发送 ENABLE_SCREEN，动画轮询消息和超时消息也可能让检查再次执行。它是由事件反复推动的状态机，不是一次调用必然走完的长流程。

蓝色实线表示条件通过后继续。橙色虚线框只标出强制路径可以跳过的两项等待；图从“尚未启用显示”的状态开始，源码最前面还有已完成就返回的检查。

5.2 正常路径保留四类独立判断

先看策略，再看窗口，然后请求动画退出、等待服务结束，最后通知 SurfaceFlinger。任何一个提前返回都只说明当前尝试停在那一层，不能直接归因于 Launcher 卡住。

本地 PhoneWindowManager.canDismissBootAnimation() 返回 mDefaultDisplayPolicy.isKeyguardDrawComplete() || mBootAnimationDismissable。在普通启动消息未显示的路径中，WMS 会先经过这项判断。这说明锁屏准备也能影响动画交接，而不是只关注应用窗口。

5.3 窗口检查不等于“所有应用都画好了”

DisplayContent.shouldWaitForSystemDecorWindowsOnBoot() 先跳过不支持系统装饰的非默认显示屏，再检查当前屏幕上的窗口。这里有两层逻辑，不能只读结尾的注释：

  1. 发现可见、未被遮挡且尚未绘制的窗口，就继续等待。
  2. 没有这样的窗口后，再看启动消息、应用、锁屏相关状态和壁纸是否满足当前阶段要求。

haveApp 对应收集到的 TYPE_BASE_APPLICATION，并没有把包名限定为某个 Launcher。haveKeyguard 也不能机械翻译为“锁屏一定已经显示”：本地代码先将 TYPE_NOTIFICATION_SHADE 记为 true，避免尚未附着的锁屏相关窗口无条件阻塞；遇到已绘制的该类窗口时，再查询策略的 isKeyguardDrawnLw()。判断要连同前面的策略门槛一起读。

在贯穿场景中，正常交接可以落在锁屏上，HOME 也可能暂时被覆盖。WMS 要解决的是“现在是否允许结束启动遮挡并推进正常显示”，并不承诺用户已经看到某个桌面的业务内容。

5.4 等待动画与强制显示，分别保证什么

这里的 SystemService 是 android.os.SystemService，用来查询 init service 状态，不是负责 onBootPhase() 的 com.android.server.SystemService 基类。两个同名类出现在同一篇启动文章里，很容易混淆。

此处精确保证的是 bootanim 不再处于 running 状态；它不证明动画成功播放了全部内容。动画被配置禁用或异常退出时，同样不能靠这个布尔值恢复播放历史。

超时处理把 mForceDisplayEnabled 置为 true 后重试。结合第 5.2 节可见，它跳过的是窗口等待和动画运行状态等待；启动状态入口、正常路径的策略判断、SurfaceControl.bootFinished() 成功检查仍然保留。因此不能说“30 秒到就无条件显示桌面”。超时放行也不能作为原有窗口、动画问题已修复的证据。

SurfaceControl.bootFinished() 经 JNI、SurfaceComposerClient 和 Binder 到达 SurfaceFlinger。SurfaceFlinger 会设置自身启动完成状态，等待初始化属性等异步工作，并再次写退出属性。调用成功后，WMS 才记录 wm_boot_animation_done、设置 mDisplayEnabled 并通知 AMS。这不是 GPU 最后一帧已扫描到面板的证明；要讨论实际呈现时刻，还要继续查看图形流水线和呈现时间。

6. AMS 怎样把显示交接接成 framework 与用户的完成事件

6.1 两个布尔字段解决“谁先到”的问题

AMS 可能先收到 finishBooting()，也可能先收到显示侧的完成通知。它用两个字段保存这两件事：mBootAnimationComplete 表示已收到相应完成通知，mCallFinishBooting 表示曾有收尾请求需要续办。

如果收尾请求先到，AMS 记账返回，WMS 通知后续办；如果显示通知先到，先记录完成，之后的 finishBooting() 就能通过门槛。锁保护了检查与字段更新，避免双方对这两项状态形成不一致认识。

注意字段的实际来源：强制显示路径也会通知 AMS。所以 mBootAnimationComplete=true 表示系统的显示收尾流程已经给出通知，不能把它进一步推断成“动画一定正常播放并自然结束”。

6.2 phase、属性与广播是三套不同的通知

信号 面向谁 到达该处能说明什么
PHASE_BOOT_COMPLETED，值为 1000 system_server 内登记的 SystemService 生命周期管理器推进到完成阶段；具体服务仍可能安排异步工作
sys.boot_completed=1 查询属性的系统组件，以及对应的 init 属性触发器 AMS 已执行到设备级完成属性写入处
ACTION_LOCKED_BOOT_COMPLETED 当前符合条件用户的 Direct Boot aware 接收器 用户启动可在凭据存储未解锁时提供部分功能
ACTION_BOOT_COMPLETED 相应用户中符合接收条件的应用 用户解锁相关准备后，系统安排这一用户的开机广播

startBootPhase() 的服务回调与广播队列不是同一机制。这里先调用阶段通知，再写属性，再推进 UserController。如果某个 phase 回调阻塞或抛出致命异常，代码未必能继续到属性写入；如果属性已经写成 1，也仍然不能证明后面的每个广播接收器都已执行。

6.3 用户解锁为什么还能晚很久

设备加密存储 DE 可用于 Direct Boot，凭据加密存储 CE 则依赖相应用户解锁。在常见文件级加密手机上，冷启动后第一次输入凭据使 CE 可用；此后再次熄屏锁屏，不等于 CE 又回到本次开机前的锁定状态。这一概念也可对照 Android 官方 Direct Boot 说明。

本地 UserController 先开放用户解锁，再按用户模式推进：

finishUserBoot() 把用户从 BOOTING 推到 RUNNING_LOCKED，在条件满足时安排 LOCKED_BOOT_COMPLETED，然后尝试解锁。资料用户还受父用户状态影响。“允许尝试解锁”只是解除 framework 的启动限制，并不绕过凭据、存储或用户关系条件。

普通用户后续经过 RUNNING_UNLOCKING、RUNNING_UNLOCKED 等准备。finishUserUnlockedCompleted() 再检查用户是否仍有效、CE 是否已解锁，并处理用户初始化、预创建用户及特定 profile 分支。满足条件后，它构造 ACTION_BOOT_COMPLETED，通过 FgThread.getHandler().post(...) 再交给广播机制。

至此还要区分三个观察点：日志 Posting BOOT_COMPLETED user #... 表示安排发送；系统的广播完成回调表示这次投递处理结束；应用接收器里自行发起的后台任务结束，则需要应用自己的完成证据。应用还必须满足接收权限、组件和用户等条件，不能仅用设备属性替代这些检查。

7. 把同一次冷启动改几个条件，会发生什么

7.1 HOME 已恢复，但壁纸仍未画出

假设前台 Activity 已回报 idle，WMS 策略允许退动画，且产品开启 config_enableWallpaperService 与 config_checkWallpaperAtBoot。如果壁纸仍未绘制，shouldWaitForSystemDecorWindowsOnBoot() 返回 true，正常路径会停在设置退出属性之前。

此时优先查看壁纸窗口及可见未绘制窗口，不能只因为 Launcher 已 onResume() 就认定动画程序有问题。若之后进入强制显示，窗口等待可以被跳过，但策略和 SurfaceFlinger 调用成功条件仍然保留。

7.2 退出请求已发出，动画服务仍在 running

WMS 已把 mBootAnimationStopped 置为 true，动画可能正在完成指定动画段、淡出，也可能卡在绘制或资源处理。正常路径会每隔约 50 ms 重新查询服务状态，而不会因为字段名含有 Stopped 就直接认为进程已结束。

排查时先确认设备确实可读退出属性，再对照 init.svc.bootanim、动画日志和线程 trace。只有请求与运行状态两项证据，尚不足以区分正常收尾耗时和动画线程故障。

7.3 锁屏已经可见，但应用没有收到 BOOT_COMPLETED

在本篇有锁屏凭据的冷启动场景中，这可能完全正常：显示交接与设备级完成已推进，前台用户仍是 RUNNING_LOCKED，CE 尚不可用。Direct Boot aware 接收器可处理锁定启动广播，普通开机广播要等相应用户解锁后的流程。

先核对目标应用属于哪个用户、用户状态及接收器条件，再判断是否为广播异常。不能根据 sys.boot_completed=1 要求所有用户的 BOOT_COMPLETED 同时到达。

7.4 动画消失了，但屏幕不是桌面

可能正显示 Keyguard、设置向导或产品指定的 HOME；也可能 HOME 启动、绘制或任务栈另有问题。动画消失只能帮助缩小显示侧阶段，无法单独确定当前前台组件与用户体验。

此时分别检查 HOME 解析结果、当前任务与 resumed Activity、窗口可见性和用户状态。若要证明“桌面可交互”，还需要对应界面的呈现和输入响应证据，而不是只增加一个完成属性查询。

8. 验证：哪些已经读到，哪些还需要启动过程证据

8.1 已执行：启动完成后的只读状态采样

本次在 2026-10-22 对一台已连接测试设备进行了只读采样。设备报告 Android 15、userdebug、LineageOS 22.2-20261014_113352-UNOFFICIAL-grus，ro.crypto.type=file。这些信息与本文源码属于同一系统系列，但未证明设备镜像与所列提交逐文件一致。

以下为本次命令返回值的摘记，不是冷启动日志，也没有执行重启、切换用户或停止系统服务：

观察入口 实际结果 可以支持的判断
getprop init.svc.surfaceflinger running init 记录显示服务正在运行；不等于帧呈现正常

8.2 可重复的只读命令

属性空输出、字段缺失或权限不足都属于观测限制，应保留原状，不自动补成源码默认值。若只需要定位 HOME，可另用 dumpsys activity activities 对照任务类型、用户与 resumed Activity；它与上面的解析查询回答不同问题。

8.3 未执行：捕获一次完整启动的证据链

本次没有录制完整冷启动 trace，也没有采集首次解锁前后的广播接收器日志。下面是可用于自有测试设备的验证方案；它要求一次计划内重启及启动期日志/trace 采集配置，不应拿重启后的零散 logcat 冒充完整过程。

要比较的阶段 观察入口 预期差异与限制
动画启动与 HOME 启动 SurfaceFlinger、BootAnimation 日志；ActivityManager / ActivityTaskManager 的进程和 Activity 启动记录 两条线可以重叠；有进程日志不代表已有窗口
Activity idle 与窗口等待 activityIdleInternal()、WMS performEnableScreen()；相关 WM_DEBUG_BOOT ProtoLog 能区分应用回报与 WMS 等待原因；普通 logcat 未必启用全部 ProtoLog
请求退出与动画收尾 trace 中 Stop bootanim，动画线程、调度和服务状态 可分析等待区间；强制显示路径会改变正常等待语义
显示交接与 AMS 收尾 wm_boot_animation_done、FinishBooting 是 framework 标记，不能直接等同于物理屏幕第一帧
设备完成与用户广播 用户状态、Posting BOOT_COMPLETED user #...、自有接收器的 action / user / 时间记录 可比较首次解锁前后；接收器后台任务还需独立结束标记

可先读取现存事件缓冲区，例如 adb logcat -b events -d，寻找 wm_boot_animation_done；日志可能早已被覆盖。还要注意时间基准：源码有 uptimeMillis()、elapsedRealtime()，trace 通常也有自己的时间轴，不要把不同基准的数值直接相减。

排障时从最早缺失的证据向前追：没有 HOME 解析结果就先查解析与用户；已有 idle 却没退出请求就查策略和窗口；已请求而服务仍运行就查动画收尾；设备完成但目标用户仍锁定，就继续查用户流程。

9. 分层记忆：先记边界，再记函数

9.1 L0：一句话说明后半程

init 管理显示与动画进程，ATMS 发起 HOME，WMS 等待策略和窗口条件并协调动画退出，AMS 推进设备级完成，UserController 再按用户状态处理广播和解锁。

9.2 L1：能够自己展开的六个连接点

  1. SurfaceFlinger 设置 ctl.start=bootanim，init 才是创建进程的一方。
  2. bootanimation 通过 Surface 生产画面，与 HOME 的应用启动路径并行。
  3. Activity idle 促成启动收尾请求，WMS 仍需独立检查绘制与策略。
  4. 退出请求、服务不再运行、WMS 显示启用是不同状态；超时只跳过部分门槛。
  5. AMS 用完成通知与待续办标志协调先后到达，再推进 phase 和属性。
  6. 设备级完成、用户解锁、广播投递、接收器后台任务完成各有证据。

10. 折叠自测

10.1 基础关系

问题 1：SurfaceFlinger 请求启动动画，为什么不能把 bootanimation 画成它的子进程？

展开参考答案

SurfaceFlinger 通过 ctl.start 发控制请求，init 依据 bootanim service 定义创建进程。业务请求方向与 Linux 进程父子关系不同。回看第 2.1、3.1 节的图和 rc 定义。

问题 2：mBootAnimationStopped=true、init.svc.bootanim=stopped、mDisplayEnabled=true 分别说明什么？

展开参考答案

第一个是 WMS 已发出停止请求；第二个是 init 当前记录动画服务已停止；第三个是 WMS 的显示启用流程已通过相应条件。它们不能互换，强制路径还可能跳过正常的动画等待。回看第 5.2、5.4 节。

问题 3：应用回报 idle，是否足以证明桌面第一帧已出现在面板上？

展开参考答案

不足。idle 来自应用主线程的空闲回调；窗口绘制、SurfaceFlinger 合成与实际呈现还有各自状态。WMS 在收尾入口之后继续检查窗口。回看第 4.3、5.3 节。

问题 4：为什么 finishBooting 先到时不用阻塞等待动画？

展开参考答案

AMS 可以用 mCallFinishBooting 记住待办并返回，让后续 WMS 显示流程继续；收到 bootAnimationComplete() 后再续办。通知先到则先保存 mBootAnimationComplete，之后收尾请求直接通过门槛。回看第 6.1 节。

10.2 场景推理

问题 5：已进入显示超时处理，但策略仍不允许退动画。是否必然立刻显示桌面？怎样验证？

展开参考答案

不必然。在没有启动消息的普通路径上，策略检查位于 mForceDisplayEnabled 控制的等待块之外，仍会提前返回。应查 performBootTimeout()、策略当前状态及后续 performEnableScreen() 的返回位置，而不是只找超时日志。回看第 5.2、5.4 节。

问题 6：属性已为 1、锁屏可见、用户仍为 RUNNING_LOCKED，普通应用没有收到 BOOT_COMPLETED，应先怀疑哪一层？

展开参考答案

先核对用户解锁和接收器条件。设备级完成与用户 CE 解锁不是同一时刻，该现象可能正常。比较目标用户首次解锁前后的状态、广播安排日志和自有接收器记录，才能判断是否存在广播异常。回看第 6.3、7.3、8.3 节。

问题 7：设备采样中退出属性为空、动画服务已 stopped，能否断言 WMS 没有发送退出请求？

展开参考答案

不能。空输出只说明当前 shell 没读到该值，服务快照也不包含历史。要核对属性可见性、设备实现并采集启动期证据。本次没有这些历史证据，因此保留限制。回看第 8.1、8.2 节。
