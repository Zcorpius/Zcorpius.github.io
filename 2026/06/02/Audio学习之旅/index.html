1. 从一次听歌与录音，建立音频系统的全局认识

音乐已经 write() 进去，为什么扬声器还没有出声？导航开始播报，为什么音乐变小了，但播放线程仍在运行？耳机刚被识别到，为什么声音还没切过去？录音对象显示 RECORDING，为什么读到的样本却全是零？

这些现象分别发生在数据供给、播放控制、设备选路和采集授权的不同环节。学习 Android Audio，首先要建立的能力是：把一个用户可感知的现象，拆成可定位的对象、状态、数据流和控制关系。 只背一条从 App 到 HAL 的箭头链，无法解释这些差异。

本篇是整个音频系列的入口，也是一份读完各篇后可以回来复盘的地图。我们沿一个场景展开：

应用 A 播放一段音乐；用户调音量，导航 B 加入；随后插拔耳机；A 又开启麦克风采集。最后，把同样的问题放到低延迟乐器和前后排独立播放的车载系统中。

主线先采用普通 PCM 流：A 的播放参数为 44.1 kHz、双声道、PCM 32 位整数，假设被分配到一个 48 kHz 的普通混音输出；录音请求为 16 kHz、单声道、PCM16，假设输入流为 48 kHz、双声道。这些是教学条件，用来观察格式转换与对象关系，不是 Android 的统一硬件配置，也不是实测结果。

读完本文，应能完成四件事：

  • 画出应用、system_server、audioserver、HAL/设备的边界，说清每个区域负责什么。
  • 分别追踪一段播放 PCM、一段采集 PCM，以及一次音量、焦点或路由请求。
  • 根据自己的问题，选择适合的专栏与源码入口，知道读完后应该验证什么。
  • 把“API 成功、对象活跃、路由选定、数据流动、用户听见”当作不同的证据层次。

2.1. 先分清四个区域

区域 典型对象 主要职责 不应从名字推导出的结论

system_server AudioService、MediaFocusControl、AudioDeviceBroker、播放/录音监控 协调用户音量、焦点、模式、设备状态与系统音频管理 PCM 不需要逐块经过 AudioService
audioserver AudioFlinger、AudioPolicyService/APM；按条件启用的 AAudioService 建立音频通道、组织数据处理、选择输入输出与设备、执行策略 AudioFlinger 与 APS 是不同服务，但同处一个进程

这里的 Codec 若指硬件 codec，是模拟/数字转换等设备部件；媒体层的压缩音频编解码器则负责 AAC、MP3 等内容的编码/解码。两者不能只凭同名合并成一个对象。

AudioPolicyManager 是 AudioPolicyService 使用的策略实现。Java android.media.audiopolicy.AudioPolicy 又是另一种对象：特权组件用它向系统注册动态 mix、焦点或音量策略。源码里都叫“AudioPolicy”，并不代表它们位于同一层、承担同一职责。

2.2. Binder、共享内存与线程分别解决什么

Binder 负责控制关系和对象能力的交接。 客户端申请创建轨道，服务端检查参数、选择资源、返回控制接口和共享内存描述；之后客户端通过控制接口启停轨道。Binder 也承载设备事件、状态通知等操作。

共享内存负责让两端访问音频数据和进度。 普通流的 PCM 不需要每一块都封装成 Binder 事务。播放时应用发布已写入帧，服务端消费；录音时服务端发布采集帧，应用消费。共享状态还需要原子操作、读写位置和等待/唤醒协议，单有一块映射内存并不能保证数据正确。

线程负责在合适的时机继续工作。 Binder 线程处理一次请求，MixerThread、RecordThread 等工作线程维持长期的数据流。start() 改了状态或唤醒了工作线程，不代表这一调用栈已经完成从用户输入到硬件发声的全过程。

这也解释了为什么“共享内存”不能直接翻译为“端到端零拷贝”：应用写入、格式转换、混音、HAL 传输和应用读取仍可能搬运数据。AAudio MMAP 的映射对象与普通 Track 共享环形缓冲也不同，需要单独分析。

3. 先统一词汇：数据规格、用途、对象和位置

3.1. PCM、帧与字节：任何缓冲讨论都要带单位

PCM 描述的是采样值。采样率表示每秒每个声道的采样时刻数；一个 frame 包含同一时刻所有声道的采样值。对于普通线性 PCM：

例如，48 kHz、双声道、PCM16 的一帧为 4 byte，10 ms 是 480 帧、1920 byte，每秒数据量为 192000 byte。这个计算只说明数据规模，不包含协议开销，也不能据此算出扬声器端到端延迟。

A 播放的 PCM32 整数与 PCM float 即使都占 4 byte，数值表示也不同。read(short[]) 的长度是 short 元素数，双声道时两个元素才是一帧；不能拿数组长度直接套入毫秒公式。压缩 offload 数据也不能套用固定“声道数 × 位深”的字节到播放时长换算。

3.2. 音频规格与声音用途是两个维度

概念 回答的问题 在贯穿场景中的例子
AudioFormat 数据怎样表示 44.1 kHz、stereo、PCM32 整数
AudioAttributes / usage 播放内容用来做什么 音乐 MEDIA，导航 ASSISTANCE_NAVIGATION_GUIDANCE
content type 内容性质是什么 MUSIC、SPEECH 等，参与相应控制规则
AudioSource / capture preset 录音希望采用哪种用途与调校 MIC、VOICE_COMMUNICATION 等
device type / address 候选或实际端点是什么 扬声器、USB 输入、车载 BUS 地址
flags / performance mode 希望或获准采用什么能力路径 FAST、direct、MMAP、LOW_LATENCY 等

usage 会成为策略输入，但“声明导航用途”不等于“自动获得焦点并保证媒体 duck”。同样，MIC 不等于某个固定麦克风编号，VOICE_COMMUNICATION 也不保证所有设备都按同一套 DSP 算法处理。

必须把应用请求值、系统协商值和设备实际行为分别记录。客户端要求 44.1 kHz，不代表输出线程和 HAL 都是 44.1 kHz；请求 LOW_LATENCY，不代表一定获得 MMAP。

3.3. Track、线程、流和设备不能一一画等号

一条应用播放对象通常对应一条服务端 Track；多条 Track 可以共享一个 PlaybackThread。线程管理的输出流又可能路由到某个或某组设备。录音侧的一条 RecordThread 也可以服务多条 RecordTrack，但每条轨道的格式、缓冲、消费进度和静音状态可以不同。

在本文假设下，A 的 44.1 kHz 音乐与 B 的 48 kHz 导航可以进入同一个普通混音输出。AudioMixer 对各轨道作必要处理，形成输出时间轴上的结果。它们共享输出资源，不代表两个应用共享一个可随意相互读写的客户端缓冲。

标识 主要定位对象 不要混淆的对象
sessionId 音效会话等关联关系 设备编号、进程 PID
client portId 策略注册的播放/录音 client 所选 device port ID
I/O handle 一个输入或输出流及相关线程 一条 App Track、物理声卡编号
device ID / address 设备端口及可寻址端点 播放 session、车载 zone ID
UID / PID 应用身份与进程 用户 userId、车载音频 zone
录音 riid 录音活动监控身份 每次重建后都固定不变的 portId

一条逻辑录音在恢复后可以继续沿用同一个 Java 对象，但底层 portId 已经换代。因此对比两次 dump，先确认是否仍是同一代通道，再解释字段变化。

3.4. 容量、占用、批次和延迟必须分别理解

缓冲容量表示最多能存多少帧；当前占用表示现在积压了多少；一次 read/write 或 callback 的块长表示应用本轮处理多少；启动阈值、通知量和 HAL burst 又属于其他约束。

以 48 kHz 为例，960 帧容量对应可容纳 20 ms 数据，但里面只有 240 帧时，该队列当前占用量约为 5 ms。这个 5 ms 仍只是一个队列的驻留量估算，后面可能还有混音周期、HAL、DSP、传输和设备缓冲。

增大容量可能提高抗调度抖动能力，也可能容许更多积压；缩小缓冲可能减少排队，也可能增加 underrun/overrun。应该同时观察实际占用、应用调度和错误，而不是把“越小越快”当作独立于设备的公式。

4. 追一次播放：创建、起播和供数是三个动作

4.1. 创建先把需求变成资源

A 在创建 AudioTrack 时提供 format、attributes、容量等要求。Java/JNI/native 客户端完成相应校验与转换，通过 AudioFlinger 的创建接口申请服务端对象。AudioFlinger 调用策略侧的 getOutputForAttr() 取得适合的 output、设备与 client 注册信息，再在相应输出线程上建立 Track，返回控制接口和数据通道。

这里不是简单的“AudioTrack → AudioFlinger → AudioPolicy → HAL”永久串行管道。策略先参与资源选择，工作线程随后持续处理 PCM；当设备或系统状态改变，控制关系又会重新介入。

创建成功说明本轮资源协商和对象建立已经成功，不说明 A 已被激活、数据已经填好，或者用户此刻可以听到声音。

4.2. play 激活轨道，write 持续发布数据

play() 沿客户端控制对象把启动请求交给服务端；服务端将轨道纳入活跃处理。普通流仍要经过就绪判断，包括数据是否达到相应启动要求。write() 则取得可写区域，把数据放入共享缓冲并发布写入进度。

写入返回的正数只说明接受了相应数量的数据。阻塞写可能等空位；非阻塞写可能只接受一部分。应用必须按实际返回值推进偏移，不能假定每次都写满，也不能把返回时刻等同于声学播放时刻。

对于本篇普通 PCM 同步写入，源码里的核心动作就是 obtainBuffer → memcpy → releaseBuffer；其完整循环与短写行为见 AudioTrack 播放链路剖析 第 5、6 章。

4.3. 工作线程按输出节拍消费

MixerThread 在自己的循环中检查活跃轨道是否可处理，向 AudioMixer 提供数据、音量与格式条件，再将结果交给下游 sink。若配置了 FastMixer，普通混音结果可能通过中间通道交给 FastMixer；不能把每个普通输出都简化成 MixerThread 直接调用一次 HAL write。

在 A、B 共用 48 kHz 输出的假设下，A 的 44.1 kHz 数据需要转换到输出时间轴；B 是否仍需格式或声道处理，取决于其实际参数。某个应用缺数时，系统要处理这条轨道的 underrun，不能为了等它而无限阻塞所有正常供数的轨道。

HAL write 或底层写入完成后，数据还可能驻留在设备链路。判断播放完成，需要明确是“写入完成”“系统消费完成”还是“可闻声音结束”。暂停、停止、flush、release 对待数据和对象的方式也不同，不能当成四个同义按钮。

4.4. 回到 A：数据写完但没声音，先拆哪几层

先确认对象初始化与 play 状态，再确认写入返回值和服务端 Track 的活跃/就绪状态；随后看选中了哪个输出、实际设备是什么、音量或 duck/mute 是否生效。若上层证据均正常，再沿 HAL 与设备继续定位。

这条排查顺序分别落到 AudioTrack、AudioFlinger、AudioPolicy 和 AudioService。它们回答的是同一次播放的不同问题。

5. 追一次录音：方向反转，规则并不完全对称

5.1. 创建输入与激活采集各有检查

A 创建 AudioRecord 时声明 source、采样率、格式、声道和容量。native 客户端向 AudioFlinger 申请录音轨道，策略侧通过 getInputForAttr() 选择输入、设备和资源，并结合身份、source、flags 与 mix 等条件检查资格。服务端建立 RecordTrack，客户端接入返回的共享缓冲。

startRecording() 进一步激活采集。服务端的启动需要与 APS 的 startInput() 协作，处理数据交付权限、AppOps、活跃状态、并发采集与路由。构造成功、native 启动成功、Java 进入 RECORDING、得到真实声音，是几个相关但不同的判断。

普通应用的播放焦点与麦克风采集并发属于不同机制。不能用“我已经拿到 audio focus”替代 RECORD_AUDIO 权限，也不能据此推断自己会成为唯一真实采集者。

5.2. 生产者变成服务端，应用负责及时消费

普通采集路径由 RecordThread 持续取得输入数据；存在 FastCapture 时，RecordThread 可能改从 pipe 读入。线程输入缓冲与每条客户端轨道的共享缓冲是两个层次。

在本文假设下，输入是 48 kHz stereo，A 要 16 kHz mono。A 的 RecordTrack 使用自己的 Converter 和 Provider 消费输入并完成必要转换；另一个要 48 kHz stereo 的轨道可以保留不同的处理需求。共享原始输入，不等于先做一次全局重采样再把同一结果分给所有应用。

服务端发布录音数据后，应用的 read() 在本地映射中取得可读区域，并拷贝到目标数组或缓冲。每次 read 不会重新发一条 Binder 命令，要求麦克风“现在采这一块”。阻塞读可能继续等待凑足本次请求，非阻塞读则可能暂时返回 0 或只返回一部分。

5.3. 对照播放，找出不能照搬的规则

维度 普通流播放 普通录音
客户端角色 向共享缓冲生产数据 从共享缓冲消费数据
服务端角色 消费轨道数据并向输出推进 取得输入并向各轨道交付数据
应用跟不上节拍的主要风险 数据供应不足，发生 underrun 消费落后，发生 overrun 或历史数据被覆盖
已激活是否等于可用结果 可能尚未达到启动要求、被静音或路由不符 可能尚无可读帧，或策略交付静音数据
缓冲规则 容量、有效大小、启动阈值等各有用途 最小容量、通知量、read 块长不是同一个数
等待与唤醒 需要看播放方向的条件与水位 不能直接照搬播放的 minimum 阈值解释

尤其是 ServerProxy::releaseBuffer()：录音方向的 !mIsOut 会直接满足唤醒分支条件；mMinimum 不能被解释成“录音必须攒够这么多帧才唤醒”。唤醒位合并、实际 futex 调用和应用 read 是否返回，又是不同层次。

5.4. A 录到全零，与 A 没有读到数据如何区分

read 返回 0，表示本次没有交付样本；返回正数但样本值为零，表示交付了数据，其内容为零。后者可能来自策略静音，也可能来自音源或下游处理，不能仅凭 RMS 为零判定权限原因。

应同时查看录音状态、AudioRecordingConfiguration.isClientSilenced()、实际路由、client/device format 和读取结果。慢消费者可能丢失部分声音，即使累计返回帧数看起来连续；通道恢复也可能维持逻辑位置而留下 PCM 内容缺口。

这些差异在 AudioRecord 采集链路剖析 中展开，尤其是第 5 章的数据/overrun/时间戳、第 7 章的并发策略、第 8 章的恢复。开始录音实验时，可以使用该篇提供的观测类，先固定一种 source 和格式。

6. 控制场景：音乐仍在流动，系统状态已经改变

6.1. 调音量：用户档位经过多层映射

用户按音量加时，系统先判断调哪个 stream 或 volume group、哪个设备，以及是否受到静音、固定音量、用户限制等规则影响。AudioService 管理相关上层状态，向 native 体系应用音量；策略侧再结合 volume group、设备类别、曲线和当前条件计算相应结果。

最终执行可以落在轨道/流增益、硬件设备 gain 或其他产品路径。一次音量键事件不等于“AudioService 把每个 PCM 样本乘一个系数”；用户看到的 index、曲线计算的 dB、硬件 gain 和 App 自身音量也不是一个变量。

回到 A：扬声器媒体音量从 5 调到 6，切到耳机后不一定继续显示同样的数字或产生同样的响度。要分别看音量对象、设备关联、保存状态及实际执行路径。完整过程见 AudioService 剖析 第 4、5 章与 AudioPolicy 剖析 第 9 章。

6.2. 导航插播：焦点结果与播放器行为分开追

B 声明导航用途并请求合适的音频焦点。普通 Android 路径由 AudioService/MediaFocusControl 体系处理焦点请求；请求的 gain 类型、持有者属性、应用状态、系统版本及策略设置会影响结果。

请求结果可能是获准、延迟或拒绝。A 的响应也可能是应用自行暂停、应用自行降低音量，或者系统在符合条件时执行 duck/fade。没有收到应用层 duck 回调，不足以证明音乐没有被系统压低。 反过来，拿到焦点也不保证 Track 已经建好或正确供数。

读者应把这段过程拆为：焦点请求与返回 → 仲裁/回调或系统处理 → 播放器状态与增益 → 最终音量。公共应用的焦点使用还受 API 与 target SDK 条件影响，应按目标版本核对 Android 音频焦点文档，不能把某个源码分支的准入条件推广到所有版本。

车载系统可能注册外部焦点策略，由 CarAudio 按 zone 组织仲裁；控制仍通过 framework 的注册与分发关系协作。后文的车载分支会说明为什么“导航压低音乐”不能只靠两个 usage 名称决定。

6.3. 插拔耳机：连接事实、选择结果与实际数据路径

设备连接后，系统先接收到连接事实并维护设备状态，再由策略决定对当前流是否选用该设备、能否复用现有 output、是否要改变路由或让客户端重建。某个设备已经连接，不等于所有活跃流都应该切过去。

拔耳机还可能涉及 AUDIO_BECOMING_NOISY 通知、应用暂停、设备状态更新和路由变化。它们发生在不同执行位置，不能用一次同步方法返回概括全部完成时刻。

分析 A 的耳机切换时，至少对照四类信息：设备是否可用、A 的偏好是什么、策略为 A 选择了什么、当前 Track 实际属于哪个输出与设备。如果记录到旧 output 消失、新 portId 出现，应先判断是否发生了重建，不要把它当成 dump 自相矛盾。

6.4. 通话与服务恢复：状态可以重放，内容未必无缝

setMode() 表达系统音频模式及其拥有者，setCommunicationDevice() 表达通信设备偏好；焦点表达播放协作。它们彼此相关，但不能互相代替。VoIP 应用还需要独立处理 AudioRecord 输入和播放输出，完整的双工延迟与回声消除也需要额外验证。

audioserver 死亡或通道失效后，AudioService 可以恢复相关系统状态，AudioTrack/AudioRecord 或 AAudio 客户端则按照各自机制恢复、重建或上报断开。服务重新可用不等于原始 PCM 无缺口；新通道的格式、容量、设备和 ID 也应重新读取。

学习控制面时，不只追“怎样设进去”，还要追“谁保存状态、谁清理死亡对象、恢复时谁重放”。这三个问题能把音量、模式、动态策略和设备管理串起来。

7. 从普通路径分叉：低延迟、特殊输出与车载音频

7.1. 先问处理路线，再问哪个 API 更快

路线 主要变化 必须保留的边界
普通 PCM 混音 多条轨道按输出节拍转换、混音并交给 sink App 规格可以不同于线程/HAL；客户端共享缓冲仍有容量和调度约束
FAST 播放 / FastCapture 用专门的快速处理路径减少普通链路中的部分工作 接受条件、格式、可用槽位和设备能力有限；请求 flag 不保证获准
direct 输出 采用专门的直接输出线程与适合的输出配置 仍有框架控制和下游处理；不能等同于 AAudio MMAP
压缩 offload 将部分压缩音频处理交给下游能力 数据可能不是 PCM；字节数不再按固定帧宽直接换成播放时长
AAudio MMAP 使用 MMAP endpoint、缓冲映射与时间戳模型；分共享/独占 仍要建链、选路、授权和处理断开；独占的是对应资源，不是整台设备

所以，“所有声音都经过普通 AudioMixer”“FAST 就是 MMAP”“使用 AAudio 就绕过全部 AudioFlinger 管理”都不能作为全局模型。

对于电子琴场景，要先定义延迟从哪里量到哪里：按键事件、合成开始、数据提交、设备消费、声学输出是不同时间点。再记录实际 backend、共享模式、burst、buffer size、callback 块长和 xrun，并分析计算耗时与调度。完整路线见 AAudio / MMAP / 低延迟路径实现剖析。

7.2. AAOS 增加了分区与车辆控制关系

把场景搬到车内：司机听音乐与导航，后排乘客播放电影。此时还要说明这些声音属于哪个 user/UID、哪个 occupant/zone，以及对应哪些设备和音量组。

CarAudioService 根据启用的模式和配置，把这些关系组织为路由、音量与焦点策略。传统动态路由会构建 AudioMix，经 AudioService 注册到 native policy；每个 zone 的焦点由相应对象仲裁。对于 duck/mute 等车辆控制，还可能通过 AudioControl HAL 通知车辆音频域。

Audio HAL 和 AudioControl HAL 是两种不同接口角色。 前者承担音频流及相关配置，后者协作车辆音频控制；不能把每块 PCM 画成从 CarAudioFocus 流经 AudioControl HAL 后再到扬声器。core routing/core volume 等模式也会改变部分管理和执行路径，应先查开关，再追具体调用。

在主区导航压低主区音乐的例子中，若希望后排电影不受影响，需要同时检查 zone/UID 归属、focus 规则、设备地址与实际混音位置。不同 zone 名称不能单独证明底层增益完全隔离；多个用途落到同一个 BUS 后，某些硬件控制的粒度可能覆盖整个设备端点。

7.3. 两份配置解决两个层次的问题

配置或对象 主要表达 不能单独证明什么
audio_policy_configuration.xml 及实际 HAL 配置 模块、mixPort、profile、devicePort、允许连接等能力与拓扑 某应用此刻正在走哪条 route
car_audio_configuration.xml zone、context、设备地址、音量组等车载组织 某 BUS 必然对应唯一物理扬声器，或 HAL 已正确接通
运行时 AudioMix / policy 选择 给定 attributes、身份、设备状态下的匹配与选路 声音已经成功经过 DSP/功放并可闻

配置中的 source/sink 是连接角色；AudioRecord 的 AudioSource 是采集用途。这两个 source 不能混读。输出时 mixPort 常是连接的 source、devicePort 是 sink；输入方向则要重新按连接方向判断。

BUS 地址是跨配置与实现关联端点的重要标识，不是可以脱离 HAL 随意改写的注释。源码文件名、构建安装后的路径和运行时实际加载的文件也要分别确认。学习配置时可进入 Audio车载音频policy配置剖析，再与 CarAudio 车载音频架构剖析 的初始化、路由和音量章节交叉阅读。

7.4. Usage 扩展放在理解现有模型之后

前后排独立播放不天然要求新增 usage。已有 usage、user/zone 映射、设备亲和和动态路由是否已经足够，应先结合产品需求确认。否则，新增一个枚举可能只是把应由身份和分区表达的问题硬塞进用途字段。

确实需要项目定制时，再沿 Audio Usage 新增流程梳理 检查定义、转换、校验、策略映射、车载 context/focus、配置和 HAL 的衔接。该篇的 MEDIA_FRONT/MEDIA_REAR、XSD 路径、BUS/PAL 处理属于具体项目的扩展示例；不能当作所有 Android 分支的固定修改清单。

尤其不能只加 Java 常量就认为整条链路已接通。还要确认 native/AIDL 表达是否一致、系统校验是否接受、策略是否匹配、配置是否被加载、HAL 是否识别地址，以及实际设备是否表现为预期结果。

8.3. 根据工作目标选择入口

  • 做播放器或录音应用：先读 AudioTrack/AudioRecord 的参数、生命周期和验证章节，再按问题补 AudioFlinger 与 AudioService。第一份产出应是稳定的观测程序和参数记录。
  • 做 Framework 排障：先串起 AudioTrack → AudioFlinger → AudioPolicy → AudioService，然后选一条录音或重路由流程，练习跨三份 dump 关联对象。
  • 做实时音频：先掌握普通流和时间单位，再读 AAudio。第一轮只改变一个缓冲或调度条件，同时记录实际后端及 xrun，避免把设备差异归因于 API 名称。
  • 做 AAOS 集成：先补齐 AudioService/AudioPolicy，再读 CarAudio 与配置篇，最后考虑 Usage 扩展。第一份产出是 usage、UID/user/zone、context、group、address、HAL 端点的映射表。

不同路线最终会汇合到同一个要求：能把一次行为解释到具体对象与证据，而不是只知道应搜索哪个类名。

9. 把学习变成验证：用同一个场景关联三层证据

以下实验均为待在目标设备执行的方案。先确认调试权限、系统构建和测试应用状态；只读快照不需要修改系统音频属性。每轮固定音源、参数与应用身份，只改变一个条件。

9.2. 四轮入门实验，把主线接起来

实验一：播放参数与输出参数。 用固定参数播放 A，记录实际写入量、session、Track 所属线程、线程和输出格式。若 A 为 44.1 kHz、输出为 48 kHz，结合对象关系追到转换位置；若设备直接选了 44.1 kHz 输出，则记录“本轮未触发假设的采样率转换”，不要为了符合教材而改写观察。

实验二：导航插播与音量变化。 让 B 使用明确的 attributes 和焦点请求，记录请求返回值、A 的回调/播放器状态、焦点状态和可能的 duck/fade 信息。比较播放是否暂停、数据是否继续消费、声音是否变轻。该实验可区分几种执行机制；仅凭听感无法确定是谁改了增益。

实验三：设备切换。 保持 A 播放，连接再移除一个受控输出设备。记录连接事件、应用路由回调、policy 中设备和 output、Flinger 中 Track/线程的前后变化。若底层对象换代，应重新关联 ID，并记录可能的短暂缺口；接口返回成功不作为“所有后续切换完成”的唯一时刻。

实验四：录音数据与静音状态。 在权限和前台条件满足时启动 A 的 AudioRecord，记录返回元素数、RMS/零样本比例、silenced、client/device format 和实际路由。再选择一个已知会影响录音资格或并发状态的受控条件，观察是否拒绝启动、配置变化或交付静音。不同系统的结果可能不同，应先记录条件，再回查策略分支。

第一轮不必同时打开两个录音应用、改 source、切设备又修改缓冲。把变量拆开后，才有可能判断变化由哪个机制引起。AudioRecord 篇的 CaptureProbe.java 可作为采集观测入口，其编译状态与未执行的设备验证已在该篇说明。

9.3. 进阶实验：慢线程、低延迟与车载分区

目标 改变的条件 应观察的差异 结论边界
播放 underrun 在测试供数线程中安排一次明确的延迟 实际写入节奏、缺数信息、Track 状态、听感/输出样本 不能只因某次 write 很快就认定此前未缺数
录音 overrun 对同一录音做一次可控停读 内容连续性、输入/轨道状态、读回结果与相关日志 累计返回帧数连续不证明 PCM 无丢失
AAudio 低延迟 固定实际 backend 与设备，单独改变 buffer size 或回调负载 xrun、callback 时间、调度、时间戳及测量延迟 不同 backend/设备之间的差异不能只归因于一个缓冲参数
AAOS 分区隔离 保持后排电影，主区启动/停止导航 各区焦点、UID/user/zone 映射、duck 地址、gain 与实际输出 zone 名称和 XML 存在都不能单独证明物理隔离

trace 用来回答“线程在哪里耗时、何时可运行、何时真正被调度”等问题。时间戳估算要注明 clock/timebase 和位置所在层级；端到端可闻延迟仍需要明确的测量基准或 loopback。不要把应用 write() 的执行耗时当成全部音频延迟。

9.4. 根据现象选择下一篇，而不是盲目翻整棵源码

现象 优先分辨 主要入口
初始化失败 参数、资格、输入输出能力、资源及实际错误码 AudioTrack / AudioRecord → AudioPolicy
write 返回正数但没声音 是否起播/就绪、实际 route、增益、下游状态 AudioTrack → AudioFlinger；随后 AudioPolicy / AudioService
read 正数且全零 音源、silenced、AppOps/并发、设备/处理 AudioRecord → AudioService 监控 → AudioPolicy
导航没压低音乐，或后排也变小 focus 请求/结果、duck 执行者、zone 与设备粒度 AudioService；AAOS 再看 CarAudio
切设备后仍在旧端点或出现断流 连接、偏好、策略选择、对象换代与恢复 AudioService → AudioPolicy → 对应客户端
周期性卡顿或缺口 供数/消费速度、实际缓冲、线程调度与下游节拍 AudioTrack / AudioRecord → AudioFlinger；AAudio 看时钟模型
新 BUS 或自定义 usage 不生效 定义转换、规则匹配、安装/加载配置、HAL 地址实现 CarAudio + 配置篇 + Usage 扩展篇
普通路径正常，低延迟模式异常 实际 FAST/MMAP/Legacy 路线、格式与能力准入、xrun AAudio + AudioFlinger
