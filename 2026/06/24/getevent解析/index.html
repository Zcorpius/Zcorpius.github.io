getEvent 解析

发表于 2026-06-24 | 分类于 input
字数统计: 7.8k | 阅读时长 ≈ 37

1. 前言

分析 Input 服务绕不开 getevent。它是 EventHub 之前、内核之后唯一的可读窗口——按压一下屏幕，从内核到 View.onTouchEvent 中间穿越的所有数据，第一个能让”亲眼看见”的地方就是 getevent。

对于 getevent ，不仅要会使用，最好也得分析一下源码、知道它输出的每一列到底代表什么、以及和 injectInputEvent 的本质区别。

2. getevent 是什么

2.1 定义

getevent 是 Android 系统自带的一个命令行工具，用于实时读取并打印 /dev/input/event* 设备节点上的输入事件流。

它的位置：

它是 toolbox 里的一个 applet（与 ls、cat 等编译在一起），通过 getevent_main 函数暴露。

2.1 在输入子系统中的位置

关键认知：getevent 与 EventHub（frameworks/native/services/inputflinger/reader/EventHub.cpp）读的是同一个东西——/dev/input/event*。两者都通过 read() 系统调用读取 struct input_event 结构体。区别仅在于：

  • getevent：读到后打印到终端
  • EventHub：读到后塞给 InputReader → Mapper → InputDispatcher

所以我们在 getevent 看到的，就是 EventHub 看到的。

  • 如果看到 getevent 有事件但应用没收到，问题在 EventHub → Dispatcher 之间；
  • 如果 getevent 都没事件，问题在内核/驱动层。这是 Input 调试最重要的判断分流。

2.3 作用

能做 不能做
列出所有 /dev/input/event* 设备及其能力（按键、绝对坐标…） 看到 injectInputEvent 注入的事件（那是 framework 层，绕过了 /dev/input/event*）
实时监控某个节点的事件流 修改事件（只能读，写用 sendevent）
显示事件的 type/code/value（默认十六进制 / -l 后可读） 跨用户读（需要 input 组权限或 root）
计算事件率（-r） 监控非输入设备（比如 /dev/snd/*）
抓 N 个事件就退出（-c N） 远程调用——必须在设备上（通过 adb shell）

4. 完整选项参考（基于源码）

源码里的 getopt 字符串是 "tns:Sv::dpilqc:rh"。下面是逐个选项的详解，全部来自 system/core/toolbox/getevent.c 的 usage() 函数和 getevent_main() 实现。

4.1 选项速览

选项 单词全称 含义 常用度
-t time 显示时间戳 ★★★★
-n no newline 不打印换行 ★
-s <mask> switch mask 显示指定 bit 的 switch 状态 ★
-S Switch (all) 显示所有 switch 状态（大写 = 全选） ★★
-v [mask] verbosity 详细程度 bitmask ★
-d descriptor 显示 HID 描述符 ★
-p possible events 显示设备可能的事件（能力） ★★★★
-i info 显示所有设备信息 ★★★
-l labels 用可读标签显示 type/code ★★★★★
-q quiet 安静模式（清空 verbosity mask） ★★
-c <count> count 抓 N 个事件就退出 ★★★
-r rate 显示事件接收率 ★★
-h help 帮助 -

命名规律小结：UNIX 传统是”选项字母取自对应英文单词的首字母”。getevent 几乎都遵循这个规律（-t=time、-p=possible、-l=labels …）。唯一需要稍微留意的是 -s 和 -S：小写后接参数（指定 mask），大写不带参数（表示”全部”——这是 GNU/POSIX 工具里常见的约定，比如 ls -R vs ls -r、grep -I vs grep -i）。掌握这个规律，以后看任何工具的 usage() 都能秒猜含义。

4.2 详解

-t : 显示时间戳

时间戳来自 struct input_event.time，是内核时钟（CLOCK_MONOTONIC），不是墙上时间。两个时间戳相减得到事件间延时——分析双击、长按、滑动节流时必备。

-n : 不打印换行

每个事件不换行，所有事件挤成一行（脚本里用）。基本不常用。

-s <mask> / -S : 显示 switch 状态

switch 是一组特殊事件（EV_SW），表示设备状态而非瞬时动作，例如：

  • SW_LID (0x00) — 笔记本盖子合上
  • SW_TABLET_MODE (0x01) — 平板模式
  • SW_HEADPHONE_INSERT (0x02) — 耳机插入
  • SW_MUTE_DEVICE (0x0e) — 硬件静音开关

-s <mask> 只查指定 bit。开关类调试时非常有用。

-v [mask] : 详细程度 bitmask

控制打印哪些信息，bit 含义：

bit 含义
1 errors
2 device path
4 device name
8 device info
16 driver version
32 pos. events
64 device properties

通常用 -i 或 -p 代替，不用算 bit。

-d : 显示 HID 描述符

对于 HID 设备（USB/蓝牙），打印其 HID Report Descriptor。调试蓝牙键盘鼠标、自定义 HID 设备时有用。

-p : 显示设备能力（必学）

不抓事件流，只列出设备支持哪些事件类型、每个 code 的范围（min/max/fuzz/flat/resolution）。

输出：

这是了解一台设备最快速的方法。看到 ABS_MT_POSITION_X max 1080 就知道屏幕宽度，看到 ABS_MT_TRACKING_ID 就知道支持多点触控（Type B 协议）。

-i : 显示所有信息

相当于 -p + 设备 bus/vendor/product/version + properties。第一次拿到设备先跑一次 -i。

-l : 可读标签（永远加这个）

把 0001 0110 00000001 翻译成 EV_KEY BTN_MOUSE 00000001。除非在脚本里，否则永远加 -l。

-q : 安静模式

清空 verbosity mask，不打印开头的设备列表。配合 getevent -lq /dev/input/eventN 只看事件流。

-c <count> : 抓 N 个事件就退出

自动化测试常用。例如抓 10 个事件后退出：

-r : 显示事件率

每隔几秒打印一次 rate N，表示事件接收速率（events/s）。调试触摸屏抖动、过高 report rate、性能问题时有用。

场景 推荐组合

5. 输出格式详解

5.1 默认输出（无 -l）

  • 第 1 列：device path（多设备时才有）
  • 第 2 列：type，4 位十六进制。0001 = EV_KEY，0003 = EV_ABS
  • 第 3 列：code，4 位十六进制。0035 = ABS_MT_POSITION_X
  • 第 4 列：value，8 位十六进制（带符号）。触摸坐标、按键状态等

5.2 带 -l 的可读输出

-l 只影响 type 和 code 的显示，value 仍是十六进制（不是十进制）。

5.3 带 -t 的时间戳

注意：

  1. 这是 monotonic 时钟，不是墙上时间。可以用 adb shell uptime 对照。
  2. 不能直接转成 2026-07-08 10:23:45 这样的时间，但相减能得到时间差。
  3. 设备休眠期间时钟会暂停（除非内核 config 改了）。

5.4 设备列表区块（-p / -i）

设备名（name）是判断节点用途的最快方式：

名字示例 通常对应
"fts_ts" / "goodix_ts" 触摸屏（FocalTech / Goodix）
"qpnp_pon" / "pmic_pon" 电源键
"gpio-keys" GPIO 按键（音量等）
"hall_sensor" 翻盖检测
"accelerometer" 重力传感器（部分通过 input 暴露）
"goldfish_input" emulator 虚拟设备
"msm8998-tlav-snd-card Button" 音频按键

5.5 完整的 value 含义对照

不同 type 下 value 的语义不同：

type value 含义
EV_KEY 0 = 抬起，1 = 按下，2 = repeat（自动重复）
EV_ABS 绝对坐标值（按 code 决定单位：触摸是像素、摇杆是 -32768~32767）
EV_REL 相对位移（鼠标：移动量；滚轮：滚动量）
EV_SYN SYN_REPORT 的 value 通常为 0；SYN_DROPPED 表示内核缓冲区溢出
EV_SW 0 = 关，1 = 开
EV_MSC 杂项数据（扫描码、时间戳等）
EV_LED LED 状态（CapsLock/NumLock）
EV_SND 蜂鸣器/音效
EV_FF 力反馈

A.2 dispatch 机制：toolbox.c 的 60 行魔法

完整的入口逻辑在 system/core/toolbox/toolbox.c：

核心逻辑就 3 步：

  1. argv[0] 是被调用的程序名（比如 /system/bin/getevent）
  2. strrchr(argv[0], '/') 找最后一个 /，取 basename → "getevent"
  3. 在 tools[] 表里查 "getevent"，找到对应函数 getevent_main 调用之

关键洞察：内核 execve 时，软链接的名字会被透传给 argv[0]。所以无论你是 exec("/system/bin/getevent") 还是 exec("/system/bin/toolbox")：

  • 内核找到的实际二进制都是 toolbox
  • 但 argv[0] 不同：前者是 "/system/bin/getevent"，后者是 "/system/bin/toolbox"
  • toolbox 的 main() 用 argv[0] 判断”我是被谁叫起来的”

A.6 这种设计的工程价值

优点 说明
省磁盘 一个二进制 ~100KB，比每个工具独立编译省 5-10 倍（嵌入式系统尤其重要）
省内存 多个工具共享同一二进制时，page cache 只缓存一份
共享代码 各 xxx.c 可共用 helper（虽然当前 toolbox 较少用）
维护简单 X-Macro 让”加新工具”成本极低
对用户透明 getevent 看起来就是个独立命令，用户感受不到 multi-call binary 的存在

A.7 同类设计：BusyBox / toybox

这套模式在 Linux 世界非常经典，有个专门的术语叫 multi-call binary：

项目 用途
BusyBox 嵌入式 Linux 的”瑞士军刀”，100+ 命令编译进一个二进制（ls/cp/cat/vi…）
toybox Android 5.0+ 大量 shell 命令的实现（ls/grep/awk…），替代 BusyBox（因 license 争议）
toolbox Android 自家的 multi-call binary，目前只剩 getevent/getprop/start/stop/modprobe/setprop 这些 Android 特有的命令
util-linux 部分工具也用类似模式

历史脉络：早期 Android 几乎所有 shell 命令都是 toolbox 实现，后来逐步被 toybox 替代，现在 toolbox 只保留 Android 特有的命令（getevent/getprop 这些是 Android 独有概念，toybox 没必要实现）。

A.9 一句话总结

toolbox 是一个 multi-call binary——把多个工具（getevent/getprop 等）打包进同一个二进制文件，通过 argv[0] + 软链接 + dispatch 表 决定执行哪个功能。新增工具只要在 tools.h 加一行 + 写一个 xxx.c 暴露 xxx_main，剩下的 X-Macro 自动处理。

这是嵌入式系统节省存储和内存的经典设计，BusyBox、toybox 都用同一套范式。Linux 内核 execve 时不修改 argv[0]，正是这种设计能成立的基础——软链接只是路径解析层面的”障眼法”，进程拿到的 argv 完全保留。
