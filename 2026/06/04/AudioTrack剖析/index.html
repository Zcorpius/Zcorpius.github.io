AudioTrack 播放链路剖析

发表于 2026-06-04 | 分类于 Audio ， AudioTrack
字数统计: 20.5k | 阅读时长 ≈ 89

1. 概述

应用常见的音频操作包括播放（AudioTrack）与录音（AudioRecord）。在 Framework 中，与这两条通路密切相关的组件包括：

  • AudioTrack 与 AudioRecord : 这两个类属于 Audio 系统对外提供的 API 类，通过它们可以完成 Android 平台上音频数据的输出与采集。
  • AudioFlinger : 这是 Audio 系统的工作引擎，管理着系统中的输入输出音频流，并承担着音频数据的混音，以及读写 Audio 硬件等工作以实现数据的输入输出功能。
  • AudioPolicy : 这是 Audio 系统的策略控制中心，具体掌握系统的声音设备的选择与切换、音量控制等功能。

Tip

Android 中的 Audio 系统经过不断的迭代可谓是相当复杂了，最好的学习方法就是边干边学，在工作中通过功能与问题进行驱动，更有针对性的进行串联学习。但是，万物皆有普遍性与特殊性，想要以不变应万变，还是得将架构的普遍性抽象出来，将主要流程与框架进行详细整理。

2. AudioTrack 简介

AudioTrack 是 Audio 系统对外提供的 API 类，在 Java 层 与 Native 层均有对应的类。 Java 层的 AudioTrack 是 Android 为 Java 应用提供音频数据输出 的核心 API，本文以 PCM 播放为主线。它处于 Java Framework 层，是应用与底层音频系统之间的桥梁。其设计定位可以从三个维度理解：

  1. 数据维度 — PCM 数据推送器：应用通过 write() 系列 API 将 PCM 音频数据”推送”到音频输出端。AudioTrack 不负责解码，普通播放输入已经解码的 PCM；设备与路由支持时，也可使用压缩 offload 或 direct/passthrough 路径，不能把压缩输入只归入 offload。
  2. 控制维度 — 传输控制器：通过 play() / pause() / stop() / flush() 控制音频播放生命周期，通过 setVolume() / setPlaybackRate() 等控制播放参数。
  3. 事件维度 — 双向通信枢纽：Java → Native 通过 JNI native 方法调用；Native → Java 通过 postEventFromNative() 静态回调将底层事件（位置通知、路由变更、offload 流事件等）分发到 Java 层回调接口。

AudioTrack 类定义与继承关系如下。继承自 PlayerBase 抽象类，实现了 AudioRouting 与 VolumeAutomation 接口。

  • PlayerBase (抽象基类)：提供播放器通用能力。
    • 音量控制（playerSetVolume）
    • 播放状态通知（baseStart/baseStop/basePause）
    • PlayerIId 注册（向 AudioService 注册以支持焦点/ducking）
    • VolumeShaper 支持
  • AudioRouting (接口)：音频路由控制，设置/获取首选设备、路由变更监听
  • VolumeAutomation (接口)：自动化音量曲线控制，通过 VolumeShaper 实现渐入渐出/ducking

2.1. pcm 简介

声音在自然界中是连续的模拟信号（空气压力随时间变化的波形）。计算机只能处理离散的数字信号（0 和 1）。PCM（Pulse Code Modulation，脉冲编码调制）就是连接这两者的桥梁。PCM是数字音频中最基础、最核心的编码方式。通过三个步骤将模拟声音数字化：

Note

模拟声波 → [采样] → [量化] → [编码] → 数字 PCM 数据

PCM 数据本质上是一个一维数组，每个数值代表声波在某一时刻的瞬时气压偏移量。当这些数值按时间顺序播放时，DAC（数模转换器）将其还原为连续的电压变化，驱动扬声器振动，就听到了声音。

Note

时间: 0ms 0.02ms 0.04ms 0.06ms … (44100Hz = 每 0.0227ms 一个点)

振幅: 120 -45 230 -180 … (16bit 范围: -32768 ~ 32767)

采样、量化、编码是数字化步骤；采样率、位深、声道数是描述 PCM 的三个核心参数。 多声道 PCM 的一帧包含同一采样时刻的各声道样本，通常按声道交错存放。

Tip

想象 PCM 就像用点描绘曲线：

  • 采样率 = 你每隔多密画一个点（点越密，曲线越平滑）
  • 位深 = 每个点的高度精确到多少级（级别越多，曲线越细腻）
  • 声道数 = 同时画几条曲线（单声道一条，立体声两条并行）

44100Hz、16bit 的立体声 PCM，相当于每秒钟在两条曲线上各画 44100 个点，每个点的高度精确到 65536 个等级之一。这就是 CD 音质背后的数字真相。

2.2. 参数三要素与构造映射

PCM 核心参数 AudioTrack 对应参数 常见值 说明
采样率 sampleRateInHz 44100 / 48000 / 96000 每秒采样次数
编码/数值类型 audioFormat ENCODING_PCM_16BIT / ENCODING_PCM_FLOAT 样本的位深及整数/浮点表示
声道数/布局 channelConfig / channelMask CHANNEL_OUT_MONO / CHANNEL_OUT_STEREO / CHANNEL_OUT_5POINT1 决定通道数量和空间布局

Important

AudioTrack 的采样率、编码和声道布局必须准确描述将要写入的数据。声明与实际字节不符时，系统不会自动识别并纠正源格式，可能出现变速变调、噪声、声道错位或静音。只有正确描述输入后，输入格式与输出链路的差异才由受支持的重采样、声道转换等处理。

2.3. sampleRateInHz

sampleRateInHz 描述输入 PCM 的采样率，应首先与源数据一致。只有上游真正完成重采样后，才能把新的数据声明为另一个采样率。

常见值(Hz) 典型来源/场景 建议
8000 窄带语音 仅语音链路使用，不建议音乐播放
16000 宽带语音 语音通话/语音消息常见
44100 音乐内容（CD 系） 音乐场景常见，兼容性高
48000 视频/直播/系统主采样率 很多设备的输出工作采样率，输入仍需按实际数据声明
96000 高采样率内容 按源数据声明；核对输出路径是否接受，以及是否会转换

Important

正确声明的输入采样率与设备工作采样率不一致时，普通混音路径可能进行重采样；direct 等路径还受格式匹配约束。例如把实际 44.1kHz 的样本不作转换就声明为 48kHz，通常会按约 1.088 倍速度解释，不能称为自动重采样。

2.4. channelConfig / channelMask

定义声道布局，旧构造常用 channelConfig，Builder 常用 channelMask。

  • nChannel 表示声道数量
  • channelMask 表示声道布局掩码
概念 典型值 表达内容 常见误区
声道数（nChannel） 1 / 2 / 6 有多少路音频通道 只看数量，不看布局位置
声道布局（channelMask） CHANNEL_OUT_STEREO / CHANNEL_OUT_5POINT1 每个通道对应的物理位置 仅按声道数创建，忽略布局映射

同样是 2 声道，语义也可能不同（立体声或双单声道）；跨模块传递时要明确布局与映射关系。

常见取值 声道数 典型场景 备注
CHANNEL_OUT_MONO 1 语音、低带宽输出 资源占用低
CHANNEL_OUT_STEREO 2 音乐、视频默认输出 最常用，优先选项
CHANNEL_OUT_5POINT1 6 外接设备/家庭影院 需设备真实支持
CHANNEL_OUT_7POINT1_SURROUND 8 高声道设备输出 兼容性要求高

Important

声明的声道数或排列与输入 PCM 不匹配时，可能把一个声道的样本当成另一个声道或另一帧，造成声道错位、噪声等。正确描述输入后，系统才能按已知布局做受支持的声道转换；下混不是修复错误声明的机制。

2.5. audioFormat

audioFormat（或 AudioFormat.Builder.setEncoding(...)）描述写入 AudioTrack 的数据编码类型。在 PCM 场景下，它主要体现位深和数值类型；在直通场景下，它也可表示压缩编码类型。

常见取值 每采样字节 典型场景 兼容性
ENCODING_PCM_8BIT 1 历史兼容场景 现代播放器较少使用
ENCODING_PCM_16BIT(默认) 2 音乐/视频主流场景 兼容性最高，推荐默认
ENCODING_PCM_FLOAT 4 高动态处理链路 带宽高于 16bit；计算开销取决于处理链实现
ENCODING_PCM_24BIT_PACKED 3 高精度 PCM 输入 Java API 31+；输出路径可能转换格式
ENCODING_PCM_32BIT 4 整数处理链路 Java API 31+；输入精度不保证端到端保留

非 PCM 编码通常用于直通/离载播放，是否可用由设备、当前路由及属性等共同决定。ENCODING_IEC61937 表示用于 HDMI/S/PDIF 等的压缩音频封装传输，与 AC3、DTS 这样的压缩编码应区分。

编码类别 常见取值 含义 说明
PCM 编码 ENCODING_PCM_16BIT / ENCODING_PCM_FLOAT 应用写入原始 PCM 数据 常规播放器最常见
压缩编码 ENCODING_AC3 / ENCODING_E_AC3 / ENCODING_DTS 向支持的输出路径提交压缩比特流 依赖设备、路由及系统支持
压缩音频封装 ENCODING_IEC61937 按 IEC 61937 封装传输压缩音频 常见于 HDMI/S/PDIF 等路径

Important

选择格式时先确认上游的数据表示，再检查设备/路由能力。ENCODING_PCM_32BIT 是 32 位有符号整数，ENCODING_PCM_FLOAT 是 IEEE 754 单精度浮点，两者不能仅因都占 4 字节就互换。32BIT/24BIT_PACKED 的公开 Java 编码从 API 31 提供，设备不保证原生支持；较高精度可以经过软件转换。字节数组或 ByteBuffer 还必须使用该编码要求的字节序。

2.6. audio Frame

对于 PCM，一帧是在同一采样时刻所有声道的完整样本集合，frameSize = 每个样本字节数 × 声道数。例如 32 位整数、双声道的帧大小为 4 × 2 = 8 bytes；44.1kHz 表示每秒 44100 帧，而不是把左右声道相加得到 88200 帧。

声卡和音频接口经常用帧表达缓冲容量与位置，但需要先确认接口中的单位：Java write(byte[]) 返回字节数，write(short[]) 返回 short 元素数，write(float[]) 返回 float 元素数；它们都不能直接当作多声道帧数。

本节的乘法公式适用于 PCM。JNI 对 audio_has_proportional_frames(format) 成立的格式按比例计算帧数，IEC61937 也有其比例帧表示；很多其他压缩格式在 AudioTrack 的缓冲接口中把一“帧”按一字节计数，不能拿 PCM 公式或编解码器压缩帧的时长直接套用。

2.7. bufferSizeInBytes：估算、实际缓冲和启动阈值

bufferSizeInBytes 是创建时的缓冲请求。getMinBufferSize() 可以提供 STREAM 模式的创建前估算，但它没有最终的路由和输出设备信息，也不保证在调度负载下持续播放。先检查返回值，再把它作为实验起点。

本地 Java 构造检查要求缓冲大小为正数，并满足当前格式的帧对齐；它不直接执行 bufferSizeInBytes >= getMinBufferSize(...) 这样的比较。普通 PCM STREAM 在服务端创建时会根据所选输出重新计算下限，并可能上调过小的请求。STATIC 则按待装载内容分配静态缓冲，不能套用 STREAM 的估算规则。实际实现见 AudioTrack.java::audioBuffSizeCheck() 与 4.5 节。

要区分的量 含义 如何确认
创建请求 调用方传入的 bufferSizeInBytes 应用记录参数
实际容量 当前 Track 能容纳的最大帧数，可能比请求大 getBufferCapacityInFrames()
有效缓冲大小 当前用于约束可写量的大小，不一定等于全部容量 getBufferSizeInFrames()；支持时用 setBufferSizeInFrames() 调整并检查返回值
启动阈值 调用 play 后开始消费所需的数据量 API 31+ 的 getStartThresholdInFrames() / setStartThresholdInFrames()
当前排队量 已接受但尚未按相应口径消费/呈现的内容 结合成功写入计数、播放位置和有效时间戳分析

缓冲大小可用 PCM 数据量公式估算：bytes = sampleRate × bytesPerSample × channels × durationSec。例如 48kHz / 16bit / 双声道 每秒 192000 字节，40ms 是 7680 字节。这只是对应内容时长的数据量，并不保证请求后就获得 40ms 的端到端延迟。

对应 PCM 时长 数据量（48kHz / 双声道 / 16bit）
20ms 3840 bytes
40ms 7680 bytes
80ms 15360 bytes
120ms 23040 bytes

可以把估算值的 1、2、4 倍作为同一设备上的对照实验，记录实际容量、有效大小、启动阈值、underrun 和测得的延迟。2 倍并非通用最佳值；增大缓冲可能容纳更多排队数据，并影响默认启动等待，减小有效大小则需要更稳定的供数节拍。

延迟来源 需要观察什么
应用解码和缓存 解码耗时、上游缓存量、工作线程调度
AudioTrack 实际排队内容、写入节拍和启动阈值
AudioFlinger 普通/FAST/direct/offload 等路径及处理周期
HAL、驱动和设备 已知硬件缓冲、蓝牙或其他外部链路延迟

这些部分不能无条件套用固定毫秒数后简单相加。需要给出设备、路由、格式、负载、测量起止点及方法，才能讨论“总延迟多少”。时间戳可能含估计值，声学回环测量回答的是另一层问题。

2.8. AudioAttributes

名如其用途：AudioAttributes 是封装描述音频流信息的属性集合的类。AudioAttributes 取代了流类型的概念（AudioManager.STREAM_MUSIC 等）来定义音频播放的行为。对比流类型，应用程序使用 AudioAttributes 可以传达更多信息：

  • usage : “why” you are playing a sound, what is this sound used for。即这个声音是用来做什么的。Usage 信息比 stream 流类型更具表现力，并允许某些平台或路由策略使用此信息来做出更精细的音量或路由决策。
  • content : “what” you are playing。即这个声音正在播放什么。Content 类型表示内容的一般类别。
  • flags : “how” is playback to be affected。即这个声音怎么受影响。

构造 AudioAttributes 时重点是 usage 和 content。

字段 常见取值 典型场景 影响
usage USAGE_MEDIA 音乐、播客、视频 媒体播放默认选择
usage USAGE_GAME 游戏音效/背景音 更贴近游戏策略
usage USAGE_VOICE_COMMUNICATION 通话/实时语音 走语音通信策略
usage USAGE_ALARM 闹钟提醒 受系统提醒策略影响
contentType CONTENT_TYPE_MUSIC 音乐内容 声明内容为音乐，不承诺特定音色处理
contentType CONTENT_TYPE_SPEECH 人声内容 语音内容标识更明确
contentType CONTENT_TYPE_MOVIE 影视内容 声明内容为影视，具体行为取决于策略
contentType CONTENT_TYPE_SONIFICATION 提示音 系统提示类声音

flags 是播放行为提示。下面区分公开 SDK 与平台内部接口；普通应用不能因为在 Framework 源码里看到 public 字段，就认为 SDK 的 android.jar 一定包含它。

flag SDK 可见性（本文基线） 含义与边界
FLAG_HW_AV_SYNC 公开 API 请求硬件音画同步；需要相应输出与数据协议支持
FLAG_AUDIBILITY_ENFORCED 公开 API 强制可听相关策略标志；不是绕过全部系统静音规则的保证
FLAG_SCO @hide 内部兼容旧 STREAM_BLUETOOTH_SCO 的关联标志，不能当普通应用的通用设备选择接口
FLAG_BEACON @hide、@SystemApi 系统级 beacon 可听性/处理策略，普通应用 SDK 不直接开放

应用应按实际用途设置 usage/contentType，并通过适用的公开路由接口请求设备、检查返回值及实际路由。AudioAttributes、首选设备和最终输出设备之间仍要经过策略仲裁。源码位置为 AudioAttributes.java 的 flag 定义及 getFlags()/getAllFlags()。

2.9. mode

取值 含义 典型场景 约束
MODE_STREAM 流式写入，边解码边播放 音乐、播客、直播、长音频 需持续写入和调度线程
MODE_STATIC 先装载再播放，可定位或循环 短音效、提示音 限线性 PCM；每次 write 覆盖目标起点，不能按 STREAM 方式追加

Important

播放器主链路默认使用 MODE_STREAM，除非是短音效才考虑 MODE_STATIC。

2.10. sessionId：共享音效与单条 Track 音量的边界

sessionId 标识音频会话，常用于将 AudioEffect（如均衡器、低音增强、可视化）关联到一组播放对象。Framework 明确支持多个 AudioTrack/MediaPlayer 使用同一已有 session 共享相关音效；这不是 API 误用。

输入 作用 使用边界
AudioManager.AUDIO_SESSION_ID_GENERATE 请求系统分配新会话 无共享需求时适合直接使用
系统生成或已有的有效 sessionId 复用音效会话 需要统一管理音效及策略兼容性；不能随意编造一个正整数

需要分开看三种控制：普通 AudioTrack.setVolume() 更新该 Track 的增益；VolumeShaper 绑定具体播放器/Track 的曲线状态；附着到 session 的 Effect 则可能被同会话的多个播放对象共享。因此，多个对象共同控制一个 Effect 时需要处理控制权及生命周期，而“同 session”本身不能推出每条 Track 的普通音量互相覆盖。

共享也有约束。本地 PlaybackThread::createTrack_l() 检查当前线程已有的外部 Track：若相同 session 使用了不同的路由策略，可能返回 BAD_VALUE，防止后续迁移冲突。AudioFlinger::acquireAudioSessionId()/releaseAudioSessionId() 则对会话持有关系计数；释放一个 Track 不等于无条件销毁其他 Track 仍使用的会话。

原有排障案例可以保留为一个待进一步定位的现象：连续切歌时，两条 Track 共用 session，淡入淡出后出现无声，更换 session 后现象消失。在缺少机型、版本、日志和控制链证据时，只能把独立 session 记为该场景的规避措施。 需要分别核对：对哪条 Track 调了 setVolume/VolumeShaper、是否共同控制同一 Effect、旧对象或音效是否被提前释放、是否有焦点/ducking/静音或路由策略变化，以及厂商实现是否修改了该链路。

没有共享音效需求时可保持各自独立会话；有明确共享需求时应正确管理会话，而不是把“每次创建都换 ID”推广成所有播放器的根治规则。

2.11. streamType（旧接口参数）

旧版构造函数使用 streamType，用于描述声音类型并关联传统流音量控制。

常见取值 典型场景 备注

5. 播放链路：play 与 write 之后发生了什么

第 4 章结束时，客户端与服务端已经通过共享内存和 Proxy 建立了连接，但 Track 仍处于 IDLE，没有任何声音。本章沿 play() 与 write() 两条主线，把两端的行为连接成完整的播放链路；共享内存协议本身的实现细节放到第 6 章。

Note

本章代码基于较新的 AOSP（Android 15/16 系源码）。不同版本间函数名与细节可能存在差异，但骨架与设计是稳定的。

5.1. 总览：数据是被拉取的，不是推送的

先给出贯穿本章的核心认知：AudioFlinger 对音频数据的消费是 pull 模型。write() 只是把数据放进共享内存，不通知任何人；audioserver 的 MixerThread 按音频时钟的节奏，每个周期主动来“拉取”。控制命令与数据分走两条通道：

操作 通道 对端何时感知
write() 写数据 共享内存（零 binder） 服务端下一混音周期 framesReady() 轮询发现
setVolume() / setSampleRate() 共享内存（写 cblk 字段） 服务端下一混音周期读走
setPlaybackRate() 共享内存（PlaybackRateQueue 状态队列） 服务端下一混音周期 poll
play() / pause() binder（另有共享内存标志配合） 立即；唤醒服务端线程
stop() 共享内存写 mStop + binder 读上限立即生效；缓冲内数据继续消费
flush() 共享内存写 mFlush + binder 服务端下一周期丢弃未消费数据

Important

“先 write 后 play” 和 “先 play 后 write” 都能正常出声：play 只负责把 Track 挂进轮询名单并唤醒线程，出声还需要数据水位达到启动阈值（见 4.6 与 6.6）。理解了 pull 模型与两条通道的分工，很多播放时序问题可以直接推理出来。

5.5. 一次 write 实际做了什么

普通 PCM STREAM 的数据从应用写线程，经 JNI 进入 AudioTrack::write()。

  • 客户端在共享环形缓冲中取得可写区，拷贝数据，再发布写入进度。
  • 服务端读取可读区并推进消费位置；空间不足时，阻塞 write 可以等待，非阻塞 write 返回已写入量或无进展结果。

读写位置及 futex 等协调逻辑位于 AudioTrackShared.cpp。

AudioTrack::obtainBuffer() 是 Proxy 之上的薄包装，值得知道它额外做的两件事（节选）：

双端视角把 write 的全貌补齐：

  • 客户端 releaseBuffer() 只推进 mRear，不唤醒服务端——对端是拉模式，无需通知（见 6.4）；
  • 服务端在下一个混音周期的 framesReady() 里自然“看见”新数据；
  • 阻塞 write 的写线程睡在 cblk 的 futex 上，被服务端 ServerProxy::releaseBuffer() 按水位唤醒（默认半缓冲，见 6.4），而不是每帧唤醒。

因此，处理 write 的规则应以返回值为准：正数只代表接受了这些数据，0/WOULD_BLOCK 表示本轮没有推进，其他负数需要按错误处理。输入不是完整帧时，末尾不足一帧的字节也不能靠“再写一次原长度”解决；应由上游保留、补齐或拒绝不合法输入。

三个常见执行者的职责不同：

  • 应用工作线程负责供数；
  • 客户端 AudioTrackThread 在配置了 callback 时处理对应通知；
  • audioserver 中的 PlaybackThread 负责调度服务端 Track。

Java 的位置监听等回调还会经 Handler/Looper 或相应 Executor 分发，不能假定它们都运行在应用写线程上。

flush() 写 mFlush mFront 拉到 mRear 未消费部分全部作废

Important

只有 flush() 真正丢数据；pause() 之后 resume 会从中断处继续。seek 场景的标准做法是 pause() → flush() → 写新数据 → play()。flush() 在 ACTIVE 状态下是空操作，所以顺序不能反。

5.7. 哪一个“完成”允许释放

观察到的事件 已经能说明什么 还不能说明什么
write 返回 N N 个字节/样本已被接口接受，单位由重载决定 这些声音已经从设备输出
普通 PCM 的播放头推进 当前计数口径下服务端消费位置推进 HAL、蓝牙及外设所有缓冲已经排空
有效 AudioTimestamp 到达目标帧，且其时间已到 按系统输出时间戳估计，内容终点已呈现或已承诺呈现 系统未知的外部链路延迟、每个样本实际可闻
stop 返回 停止控制已经发出/状态已经改变 同步等待了所有音频的最终呈现

AudioTrack::getPosition() 在 STOPPED/FLUSHED 状态下返回 0，所以不能先 stop 再等待播放头达到原来的总帧数。Java release() 会释放 native 引用；服务端 PlaybackThread::destroyTrack_l() 将 Track 标记为 terminated，Mixer 的正常消费分支排除 terminated Track。过早释放可能丢弃还未消费的尾部内容。

第 3 章使用时间戳确认内容终点，并且保持 Track 处于播放状态。在最后一小段内容之后追加零值 PCM 静音，是为了让输出和时间戳继续推进；这段静音不参与内容长度统计。若设备长期不给出有效时间戳、路由发生变化或出现失效，则不能把“已经等了一段时间”写成播放成功。示例会超时报错并结束本次尝试，业务播放器需要另行设计恢复、重播和完成通知策略。

AudioTimestamp 是系统的尽力估计，Native 普通路径在可用时使用内核位置，也存在退回服务端位置并按已知延迟校正的情况。它适合这里的接口级完成判断；要验证扬声器或蓝牙接收端实际声学延迟，需要回环测量等额外证据。

5.8. 对象对应关系也有生命周期

创建成功后，客户端 mAudioTrack 持有当前服务端 Track 的 IAudioTrack 接口。在服务失效、路由变化等触发的恢复场景中，restoreTrack_l() 可以再次调用 createTrack_l()，替换远端对象、控制块和 Proxy；它并不保证先前缓冲中的数据全部保留。

所以“一一对应”应理解为当前连接中的对应关系。对 direct/offload、doNotReconnect 等条件，恢复行为还不同。Native 示例显式设置 doNotReconnect=true，由调用方收到失败后决定是否重新开始；Java 普通路径可能在内部恢复，示例的时间戳完成条件不能额外证明期间没有丢帧。本文示例验证固定路由、连续播放的基础行为，不实现媒体播放器的容错状态机。

6. 共享内存与缓冲管理：cblk 协议详解

第 5 章反复引用了 mFront/mRear/mStop/mFlush 与水位、underrun 账本。本章进入 AudioTrackShared.h/.cpp，把这套跨进程协议一次讲透。它由两个进程共同编译（客户端的 libaudioclient 与 audioserver 引同一份实现），协议两端的行为由同一份代码保证一致。

6.1. audio_track_cblk_t：两进程的契约

控制块本体是一段被两端 mmap 的裸内存，定义里刻意排除了虚函数等 C++ 特性（不破坏布局）：

按“谁写、谁读”整理所有权（这是理解并发正确性的钥匙）：

mStop / mFlush 的位打包

mStop 与 mFlush 除了位置，还要传达“又有一次新指令”这一事件信息——因为客户端可能在同一个位置连续 stop 两次。方案是把 32 位拆成 [ 指令计数 ][ 环形偏移 ]：

要点：

  • 低 log2(2×P2) 位是环形偏移（含一位溢出位，用于消歧），高位是指令计数；
  • +increment 恰好只让计数进位、偏移不变，所以“同位置重复指令”也能被服务端察觉；
  • 服务端各自保留 mStopLast / mFlush 本地记录，比较共享值即可检测新指令，全程无锁；
  • 先写 mStop 再写 mFlush，保证服务端读指针不会越过上一次 stop 的边界。

6.3. 客户端 obtainBuffer()：申请一段可写区

ClientProxy::obtainBuffer() 是写路径的核心。去掉等待状态机后，主干是三步：算余量 → 切连续段 → 没有余量则等待：

三个容易忽略的细节：

  • 非连续段。环形缓冲回绕时，可写空间被物理末尾切成两段。obtainBuffer 只返回第一段，剩余长度放在 mNonContig；AudioTrack::write() 的循环会立刻再次 obtain 拿到第二段，调用方无感知。
  • 等待状态机。requested 分为 kNonBlocking（零等待，即非阻塞 write）、有限时长（供 write() 之外的调用方超时控制）、kForever（阻塞 write）。有限等待被切成至多 5 秒一段的 futex 等待，便于及时检查 CBLK_INVALID 等异常，加快服务端故障的感知。
  • futex 协议。睡眠前先原子清除 CBLK_FUTEX_WAKE 再 FUTEX_WAIT——若清除时发现标志已置位，说明唤醒已到，跳过睡眠，避免丢失唤醒；唤醒方则先置标志再 FUTEX_WAKE。这是无锁跨进程唤醒的标准做法。

6.6. 两个水位：有效大小与启动阈值

2.7 节的表格里区分过“有效缓冲大小”和“启动阈值”，这里给出它们在协议里的落点。ServerProxy 构造时两者都初始化为总容量——默认行为是“灌满才开播”：

mBufferSizeInFrames mStartThresholdInFrames
语义 环形缓冲的有效容量：写入不得超过它 启动门槛：缓冲内达到该帧数才开始消费
谁消费 客户端 obtainBuffer 的余量计算 服务端 Track::isReady()（4.6）
调整接口 setBufferSizeInFrames() setStartThresholdInFrames()（API 31+）
钳制规则 [16, frameCount]；下限 16 来自 AudioMixer::BLOCKSIZE 0 或 > frameCount 一律回落为 frameCount
调小的效果 排队上限变小、可写余量提前出现（延迟可控） 更早起播（首帧延迟小）

Important

两个水位解耦是刻意的：把启动阈值调小能加快起播，但不会让小缓冲自动获得抗调度抖动的能力——供数跟不上时的 underrun 仍由账本如实记录。第 3 章示例先取实际缓冲大小、再把阈值设为“内容帧数与缓冲帧数的较小值”，正是在这两个水位的语义边界内工作。

6.7. underrun 的账本与自动重启

underrun 的记账在服务端，账本就在 cblk 里，客户端经 getUnderrunCount() / getUnderrunFrames() 直接读取：

mUnderrunCount 统计的是事件次数（一次连续饥饿算一次），mUnderrunFrames 统计缺帧总量。两条路径会写入账本：prepareTracks_l 的延迟提交（真实混音缺口），以及周期性静音填充时的整周期记账（5.4）。

underrun 持续到重试耗尽会触发禁用与自愈闭环：

所以“写得太慢导致声音断一下、供数恢复后声音自己回来”不是巧合，是协议内建的恢复路径；代价是断点处的一次 underrun 事件永久记入账本。

6.8. MODE_STATIC：没有环形缓冲，只有状态队列

静态模式下数据一次性放在共享缓冲里，没有“生产-消费”流转，mFront/mRear 一整套机制都不适用。客户端到服务端的控制信息改为状态队列（SingleStateQueue）：

为什么用队列而不是字段：position 与 loop 是一组需要原子生效的参数，单字段无法无锁地原子更新；SingleStateQueue 以“单生产者单消费者、单槽+序号”的方式提供了无锁的原子状态传递。客户端 setLoop() / setBufferPosition() 把整个 StaticAudioTrackState push 进队列：

服务端在消费前 pollPosition() 拉取并校验新状态（loop 区间、位置合法性），非法状态直接把 proxy 关停；mPosLoopQueue 反向把“当前播放位置与剩余循环数”异步回报给客户端，getBufferPosition() 优先读它，形成“同步生效”的观感。两端差异总结：

MODE_STREAM MODE_STATIC
数据放置 环形缓冲，持续写入 创建时一次性放好
客户端 → 服务端控制 mRear/mStop/mFlush 计数 mSingleStateQueue（position/loop）
服务端 → 客户端反馈 时间戳队列 + mServer 镜像 mPosLoopQueue（位置与循环数）
播放进度语义 消费到 mFront 的连续计数 缓冲内位置，受 loop 规则约束
flush mFlush 计数 不适用（静态模式 flush 是逻辑错误，直接 fatal）

7.3. 本文边界与延伸

本文以普通 PCM STREAM 播放为主线，刻意没有展开这些相邻主题：

  • AudioMixer 内部：重采样器选择、float 定点混音路径、按 track 的 hook 分派；
  • FastMixer / AUDIO_OUTPUT_FLAG_FAST：低延迟路径的 MonoPipe、AudioTrackThread 的 callback 供数模式（TRANSFER_CALLBACK）；
  • offload / direct / passthrough：压缩数据卸载到 DSP、drain 状态机与 offload 事件回调；
  • AudioPolicy 选路细节：getOutputForAttr() 之后策略如何决定输出线程与设备；
  • 音频焦点与 ducking：VolumeShaper 如何从 prepareTracks_l 的音量合成链生效；
  • AudioRecord：同一套 cblk 协议在采集方向的镜像（mFront/mRear 角色互换）。

这些主题各自成文更合适；本文提供的“两条通道 + pull 模型 + cblk 契约”骨架，可以作为阅读它们的底图。
