AudioTrack 剖析

发表于 2026-06-04 | 分类于 Audio ， AudioTrack
字数统计: 7.2k | 阅读时长 ≈ 32

1. 概述

在平常的使用中，Audio 上层应用的无非两种场景，播放(AudioTrack)与录音(AudioRcorder)。而在 Framework 中，Audio 系统主要的重要组成部分包括三个方面：

  • AudioTrack 与 AudioRcoder : 这两个类属于 Audio 系统对外提供的 API 类，通过它们可以完成 Android 平台上音频数据的输出与采集。
  • AudioFlinger : 这是 Audio 系统的工作引擎，管理着系统中的输入输出音频流，并承担着音频数据的混音，以及读写 Audio 硬件等工作以实现数据的输入输出功能。
  • AudioPolicy : 这是 Audio 系统的策略控制中心，具体掌握系统的声音设备的选择与切换、音量控制等功能。

Tip

Android 中的 Audio 系统经过不断的迭代可谓是相当复杂了，最好的学习方法就是边干边学，在工作中通过功能与问题进行驱动，更有针对性的进行串联学习。但是，万物皆有普遍性与特殊性，想要以不变应万变，还是得将架构的普遍性抽象出来，将主要流程与框架进行详细整理。

2. AudioTrack 简介

AudioTrack 是 Audio 系统对外提供的 API 类，在 Java 层 与 Native 层均有对应的类。 Java 层的AudioTrack 是 Android 为 Java 应用提供 PCM 音频播放 的核心 API。它处于 Java Framework 层，是应用与底层音频系统之间的桥梁。其设计定位可以从三个维度理解：

  1. 数据维度 — PCM 数据推送器：应用通过 write() 系列 API 将 PCM 音频数据”推送”到音频输出端。AudioTrack 不负责解码，输入必须是已经解码的 PCM 数据（或 offload 模式下的压缩数据）。
  2. 控制维度 — 传输控制器：通过 play() / pause() / stop() / flush() 控制音频播放生命周期，通过 setVolume() / setPlaybackRate() 等控制播放参数。
  3. 事件维度 — 双向通信枢纽：Java → Native 通过 JNI native 方法调用；Native → Java 通过 postEventFromNative() 静态回调将底层事件（位置通知、路由变更、offload 流事件等）分发到 Java 层回调接口。

AudioTrack 类定义与继承关系如下。继承与 PlayerBase 抽象类，实现了 AudioRouting 与 VolumeAutomation 接口。

  • PlayerBase (抽象基类)：提供播放器通用能力。
    • 音量控制（playerSetVolume）
    • 播放状态通知（baseStart/baseStop/basePause）
    • PlayerIId 注册（向 AudioService 注册以支持焦点/ducking）
    • VolumeShaper 支持
  • AudioRouting (接口)：音频路由控制，设置/获取首选设备、路由变更监听
  • VolumeAutomation (接口)：自动化音量曲线控制，通过 VolumeShaper 实现渐入渐出/ducking

AudioTrack 是 Android 提供的底层音频播放 API，它的设计就是直接接收 PCM 原始数据，然后交给音频硬件播放。可以先从 pcm 的角度来看。

2.1. pcm 简介

声音在自然界中是连续的模拟信号（空气压力随时间变化的波形）。计算机只能处理离散的数字信号（0 和 1）。PCM（Pulse Code Modulation，脉冲编码调制）就是连接这两者的桥梁。PCM是数字音频中最基础、最核心的编码方式。通过三个步骤将模拟声音数字化：

Note

模拟声波 → [采样] → [量化] → [编码] → 数字 PCM 数据

PCM 数据本质上是一个一维数组，每个数值代表声波在某一时刻的瞬时气压偏移量。当这些数值按时间顺序播放时，DAC（数模转换器）将其还原为连续的电压变化，驱动扬声器振动，就听到了声音。

Note

时间: 0ms 0.02ms 0.04ms 0.06ms … (44100Hz = 每 0.0227ms 一个点)

振幅: 120 -45 230 -180 … (16bit 范围: -32768 ~ 32767)

PCM 有三个核心步骤，分别是采样率、位深、声道数，与 AudioTrack 中的参数有对应。

Tip

想象 PCM 就像用点描绘曲线：

  • 采样率 = 你每隔多密画一个点（点越密，曲线越平滑）
  • 位深 = 每个点的高度精确到多少级（级别越多，曲线越细腻）
  • 声道数 = 同时画几条曲线（单声道一条，立体声两条并行）

44100Hz、16bit 的立体声 PCM，相当于每秒钟在两条曲线上各画 44100 个点，每个点的高度精确到 65536 个等级之一。这就是 CD 音质背后的数字真相。

2.2. 参数三要素与构造映射

PCM 核心参数 AudioTrack 对应参数 常见值 说明
采样率 sampleRateInHz 44100 / 48000 / 96000 每秒采样次数
位深 audioFormat ENCODING_PCM_16BIT / ENCODING_PCM_FLOAT 每个采样点的数据精度
声道数/布局 channelConfig / channelMask CHANNEL_OUT_MONO / CHANNEL_OUT_STEREO / CHANNEL_OUT_5POINT1 决定通道数量和空间布局

Important

这三个参数需要成组匹配；只改其中一个，常见结果是重采样、下混或异常静音。

2.3. sampleRateInHz

sampleRateInHz 常见取值如下，优先与源音频和设备主采样率对齐。

常见值(Hz) 典型来源/场景 建议
8000 窄带语音 仅语音链路使用，不建议音乐播放
16000 宽带语音 语音通话/语音消息常见
44100 音乐内容（CD 系） 音乐场景常见，兼容性高
48000 视频/直播/系统主采样率 Android 设备主流推荐值
96000 Hi-Res 场景 仅在设备和链路都支持时启用

Important

与设备工作采样率不一致时，系统可能触发重采样并引入额外开销。

2.4. channelConfig / channelMask

定义声道布局，旧构造常用 channelConfig，Builder 常用 channelMask。

  • nChannel 表示声道数量
  • channelMask 表示声道布局掩码
概念 典型值 表达内容 常见误区
声道数（nChannel） 2001/2/6 有多少路音频通道 只看数量，不看布局位置
声道布局（channelMask） CHANNEL_OUT_STEREO / CHANNEL_OUT_5POINT1 每个通道对应的物理位置 仅按声道数创建，忽略布局映射

同样是 2 声道，语义也可能不同（立体声或双单声道）；跨模块传递时要明确布局与映射关系。

常见取值 声道数 典型场景 备注
CHANNEL_OUT_MONO 1 语音、低带宽输出 资源占用低
CHANNEL_OUT_STEREO 2 音乐、视频默认输出 最常用，优先选项
CHANNEL_OUT_5POINT1 6 外接设备/家庭影院 需设备真实支持
CHANNEL_OUT_7POINT1_SURROUND 8 高声道设备输出 兼容性要求高

Important

与输入 PCM 声道不匹配时，可能出现声道错位、下混异常或静音。

2.5. audioFormat

audioFormat（或 AudioFormat.setEncoding(...)）描述写入 AudioTrack 的数据编码类型。在 PCM 场景下，它主要体现位深和数值类型；在直通场景下，它也可表示压缩编码类型。

常见取值 每采样字节 典型场景 兼容性
ENCODING_PCM_8BIT 1 历史兼容场景 现代播放器较少使用
ENCODING_PCM_16BIT(默认) 2 音乐/视频主流场景 兼容性最高，推荐默认
ENCODING_PCM_FLOAT 4 高动态处理链路 精度高但带宽和算力成本更高
ENCODING_PCM_24BIT_PACKED 3 高保真输出 机型支持差异较大
ENCODING_PCM_32BIT 4 专业处理链路 需确认端到端支持

非 PCM 编码通常用于直通/离载播放，是否可用由设备能力决定。

编码类别 常见取值 含义 说明
PCM 编码 ENCODING_PCM_16BIT / ENCODING_PCM_FLOAT 应用写入原始 PCM 数据 常规播放器最常见
压缩编码 ENCODING_AC3 / ENCODING_E_AC3 / ENCODING_DTS / ENCODING_IEC61937 向设备直通压缩比特流 依赖 HDMI/外设与系统支持

Important

选择格式时同时看三件事：设备支持、上游解码输出、CPU/带宽成本。

2.6. audio Frame

与 AudioFormat 密切相关的是音频帧的概念，基本用于表示音频数据的最小尺寸完整单元，被用来直观的描述数据量的多少。Frame 的大小就是一个采样点的字节数 * 声道数。比如PCM 32，双声道的1个 Frame 等于 4 * 2 = 8 字节。

Important

在声卡驱动程序中，其内部缓冲区就是采用 Frame 作为单位来分配和管理的。

2.7. bufferSizeInBytes

缓冲区大小没有固定枚举值，通常按 getMinBufferSize(...) 的倍数调优。

Tip

  • 缓冲大小可先用 PCM 数据量公式估算：bytes = sampleRateInHz x (bitDepth / 8) x channels x durationSec。
  • 示例：48kHz/16bit/立体声 每秒约 192000 bytes，则 40ms 约 7680 bytes。
取值策略 经验值 适用场景 风险
最小值 minBuffer 延迟优先实验 最易出现缓冲不足与卡顿
稳定优先 2 x minBuffer 大多数音乐播放 常用平衡点
抖动兜底 4 x minBuffer 低端机/复杂解码链路 时延上升明显
强兜底 > 4 x minBuffer 极端卡顿规避 交互延迟偏大
目标缓冲时长 示例值（48kHz/立体声/16bit） 体验特征
20ms 3840 bytes 低延迟，风险高
40ms 7680 bytes 常见平衡
80ms 15360 bytes 稳定性更好
120ms 23040 bytes 更稳但拖尾明显

对于延迟应按分层模型看，不只盯 bufferSizeInBytes。

延迟分层 典型范围 说明
App Buffer 20~50ms 上层缓存与写入节拍
AudioTrack Buffer 与 bufferSizeInBytes 相关 可通过 minBuffer 倍数调优
AudioFlinger ~20ms 系统混音与调度
Audio HAL/设备 10~50ms 硬件与驱动链路

Tip

  • 经验上总延迟常在 80~200ms 区间，2 x minBuffer 往往是体验与稳定性的平衡点。
  • bufferSizeInBytes 必须大于等于 minBuffer，生产环境建议从 2 x minBuffer 起步。

2.8. AudioAttributes

名如其用途：AudioAttributes 是封装描述音频流信息的属性集合的类。AudioAttributes 取代了流类型的概念（AudioManager.STREAM_MUSIC 等）来定义音频播放的行为。对比流类型，应用程序使用 AudioAttributes 可以传达更多信息：

  • usage : “why” you are playing a sound, what is this sound used for。即这个声音是用来做什么的。Usage 信息比 stream 流类型更具表现力，并允许某些平台或路由策略使用此信息来做出更精细的容量或路由决策。
  • content : “what” you are playing。即这个声音正在播放什么。Content 类型表示内容的一般类别。
  • flags : “how” is playback to be affected。即这个声音怎么受影响。

构造 AudioAttributes 时重点是 usage 和 content。

字段 常见取值 典型场景 影响
usage USAGE_MEDIA 音乐、播客、视频 媒体播放默认选择
usage USAGE_GAME 游戏音效/背景音 更贴近游戏策略
usage USAGE_VOICE_COMMUNICATION 通话/实时语音 走语音通信策略
usage USAGE_ALARM 闹钟提醒 受系统提醒策略影响
contentType CONTENT_TYPE_MUSIC 音乐内容 音色策略更偏音乐
contentType CONTENT_TYPE_SPEECH 人声内容 语音内容标识更明确
contentType CONTENT_TYPE_MOVIE 影视内容 适配视频类内容策略
contentType CONTENT_TYPE_SONIFICATION 提示音 系统提示类声音

flags 是对播放行为的附加提示，默认 0 即可；只有明确场景再设置。

flags 常见值 含义 典型场景 注意点
FLAG_HW_AV_SYNC 请求硬件级音画同步 视频播放、隧道播放 需设备/解码链路支持
FLAG_SCO 倾向走蓝牙 SCO 语音链路 通话/对讲类语音 音质与带宽受限
FLAG_AUDIBILITY_ENFORCED 强制可听策略 系统级提示音 多数三方应用不建议使用
FLAG_BEACON 声音 beacon 提示策略 特定辅助提示场景 使用场景较少

2.9. mode

取值 含义 典型场景 约束
MODE_STREAM 流式写入，边解码边播放 音乐、播客、直播、长音频 需持续写入和调度线程
MODE_STATIC 一次装载后播放 短音效、提示音 不适合长音频，内存占用集中

Important

播放器主链路默认使用 MODE_STREAM，除非是短音效才考虑 MODE_STATIC。

2.10. sessionId（Builder/构造参数）

sessionId 用于标识音频会话，常用于把 AudioEffect（如均衡器、低音增强、可视化）绑定到指定播放链路。

常见取值 含义 典型场景
AudioManager.AUDIO_SESSION_ID_GENERATE 让系统分配新的会话 ID 普通音乐播放默认选择
已有 sessionId（>0） 复用已有会话 多实例共享同一组音效或统一控制

不需要共享音效链路时，优先使用 AUDIO_SESSION_ID_GENERATE，避免手动管理会话冲突。

多个 AudioTrack 使用同一 sessionId 的影响 现象
音效共享 调整一个 Track 的 EQ/低音，另一个也会被影响
参数互相覆盖 多处同时改音效参数，听感会忽强忽弱
生命周期互相牵连 一方重建或释放后，另一方可能出现效果失效

如果没有明确要共享同一套音效的场景，建议每个 AudioTrack 用独立 sessionId 更稳。

Note

线上有用户反馈歌曲在播放过程中，上一首歌正常播放结束到下一首歌后出现了播放无声问题。初步排查问题就是两个AudioTrack对象使用了同一个 sessionid，导致淡入淡出效果触发时，针对AudioTrack设置音量时系统处理异常，导致播放无声。

根本解决方案：每次创建AudioTrack时都要生成新的sessionId。

2.11. streamType（旧接口参数）

旧版构造函数使用有 streamType，用于描述声音类型和音量组。

常见取值 典型场景 备注
STREAM_MUSIC 音乐、视频、播客 最常用，播放器默认选项
STREAM_RING 来电铃声 走铃声音量组
STREAM_ALARM 闹钟提醒 走闹钟音量组
STREAM_NOTIFICATION 通知提示 走通知音量组
STREAM_VOICE_CALL 通话语音 走通话链路策略
STREAM_SYSTEM 系统提示音 系统级提示场景

可把 streamType 视为旧模型，AudioAttributes 视为新模型；新项目优先后者。
