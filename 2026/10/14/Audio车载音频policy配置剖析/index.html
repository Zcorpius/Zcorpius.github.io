1. 文件准备

代号 文件 负责什么
P audio_policy_configuration.xml HAL 模块、流能力、设备端点、允许的连接
C car_audio_configuration_pure.xml 车机音频分区、context 到地址的映射、音量组；根版本为 2
X audio_policy_configuration.xsd 本文实际使用的结构、属性和取值校验规则

P 被安装为 /vendor/etc/audio_policy_configuration.xml，C 被安装为 /vendor/etc/car_audio_configuration.xml。工程里还有 /vendor/etc/audio_ar/ 下的另一套配置；分析设备时，应先确认实际加载路径。源文件叫什么、安装文件叫什么、服务实际读了哪个文件，是三个需要分别确认的问题。

正文默认先讲传统 AAOS 动态 AudioMix 路由，以及由 CarAudioService 调设备 gain 的模式。是否启用这些模式由产品资源配置决定。

2. 声音数据与路由决策

2.1 五个专业名词

词 零基础解释
PCM 用一串数字样本表示声音。普通播放器通常先把 MP3/AAC 等文件解码为 PCM，再交给播放系统
采样率 每秒每个声道有多少个样本。48000 表示 48 kHz
声道 同时传输几路声音，以及每路的含义。立体声通常是左、右两路
流（stream） 持续传输音频数据的一次播放或采集通路；这里的“流”不特指网络直播
用途（usage） App 对声音用途的声明，例如媒体、导航、通话；它与 PCM 数据的采样率、声道是不同维度

Tip

例如“48 kHz、16 位、立体声”的 PCM，在不计协议开销时每秒数据量为：

$$
48000\,\mathrm{s}^{-1} \times 2\,\mathrm{bytes} \times 2 = 192000\,\mathrm{bytes/s}
$$

这个计算帮助理解 profile 描述的是数据规格；它并不告诉系统声音应该去主驾还是副驾。

2.2 数据通路：谁实际搬运声音

下面是普通 PCM 混音播放的简化数据通路：

AudioPolicyManager，简称 APM，负责策略控制：选择设备与输出、判断能力是否匹配、协调开流和建立连接。PCM 不需要先进入 APM，再从 APM 交给 HAL。

direct、压缩 offload、MMAP 等路径与普通混音路径不同，例如 offload 可以把压缩数据交给支持它的 HAL/DSP。上图用于建立普通播放的基本认识，不覆盖所有播放模式。

2.3 控制关系：谁决定声音去哪

两份 XML 回答的问题不同：

  • P：有哪些端口，它们支持什么，允许怎么连？
  • C：某个分区里的某类声音映射到哪个设备地址，归哪个音量组？

Note

例如 P 中 name="media" 只是端口名。系统不会仅靠这个英文名字，自动把 USAGE_MEDIA 的声音送过去。

2.4 水管比喻：用来理解端口与连接

XML 专业名词 名词在音频系统中的具体含义 输出场景下的比喻 准确含义
module 音频 HAL 模块 一套水路的配置单元 对应一个音频 HAL 模块；不一定是一颗独立芯片
mixPort 混音端口（音频流端口） 可以接入音频数据的管道接口 HAL 暴露的输入/输出流 profile，可据此打开实际 I/O 流
devicePort 音频设备端口 出水口 设备端点；录音时它也可以是“进水口”
route 音频路由（端口连接关系） 允许接哪些管子的连接表 声明可行连接，不等于已经打开流或接通硬件
profile 音频能力描述 管径与介质规格 格式、采样率、声道能力
gains 增益能力集合 可调阀门的规格 增益能力与范围；要有框架/车机服务/HAL 实际执行调节

其中 mixPort 描述能打开什么样的音频流，devicePort 描述音频流可以连接到什么设备。的具体区别可以看下表格：

对比项 mixPort devicePort
理解重点 流接口 设备端点
回答的问题 HAL 能提供什么播放/录音流？ 声音送到哪里，或从哪里采集？
典型例子 普通媒体输出、低延迟输出、主录音输 媒体BUS、扬声器、麦克风

把 mixPort、devicePort 分开，是为了表达多对多关系：一个流 profile 可以支持多个设备，一个设备也可以接受多个流 profile。P 主模块有 63 个 mixPort、46 个 devicePort、43 条 route；它们的数量不是一一对应的。

3. 逐步搭建一份最小输出 policy

本章逐步扩展的完整 XML 文件，讨论的 APM 基本配置条件。它们都是教学构造，并非生产配置的直接删减副本。是用于理解单路输出的最小教学文件集。

3.1 基本骨架

这一步先认识三层嵌套：audioPolicyConfiguration → modules → module，以及顶层的音量配置。

  • version="7.0" 指定本文使用的格式版本。
  • name="primary" 用于定位主 HAL 模块；halVersion="3.0" 表示 legacy HAL API 版本标记，不能读成 HIDL 3.0 或“能力越大越强”。
  • speaker_drc_enabled 保留样本写法，含义和本地解析情况见 4.2；不能把它当成启动硬件 DRC 的通用开关。
  • 两个 include 展开为 volumes 区块，使顶层满足本地 XSD 对音量配置的结构要求。

空模块能通过 XSD，是因为模块内部端口区块在 XSD 中可以省略。它仍没有 APM 正常工作的输出条件。

3.2 声明输出设备

这一步只加一个 devicePort。它声明一个名为 Media Bus 的输出端点，地址是 bus00_media_out，能够接受 16 位 PCM、48 kHz、立体声。

属性 本例值 解释
tagName Media Bus 模块内的配置引用名；空格是名字的一部分
role sink 输出设备接收声音，因此是数据汇
type AUDIO_DEVICE_OUT_BUS 可寻址的输出 BUS 设备类型
address bus00_media_out 框架、HAL 与 car 配置用于定位该 BUS 的字符串
profile 16 位 / 48000 / 立体声 此端点声明的音频能力

地址对应哪条物理链路由 HAL 和底层配置实现；XML 中声明一个新字符串，不会自动创建硬件通路。

3.3 声明输出流能力

新增的 mixPort name="media" role="source" 声明一个输出流端口，其 profile 描述的音频能力与设备端点匹配。

属性 本例值 解释
name media 本模块内的流端口引用名；后续输出 route 的 sources 用这个名字引用它
role source 输出流向设备提供声音，因此在连接关系中是数据源；录音用的输入 mixPort 则为 sink
profile 16 位 / 48000 / 立体声 此端点声明的音频能力

表中的 profile.xxx 表示子节点 profile 上的属性，不是直接写在 mixPort 上的属性。这里的 profile 描述流接口的能力；上一节 devicePort 中的 profile 描述设备端点的能力。

现在存在“流接口”和“设备端点”，但还没有声明它们允许相连。name="media" 是后续 route 使用的键，不是 USAGE_MEDIA 的自动路由指令。

尽管先讲设备、后讲流，XML 内仍要按 XSD 顺序把 mixPorts 写在 devicePorts 前面。

3.4 声明允许的连接

新增 <route type="mix" sink="Media Bus" sources="media"/>，声明输出流 media 可以连接到设备 Media Bus。

名词/属性 本例值 解释
routes 包含一条 route 路由集合，集中存放本模块允许的端口连接关系
route 从 media 到 Media Bus 一条路由声明，说明哪些源端口允许连接到某个汇端口；不代表连接已经启用
route.type mix 连接类型；mix 表示允许多源混合连接，但这行配置本身不执行混音，也不保证多个来源同时播放
route.sink Media Bus 数据汇，即连接中接收声音的一端；本例引用输出 devicePort 的 tagName，每条 route 只有一个 sink
route.sources media 数据源列表，即连接中提供声音的一端；本例引用输出 mixPort 的 name，多个来源用逗号分隔

表中的 route.xxx 表示 route 节点上的属性。本例连接关系是 media（输出流端口）→ Media Bus（输出设备端点）；引用的是端口名，不是设备的 address="bus00_media_out"。

Tip

此时仍缺少常驻设备登记、默认输出以及 primary 输出标识，所以标题不能写成“加 route 就能出声”。

3.5 登记设备并标识 primary 输出

本步增加常驻设备清单、默认输出设备和 primary 输出标识：

名词/属性 本例值 解释
attachedDevices 包含一个 item 常驻设备清单，告诉 APM 在初始化时尝试访问哪些设备；不是已验证可用的设备列表
item Media Bus 常驻清单中的一项；节点文本引用 devicePort 的 tagName
defaultOutputDevice Media Bus 默认输出设备；节点文本引用输出 devicePort 的 tagName，该设备仍须通过 HAL 访问而成为可用设备
mixPort.flags AUDIO_OUTPUT_FLAG_PRIMARY 流的特性标记；本例的 PRIMARY 将 media 标识为主输出流候选，供 APM 初始化与选择使用

defaultOutputDevice 指向设备端点，PRIMARY 标记的是输出流端口；两者分别回答“默认用哪个设备”和“哪个流可以作为主输出”。flags 写在 mixPort 上，不写在 devicePort 上。

Note

本地 APM 会打开访问常驻设备所需的输出，并检查默认设备可达；initCheck() 还检查 primary 输出是否存在。登记只是开始尝试，HAL 开流失败时设备仍可能不可用。

3.6 增加设备增益

本步增加gain。保留 name="" 很重要，因为本地 7.0 XSD 要求 gain 有 name 属性，样本使用空字符串也是合法写法。

增益描述对信号强度的放大或衰减。这里的数值单位是毫贝（mB），换算关系为：

$$
100\,\mathrm{mB} = 1\,\mathrm{dB}
$$

属性名中的 MB 不表示兆字节。

名词/属性 本例值 解释
gains 包含一个 gain 增益能力集合；本例放在 devicePort 中，描述该设备端点支持的增益控制
gain 一组增益能力 描述一种增益控制的模式、范围、默认值和步进
gain.name ""（空字符串） 这组增益能力的名称；本例使用空字符串，不用于 route 寻址
gain.mode AUDIO_GAIN_MODE_JOINT 共同调节模式，同一个增益值作用于所有相关声道；本例立体声的左、右声道一起调节
gain.minValueMB -3000 最小增益为 −30 dB，即此级最多衰减 30 dB；不等于完全静音
gain.maxValueMB 0 最大增益为 0 dB，即此级不放大也不衰减；不是“音量为零”
gain.defaultValueMB -1500 声明的默认增益为 −15 dB；实际启动音量还可能被服务保存值、当前限制等覆盖
gain.stepValueMB 100 支持的增益步进为 1 dB；本例范围内的可设值按 −30、−29、…、0 dB 排列

表中的 gain.xxx 都是子节点 gain 上的属性。增益值应处于最小值与最大值之间，并按声明的步进取值；它与界面显示的音量等级（index）不是同一种数值。gain 只是声明可调能力，调节由服务与 HAL 实现。

3.7 把完整示例读成一张表

对象 本例名字/值 引用关系
HAL 模块 primary APM 按模块名请求加载 HAL
输出流 profile media route.sources 引用这个 name
输出设备 Media Bus route.sink、常驻清单、默认输出都引用这个 tagName
BUS 地址 bus00_media_out HAL 寻址；配套 car 配置通过 address 匹配设备
音频能力 PCM16 / 48000 / stereo 同时约束本例的流端口与设备端口
设备 gain −30～0 dB，默认 −15 dB，步进 1 dB 声明设备可调增益能力

读取顺序是 设备 → 流 → route → 登记 → 增益，写入顺序由 XSD 决定。记住这张表后，再看真实文件只是规模变大，而不是每条真实通路都必然等同于本例。

4.2 globalConfiguration：声明与实际解析

其中 DRC 是动态范围压缩，通常用来改变强弱声音之间的动态范围；这个 legacy 配置项与扬声器路径的 DRC 声明有关。

Note

注意，不能仅凭这一个字段判断已开启硬件/软件压缩器。 本地 Serializer.cpp 的 GlobalConfigTraits 和全局配置反序列化函数只处理 call_screen_mode_supported、engine_library，没有在此读取 speaker_drc_enabled。

本地 XSD 仍要求该属性存在，所以教学示例保留它。要确定产品 DRC 效果，还要查当前分支其他消费者、音效配置、HAL/DSP 实现和实际测试。

4.3 module：与 HAL 模块对应

属性 XSD 要求 含义
name 必填 请求加载的 HAL 模块名，例如 primary、a2dp、usb、r_submix
halVersion 必填 描述 legacy HAL API 版本，HIDL/AIDL 版本另有机制

APM 按 name 调用加载 HAL 的接口。名字不匹配或 HAL 不存在时，模块可能加载失败，端口也无法正常用于开流；最终行为还受其他模块和回退机制影响，不能一概断言 audioserver 必然启动失败。

Tip

模块的配置常驻，不等于它的所有设备永远可用：USB、蓝牙设备连接状态通常动态变化。

4.4 mixPort：描述可打开的 HAL I/O 流

属性/子节点 XSD 要求 使用时怎样理解
name 必填 模块内的流端口引用名；保持与设备 tagName 不重名，以免 route 解析歧义
role 必填 输出 mixPort 为 source，输入 mixPort 为 sink
flags 可选 流特性、处理模式与能力标记，有些影响优先选择，有些参与硬匹配
maxOpenCount 可选 该 profile 可同时打开的 HAL I/O 流数量上限
maxActiveCount 可选 该 profile 可同时激活的 HAL I/O 流数量上限，输入也适用
profile 可选，可多个 音频能力；省略时本地解析器建立动态 profile，仍需从 HAL 获得能力
gains 可选 XSD 也允许 mixPort 声明 gain；本教程主要讨论 devicePort 的 gain

mixPort 本身是配置描述，并不是已经运行的流。多个 AudioTrack/AudioRecord 客户端可能共用 HAL 流，因此 maxOpenCount="3" 不能直接翻译成“最多 3 个 App”。

本地 IOProfile.h 对 active 计数也明确说明统计的是 HAL 流，不是活动客户端数。当前实现中上限 0 表示不以这个计数限制新的 I/O，具体并发还受其他条件约束。

4.5 profile：格式、采样率、声道能力

一个 profile 描述一种格式，以及该格式下可用的采样率和声道列表；上例声明 PCM24 紧排、44.1/48 kHz、立体声。不同格式通常分开写多个 profile，例如 compressed_offload 的 MP3 与三个 AAC 变体。

选择输出时，APM 还要结合目标设备、flags、可用输出、动态路由等条件。对于普通混音播放，App 的 44.1 kHz PCM 可以在 48 kHz 输出线程中重采样；不能据此断言 profile 与 App 参数没有直接交集就一定开流失败。``direct/offload/MMAP` 的匹配更严格，失败或回退行为依路径而定。

4.6 devicePort：设备端点

属性/子节点 XSD 要求 含义
tagName 必填 模块内设备引用名；输入端点还可出现在 route.sources 中
type 必填 框架设备类型，例如输出 BUS、内置麦克风
role 必填 输出设备为 sink，输入设备为 source
address 可选 寻址串；AAOS 的多 BUS 配置应明确写非空且准确的地址
encodedFormats 可选 编码格式能力/选择信息，例如蓝牙链路的 AAC、SBC 等
default 可选 XSD 文档将它定义为同类型设备未被显式指定时的默认选择信息；本地解析情况见下文
profile、gains 可选 设备音频能力与增益能力；profile 省略不等于设备没有能力

三个名字分别负责：

  • tagName：P 内部的设备引用键，例如 Media Bus
  • type：框架设备类别，例如 AUDIO_DEVICE_OUT_BUS
  • address：设备实例的寻址字符串，例如 bus00_media_out

devicePort.default 与 module 的 defaultOutputDevice 是不同配置项。本地 Serializer.cpp 的 DevicePortTraits 及其反序列化函数没有读取 default，不能仅凭 XSD 对该属性的说明就认定它在本分支生效；本样本也未使用该属性。

Important

  • 改 tagName 时，至少要同步 P 中所有引用；也要检查项目外部工具是否另有依赖。
  • 改 address 时，要核查所有使用该地址的 car 配置、HAL 映射及底层配置。
  • 只有实际引用该地址的文件才需要同步修改，不是每个 BUS 都必须在每份 car 配置里出现。

4.7 route：连接能力与检查边界

  • 输出 route 一般是 mixPort(source) → devicePort(sink)。

  • 输入 route 一般是 devicePort(source) → mixPort(sink)。

配置也能描述受支持的设备到设备连接，不能把所有 route 都限定为“流到扬声器”。

属性 含义
type="mix" 声明来源可混合连接；实际同时播放由流、HAL/DSP、焦点与并发共同决定
type="mux" 声明来源互斥选择
sink 一个汇端口引用名
sources 一个或多个源端口引用名，用逗号分隔；避免逗号后加空格

Important

本地 route 解析器使用逗号拆分 sources 后查找端口，没有在这里为名字去掉前导空格。因此应写 media,mmap_no_irq_out，不要写 media, mmap_no_irq_out。

XSD 不会逐项检查 sources 引用，也不能完整验证连接方向 ，它能检查 sink 引用是否存在、同一 sink 是否出现多条 route。本地运行时解析器会继续查 sources，找不到时在正常解析模式下返回错误。。

4.8 attachedDevices 与 defaultOutputDevice

attachedDevices 是初始化时应访问的常驻设备清单，不是“已证实硬件可用”的报告。常见对象是 BUS、内置麦等；插拔设备一般由连接状态事件接入，不要为了让它“看得见”随意列为常驻。

defaultOutputDevice 指定默认输出设备，例如 Media Bus。它必须是正确的输出端点，还要通过 HAL 访问而成为可用设备。默认出口无法挽救格式不支持、HAL 开流失败、音频焦点限制或功放未工作等问题。

5. source、sink 与输入输出

audio_policy_configuration.xml 所描述的是 HAL 向 Android 框架暴露的音频拓扑与能力：

  • module 对应一个音频 HAL 模块；
  • mixPorts 描述可打开的播放、采集流能力；
  • devicePorts 描述输入、输出设备端点；
  • routes 描述端口之间允许的连接。

因此，本章的 source/sink 描述端口在上述拓扑的一条连接中提供还是接收音频数据。 App 向播放流提供数据、从采集流读取数据属于另外一段关系，不是这里的端口 role 所描述的连接。

5.1 系统方向与连接角色

输入/输出 描述 Android 音频系统的播放、采集方向；

source/sink 描述端口在一条连接中提供数据还是接收数据。

两者回答的问题不同，不能直接把 source 等同于输入，或把 sink 等同于输出。

要判断的概念 参照对象 判断方法
输入 / 输出 Android 的播放、采集通路 数据从 Android 送往输出设备，是输出；从输入设备进入 Android 采集通路，是输入
source / sink 一条音频端口连接 向连接提供数据的一端是 source；从连接接收数据的一端是 sink

以普通播放与采集为例：

播放音乐、导航提示音属于输出；取得麦克风或输入 BUS 的数据属于输入。这里的输入不一定来自麦克风，输出也不一定直接连接扬声器；BUS 是逻辑端点，其物理通路仍由 HAL 与底层实现。

Note

“输入/输出”必须带着参照对象理解。例如:

  • 音乐文件进入播放器，属于播放器自己的输入；
  • 播放器解码后通过 AudioTrack 播放，仍然属于 Android 音频输出。

不能因为 App 读取了文件，就把它判定为 policy 的输入流。

5.2 source 与 sink 输出与输入

source 可译为数据源，sink 可译为数据汇。一条连接的数据方向始终按下面的箭头理解：

这里的角色针对端口连接，而不是判断“谁最初创造了声音”或“声音最终在哪里结束”。

  • source 可以把上游提供的数据继续送给下游，不要求自己生成声音。例如，播放 mixPort 的数据来自 App / 框架，但它向设备端点提供数据，因此在 mixPort->devicePort 这条连接中， mixPort是 source， devicePort 是 sink。
  • sink 接收到数据后还可以继续处理或传递，不要求它是整条系统通路的终点。例如，采集 mixPort 接收设备的数据，供给框架/App 读取这些数据，因此在 devicePort->mixPort 这条连接中， devicePort 是 source， mixPort 是 sink。

5.5 mixPort 与 devicePort 的 role 关系

原因在于它们处在“流与设备”连接的两侧。

  • 播放时，流提供数据、设备接收数据；
  • 采集时，设备提供数据、流接收数据。

因此四种组合如下：

通路 端口种类 role 数据关系
播放输出 mixPort source 向输出设备端点提供音频
播放输出 devicePort sink 接收输出流提供的音频
采集输入 devicePort source 向输入流提供采集数据
采集输入 mixPort sink 接收设备提供的数据，供框架/App 读取

AOSP 官方配置示例采用相同的四种组合，并将 mixPort 定义为 HAL 播放、采集流的能力描述，将 devicePort 定义为设备描述。

从普通 HAL 流的读写操作也可以理解这两条方向：

  • 播放输出流：框架向 HAL 输出流写入数据，送往输出设备。
  • 采集输入流：框架从 HAL 输入流读取数据，取得输入设备提供的声音。

Note

“输入流”是框架用来读取采集数据的流，但在设备到流的连接中，它接收设备的数据，所以输入 mixPort 是 sink。这个 role 不表示 App 把数据写进录音流。

5.6 role 与 route 的 sources、sink

  • 端口上的 role="source"、role="sink" 声明端口自身的连接角色；

  • route 上的 sources="..."、sink="..." 则指定这一条连接引用哪些端口。

为单独说明引用关系，下面用只保留 media 一个来源的简化写法；

虽然这行 XML 先写 sink、后写 sources，数据方向仍然是 media（source）─> Media Bus（sink）

属性的书写先后不决定数据流向。判断连接时，始终从 sources 指向 sink，并检查被引用端口的 role 是否相符。

普通播放、采集的引用关系如下：

通路 route.sources 引用 route.sink 引用
播放输出 输出 mixPort 的 name 输出 devicePort 的 tagName
采集输入 输入 devicePort 的 tagName 输入 mixPort 的 name

例如，输出 route 的 sink="Media Bus" 引用设备端口名，而设备的 address="bus00_media_out" 用来标识 BUS 实例。route 用端口名连接拓扑，address 用来定位设备实例，两者不能互换。 sources 引用多个端口时用逗号分隔。

5.7 按三个步骤读懂一条连接

  1. 看端口种类。 mixPort 描述流接口能力，devicePort 描述设备端点。
  2. 看方向声明。 对 mixPort，source 对应输出流，sink 对应输入流；对 devicePort，AUDIO_DEVICE_OUT_* 对应输出设备且 role 为 sink，AUDIO_DEVICE_IN_* 对应输入设备且 role 为 source。
  3. 沿 route 的 sources → sink 核对连接。 确认名字引用正确、角色匹配，并区分“允许连接”与“当前已经接通”。

读懂 source/sink 后，才能准确判断一条 route 声明的是哪种数据连接。声音最终走哪个 BUS、哪个分区，以及当前是否有数据。

6.1 四个层次：用途、归类、分区、设备

层次 谁定义/提供 例子
usage App 的 AudioAttributes，平台定义其可用值 USAGE_MEDIA、USAGE_ASSISTANCE_NAVIGATION_GUIDANCE

C 的 inputDevices 与输出 context 路由不是同一套声明。也不能仅凭“某输入未列入 C”推导该输入绝对无法通过普通录音策略使用。

7.4 address 的三条使用原则

  1. 逐字符匹配。 大小写、后缀都是地址的一部分。bus02_navigation_out 与 BUS02_NAV_GUIDANCE 是不同端点；数字 02 相同没有特殊匹配意义。
  2. 编号规律只适用于自己项目约定。 有时可观察到一些 1xx private、2xx driver 命名，但 AAOS 不会自动解析数字含义。不能自行新造 BUS204_... 就期望得到 driver 路由。
  3. 沿消费者检查变更。 若修改一个正在由 C 使用的地址，P、C、HAL 及底层映射需要一致；若是未被 C 引用的端点，则需查它的实际使用者，而不是向每个 zone 强行添加它。

两套大小写命名并存是可观察的事实；哪个团队何时加入、是否因历史平台迁移造成，不能仅从名称推断。

8. 设备类型、flags、格式、声道与音量

8.1 设备 type：声明设备类别

下表覆盖 P 主模块中出现的全部设备类型；分组中的 AUDIO_DEVICE_ 前缀在实际 XML 中不可省略。

type 方向与含义 阅读样本时的注意点
AUDIO_DEVICE_OUT_BUS 输出 BUS 24 个可寻址输出端点；实际硬件由地址映射
AUDIO_DEVICE_OUT_EARPIECE 听筒输出 有声明不表示车机必有独立听筒
AUDIO_DEVICE_OUT_SPEAKER 扬声器输出 传统设备类型；本样本常驻输出清单以 BUS 为主
AUDIO_DEVICE_OUT_SPEAKER_SAFE safe 扬声器输出路径 框架可为通知/响铃等选择该路径；不能定义为车机高优先级专用声道或安全认证保证
AUDIO_DEVICE_OUT_BLUETOOTH_SCO、AUDIO_DEVICE_OUT_BLUETOOTH_SCO_HEADSET、AUDIO_DEVICE_OUT_BLUETOOTH_SCO_CARKIT SCO 输出的几种设备类型 常用于通话语音路径
AUDIO_DEVICE_OUT_BLUETOOTH_A2DP、AUDIO_DEVICE_OUT_BLUETOOTH_A2DP_HEADPHONES、AUDIO_DEVICE_OUT_BLUETOOTH_A2DP_SPEAKER A2DP 输出的几种设备类型 常用于高音质蓝牙音频；与 SCO 的 profile/连接处理不同
AUDIO_DEVICE_OUT_TELEPHONY_TX 电话上行输出端点 音频送往电话链路；不是扬声器
AUDIO_DEVICE_IN_BUILTIN_MIC、AUDIO_DEVICE_IN_BACK_MIC 内置麦、背麦输入 具体硬件位置与采集处理需查板级设计
AUDIO_DEVICE_IN_BLUETOOTH_SCO_HEADSET SCO 麦克风输入 与 SCO 输出组成语音收发路径
AUDIO_DEVICE_IN_TELEPHONY_RX 电话下行输入端点 接收电话链路提供的声音
AUDIO_DEVICE_IN_BUS 输入 BUS 本样本共 6 个，包含分区输入与 VR 命名端点
AUDIO_DEVICE_IN_ECHO_REFERENCE 回声参考输入 可向 AEC 等处理提供参考信号；声明该端点本身不会开启 AEC
AUDIO_DEVICE_IN_FM_TUNER FM 收音输入 本样本连接到 mixport_tuner0

SCO 常用于双向语音，包含窄带/宽带等实际协商情况；不要将它固定等同于“永远窄带”。A2DP 常用于较高音质媒体，本产品还通过单独 a2dp 模块声明 A2DP 输入能力，所以也不能说 Android 侧只会有 A2DP 输出。

8.2 flags：输出能力

以下覆盖 P 的 flags，均保留完整枚举名：

flag 含义 样本使用者
AUDIO_OUTPUT_FLAG_PRIMARY 标识 primary 输出候选，涉及 APM 初始化与选择 media_714、primary output
AUDIO_OUTPUT_FLAG_FAST 请求/声明低延迟 fast 输出能力；客户端仍需满足 fast track 条件 primary output、raw
AUDIO_OUTPUT_FLAG_RAW 请求较少信号处理的输出路径 raw，并与 FAST 一起声明
AUDIO_OUTPUT_FLAG_DEEP_BUFFER 深缓冲路径，常用于功耗与延迟的取舍 deep_buffer
AUDIO_OUTPUT_FLAG_DIRECT direct 输出模式，区别于普通混音输出选择 compressed_offload、mmap_no_irq_out
AUDIO_OUTPUT_FLAG_COMPRESS_OFFLOAD 支持压缩音频 offload 播放，由下层处理解码等 compressed_offload
AUDIO_OUTPUT_FLAG_NON_BLOCKING 声明对应输出的非阻塞交互能力 compressed_offload
AUDIO_OUTPUT_FLAG_MMAP_NOIRQ MMAP 低延迟缓冲模式 mmap_no_irq_out
AUDIO_OUTPUT_FLAG_VOIP_RX VoIP 接收/播放路径标记 voip_rx
AUDIO_OUTPUT_FLAG_INCALL_MUSIC 通话中音乐上行路径标记 incall_music_uplink
AUDIO_INPUT_FLAG_FAST fast 低延迟采集能力 fast input
AUDIO_INPUT_FLAG_MMAP_NOIRQ MMAP 采集模式 mmap_no_irq_in
AUDIO_INPUT_FLAG_VOIP_TX VoIP 发送/采集路径标记 voip_tx

没有 flags 的 mixPort 也能成为普通流候选，如 media。但是“所有 flags 都只是加分项”不准确：本地 IOProfile::isCompatibleProfileForFlags() 对输出的 DIRECT、HW_AV_SYNC、MMAP_NOIRQ 等执行必要匹配，对输入 flags 也有匹配规则，不能把任何 App 请求交给任何 profile。

PRIMARY 也不是“每个 module 都必须有一个”的规则：本例 include 的 a2dp、usb、r_submix 模块不必带这个 flag。本地 APM 需要成功建立 primary 输出；样本自身有两个带 PRIMARY 的 profile，不能据此推导所有输出都要加 PRIMARY。

MMAP 常与 AAudio 的低延迟实现有关，但调用 AAudio 不意味着必走 MMAP。是否可用、共享或独占、是否回退到普通路径，都取决于系统与 HAL；也不能把 MMAP_NOIRQ 理解为全链路保证没有中断、没有任何复制或永远不混音。

8.3 format：编码

format 解释 P 中位置
AUDIO_FORMAT_PCM_16_BIT 每样本 16 位 PCM 多数普通端口
AUDIO_FORMAT_PCM_24_BIT_PACKED 每样本紧排为 3 字节的 24 位 PCM deep_buffer
AUDIO_FORMAT_PCM_8_24_BIT 24 位有效数据使用 32 位容器的 PCM 表示 primary/fast input
AUDIO_FORMAT_MP3、AUDIO_FORMAT_AAC_LC、AUDIO_FORMAT_AAC_HE_V1、AUDIO_FORMAT_AAC_HE_V2 压缩音频格式 compressed_offload 的四个 profile
AUDIO_FORMAT_LDAC、AUDIO_FORMAT_APTX、AUDIO_FORMAT_APTX_HD、AUDIO_FORMAT_AAC、AUDIO_FORMAT_SBC 蓝牙编码格式能力/选择信息 A2DP 输出设备的 encodedFormats

MP3 文件经 App/媒体框架解码后可以走 PCM profile。只有满足 offload 条件时，才可能使用相应压缩 profile。APM 不会因为某个 profile 不匹配就自动给任意媒体“转码”。

PCM 位深更高只是数据规格，不自动保证更高音质；音源、处理链、转换与硬件同样影响最终效果。

8.4 channelMasks：位置式与索引式

掩码 含义 样本例子
AUDIO_CHANNEL_OUT_MONO 单声道输出 voice_tx 与 compressed_offload 的可选能力
AUDIO_CHANNEL_OUT_STEREO 左、右两个输出声道 普通输出 BUS
AUDIO_CHANNEL_OUT_7POINT1POINT4 7.1.4 位置式输出，共 12 通道 media_714 与 Media 714 Bus
AUDIO_CHANNEL_IN_MONO 单声道输入 部分输入 profile
AUDIO_CHANNEL_IN_STEREO 立体声输入 分区输入 BUS、部分采集 profile
AUDIO_CHANNEL_IN_FRONT_BACK 前/后位置式双通道输入 primary/fast input 的可选能力
AUDIO_CHANNEL_INDEX_MASK_1 索引式 1 通道 vr_robotdog
AUDIO_CHANNEL_INDEX_MASK_3 索引式 3 通道 primary/fast input 的可选能力
AUDIO_CHANNEL_INDEX_MASK_8 索引式 8 通道 VR 家族中的部分端口

位置式描述声道角色，索引式按 0～N−1 编号描述各路数据，后者不携带前左/后右等位置含义。索引式不仅能用于麦克风阵列；是否采用它取决于该通路的数据语义。

profile 同时列出 MONO、STEREO、INDEX_MASK_3，表示这些都是声明的可选配置，并非每次采集都自动成为三通道。

8.5 gain：设备能力、毫贝与边界

以下是完整 gain 片段，应置于某端口的 gains 内：

属性 含义 检查点
name gain 的声明名 当前 XSD 必填；样本为空字符串，不是 HAL 地址
mode JOINT 共同调节，CHANNELS 按声道调节，RAMP 支持渐变 RAMP 是可组合能力；使用 CHANNELS/RAMP 时还需相关声道/时间参数
minValueMB、maxValueMB 最小/最大增益，单位毫贝 见下方范围检查公式
defaultValueMB 声明的默认增益 落入范围，并与步进对齐
stepValueMB 步进 本文静态 gain 使用正步进，样本为 100

$$
100\,\mathrm{mB} = 1\,\mathrm{dB}
$$

属性里的 MB 在这里不是兆字节；在说明中也可写 mB 以减少歧义。

本样本的 gain 情况应按实际数值分类，而不是笼统叫“媒体型/提示型”：

端点 范围 默认 步进
多数输出 BUS，包括 VW system/navi/tts 等 −30～0 dB −15 dB 1 dB
BUS332_TTS_OUTSIDE −30～0 dB 0 dB 1 dB
Phone、Alerts、Front Passenger、Rear Seat 四条大写输出 BUS −60～+6 dB 0 dB 1 dB
三条大写输入 BUS −60～+6 dB 0 dB 1 dB
三条小写 VR 输入 BUS 未声明 gain — —

XML 只给出了范围，不能由此证明“+6 dB 是专为穿透路噪”或“0 dB 已由功放满刻度设计保证不破音”。这些原因需要调音规格或硬件证据。

对本文的离散正步进 gain，应检查：

$$
\begin{gathered}
\mathrm{step} > 0 \\
\mathrm{max} \ge \mathrm{min} \\
\mathrm{default} \in [\mathrm{min},\mathrm{max}] \\
(\mathrm{max} - \mathrm{min}) \bmod \mathrm{step} = 0 \\
(\mathrm{default} - \mathrm{min}) \bmod \mathrm{step} = 0
\end{gathered}
$$

这些数值关系并未由当前 XSD 的普通整数类型完整检查。声明也必须符合 HAL 的实际能力；写进 XML 的 gain 不会替代驱动或 DSP 的实现。

XSD 允许省略 gains，但本地 CarAudioDeviceInfo 构造时会通过 AudioManagerHelper.getAudioGainInfo() 查找有效的 AUDIO_GAIN_MODE_JOINT 增益，并检查范围、默认值和步进对齐。进入这条初始化路径的输出设备若没有有效 JOINT gain，仍会在运行时失败。

0 dB 表示此级增益不衰减/不放大，不表示静音。 最小 −30 dB 也不等于数字静音，是否 mute 由相应静音机制控制。音量 UI 的 index 与设备 gain 是不同的量，下面两个零值不能混淆：

$$
\mathrm{index} = 0,\qquad \mathrm{gain} = 0\,\mathrm{mB}
$$

8.6 音量应用

设备 gain 模式：在动态路由、未启用 core 音量的本地实现中，CarAudioVolumeGroup 根据音量组 index 计算：
$$
\mathrm{gain}\,(\mathrm{mB}) = \mathrm{groupMinGain} + \mathrm{index} \times \mathrm{groupStep}
$$

例如，增益范围和步进为：

$$
\begin{gathered}
\mathrm{groupMinGain} = -3000\,\mathrm{mB} \\
\mathrm{groupMaxGain} = 0\,\mathrm{mB} \\
\mathrm{groupStep} = 100\,\mathrm{mB}
\end{gathered}
$$

通常对应的 index 范围，以及 index 取 15 时的增益计算如下：

$$
\begin{gathered}
\mathrm{index}_{\max} = \frac{0 - (-3000)}{100} = 30 \\
\mathrm{index} \in \{0,1,\ldots,30\} \\
\mathrm{gain}(15) = (-3000 + 15 \times 100)\,\mathrm{mB} = -1500\,\mathrm{mB}
\end{gathered}
$$

计算后的增益经 CarAudioDeviceInfo 下发设备 gain 接口，最终由 HAL/硬件应用。同组多设备的步进须一致，组范围由当前实现汇总，每个设备下发时还可按本设备范围裁剪。

启动时服务可以恢复保存的 index，并叠加静音、限制、ducking 等状态；不能把 defaultValueMB 直接等同于每次开机最终增益。

framework/core 音量模式：音量曲线描述音量 index 到衰减量的映射，并由相应策略引擎和音量控制路径应用。P include 的曲线中：

  • stream 是 MUSIC/RING 等 legacy 流类别；
  • deviceCategory 是 SPEAKER/HEADSET/EXT_MEDIA 等音量设备类别；

reference 存放被引用的曲线点。启用本地 core 音量后，CoreAudioVolumeGroup 通过 AudioManager 的 attributes/volume group 接口读取范围、设置 index。P 引入的 legacy 曲线文件不能被直接当成所有 core 音量组配置；还需确认当前策略引擎及其音量组定义。
