1. 概述

在手机上，音频策略是”单用户、单输出、栈式焦点”：一台设备接一副扬声器，同一时刻一个焦点栈仲裁所有应用。这套假设在汽车座舱里全部失效，本篇进入的是车载场景下 Android 音频的”控制面“：

  • 多音区（Multi-zone）：主驾、副驾、后排各有独立的功放总线（bus），司机听导航、后排看电影、副驾听广播可以同时发生；
  • 多用户（Multi-user）：Android Automotive 支持按座位分配 Android 用户（OccupantZone），每个用户的音频必须路由到自己座位的扬声器，音量设置也按用户隔离；
  • 并发播放是常态：导航播报要”压低”音乐而不是”杀死”音乐，倒车雷达音、安全带提示音按法规必须与任何声音叠加；
  • duck 与 mute 的执行者是硬件：压低某根 bus 的增益由车外功放完成最快、最可控，第三方 App 自愿降音量的路径既不可控也不及时；
  • 车外声源是一等公民：蓝牙电话、紧急呼叫（eCall）、ADAS 提示等外部音源也要参与 Android 的焦点仲裁。

于是 AAOS（Android Automotive OS）在 CarService 中构建了一套完整的音频控制体系：以若干个 AudioPolicy 接管 framework 的路由、音量与焦点三大控制权，以 CarAudioContext 为统一坐标系，以 AudioControl HAL 为对车接口。

Note

本文代码基线为 2024 年前后的 AOSP 主线形态（含 CarAudioZoneConfig 多配置、AIDL AudioControl、Trunk-stable feature flags 等）。不同版本间类名与细节有差异，但”多区 + 上下文 + 矩阵 + HAL”的骨架是稳定的。

2.4. 音频上下文 CarAudioContext：全体系的坐标系

CarAudioContext 把 AudioAttributes 的 21 个合法 usage（isValidAudioAttributeUsage 认可的集合）中的 18 个，收敛为 13 个（012）逻辑上下文——112 号各有归属，INVALID(0) 则是给”没有映射的 usage”准备的兜底位。类注释一句话点题：“Groupings of AttributeUsages to simplify configuration of car audio routing, volume groups, and focus interactions for similar usages.”（对相似 usage 的分组，用于简化路由、音量组与焦点交互的配置。）

没有拿到 context 的 usage 分三类：

  • NOTIFICATION_COMMUNICATION_REQUEST/INSTANT/DELAYED（值 7/8/9）是合法 usage 但从未进表，legacy 路由下查表返回 INVALID——这类请求在焦点矩阵里基本拿不到焦点；
  • system usage 家族的 USAGE_SPEAKER_CLEANUP（1000+4，扬声器自检音）同在此列——新的 system usage 会随版本持续加入 framework，只要不写进 CAR_CONTEXT_INFO 常量组，命运就与 COMMUNICATION_* 一样落到 INVALID；
  • 隐藏的 USAGE_VIRTUAL_SOURCE（=15，虚拟采集源）是唯一被显式映射进 INVALID 的 usage（见上表末行），供音频策略内部构造”不属于任何播放场景”的流。

4.4. 配置校验

三条路径产出统一对象后，CarAudioZonesValidator.validate 逐条校验（全部规则）：

  1. 至少一个 zone："At least one zone should be defined"；
  2. 每个 zone 至少一个 config，恰好一个默认 config；config 的 zoneId 必须匹配；
  3. volume group 层（CarAudioZoneConfig.validateVolumeGroups）：
    • 一个 context 不得出现在两个组："Context %d appears in two groups"；
    • 非 core routing 下一个地址不得出现在两个组（core routing 允许互斥 context 共享设备，由 AudioPolicyManager 在设备激活时施加对应增益）；
    • 所有 context 必须被分配（"Audio context %s is not assigned to a group"），所有 attributes 必须被某 context 覆盖——保证任意声音都有归宿；
    • 动态设备类型不得跨组复用、动态设备必须单独成组；
  4. 动态 mix 可用性（validateCanUseDynamicMixRouting）：同一 usage 不得路由到两个设备（mix 规则只能按 usage 匹配）；core routing 下冲突设备被降级 resetCanBeRoutedWithDynamicPolicyMix()；
  5. 地址跨 zone 不共享（core routing 时跳过；同 zone 跨 config 共享是允许的——切配置时同一 bus 复用）；
  6. 主区必须有麦克风："Primary Zone must have at least one microphone input device"。

7.1. 为什么必须接管 framework 焦点

framework 默认焦点（audioserver 内 MediaFocusControl）是”单栈、排他为主、App 自愿让路”的模型，与车载需求正面冲突：

  1. 多区：framework 焦点全局唯一，无法表达”主驾听音乐、后排看电影”两个互不相干的焦点域。CarService 给每个 zone 建一个独立的 CarAudioFocus 仲裁器；
  2. 并发持有：导航播报要和音乐同时持有焦点（导航只压低不驱赶），安全提示音按法规叠加。mFocusHolders 是 Map 而非单例，天然支持多 context 并存；
  3. duck 的执行者在硬件：给音乐 App 发 LOSS_TRANSIENT_CAN_DUCK 再指望它自己降音量，既不可控也不及时。CarService 接管后，被 duck 的 App 默认根本收不到任何回调，duck 由 HAL 拉低 bus 增益完成；
  4. 车外声源：蓝牙电话、eCall 等 HAL 侧音源也要进仲裁。

9.1. 音频镜像的三件套

镜像的落地依赖三件事，全部建立在第 5 章的 affinity 机制上：

  1. mirror bus 预挂 mix：routing policy 构建时每根 mirror bus 一条只匹配 USAGE_MEDIA 的 RENDER mix（setupAudioDynamicRoutingForMirrorDevice）——mirror bus 在策略里始终”待命”；
  2. user affinity 改道：把参与 zone 各自 user 的设备亲和改为”本 zone 设备 + mirror 设备”——该 user 的媒体流被额外渲染到 mirror bus；
  3. HAL 物理复制：AudioManager.setParameters 下发 mirroring_src=<mirror地址>;mirroring_dst=<zone1媒体地址>,<zone2媒体地址>;，vendor audio HAL 把 mirror bus 的输出复制到各目的 bus。

mirror 设备池来自配置（XML <mirroringDevices> 或 HAL getOutputMirroringDevices()），池子非空 = 镜像功能开启（isMirrorAudioEnabled() = !mMirrorDevices.isEmpty()）——没有空余 bus 就没有镜像，这正是 canEnableAudioMirror() 返回 AUDIO_MIRROR_OUT_OF_OUTPUT_DEVICES 的原因。

13.2. 设计要点回顾

  1. 一套坐标系：usage → context 的收敛表贯穿路由（mix 规则）、音量（组划分）、焦点（矩阵索引）、duck（压低矩阵）四个子系统，CarAudioContext 是全体系的公共语言；
  2. 一切特殊路由皆 affinity：uid 定向、主区共享、音频镜像全部落在 AudioPolicy.setUid/UserIdDeviceAffinity 上，切换时的焦点 transient loss → regain 是唯一的状态迁移协议；
  3. 仲裁与执行分离：CarService 只做”决策”（谁被 duck/谁被 mute/焦点给谁），”执行”（拉增益）全部下沉 HAL——决策可审计，执行零延迟；
  4. 不打扰哲学：CONCURRENT + MAY_DUCK 的被压者零回调；需要知情的 App 显式 opt-in；恢复靠 blocker 链的事件驱动而非轮询；
  5. HAL 是一等公民：车外声源可反向请求焦点进入同一仲裁，HAL 增益回调驱动 block/limit/attenuate 三态，配置本身也可由 HAL 下发（V5）——Android 与车外音频域在控制面最终一致；
  6. 可演进性：特性开关三层来源（RRO → XML → HAL）、配置格式 v1→v4 的增量演进、AIDL 接口 V1→V5 的版本门槛探测，都服务于”vendor 分区冻结后仍能演进”这一约束。

13.3. 源码彩蛋：两个隐藏的坑

梳理源码时顺带挖到两个 AOSP 自身的小问题。它们不是设计意图，而是 Mainline 代码里真实存在的疑点——触发条件都很窄，现网几乎不会踩到，但作为”读源码要带着怀疑”的注脚非常合适。

13.3.1. 路径 C 构造 CarAudioContext 传错了开关

第 4.2 节的三条配置加载路径最终都会 new CarAudioContext(...)。构造器第二个参数的语义是 useCoreAudioRouting——正是 2.4 节双引擎分支的总开关——而三条路径的传法并不一致：

路径 构造点 第二实参 评价
A：HAL 下发 AudioControlZoneConverterUtils.java:214 deviceConfiguration.routingConfig == CONFIGURABLE_AUDIO_ENGINE_ROUTING ✔ 语义正确
B：统一 XML CarAudioZonesHelperImpl.java:376 mUseCoreAudioRouting ✔ 语义正确
C：legacy CarAudioService.java:2036 mUseCoreAudioVolume ✘ 疑似笔误

影响链：audioUseCoreVolume 与 audioUseCoreRouting 是两个独立开关（第 3 章），一旦出现”volume 开、routing 关”的组合且机器恰好走路径 C，CarAudioContext 就会被错误地置于 core-routing 模式——getContextForAudioAttribute 切到 strategy-id 引擎、AudioAttributesWrapper 的相等语义随之切换（按 context id 比较）、OEM 扩展 context 判定（mOemExtensionContexts）被启用——整条链都建立在错误的前提上。

为何现网难见：路径 C 要求 HIDL V1.0 HAL 且不存在 car_audio_configuration.xml，这种最早期形态的量产配置上两个 core 开关几乎必然同为 false，传参错误只有在”老 HAL + 新开关”的混搭下才会显形。修复方向也很直白：改传 mUseCoreAudioRouting，或者在 legacy 路径上干脆断言两个开关必须一致。

13.3.2. duck 期间调音量：档位会”丢”

第 6.4 节说过，attenuated（duck）状态下对外可见 index 是三个限制态合成的结果。合成函数里躺着一条没有 bug 号的 TODO：

TODO 的纠结点是双基准错位：duck 期间 UI 显示的是压低后的 mAttenuatedGainIndex，而组内部记忆的用户设定是 mCurrentGainIndex——两个数从 duck 生效那一刻起就分道扬镳了。把 6.3 与 6.4 的代码串起来推演（数值为示例）：

  • 初始状态：组的 mCurrentGainIndex = 30；ADAS duck 回调把 mAttenuatedGainIndex 设为 15；对外 getCurrentGainIndex() 返回合成值 15，UI 显示 15 档；
  • 方向一（用户碰了音量键 → 档位丢失）：用户按”+”，evaluateVolumeAdjustmentInternal 以显示值 15 为基准算出 16，setCurrentGainIndex(16) 里 isAttenuatedLocked() 命中 → resetAttenuationLocked() 解除 duck，且 mCurrentGainIndex = 16——duck 解除了、硬件增益直接写为 16 档，但用户真正的 30 档设定被永久丢弃。导航播报期间顺手按了一下音量键，播报结束后音乐再也回不到原来的音量；
  • 方向二（用户不碰按键 → UI 跳档）：duck 自然结束，HAL 清除 reason，onAudioGainChanged 把 mAttenuatedGainIndex 复位为 UNINITIALIZED（其注释 “Do not update current gain cache, keep it for restoring” 明确不动 mCurrentGainIndex），对外显示从 15 一步跳回 30——gap = 15 > 1，正是 TODO 担心的跳变。

两难的根源在于：duck 期间任何对外 index 都只能说谎——参考值定为 ducked index 就有方向一的档位丢失，定为 current index 就有方向二的显示跳变，区别只是谎报多久、何时穿帮。AOSP 把这个问题留在了 TODO 里没有定论；对 OEM 的实际启示是：若产品语义要求”播报期间不允许丢音量设定”，应在 duck 态拒绝音量键、或缓存原设定档位并在 duck 结束后恢复，而不是依赖 framework 的默认行为。

Note

6.4 节”用户主动调音量会解除衰减（duck 状态被用户操作打断）”的描述与源码一致，本节展开的正是这个行为的代价面——“打断”的实现方式是以压低后的档位为新基准，而不是恢复原档位。
