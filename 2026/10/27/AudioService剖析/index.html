1. 从一次听歌过程认识 AudioService

手机正在播放音乐，用户按了一次音量加，导航随后播报“前方右转”，接着用户拔掉耳机，又接起一通语音电话。听起来是一组日常操作，系统却必须回答不同的问题：

  • 音量键应该调媒体还是通话？调的是哪一种设备的档位？
  • 导航来了，音乐应该暂停、变小，还是继续播放？谁通知播放器？
  • 耳机拔掉后，什么时候通知应用，什么时候更新设备，谁决定改走扬声器？
  • 通话模式属于哪个应用？应用异常退出后，谁清理它留下的状态？
  • audioserver 重启了，用户音量、连接设备和动态策略怎样恢复？

AudioService 是 system_server 中的音频管理服务：它把应用、用户和系统提出的控制需求，转换成经过权限检查与策略协调的音频状态，再交给下层音频系统执行。 它不在音乐 PCM 的必经传输路径上，也不负责在 Java 层混合每一帧音频。

本文以“音乐播放 → 调音量 → 导航播报 → 耳机切换 → 语音通话 → 服务恢复”为贯穿场景，重点读懂控制面。阅读后应能分清“请求受理、Java 状态变化、native 配置生效、设备实际出声”这几个不同的完成点，而不仅是记住一串函数名。

2. 先划清四条边界

图中外框区分进程，内部面板表示组件/职责。绿色线横向经过排版区域但不接入 AudioService；它概括普通 AudioTrack 数据通路，省略共享缓冲、native 客户端与具体输出类型。橙色线只画本篇主干，不能据此推断 AudioSystem 只访问 AudioPolicyService。

2.1. AudioManager、AudioService、AudioSystem 分别在哪里

应用需要一个方便使用的对象来发起请求，这就是 AudioManager。它并不是服务本体，而是应用进程中的客户端门面。getService() 通过 ServiceManager 取得名为 audio 的 Binder 服务，再转换为 IAudioService 接口。

普通应用进程获得的是 Binder 代理；请求进入 system_server 后由 AudioService 处理。AudioService 实现 IAudioService.Stub，而 AudioSystem 是 Java 到 native 音频系统的桥接类。后者的静态接口经 JNI 调用 C++ AudioSystem，再根据具体操作访问 AudioPolicyService 或 AudioFlinger。

因此不要把“AudioManager 调 AudioService”和“AudioSystem 调 native”混成同一层 IPC。JNI 本身也不等于跨进程：Java 进入 JNI 仍在原进程，后续 native Binder 调用才跨入 audioserver。

2.2. AudioService 与 AudioPolicyService 的职责边界

对象 所在进程 主要保存或决定的内容 不应归给它的工作
AudioService system_server 用户音量、静音、模式、焦点协调、设备事件与动态策略注册 持续搬运所有 PCM、执行软件混音
MediaFocusControl system_server，AudioService 协作者 默认焦点仲裁、焦点请求生命周期、外部焦点策略对接 直接选择物理扬声器或计算音量曲线
AudioPolicyService / AudioPolicyManager audioserver native 策略入口、输出选择、设备路由、音量曲线与 patch 等 绘制系统音量面板、替应用管理业务播放队列
AudioFlinger audioserver track、音频线程、混音/输出和底层控制执行 决定应用应该如何响应业务层的焦点变化

音量管理跨越多层：AudioService 主要管理“用户要第几档”，APM 把档位和设备类别等条件结合起来计算音量，AudioFlinger/HAL 执行相应控制。某些输出使用硬件增益、offload 或远端绝对音量，不能把所有路径都描述成“AudioFlinger 把 PCM 乘以同一个系数”。

2.3. 数据面不穿过焦点栈

音乐播放器可以同时做两件事：用 AudioManager 申请焦点，用 AudioTrack 等接口建立实际播放。焦点请求不是创建音频轨道，焦点栈也不是 PCM 队列。 反过来，存在一个已启动的播放器，并不能证明它当前拿到了焦点。

这两个事实解释了常见现象：焦点申请成功却没有声音，可能是播放轨道、路由或音量出了问题；焦点申请失败，应用若仍错误地启动播放，也不能仅凭失败返回就断言底层一定完全没有声音。现代框架存在有条件的 duck、fade 和通话静音干预，仍要分别检查焦点决策与播放器执行。

2.4. Java AudioPolicy 不是 native AudioPolicyService

特权应用可以创建 Java android.media.audiopolicy.AudioPolicy，携带动态 mix、焦点监听/策略或外部音量控制能力，向 AudioService 注册。注册对象在服务端对应 AudioPolicyProxy。

它和 audioserver 中的 AudioPolicyService 同名近似，却不是同一对象。焦点策略回调在 Java Binder 通道上完成；mix 配置才通过 AudioSystem 注册到 native 策略系统。这一区分在车载系统中特别重要，第 10 章再展开。

3. 服务怎样启动，又怎样长期处理事件

3.1. 生命周期：构造、发布、就绪是三个阶段

SystemServer 的音频启动段在普通路径上通过 SystemServiceManager.startService(AudioService.Lifecycle.class) 启动服务；同一段还保留设备指定 AudioService 实现的配置分支。因此下面讲的是本树中的标准实现，不把它当成所有产品唯一入口。

Lifecycle 将 SystemService 生命周期接到真正的 AudioService 对象：

构造阶段创建状态和协作者，读取音量范围、设备配置和设置，建立线程与回调。发布阶段让客户端可以找到服务。到 ActivityManager ready 阶段，systemReady() 再投递 MSG_SYSTEM_READY，由 AudioHandler 调用 onSystemReady()：设置 mSystemReady，启动设备相关处理、声音效果加载及其他依赖系统就绪的工作。

注意 systemReady() 与 onSystemReady() 并非同义名字：前者是触发入口，后者是消息消费者。调用前者返回，不表示后者及全部异步初始化已经完成。

3.4. 消息策略与锁分别解决什么

sendMsg() 的三个模式决定同类待处理消息怎样处理：

策略 实现含义 不能据此推断的事情
SENDMSG_REPLACE 删除同 what 消息，再发送新消息 不按任意业务对象自动精确去重
SENDMSG_NOOP 已有同类消息则不再投递 不表示已有消息已经执行
SENDMSG_QUEUE 继续排队 不保证每条消息都保存独立状态快照

最后一点直接影响音量分析：MSG_SET_DEVICE_VOLUME 携带的是 VolumeStreamState 对象与设备值。连续请求可能先修改同一对象，多条消息消费时读到较新的 index。要知道历史变化，得看请求日志和状态更新，而不能把消息数量当成“native 必然逐个经历了每个旧档位”。

队列不能替代锁。Binder 线程、AudioHandler、BrokerHandler 可能共同访问状态，代码使用 VolumeStreamState.class、mSettingsLock、mSetModeLock、mDeviceStateLock、焦点锁等保护不同数据。在 Broker 的设备恢复路径中，能看到先取 mSetModeLock、再取 mDeviceStateLock 的嵌套顺序。修改源码时，应沿既有调用路径保持锁顺序，不能因为“最终都发消息”就删除同步。

4. 音量模型：先理解状态，再看按键

4.1. Stream、Attributes、Strategy、Group 是四种描述

STREAM_MUSIC、STREAM_RING 等 legacy stream 表达传统音量分类；AudioAttributes 表达声音的用途、内容类型和标志，例如媒体音乐或导航播报。native 策略系统再用 product strategy 组织路由行为，用 volume group 组织音量行为。

它们有映射关系，但不能直接画等号。相同 usage 不代表应用独占一个输出；相同 volume group 不代表多个应用就是同一个播放器；stream alias 也不是设备路由规则。

概念 回答的问题 本篇关注点
legacy stream 传统 API 要调哪类音量？ AudioManager 的兼容入口
AudioAttributes 这是什么用途、什么内容的声音？ 焦点、策略与组映射的输入
product strategy 哪组属性遵循相应路由策略？ 设备选择交给 native 策略
volume group 哪些声音共享音量控制语义？ VolumeGroupState 与 native 曲线

AudioService 构造时查询 AudioProductStrategy 及属性音量范围，还结合资源和系统属性确定范围。源码中注释明确给出相关初始化优先级：属性、Audio Policy Service、默认值。不能拿一台手机的“媒体 15 档”当成系统常量。

4.3. Alias：为什么改通知音量会影响铃声

不同 stream 可以共享控制行为。sStreamVolumeAlias 保存“请求的流 → 负责控制的流”的映射。调音时先找到 alias，修改对应的状态，再传播到使用该 alias 的其他流。

updateStreamVolumeAlias() 会结合设备平台、单音量模式、通知是否绑定铃声、辅助功能独立音量、通信状态以及 volume group alias 配置等建立或更新映射。因此不能直接抄一张老版本 alias 数组，再声称所有 Android 都固定如此。

例如在通知绑定铃声的配置下，通知音量请求可落到铃声对应的状态；进入通信场景后，部分流的 alias 或控制逻辑又会变化。映射决定的是音量联动，不是“通知 PCM 被重分类成电话音频”。当两个流的范围不同，代码还会做比例换算，不能机械复制同一个数值。

4.4. VolumeGroupState 与 legacy stream 怎样共存

本树中同时存在 stream state 和 group state。VolumeGroupState 使用一组 AudioAttributes 表达组的音量，保存范围、设备索引与静音状态，通过 setVolumeIndexForAttributes() 下发 native。组关联的 legacy stream 也需要保持状态协调。

setVolumeGroupVolumeIndex() 等组接口与 legacy setStreamVolume() 并存；config_handleVolumeAliasesUsingVolumeGroups 决定是否用 volume groups 帮助处理 alias。分析产品时应先看 mUseVolumeGroupAliases 和实际组定义，再判断哪条通路生效。

即使应用走 legacy stream 接口，到了本树的 APM，setStreamVolumeIndex() 也会先取得该 stream 的 attributes，再进入 setVolumeIndexForAttributes()。旧 API 与新组模型是通过适配衔接的，不能简单分成“旧系统只有 stream、新系统只有 group”。

4.5. 档位、静音、铃声模式与 DND 不能混成一个值

状态 例子 对“没有声音”的解释
index 媒体第 5 档 表示记住的用户档位
stream mute / internal mute 某条流被静音 可能保留非零 index，实际应用静音
ringer mode 正常、振动、静音 改变一组相关流的行为
Zen / DND 勿扰策略限制某类声音 决定允许什么声音和哪些调整

所以 getStreamVolume() 返回非零，不足以证明能听见；导航播报时音乐变小，也不意味着 STREAM_MUSIC 的用户档位被改低。后面排障时要按这些不同状态逐层判断。

5. 一次音量调整：从请求到 native，再到设置保存

5.1. “音量键调谁”与“怎样调整”是两个问题

物理音量键先由输入、窗口/媒体会话等上层机制分发，具体产品还可能让活动 MediaSession 或远端会话处理。本文从请求已经进入 AudioService 开始分析，不假设所有按键都直接调用同一个方法。

adjustSuggestedStreamVolume() 先决定目标流，考虑强制控制流、当前活跃流、默认建议和外部音量控制器等，再进入调整逻辑。adjustStreamVolume() 则已经给定 stream，表达“加、减、静音、取消静音”等方向；setStreamVolume() 表达“设置到指定档位”。

因此“音量键调错流”要先查目标选择；“流选对但档位没动”才进入权限、alias、设备行为和安全音量检查。远端媒体会话的音量也不能强行套成本机扬声器的 VolumeStreamState。

5.2. 调整前为什么有那么多检查

adjustStreamVolume() 的主干不是先加一再补救，而是先建立允许调整的条件。源码中的关键判断可以按因果顺序读：

  1. 全局固定音量模式可直接返回；替换 SCO stream 的 feature flag 可能先转换目标流。
  2. 校验方向和 stream，检查此流是否可静音；语音流静音、助手流等有额外权限条件。
  3. 找到 stream alias 和目标设备，读取该设备旧 index。
  4. 验证包名、UID 与 AppOps；系统 UID 发来的请求还要按当前用户处理相关限制。
  5. 计算步长。普通路径由内部十倍单位及比例换算得到；固定音量设备可能用整个允许范围作为一步。
  6. 检查铃声模式、Zen/DND；某些加音量/取消静音动作不能越过当前策略。
  7. 若由绝对音量控制器处理 adjustment，转发给它并返回。
  8. 对允许的请求，修改 mute 或 index；安全音量可能拦截继续加大。
  9. 投递实际设备音量更新，并按设备类型协调蓝牙、HDMI 与 UI 等后续行为。

这是阅读顺序，不是对所有 flag 组合的穷举。尤其不要把“没有抛异常”当成音量一定发生变化：不少拒绝路径是返回、无操作或仅显示提示。

5.3. 具体例子：扬声器媒体音量从 5 调到 6

先限定条件：普通可调扬声器、媒体 alias 仍是媒体、无静音/勿扰阻止、无安全音量拦截、无外部控制器接管，步长因子为 1，未到上限。输入是 STREAM_MUSIC + ADJUST_RAISE。

5.7. 四个“音量不动”分支

固定音量与满音量。 全局 mUseFixedVolume 可以让调整入口无操作。mFixedVolumeDevices 表示特定设备上的固定音量行为，媒体路径可能在 0 与最大允许值之间切换；mFullVolumeDevices 则在应用音量时走 full-volume 逻辑。两者不能按名字猜成同一集合。

绝对音量。 蓝牙或其他控制器可接收统一档位/调整请求。对应 flag 用于识别来源，避免把远端报告的变化又无限发回远端。排障要同时看本地 index、设备行为、协议支持及远端设备结果。

铃声与勿扰。 checkForRingerModeChange() 可能把某次音量动作转成铃声模式变化；volumeAdjustmentAllowedByDnd() 可能不允许调整。请求触发勿扰变化时，setStreamVolume() 还检查通知策略访问资格。

安全音量。 SoundDoseHelper 判断媒体 alias、受保护设备和安全阈值等条件。设置指定档位时，超阈值请求可能保存为 mPendingVolumeCommand 并显示警告，用户通过正常 UI 确认后才有机会执行。增加音量路径也有安全提示判断。它不是“先调大再弹一个无关提示”。

这里有个容易读反的返回值：checkSafeMediaVolume_l() 返回 true 表示命中了需要安全音量处理的条件，并非“本次音量已经被证明安全”。

必须沿调用者继续读：willDisplayWarningAfterCheckVolume() 在上述条件为 true 时显示提示、记录待处理命令，并返回 true；调用方因此跳过正常设置分支。仅按方法名猜测布尔值含义，很容易把整个控制流解释反。

CSD（累计声音剂量）还涉及暴露累计和告警，与传统安全媒体音量不是完全相同的状态机；本树按配置决定它们的启用和协作。本文解释控制职责，不把源码中的阈值或产品配置推广成通用健康建议。

6. 音频焦点：从请求仲裁到播放器行为

6.1. 焦点到底管理什么

导航和音乐可以在硬件上同时播放，但“能混在一起”不意味着“用户体验上应该一样大声”。焦点协议让声音发起者表达短时打断、长期占用、允许被压低等需求，系统再把影响传给已有持有者。

每次请求由 AudioAttributes、gain 类型、clientId、调用 UID/包名、目标 SDK、flags、回调接口和 Binder token 等共同描述。FocusRequester 把这些数据与当前 loss 状态封装起来；它不是 AudioTrack，也不是每个 UID 永远唯一的一份对象。

请求 gain 常见意图 对既有持有者的典型影响
AUDIOFOCUS_GAIN 较长期占用，如新的音乐播放 可能造成永久 loss
GAIN_TRANSIENT 短时占用 通常 transient loss，之后可恢复
GAIN_TRANSIENT_MAY_DUCK 短时声音，允许其他声音压低继续 可能产生 can-duck loss
GAIN_TRANSIENT_EXCLUSIVE 希望暂时独占的场景 焦点协议中的更强临时需求，不能据此保证所有硬件声音消失

这里是主干语义，不是无条件映射表。已有 loss、锁定持有者、外部策略、多焦点配置与播放器类型都会影响后续行为。

6.2. 请求先过准入，再进入焦点仲裁

AudioManager 通过 IAudioService.requestAudioFocus() 发请求。AudioService 先检查 attributes usage、参数、锁定焦点权限等，再调用 HardeningEnforcer 和 MediaFocusControl。

本树 HardeningEnforcer.blockFocusMethod() 检查 OP_TAKE_AUDIO_FOCUS；目标 SDK 低于 VANILLA_ICE_CREAM 有兼容放行分支，特权身份也可能在上层绕过该阻止检查。因此，看到“焦点失败”时不能直接认定是另一播放器占着栈顶，应先判断是否根本没有通过准入。与前台资格相关的策略最终如何反映在 AppOps，还需结合设备上的权限策略和应用状态观察。

Binder token 用于 linkToDeath()：应用进程在主动 abandon 前崩溃，系统仍可清理其请求。失效 client 不应该永远留在焦点结构里占位。这里用的是 Binder 生命周期，不是靠播放器自己保证执行 finally。

6.3. 默认栈怎样处理新请求

在没有外部焦点策略、未走多焦点特殊分支的普通路径中，MediaFocusControl.requestAudioFocus() 在焦点锁内做以下事情：

  1. 判断能否重分配焦点。栈顶是锁定持有者时，普通请求可能失败；允许 delayed gain 的请求可等待。
  2. 对相同客户端的重复请求做匹配、清理或复用处理。
  3. 创建 FocusRequester，关联死亡监听。
  4. 若需延迟，将请求插入锁定持有者下方；否则传播新 gain 对旧请求的 loss，再把新请求压入栈顶。
  5. 返回 grant/delay/failure，按路径通知焦点观察者。

普通立即授予分支中的顺序值得注意：先传播 loss，再压入新请求。不能把焦点栈想成简单的“只通知旧栈顶，再覆盖一个全局变量”。propagateFocusLossFromGain_syncAf() 会遍历现有栈中的请求并处理影响；永久 loss 的请求可能被移除，临时 loss 的请求可以保留以等待恢复。

abandonAudioFocus() 或死亡清理移除请求后，如果需要，系统通知可恢复的栈顶。恢复表示焦点状态变化，播放器是否正确恢复业务进度，仍要看应用和框架播放器控制的处理结果。

6.4. GRANTED、DELAYED 与外部策略等待

结果 应用应该理解为 不应理解为
AUDIOFOCUS_REQUEST_GRANTED 此次请求被授予 音频输出和路由已经建立
AUDIOFOCUS_REQUEST_DELAYED 接受等待，后续 gain 才能开始预定播放 已获得焦点，可以立即播放
AUDIOFOCUS_REQUEST_FAILED 此次请求失败 系统一定对所有播放通路施加静音

延迟焦点不是调用线程一直阻塞到电话结束。它是一种“先记录等待者，之后回调”的协议。外部策略等待又是另一条机制，不要把它和 DELAYED 混为一谈。

旧印象往往是“框架只发通知，应用自己调小音量”。本树并不止于此：FocusRequester.handleFocusLoss() 会尝试 frameworkHandleFocusLoss()，符合条件时由框架实际控制播放器。

先看框架处理入口：

图中的菱形概括分散在 FocusRequester 与 PlaybackActivityMonitor 中的条件，不是一处独立的同名函数。它以默认焦点、无外部 duck 接管的普通场景为前提；左路也要满足播放器可处理条件，箭头仅表示处理方向，省略线程与 IPC。

MediaFocusControl 再委托 PlaybackActivityMonitor.duckPlayers() 找出 loser UID 下正在启动状态的播放器。它还检查是否是语音内容、是否属于不能自动 duck 的播放器类型。本树 UNDUCKABLE_PLAYER_TYPES 包含 AAudio、SoundPool 对应类型，不能把支持范围推广成所有播放器。

符合条件时，DuckingManager 通过播放器代理应用 VolumeShaper，并记住被 duck 的 UID，后续新启动的同 UID 播放器也能按状态处理。若框架已经处理，某些 loss 通知不再按普通路径交给应用，所以“回调没来但音乐变小”可以是预期结果。若不满足自动处理条件，则回到应用通知等路径。

CONTENT_TYPE_SPEECH 是有意义的反例：把有声书压得太低可能损害可理解性，所以常规非 forceDuck 路径会放弃框架自动 duck，让应用处理焦点损失。forceDuck 又可改变该判断，不能省掉这个前提。

应用回调还要跨 Binder，再投递到应用 Handler

需要通知应用时，FocusRequester 调用 IAudioFocusDispatcher.dispatchAudioFocusChange()。AudioManager 的 Binder 回调通过 clientId 找到注册的 listener 与 Handler，再投递 MSSG_FOCUS_CHANGE，最终由应用侧 Handler 调用监听器。

这意味着系统决定 loss、Binder 通知抵达、应用 listener 执行、应用实际暂停是四个不同时间点。注册时选择的回调 Handler 如果忙碌，业务处理就可能延后；不能把“服务端调用了 dispatcher”当成“应用已经停播”。初始 GRANTED 也通常由请求返回值告知，不应假设每次成功请求都还必须等待一个独立 GAIN 回调才证明授予。

还有一条独立分支：若外部策略接管 duck，handleFocusLoss() 可在框架自动处理之前按 mustNotifyFocusOwnerOnDuck() 等条件停止普通通知。因此排查“没有回调”时，要同时区分框架自动 duck 和外部 duck 接管，不能把二者混为一种原因。

6.6. Fade-out 与 duck 的区别

Ducking 是暂时压低，通常期待之后恢复；永久焦点 loss 的某些路径则尝试 fade-out。FocusRequester 若成功启动 fade，会记录 mFocusLossFadeLimbo，通过 postDelayedLossAfterFade() 延后发送 loss。

这说明“loss 回调时刻”不一定等于“声音开始变小的时刻”，也不等于“栈中的全部资源已经释放”。fade 能否应用仍依赖播放属性、UID、播放器与当前配置。本文只讲经过核对的调度关系，不把任意媒体播放都承诺成固定时长的淡出。

贯穿场景至此可以预测：音乐 6 档，导航申请 GAIN_TRANSIENT_MAY_DUCK；若框架自动 duck 成立，音乐实际变小，但媒体档位仍可能是 6。导航 abandon 后，恢复焦点/播放器形状的路径使音乐恢复。若音乐声明 pause-on-duck，或播放语音内容，则不能用同一结果推演。

7. 设备切换：连接事实、策略偏好与实际路由

7.1. 为什么“耳机已连接”不等于“音乐已走耳机”

音频设备有三个不同层面的状态：

  1. 连接事实：系统当前认为哪些设备可用，类型、地址、名称和能力是什么。
  2. 策略输入：媒体/通信偏好、模式、force use、动态 mix 等告诉策略引擎如何选择。
  3. 实际路由：某个活跃播放客户端最终使用的 output、device、audio patch 与 HAL 通路。

AudioDeviceInventory 的 connected devices 主要回答第一层；AudioDeviceBroker 协调第二层的许多输入；native AudioPolicyManager 结合播放属性、可用设备和配置形成第三层的选择。连接列表有耳机，只能证明它进入了可用候选范围，不能单独证明当前播放器路由到了它。

同样，AudioRoutesInfo 中的主路由摘要不是每条 track 的完整路由快照。分析具体播放要继续关联 native policy client、output 与 AudioFlinger track。

7.2. 一次有线耳机连接怎样被处理

上游有线、USB 或蓝牙组件报告变化后，设备操作经 AudioService/Broker 进入 Inventory。不同传输类型入口有所区别，这里跟踪有线状态路径。

Inventory 的入队方法非常短，但揭示了两个关键动作：先计算 noisy 通知及延迟，再把连接状态交给 BrokerHandler。

BrokerHandler 收到 MSG_L_SET_WIRED_DEVICE_CONNECTION_STATE 后，在设备状态锁下调用 onSetWiredDeviceConnectionState()。后者执行连接处理、调整相关蓝牙媒体行为、检查音乐活动/HDMI 条件，发送连接广播并更新路由摘要。

handleDeviceConnection() 使用设备类型和地址构造 key；这与第 4 章 stream 音量 map 的 key 粒度不同。它调用 AudioSystemAdapter.setDeviceConnectionState() 把设备可用性送入 native。连接路径只有 native 返回成功才加入 mConnectedDevices；重复相同状态会按幂等方向处理，不把每个重复事件都当成新插入。

断开路径则通知 native unavailable，再移除本地记录，并触发通信设备移除检查。源码注释明确说明，即便断开失败也移除本地记录。因此排查异常恢复时，Java 与 native 暂时不同步是需要考虑的情况，不能断言两者每个瞬间都严格一致。

7.3. 拔耳机为什么先发 AUDIO_BECOMING_NOISY

若音乐突然从私密耳机外放，用户通常不希望等外放之后应用才知道。checkSendBecomingNoisyIntentInt() 判断是否存在这种转换风险，条件满足时先投递广播，并给设备断开处理加上 BECOMING_NOISY_DELAY_MS 延迟。

这个判断不是“任何设备拔出都广播”。本树会检查：

  • 必须是断开事件，且设备属于可能导致 noisy 的集合。
  • 断开的设备与媒体当前设备相关，或当前在通信状态。
  • 剩余 noisy 设备类型满足 isSingleAudioDeviceType() 的条件。
  • 没有相关媒体动态策略介入，媒体设备也不是 remote submix。
  • 存在媒体播放活动或焦点使用者；否则可能直接放弃广播。

这里的集合按设备类型处理，不能直接翻译成“只剩最后一只物理耳机”。多个同类型设备、动态路由和通信场景都要按实际代码条件理解。

广播与延迟提供了应用暂停的机会，不是等待应用回复的握手机制，也不是“AudioService 保证在断开前暂停所有播放器”。应用如何注册并响应广播、是否及时暂停，以及硬件何时真正失去连接，都影响最终听感。

回到场景：音乐正在耳机上播放，拔掉耳机；条件成立则应用收到 noisy 事件，可先暂停，随后设备状态被更新，APM 根据可用设备重新计算路由。若音乐已经暂停，仍不能仅由“后来没外放”推断系统没有重路由——可能只是没有待输出的音频数据。

7.4. 蓝牙不是一个开关

蓝牙音乐播放、电话双向语音、LE Audio 和助听器有不同的设备类型、协议及控制路径。Broker 协调设备与模式，BtHelper 处理 profile/SCO 等交互，Inventory 更新设备可用性与偏好，APM 决定实际路由。

情况 必须区分的状态 常见误判
A2DP 媒体 profile 连接、active device、音频设备可用、媒体路由、绝对音量 蓝牙图标亮就等于媒体走蓝牙
SCO 通信 请求者、SCO 连接过程、模式 owner、通信首选设备 调用 start/request 就等于 SCO 已建立
LE Audio LE 设备与组、上下文、设备音量控制 用经典 A2DP 的所有假设套用
助听器 对应设备状态与音量适配 将音量 index 原样当成远端增益

本文不展开蓝牙协议状态机，但要保留这个边界：AudioService 管理/协调需求，不代替 Bluetooth 服务完成射频和协议连接。 API 成功受理、profile 成功建立和实际音频出声仍是不同完成点。

8. 通话模式与通信设备：两套相关但独立的仲裁

8.1. setMode 不是“给当前应用加个标签”

MODE_NORMAL、MODE_RINGTONE、MODE_IN_CALL、MODE_IN_COMMUNICATION 是系统音频模式。它影响 native 策略、相关音量处理和通信路由。多个应用可能同时提交模式需求，所以 AudioService 保存 SetModeDeathHandler 列表，记录调用者、模式、权限、活跃情况和更新时间。

普通应用不能随意冒充蜂窝通话：setMode() 先检查音频设置权限，MODE_IN_CALL 等受保护模式还要求 MODIFY_PHONE_STATE。通信应用常用的 MODE_IN_COMMUNICATION 也不能据此与电话模式等同。

MODE_NORMAL 的请求会移除本调用者的模式记录。它不是无条件清空所有其他调用者，然后强制整个系统正常模式。这个差别解释了为什么某个 VoIP 应用退出后，如果还有真正的通话请求，系统仍可以留在通话模式。

因此“最后一次 setMode 永远获胜”不成立。普通通信应用进入模式时，本树会暂时设置播放/录音活跃状态，并延后检查真实活动，避免应用先设模式、稍后才启动播放/录音时立刻被当成不活跃。后续播放与录音状态能影响模式 owner。

选出 owner 后，onUpdateAudioMode() 调用 mAudioSystem.setPhoneState(mode, uid)。只有成功，才更新 mMode、分发模式变化，重新应用相关音量/alias，并通知 Broker 模式 owner。这里又体现了“请求的模式”和“成功应用的模式”必须区分。

客户端异常死亡时，death handler 清理请求并触发重评估。这是防止残留模式的重要机制，但不代表所有通话后的无声问题都必然由死亡清理解决；路由、播放器和 HAL 状态仍可能各有问题。

8.3. setCommunicationDevice：提交偏好，不是直接打开扬声器

通信应用可选择适用的通信设备，AudioService 校验后将请求交给 Broker。Broker 保存按调用者关联的 CommunicationRouteClient，协调模式 owner、请求优先级、可用设备与蓝牙 SCO 状态。

setCommunicationRouteForClient() 保存请求，并在需要时启动/停止 SCO，失败时清理或恢复先前客户端选择，再更新通信路由。updateCommunicationRoute() 通过通信策略相关的设备偏好把结果交给下层。

“请求的设备”“当前首选设备”“实际 active communication device”可能短暂不同。特别是蓝牙连接需要时间，不能把 true 返回直接展示成“用户已听到耳机声音”。应结合通信设备变化回调、Broker 状态和 native route 判断。

8.4. 焦点、mode、route 三者不是互相替代的 API

控制 主要作用 单独调用不能保证
requestAudioFocus 协调与其他声音的关系 进入通信模式、选择扬声器
setMode 声明/仲裁系统音频模式需求 获得焦点、建立 SCO、启动录音
setCommunicationDevice 提交通信设备选择 自动创建播放/录音轨道、获得麦克风权限

贯穿场景中，音乐遇到语音通话，往往同时看到焦点变化、mode 变化、通信设备调整和录音活动。但这些是业务场景把多条控制链组合在一起，不是一个 API 必然隐式完成全部工作。

9. 播放/录音监控与麦克风静音

9.1. 为什么系统还要维护播放器列表

焦点请求告诉系统“应用想获得什么”，却不能完整说明“实际有哪些播放器正在播放”。一个应用可以有多个 player，也可能拿着焦点没有启动播放。PlaybackActivityMonitor 保存 player interface ID、UID/PID、播放器类型、attributes 和状态等，接收注册、属性变化、start/stop/release 等事件。

这份状态使框架能够把焦点决策落到具体 player：duck/fade、通话期间的播放器控制、播放活动回调，以及 mode 活跃状态判断。它不是 PCM 数据缓存，也不以音频波形为输入判断“用户听到了什么”。

本树注释明确指出部分 player 更新是 oneway 调用：报告操作具有异步性。观察焦点、player 配置与 native track 时，要允许采样时刻不同造成的短暂差异，不能只取三份相隔很久的 dump 就声称获得同一时刻的一致快照。

9.2. 录音监控也不等于录音授权

RecordingActivityMonitor 处理录音配置更新、活跃录音查询与回调，向普通客户端分发时有匿名化路径。它可以帮助判断当前有哪些录音活动，但不替代 RECORD_AUDIO、AppOps、传感器隐私和 native 并发采集策略。

有录音配置不等于采集到非静音数据；录音无声也不能直接归因于 AudioService 的模式。完整排查还需关联录音 source、device、client silenced 状态、隐私开关和 native input。本文覆盖其与 AudioService 的协作，不展开 AudioRecord 缓冲和并发采集完整算法。

9.3. 麦克风静音是多个来源合成的结果

本树区分 API 请求、物理开关、用户限制和隐私开关四个来源：

setMicrophoneMuteNoCallerCheck() 在适用用户条件下调用 native mute，再查询真实状态更新 mMicMuteFromSystemCached，即使设置调用失败也以查询结果维护缓存。它区分了“希望静音”和“底层报告静音”。

因此应用调用取消静音，只能撤销其 API 来源的要求，不能绕过物理开关或隐私策略。另一个细节是本树公开 isMicrophoneMuted() 对隐私来源做了额外过滤：公开 API 返回值不能简单等同于这四个布尔值的 OR。验证麦克风问题应结合隐私状态和 native 状态，而不是只盯一个 getter。

9.4. 空间音频与系统音效在本篇的位置

SpatializerHelper 维护空间化相关能力、设备与启用状态，audioserver 恢复时也需要重新建立状态；实际空间音效处理不在 AudioService 的普通 Java 消息循环中逐帧执行。SoundEffectsHelper 管理系统音效加载/播放，不等于所有应用音乐都由它统一播放。

这两部分是理解服务全貌所需的职责定位；本篇不展开空间化算法、头部跟踪传感器融合或 SoundPool 资源管理细节。

10. 动态 AudioPolicy：把部分决策交给特权组件

10.1. 为什么需要外部策略

普通手机的默认焦点栈和音量模型不一定足以描述车载多区域、投射、虚拟设备等产品需求。框架因此允许经过权限检查的组件注册 Java AudioPolicy，并按能力接入焦点、音量或动态混音规则。

registerAudioPolicy() 校验注册资格与配置，创建 AudioPolicyProxy，保存 callback 和 Binder 生命周期。不同能力的权限与投射条件不同，不能概括为“有 MODIFY_AUDIO_SETTINGS 就能任意接管音频”。

10.2. 一份注册对应三条不同的控制关系

能力 服务端处理 最终影响
焦点观察者 addFocusFollower() 观察焦点事件，不自动成为决策者
外部焦点策略 setFocusPolicy() 焦点请求转交策略回调，等待结果
外部音量控制器 setExtVolumeController() 特定音量调整路径转交外部组件
动态 mix connectMixes() → registerPolicyMixes() native 策略按 mix 规则建立相应路由行为

AudioPolicyProxy 构造函数中分别设置这些关系，随后调用 connectMixes()。这证明了“焦点接管”和“native mix 注册”是并列能力，不是同一条转发链。

clearCallingIdentity() 让经过校验后的系统内部工作使用服务自身身份；finally 恢复原身份。这不表示可以把前置权限检查删除，也不能把它当成“所有调用都会自动获得系统权限”的通用写法。

10.3. 外部焦点策略改变了哪条主线

在 MediaFocusControl.requestAudioFocus() 中，如果存在 mFocusPolicy，会调用 notifyExtFocusPolicyFocusRequest_syncAf()，成功则返回内部等待结果状态，停止继续按默认焦点栈授予。

外部策略通过相应 API 报回决策，AudioManager 端有 BlockingFocusResultReceiver 等结果协调逻辑。这个有限等待结果机制与“电话占用时返回 DELAYED，未来收到 gain”不是一回事。

因此车载焦点问题不能只看默认 mFocusStack 是否符合手机模型；应该先确认是否注册了外部 focus policy，再检查其回调和决策。AudioPolicyService 并不是这条 Java 焦点回调链的中转站。 它处理的是 native 路由等职责。

10.4. 策略退出与恢复同样属于生命周期

策略进程死亡、主动注销或投射停止时，需要释放注册关系、mix、focus policy/observer 及其他关联状态。持有配置并不意味着可永远有效使用。

audioserver 重启时，Java 侧仍存在的代理会尝试重新 connectMixes() 与恢复设备 affinity；本树会收集恢复失败的代理并释放。注册曾经成功，不保证未来每次恢复都成功。第 11 章将它放回整个恢复流程中看。

11. audioserver 死亡后：重新下发状态，而不是重建所有业务

11.1. 谁发现死亡，谁执行恢复

AudioService 注册 AudioSystem.ErrorCallback。收到 AUDIO_STATUS_SERVER_DIED 后，回调通知播放/录音监控器，并投递 MSG_AUDIO_SERVER_DIED 和服务状态分发消息。恢复主体在 AudioHandler 调用的 onAudioServerDied() 中执行。

这个方法名容易误导：它既处理“还没恢复，继续等待”，也处理“native 服务已经回来，重建配置”。

AudioService 并不是在这里 fork 一个新的 audioserver。native 服务进程的拉起属于其服务生命周期管理；AudioService 的任务是在发现可用后，把仍掌握的控制状态重新下发。

11.2. 恢复哪些内容，为什么需要重放

audioserver 里的 AudioPolicyManager、输出和相关 native 对象重建后，不会自动拥有 system_server 还保存着的全部状态。本树恢复内容包括：

状态 恢复方向 依据位置
连接设备、蓝牙与设备角色 Broker → Inventory → AudioSystem MSG_RESTORE_DEVICES、onRestoreDevices()
当前 mode 重新选择 owner 并设置 phone state onUpdateAudioMode(... force=true ...)
stream 音量及 volume groups 初始化范围、应用设备音量、恢复组 onReinitVolumes()、restoreVolumeGroups()
铃声、mono、balance、surround 等 从 Java/设置状态重下发 onAudioServerDied() 内各更新调用
动态策略 mix 与 affinity 每个 proxy 尝试重连 connectMixes()、setupDeviceAffinities()
capture policy、空间化、声音剂量 恢复或重置相关 helper/native 关系 playback monitor、SpatializerHelper、SoundDoseHelper
麦克风静音与其他系统信息 重新计算并应用 microphone mute、vibrator info 等

这是恢复职责表，不是严格同步完成的时间轴。尤其 mDeviceBroker.onAudioServerDied() 会投递 MSG_RESTORE_DEVICES 到另一个线程；AudioService 后续代码继续执行。因此不能因为函数里设备恢复调用写在音量恢复之前，就声称所有设备恢复都已结束后才开始音量恢复。

Broker 消费恢复消息时重新初始化策略 ID、恢复设备、重应用蓝牙状态和通信路由。本地 UAC2 扩展还在 Broker 完成后收到 onUac2AudioDevicesRestored()，这恰好说明“发出恢复请求”和“对应线程完成恢复”需要不同通知点。

11.3. 恢复也可能失败

Inventory 重报设备时，asDeviceConnectionFailure() 开关启用后会收集恢复失败设备并移除对应记录，必要时清理 SCO active device。AudioPolicyProxy 的 mix 或 affinity 恢复失败会导致代理释放。

所以“服务已经 started”并不能证明每项状态都完整恢复。更不能推断所有应用无需处理错误就能继续播放：旧 track、录音会话、应用媒体对象以及其缓冲中的数据可能需要各自恢复或重建。AudioService 重放的主要是控制状态，不是替每个应用保存和重放此前的 PCM。

11.4. 本地 UAC2 扩展的边界

本树 Uac2AudioRouteController 明确把用户请求、USB transport 和路由 lease 作为分开的状态处理。构造时读取产品支持开关，在 onSystemReady() 启动，并在音量变化、audioserver 恢复及设备恢复完成处接入。

这意味着在本机源码上调试 USB 收发音频时，除了标准 AudioService/Broker/APM，还要检查这套扩展的有效状态和恢复时序。它不是本文默认手机场景的前提，也不是 upstream AudioService 必然拥有的类。本文只核对其接入位置，不展开 USB transport、HAL bridge 和路由 lease 的完整实现。

12. 把贯穿场景完整走一遍

下面所有数值均为解释机制的假设，不是真机采集。产品采用默认焦点策略、普通可调音量，音乐与导航来自不同 UID，未启用多焦点特殊分支。

12.1. 音乐开始播放

音乐应用以媒体 attributes 申请长期焦点，准入通过后，MediaFocusControl 记录请求并授予。应用建立并启动实际播放器，播放监控器开始记录 player 活动；native policy 为其选择输出和设备，AudioFlinger/HAL 完成数据输出。

此时分别存在焦点请求、player 配置和 native track/output。它们相互关联但不是同一对象。焦点成功但播放器未 start，用户仍听不到声音。

12.2. 用户按音量加

请求目标最终确定为媒体，当前设备是扬声器。alias 对应媒体，内部 index 从 50 变成 60；AudioHandler 应用整数档位 6，APM 按扬声器相关音量曲线处理，保存消息稍后把设置写入当前用户。

如果紧接着又按一次，状态可能先变成 70。由于消息持有状态对象，不能按第一个消息的身份推定它一定应用过 60。验证时需记录请求时间、状态更新和下发日志。

12.3. 导航短时播报

导航申请 MAY_DUCK。满足框架自动处理条件时，音乐 UID 的合适播放器被 VolumeShaper 压低，媒体 index 仍可保持 70。导航结束并 abandon，焦点/播放器恢复路径使音乐回到原有增益。

若音乐内容是 speech、应用要求 pause-on-duck，或播放器类型不支持自动 duck，则检查应用回调处理；不能用“导航来了”直接预测唯一结果。

12.4. 插入耳机，再拔出

插入先成为设备事件，经 Broker/Inventory 向 APM 报告可用。APM 若按策略选择耳机，应用对应耳机设备音量，例如此前记住的 4 档。这里有两个同时发生但不同的变化：路由换设备，音量换设备对应状态。

拔出时若 noisy 条件成立，先广播，再延迟处理设备状态变化。应用可能暂停；native 策略在耳机不可用后选择剩余设备。扬声器原来保存的 7 档仍是后续应用音量的依据之一，而不是直接继承耳机 4 档。

12.5. 语音通话接管

通信应用分别申请焦点、请求 MODE_IN_COMMUNICATION、选通信设备并启动录放音。模式 owner 由权限、活跃与更新时间选出；Broker 按通信客户端与模式状态协调路由。若选择蓝牙，连接阶段与最终活动设备可能不同步。

通话结束，应用放弃焦点、清除设备请求、恢复自己的 mode 请求并释放录放音资源。某一项遗漏可能留下异常行为；死亡监听能帮助处理进程退出，不能替代正确的业务生命周期。

12.6. 此时 audioserver 恢复

AudioService 发现 native 可用后重放音量、模式、设备和策略等控制状态。设备恢复在 Broker 线程继续处理，应用播放器也可能需要各自恢复。最终应同时观察 Java 控制状态、native 路由/输出和应用播放结果，不能用一条“started”日志证明场景完全恢复。

13. 怎样验证：按证据层次缩小问题

13.2. 实验 A：验证设备音量与异步保存

操作：使用普通媒体播放器在扬声器播放，记录当前媒体档位；按一次音量加；分别立即、稍后采集 audio/policy 快照；再插上有线耳机并观察音量，最后拔出并重新观察。

重点看媒体对应设备的 index、是否静音、alias、native 音量组和设备。Settings 项名应由实际设备和 getSettingNameForDevice() 推导，不假设所有产品都只有一个 volume_music 值。

预期：普通无拦截分支下，目标设备的档位变化；耳机与扬声器可能各有不同值。立即快照与稍后快照可能不同，但没有捕捉到差异不代表不存在异步：adb 往返本身足以覆盖短暂窗口。若要验证线程级时序，需要在自有调试构建增加精确日志/trace，而不是凭两份粗粒度 dump 推断毫秒级顺序。

13.3. 实验 B：区分自动 duck 与应用暂停

使用两个可控测试应用：音乐应用以媒体/音乐内容播放并申请 GAIN；导航应用短时申请 MAY_DUCK。记录双方焦点回调、播放状态和请求返回值，同时采集 audio 与 AudioFlinger 状态。

做两组对照：第一组允许常规自动 duck；第二组让音乐请求声明 pause-on-duck，并由测试应用在回调中真正暂停。还可以将内容改成 speech，对照框架自动处理分支。

预期第一组可能在媒体档位不变时音乐变小，且普通 duck 回调不按预想出现；第二组应结合回调与应用 pause 日志确认行为。仅凭听感不能判断是系统 VolumeShaper、应用音量、DSP duck 还是换路由；必须结合播放器配置与控制记录。

外部焦点策略或多焦点配置启用的设备应另建对照，不把它们和默认栈混测。

13.4. 实验 C：耳机断开与 noisy 事件

在可控播放器记录 ACTION_AUDIO_BECOMING_NOISY 接收时间与暂停时间，播放中拔出有线耳机；比较 Broker/Inventory 设备日志和 native policy 设备变化。再以“无媒体播放、无焦点使用者”重复。

预期第一组在满足条件时广播先于延迟设备处理，第二组可能因不构成 noisy 场景而不广播。广播到达不证明应用已经暂停；广播缺失也不直接证明异常，先核对动态策略、设备类型集合、媒体活动和当前路由条件。

物理断开实际发生时刻不由 Java 延迟保证。若分析的是极短外放泄漏或蓝牙切换爆音，需要更细的 native/HAL 日志与录音测量，本实验只能解释上层控制顺序。

13.5. 实验 D：通信模式残留

启动一个可控 VoIP 场景，分别记录 setMode、焦点请求、选通信设备和录放音启动。正常退出一次，再在测试设备上让该测试应用进程异常退出一次，观察 mode owner、通信客户端和焦点请求是否重新评估。

预期正常退出会主动清理；进程死亡会触发相应 death handler。若模式没有回到 NORMAL，先检查是否有其他活跃或特权请求者，而不是立即判断清理失败。若 mode 已恢复但仍无声，再检查设备路由、音量和播放器生命周期。

13.6. 实验 E：audioserver 恢复

这是会打断整机音频的实验，仅适合已授权的专用调试设备和可控环境。本文没有执行服务停止或进程终止命令；需要按设备构建支持的管理方式触发 audioserver 重启，再保存前后 PID、生命周期日志和三层 dump。

观察时先关联死亡通知与 AudioFlinger 可用检查，再分别核对配置重放、Broker 设备恢复、动态策略重连结果和应用实际重新播放；它们包含跨线程过程，不能把采样清单当成严格串行时序。对照媒体音量、通信 mode、设备集合、mix 与麦克风状态。

预期是相关控制状态尝试恢复，不承诺播放无缝。若 Java 保存值正确但 native 缺少设备，查 Broker/Inventory 恢复返回值；若 mix 不见，查代理重连是否失败；若两层状态正常但应用不响，继续查 track 是否重建。

14. 分层记忆与源码导航

14.1. L0：只记住这幅全局图

14.2. L1：能够独立展开的五条主干

  3. 焦点：准入 → 默认栈或外部策略 → loss/gain → 框架 duck/fade 或应用回调 → abandon/death 清理与恢复。
  4. 设备/通信：连接事件 → Broker 队列 → Inventory/native 可用性 → 模式与偏好 → APM 实际路由。
  5. 恢复：发现死亡 → 等待 native 可用 → 重放 Java 保留状态 → 各协作者恢复；应用媒体对象仍有自己的生命周期。

15. 自测：先预测，再展开答案

15.1. 基础题

题 1：AudioManager、AudioService 与 AudioPolicyService 各在哪个进程？PCM 必须经过 AudioService 吗？

展开参考答案

AudioManager 通常在应用进程，AudioService 在 system_server，AudioPolicyService 在 audioserver。普通 AudioTrack 播放数据不把 AudioService 当成逐帧 PCM 中转站。AudioService 负责控制请求、状态和策略协调；JNI 与 Binder 的边界也不同。回看第 2 章。

题 2：内部 index=60 能否直接解释成 60 dB，或每一只耳机都分别保存了 60？

展开参考答案

不能。普通 stream 路径通常用十倍整数表示 UI 档位，60 对应第 6 档，native 再结合曲线与设备处理。VolumeStreamState 的 map 按 native 设备类型保存，不等于每个蓝牙地址或 AudioDeviceInfo ID 都有独立项。回看 4.2、5.5 节。

题 3：音量调整方法返回后，设备音量和 Settings 一定都更新了吗？

展开参考答案

不一定。可能在检查阶段被拒绝，也可能只更新了 Java 状态并入队；实际下发在 AudioHandler 消费，保存是后续延迟消息。连续请求还会共享可变状态对象。不能从返回时刻推出硬件完成或落盘完成。回看 3.4、5.2—5.6 节。

题 4：为什么 AudioService 既需要焦点请求对象，又需要播放器监控对象？

展开参考答案

焦点请求表达应用的协调需求，player 配置表达实际播放器活动。应用可能持有焦点但没有播放，也可能有多个播放器。框架要把 duck/fade 落到具体 player，必须关联 UID、属性、类型和状态。回看第 6 章与 9.1 节。

15.2. 场景推理题

题 5：导航播报期间音乐明显变小，STREAM_MUSIC 仍是 7，而且音乐应用没收到预期的 duck 回调，这是必然的 bug 吗？怎样验证？

展开参考答案

不是。满足条件时，框架可以用 VolumeShaper 自动 duck，保持用户档位不变，并不走预期的普通应用回调分支。应检查 gain/loss、不同 UID、SDK/flags、内容类型与 player 类型，再看播放监控中的 duck 状态和应用日志。若用了外部策略或 DSP，还需检查对应执行者，不能只凭听感定性。回看 6.5 节及实验 B。

题 6：拔耳机时没有收到 noisy 广播，是否说明设备事件丢失？

展开参考答案

不能直接判断。广播有设备集合、当前媒体设备/通信、媒体动态策略、remote submix、媒体活动/焦点使用者等条件。先核对是否构成需要广播的场景，再查 Broker/Inventory 设备事件。广播与设备更新不是同一个状态。回看 7.2—7.3 节及实验 C。

题 7：VoIP 应用最后调用 MODE_NORMAL，系统为什么还可能保持通话模式？

展开参考答案

该调用主要清除该调用者的 mode 请求；其他活跃请求尤其特权持有者仍可能成为 owner。模式选择不是无条件最后调用者获胜。先看 mode requester 列表、权限、活跃和更新时间，再看 native setPhoneState 是否成功。回看 8.1—8.2 节及实验 D。

题 8：setCommunicationDevice 返回 true，但蓝牙还没出声，应该先怀疑哪个完成点被混淆了？

展开参考答案

返回 true 可表示请求被提交给 Broker，不证明 SCO/其他通信链路已建立，也不证明实际 active device 已切换。检查通信客户端、请求/首选/实际设备、蓝牙连接状态和 native route，最后检查播放器/录音是否启动。回看 8.3—8.4 节。

题 9：audioserver 恢复日志已出现，Java 音量正确，某条动态 mix 却不见了，可以断言恢复函数没执行吗？

展开参考答案

不能。恢复可能已执行，但 mix 或 affinity 重连失败，代理被释放；设备恢复还在另一个线程进行。应检查代理恢复返回值、相关日志和 native mix，区分未触发、执行中和执行失败。控制状态恢复也不保证应用 track 自动恢复。回看 10.4 节与第 11 章。

题 10：应用取消麦克风静音后仍然录到静音，是否应该反复调用 setMicrophoneMute(false)？

展开参考答案

先检查其他静音来源和录音条件。API 来源撤销不等于物理开关、用户限制或隐私开关撤销；公开 getter 还有隐私相关语义。应把期望静音、native 实际状态、录音配置/权限和 input 状态分别检查。回看 9.2—9.3 节。
