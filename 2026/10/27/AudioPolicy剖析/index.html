AudioPolicy 剖析

发表于 2026-10-27 | 分类于 Audio ， AudioPolicy
字数统计: 21.8k | 阅读时长 ≈ 101

1. 概述

AudioTrack 那篇讲的是”PCM 怎么写进去”，AudioFlinger 那篇讲的是”PCM 怎么混出来”，CarAudio 那篇讲的是”车载怎么接管控制面”。它们都不约而同地把同一个问题推到了本篇：App 拿着一个 AudioAttributes（或 stream type）创建播放/录音流时，到底是谁、依据什么，决定了这路声音走哪个 HAL、开哪种输出线程、落哪个设备、用多大的音量？

回答并执行这个决定的就是 AudioPolicy——Android 音频系统的”控制面大脑“。它常驻 audioserver 进程，与 AudioFlinger 并肩而立：

  • AudioFlinger 是数据面：收 PCM、重采样、混音、做特效、写 HAL，它只认 output/track，不知道”这路声音该去哪”；
  • AudioPolicy 是控制面：维护全部音频设备拓扑、为每条流选择 output 与设备、计算并下发音量、管理音频补丁（AudioPatch）、接待动态路由策略（AudioPolicyMix）、配合上层仲裁焦点。

一句话分工：AudioFlinger 搬砖，AudioPolicy 画图纸、发号施令。

Note

本文代码基线为 LineageOS 22.2（对应 Android 15，2024–2025 年 AOSP 主线形态）。不同版本间类名与细节有差异，但 “Service / Manager / Engine 三层 + XML 拓扑 + 策略引擎 + 动态 mix” 的骨架自 Android 10 起保持稳定。

1.1. “AudioPolicy” 一词的三种含义

阅读源码与文档时，”AudioPolicy” 至少指三个不同的东西，先厘清，后文不再混淆：

称呼 位置 是什么
AudioPolicyService（native 服务） frameworks/av/services/audiopolicy/service/ audioserver 里的 Binder 服务 IAudioPolicyService，对 AudioFlinger / AudioService（system_server）提供策略接口，内部持有 AudioPolicyManager
AudioPolicyManager（APM） frameworks/av/services/audiopolicy/managerdefault/ 策略的真正实现者：路由、设备、音量、patch、动态 mix。单实例、单线程模型
AudioPolicy（Java API） frameworks/base/media/java/android/media/audiopolicy/AudioPolicy.java 面向特权 App（如 CarService、穿戴、电视）的客户端侧策略注册 API：携带 AudioMix、注册焦点/音量接管

此外还有两个容易混淆的邻居，也划清边界：

  • 焦点（audio focus）不在 audioserver。MediaFocusControl 住在 system_server 的 AudioService 里（frameworks/base/services/core/java/com/android/server/audio/MediaFocusControl.java），维护焦点栈；audioserver 的 AudioPolicyService 只在”外部焦点策略”注册时做转发（第 12 章）。
  • 音量的”决策权”也不完全在 APM。用户档位（index）的存储、音量键处理、UI 事件都归 system_server 的 AudioService；APM 负责”档位 → dB → 写到输出/HAL”的下半场（第 9 章）。

1.2. 在音频栈中的位置

记住三条经线，后文全部沿它们展开：

  1. 注册经线：特权 App 用 Java AudioPolicy 注册动态 mix / 接管焦点与音量 → AudioService(AudioPolicyProxy) → audioserver APM registerPolicyMixes（第 11 章）；
  2. 选路经线：App 创建 AudioTrack → AudioFlinger createTrack → APM getOutputForAttr → 命中 output + 设备 → 建 AudioPatch（第 6、7 章）；
  3. 音量经线：AudioService 档位变化 → APM 曲线换算 dB → 软件音量写 AudioFlinger 或硬件增益写 device port（第 9 章）。

2. 三层架构与对象模型

2.1. Service / Manager / Engine 三层

audioserver 里的策略栈是一个清晰的洋葱结构，每层只依赖内层的接口：

三层各自的”一亩三分地”：

层 知道什么 不知道什么
Service binder、权限、异步命令、客户端回调 不做任何策略决策
Manager 全部运行态（可用设备、已开输出、clients、patch、mix）与决策流程 不直接碰 binder 事务、不解析 XML
Engine 规则表（strategy/音量组/曲线/force use/模式）与”纯函数式”的设备选择 不持有输出/clients 等运行态（通过 AudioPolicyManagerObserver 只读回调查询）

audio_policy_configuration.xml 里的每个标签都精确对应一个 C++ 类。这张对照表是阅读第 3、4 章的钥匙：

<mixPort name="deep_buffer" role="source" flags="..."> IOProfile HAL 暴露的一条流模板（输出 source / 输入 sink），带 flags 与能力集
<devicePort tagName="Speaker" type="AUDIO_DEVICE_OUT_SPEAKER"> DeviceDescriptor 一个设备端点（sink/source），可带 address、profile、gains

2.3. 坐标系：usage → strategy → volume group → stream

Engine 内部有两张独立的映射表，都以 audio_attributes_t 为入口：

  • 路由维度：getProductStrategyForAttributes()——把属性归入某个 ProductStrategy（如 STRATEGY_MEDIA），每个策略有独立的设备选择规则；
  • 音量维度：getVolumeGroupForAttributes()——把属性归入某个 VolumeGroup（如 music），每个组有独立的档位范围与曲线；
  • stream type 是兼容层：AUDIO_STREAM_MUSIC 等 legacy 概念通过 AttributesGroup 的 streamType 属性挂在策略/音量组上，getStreamTypeForAttributes() 反向换算，使老的 stream 音量 API 仍能工作。

一个策略可以包含多个 AttributesGroup（不同 attributes、不同流、甚至不同音量组）——例如 STRATEGY_MEDIA 同时覆盖 MUSIC/SYSTEM/ASSISTANT 三个流、music/system/assistant 三个音量组（见 3.3 节示例）。

2.5. 可替换的引擎与可替换的 Manager

两个 dlopen 扩展点，让芯片厂/OEM 能不动 framework 就换掉”大脑”：

① 引擎可替换。 APM 构造时按配置里的后缀装载引擎库：

  • 后缀 default（libaudiopolicyenginedefault.so）：本篇第 7 章的 legacy 路由表实现；
  • 后缀 configurable（libaudiopolicyengineconfigurable.so）：基于 parameter-framework 的可配置引擎（engineconfigurable/ 目录），策略完全由 vendor 的 XML 描述——当 AIDL 配置里带 capSpecificConfig 时自动选择它（3.2 节）。

② Manager 也可替换。 AudioPolicyService 启动时先尝试装载厂商定制实现：

读这份配置的三个要点：

  • 模块名是身份证：primary（本地声卡+通话）、a2dp/a2dp_in（蓝牙音乐）、usb、r_submix（虚拟设备，动态 mix 的宿主，见 11.3）、bluetooth（LE Audio）、msd（Multi-Stream Decoder，多路解码硬件桥）。APM 初始化时逐个 loadHwModule(name) 加载；

要点：

  • 曲线点横轴是 0~100 的”百分比刻度”，与组的 indexMin/indexMax 解耦——换档位范围不用改曲线（插值算法见 9.2 节）；

  1. 音量组名全局唯一；
  2. 一个 legacy stream 只能归属一个音量组；
  3. 引擎还会把两组系统内部策略/音量组（rerouting/patch）追加到表尾——它们不出现在 XML 里，却参与部分内部流程。

MUTE_TIME_MS = 2000：进入通话时媒体/铃声策略先静音、2 秒后自动解除（若那时它们还活着）——用静音窗口盖住设备切换的爆音与”音乐尾巴灌进听筒”。updateCallRouting 则按”primary 模块是否声明 Telephony RX/TX 设备”分两条路：有就在 HAL 内建 telephony patch（RX→sink 直连），没有则用软件 AudioSource 桥接（connectTelephonyRxAudioSource，通话下行变成一个普通混音源）。末尾的 mLimitRingtoneVolume 喂给 9.3 的规则 3a。

10.2. checkOutputForAttributes：搬 track 的唯一方式是”请它重开”

重路由的核心难题：AudioTrack 建立时就绑定了 AudioFlinger 的输出线程（共享内存、格式协商），APM 无法把一条已存在的 track 从线程 A 挪到线程 B。解法是 invalidate（失效）——让 client 收到错误后自动重建：

invalidateStreams → client interface → AudioFlinger 把对应 track 置为 invalid → AudioTrack/AudioRecord 客户端框架层收到 FRAME_COUNT/回调后自动走”无效重建”路径，重新 getOutputForAttr——此时世界已是新拓扑，流自然落到正确输出。App 全程无感（除了短暂的声音中断）。

静音时序的数学：解除延迟 = maxLatency × LATENCY_MUTE_FACTOR(4)——先等缓冲里旧的 PCM 全部放完（约 2×latency），再留一倍余量，确保静音窗口完整覆盖”旧缓冲播完 + 新流建立”的空档。

10.3. setOutputDevices：改路由的标准动作

对一个已打开的输出换设备，全部经由 setOutputDevices（设备连接、模式切换、force use、start/stopOutput 都汇聚于此）：

AudioPatch 是”执行”的最终形态：installPatch 把 (源端口=mix 流, 汇端口=device) 的组合经 AudioFlinger 下发 HAL，HAL 在内部把这个流接到那个设备（同模块内走硬件路由，跨模块由 AudioFlinger 建复制线程或 HAL 间直连）。listAudioPatches/dumpsys 里看到的 patch 表就是这棵”当前物理连接图”。

checkDeviceMuteStrategies 负责静音编排，两件事：

  1. 策略互斥静音：一个输出同时路由到 ≥2 设备时，按策略逐个检查”它的设备 ≠ 输出全部设备”（说明它只该去其中一部分）→ 该策略在这组共享输出上静音，防止声音串到不属于自己的设备；
  2. 临时静音防爆音：设备真的要换了（devices != prevDevices）→ 对输出上所有活跃音量组”先静音、recommendedMuteDuration（HAL 建议值）或 4×latency 后解除”——盖住切换瞬间的爆音；必要时 usleep(muteWaitMs) 阻塞等待 PCM 排空再动手（这正是 setOutputDevices 返回”睡了多久”的原因）。

前 10 章是”framework 内建策略”；本章反过来看特权 App 如何给 APM 注入自己的路由规则。这是 CarAudio、电视分屏、穿戴多设备、屏幕录制（媒体投影）共同的底层机制。

11.1. Java AudioPolicy：一个 Builder 说清全部能力

规则的五个维度与 6.2 节 native 侧一一对应：

三种 route flag 划定三种用途（CarAudio 篇只深挖了 RENDER，这里补全）：

flag mix 方向 数据去哪 典型用户

11.3. 注册链路：从 Java 到 registerPolicyMixes

注册的跨进程落点在 AudioService 的内部代理类：

connectMixes → AudioSystem.registerPolicyMixes → AudioPolicyService → APM::registerPolicyMixes。native 侧对两类 flag 的处理截然不同（LOOP_BACK 分支几乎是一场”外科手术”）：

LOOP_BACK 的魔术：注册一条回采 mix，等于在 r_submix HAL 上凭空捏出一对虚拟设备（addOutputProfile/addInputProfile 以 mix 地址命名），然后立刻模拟”设备连接”事件。此后：被规则匹配的播放流在选路时命中这条 mix → 输出到 AUDIO_DEVICE_OUT_REMOTE_SUBMIX(address)；采集 App 用 AUDIO_SOURCE_REMOTE_SUBMIX + tags addr=<同一地址> 从对端设备录入——两个方向在 r_submix HAL 内部由一个环形缓冲对接。内录从此不需要改一行 framework 代码。

RENDER 的纪律：目标设备必须已声明在 audio_policy_configuration.xml（getDeviceDescriptor 拿不到直接失败——CarAudio 篇 5.3 节”bus 地址必须真实存在”的根因）；mix 与输出双向绑定，找不到现有输出就挂到 direct profile 上懒创建。

注册成功后立刻 checkForDeviceAndOutputChanges：已有流如果现在该走这条 mix（规则命中），invalidate 机制会把它们搬过来——注册即生效。

AudioPolicy.setUidDeviceAffinity(uid, devices) / setUserIdDeviceAffinity(userId, devices) 的语义是”这个 uid/user 的声音只能去这些设备”。native 实现出人意料——它不新建任何数据结构，而是逐条改写所有 RENDER mix 的规则：

即：“uid X 只能去设备集合 S” 被翻译成 “所有目标设备不在 S 里的 mix 都加上 EXCLUDE_UID(X)”。userId 版本同理（setExcludeUserId），且额外给被改写的 mix 加上 MIX_ROUTE_FLAG_DISALLOWS_PREFERRED_DEVICE——这就接上了 6.2 节的 mixDisallowsRequestedDevice：被亲和改写过的 mix 能压过 App 的 setPreferredDevice 显式路由。”多用户媒体各回各的音区”（CarAudio 的 occupant 路由）正是靠这最后一环兜底的。

反注册（removeUidDeviceAffinities）就是把这些 EXCLUDE 规则擦掉；getDevicesForUid/getDevicesForUserId 反向查询”该 uid/user 目前允许去哪些 mix 设备”（未排除它的 mix 的设备全集）。

14.2. 设计要点回顾

  1. 三层洋葱 + 两个 dlopen：Service（binder/权限/命令线程）→ Manager（全部决策）→ Engine（规则表），Engine 与 Manager 双双可被厂商库替换（libaudiopolicyengine*.so / libaudiopolicymanagercustom.so）——稳定接口 + 开放实现；
  2. 配置即世界：audio_policy_configuration.xml 声明的拓扑就是能力的边界（没声明的设备连了白连、RENDER mix 的目标设备必须已声明）；三级 fallback（AIDL→XML→默认）保证永不开天窗；
  3. 一套坐标系贯穿始终：attributes →（打分）→ ProductStrategy（路由）+ VolumeGroup（音量）双轨映射，stream type 降级为兼容层；client 从诞生起携带 strategy/volumeSource/mix 三重身份，后续一切重估、聚合、失效都按这三把钥匙分组；
  4. 显式路由的四层优先级：mix 否决 > 请求级 preferredDevice > 会话级 setPreferredDevice（多数决）> 策略默认路由——“用户意志”层层压过”默认规则”，而 userId 亲和可以越过这一切（多用户隔离的代价）；
  5. 决策与执行分离：APM 所有”执行”（开关流、建 patch、设参数、设音量）都经 AudioPolicyClientInterface 走异步命令线程，带时间戳调度——静音窗口、延迟解除、排空等待这类时序敏感的操作因此可编排；
  6. 流不可搬，只能请它重生：AudioTrack 与输出线程的绑定是物理的（共享内存），重路由 = mute（盖住切换）→ invalidate（宣布旧家作废）→ client 自动重建（搬进新家）。App 无感、framework 无需”迁移”任何缓冲；
  7. 两种音量执行者自动切换：设备 port 声明增益即走硬件（软件侧顶满 0dB 让位），否则软件衰减进混音器；通话音量再单开一条 setVoiceVolume 直达 primary HAL；
  8. 动态 mix 是万能插槽：RENDER 接管路由、LOOP_BACK 凭空造虚拟设备对（内录）、LOOP_BACK|RENDER 做副输出（媒体投影）、uid/userId 亲和改写规则实现多用户路由——CarAudio 的四大接管全部长在这一个机制上。
