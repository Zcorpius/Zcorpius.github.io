AudioFlinger 剖析

发表于 2026-10-27 | 分类于 Audio ， AudioFlinger
字数统计: 30.5k | 阅读时长 ≈ 117

1. 从“数据写进去了，为什么还没有声音”开始

调用 AudioTrack.write() 成功，只能说明这一批数据被客户端播放通道接受。要让它变成扬声器里的声音，还需要有人决定何时取数、怎样让不同格式的声音一起播放、怎样处理音量和效果，以及何时把结果交给硬件。

AudioFlinger 就是 Android 音频系统中负责组织这项实时工作的服务端引擎。 它管理播放与录音轨道、输入输出线程、共享缓冲和效果链，通过 Audio HAL 接口连接设备。AudioPolicy 则负责依据用途、设备能力和当前系统状态，选择合适的输入输出与路由。两者相互调用，但承担的职责不同。

本文选择一个贯穿场景：音乐应用 A 持续播放 44.1 kHz、双声道、PCM 32 位整数；提示音应用 B 随后加入，提供 48 kHz、双声道 PCM。假设策略把它们放进同一个 48 kHz 的普通混音输出，接着观察暂停、缺数、插入耳机和录音。

这里的 48 kHz 是场景条件，不是“Android 所有输出固定为 48 kHz”。也不预设通知一定与音乐共用输出、一定降低音乐音量；真正的路由与 ducking 由策略、音频焦点及产品配置决定。

读完后应能回答：

  • 一个应用、一条 Track、一个 PlaybackThread 和一个硬件设备之间是什么关系？
  • createTrack()、start()、write() 分别在哪个进程、哪类线程中产生作用？
  • PCM 怎样从共享缓冲进入 AudioMixer，何时重采样、乘音量、处理效果并写出？
  • 普通混音、FAST、direct、offload、MMAP 各省掉了什么，又保留了什么？
  • 同样是“没有声音”，怎样区分未激活、未填够、被静音、缺数、路由错误和 HAL 阻塞？

2. 先分清服务、线程、轨道和输出

2.1. AudioFlinger 与 AudioPolicy 怎样分工

音乐应用表达的是“我要以某种属性播放某种格式的数据”。它通常不能直接指定“占用第几个 MixerThread，使用哪条 HAL stream”。中间需要把用途映射成可运行的音频通路。

组件 主要回答的问题 典型工作
Java / Native AudioTrack 应用如何提交数据并控制播放？ 参数协商、映射缓冲、写 PCM、启动/暂停、错误恢复
AudioPolicyService / AudioPolicyManager 应当使用哪个输出和设备？ 根据 attributes、设备、profile、flags、策略选择或打开输出，管理路由与音量决策
AudioFlinger 选定的通路怎样持续工作？ 创建轨道、管理线程、消费/分发数据、混音、效果、音量执行、调用 HAL
Audio HAL 把平台请求怎样落实到具体音频实现？ 建立设备流、传输数据、配置硬件路由、报告位置及延迟
驱动 / DSP / Codec / 功放 数据怎样最终被处理和播放？ 硬件队列、DMA、设备处理与电声转换，具体实现依产品而异

AudioFlinger 不是一个通用媒体解码器。普通 AudioTrack 混音路径的输入已经是 PCM；MP3/AAC 解码一般发生在播放器解码链路中。压缩 offload 是另一条专门分支，不能拿它解释普通 MixerThread 的输入。

AudioFlinger 也不独自决定音频焦点。焦点变化可能促使播放器暂停、降低音量或触发系统控制，但“收到焦点事件”与“MixerThread 如何处理某条 Track”之间还有控制链路，不能在混音器里凭空增加一套焦点裁决。

2.2. 四个最容易混淆的对象

AudioFlinger 是服务对象，PlaybackThread 是执行单元，Track 是被执行单元管理的一路流，AudioMixer 是计算工具。

对象 管理什么 与其他对象的关系
AudioFlinger 模块、输入输出线程、客户端、全局状态 通过 I/O handle 查找线程
PlaybackThread 某个输出通路上的轨道、缓冲和播放循环 普通输出关联一个 AudioStreamOut；具体子类决定怎样消费和写出
Track 一路播放的格式、状态、共享缓冲代理、session、port 挂到一个播放线程；同一应用可以有多条 Track
AudioMixer 当前参与混音的轨道配置、BufferProvider、处理函数 由 MixerThread 在循环中调用，本身不是另一个 Linux 线程

在本地版本中，MixerThread、Track 等已经是独立类，使用 IAfPlaybackThread、IAfTrack 等接口组织内部关系。阅读旧文章时常见的 AudioFlinger::PlaybackThread::Track 不宜直接当作本版本的类名去搜索。

2.3. 两份 Track 集合为何都需要

一个播放线程既要知道“有哪些轨道归我管理”，又要知道“哪些轨道当前需要被调度”。因此 PlaybackThread 保留了两层集合：

  • mTracks：该线程拥有的轨道集合。创建成功但还没 start() 的 Track 可以在这里。
  • mActiveTracks：当前需要播放循环处理的轨道集合。里面可能有正在填充、暂停收尾、停止排空或者暂时缺数的轨道。

所以 active 不能翻译成“此刻一定发出可闻声音”。一条 Track 可能已经激活但启动阈值尚未满足；也可能正在消费数据却被静音；还可能已经停止接收新内容，但下游仍有尾部数据。

AudioMixer 内部也有一份按 track id 管理的处理状态。服务端 Track 保存长期状态和缓冲入口，AudioMixer 内部的轨道状态保存这一轮计算需要的参数，两者不能当作两个应用播放器。

2.4. 不同 ID 对应不同问题

排查时，“看到一个数字相同”不是充分的对象关联证据。

标识 用途 容易出现的误读
PID / UID 客户端进程与身份归属 一个 PID 不只对应一条 Track
Track id AudioFlinger 内部某个轨道对象 重建后可能改变；不能永久标识同一个 Java 对象
Session id 音频会话，关联会话效果等 可以被多条 Track 共用，不保证唯一
Port id 策略层客户端的端口身份 不等于硬件插孔编号，也不等于 output handle
I/O handle 找到某个输入或输出线程 不等于物理设备 id；切换输出可能变化
Module handle 找到 HAL 模块包装对象 一个模块可支持多个设备与多个 stream
Device port / address 描述被选择的设备端点 地址是否有意义依设备类型与 HAL 而定

贯穿场景中的 A、B 是两条 Track。若策略把它们分配到同一个普通输出，它们共享一个 MixerThread；若 B 被送到另一种输出，它们就不在同一轮 AudioMixer 中相加。应用数量不能直接推导工作线程数量，工作线程数量也不能直接推导扬声器数量。

AudioFlinger 构造与 onFirstRef() 建立的是全局管理基础：唯一 ID 分配、日志与统计、HAL 工厂回调、设备效果管理、PatchPanel、声音剂量统计等。mDevicesFactoryHal 通过 DevicesFactoryHalInterface::create() 初始化；具体模块由 loadHwModule_ll() 连接。

加载模块后仍需协商具体输入/输出 stream。策略初始化及后续设备、播放需求会推动这些操作。可以从 AudioPolicyManager.cpp 的模块加载代码，沿 AudioPolicyService::AudioPolicyClient::openOutput() 反向进入 AudioFlinger；不要把“每次创建 AudioTrack”写成“必然新开一条 HAL stream”。普通混音输出通常可以被多条 Track 复用，direct 等路径有不同的打开与关闭规则。

3.4. openOutput：先取得 HAL stream，再选择线程类型

openOutput_l() 的两个产物是：一条已经协商的 HAL 输出流，以及负责它的服务端线程对象。线程类型取决于最终 flags 和 HAL 配置，不只看应用最初请求了什么。

由此可以排除三个误解：

  1. PRIMARY 是输出角色标志，不是 PrimaryThread 类名；FAST 也不是这个函数创建的某种独立 PlaybackThread 子类。
  2. DIRECT 与 COMPRESS_OFFLOAD 不是同义词。direct 可以承载 PCM；offload 有压缩数据、异步回调和 drain 等专门语义。
  3. “服务存在”“模块连接成功”“输出打开成功”“Track 创建成功”“Track 开始产生声音”是不同阶段，可以分别失败。

4. createTrack：把一次播放请求变成服务端对象

4.1. 请求中既有数据条件，也有策略条件

Native AudioTrack 在 createTrack_l() 中向 AudioFlinger 提交请求。理解服务端之前，把主要输入分成三组更容易：

条件 例子 后续用途
音频数据条件 sample rate、format、channel mask、frame count、speed 判断线程能否处理，计算缓冲与通知周期
策略与身份条件 attributes、uid/pid attribution、session、selected device、flags 选择输出、关联效果、检查身份与能力
通道建立条件 STATIC 的 sharedBuffer、回调接口、客户端 tid 建立共享数据入口、通知与调度关系

创建返回的也不只是“成功/失败”。服务端会返回协商后的采样率、frame count、flags、输出参数、port id、session id 和 IAudioTrack 接口。客户端必须以实际结果建立本地代理，不能始终拿请求值解释运行行为。

4.3. PlaybackThread 再做一轮能力检查

策略选出输出，不代表所有请求参数都能原样使用。PlaybackThread::createTrack_l() 会继续处理：

  • 请求 flags 与输出 flags 的兼容性；存在 FastMixer 时，单独考虑 FAST 能力。
  • FAST 的采样率、声道、空闲槽位和效果兼容性。
  • STREAM / STATIC、PCM / 非比例帧格式对应的 frame count 与通知周期。
  • direct PCM 与 offload 对采样率、格式、声道的匹配要求。
  • 普通混音轨道的 PCM 与重采样范围限制。
  • 同一 session 中已有外部 Track 的路由 strategy 是否一致。

成功后，Track 加入 mTracks，此时还没有因创建本身加入 mActiveTracks。如果会话已有效果链，会把该轨道的主输出缓冲指向效果链输入。

缓冲的意义也在这里分开：应用请求的 Track 容量、普通混音周期的 mNormalFrameCount、HAL 对应的 mFrameCount 不是同一个值。请求了 4096 帧容量，不表示 HAL 每次恰好写 4096 帧；输出每轮混 960 帧，也不表示客户端环形缓冲只能容纳 960 帧。

4.4. 共享缓冲在哪里分配

普通 STREAM Track 的控制块和数据区由服务端建立。当前版本 Client 持有 AllocatorFactory::ClientAllocator，TrackBase 通过这个 allocator 分配共享区域；不要把所有新版本代码一概描述成 Client 直接持有一个 MemoryDealer。

new(mCblk) audio_track_cblk_t() 是 placement new：在指定地址构造对象，不是再申请一份独立内存。mCblkMemory 提供可共享的区域描述；两进程映射同一底层内存，但各自的虚拟地址可以不同。

普通播放时，客户端建立 AudioTrackClientProxy，服务端建立 AudioTrackServerProxy。代理在共享控制块上维护读写位置，并向上提供 obtainBuffer() / releaseBuffer() 等操作。STATIC 使用预先提供的数据区及专门代理；录音和 FastCapture 的分配方式也不同，不能把上面的布局套到所有轨道。

4.5. IAudioTrack 是遥控入口，Track 才保存播放状态

本地 TrackHandle 继承 Binder 服务端接口，持有 sp<IAfTrack>。IAfTrack::createIAudioTrackAdapter() 返回这个适配对象；客户端再通过 getCblk() 取得共享区域描述。

因此一次创建之后存在两条并行通道：

  • 控制通道：客户端 IAudioTrack → 服务端 TrackHandle → Track。
  • 数据通道：客户端 proxy → 共享 PCM 缓冲 → 服务端 proxy / BufferProvider。

后续 write() 不需要再调用一次 createTrack()，也不需要为每个 PCM 包调用 IAudioTrack 的 Binder 方法。对象创建完成只是把两条通道接好，真正起播还要经过下一章的激活与就绪判断。

5. start 与共享缓冲：让轨道进入可消费状态

5.1. start 改变状态，工作线程负责执行

Java play() 最终经 Native AudioTrack 和 IAudioTrack.start() 到达服务端 Track::start()。这次 Binder 调用发生在控制路径，不承担连续搬运 PCM 的任务。

Track::start() 取得所属线程的强引用，在线程锁下处理状态：新建或停止后的轨道通常进入 ACTIVE；从暂停恢复时可能先进入 RESUMING。然后调用 PlaybackThread::addTrack_l()。

addTrack_l() 对应用等外部轨道还会先执行 AudioSystem::startOutput(portId)。这里的 getOutputForAttr() 与 startOutput() 不重复：前者取得输出及客户端归属，后者把一次播放真正登记为正在使用，策略仍可能拒绝或要求重建。

onAddNewTrack_l() 调用 broadcast_l() 唤醒播放线程。对于已经在 active 集合中的 Track，会识别 ALREADY_EXISTS，而不是再次插入同一个对象。Track::start() 对成功或已存在的情况解除服务端读指针的 stop 限制，并协调尚未确认的 flush。

这里不能把“释放锁以后继续执行”理解成状态没有变化。代码保存并重查旧 state，正是为了处理另一控制线程在间隙里发出暂停、停止等请求的竞争。

5.2. ACTIVE 之后还有启动填充门槛

如果应用刚写入一点点数据就开始播放，第一次硬件周期可能立刻缺数。因此普通轨道还有 filling 状态。当前实现不是死板地要求“整个物理分配区写满”，而是考虑启动阈值和有效缓冲大小。

例如普通 Track 容量为 4096 帧，有效大小为 2048 帧，启动阈值为 1024 帧：只写 300 帧就 play()，可能已经 ACTIVE，却仍处于 FS_FILLING。继续写到满足门槛，才有资格参与后续混音。实际能否在该轮参与，还取决于第 6 章的可读帧数与状态判断。

这个函数的源码明确提示不要用于 fast tracks。FAST 的取数和不足一周期数据的处理在 FastMixer 分支中进行，不能把普通轨道的全部起播规则照搬过去。

5.3. PCM 是怎样从共享内存被取走的

这里的 release/acquire 内存顺序有实际用途：让另一端在看到“数据已经发布”时，也能看到此前写入的数据；让生产者重用空间时，不覆盖消费者仍在读取的部分。仅仅把整数位置改成 volatile，不能替代这种跨线程、跨进程的发布协议。

Futex 用于需要等待时休眠和唤醒，共享内存并不意味着忙等，也不意味着从应用到声卡全程零拷贝。应用复制、格式转换、混音输出以及 HAL 传输都可能产生拷贝。这里节省的是把每一批 PCM 作为 Binder Parcel 发送的工作。

5.4. pause、stop、flush 改变的是不同阶段

主线限定为普通 PCM STREAM Track。服务端状态不是 Java 播放状态的逐字镜像。

操作 服务端主要变化 缓冲与声音的后续结果
start 加入 active；新轨道进入 ACTIVE，恢复时可能先 RESUMING 等待必要填充，再由循环消费
pause ACTIVE/RESUMING → PAUSING；循环处理到 PAUSED 通常保留尚未消费数据；下游已有数据不会瞬间消失
stop 普通 active 混音轨道可直接标记 STOPPED 仍可能消费停止边界前的数据并等待呈现完成
flush 允许的停止/暂停等状态下进入 FLUSHED，并协调缓冲清理 丢弃相应待播旧数据；不是追回已经到达硬件的声音
release / Binder handle 销毁 触发 destroy/terminate，交由线程移除与释放 活跃轨道不能在另一线程仍持有裸 BufferProvider 指针时直接释放

对普通流式播放，客户端 stop 协议还会发布 mStop，AudioTrackServerProxy::getRear() 据此限制本次允许消费的尾部。STOPPED 轨道在 prepareTracks_l() 中仍可读取已有数据；等数据用尽及呈现判断满足，才移出 active 集合并 reset。因此“状态为 STOPPED”和“停止瞬间把全部 PCM 丢掉”不能画等号。

6.1. Binder 线程接指令，AudioOut 线程维持节拍

6.2. 用六个动作读主循环

阶段 关键入口或状态 这一阶段产生什么结果
接收变化 processConfigEvents_l()、时间戳收集 配置和 patch 等请求在工作线程中落实，更新位置与环境

这六步不是六个独立线程。普通路径主要由同一个 PlaybackThread 执行，其中具体混音、写出行为由子类覆盖。需要 FastMixer 时，最终硬件写出会转交给另一个快速线程。

锁的安排也有层次：循环在工作线程锁下处理集合与配置，复制本轮要使用的强引用，并锁定相关效果链；随后释放线程锁执行混音和效果处理。效果链锁用于防止计算过程中缓冲被另一控制线程拆掉，不代表整轮都持有 AudioFlinger 的全局锁。

6.3. prepareTracks_l：active 只是候选，还要过就绪检查

普通轨道先检查 AudioMixer 中是否已有对应处理状态，再估算本轮需要多少输入帧。重采样、播放速度及重采样器尚未释放的帧都会影响这个估算。

这里同时存在两个门槛：

  1. 起播门槛：isReady() 解决开始播放前要积累多少数据。
  2. 本轮门槛：framesReady >= minFrames 解决当前是否适合完成这一轮处理。

minFrames 在某些持续播放条件下提高到 desiredFrames，在停止、暂停收尾等条件下又允许只剩很少帧的数据被取走。不能只看到 minFrames = 1 就说“所有轨道有一帧就立即混音”，也不能把后面的条件概括成“永远要求完整一周期”。

6.4. A 缺数时，B 会不会被永远拖住

不会为 A 无限等待，但也不能简单说“某条轨道缺数，一律立即补零，其他轨道完全不受影响”。本版本会结合上一轮混音状态与当前轨道状态，在 MIXER_TRACKS_READY、MIXER_TRACKS_ENABLED、MIXER_IDLE 等状态之间选择，给予短暂的填充/重试机会。

普通轨道缺数时，关键后果包括：

  • 当前轨道可被 AudioMixer 暂时禁用；其效果链输入需要清空，防止把上一轮音频再次送进效果处理。
  • threadLoop_sleepTime() 根据状态安排等待；在需要维持输出时清零混音或 sink 缓冲，再继续写出。
  • 对仍应播放但持续得不到数据的轨道，重试次数耗尽后移出 active 集合，并设置 CBLK_DISABLED。
  • 客户端后来继续提供数据时，若自身仍是 STATE_ACTIVE，可经 restartIfDisabled() 再次启动同一控制接口。

Track::disable() 设置 CBLK_DISABLED。与之相对，Track::invalidate() 设置 CBLK_INVALID，意味着现有通道失效，通常需要重建。两者在排查“写入后突然又恢复”的问题时尤其重要：前者可能只是在恢复同一条 Track 的调度，后者才涉及新的服务端对象与输出选择。

underrun 表示消费者需要数据时供应不足，不是“某个 buffer 曾经为空”就一定算一次。停止、暂停、尚未真正起播等状态有各自排除和统计条件，计数也有 frames 与事件次数之别。

6.6. 上一块没写完，不能用下一轮数据覆盖它

HAL 或 sink 不保证每次接受完整请求。mCurrentWriteLength 记录当前音频块长度，mBytesRemaining 记录剩余未写长度。主循环仅在 mBytesRemaining == 0 时生成新的混音块；短写后保留余量。

假设一块有 3840 字节，第一次只接受 1536 字节，下一次从偏移 1536 继续写剩下的 2304 字节，而不是重新从零写、丢掉尾部或者先混出下一块覆盖它。主循环在正返回时累加 mBytesWritten 和 mFramesWritten、减少 mBytesRemaining；错误路径另行处理。

这也提示了调试时的一个单位陷阱：客户端 API 可能返回字节或样本数量，NBAIO 常以 frame 计数，HAL 适配层 write 以字节长度交互。比较日志之前必须统一单位。

6.7. 没有 active Track 之后，为何线程还存在

一条 Track 播完，不代表整个共享输出立刻被销毁。循环会判断 standby 延迟，在合适时机让输出进入 standby；没有 active Track 和配置事件时，释放相应 wakelock 并在条件变量上等待。

因此应区分：

  • 轨道结束：某条流不再参与；同输出上其他轨道可以继续工作。
  • 输出 standby：底层进入空闲，线程对象仍可保留并等待唤醒。
  • 关闭输出：策略要求关闭，AudioFlinger 移除映射、停止线程并释放 stream。

首次起播比持续播放或短暂停后恢复慢，可能包含 HAL 从 standby 唤醒和硬件管线预热成本。它不能只由 AudioTrack.write() 调用耗时解释。

7. AudioMixer：让不同轨道对齐到同一输出时间轴

7.1. frame 与 sample：先统一帧、样本与字节

PCM 的一帧包含同一时刻的所有声道样本。A 的双声道 32 位整数，每帧是 2 × 4 = 8 字节；48 kHz 双声道 16 位输出，每帧则是 2 × 2 = 4 字节。输入与输出的 frame size 可以不同。

以仅用于计算的 20 ms 周期举例：

流 20 ms 对应帧数 示例中的数据意义
A：44.1 kHz 882 帧 客户端 7056 字节的双声道 s32 PCM
B：48 kHz 960 帧 与输出时间网格一致的提示音
输出：48 kHz 960 帧 混音器要生成的输出时段

这说明“同时播放 20 ms”并不意味着从所有输入都取 960 帧。真实重采样器还有滤波历史、相位、取整及未释放帧，不能把 882 当成每一次 getNextBuffer() 必然请求的固定长度。第 6 章使用 sourceFramesNeededWithTimestretch()，正是在处理这类供数需求。

7.2. 混音前要解决四类不一致

不一致 处理目标 与主线的联系
采样率 把输入信号转换到输出采样时间网格 A 的 44.1 kHz 对齐到 48 kHz；B 在采样率上无需此转换
声道布局 按 channel mask 建立或变换声道关系 mono、stereo、多声道不能只靠数组长度判断映射
样本格式 在整数、浮点及处理精度之间转换 s32 输入不意味着所有中间运算和 HAL 都是 s32
音量与速度 按轨道增益、渐变和 playback rate 生成本轮数据 暂停渐弱、恢复、VolumeShaper、变速可改变计算路径

重采样不是“修改 sampleRate 元数据”，也不是“简单重复或删除若干数字就足够”。它要根据原始信号估计新采样时刻的数值，涉及滤波和历史状态。格式转换只改变数值表示，声道转换改变空间布局，time stretch 则处理播放速度/音调相关要求；这些操作应分开理解。

本版本 AudioMixer::Track::reconfigureBufferProviders() 将格式、声道、downmix、time stretch 等 provider 按需连接，重采样计算再由混音实现选择。所有轨道不必拥有完全相同的 provider 链，具体分支取决于输入与输出条件。

FAST 不是“正常混音功能全部保留，再把线程优先级调高”。EffectChain::checkOutputFlagCompatibility() 会依据链的能力清除不兼容的 FAST、RAW、BIT_PERFECT 标志。

本地 isFastCompatible() 拒绝实现了数据处理的软件效果，但允许不处理数据的效果或硬件加速效果。因此正确结论是“效果可能导致 FAST 不兼容”，而不是“只要应用创建任意效果对象就绝对不能 FAST”。

offload 也有边界：Track::start() 检查非 offloadable 的全局/会话效果；ThreadBase::onEffectEnable() 在相关条件下可以使 offload 轨道失效。播放器因此可能需要回退或重建到可完成这些处理的输出路径。单看解码器是否支持 offload，无法判断整个播放组合是否仍满足 offload 条件。

9. 从 sink 到 Audio HAL：还有另一段数据通道

9.1. mNormalSink 不一定直接指向 HAL

普通 MixerThread 的 mNormalSink 是 NBAIO sink 抽象。它可能是：

  • mOutputSink：AudioStreamOutSink，把混音结果转交给 HAL stream。
  • mPipeSink：MonoPipe，先保存普通混音结果，再由 FastMixer 读取并最终写出。

所以在 PlaybackThread::threadLoop_write() 看到 mNormalSink->write()，只证明向当前 sink 提交数据；要继续看实际对象，才能判断这一轮是在写 HAL 还是写内存管道。

NBAIO 是音频 source/sink 的一套内部接口。不能只凭名称里包含 non-blocking，就断言所有具体 sink 的 write 永不等待；本版本创建 MonoPipe 时显式传入了 writeCanBlock=true，它也承担普通线程与快速线程之间的节拍协调。

9.2. AudioStreamOutSink 完成帧与字节的边界转换

mStream 是 StreamOutHalInterface 抽象，不等于内核 PCM 文件描述符。对普通输出，之后还要进入 HIDL 或 AIDL 适配实现；direct/offload 通过 AudioStreamOut::write() 包装层进入 stream 接口，也不能省略后面的边界。

9.5. HAL write 返回为什么还不等于可闻声音

返回说明数据在该接口的语义下被接受或处理到相应阶段。后面仍可能有 HAL、驱动、DSP、蓝牙传输和硬件队列。不同设备的 getPresentationPosition() 与 latency 报告也是特定实现的观测边界。

因此要分别记录：客户端接受多少、服务端消费多少、sink 接受多少、HAL 报告呈现到哪里。第 14 章会解释这些位置怎样映射；只有要测声学端到端延迟时，才需要真正连接采集/回环设备测量。

10. FastMixer：把最终输出周期中的工作压缩到必要范围

10.1. 普通混音为什么还需要一个快速线程

普通 MixerThread 需要处理多种格式、重采样、效果和复杂状态；如果 HAL 要求较小周期地持续拿到数据，把这些工作全塞到同一短周期里，会增加调度和计算压力。

FastMixer 的组织方式是：普通线程先完成较复杂的处理，把普通轨道的子混音写入 MonoPipe；快速线程按较小的输出块读取它，再与获得 FAST 资格的轨道一起混合并写出。快速轨道因此避开普通 MixerThread 的大块混音与中间排队。

绿色箭头是 PCM，橙色箭头是状态控制。MonoPipe 是单写入者、单读取者的管道，可以传输多声道音频；不能把 Mono 理解成声道数固定为 1。 AudioStreamOutSink 是输出适配对象，也不是额外的一条 Linux 输出线程。

图中普通 Track A/B 的结果经过 FastMixer，不会使它们变成 fast tracks。判断一条轨道是否 FAST，应看最终获准标志、fast index 和实际线程状态，而不是只看设备上有没有名为 FastMixer 的线程。

10.2. 每个 MixerThread 都有 FastMixer 吗

没有。构造函数会根据配置和线程类型决定是否初始化。当前源码默认 kUseFastMixer = FastMixer_Static；该模式下，普通 deep-buffer 输出不创建 FastMixer，其余相关情况以 mFrameCount < mNormalFrameCount 等条件判断。Spatializer 和 BitPerfect 也有明确排除。

这里 mNormalFrameCount 是普通混音块帧数，state->mFrameCount 则取 HAL 对应的较小块。正常工作时可以形成“一块普通子混音，分多个快速周期消费”的关系。实际周期要用帧数和采样率计算，再结合运行状态观察；不能把早期设计中常见的毫秒数当成所有产品的常数。

10.5. StateQueue 为什么比一把大锁更适合这条路径

普通线程需要告诉 FastMixer：哪些槽位有效、BufferProvider 是谁、输出 sink 是谁、当前是否混合和写出。它通过 FastMixerStateQueue 发布状态，FastMixer 在自己的执行路径观察状态并更新处理对象。

这里有两类队列，必须分开：

  • MonoPipe 装音频数据，解决普通子混音如何进入快速周期。
  • StateQueue 装配置快照，解决生产状态与观察状态如何协调。

FastMixerState 内部包含原始指针，指针所指对象由普通线程侧管理引用。删除快速轨道时，普通线程不能“从自己的列表移除后马上释放对象”，因为 FastMixer 可能还在使用上一份状态中的 BufferProvider。

因此 prepareTracks_l() 在移除 fast track provider 时使用 BLOCK_UNTIL_ACKED，等待快速线程确认不再使用旧状态，再安全释放相关引用。这个 ACK 是生命周期正确性的一部分，不只是为了让日志显示及时。

快速路径的目标是减少锁竞争、分配、复杂处理与不可控等待，但不能将其夸大成“整条路径任何时候都绝不会阻塞”。HAL 写出、状态切换、冷启动以及源码明确保留的待改进点都需要分别看。

10.6. FastMixer 自己也要处理缺数和静音

FastMixer::onWork() 读取当前 mask，对每条 fast track 检查 framesReady()：

  • 够一周期：启用相应 mixer 项。
  • 有数据但不足一周期：允许部分混合，并记录 partial 情况。
  • 完全没有数据：禁用该项，记录 empty 情况。

具备有效输入时调用自己的 AudioMixer 实例；需要写出但没有有效结果时清零相关缓冲，再经 mOutputSink->write() 提交。FastMixer 也处理音量和必要的输出格式转换，不能简化为“裸 memcpy 线程”。

官方早期低延迟设计有助于理解普通/快速线程的分工，但其中的 TRACK_FAST、CBLK_FAST 等历史接口描述不能替代本版本的 flags、状态队列和槽位实现。降低延迟的设计

11. 其他输出路径：不要把所有声音都画进普通混音器

11.1. 先按“数据怎样走”比较

路径 AudioFlinger 中的主要组织 绕过或改变的环节 仍需要关注
普通混音 MixerThread + AudioMixer 支持按需转换、多轨混合 缓冲、效果、音量、sink
FAST MixerThread 管理 + FastMixer 消费 fast track 绕过普通混音与其子混音队列 格式匹配、槽位、调度、HAL 周期
direct DirectOutputThread 不把该流放进普通多轨混音流程 精确格式条件、状态、音量、设备能力
compressed offload OffloadThread 压缩数据交由支持的 HAL/硬件链路处理 非阻塞写、回调、drain、效果兼容
duplicated output DuplicatingThread + OutputTrack 把混音结果分发给下游输出线程 多时钟、缓冲与输出同步
spatialized output SpatializerThread 增加空间化所需的配置与处理缓冲 哪些轨道空间化、效果与设备支持

这些名称不能排成“普通 < FAST < direct < offload < MMAP”的通用性能排行榜。它们面向不同数据、功耗、格式和时延要求；设备是否支持、应用实际获准哪条路径，都需要协商和观测。

11.2. DirectOutputThread：直接输出不等于不需要服务端

DirectOutputThread 仍然管理 Track、共享缓冲、停止暂停、音量、时间戳和 HAL 写出。它改变的是混音方式，而不是把 AudioFlinger 从控制和调度链路里整个删除。

对 direct PCM，本地 createTrack_l() 要求 sample rate、format、channel mask 与线程配置一致，不能像普通 MixerThread 一样假设服务端会替你完成所有转换。

一个 direct 输出在对象管理上也可能暂时有多条 Track，例如切换或接替阶段。prepareTracks_l() 通过 mActiveTracks.getLatest() 确定当前主要轨道，并可能使前一轨道失效；这不等于多路 direct Track 可以像普通混音那样长期无条件相加。

“Direct”更不等于“最终比特必然不变”。HAL、设备音量、效果和硬件处理仍可能改变内容；本版本还专门存在 BitPerfectThread，应按实际模式解释。

11.3. OffloadThread：数据量与播放时长不再简单成比例

OffloadThread 继承 DirectOutputThread。压缩 offload 把压缩音频交给可承担相关处理的下游链路，AudioFlinger 不在普通 AudioMixer 中先把它解码成 PCM 再混音。

这会改变三个重要判断：

  1. 字节数不能直接除以 PCM frame size 得到播放时长。 压缩格式的数据量、实际解码样本和下游延迟有专门语义。
  2. 一次 write 可能异步完成。 输出支持 NON_BLOCKING 且 callback 注册成功时，线程使用 AsyncCallbackThread、写入确认序列和等待状态，避免把“还没收到完成回调”当成可继续无限写。
  3. 停止要考虑 drain。 HAL 可能还存有可变长度的解码/输出内容，不能仅用普通混音的固定帧数估算完成。

PlaybackThread::threadLoop_drain() 查询并调用 HAL drain，区分提前通知与全部排空。OffloadThread 的停止路径还协调 STOPPING_1、STOPPING_2、pause/resume/flush pending 和回调。

因此播放器要做无缝切歌、seek 或重新路由时，不能套用“客户端缓冲空了就可释放”的规则。非 offloadable 效果、输出资源变化或设备不支持，都可能让原有 offload 路径不可继续。

11.4. DuplicatingThread：向多个下游提交同一份结果

DuplicatingThread 继承 MixerThread，先产生混音结果，然后通过内部 OutputTrack 写到下游播放线程。其构造分支不会建立普通 MixerThread 那套 FastMixer / output sink / pipe sink。

这里复制的是待分发的数据结果，不是把一个硬件流直接变成两个物理插孔。两个下游可能有不同缓冲、延迟或时钟，不能据此保证声学上严格同步。

另外，当前 createTrack() 返回的 secondaryOutputs 还会进入 updateSecondaryOutputsForTrack_l()，使用相关 patch/tee 机制建立次输出。“多路播放”不必然只由 DuplicatingThread 实现；要沿具体策略与 secondary output 分支继续追踪。

11.5. Spatializer 与 BitPerfect 是实际存在的专门分支

SpatializerThread 基于 MixerThread，但有独立 mixer configuration 和空间化前后的缓冲安排。prepareTracks_l() 对未参与空间化的 Track 可以把结果送到 mPostSpatializerBuffer。所以不能因为某输出是 Spatializer，就认为其中每条 Track 必然经过同样的空间处理。

BitPerfectThread 也基于 MixerThread，而不是 DirectOutputThread 的别名。它在可比特保持传递的条件成立时，通过 AudioMixer 的 tee buffer 将对应数据写入 sink，并避免后续混音结果覆盖该数据。

条件还受 feature flag 影响：getTrackToStreamBitPerfectly_l() 的一条分支要求只存在一条 active bit-perfect Track；另一条允许在其余轨道都被静音时选择相应 bit-perfect Track。若内部静音、并发状态或格式条件不满足，结果会变化。

因此仅在 dump 看到线程类型 BIT_PERFECT，不足以证明当前每一轮、每个声道直至最终 DAC 都完全不变；仍要观察该轮实际选择的 Track、音量、其他轨道与设备实现。

11.6. MMAP：数据绕过普通混音，管理关系仍然存在

openOutput_l() 对 MMAP_NOIRQ 创建 MmapPlaybackThread，并放入 mMmapThreads。这类对象负责 wake lock、路由、音量、效果状态和流控制等，数据传输由创建 MMAP 流的客户端侧体系处理。

AAudio 是应用侧 API/服务体系，MMAP 是其可能使用的数据路径之一。AAudio 共享与独占模式的具体传输、混合关系不同，也可能回退到传统路径；不能画成“只要调用 AAudio，应用就必然直接写独占声卡缓冲”。

本节只建立 MMAP 与普通 Track 主线的边界。继续阅读可从 services/oboeservice/AAudioServiceEndpointMMAP.cpp、AAudioServiceStreamMMAP.cpp 以及 MmapThread 的 start、position、standby 入口展开。

12. RecordThread：把采集数据分发到客户端

12.1. 录音不只是把播放箭头机械反过来

普通播放由多个客户端分别供数，服务端需要合成输出；普通录音由输入设备持续产出数据，服务端把它交给获准的录音客户端。多个 RecordTrack 可以有不同采样率、格式与声道要求，但不是“把多个应用的麦克风数据混在一起”。

策略允许哪些客户端同时采集、哪些客户端需要静音、选用哪个输入源，必须结合 AudioPolicy、权限和当前系统状态。RecordThread 支持多个轨道的事实，不能推导为任意应用都可以同时得到麦克风原始声音。

图中绿色箭头表示采集 PCM 的方向。它展示策略已允许的普通 RecordTrack 分发，不包含 FastCapture 和 MMAP 分支。

12.2. createRecord 先选择输入，再建立 RecordTrack

AudioFlinger::createRecord() 与播放创建有对应结构：

  1. 转换与检查请求、身份、format/channel mask、session。
  2. 调用 AudioSystem::getInputForAttr()，取得 input handle、port id、实际输入源等。
  3. 在 mRecordThreads 中找到该输入的 RecordThread。
  4. 调用 createRecordTrack_l()，协商缓冲与 FAST 等能力。
  5. 返回 IAudioRecord 适配接口、控制块和数据缓冲，以及客户端/服务端/HAL 配置信息。

本地有一个特别重要的重试：若 FAST 录音条件不满足，createRecordTrack_l() 可以清除相关 flags 并返回 BAD_TYPE；createRecord() 随后释放之前申请的输入，重新向策略请求不带原 FAST 约束的输入。不能把每个 BAD_TYPE 都解释成“整个 AudioRecord 必然构造失败”。

普通录音数据缓冲可使用 RecordThread 的只读共享 heap，控制块与数据区在返回中分别描述；FastCapture 又可能直接共享 pipe 区域。这与第 4 章普通播放 ALLOC_CBLK 连续分配的示例不同。

12.3. startInput 与 STARTING 阶段协调两条线程

RecordTrack::start() 转入 RecordThread::start()。它先将 Track 放入 STARTING_1 并登记到 active 集合，释放线程锁调用策略 startInput(portId)，重新取得锁后检查是否失效、状态是否被别人改变及策略是否成功。

通过后重置相关 buffer provider / converter 状态，进入 STARTING_2 并唤醒工作线程。RecordThread 循环再将它推进到 ACTIVE。

这个两阶段状态的意义在于：工作线程可能已经在持续采集，同时新的 Binder start 请求正在等待策略结果，双方需要共享一个明确的“尚未完成启动”状态。普通情况下新客户端从启动时的输入位置开始，不应未经约定读到开始录音之前留下的历史数据；本版本对共享音频历史有另外的专门能力与约束。

12.5. 播放缺数是 underrun，录音跟不上是 overrun

两种问题从生产者和消费者的关系看最清楚：

场景 生产者 消费者 常见问题
普通播放 App AudioFlinger App 来不及供数，消费者无数据可取：underrun
普通录音 AudioFlinger / 设备链路 App App 来不及读取，积压超过可保留范围：overrun / overflow

录音的 cblk 方向也相反：服务端生产推进 mRear，客户端读取推进 mFront。第 5 章 ServerProxy::releaseBuffer() 中的 mIsOut 分支已经展示了这种区别。

RecordThread 的 resampler provider 与 pipe 路径都有各自的溢出检测和追赶逻辑。丢失的采集数据不能靠稍后多读几次自动恢复；应用应记录实际 read 返回量、时间戳与错误，同时把处理工作移出高频采集路径，减少持续拖慢读取的因素。

12.7. FastCapture 与 FastMixer 相似，但不是镜像复制

FastCapture 负责较短周期地从输入 source 读取，再写入 pipe。普通 RecordThread 从 pipe 读出后转换/分发；获准的快速录音客户端可以使用对应共享 pipe 路径，普通 RecordThread 的逐轨分发循环会跳过 fast track。

本地 RecordThread 使用 mFastTrackAvail 管理快速录音槽位，循环注释明确是第一个且唯一的 active fast track；这与播放侧可配置的多 fast slots 不同。

FAST 录音还要求采样率与输入线程一致、channel mask 一致、PCM、pipe 容量与效果兼容等。输入与客户端格式不同不一定直接拒绝，当前实现允许相关格式转换由客户端侧处理。共享音频历史需求及被静音时的处理也可能使快速轨道失效或不再获准。

所以不要把播放侧的“默认七个客户端槽位”“所有格式转换都在服务端”“普通 isReady 起播阈值”迁移成 FastCapture 的规则。

13. 路由变化、失效与重建

13.1. PatchPanel 连接的是端点关系

音频 patch 表达 sources 与 sinks 之间的连接关系。端点可以是 mix port，也可以是 device port。AudioFlinger 通过 PatchPanel 管理这些连接，并按类型交给对应线程或 HAL。

patch 关系 常见含义 实现上需要继续看什么
mix → device 播放输出接到设备 该 mix 的 I/O handle、PlaybackThread / MmapThread、HAL patch
device → mix 采集设备接到输入 RecordThread / MmapThread、输入源与设备
device → device 设备之间连接 同模块硬件 patch，或需要软件桥接的情形

因此 patch 不一定包含应用 Track，也不一定需要普通 AudioMixer 逐样本搬运。跨硬件模块的连接可能创建内部 record/playback tracks 组成软件桥，支持情况取决于具体端点与实现。车载外部音源或某些硬件通话路径，也不能一律画成“App AudioTrack → 普通 MixerThread”。

13.2. createAudioPatch 到底在哪条线程执行

对于普通播放 mix → device，PatchPanel 找到对应播放线程，把请求作为配置事件交给它。它不会仅因调用了一个“创建 patch”的入口，就在原调用线程里完成所有硬件切换。

播放循环开头的 processConfigEvents_l() 消费队列。在 CFG_EVENT_CREATE_AUDIO_PATCH 分支调用 createAudioPatch_l()，记录状态并通知等待者。PatchPanel 在调用线程的同步等待入口之前，也按实现释放 AudioFlinger 主锁，避免工作线程需要主锁时互相卡住。

这是一种“通过队列交给工作线程执行，但调用方可等待结果”的模式。排队执行不等于调用接口一定立即返回；调用接口返回成功也不等于设备已经在声学上稳定出声。

13.3. 线程把设备状态与 HAL 路由一起更新

PlaybackThread::createAudioPatch_l() 先更新设备信息并通知效果链，再通过支持的 HAL 接口创建 patch；不支持相应 patch 能力时走 legacy 适配。

由此可以解释：一次切设备除了“更换声音去向”，还可能影响效果配置、元数据、时间戳连续性和延迟统计。不能只比较前后一个 routing 参数就认定整条通路的所有状态都相同。

13.4. 插耳机不必然重建 Track

橙色箭头表示控制/状态推进，两侧代表不同条件下的路径，不是每次切换都连续执行的两个阶段。

回到主线，A 正在扬声器上播放，用户插入耳机。至少要分别考虑：

情况一：现有输出可以继续使用。 策略更新设备连接与 patch，原 PlaybackThread、原 I/O handle 以及 Track 可以保留。数据仍从原共享缓冲被消费，但输出设备变了。

情况二：需要改用另一个输出。 新设备、profile 或模式要求不同通路，旧 Track 可能被 invalidate，客户端再选择输出并创建新的服务端 Track。采样率、缓冲、flags、效果归属和时间戳都可能随之变化。

这两种情况不能仅凭“有线”或“蓝牙”四个字固定下来，实际取决于产品配置和策略。也不能把“策略重新选输出”描述成在 AudioFlinger 内把所有旧 PCM 原样搬到新线程，源代码并没有提供这样的通用保证。

但这不是无条件、无损的恢复：

13.6. 关闭输出还要处理引用、效果与线程退出

closeOutput_nonvirtual() 先在 AudioFlinger 的管理范围内移除输出关联，处理 duplicating 输出及效果链迁移、发出 I/O 关闭通知；随后让工作线程退出并释放输出包装对象。

效果可能需要移到其他线程或暂存为 orphan chain，客户端 Track 也可能需要被通知失效。这里的强引用用于确保“退出线程这项工作执行期间，线程容器对象还活着”。从全局表删除对象、停止执行线程、释放底层 HAL stream 是不同动作。

这种分层清理解释了为什么不能在持有全局锁时随意等待另一个音频线程退出，也不能以“一个容器里已找不到 handle”推断所有关联引用和硬件资源已在同一条语句中消失。

14. 时间戳、延迟与并发：让不同位置说同一种语言

14.1. 至少区分四个播放位置

假设应用已经向 AudioTrack 写入 100 ms 音频，此时耳机里是否已经响了 100 ms？仅靠 write() 返回值无法回答，因为不同位置对应不同阶段。

位置 代表什么 不能单独证明什么
客户端累计接受帧数 这一批数据已经提交给播放通道 不代表服务端已消费，更不代表已发声
Track 服务端释放位置 共享缓冲中的这些帧已被服务端取走、释放 不代表它们已离开混音、pipe 或 HAL 缓冲
输出线程 / sink 写入位置 输出时间轴上的数据已交给当前 sink sink 可能是 MonoPipe，不能一律解释成扬声器位置
HAL presentation position HAL 给出的呈现位置与关联时刻 精度和覆盖范围取决于 HAL；不是麦克风测得的声学结果

这些位置还可能采用不同采样率。A 的 44.1 kHz 输入帧，与输出的 48 kHz 帧，既不能直接相减，也不能因为计数都叫 frames 就认为一一对应。

ExtendedTimestamp 同时记录不同阶段的位置和时间，并保留有效性信息。普通输出的 AudioStreamOutSink::getTimestamp() 把 HAL 的 getPresentationPosition() 结果放入 LOCATION_KERNEL。这个枚举名称是框架的阶段标识；不能据此声称每家 HAL 返回的就是裸 ALSA DMA 指针。

普通输出、FastMixer、direct/offload、MMAP 获取位置的路径并不完全相同。分析时间戳时，应先确认实际输出类型与 sink，再沿其实现追踪，不能拿普通混音的计数规则解释压缩 offload 字节数。

14.2. FrameMap 为什么需要同时记 Track 与 sink 的位置

如果 A 从一开始就以固定速度播放，理想情况下可以用采样率比例建立输入帧到输出帧的映射。但真实播放会暂停、缺数、变速、flush，也会经历起播等待；输出线程仍可能因 B 持续播放而向前推进。

因此，A 的 Track 时间轴不是从输出线程创建开始就永远线性增长的一条固定比例直线。Track::updateTrackFrameInfo() 在普通 PCM 路径中记录两侧实际进度，再把输出阶段的时间戳翻译到该 Track 的坐标。

这里的 drained 与“共享缓冲已空”不是同一件事。共享缓冲可能已经全部释放，而最后一部分数据还在下游等待呈现。框架要结合更靠后的有效位置，判断已释放数据是否走完相关输出阶段，再推进尾部清理、回调或资源管理。

Fast Track 不走这里相同的普通 Track 线性映射；offload 又需要结合 HAL drain 回调。第 5 章停止状态和第 11 章异步排空之所以不能统一成“队列空就结束”，原因就在这里。

这 30 ms 不包含尚未进入该输出坐标的应用端积压，也不自动包含无线传输、外设 DSP、功放与声学传播的全部延迟。若两位置对应的时间不同，还要做时间对齐；若采样率、播放速度或时钟基准不同，也不能直接代入。

实际排查需要区分：

  • 容量：例如缓冲最多容纳 4096 帧；这是上限，不等于此刻排了 4096 帧。
  • 占用：当前生产与消费位置之差；决定这一段眼下积压了多少数据。
  • 周期：某线程每轮处理的帧数除以其采样率；它约束补充数据的节拍。
  • 起播等待：填充阈值、路由启动、HAL 退出 standby 等引入的启动时间。
  • 稳态端到端延迟：从应用产生数据到目标测量点观察到结果的时间，必须说清测量起止点。

扩大缓冲通常增加抵抗供数抖动的余量，但只有实际积压增大时，才会相应增加这一段排队时间。缩小缓冲也不会让 HAL、DSP 或蓝牙传输中的固定处理阶段消失。因此调优要同时看实际占用、underrun 与尾延迟，不能只比一个 bufferSizeInFrames。

遇到时间戳不可用、位置跳变或突然回退时，先检查是否刚启动、停止、flush、切换设备或重建 Track，再检查 HAL 的有效性和时钟关系。不要先把所有不连续解释成算术溢出，也不要把一次成功返回的旧时间戳无限外推。

14.4. 锁不是越少越好，关键是保护什么、在哪个阶段等待

音频服务同时面对 Binder 控制线程、普通音频工作线程、快速线程和异步 HAL 回调。它们并非共享一把全局锁来串行完成所有工作。

同步对象 主要保护或协调的内容 读源码时要注意
AudioFlinger mutex() 线程表、全局服务状态及关联管理 不应被理解为所有 PCM 计算必持有的锁
clientMutex()、hardwareMutex() 客户端注册与 allocator 生命周期、硬件设备管理 独立保护域有专门锁序，不能任意交换
ThreadBase mutex() Track 集合、状态、配置事件与线程内部控制信息 工作循环会在合适位置释放；跨策略调用尤其要检查解锁
EffectChain / EffectBase 锁 效果链资源、模块状态和处理过程的一致性 必须避免效果回调形成反向锁序
cblk 原子字段与 futex 应用和服务端之间发布帧、等待容量、异常唤醒 与服务内 C++ 对象锁是不同协议
FastMixer StateQueue 普通线程向快速线程发布配置快照 发布成功与旧对象可以销毁之间，仍可能需要 ACK

Effects.h 明确记录多锁共同持有时的相关顺序：AudioFlinger → ThreadBase → EffectChain → EffectBase；效果 handle 路径也有相应层次。它同时指出，可能取得 AudioPolicyService 锁的相关调用，不应在持有 AF / ThreadBase 锁时贸然执行，因为策略端又可能回调 AudioFlinger。

这解释了 createTrack() 先做策略选择，以及 addTrack_l() 调用 startOutput() 前临时释放线程锁的安排。解锁后的状态不能假定未变，所以恢复持锁后还需要检查 Track 状态与调用结果。这不是重复检查，而是在处理并发窗口。

函数名中的 _l / _ll 是锁约定的提示，实际仍应结合声明上的 REQUIRES、EXCLUDES 与调用上下文判断；后缀本身不会替程序自动上锁。

S getTrackStateAsCodedString() 输出的轨道状态缩写 与 Java getPlayState() 的数值枚举直接比较
Flags 这里打印的是 mCblk->mFlags，即共享控制块状态位 当成 AUDIO_OUTPUT_FLAG_FAST / DIRECT / ... 申请或批准结果
Format、Chn mask、SRate 轨道格式、声道掩码、采样率 与所属输出线程参数混成一组
G db、L dB、R dB、VS dB 最终增益、左右音量、VolumeShaper 等观测 把 dB 值当线性音量相乘；-inf 通常对应零增益
PortVol dB、PortMuted、InternalMute port 音量与静音、内部静音状态 只看应用 setVolume() 就排除静音可能
Server mCblk->mServer，按十六进制输出的服务端进度 当成十进制毫秒，或当作硬件呈现位置
FrmCnt 当前有效缓冲帧数；小于分配容量时可带 r 标记 一律认作初始分配容量或 HAL burst 大小
FrmRdy 安全读取的服务端可见就绪帧数，输出还做了显示上限裁剪 当作无竞争、跨状态绝对精确的永久积压值
F 填充阶段：I/f/F/A 对应 invalid/filling/filled/active 与前面的 FAST F槽位号 混淆
Underruns 此处核心数字为 underrun 帧数，并可能附带近期状态字符 直接当作 Java getUnderrunCount() 的事件次数
Flushed 被 flush 的帧计数显示 认为这些帧已经播放完
Latency 该路径可提供的服务端延迟信息；后缀 t/k 表示不同来源 当成全链路声学延迟或永远有效的固定值

线程段还应看 HAL frame count、Normal frame count、输出采样率、Frames written、Total writes、Delayed writes、Blocked in write、AudioStreamOut ... flags 以及 FastMixer / pipe 信息。轨道、输出 stream、控制块的 flags 属于不同层，名称相近也不能混用。

Blocked in write: yes 只是采样时线程处在写调用里。音频写出本来就可能承担节拍控制；需要结合持续时间、输出周期和历史分布，才能判断是否异常阻塞。

录音表使用另一套表头，包含 Source、Sil 等字段。应回到 IAfRecordTrack::getLogHeader() 与 RecordTrack::appendDump() 对照，不能把播放表的 F、underrun 解释直接套过去。

15.3. 场景一：证明“创建、激活、开始消费”是三个阶段

准备一个可控制写入节奏的普通 PCM STREAM 测试程序。程序应记录 PID、AudioTrack session id、请求参数、构造结果、实际缓冲大小、实际启动阈值（接口可用时）、每次写入量与返回量，以及基于单调时钟的操作时间。避免把文件解码耗时和网络下载混入第一轮实验。

操作分三步：

  1. 只创建 AudioTrack，暂不 play()，抓取快照。
  2. 写入少量数据，再 play()；数据量有意低于实际生效的启动阈值，保持短暂可观察窗口。
  3. 继续供数，达到阈值后持续写入，再抓快照或看 trace。

预期差异是：第一步可能在 mTracks 对应 dump 中看到对象，但不在 active 集合；第二步可出现 active 但仍在 filling 的状态；第三步服务端位置开始推进、填充阶段发生变化。具体过渡是否能被 dump 抓到，取决于窗口长度和线程调度。

这个场景的判定条件必须包含“实际阈值”。若测试程序申请阈值后被夹紧，或写入量已经超过阈值，观察到立即起播并不能推翻第 5 章。若程序使用 static、direct 或 FAST，也不能套用普通 MixerThread 的 isReady() 解释。

15.4. 场景二：两种采样率怎样汇入同一输出

使用开篇 A / B 的输入参数，同时播放可区分的固定测试信号。第一项工作不是听声音，而是通过 PID、session 或 port 找到两条 Track，确认它们确实隶属同一个普通 MixerThread。

对照三组值：A 的 Track 采样率、B 的 Track 采样率、所在输出线程采样率。如果 A 为 44100、B 和输出为 48000，就具备了讨论本例重采样的条件。若设备不接受所选 PCM 32 位格式，可另外建立 PCM 16 位对照组，并明确记录格式变化；不能悄悄改参数后声称复现了原配置。

预期是输出维持自身时间轴，两个输入按各自条件供数并汇入结果。A 在理想 20 ms 时间跨度对应 882 输入帧，输出对应 960 帧，但单次共享缓冲请求可能因滤波历史、相位和连续区域边界而不同。

若两条 Track 被策略放到不同输出，实验首先验证了“路由不由应用参数单方面决定”。此时应记录两个 I/O handle 与实际类型，不应强行把它解释成 AudioMixer 同一轮处理。

15.5. 场景三：区分应用缺数、调度延迟和下游写阻塞

先让普通 Track 稳定播放，再在测试程序的供数线程中主动停止供数一小段时间，例如从 100 ms 开始逐步调整，期间保持 AudioTrack 播放状态；随后恢复正常供数。另保留 B 持续播放，便于观察同一混音输出是否仍在推进。

记录实验前后应用的 underrun 事件计数、服务端 Underruns 帧数、FrmRdy、Server、active 状态和日志。由于缓冲可能足够大，100 ms 不一定导致缺数；应先根据实际占用和播放速度判断这段停顿是否会耗尽队列。

预期因果链是：A 供数暂停 → 可读帧数下降 → 普通轨道就绪条件不满足 → 相关 underrun / 重试逻辑生效。若持续时间足够，还可能看到 BUFFER TIMEOUT、移出 active、CBLK_DISABLED，恢复供数时由客户端重新启动。并非每次短暂 underrun 都会达到 disable 门槛。

15.6. 场景四：验证低延迟申请是否成为 FAST

用同一测试程序创建两组轨道：一组普通模式，一组请求低延迟。先记录输出实际采样率，再让低延迟组尽量使用该采样率和兼容声道、格式；在稳定基线下，一次只改变一个条件，例如采样率或效果配置。

检查客户端实际报告的模式、Track 的 Type 前缀、所属输出类型、FastMixer 槽位与可用 mask；不能只看构造时传入的选项。特别注意：Track 表的 Flags 是 cblk 状态位，不能据此直接检验 AUDIO_OUTPUT_FLAG_FAST。

预期可比较的结果包括：条件满足且资源可用时成为 FAST；采样率或效果不兼容、无 FastMixer、槽位不足等情况下被拒绝或退回其他可行路径。低延迟申请没有被接受，本身不是框架错误。

若要测试槽位上限，需要记录所有占用者，并理解“槽位在创建时取得”与“当前是否活跃”并不相同。不要只数正在出声的应用数。默认配置下的七条应用快速轨道也不能当成所有设备不可改变的常量。

15.7. 场景五：声音消失时，沿哪条分支查

先确定应用确实在提交预期的非零 PCM，再按下面的顺序缩小范围：

  1. 对象与输出：服务端有无对应 Track？是否属于预期 I/O handle 和设备？创建、start 或写入是否已经报错？
  2. 激活与填充：是否 active？状态与 filling 阶段是什么？可读帧是否达到实际门槛？
  3. 消费进度：连续观察 Server 或时间戳是否前进；不能凭单次相同数值下结论。
  4. 幅度处理：应用 LR 音量、VolumeShaper、最终/port 增益、mute、内部静音以及效果链是否把信号变为零？
  5. 输出推进：所属线程、pipe / HAL 写入位置是否前进，是否有错误或长期等待？
  6. 呈现与设备：HAL 呈现位置、patch、设备连接和实际外设是否符合预期？

可以在稳定播放时仅将应用音量置零，再恢复，作为对照。预期数据消费仍可继续，但幅度被压为零；这能证明“没有声音”和“服务端没有消费”是不同问题。是否能在特定 dump 中看到对应音量变化，取决于实际音量管理分支。

如果 Track 消费与输出位置都前进，而目标扬声器仍静音，应继续查信号内容、效果、HAL 和设备路径。不能据此直接宣判 AudioFlinger 完全无问题，也不能继续只盯着 write() 返回值。

15.8. 场景六：切设备时分清 patch 更新与 Track 重建

持续播放普通 PCM，在扬声器与一个已连接、可用的目标输出设备之间切换。切换前后记录 Track id、port id、I/O handle、输出类型、采样率、flags、设备和 patch；应用记录写入返回、时间戳以及路由变化回调（若使用）。

两类符合源码的结果是：

  • 原 I/O handle 和 Track 保留，设备/patch 改变：与复用现有输出相符。
  • 旧 Track 失效，出现新的 Track / port / 输出关系：需要继续确认客户端是否进行了恢复、参数如何变化、是否丢失待播数据。

某个数值没有变，并不能证明没有其他阶段变化；某个数值变了，也不能仅凭它确定全部重建原因。应结合策略与 AF 两份 dump，必要时加入客户端恢复日志。

对 direct/offload，单独做实验并记录上层如何处理错误，不能沿用“普通 PCM 会尝试自动恢复”的预期。切换后的音频听起来连续，也不代表每一帧都被无损迁移。

15.9. 场景七：录音的静音与 overrun 分开验证

在已获得必要录音授权、用途明确的测试程序中进行采集，记录 source、请求与实际参数、session、read 的实际返回量、数据幅度和时间戳。先确认 RecordTrack 已开始、Sil 状态如何，再讨论声音内容。

静音对照：在设备支持的用户麦克风隐私控制下切换状态，同时观察 read 返回量、样本幅度和 Sil / 策略状态。若 read 继续成功但样本为零，这与策略静音或相应硬件静音路径可能相符；还要结合来源和 HAL 状态，不能仅凭“零”确定具体哪一层清零。

供数跟随对照：在稳定录音后故意让客户端读取线程停顿超过其实际缓冲可容纳的时长，再恢复。预期可能出现 overrun、位置追赶或数据不连续，而不是把停顿期间所有历史音频补读回来。停顿未超过余量时没有 overrun，也符合缓冲设计。

多应用同时录音要先检查策略是否允许、哪些客户端被静音以及是否共用一个输入。第 12 章的分发图表达的是获准共享同一普通 RecordThread 的情况，不是绕过 Android 录音竞争规则的承诺。

16. 分层复习与折叠自测

16.1. L0：先能用自己的话说清主干

AudioPolicy 选择合适的输出和设备关系；AudioFlinger 为输入输出组织持续运行的线程与 Track。普通 AudioTrack 通过 Binder 创建和控制服务端对象，通过共享内存提交 PCM；MixerThread 从就绪轨道取数，让不同格式和采样率的信号在共同输出时间轴上参与处理，再经过音量、效果和 sink 写出。

存在 FastMixer 时，普通混音结果可以先进入 MonoPipe，再作为 FastMixer 的一个输入，与快速轨道汇合；普通轨道并不会因此变成 FAST。RecordThread 则从输入源取得音频，按各个获准 RecordTrack 的格式和进度分发给客户端。

记住六个不能合并的边界：

  1. 创建成功，不等于已经激活。
  2. 已经激活，不等于填充与本轮就绪条件满足。
  3. 服务端已经消费，不等于硬件已经呈现。
  4. 数据持续前进，不等于其幅度非零或路由正确。
  5. 请求某种模式，不等于最后获得该模式。
  6. 队列暂时缺数，不等于通道已经失效。

16.3. L2：能解释条件变化后的结果

当题目增加一个条件，先判断它影响哪一层，再推演后续：

  • 改变采样率或速度：影响每轮输入帧需求，也可能改变 FAST 准入；不能只调整一个毫秒换算公式。
  • 增加效果：影响 mainBuffer 与链顺序，还可能影响低延迟或 offload 路径资格。
  • 供数停顿：先看实际缓冲占用，再看就绪、重试与 disable；不要直接推断服务死亡。
  • 切输出设备：先看原输出是否可复用，再讨论 patch、失效与客户端重建。
  • 观察到静音：先确定数据是否推进，再区分幅度处理、策略静音、路由和 HAL。
  • 要求更低延迟：同时讨论应用供数稳定性、有效缓冲、输出周期、路径资格和下游固定延迟。

16.3.1. 一个完整的综合推演

假设 A 与 B 在同一普通 MixerThread 中播放，该线程存在 FastMixer；A 需要从 44.1 kHz 重采样，B 是 48 kHz。A 的写线程停顿，而 B 继续供数；随后用户切换输出设备。

先处理 A 的缺数：MixerThread 逐轨道检查，不会无限等待 A；短暂等待、就绪状态调整、禁用该混音槽位或耗尽重试均有条件。B 的持续存在意味着输出可能仍推进，但 A 是否已被 disable 要看实际停顿长度与缓冲。FastMixer 的 slot 0 接收的是普通混音结果，不能用它仍在工作来证明 A 仍有数据。

再处理切设备：如果输出被复用，原 Track 可保留，仅更新 patch 等状态；如果旧通路失效，可重连的普通 AudioTrack 尝试重新创建。此时 A 此前的缺数与本次路由重建是两个不同原因，应分别用 CBLK_DISABLED 与 CBLK_INVALID / 新旧对象关系解释，不能把所有中断统称为“FastMixer 出问题”。

最后核对进度：A 的输入帧、普通输出帧、FastMixer / HAL 位置不是同一坐标。必须先统一时间轴与阶段，才有资格讨论丢了多少、积压多少、延迟增加在哪一段。

基础对象与数据边界

1. AudioFlinger、MixerThread、AudioMixer、Track 分别是什么？

AudioFlinger 是管理整个服务端音频执行体系的服务；MixerThread 是承担普通播放循环的工作线程对象；AudioMixer 是被线程调用的音频处理组件，不自行创建一条同名工作线程；Track 是某条播放轨道的服务端状态与缓冲访问对象。一个 MixerThread 可以处理多条 Track。

回看第 2、6、7 章。不能用“应用数”直接推算线程数，也不能把 AudioMixer 当作 Binder 服务。

2. AudioTrack.write() 的 PCM 为什么不需要每次通过 Binder Parcel 交给 AudioFlinger？

普通 STREAM 通道建立时已经提供了共享区域。客户端把 PCM 写入共享缓冲并按协议发布位置，服务端通过 proxy 取得数据；Binder 主要承担创建、start、pause 等控制。cblk、原子位置和 futex 共同协调容量与等待。

回看第 4–5 章。这不等于全链路零拷贝，混音、格式转换与 HAL 传输仍可能复制数据。

3. 普通播放的 front 和 rear 分别由谁推进？录音呢？

播放时客户端是生产者，推进 rear；服务端是消费者，释放已读帧后推进 front。录音时服务端生产并推进 rear，客户端消费并推进 front。共同点是“生产者发布 rear，消费者释放 front”，而不是“front 永远属于服务端”。

回看第 5.3、12.5 节。

4. dumpsys 里 Active=yes，为什么仍然可能没有声音？

可能仍未达到启动填充门槛，本轮帧数不足，处于特定状态转换，音量或效果将信号清零，或者输出设备与预期不同。还需要查 filling、FrmRdy、状态、连续消费进度、音量与设备关系。

回看第 5–6、8、15 章。active 表示调度集合归属，不是声学结果。

主循环与特殊路径

5. A 是 44.1 kHz、输出是 48 kHz，处理 20 ms 时为什么不能给每条轨道都请求 960 输入帧？

960 是 48 kHz 输出在 20 ms 中对应的帧数；44.1 kHz 输入理想上对应 882 帧。实际源帧需求还要考虑重采样历史、播放速度和未释放帧，所以代码计算 desiredFrames，而不是对所有轨道套固定输出帧数。

回看第 6.3、7.1 节。单次 obtain 的连续段长度也不必正好等于整个时间跨度所需帧数。

6. 一块 sink 缓冲只写出去一半，下一轮能立即把新混音结果覆盖上去吗？

不能。mBytesRemaining 保留未提交部分，写入位置由当前块长度减去余量计算。上一块未完成时继续处理剩余部分，不能用新音频覆盖仍待写出的数据。

回看第 6.6 节。需要同时考虑错误、异步等待和状态变化，不能把一轮循环等同于一次完整硬件提交。

7. 普通音乐的输出经过 FastMixer，为什么它仍然不是 FAST Track？

普通 Track 先由 MixerThread 处理，其混音结果经 MonoPipe 进入 FastMixer slot 0。真正 FAST Track 经单独准入与槽位分配，绕过普通逐轨混音阶段进入其他 slot。两者只是在最终快速混音阶段汇合。

回看第 10 章。FAST 默认可用应用槽位数也要扣除保留的 slot 0，并考虑实际配置与占用。

8. Direct、offload、MMAP 都能简称为“绕过 AudioFlinger”吗？

不能。DirectOutputThread 与 OffloadThread 仍在 AudioFlinger 中承担轨道管理、状态推进和相应写出；offload 改变解码/渲染承担者。MMAP 普通数据路径绕过共享环形缓冲加 MixerThread 的模型，但 AudioFlinger 仍有 MMAP 控制、流与客户端管理。

回看第 11 章。必须分别描述“数据走哪里”和“谁负责控制”。

9. 给 A 添加会话效果，为什么不能先把 A、B 混成一块再对整个结果处理？

这样会让本来只属于 A 会话的效果也作用到 B。普通混音通过不同 mainBuffer 保留效果作用域，效果链按会话、输出混合与输出阶段等关系处理。不同会话的轨道并非都先进入同一个不可分离缓冲。

回看第 7.5、8.3–8.4 节。效果变化还可能影响 FAST / offload 资格。

故障与场景推理

10. 供数恢复后又有声音，是不是说明 AudioTrack 一定被重新创建了？

不一定。缺数导致的 CBLK_DISABLED 可以让仍处于播放状态的客户端重新启动原 Track；CBLK_INVALID 才表示现有通道失效并可能进入重建。应对照 Track id、port、I/O handle 与日志，区分恢复调度和恢复通道。

回看第 6.4、13.5 节。

11. 看到 Track 表 Flags 的某一位，能直接确认 AUDIO_OUTPUT_FLAG_FAST 吗？

不能。本版本 Track 表的该列打印的是 mCblk->mFlags。输出 stream flags、Track 获准的路径属性、cblk 状态位分属不同语义。应结合 Type 的快速槽位标记、线程类型、FastMixer 状态以及客户端实际模式判断。

回看第 10.3、15.2、15.6 节。

12. AudioOut 线程有一个很长的 write slice，为什么不能直接判定 HAL 卡住？

先确认这个 AudioOut 的 sink 是什么。存在 FastMixer 时，普通线程可能在向 MonoPipe 写，背压来自后续消费节拍；即使直接写 HAL，也可能存在正常的阻塞节拍控制。需要结合持续时间、输出周期、FastMixer / HAL 线程与调度状态判断异常发生在哪一层。

回看第 9–10、15.5 节。

13. AudioRecord.read() 持续返回正数但采样全零，首先应该查什么？

先确认数据格式解析、信号源和实际 RecordTrack，再检查 Sil、策略与用户麦克风隐私状态、HAL 输入。RecordThread 可在策略要求下清零并正常释放录音缓冲，因此成功 read 不保证内容未经静音。零样本也可能原本就来自静音源，不能只凭幅度确定清零层级。

回看第 12.6、15.9 节。

14. 耳机插入后必须销毁所有 Track、创建新 MixerThread 吗？

不必。如果原输出可复用，可以更新 patch 等设备关系并保留原 Track。需要换输出时，旧 Track 才可能失效并由客户端按条件恢复；direct/offload 与普通 PCM 的恢复限制不同。

回看第 13 章。比较设备连接类型不足以决定结果，必须看实际策略与 profile。

15. 服务端已释放 44100 输入帧，HAL 已呈现 47000 输出帧，能直接相减得到延迟吗？

不能。题目没有给出相同坐标、对应时间、采样率和播放状态；输入与输出帧数甚至可能分别处于 44.1 kHz 和 48 kHz 时间轴。普通 PCM 的 FrameMap 用实际进度建立关系，时间戳还要考虑有效性、flush 与状态变化。

回看第 14.1–14.3 节。即使正确算出两个阶段的积压，也不自动等于完整声学端到端延迟。

16. removeTracks_l() 已持有线程锁，为什么还要设置 busy 标志？

因为通知策略停止或释放输出时会临时解锁。busy 配合控制入口的条件变量等待，使相关 TrackHandle 操作不会在这个移除事务的中途越过等待点。等待时会释放线程锁，事务完成后重新竞争锁并检查条件。

回看第 14.4–14.5 节。它保护特定的跨解锁过程，不意味着普通混音整轮都封锁全部控制操作。
