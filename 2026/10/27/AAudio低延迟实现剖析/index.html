1. 从一次电子琴按键开始：低延迟究竟优化什么

假设我们正在实现一架 Android 电子琴：手指按下琴键，应用生成一段 PCM，用户希望几乎立即听到声音。把 AudioTrack 换成 AAudio、设置 LOW_LATENCY，是否就完成了低延迟优化？如果再请求 EXCLUSIVE，数据是不是直接交给声卡，系统再也不参与？

这两个问题都不能只从 API 名称回答。AAudio 是应用接口；MMAP 是一种数据通路；低延迟是整条链路在设备、配置、调度和负载共同约束下的结果。 AAudio 可以使用 MMAP，也可以退回 AudioTrack / AudioRecord。MMAP 又分独占与共享：前者让应用进程中的音频库访问硬件共享缓冲，后者由 audioserver 中的 AAudioService 汇合多路应用数据后访问它。

本文以“电子琴打开低延迟输出流 → 回调合成 PCM → 连续播放 → 第二个应用竞争设备 → 路由切换后重建”为主线，回答以下问题：

  • Builder 的请求经过哪些判断，才真正落到 MMAP、共享 MMAP 或 Legacy？
  • PCM、控制命令、时间戳分别走哪里，AudioFlinger 到底被绕过了哪一部分？
  • 没有逐 burst 的设备中断来催促应用时，软件如何知道何时读写环形缓冲？
  • burst、callback、capacity、buffer size 各自约束什么，为什么越小不一定越好？
  • 怎样区分选路失败、供数不足、调度抖动、时间戳异常和下游设备固有延迟？

图中绿色实线只表示 PCM 的主要流向。Legacy 一行概括 AudioFlinger 的普通/快速混音路线，不能据此认定回退一定经过普通 MixerThread；MMAP 两行省略客户端转换过程及控制接口。应用独占的是所分配的 MMAP endpoint 资源，不是整台设备的全部音频系统。

2. 先把六个容易混淆的概念拆开

2.1 AAudio：统一的流接口，不是唯一的实现路线

应用使用 AAudioStreamBuilder 描述希望得到的流，调用 AAudioStreamBuilder_openStream() 建立 AAudioStream，再通过 callback 或 read() / write() 传输 PCM。Builder 保存的是请求；open 后的 stream 保存协商结果。

接口的便利之处在于，应用不必自行绑定 AudioFlinger、分配 Binder 共享内存、申请硬件映射并维护时钟模型。但这也意味着应用不能仅凭“我调用了 AAudio”判断底层用了什么。

维度 典型值 它回答的问题
方向 OUTPUT / INPUT 生成声音还是采集声音
性能模式 NONE / LOW_LATENCY / POWER_SAVING 延迟与功耗如何取舍
共享模式 SHARED / EXCLUSIVE endpoint 能否按独占方式分配给当前流
数据方式 callback / read-write 由库调度应用供数，还是应用自己安排读写
后端 MMAP / Legacy PCM 最终走哪条系统路径
实际参数 采样率、格式、声道、burst 等 本次打开真正协商到了什么

这些维度彼此相关，但不是同一个开关。例如 SHARED 可以是 MMAP SHARED，也可以是 Legacy；LOW_LATENCY 可以是 MMAP，也可以是 Legacy FAST。

2.2 MMAP：映射的是哪一块内存

Linux 的 mmap() 把一个可映射的文件描述符所代表的内存区域接入进程虚拟地址空间。两个参与者可以有不同的虚拟地址，却访问同一段共享存储。Binder 在建流时传递 FD 和描述信息，不需要为每个音频采样发送一次 IPC。

但 “用了共享内存”不等于“用了 AAudio MMAP”。AudioTrack 的客户端和 AudioFlinger 之间也有共享缓冲；MMAP 低延迟路径的关键是硬件/DSP/驱动所使用的数据区域能够通过 HAL 提供给相应软件端，从而减少中间软件搬运和排队环节。

应用拿到的是受框架管理的 AAudio 流，不是 ALSA 设备节点或任意 DMA 内存访问权。FD 是否可以安全交给应用，有单独的 AUDIO_MMAP_APPLICATION_SHAREABLE 条件，第 5 章会追到检查点。

2.3 NOIRQ：少一类唤醒来源，多一份时间责任

传统周期式音频设备可以通过 period interrupt 通知软件“又消费/采集了一段数据”。MMAP/NOIRQ 路径不依赖这种逐周期通知驱动应用搬运，设备侧持续推进，软件依据时间戳估算位置并安排下一次醒来。

NOIRQ 不表示整个系统没有硬件中断，也不表示应用永远不用睡眠或系统调用。它把持续供数的核心问题变成：硬件此刻大约走到哪里，我最晚应该在什么时候填好下一批数据？

因此，MMAP 不是只做一次 mmap() 就结束。准确的时间戳、正确的帧计数、合理的提前量和可预测的线程调度缺一不可。

2.4 FAST 与 MMAP：两条不同的低延迟路线

FAST track 属于 AudioTrack / AudioFlinger 体系，符合条件的轨道可由 FastMixer 路径处理。MMAP 使用 MmapThread 管理 HAL 流和控制关系，PCM 不按普通 MixerThread 的软件混音循环传输。

两者都追求更短的排队与更及时的处理，但对象、缓冲协议和准入条件不同。不能把 AUDIO_OUTPUT_FLAG_FAST 与 AUDIO_OUTPUT_FLAG_MMAP_NOIRQ 混为一谈，也不能把 MMAP SHARED 中的 AAudioMixer 当成 AudioFlinger 的 FastMixer。

2.5 低延迟：必须先说测量区间

电子琴“按下去多久出声”至少涉及输入事件分发、应用参数更新、等待下一次合成、音频排队、HAL/DSP、DAC 与声学传播。

为了避免重复相加，可以把一次触发到出声的延迟概念性拆成：

事件到达与合成等待 + 本次计算时间 + 生成帧之后沿各级队列的驻留时间 + 未被前述队列覆盖的下游处理与输出时间。

队列帧数 / 采样率 只描述相应队列的音频时长。它不自动包含所有下游延迟，也不等于从手指触屏开始计时的总延迟。双向监听的 round-trip latency 则还包含输入链、应用处理以及输出链；不能拿单向 buffer size 冒充往返结果。

2.6 frame、sample 与 burst

PCM 的一个 sample 是某个声道在某一采样时刻的数值；一个 frame 包含该时刻所有声道的 sample。48 kHz、双声道 float 的每个 frame 是 8 字节，每秒有 48,000 frame，而不是 96,000 frame。

burst 是底层或软件一次推进/处理的基本批次。假设实际报告 192 frame/burst、48 kHz，则一个 burst 对应 192 / 48000 = 4 ms。这只是例子，不能把 192 当成 Android 统一常量。第 8 章还会说明 API 报告的 burst 可以经过软件放大和采样率换算，并不一定就是驱动原始 period。

3. 总体架构：三条数据路径，三类通信

3.1 谁负责什么

位置 对象 责任与边界
应用进程 AudioStreamBuilder 校验请求，决定是否尝试 MMAP，失败时是否允许 Legacy
应用进程或服务内部 AudioStreamInternalPlay/Capture MMAP 家族客户端；映射 endpoint、转换数据、维护时钟与回调
应用进程 AudioStreamTrack/Record Legacy 适配，内部使用 AudioTrack / AudioRecord
audioserver AAudioServiceStreamMMAP/Shared 单条服务端流的身份、状态、事件、时间戳和资源关系
audioserver AAudioServiceEndpointMMAP 连接一个 MMAP 硬件 endpoint，取得缓冲和位置，接收路由/音量事件
audioserver AAudioServiceEndpointPlay/Capture 共享流的混音或采集分发，持有服务内部 MMAP 流
audioserver MmapThread（AudioFlinger 内） 管理 HAL 流、启停、客户端和控制；不是普通 PCM 混音循环
audioserver AudioPolicy 根据属性、设备、profile 和资源约束选择输入输出

注意服务代码目录叫 services/oboeservice，其实现是平台的 AAudioService；不能因为目录包含 oboe，就把它当成应用侧 Oboe C++ 库。

Stream 与 Endpoint 也不要混用：前者描述一条客户端连接，后者描述它接入的实际资源。多个 shared stream 可以注册到同一个共享 endpoint，endpoint 再共同持有内部 MMAP 流。流数与硬件 endpoint 数不必相等。

3.2 控制、PCM、事件各走一条路

一次 MMAP 播放至少存在三类通信：

  1. 控制面：应用通过 Binder 调用 AAudioService 的 open、start、stop、close 等；服务再经 AudioFlinger / AudioPolicy / HAL 建链和管理设备。某些服务操作还要进入命令线程，并等待其结果，不能把 Binder 接收线程画成所有工作的唯一执行者。
  2. 数据面：PCM 放进共享 FIFO 或硬件 MMAP 区域。应用每次产生一批 PCM，不需要把这批 PCM 放进 Binder Parcel。
  3. 服务到客户端的消息面：共享的 up message queue 承载开始/停止/断开/音量/XRun 事件，以及时间戳。客户端在 processCommands() 等入口消费这些消息。

这解释了为什么“数据不经过普通 AudioFlinger mixer”与“系统仍能控制设备、音量、权限和路由”可以同时成立。被缩短的是 PCM 主路径，不是把整个音频策略系统删除。

3.3 独占与共享到底差在哪

在 MMAP EXCLUSIVE 下，应用进程中的 AudioStreamInternalPlay 写向硬件共享区域；AAudioService 仍负责创建资源、获取时间戳和转发事件。

在 MMAP SHARED 下，应用写的是自己的共享 FIFO。AAudioService 的共享线程从多个 FIFO 取数据，用 AAudioMixer 混成一份，再通过服务内部的 AudioStreamInternalPlay 写入硬件 MMAP 区域。因此它多了客户端 FIFO、共享线程调度和混音，但仍可以保留 MMAP 的底层通路。

这也是“请求独占失败”不一定等于“MMAP 失败”的原因：服务端可能先从独占改为共享，只有整个 MMAP 家族打开失败，Builder 才考虑 Legacy。

4. openStream：低延迟请求怎样变成实际路径

4.1 第一层判断：系统到底允许尝试 MMAP 吗

AAudioStreamBuilder_openStream() 最终进入 AudioStreamBuilder::build()。这版代码不是简单读一个属性就构造 MMAP 对象，而是先结合进程级策略与 AudioSystem::getMmapPolicyInfos(DEFAULT) 的查询结果。

策略 数值 Builder 层的含义
UNSPECIFIED 0 未指定，由系统策略与默认值补足
NEVER 1 不尝试 MMAP
AUTO 2 可以尝试 MMAP，打开失败可退 Legacy
ALWAYS 3 要求 MMAP，不能退 Legacy

还有一组 EXCLUSIVE 策略，用来控制能否请求应用独占。两组策略不能混为一个开关。ALWAYS 要求的是 MMAP 后端，不自动要求 EXCLUSIVE。

当前 AAudio_getAAudioPolicy() 对系统返回的策略列表做聚合：只要有 AUTO 或 ALWAYS 项，就返回 AAUDIO_POLICY_AUTO。这表示“存在可尝试的设备能力”，并不是“所有设备都支持”，也不是直接把某个设备的 ALWAYS 提升成整个进程的强制策略。

若系统明确 NEVER，进程级请求不能凭空启动不受支持的服务；查询失败时当前实现也会禁止普通 MMAP 尝试，强制 MMAP 的情况返回错误。media/audioserver/main_audioserver.cpp 则在成功查到至少一个 AUTO/ALWAYS 项时才实例化 AAudioService。客户端选择与服务是否存在必须配套。

5. MMAP 建链：从服务端请求到应用可用的地址

5.1 open 不只是分配一个对象

AudioStreamInternal::open() 先拷贝应用请求，再构建 AAudioStreamRequest，通过服务接口打开流。服务返回实际配置后，客户端获取 endpoint description，将其中的共享内存映射到本进程，再配置数据队列、消息队列、burst、时钟模型和回调缓冲。

关键顺序是：

openStream(request, configurationOutput) → 保存 actual 配置 → getStreamDescription() → resolve() → AudioEndpoint::configure() → configureDataInformation() → 状态 OPEN。

这里传回的 description 是内存协议：它包含共享区域、偏移、容量、每 frame 字节数、计数器位置等。它不是 PCM 文件，也不是让应用任意解释的裸指针。

应用地址在本进程通过 mmap() 获得，因此不能把服务端虚拟地址原封不动传给应用使用。SharedMemoryParcelable 做了 FD 复制、区域范围检查和映射生命周期管理。

5.2 AudioFlinger 没有消失：它为 MMAP 建立专门的线程对象

服务端的 AAudioServiceEndpointMMAP::openWithConfig() 调用 MmapStreamInterface::openMmapStream()，再进入 AudioFlinger::openMmapStream()。

对于输出，AudioFlinger 调用 AudioSystem::getOutputForAttr() 时带上 MMAP_NOIRQ | DIRECT；对于输入，调用 getInputForAttr() 时使用 AUDIO_INPUT_FLAG_MMAP_NOIRQ。AudioPolicy 根据设备、属性与 profile 选择或打开相应 I/O。AudioFlinger 再从 mMmapThreads 取回已经建立的线程对象，包装成 MmapStreamInterface。

这里的 DIRECT 表示该输出选择中的直接路径标志，不等于应用 EXCLUSIVE 共享模式。MMAP SHARED 也要依托服务内部的 MMAP endpoint，因此可以关联同样的底层 MMAP/DIRECT 输出资源。

普通播放中，MixerThread 要周期取 Track 数据并混音；这里 MmapPlaybackThread 主要承担 HAL 管理、客户端、音量、路由和状态等工作。名字里都有 Thread，但不能据此假设二者运行同一种 PCM 循环。

5.3 createMmapBuffer：最小需求由软件提出，实际容量由底层返回

endpoint 调用 createMmapBuffer() 请求缓冲。经 MmapThread 转发到 HAL 适配层后，得到包括共享 FD、容量、burst 和标志的信息。

这段逻辑给出一个很实用的诊断：设备可以支持 MMAP SHARED，却不支持普通应用的 MMAP EXCLUSIVE。 例如底层缓冲不允许跨到应用 UID，共享服务仍可能自己持有 MMAP，再用普通共享 FIFO 面向应用。

FD 可映射不代表可以暴露完整硬件控制权。驱动和 HAL 必须保证交给应用的映射范围与访问能力满足隔离要求；应用不能靠增加权限或手工打开声卡绕过框架契约。

5.4 客户端映射：零 IPC 搬运不等于零复制

mmap() 省掉的不是所有内存访问，而是避免为跨软件/硬件边界再采用另一套逐批传输。应用给 AAudio 的 buffer 仍可能经过格式转换、声道适配、采样率转换、音量渐变和写入。

当前 configureDataInformation() 会为数据回调分配 mCallbackBuffer；AudioStreamInternalPlay::callbackLoop() 先把它交给应用，再调用 write()。所以“应用代码获得 DMA 地址并原地合成”并不符合这版标准 callback 路径。第 6 章会看到真实调用。

5.5 HAL 代际与产品配置：不要只看 XML 或一个属性

框架内部使用 createMmapBuffer() / getMmapPosition() 这样的统一接口，下面可以由 HIDL 或 AIDL 适配。AIDL 音频 HAL 的 MMAP 数据描述可定位到 MmapBufferDescriptor.aidl 与 StreamDescriptor.aidl；HIDL 可查 audio/2.0/IStream.hal。同名框架操作不意味着两代 HAL 传输协议完全一样。

例如本地 StreamHalAidl::createMmapBuffer() 并不在这一刻重新分配一块缓冲，而是从已打开的 stream context 读取 MmapBufferDescriptor、buffer size 与 burst，填回框架结构；其 minSizeFrames 参数在此适配方法中标记为 unused。HIDL 的方法命名不能直接套成 AIDL 的调用时序。应用最终仍应信任实际返回的资源描述，而非请求容量。

在产品侧，需要同时具备以下条件：支持的 MMAP 策略、能匹配的 input/output profile 与 route、HAL 缓冲与位置接口、真正可运行的设备通路。对于应用独占还需要可分享给应用的缓冲。

AudioPolicyManager::updateMmapPolicyInfos() 能识别“默认设备项表示属性来源”的情况，再根据 MMAP profile 的 supported devices 补充设备类型映射；也能接收逐设备的策略信息。因此，读取 aaudio.mmap_policy 是排查线索，但不是当前实现的完整能力查询。改成 AUTO 不会给缺失的驱动生成 MMAP 能力。

AOSP 的 AAudio/MMAP 说明适合了解平台接入的总体要求；本文的具体策略查询和回退顺序以本地提交为准，尤其不要直接套用早期版本的属性判定伪代码。

6. 连续播放：谁唤醒应用，谁推进缓冲

6.1 requestStart 返回不等于已经听到第一帧

AudioStreamInternal::requestStart_l() 先把客户端状态设成 STARTING，清理上次运行遗留的时间戳，准备缓冲，再调用服务端 start。若资源处于 standby，可能需要退出 standby、重新取得资源并再次 start。随后启动时钟模型，设置 catch-up 请求，并在配置了 callback 时启动回调线程。

服务端 AAudioServiceStreamBase::start() 会把 START 命令交给命令线程，且 waitForReply=true。命令线程执行 start_l()，启动设备，向 up message queue 写入 STARTED 事件，再更新服务端状态。因此：

  • API 的“请求型状态转换”不等于“内部每一步都完全异步、永不等待”；这个实现可能同步等待服务处理。
  • 客户端进入 STARTED 需要消费对应事件；OPEN、STARTING、STARTED 是不同阶段。
  • STARTED 仍不能证明 DAC 已播放第一帧，更不能证明扬声器已经有可听声音。

首启还涉及设备冷启动和时间模型同步，不能用稳定运行时的 4 ms burst 推断首次起音只要 4 ms。

6.2 callback 实际运行在应用进程，不是服务 Binder 线程

MMAP 输出的回调循环由客户端库创建的线程运行。服务负责注册线程、校验关联并经 requestPriority() 请求音频优先级；不是普通应用自己任意获得实时调度权。优先级请求也可能失败，不能把“调用了 callback API”理解为硬实时承诺。

回调不是硬件中断处理函数。它是一条受操作系统调度的用户态线程，可能因为锁、缺页、CPU 竞争、降频、过重算法或其他原因晚于计划执行。

6.3 一次 write 如何拆成“能写多少”和“睡到何时”

AudioStreamInternal::processData() 是外层循环：调用不阻塞的 processDataNow()，推进已处理 frame 和应用 buffer 指针；必要时根据返回的绝对唤醒时间睡眠，直到全部完成、出错或超时。

若 timeoutNanoseconds == 0，它完成当前可完成的部分就返回；不能假设一次非阻塞 write 一定提交全部数据。callback 内部的 write 也检查是否提交完整，部分写入会触发错误处理。

processDataNow() 先消费消息，再判断时钟是否尚处 STARTING。尚未收到有效时间戳时，它返回“当前没有写入、稍后重试”。建立时间锚点以后，才知道应当从正在推进的 MMAP 缓冲哪里开始。

6.4 谁推进硬件侧读指针：free-running 判定

普通软件共享 FIFO 可以让生产者推进 write counter、消费者推进 read counter。硬件 DMA/DSP 不会替客户端更新这份软件计数器，因此客户端要自己估计它。

AudioEndpoint::configureDataQueue() 根据远端计数器地址判断是不是 free-running：播放看远端 read counter，录音看远端 write counter；地址为空，意味着需要用本地计数器和时间模型模拟远端推进。

这是理解共享路径的关键：MMAP 家族客户端不一定直接面对 free-running 硬件。 共享应用面对服务端软件 FIFO，可以读取服务推进的计数器；服务内部的 MMAP 流才直接面对硬件时间模型。共享客户端也会使用服务时间信息安排供数，但不能把两个计数域当成同一个位置。

6.5 独占输出：预测消费位置，再把数据写到前面

把软件逻辑位置记为 W（累计写入）和 R（累计读取或估计消费），则 W - R 是逻辑队列深度。物理数组下标则通常由累计位置对容量取模得到；逻辑位置应继续增长，不能在数组回绕时一起归零，否则无法区分第几圈。

对独占播放，R > W 意味着设备已经越过供数前沿。这里的 XRun 统计来自软件对这种条件的检测，不能直接等同于“硬件中断上报了几个 underrun”，也不能由计数精确推出丢了多少 sample。

writeNowWithConversion() 从环形队列取得一段或两段可写区域，再让 FlowGraph 做转换并写入；回绕时之所以是两段，是因为物理数组末尾与开头在地址上不连续。最后按设备 frame 数推进 endpoint 写指针，按应用 frame 数返回处理量。发生重采样时，两种 frame 数可能不同。

6.6 写完以后为什么不立刻再回调

持续无节制地产生 PCM 会把缓冲填满，声音变得稳定却越来越迟。当前实现用有效 buffer size 控制排队深度。当队列达到相应目标时，计算需要等到硬件消费多少 frame，才值得再次供数。

STARTED 分支中的关键关系是：

targetReadPosition = writeCounter - bestBufferSize，然后用 convertPositionToTime(targetReadPosition) 计算唤醒时间。

bestBufferSize 结合应用目标大小和 endpoint 剩余安全空间取值；外层还会应用最小睡眠时间、软件远端的附加等待和超时约束。它不是固定 sleep(4ms) 的永久循环。队列位置、时间模型和流状态都会影响下一次等待。

假设采样率 48 kHz、每 burst 192 frame、当前 W=1920、估计 R=1536，那么已有 384 frame，即约 8 ms 的该级音频数据。设备继续读取一个 burst 后，R 变为 1728，若应用及时补入 192 frame，队列又回到相近深度。若应用晚了数个 burst，队列可能耗尽；若总是额外预存很多 burst，则排队时间会上升。

这个例子只展示单个队列的节奏；不能把 8 ms 直接写成真实扬声器延迟，也不能把软件估计的 R 当成声学测量。

6.7 暂停、停止、清空与关闭是不同动作

电子琴按键松开不一定要 stop 音频流：通常先让包络收尾，在持续回调中生成静音或其他音符。只有业务确实不再需要音频时才改变流生命周期，这样可以避免每次按键都承担冷启动。

操作 输出主线中的语义 当前 Internal 实现的相关动作
pause 尽快暂停传输 停止回调、停止时钟模型，进入 PAUSING，再请求服务暂停
stop 停止传输并完成相应收尾 停止回调，准备输出缓冲收尾，再进入 STOPPING 并请求服务停止
flush 丢弃待处理的数据 进入 FLUSHING；收到 FLUSHED 后对齐客户端与服务端位置
close 释放流与其资源 结束相关活动、解除服务端关系、释放映射和对象；旧 handle 不再使用

pause/flush 不是所有方向都支持的通用操作，具体可用状态还需遵循 API 校验。不能在任意状态随意 flush，也不能把 DISCONNECTED 当作 PAUSED。

这里值得特别看 AudioStreamInternalPlay::prepareBuffersForStop()：free-running 输出会根据模型等待已写数据被设备消费，擦除空闲区域并保留一个 burst 安全边界，最后清零缓冲，避免设备继续运行或回绕时重放旧内容。等待消费的部分有 200 ms 上限；若已有有效呈现时间戳，还会估算下游到 DAC 的时间并以 30 ms 为上限等待。它们是该提交收尾实现的限值，不是平台承诺的固定延迟。

共享流不走这套直接面对 DSP 的清理逻辑，而由共享 mixer 的停止/暂停分支消耗已有 FIFO 数据。可见“调用 stop 后立刻绝对静音”“pause 后重新 start 必定保留所有未播数据”都不是可以跨后端随意套用的假设。实际控制语义与听感仍需结合缓冲、服务状态和设备测量。

7. 时间戳与时钟模型：NOIRQ 路径的核心

7.1 时间戳是一对值，不是“收到消息的时间”

一个有效音频时间戳包含 frame position 和对应的时间，例如“位置 P 在时刻 T 被设备推进到”。消息到达客户端的时刻可能更晚。如果错误地用 Binder/队列接收时间替换 T，线程调度延迟就会被误认为设备运行变慢。

服务端 MMAP endpoint 通过 getMmapPosition() 得到位置与时间；把底层 32 位位置扩展成累计 64 位位置后，向流的消息通道发送。停止后硬件位置可能复位，服务还需要修正累计计数与环形缓冲对齐，不能天真地把下一次 0 看成时间倒流。

AAudioServiceStreamBase::run() 中的命令线程同时安排周期性时间戳发送。周期来自 timestamp scheduler，不是应用每写一个 burst 就同步问 HAL 一次位置。

7.2 SERVICE 与 HARDWARE 时间戳不能混读

客户端 onTimestampService() 把服务时间戳交给时钟模型；onTimestampHardware() 保存到原子时间戳对象，供呈现/采集位置查询等使用。

对独占流，getHardwareTimestamp_l() 优先尝试 external position；失败后，可能使用已保存的流时间戳加上硬件时间偏移估计。因此 “API 返回了 timestamp”仍不等于拿到了理想的 DAC 声学时刻。HAL 的实现与可用精度决定它能支持多强的测量结论。

对共享流，还需处理客户端 FIFO frame 域与底层 MMAP frame 域的偏移。混音线程记录当前 mmapFramesWritten - clientFramesRead，以便把底层时间关联回客户端流。若直接拿两个域的位置相减，得到的“延迟”可能根本没有物理意义。

7.3 IsochronousClockModel 怎样从时间预测位置

先用连续模型理解：如果位置 P0 对应时刻 T0，采样率为 Fs，那么经过 Δt 后大致推进 Fs × Δt frame；反过来，要推进 ΔP frame，大致需要 ΔP / Fs 秒。

实际设备通常以 burst 为粒度更新位置，所以代码不只是做一次直线插值，还会按 burst 边界取整。

反向的 convertPositionToTime() 把目标位置向下一个 burst 边界取整后再求时间。这样得到的是与设备批次推进相匹配的调度点，而非“每个采样都有一个独立中断”。

7.4 模型自身也有状态机

模型的 STOPPED / STARTING / SYNCING / RUNNING 与 AAudioStream 的 OPEN / STARTING / STARTED 是两套状态。流已开始，不代表时间估计已经稳定。

模型阶段 触发与处理 对读写的意义
STOPPED 暂停模型推进，保留锚点 不继续按运行中的时钟外推
STARTING 等第一个有效时间戳并建立位置/时间锚点 客户端数据操作可能先等待
SYNCING 处理初始快速推进，必要时更新锚点 冷启动阶段不宜当作稳定延迟样本
RUNNING 根据时间戳相对预期的早晚修正窗口 支撑持续估计、唤醒与抖动余量

RUNNING 中，较早的时间戳会更新锚点；一般迟到可小幅漂移调整；连续非常迟的时间戳可能触发窗口跳转，并增加 DSP stall 相关计数。这里是从时间观察推断状态的实现，不应把每一次“late”直接定性为 CPU 调度故障或硬件坏了。

固定的名义采样率也不意味着永远无需重新校准。硬件时钟误差、DSP 停顿、时间戳上报方式和线程调度，都可能让预测与新样本出现偏差。

7.5 播放怕写晚，采集怕读早

播放时，要在设备可能读取该区域之前完成写入。若把一个迟到的上报简单当成“硬件还没读”，客户端可能覆盖设备正在使用的数据或来不及供数。

采集时，硬件/DSP 是生产者，应用必须等到数据确实写好。AudioStreamInternalCapture::processDataNow() 使用 convertLatestTimeToPosition() 估计安全可读前沿，而不是直接照搬播放的 convertTimeToPosition()。

后者考虑模型的 late offset：由观测到的迟到量和额外安全量形成。可读位置更保守，就能降低读到尚未完成数据的风险，但代价是多一点等待。输出提前写、输入稍晚读，都是为了避开硬件与软件对同一区域的访问冲突。

采集方向若积压数据超过环形容量，就发生 overrun：硬件继续写，旧数据可能已被覆盖。该方向的软件检测是 fullFramesAvailable > capacity；播放则关注 fullFramesAvailable < 0。二者都被归入 XRun，但原因与数据损失方式不同。

8. 缓冲调优：四个数不能混成一个

8.1 capacity、size、burst、callback 的区别

数量 含义 是否直接等于延迟
Buffer capacity 本次流可用的缓冲容量上限 否，容量不等于当前占用
Buffer size 客户端用于调节队列深度/供数节奏的有效大小 只能提示相应队列的目标音频时长
Frames per burst 流向应用报告的处理批次粒度 只能换算该批次时长
Frames per callback 应用一次回调被要求处理的 frame 数 影响计算和调用节奏，但不是总排队长度

应用请求的 capacity 是建流协商输入，底层可以返回不同值。调 setBufferSizeInFrames() 不意味着重新分配硬件 DMA 区，也不意味着改变驱动 period。

当前 configureDataInformation() 会根据 AudioSystem::getAAudioHardwareBurstMinUsec() 将过小的硬件 burst 成倍放大，以免唤醒过密；再按应用采样率与设备采样率换算 API 报告的 burst。若 callback 大小未指定，内部 MMAP 实现默认取报告的 burst，但显式配置、Legacy 实现和重采样都会影响实际行为。应用始终按 callback 参数 numFrames 工作。

8.2 当前 setBufferSize 的真实作用

AudioStreamInternal::setBufferSize() 会限制请求不超过 capacity - burst，按 burst 换算，至少保留一个 burst；使用采样率转换时还会施加额外最小 burst 数约束。它把 endpoint 允许写入的范围设得较大，而把 mBufferSizeInFrames / mDeviceBufferSizeInFrames 留作常态供数深度目标。

这样做的效果是：有数据时可以适当多写以降低毛刺概率，但正常唤醒节奏仍按应用目标深度控制。有效 size 不是一堵绝对禁止写过的内存墙。

此提交还有一个容易影响调试的小细节：该方法最终返回 adjustedFrames，成员保存的却是按 burst 处理后的 numBursts * getFramesPerBurst()。因此不要只打印 setter 返回值就结束记录；还要读取 AAudioStream_getBufferSizeInFrames()。这里是本地实现的具体行为，不推广成所有 Android 版本的 API 契约。

8.3 从两个 burst 开始，是实验起点，不是平台定律

对于支持低延迟的输出，可以把约两个 burst 作为初始测试目标，观察持续负载下 XRun 与回调耗时，再按 burst 增减。实际设定必须服从返回结果、容量和设备约束。默认值也不必已经是两个 burst：当前 Internal 初始化先设为容量的一半；共享服务底层流另有 mixer burst count 的配置与默认逻辑。

仍以 48 kHz、192 frame 为例：

  • 192 frame 对应 4 ms；384 frame 对应 8 ms；768 frame 对应 16 ms。
  • 384 frame 的目标队列可以提供比 192 frame 更多的供数余量，但也可能让新生成的声音多等待。
  • 如果算法一次处理耗时 6 ms，而每 4 ms 就需要一批数据，仅靠“优先级更高”不能补足持续的计算吞吐缺口。
  • 如果平均计算只需 0.5 ms，却偶发等待锁 12 ms，平均值仍很好看，但小缓冲会暴露长尾停顿。

应同时看耗时分布、最大连续晚到、调度间隙与 XRun 增量，不要只看平均 CPU 占用。目标是在可接受的延迟内找到稳定余量，而不是把 size 设到 API 允许的最小值就宣布成功。

8.4 重采样为什么要单独算账

应用可能按 44.1 kHz 生成数据，设备则以 48 kHz 工作。当前 Internal 实现区分应用参数与设备参数，通过 FlowGraph 处理所需转换，所以不能再用“采样率不一致必然无法 MMAP”概括这个提交。

但不一致并非免费：转换增加计算与内部状态，读写两端的 frame 计数不同，buffer size 换算还要处理取整和最小余量。排查时要同时记录 app sample rate 与 hardware/device sample rate，不能把 441 frame 与设备的 480 frame 当成时长不同；它们在相应采样率下都可以代表 10 ms。

电子琴若没有固定文件采样率的约束，可以让系统协商参数后按实际采样率合成。若业务必须固定采样率，则明确承担转换成本，并在该组合下重新测量。

9. 共享、Legacy 与录音：三种分支怎样改变结论

9.1 MMAP SHARED 不是“多应用同时写同一 DMA 区”

多个应用若直接往同一硬件区域任意写入，会互相覆盖；共享路径通过服务端汇合解决这个问题。

AAudioServiceEndpointShared::open() 创建服务内部的流时，把 sharing mode 设成 EXCLUSIVE，并设置 sharingModeMatchRequired=true。这个“独占”属于服务内部：服务是底层 MMAP 区的单一软件使用者，应用则分别连接到它管理的 FIFO。若底层也允许退 SHARED，就会形成“共享 endpoint 为自己再创建共享 endpoint”的递归，所以必须严格匹配。

共享输出运行时，AAudioServiceEndpointPlay::callbackLoop() 每轮先清空混音输出，再遍历活跃的客户端流，取得各自 FIFO，建立 frame 位置偏移并混音。最后经服务内部 AudioStreamInternalPlay::write() 写入一个 burst，并由这个阻塞式写入约束共享线程节奏。

混音器没有为每个应用单独同步调用硬件 write；硬件消费的是合成后的一份输出。每个客户端自己的 FlowGraph 可负责必要的格式/采样率转换，共享服务的混音输入则要求匹配的 float 数据。

9.2 某个共享应用来不及供数，会不会拖住全部应用

AAudioMixer::mix() 默认按一个 burst 推进消费位置。某路数据不够时，能取得多少就混多少；混音输出预先清零，该路缺失部分不会凭空产生样本。正常运行允许 underflow 时，读指针仍按期望批次推进，避免该客户端的时间轴因每次缺数不断漂移。

共享线程因此可以继续服务其他客户端，而不是无限等待一个应用补齐。对应流已经开始供数后，若实际混入量不足一个 burst，服务增加该流 XRun，再通过事件通知客户端。

不过，“不等待某个应用补齐”不代表共享路径没有任何锁或调度风险。该循环本身有流列表与 FIFO 生命周期保护；共享线程或底层 MMAP 流一旦受阻，仍可能影响多个客户端。排查时要区分“单个客户端缺数”和“公共下游不及时”。

9.3 Legacy 回退后仍可能低延迟

AudioStreamTrack::open() 对 LOW_LATENCY 请求设置 FAST；在没有 session 且 usage 是 GAME/MEDIA 时，还会请求 RAW。配置了数据回调则使用 TRANSFER_CALLBACK，否则使用 TRANSFER_SYNC。本地代码明确指出同步传输不允许 FAST track。

打开后再检查 AudioTrack 实际 flags：只有实际拿到 FAST，才把 performance mode 报为 LOW_LATENCY；Legacy sharing mode 则设为 SHARED。

所以，下面几种观察都可能成立：

观察结果 正确解释
isMMapUsed=false，performance=LOW_LATENCY 可能是 Legacy FAST，不能说低延迟请求完全失败
isMMapUsed=true，sharing=SHARED MMAP 共享路径，不是普通 AudioTrack 共享混音的同义词
请求 LOW_LATENCY，actual=NONE 后端没有实现所请求的低延迟模式，应继续看 flags、参数与资源
请求 EXCLUSIVE，actual=SHARED 可能在独占策略处理或服务端建流时降级，也可能已经 Legacy 回退

这也是为何低延迟应用优先采用数据回调：它不仅方便库控制周期，还会影响 Legacy 后端是否具备 FAST 的传输条件。对于回退兼容性，callback 与普通阻塞 write 不能只当作两种语法风格。

9.4 录音的主干相似，风险方向相反

独占采集由硬件向 MMAP 区写入，客户端按安全位置读取，再转换为应用要求的格式，调用输入 callback。共享采集则由服务内部 AudioStreamInternalCapture 读取一个 burst 到分发缓冲，遍历运行中的客户端，把数据分发到各自 FIFO。

因此共享输入的核心是分发，不是把多个应用“混音成麦克风”。AAudioServiceEndpointCapture::callbackLoop() 与共享输出循环的顺序正好不同：先从公共源读，再写给客户端。

录音权限、隐私限制、input preset、设备选择和静音状态仍受系统约束。MMAP 不绕过 RECORD_AUDIO 或系统采集策略。对于实时监听，低延迟输入和低延迟输出必须分别确认；拿到一个好的输出流，不能证明麦克风输入同样走 MMAP。

全双工还要处理输入/输出时钟可能不完全一致：长期看即使名义采样率都为 48 kHz，两端速度也可能有差异。应用通常需要有界的中间队列、输入不足时的补零策略，以及必要的速率匹配；不要在输出 callback 里无限阻塞等待输入“凑齐”，否则把采集停顿变成播放 underrun。

10. 把实现放回电子琴场景

10.1 一次正常的打开与持续合成

为了让路径和业务对应起来，可以按以下过程设计电子琴音频引擎：

  1. 在控制线程创建 Builder，请求 OUTPUT、LOW_LATENCY、EXCLUSIVE，配置数据与错误回调；没有业务必要时不强制采样率，也不申请 session。
  2. open 成功后读取实际参数；根据实际采样率建立振荡器、包络和滤波器状态；预分配所有回调所需内存。
  3. 记录 burst、capacity、实际 size；在允许范围内选择初始供数深度。
  4. requestStart 后，回调按 numFrames 生成连续 PCM。UI 通过有界消息或经过审查的 lock-free 数据结构更新音符参数。
  5. 控制线程采集统计，不在音频回调里持续打印日志或写文件。
  6. 停止时协调线程生命周期，等待回调不再使用对象后关闭流并释放上下文。

下面是应用侧示意代码，只展示配置与参数读取顺序，不是平台源码，也不是完整可运行 App。renderCallback、errorCallback 与 engine 由应用实现；错误回调的职责见 10.3。

真实工程要为 prepare() 失败和不满足业务要求的 actual 参数补上关闭路径；音频数据类型必须与实际格式一致。初始化函数成功后再由控制线程发起 start，并检查结果。此处故意把 open 与 start 分开，使上下文在首次回调之前准备完毕。

10.2 回调的工作应该有明确上限

回调可以做确定成本的合成、包络、滤波、短块处理，以及有界消息读取；应避免动态分配、文件/网络 I/O、睡眠、长时间锁等待和不可预测的跨线程同步。一个看似简单的“取 UI 最新状态”若需要等 UI 持有的互斥锁，也会把 UI 卡顿传入音频线程。

数据共享必须满足 C++ 内存模型，不能为了避免锁而使用有数据竞争的普通变量。多字段参数需要一致快照，消息队列应有容量与满队列策略；单个 atomic<float> 是否 lock-free 也需按目标 ABI 检查。这里追求的是执行成本可界定，不是把所有对象名字都改成 atomic。

NDK AAudio 指南对低延迟 callback 和回调中的限制给出了应用侧说明；实际禁止在回调中调用的 AAudio 操作还应对照目标 NDK 头文件。尤其不要在数据或错误回调里直接 close 正在回调的流。

10.3 第二个应用竞争：独占流可能被撤销

AAudioEndpointManager::openExclusiveEndpoint() 不只实现“资源忙就拒绝”。在找到已有匹配独占 endpoint、启用了 stealing、原 endpoint 不是共享服务专用且新请求不要求严格匹配等条件下，可以释放旧流资源，为共享使用腾出空间。

AAudioService::openStream() 的递归锁用于约束这个过程：避免旧应用在新应用切到共享之前抢先重新拿回独占。对应 tracker 还会限制竞争进程继续申请独占，减少双方重开时反复碰撞。

这不意味着“任意第二个 App 一播放就抢走所有独占流”。匹配的 endpoint、配置和资源条件都重要。但它证明 EXCLUSIVE 不是永久租约，即使 open 成功，start 前后也可能失去资源。

错误回调收到 DISCONNECTED 后，合理的处理是把重建请求交给独立控制线程：

标记旧流不可继续使用 → 停止业务向旧流提交操作 → 按 API 生命周期协调关闭 → 重新建 Builder/open → 读取新 actual 配置 → 重配算法与缓冲 → start。

错误回调本身不执行可能死锁的 stop/close 等操作。上下文也不能在通知控制线程后立刻销毁，因为回调可能尚未返回。应通过明确的所有权、流代次和线程同步避免旧流事件误伤新流。

10.4 扬声器切到耳机：不要沿用上一次的参数缓存

AAudioServiceEndpointMMAP::onRoutingChanged() 发现已连接设备发生变化时，会将 endpoint 标记为不再可连接，并异步释放已注册流；onTearDown() 也把拆除转移到独立线程，避免在控制回调链上形成死锁。

客户端处理 DISCONNECTED 事件时，输出方向还会擦除数据内存，防止硬件循环播放旧数据形成持续杂音。之后旧流只能按生命周期释放，应用需要重新打开。

新设备可能有不同采样率、声道、burst、容量和 MMAP 能力。此前“48 kHz、192 frame、EXCLUSIVE”的配置不能直接复用。切到某种蓝牙路由时，即使应用端供数很及时，传输、编码和耳机缓冲仍可能主导最终延迟，不能只靠缩小 AAudio buffer 解决。

11.2 API 可用性必须按目标系统判断

本地 AAudio.h 将 AAudioStream_isMMapUsed()、AAudio_setMMapPolicy()、平台 MMAP 策略查询标为 __INTRODUCED_IN(36)。因此，本文源码中“函数存在”不代表所有 API 26+ 设备上的应用都能直接静态链接这些公开接口。

  • 使用 API 36 及匹配 NDK 时，可按运行时可用性使用公开 MMAP 查询。
  • 兼容较低版本时，使用该版本可用的诊断方法、系统 dump 与日志；不要把内部/测试符号未经说明当作稳定公共 API。
  • 进程级 NEVER/AUTO/ALWAYS 对照实验只在接口受支持时做，影响后续 open；不要假设能改造已经打开的流。

同理，硬件采样率/格式等较新 getter 应按实际 NDK 与运行系统做 API guard。本例初始化只使用基础接口；较新的诊断接口不应无条件塞进旧版兼容代码。

11.5 用 trace 区分“算得慢”和“没被调度”

当前源码包含 aaProc、aaWrNow、aaRdy、aaSlpNs、aaUnderRuns，共享 mixer 中包含 aaMix 和 aaMixRdy# 等 ATrace 点。录音对应 aaRdNow、aaRead、aaOverRuns。在允许采集的测试构建上，可用 Perfetto 配置音频 atrace 类别和调度事件，对齐应用回调的自定义 trace。

需要关注的是同一时间窗口中的因果关系：

  • 回调线程持续 Running 且执行过长，优先检查算法、数据规模与缓存行为。
  • 线程已经 Runnable，却很久没有被调度，检查 CPU 竞争、优先级与系统负载。
  • 线程阻塞在应用锁或 I/O，回到 callback 的工作边界，不能仅增大缓冲掩盖。
  • 应用按时完成，共享 mixer 或硬件位置却长时间不推进，再检查服务线程和 HAL 时间戳。
  • 缺数计数与 aaRdy 下探对应，可支持供数/排队不足的判断；仍需结合具体后端和 frame 域。

需要的调度事件和内核数据依构建权限而定，某个 trace 点没显示也可能是类别未启用。不能把没有采集到的区间画成“线程没有运行”。

11.6 时间戳估算与真实 loopback 各能证明什么

若已知一个待播放 frame 的逻辑位置 F，且 API 给出同一流、同一坐标系中的 (P, T)，可用 T + (F-P)/Fs 估算它的呈现时间。计算时还要统一纳秒/秒单位、时钟域与采样率，检查 timestamp 是否有效、是否跨越了重建/停止边界。

这种估算依赖 HAL timestamp 语义，不能消除 HAL 下游未知缓冲。不要跨 stream generation 复用时间锚点，也不要把 shared FIFO transfer timestamp 当作扬声器已经播放的位置。

要测端到端或往返延迟，应设计 loopback：输出已知脉冲/相关序列，通过物理连线或受控声学路径采集，再做相关性分析。测试报告至少说明路由、设备、采样率、连接方式、是否包含应用处理和声学传播，以及多次样本的分布。

电子琴触屏到出声则需要把输入触发时刻也放进同一测量方法，单纯音频 loopback 不含完整 UI 路径。蓝牙还要把编解码与传输缓冲算进测量范围；不能用扬声器上的结果替代耳机结果。

11.7 看到异常时的排查顺序

先问 open 是否成功，再问实际后端是什么；后端正确以后，核对 actual 参数与数据格式，确认 callback 在持续供数；然后看 XRun、队列与调度；最后用 timestamp/loopback 验证下游延迟。

这个顺序可以避免几类无效优化：Legacy 回退却一直调 MMAP offset；SHARED 的公共下游出问题却只缩某个应用的 FIFO；算法耗时已超过周期却只提高线程优先级；蓝牙固有延迟占主导却把输出 size 调到不稳定。

12. 分层复习：能解释到哪一层

12.1 L0：先记住全局关系

AAudio 把流接口与后端选择封装起来。MMAP 缩短 PCM 的软件传输路径，但控制仍由服务与策略系统管理。独占流由客户端库面对硬件共享区，共享流经 AAudioService 混音/分发。NOIRQ 依靠时间戳模型安排供数，低延迟依靠小而稳定的队列与及时执行共同成立。

12.2 L1：能够展开的主干

  • 选路：系统/进程策略 → LOW_LATENCY、PCM、session 条件 → Internal 尝试 → 服务端独占/共享 → 必要时 Legacy → 读取 actual。
  • 建链：服务 stream → endpoint → AudioFlinger/Policy → HAL MMAP 资源 → FD/description 返回 → 客户端映射与队列配置。
  • 播放：start 请求与事件 → 时钟锚点 → callback 产数 → 转换写入 → 预测硬件消费 → 按目标队列深度等待。
  • 共享：各应用 FIFO → AAudioMixer → 服务内部 MMAP 流；单路缺数不会无限阻塞所有应用。
  • 恢复：资源或路由改变 → DISCONNECTED → 控制线程关闭旧流 → 重开、重读参数、重配算法。
  • 验证：请求与 actual → dump 对象关联 → XRun/trace → 时间戳估算 → 需要时做端到端测量。

13. 自测：先预测，再展开答案

13.1 基础题

问题 1：open 成功，actual sharing mode 是 SHARED，能否判断已经回退 AudioTrack？

展开参考答案

不能。可能是 MMAP SHARED，也可能是 Legacy。先区分第 4 章的两层回退，再用受支持的 MMAP 查询、AAudioService endpoint 与 AudioFlinger 信息确认。sharing mode 只描述共享模式，不唯一标识后端。

问题 2：MMAP EXCLUSIVE 是否意味着 AudioFlinger、AudioPolicy、音量和路由管理都被绕过？

展开参考答案

不是。PCM 主路径绕过普通 mixer，但 AudioFlinger 仍通过 MmapThread 管理 HAL，AudioPolicy 仍参与选路，音量和断开事件仍能到达客户端。回看第 3、5 章，分别画数据、控制和消息三类关系。

问题 3：为什么 callback 收到的地址不能直接称为 DMA 地址？

展开参考答案

这版 Internal 输出先把 mCallbackBuffer 交给应用，再调用 write()，经 FlowGraph 处理后写到 endpoint。MMAP 减少中间通路，不保证 API 层零复制。回看 5.4 与 6.2。

问题 4：capacity=1920 frame、48 kHz，是否说明当前输出延迟是 40 ms？

展开参考答案

只能说容量可容纳 40 ms 的该采样率数据。实际占用和有效 size 可能更小，下游又可能有额外延迟。必须分别检查队列深度、时间戳和测量区间。回看 2.5 与第 8 章。

13.2 场景推理题

问题 5：设备支持 MMAP，但日志提示 FD 不可分享给应用。电子琴请求 EXCLUSIVE，应该预期什么？怎样验证？

展开参考答案

普通应用的独占建流会在共享能力检查处失败；若允许共享降级，服务可尝试用自身身份持有底层 MMAP，再向应用暴露共享 FIFO，因此仍可能成功使用 MMAP SHARED。检查 actual sharing、MMAP 标记和共享 endpoint 的内部流关系。若整个 MMAP 家族仍打不开，AUTO 才会允许 Builder 继续 Legacy。依据见 4.4、5.3、9.1。

问题 6：为了接效果申请了 session，发现 MMAP 消失。应先怀疑 CPU 性能不足吗？

展开参考答案

先看选路条件。此提交只要 session 不为 NONE，Builder 就关闭 MMAP 尝试；即使效果没有消耗明显 CPU，也会发生路径变化。保持其他变量不变做 session 对照实验，检查 actual 后端。性能分析应在确认后端后继续。依据见 4.2 与 11.4。

问题 7：输出回调平均耗时 0.5 ms，每 4 ms 需要一批数据，却偶尔有 12 ms 的锁等待。把 buffer 缩到一个 burst 会怎样？

展开参考答案

更可能暴露缺数：平均值不能覆盖长尾等待，队列余量也不足以承受长停顿。应先去掉不受控锁等待，再用 burst 阶梯与 trace 观察稳定余量；不能仅用高优先级替代并发设计。依据见 8.3、10.2、11.5。

问题 8：共享输出中，一个应用停止供数，其他应用是否必须等它？

展开参考答案

正常运行的共享 mixer 不无限等待单个应用补齐；混入可用部分，按批次推进该路时间轴，并在满足条件时统计缺数。其他应用仍可混入。但公共共享线程或下游 MMAP 故障会影响多路。要通过各流 XRun 与公共线程 trace 区分。依据见 9.2。

问题 9：耳机切换后，旧流返回 DISCONNECTED，但原来的采样率和 callback size 缓存还在。能直接对旧流再 start 吗？

展开参考答案

不能按普通暂停恢复处理。把重建交给控制线程，协调关闭旧流，重新 open 并读取 actual 参数，再重建依赖采样率与批次的算法状态。新路由可能改变后端与设备能力，旧参数不能当作契约。依据见 10.3–10.4。

问题 10：为什么输入不能直接复用输出的硬件位置预测方式？

展开参考答案

输出需要赶在硬件读取前写好；输入需要确认硬件已经写完后再读。采集用带 late offset 的保守位置估计，避免把 DSP 尚未完成的区域当成有效数据。两者的安全方向相反；出问题分别表现为 underrun 与 overrun 等情况。依据见 7.5。
