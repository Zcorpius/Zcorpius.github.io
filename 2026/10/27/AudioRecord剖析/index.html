AudioRecord 采集链路剖析

1. 概述

上一篇 AudioTrack 讲的是声音如何”出去”；这一篇讲声音如何”进来”。AudioRecord 是 Android 框架给应用的主麦克风采集入口：App 创建它、启动它、然后循环 read() 把 PCM 数据从框架拉走。看起来只是”半个 AudioTrack 反过来用”，但真正深入源码后会发现，采集链路与播放链路在三个维度上本质不同：

  • 方向反转了数据通路的生产者/消费者关系：播放时 App 是生产者（写共享内存）、AudioFlinger 是消费者；采集时 AudioFlinger（RecordThread）是生产者，App 是消费者。环形缓冲的 mFront/mRear 语义、overrun（对播放是 underrun）、futex 唤醒策略全部随之镜像；
  • 录音是隐私敏感操作，多出一整层”控制面”：RECORD_AUDIO 运行时权限、AppOps（用户随时可在隐私面板撤销单个 App 的麦克风）、并发采集仲裁（同一时刻谁能真采、谁被静音成全零数据）、sensor privacy 总开关——这些在 AudioTrack 的世界里几乎没有对应物。控制面的核心不在 AudioFlinger，而在 AudioPolicyService 的 updateUidStates_l()：它维护一张”活跃录音客户端”表，用 TOP/最近启动/隐私敏感/助手/无障碍/通话等一串谓词决定每个客户端是拿到真数据还是被”静音”（数据照常流动，只是内容被 memset 成 0）；
  • 创建即被审视：AudioRecord 构造函数会穿过 4 个进程/服务（App → audioserver 的 AudioFlinger + AudioPolicyService → system_server 的 AudioService/appops），设备选择、输入流复用与抢占、权限矩阵、按 source 挂预处理音效，全部发生在 new AudioRecord() 到 STATE_INITIALIZED 之间。

Note

本文代码基线为 2024~2025 年前后的 AOSP 主线形态（LineageOS 同源树：audioserver 侧已拆出 RecordTracks.h/PlaybackTracks.h、策略侧权限收敛到 PermissionEnum、audioserver_permissions flag 等）。不同版本类名与细节有差异，但”双进程生产者-消费者 + 策略层静音仲裁“的骨架是稳定的。

三句话总结分工：

  • App 进程的 AudioRecord（Java + native）：参数校验、共享内存的消费者、回调线程管理、以及一套完整的通道自愈逻辑（audioserver 死亡/重路由/被抢占后自动重建 IAudioRecord）；

  • AudioPolicyService（同在 audioserver）+ AudioService（system_server）：决定”谁能在哪个设备上采、采到的是真声还是静音、以及把这一切状态广播给关心的人”。

2. 核心概念与对象模型

2.1. 两层状态机：state × recordingState

Java 层 AudioRecord 有两个容易混淆的状态字段，分别回答”对象建好了没”和”正在采吗”：

STATE（生命周期） RECORDSTATE（运行态）
值 UNINITIALIZED / INITIALIZED STOPPED(1) / RECORDING(3)
迁移 构造成功 → INITIALIZED；release() → 回 UNINITIALIZED startRecording() / stop()
只读吗 release() 后可无限次读，恒 UNINITIALIZED getRecordingState() 加 mRecordingStateLock 读取

值 1/3 对齐 OpenSL ES 的 SL_RECORDSTATE_* 常量（Java 注释里明确写着 “matches SL_RECORDSTATE_STOPPED/RECORDING”）——这是 AudioRecord 从 OpenSL ES 时代继承的化石。另外要记住：RECORDSTATE 只是客户端本地状态，被并发策略静音（第 4 章）的录音照样处于 RECORDING。native 层对应的是 mStatus（set() 的返回值，一旦 NO_ERROR 不再变化）与 mActive（bool）；服务端另有 AudioRecordClient.active / RecordClientDescriptor.active 各一份。

注意一个不对称设计：RECORDSTATE_RECORDING 不代表”正在收到真声音”。被并发策略静音（第 4 章）的录音流同样处于 RECORDING，数据照常流动——只是每一帧都是 0。想知道自己是否被静音，得走 AudioRecordingMonitor 的回调（8.7 节）。

采集链路上有四个标识符，各自属于不同层：

2.6. 隐私标志：AUDIO_FLAG_CAPTURE_PRIVATE

privacy sensitive 是并发仲裁的一等公民（4.4 节的核心谓词之一）。来源有三，按优先级：

  2. 默认值（native set()）：不带 attributes 构造时，VOICE_COMMUNICATION 与 CAMCORDER 自动标记：
  1. Java AudioAttributes.Builder.setPrivacySensitive（SystemApi），同 flag 的另一入口。

语义：被标记的采集”独占麦克风”——它活跃期间，其他不满足豁免条件的采集（即使 TOP）会被静音；反过来它也会压制别人。这就是”打电话/拍视频时助手不能偷听”的实现基础。

六个关键设计点：

  1. 两级缓冲、一份重采样源。mRsmpInBuffer（线程级，P2 环形，容量按 HAL 格式）是唯一的 HAL 数据落地处；每条 track 有自己的 sink 环形缓冲（App 格式）。重采样只在 HAL 采样率 ≠ 线程采样率时于 converter 内部发生一次——多条不同采样率的 track 共享同一份线程缓冲（ResamplerBufferProvider 从线程缓冲按各自进度消费），HAL 数据绝不会被重采样两遍；
  2. sink metadata 动态下发。每轮 threadLoop 把活跃 track 的 (source, channel_mask, tags) 列表经 updateMetadata_l() → mInput->stream->updateSinkMetadata() 推给 HAL——支持多路采集的 HAL（如麦克风阵列 DSP）据此决定各 stream 的波束/路由。这就是”软件多客户端复用一条 HAL 流”之外，”硬件多流”形态的协议基础：
  1. “跟最快的客户走”。源码注释（threadLoop 第④段上方）直白：“Read from HAL to keep up with fastest client if multiple active tracks, not slowest one. Only the client(s) that are too slow will overrun.”——HAL 读节拍只保证最快消费者不掉线，慢客户的 overrun 是它自己的责任（6.6）；
  2. 静音在交付前最后一刻执行（memset），效果链、转换、时间戳全部照常——被静音的流从 HAL 到 track 的整条链路都在跑，只有内容归零。这让”解除静音”是零成本的（改个 bool）；
  3. overrun 的三处检测：sink 满（getNextBuffer 返回 0 帧时 RecordTrack::getNextBuffer 置 CBLK_OVERRUN）、线程缓冲追不上（ResamplerBufferProvider::sync 的 filled>容量分支）、pipe 溢出（fast 路径 OVERRUN 重试）；
  4. standby 精细管理：无活跃 track → HAL standby + 释放 wakelock + 线程睡眠；全部 PAUSING → standby。麦克风是高功耗器件（尤其 DSP 链），空闲即断电。

7. 通道自愈：restoreRecord_l 与四类失效

采集链路是长生命周期对象（一次录音几十分钟很常见），期间任何一环失效都必须自愈，否则 App 只能崩溃重来。失效的统一信号是 cblk 里的 CBLK_INVALID 位；自愈的统一入口是 AudioRecord::restoreRecord_l()。

7.2. restoreRecord_l：重建的完整流程

四个要点：

  1. ++mSequence 代际号机制。obtainBuffer 把当次代际写进 Buffer::sequence，releaseBuffer 发现 sequence 不匹配就丢弃（”This Buffer came from a different IAudioRecord instance, so ignore the releaseBuffer”）——防止 App 拿着旧通道的指针操作新通道的缓冲。processAudioBuffer 对比 mObservedSequence != mSequence 时回调 onNewIAudioRecord() 通知上层（如 AAudio 重建其内部状态）；
  2. createRecord_l(position) 的 epoch 参数。新 proxy 的位置基准从”旧通道停止时的位置”续起，配合 mFramesReadServerOffset（server 侧新计数从 0 开始，offset 补上旧世界的总数），getTimestamp/getPosition 在 App 视角无缝连续。数据本身无法无缝（重建期间必然丢一段），但”表”是无缝的；
  3. 恢复即重新 start（SYNC_EVENT_SAME）。若并发/权限环境已变，start 会按新环境重新仲裁（可能直接被静音）。restored 后 mReqFrameCount 只增不减（”don’t let the requested frameCount decrease. This can confuse clients that cache frameCount()”，createRecord_l 尾部）；
  4. 压缩流（direct）不恢复。obtainBuffer 的 restore 分支里：if (!audio_is_linear_pcm(mFormat)) { tryCounter = 0; }——压缩流的上下文（编码器状态）不可重建，直接把 DEAD_OBJECT 上抛给 App。

7.3. 三处调用时机

读线程与回调线程不会同时 restore（都持 mLock；obtainBuffer 的原子性由 mSequence == oldSequence 二次确认保证）。第 5 处在 setInputDevice 活跃分支：先 stop + 置 INVALID，等下一轮 obtainBuffer/start 自然走 restore——“拆管道”与”建管道”解耦，中间态永远一致。

7.4. release 与析构

stopAndJoinCallbacks 的顺序是刻意的：stop()（打断阻塞中的 obtainBuffer）→ requestExit → mProxy->interrupt()（二次保险）→ requestExitAndWait()（join）。Java 层 release() 更早一步：先 stop()、注销捕获策略（playback capture 场景的 AudioPolicy）、native_release()（清空 Java 对象持有的两个 sp 字段——native 对象引用归零，触发析构链）→ mState = STATE_UNINITIALIZED。

服务端对称：RecordHandle 析构（binder 死亡或客户端引用清零）→ stop_nonvirtual() + mRecordTrack->destroy() → destroyTrack_l → releaseInput（策略档案注销）→（无人复用时）closeInput（HAL 关流、线程退出）。整条链任何一环崩坏，下一环都能兜底——采集资源没有单点依赖。

8.1. 显式路由：setPreferredDevice

换设备的本质仍是”拆了重建”：活跃时 stop+INVALID（下一轮 obtainBuffer 自愈到新设备）；空闲时立即重建（体验更好——start 前路由已就绪）。getRoutedDevices() 的结果只在活跃时有意义（updateRoutedDeviceIds_l 对 inactive 直接返回旧值），dumpsys 排查”为什么还在用旧麦克风”时先确认 track 是否 active。

10.2. 设计要点回顾

  1. 一套共享内存，两种方向。AudioTrack/AudioRecord 复用同一个 audio_track_cblk_t 与 proxy 骨架，靠 mIsOut 镜像掉 producer/consumer 角色——采集侧的三不对称（server 写 client 读、server 永不阻塞、每次 release 都唤醒）是理解全部细节的钥匙；
  2. “拒绝”分层沉淀为”静音”。硬失败（权限/特权/source 非法）留在创建与启动；运行期的并发冲突一律不拆流、只静音——数据面保持物理连续（帧数、时间戳、效果链全部正常），控制面只改一个 bool。这让 UI 指示、App 感知（回调）、解除静音的成本都最小化；
  3. 仲裁与执行分离。谁被静音由 AudioPolicyService 的 updateUidStates_l 纯函数式重算（全量扫描活跃表），执行下沉到 RecordThread 交付点 memset——决策可审计（注释即规格），执行零延迟；
  4. 恢复是常态路径。CBLK_INVALID + mSequence 代际 + restoreRecord_l 构成自愈协议：重路由、抢占、换设备、audioserver 崩溃四种失效共享一条重建路径，且”表”（位置/时间戳）无缝、”数”（音频内容）尽力；
  5. 两级缓冲换多路复用。线程级 mRsmpInBuffer 保证 HAL 数据只采一次、重采样只做一次；track 级 sink 让 N 个异构格式客户端共享一条 HAL 流。”跟最快的客户走 + 慢者 overrun 追新”明确了资源倾斜方向；
  6. ID 体系即职责边界。sessionId（效果域）/ portId（策略域）/ ioHandle（物理域）/ riid（观测域）四个 ID 各自由不同服务分配、生命周期各异——跨 dump 对齐这四个 ID 是排查采集问题的基本功；
  7. 状态上报双通道。高层客户端的 START/STOP 由客户端自报（recorderEvent，及时且抗 audioserver 重启），设备/格式/静音 UPDATE 由 audioserver 上报，RecordingActivityMonitor 以 riid 合并去重——每个通道都在对方失效时提供兜底，audioserver 崩溃不会让隐私指示灯失控。

10.4. 源码彩蛋：两个真实的代码瑕疵

对标 CarAudio 篇的传统，梳理源码时也挖到两个 AOSP 自身的小问题。它们同样不是设计意图、触发条件同样很窄，但作为”读源码要带着怀疑”的注脚很合适。

10.4.1. JNI 的 getRoutedDeviceIds：一次 i++ 被花掉了两次

AudioRecord.getRoutedDevices()（flagged 新 API）的 JNI 实现：

values[i++] 的后缀自增叠加循环头的 i++，实际行为（C++17 起赋值表达式右侧先于左侧求值，良定义）：values[0]=dev[0]，values[2]=dev[2]，values[4]=dev[4]……——偶数槽填了正确值，奇数槽保持 GetIntArrayElements 返回内存的未初始化内容，dev[1]、dev[3] 被跳过。Java 侧 getRoutedDevicesInternal 会把这些垃圾 id 逐一送进 AudioManager.getDeviceForPortId（查不到的返回 null 被丢弃）。

更耐人寻味的是对照：android_media_AudioTrack.cpp:1206 的 android_media_AudioTrack_getRoutedDeviceIds 一字不差地带着同一个 values[i++]——这不是 AudioRecord 单方面抄错了 AudioTrack 的正确写法，而是两个文件共享同一个 bug（大概率同源拷贝时只拷对了形状没拷对语义；C++14 及之前这行还是 UB，两处一起升级成”良定义地错”）。修复都只需把 values[i++] 改成 values[i]。

现网难见的原因：getRoutedDevice() 只取列表第一个元素——单输入/输出设备（绝大多数手机）时 values[0]=dev[0] 恰好正确；只有多设备并发路由（真正需要 getRoutedDevices() 复数 API 的场景）才会暴露。

10.4.2. RecordThread::stop：ALOGW_IF 把格式串当成了条件

ALOGW_IF(cond, fmt, ...) 的第一个参数应该是条件，这里传的是字符串字面量——退化成非空指针恒为真。于是这条”非同步 stop”警告：条件恒真（本应只在异常路径出现）、真正的格式串变成了第二个参数 __func__（即 "stop"）、三个参数全部被丢弃。实际效果：任何走到这条路径的 stop 都只打一行内容为 stop 的 WARN，排查时看不到 track id 和 state。应为 ALOGW(...)。典型的宏签名相近导致的笔误——也提醒我们：日志宏的参数错位编译器不会报错，”日志打了但信息不对”时先检查宏用没用对。

10.5. 本文边界与延伸

刻意没有展开的相邻主题：

  • AAudio：AAudioStream（输入方向）在 MMAP 模式直接走 MmapCaptureThread（零 binder 数据面、静音走 DSP setGain），STREAM 模式则完全包装本文的 native AudioRecord（setCallerName("aaudio")）——值得单独立一篇；
  • OpenSL ES：android_GenericPlayer 之外的 recorder 侧（sles_object → AudioRecord CALLBACK 模式的经典封装）；
  • audio_policy_engine 的 input 策略：source → device 的 XML 可配置化（与 CarAudio 篇的 engine 同一套机制）；
  • remote submix HAL（audio.r_submix 模块）：虚拟设备对的实现；
  • SoundTrigger：热词硬件检测全链路（与本篇只在 APM 交汇）；
  • audio mode 与录音的双向耦合细节：SetModeDeathHandler 栈、updateAudioModeHandlers 的宽限期与乐观激活（system_server 侧的另一半状态机）。
