1. 从一次录音出发：AudioRecord 究竟连接了什么

一个录音应用的核心代码通常只有三步：创建 AudioRecord、调用 startRecording()、循环 read()。但这三个动作解决的是不同问题：创建建立采集通道，启动申请并激活采集，读取消费已经交付到共享缓冲中的数据。 read() 并不是每调用一次，就跨 Binder 命令麦克风采集一次。

这一区分能够解释许多看似矛盾的现象：对象创建成功却没有数据；getRecordingState() 是 RECORDING，读到的却全是零；应用要求 16 kHz，而 AudioFlinger 的输入线程显示 48 kHz；换一个输入设备后，Java 对象没变，服务端的录音轨道却已经换过一代。

本文沿一个贯穿场景展开：录音应用 A 使用 MIC，要求 16 kHz、单声道、PCM16；假设策略为它选择了一个 48 kHz、双声道的 PCM 输入流。A 正常读取，随后遇到另一应用录音、读取线程变慢、切换输入设备，最后停止并释放。 这组设备参数是教学假设，不是某台手机的实测配置。若设备实际采用 16 kHz 单声道输入，不需要的转换分支就不会发生。

读完后，应能独立回答：

  • AudioRecord、RecordTrack、RecordThread、AudioPolicyService 各管什么？哪些在应用进程，哪些在 audioserver？
  • 一个 PCM 帧在哪里产生、转换、跨进程共享并拷贝到应用？谁推进读写位置，谁等待谁？
  • 最小缓冲、实际容量、读取块长和通知周期有什么区别？它们怎样影响延迟和丢帧？
  • 为什么“有权限”“启动成功”“没有被静音”“内容连续”是四个不同判断？
  • 如何用源码位置、录音回调和 dumpsys 区分路由错误、策略静音、overrun 与通道重建？

1.2. 先分清三个进程区域与两条通路

区域 主要对象 对一次录音承担的工作
应用进程 Java AudioRecord、JNI、native AudioRecord、AudioRecordClientProxy 校验参数、保存客户端状态、消费共享 PCM、回调与重建
audioserver：数据处理 AudioFlinger、RecordThread、RecordTrack、AudioRecordServerProxy 建立服务端轨道、持续获取输入、按轨道转换与交付
audioserver：策略 AudioPolicyService、AudioPolicyManager 验证使用资格、选择/复用输入、计算并发采集状态
system_server AudioService、RecordingActivityMonitor，以及权限/AppOps 相关服务 录音活动台账、配置通知、权限状态协作
HAL 与设备 输入流、驱动、麦克风或虚拟输入设备 获取硬件或虚拟音源数据，提供底层格式与时间信息

AudioPolicyManager 是 AudioPolicyService 使用的策略实现，不能把它算作第四个独立进程。AudioFlinger 和 AudioPolicyService 虽然通过服务接口协作，但通常同处 audioserver；看到 AudioSystem::... 或 Binder 接口名，不代表这一跳必然跨越进程。

两条通路的分工是：

  • 控制通路：创建、启动、停止、选设备、权限检查、状态通知。这些操作决定“通道是否存在、谁可以用、如何配置”。
  • PCM 数据通路：输入流持续产生数据，服务端填充共享缓冲，客户端在本地读取映射并拷贝到应用目标数组。Binder 不承载每一块 PCM。

共享内存避免的是“为每一块 PCM 发起 Binder 事务并传输其 payload”。普通路径仍有 HAL 侧搬运、格式转换和 read() 的内存拷贝，不能称为从麦克风到 Java 数组的端到端零拷贝。

2. 读源码之前：帧、缓冲、对象和状态

2.1. 采样点、帧、字节：先统一计量单位

PCM 的一个采样点，是一个声道在某个采样时刻的数值；一个 帧（frame） 包含该时刻所有声道的采样点。PCM16 表示每个采样点占 16 bit，即 2 byte，而不是“一帧永远占 2 byte”。

本文场景的两端单位如下：

数据所在位置 格式 每帧字节数 10 ms 的帧数 10 ms 的字节数
假设的 HAL 输入 48 kHz、双声道、PCM16 2 声道 × 2 byte = 4 480 1920
A 请求的录音数据 16 kHz、单声道、PCM16 1 声道 × 2 byte = 2 160 320

对普通线性 PCM：

因此，A 一次 read(short[], ..., 320) 请求的是 320 个 short 采样点；在单声道 PCM16 下恰好是 320 帧、640 byte、20 ms。如果改为双声道，同样 320 个 short 只有 160 帧。read(byte[]) 与 read(ByteBuffer) 的长度和返回值以字节计，read(short[])、read(float[]) 则以对应数组元素计。

主线普通 PCM 的一个输入帧不必对应一个输出帧。48 kHz 转到 16 kHz，长期平均是 3 个输入帧对应 1 个输出帧；滤波器状态、可用数据和处理分块会影响某一轮具体产出，不能逐次要求“HAL 本轮 480 帧，App 本轮恰好返回 160 帧”。

2.2. 几种“大小”分别约束什么

阅读 AudioRecord 时，最容易把几个都叫 buffer 的数混起来：

量 谁决定 它真正表示什么
HAL buffer / RecordThread::mFrameCount 输入流配置、HAL 一次底层处理的帧量及其节拍
getMinBufferSize() 客户端查询输入缓冲能力后换算 API 给出的最小缓冲建议，单位 byte；不是最终轨道容量
native mFrameCount / Java getBufferSizeInFrames() 服务端协商后回填 本条录音轨道的实际容量，单位为客户端帧
read() 的请求长度 应用 本次希望取走多少数据，不会自动改大共享环形缓冲
notificationFrameCount 客户端请求、服务端约束 native 数据回调的处理批次等内部通知参数；不是 Java 每次 read 的长度

容量、占用量和延迟也要分开。640 帧的 16 kHz 缓冲可容纳 40 ms 数据；若里面只有 160 帧等待消费，当前排队量只有约 10 ms。反过来，即使共享缓冲很大，应用每次请求 1600 帧的阻塞读取，仍可能为了凑齐 100 ms 数据而引入较大的批次等待。

2.3. 一个应用录音对象，对应哪些服务端对象

应用中的 AudioRecord 表达一条逻辑录音需求。AudioFlinger 为它建立 RecordTrack，保存该客户端的格式、共享缓冲、状态与 portId；一条 RecordThread 管理一个输入流，并可以服务多条 RecordTrack。

这里的“一对多”是对象关系，不是继承：

A 与 B 是否实际被分配到同一条输入流，由策略、profile、资源上限和用途决定；不是因为它们都录麦克风就必然共享。共享输入也不等于两个应用都获准接收真实声音，后者属于第 7 章的并发策略。

对每一条普通 RecordTrack，两个代理映射同一个跨进程缓冲：

  • AudioRecordServerProxy 在 audioserver，为服务端取得可写区域、提交已写帧。
  • AudioRecordClientProxy 在应用进程，为客户端取得可读区域、归还已读帧。

proxy 是访问共享状态的本地对象，不是“每次调用都会走远程 Binder”的代理。真正的 Binder 控制对象是 IAudioRecord；服务端用 RecordHandle 适配 RecordTrack 的操作。

2.4. 四个 ID 与设备 ID：排障时不要串号

标识 主要生成或维护位置 用来关联什么
sessionId AudioFlinger 分配，或应用请求使用既有 session 录音的音效会话；部分历史共享协议也使用它
客户端 portId APM 在 getInputForAttr() 中分配 本次策略注册的录音 client，startInput/stopInput/setRecordSilenced 的定位键
ioHandle / native mInput AudioFlinger 打开输入时分配 输入流及对应 RecordThread，多个 portId 可归属同一个 input
riid AudioService 的 trackRecorder()，由 RecordingActivityTracker 持有 录音对象在系统录音活动台账中的身份，可跨 stop/start 使用
selectedDeviceId / routed device ID 音频端口与路由体系 输入设备端口；不是这条录音 client 的 portId

riid 不是每次按下录音按钮都必然重新分配。native 对象中的 tracker 可以跨多次 start/stop 复用；内部恢复也可继续使用它。相反，restoreRecord_l() 重新执行 getInputForAttr()，通常会获得新的客户端 portId。因此追踪长时间录音，不能只用一个 portId 假定整个生命周期不变。

ioHandle 也不等价于“物理麦克风编号”：REMOTE_SUBMIX 等虚拟输入同样有 input handle。读 dump 时先看字段属于 client、输入流还是 device，再做关联。

2.5. AudioSource 是用途声明，不是麦克风地址

audioSource 进入 AudioAttributes 的 capture preset，native 对应 audio_attributes_t.source。它会参与路由、权限、输入 flags 和预处理配置，但不会凭空创造设备能力。

source 值 应怎样理解
DEFAULT / MIC 0 / 1 默认/通用麦克风用途；APM 将 DEFAULT 规整为 MIC
VOICE_UPLINK / VOICE_DOWNLINK / VOICE_CALL 2 / 3 / 4 通话上行、下行、双向通话源，涉及系统权限和底层支持
CAMCORDER 5 面向视频录制的输入调校；有条件时与摄像方向相适配
VOICE_RECOGNITION 6 面向语音识别的调校；不能仅凭名字断言禁用了全部预处理
VOICE_COMMUNICATION 7 面向 VoIP 的调校，可利用可用的回声消除、增益等能力
REMOTE_SUBMIX 8 虚拟混音输入；需要结合 policy mix、地址和授权链理解
UNPROCESSED 9 请求尽量未经处理的数据；不支持时有回退，不保证所有 DSP 处理消失

常量的存在不代表普通应用都能使用它们。系统专用 source、隐藏 Builder 方法与 SDK 公共 API 要分开；权限细节见 7.1。路由到同一个麦克风，source 不同仍可能触发不同的预处理与并发规则。

VOICE_COMMUNICATION 和 CAMCORDER 默认 privacy sensitive。Java 的默认标志来自 AudioAttributes.Builder.build()；native 的 AudioRecord::set() 在未传 attributes 时也有对应默认逻辑。显式 Builder.setPrivacySensitive() 可在允许的 source 上覆盖默认值。它声明并发策略中的敏感性，不是应用拿到一把绕过所有特权规则的硬件独占锁。

2.6. 两层 Java 状态与服务端状态不能画成一个枚举

状态层 主要字段/枚举 回答的问题
Java 对象 STATE_UNINITIALIZED / STATE_INITIALIZED 对象是否已成功初始化，是否已 release
Java 录音 RECORDSTATE_STOPPED / RECORDSTATE_RECORDING 本地 API 是否进入录音状态

STATE_INITIALIZED 不代表已经 start；RECORDING 不代表没有被静音；silenced=false 也不能证明物理麦克风一定采到了有效声学信号。状态机解决的是控制问题，声音内容还要用数据与设备证据判断。

3. 创建：从 Builder 到共享内存连接

3.1. Java 校验与初始化：参数成功不等于系统建链成功

应用传入的核心参数是 source、sample rate、channel mask、encoding 和 buffer size。Java 先校验参数关系，JNI 再做类型与单位转换，native/服务端继续验证实际能力与权限。

传统构造器和 Builder 的失败表现不同：传统构造器可能返回一个 STATE_UNINITIALIZED 的对象；Builder 检查到这一状态后抛 UnsupportedOperationException。参数本身非法还可能在更早的位置抛异常，不能把所有失败都归结为“没给麦克风权限”。

“一帧请求”不等于实际分配一帧环形缓冲。它是把容量下限的决定交给底层，最终值会通过 createRecord 的响应回填。显式调用 setBufferSizeInBytes() 时，字节数必须与当前帧大小相容；设置更多容量是给消费者调度留余量，不会强制硬件以同样大小的块返回。

普通 Java 构造的关键终点是 native_setup()。其返回成功后才保存协商采样率、session 并设为 STATE_INITIALIZED：

这里的 sampleRate[]、session[] 是出入参。请求采样率为 0 时可由底层决定；明确请求采样率时，客户端目标格式与 HAL 实际格式仍须区分。session 的解析优先显式请求，其次是 Context 对应虚拟设备的录音 session，最后才是自动生成。

3.2. JNI：把“字节容量”转换成“帧容量”

JNI 的 android_media_AudioRecord_setup() 建立 native AudioRecord，转换 AudioAttributes、声道掩码和音频格式，把 Java 的 buffer 字节数转换为 frameCount，并建立回调 storage。它调用 AudioRecord::set() 时传入 TRANSFER_DEFAULT 与 threadCanCallJava=true，这就是第 2.7 节 SYNC 模式的来源。

JNI 同时保存两类引用：Java 对象持有 native 对象；native 事件回调通过 storage 保存的弱引用找到 Java 对象，再交给 Handler 或路由通知分发。弱引用避免仅凭回调关联把 Java 对象永久保活，不能代替应用显式 release。

AttributionSource 记录 UID、PID、包名及归因链，用于“这次音频访问算到谁头上”。客户端参数只能表达归因请求，不能成为可信身份凭证。AudioFlinger 服务端仍会结合 Binder 调用上下文验证：旧分支校正非可信调用者的 UID/PID 并检查包名，新权限分支使用 validateAttributionFromContextOrTrustedCaller()。

3.3. native set：保存需求，准备事件线程和权限同步

AudioRecord::set() 只允许初始化一次。它保存 source/attributes、客户端格式、请求容量、flags、设备偏好与回调，创建 RecordingActivityTracker，并准备第 2.7 节的线程。

还有一个容易漏掉的步骤：调用 system_server 的 permissionUpdateBarrier()。本地实现通过 AudioService 的权限提供者同步机制，使客户端继续创建录音前，相关权限更新能够按其协议传播。它针对“运行时权限刚变化，而 audioserver 仍使用旧视图”的一致性问题；不能把一次屏障理解为之后权限永远不会变化，启动和运行期仍有检查。

set 的最后在客户端 mLock 保护下调用 createRecord_l(0)。方法名中的 _l 提醒读者它依赖调用方持有相应锁；这不是全局统一的 Java synchronized，也不是远程事务自动提供的锁。

创建的重试要分清两种：

  • 客户端在 FAILED_TRANSACTION 这一特定错误下重试创建；本快照最多 3 次，间隔表达式为 (20 + rand() % 30) * 10000 微秒，即 200—490 ms。代码说明针对输入打开过程中 APM 与 AudioFlinger 状态不一致的特定竞态，并非所有参数或权限错误都重试。
  • 服务端在 FAST 不满足时去掉 FAST/RAW 约束重新向策略申请输入，属于同一次 createRecord() 内的回退，见 3.7。

失败原因不能只看“重试了”：权限拒绝、profile 不支持、轨道容量失败、服务死亡和竞态失配的后续动作不同。

3.5. 策略申请：先知道选了什么，才能判断能否使用

AudioFlinger 调用 AudioSystem::getInputForAttr()，由 AudioPolicyService 进入 APM。普通输入的关键顺序是：

  1. 把 DEFAULT 规整为 MIC，整理 source、flags、虚拟设备和 call redirection 等上下文。
  2. 根据 REMOTE_SUBMIX 的 addr tag、有效的显式设备 ID 或策略引擎选择候选设备。
  3. 依据source + 设备/mix 类型 + flags + attribution调用权限检查。
  4. 为这个设备寻找兼容 input profile，再复用、打开或在特定分支抢占输入。
  5. 分配客户端 portId，创建 RecordClientDescriptor 并挂到 AudioInputDescriptor。
  6. APS 创建 AudioRecordClient，必要时安装 AppOps 监听；随后通过 AudioPolicyEffects::addInputEffects() 尝试按 source/session 附加预处理。

权限检查不能简单画成“APM 之前统一问一次 system_server”。候选设备会影响 mix 类型：普通远程混音、MediaProjection 动态 mix、外部策略重路由和虚拟设备注入对应不同前提。新权限模型还可能直接查询 audioserver 的权限提供者；不必每次都同步跨到 system_server。

选设备与开输入是两层决定。 设备表示声音来源，input profile 描述某模块的输入能力与 flags。客户端要 16 kHz，兼容的 profile 可能使用 48 kHz；策略与 AudioFlinger 可以协作提供转换。相反，source 名称不能保证某个 profile 存在，也不能保证 VOICE_COMMUNICATION 一定走内置麦克风。

3.7. AudioFlinger 建 RecordTrack：FAST 偏好可能被拒绝

拿到 input handle 后，AudioFlinger 查找对应 RecordThread，再调用 createRecordTrack_l()。这里校验线程、格式、FAST 条件，计算容量并建立 RecordTrack。FAST 被修改时可返回 BAD_TYPE，AudioFlinger 释放此前的策略注册，再用收窄后的 flags 重新申请 input。

4. 启动与停止：把对象状态交给持续工作的线程

4.1. Java startRecording：先检查对象，再检查实际启动结果

startRecording() 是 void API。在这份实现中，未初始化会抛 IllegalStateException；native 启动成功时才更新 Java 录音状态。不能用“方法返回且没有异常”代替对运行态的检查。

对应用 A，初始化后首次调用 start，应确认 getRecordingState() 已变为 RECORDSTATE_RECORDING。随后若策略将它静音，这个字段仍可保持 RECORDING；静音要用录音配置或策略 dump 观察。

4.2. native start：清残留、重置计数，再启动服务端

本快照只有在没有 AudioRecordThread的分支里，start 才给当前调用线程设置音频优先级，并在 stop 恢复。普通 Java AudioRecord 有 JNI callback，从而建有该线程；不能概括成“所有 Java SYNC start 都会给应用读取线程自动提优先级”。应用仍需合理安排自己的采集线程。

服务端 start 不是直接把一个布尔量改为 true。调用入口通常在处理控制请求的线程上，而真正读输入、发布 PCM 的是 RecordThread 的 threadLoop；两者还要与策略服务协调。

主动放锁不是可有可无的优化：startInput() 可能导致策略计算静音状态，再调用 AudioFlinger 的 setRecordSilenced()。如果一直持着 RecordThread 锁去等待外部服务，就可能与反向访问形成锁依赖。状态机把这段暂时不持锁的过程变成可识别、可清理的阶段。

4.4. startInput 做什么：数据交付资格和输入路由同时激活

APS 的 startInput(portId) 先定位创建时登记的 AudioRecordClient，开始权限/AppOps 数据交付检查。硬拒绝直接失败；其余路径更新活跃状态、记录 startTime，再重算并发录音。之后 APM 的 startInput 激活输入 client、配置输入设备/patch，并按输入用途处理后续联动。

这几层状态各有用途：

  • APS client 的 active 与 startTimeNs 用于第 7 章并发选择。
  • APM 的活跃计数影响当前输入设备选择及输入用途管理。
  • AudioFlinger 的 ACTIVE 让 threadLoop 实际处理这条轨道。
  • HAL 流是否已经在读，取决于是否有人共用该输入；新 client start 不必对应一次新的硬件 open。

对主模块的首个相关输入活动，APM 会通知 SoundTrigger capture state；对某些 remote submix 场景，会处理配对虚拟输出的可用状态。这些是“采集开始”的跨子系统协作，不能从一条通知直接推定 DSP 必须关闭热词检测，实际并发能力仍取决于设备。

4.5. start 之前的数据究竟会不会读到

普通新一轮 start 有两处主动丢弃残留：客户端 flush 清掉 track 共享缓冲，服务端 Provider reset 把当前 track 的输入消费位置接到线程 rear。这样不会刻意把已有软件积压当成新一轮录音交付。

但这不是精确的声学时间边界保证。HAL、驱动、DSP 内部可能已有流水线延迟，控制调用与硬件采样也不是一个同步时刻；历史共享路径还会有意把 Provider 起点设到过去。正确说法是“普通启动清理相关软件缓冲的旧状态”，不能保证“第一帧的声学采样时刻必定晚于 Java startRecording 调用时刻”。

在实验中，应使用音频时间戳或外部可控信号定位边界；单看第一轮 read 的返回时间，只能知道应用何时拿到数据。

4.6. stop：中断等待，并等待采集线程确认暂停

客户端 stop 先 mActive=false，再通过 mProxy->interrupt() 打断正在等待共享缓冲的读取，随后调用服务端 stop、报告 recordingStopped 并暂停事件线程。

服务端并不是只从列表中删一个元素就返回：

threadLoop 扫描到 PAUSING 后，置 PAUSED、移出活跃集合并唤醒等待者。等待条件变量时会释放锁，供 threadLoop 完成状态更新；它不是拿着锁忙等。

这使停止在服务端与采集循环之间有同步确认。源码没有给出“stop 最多一个 HAL 周期”的硬时间上限：实际耗时还包括 HAL 读、调度、锁竞争、策略调用和异常情况，不能把正常节拍当作超时承诺。

stop 不等于 flush 或 release。本快照停止后仍可尝试读出已经交付的剩余数据；native obtain 发现 !mActive 会改用非阻塞方式，缓冲排空就不会无限等新帧。下一次 start 才再次清理剩余缓冲并重置本轮计数。

4.7. release：撤销这条 client，而不是无条件关闭整个麦克风

Java release() 尝试 stop，注销其托管的播放捕获 policy，调用 native_release() 并把对象状态改回 UNINITIALIZED。native 析构会停止并等待回调线程退出，解除死亡通知、清共享内存和控制引用，并释放 session 的持有关系。

服务端 RecordHandle 析构进入 stop/destroy。RecordTrack 的 destroy 根据先前状态补做 stopInput()，然后 releaseInput(portId)。APM 移除这个 client 后检查输入还是否有其他客户端：有则保留 input，无则关闭 input；同 session 的效果也会按条件转为 orphan chain 等待后续归属，不能简单描述成“release 一律销毁全部效果”。

对 A 和 B 共用一个输入的场景：A stop 后，B 可以继续驱动采集；A release 只撤销 A 的轨道与注册；只有输入确实无人持有时，才走相应关闭流程。standby 与 close 也不同：前者是流暂时无工作，后者是输入资源被拆除。

应用应显式管理生命周期，在读线程退出后释放对象，避免与另一个线程继续访问缓冲竞争。finalize 和 Binder 引用清理是兜底，不能成为录音结束的及时性保证。

5. 持续采集：一帧 PCM 如何到达应用数组

5.1. RecordThread 的工作循环不是 read() 的远程实现

A 调用阻塞 read 时，应用线程可以睡眠；与此同时，RecordThread 按输入流节拍持续工作。对普通 PCM，它的主干可以分为六个阶段：

  1. 在锁内处理配置事件、活跃列表和 STARTING/PAUSING 状态，无工作时进入 standby/等待。
  2. 按当前需要更新 metadata、协调效果链与 FastCapture 状态。
  3. 从输入流读取，或在启用 FastCapture 时从 pipe 读取，放进线程级 mRsmpInBuffer。
  4. 更新线程输入位置、处理环形回绕、采集时间戳信息。
  5. 对每条普通活跃 track，取其可写 sink 区域和对应输入片段，按需要转换。
  6. 执行同步丢帧/静音判断，提交该 track 的输出帧，发布轨道时间信息。

“服务端不会为某条满缓冲的 track 等待”只针对向该 track 分发的环节。RecordThread 从 HAL 的读取可以阻塞，空闲时也会等待条件变量；不能笼统说“服务端线程永不阻塞”。

有 FastCapture 时，实际执行 HAL read 的是 FastCapture，RecordThread 从 pipe 取数据再给普通 track 分发。没有 FastCapture 的主线里，才由 RecordThread 自己读取输入。一个输入的两种模式不能写成两个线程同时竞争读同一条 HAL 流。

5.2. 两级缓冲与每条轨道独立的转换器

图中所有绿色箭头都是 PCM 数据流。左侧共享的是原始输入缓冲及其写入进度；中间每条轨道有独立 Provider 和 Converter，右侧也有独立共享环形缓冲。没有 A→B 的数据依赖。

第一层 mRsmpInBuffer 属于 RecordThread，保存输入流格式的数据；名字里虽然有 Rsmp，也不能据此认为它已经是每个客户端要的重采样结果。每条 track 的 ResamplerBufferProvider 保存自己的 mRsmpInFront，用来确定从这份线程缓冲哪里继续取输入。

5.3. Converter 具体转换什么，哪里仍然会拷贝

RecordBufferConverter 处理采样率、声道映射与 sample format。updateParameters() 决定是否建立 resampler，以及是否需要格式或声道处理；convert() 按 Provider 可提供的连续区域取输入。

对 A，采样率转换在服务端这条 converter 中发生；到了 A 的普通共享缓冲，数据已经是 A 要的 16 kHz 单声道格式。客户端 read() 的职责是把这些帧取走并放入应用目标内存。

格式全匹配时可以避开重采样计算，但目的缓冲写入与后续 read 拷贝仍存在，不能说“零开销”。同理，ByteBuffer.allocateDirect() 让 JNI 直接找到目标缓冲地址，减少 Java 数组访问可能涉及的额外搬运，但不会把应用 ByteBuffer 自动变成服务端共享 ring。

预处理与格式转换也不是一件事。AEC/NS/AGC 等效果属于 session/source、效果链与 HAL 处理能力范畴；converter 解决的是数据格式适配。代码中调用效果链处理，不代表所有效果都由这段 C++ 对同一块 PCM 做一次纯软件处理，更不意味着多个录音客户端能要求同一硬件输入同时实现互不影响的所有预处理方案。

5.4. 共享环形缓冲：发布顺序比“两个指针”更重要

普通录音共享的控制结构沿用 AudioTrackShared。录音方向 mIsOut=false：server 是生产者，推进 rear；client 是消费者，推进 front。

5.6. CALLBACK 模式与位置通知：事件不等于数据

AudioRecordThread::threadLoop() 调用 processAudioBuffer()。该方法先检查 cblk 中的 overrun/invalid 标志、marker、周期位置与代际变化，在释放客户端锁后投递回调，避免拿着内部锁执行用户代码。

如果当前不是 TRANSFER_CALLBACK，做完事件处理便返回下一次需要运行的时间，不进入数据回调循环；如果是 CALLBACK，则按剩余通知帧数 obtain 数据，必要时转换 sample format，调用 onMoreData()，最后只 release 回调声明已消费的部分。

返回值构成内部调度协议：0 表示尽快继续，正数表示一段等待时间，特殊值表示暂停、等待合适事件或退出。设置 marker 等操作还可以唤醒线程重算。该设计减少了无意义的持续轮询，但某些路径仍有超时/重试，不宜把整个函数绝对描述成“完全无轮询”。

Java setRecordPositionUpdateListener() 收到的是位置事件；registerAudioRecordingCallback() 收到的是配置/静音变化；两者都不直接携带 PCM。只有明确的 native CALLBACK 数据消费路径，才由 onMoreData() 接收音频缓冲。

6. FastCapture：同一套客户端接口下的另一条数据路径

6.1. 为什么需要一个专门的快速读取线程

普通 RecordThread 同时管理轨道状态、效果、转换和多个消费者。若 HAL 输入周期很短，让这些工作与每个短周期读取完全绑定，调度压力会增加。FastCapture 将紧凑的 HAL 读与 pipe 写放到专门线程中，普通 RecordThread 可以按较合适的节拍从 pipe 取数并继续分发。

它与两个概念必须分开：

  • 存在 FastCapture 线程：输入读取架构的一种安排；即使客户端是普通 track，也可能由它间接供数。
  • 某客户端获准 fast track：该客户端直接消费 pipe 对应数据区，绕过普通 RecordThread 的逐 track 转换/分发循环。

绿色箭头是 PCM，橙色箭头是控制块的发布与唤醒，蓝色虚线只表示 fast client 与其 cblk 的关联。图中“同一份 PCM”强调 pipe 与 fast track 数据区的复用，不代表 FastCapture 从 HAL 到 pipe 完全没有拷贝，也不表示所有对象都在同一进程。

FastCapture 还有自己的读暂存区 mReadBuffer：HAL → 读暂存区 → pipe，之后才由各消费者读取。fast 的优势是避开普通逐 track 分发的部分处理与调度路径，不是消灭所有数据搬运。

sample format 可以不同：AudioFlinger 对 fast 返回线程格式作为 serverConfig，客户端通过读出时的编码转换适配。例如输入是 float，而应用要 PCM16，允许的转换仍不等于可把 48 kHz 自动改成 16 kHz。

所以本文的 A 若要 16 kHz，而输入线程为 48 kHz，就不能仅靠 FAST flag 直达 pipe。它应走普通转换路径，或底层重新选择真正兼容的输入；最终要看返回 flags 和 dump 的 fast 标记，而不是看应用曾请求过什么。

6.4. FastCapture 的容量、优先级与静音限制

本快照默认 Static 选择会检查非 MSD 设备、线性 PCM，以及 HAL buffer 时长小于普通采集最小周期阈值等条件。pipe 容量按 roundup(4 * 20ms * sampleRate) 形成 P2 深度。以 48 kHz 为例，80 ms 为 3840 帧，向上对齐到 4096 帧，约 85.3 ms。客户端代码中某些说明性注释提到 2048 帧，不能用它覆盖本地构造代码实际计算。

大 pipe 容量也不等于每次要等满 85.3 ms 才读。FastCapture 每次有效写入后推进 cblk，客户端可及时消费，容量主要给调度和读取进度提供余量。

线程启动后会请求音频实时调度优先级，服务端还可根据有效 clientTid 给客户端回调线程申请优先级。它依赖调度配置与申请结果，不能仅从线程名就证明运行时实际是 SCHED_FIFO，更不能保证应用回调里做文件压缩、网络请求也不会错过周期。

静音是 fast 路径的一个重要限制：

  • fast track 是唯一活跃 track 时，RecordThread 可把 mSilenceCapture 传给 FastCapture，在写 pipe 前将整份读缓冲清零。
  • fast track 被静音但还有其他活跃 track 时，不能把共用 pipe 整体清零，否则会连带影响其他客户端。因此本快照使这条 fast track 失效，促使客户端重连。
  • 重连并不保证必然降为普通 track。restoreRecord_l() 从 mOrigFlags 重试 FAST，源码注释明确允许重连后仍被再次 invalidate，直到条件改变。

这条分支再次说明：权限策略相同，落地方式可能因数据路径不同而改变。不能把普通 track 的 per-track memset 画进所有 fast 数据流。

7.3. 读懂 updateUidStates_l：先选代表，再算每个 client

这段仲裁逻辑较长，但可以拆成四个顺序阶段。这样既能保留复杂性，也不会要求读者先背所有布尔表达式。

第一阶段：隐私开关短路。 mSensorPrivacyPolicy->isSensorPrivacyEnabled() 成立时，调用 silenceAllRecordings_l()，将非虚拟 source 静音后返回。这里的 virtual source 包含通话上下行/双向、REMOTE_SUBMIX、FM_TUNER、ECHO_REFERENCE；它描述该算法的源分类，不等同于所有“非物理麦克风”的泛称。也不宜把 SensorPrivacyPolicy 一概叫作硬件物理开关。

第二阶段：扫描活跃 client，选择候选代表。 忽略 inactive 与映射为 APP_STATE_IDLE 的 UID；无障碍和 virtual source 不参加普通 top/latest 选举，避免它们遮蔽普通录音者。

8.2. restoreRecord_l 重建的不是整个 Java 对象

restoreRecord_l() 重新执行 native 创建通道：从原始 flags 重新协商，获得新的 IAudioRecord、共享内存、proxy、portId/input，必要时重新 start。

内部最多三轮、失败间隔 500 ms，是本方法的一层重试。它调用的 createRecord 又有特定 FAILED_TRANSACTION 重试，外层 obtain 也有自己的循环；不能把其中一个数字当作“从 API 调用到彻底失败的统一总次数或总时长”。

恢复还保留了重要语义：active 的客户端尝试继续启动，不 active 的客户端只预建连接；原始 FAST 偏好会再试；请求 frameCount 在服务端曾增大后不向下收缩，以避免客户端缓存容量产生混乱。但输入设备、HAL 格式、portId 与实际 flags 都可能变，应重新观察。

8.3. 代际号与额外引用：避免把旧 Buffer 归还给新通道

恢复可能发生在事件线程，也可能由读线程发现错误触发。阻塞 obtain 期间不能一直持有 native mLock，否则 stop、路由修改和其他操作会被长时间阻塞。

实现采取两个保护：obtain 先复制 proxy、cblk IMemory 和 buffer IMemory 的强引用，再放锁等待；这样另一个线程替换成员时，当前调用依赖的对象不会立即消失。每次拿到的 Buffer 还带上当前 mSequence。

obtain 在遇到 DEAD_OBJECT 后还检查 mSequence == oldSequence：如果别的线程已经恢复过，不必再重复创建。锁保证重建串行化，sequence 保证跨越等待后的语义仍属于同一代，两者解决的是不同问题。

这并不意味着应用可以在任意线程无限期保留 native 缓冲指针。obtain/release 的生命周期和模式约束仍须遵守；generation 检查只是在框架换代时防止错误归还污染新通道。

8.4. 恢复入口、错误暴露与连续性的边界

本快照至少有以下恢复入口：start 检查 INVALID，obtain 处理 DEAD_OBJECT，processAudioBuffer 检查 INVALID，以及空闲时 setInputDevice 的主动预建。活跃 setInputDevice 则先停旧服务端接口、置 INVALID并 interrupt，等待后续路径重连。

压缩捕获在 obtain 的 DEAD_OBJECT 分支不尝试该处自动恢复，而是把问题交给调用者；不能据此宣称所有 start/事件入口都被同一个条件禁用了。本文主线是 PCM，不用 PCM 的计数恢复经验代替压缩流的格式与解码上下文管理。

对应用的实际结论是：

  • 有些失效被内部恢复掩盖，read 只表现为一次较长等待，Java 对象还可继续工作。
  • 内部恢复不保证成功；如果最终返回 ERROR_DEAD_OBJECT 或其他错误，应用要按状态退出、释放并在合适条件下重新创建。
  • epoch 和 server offset 让逻辑位置尽量接上旧位置，不能补回恢复期间未采集/未交付的 PCM。
  • SYNC_EVENT_SAME 不保证跨 audioserver 重启保留原同步事件，源码本身对此有待解决注释。

例如 A 在切换设备期间停顿 300 ms，恢复后累计帧位置仍不倒退，不代表这 300 ms 的声音被录下来了。对语音识别可在业务层标记不连续并重置相关算法；对需要严格时间轴的录制，应结合时间戳、内容和业务策略记录缺口，不能只靠“read 又开始返回正数”宣布无损恢复。

9. 路由与特殊采集：哪些环节复用主线，哪些改变了输入来源

9.1. setPreferredDevice：保存偏好与观察实际路由是两件事

Java setPreferredDevice() 首先检查设备是否是有效输入设备，然后调用 native setInputDevice()。客户端保存的是 mSelectedDeviceId，实际已经路由到的设备另有 mRoutedDeviceIds。

返回成功在这里更多表示请求被接受/保存，不能单凭它证明已完成硬件切换。应用应在活跃录音期间读取 getRoutedDevice()，结合路由变更监听和录音配置确认。空闲状态的 Java 查询可以返回 null；native 保存过旧路由也不表示现在仍在该设备采集。

例如 A 切到 USB 输入，服务端可能重新选择 profile 和 HAL 格式，但 A 的输出需求仍是 16 kHz 单声道，新的 converter 应继续适配。不要把“HAL 变为 48 kHz”误判成应用数组突然变成了 48 kHz。

本快照的复数 getRoutedDeviceIds JNI 循环还存在可疑的双重自增，见附录 13.3；多设备路由诊断应同时用服务端 dump 交叉验证，不只依赖这一个客户端结果。

9.2. 播放回采：输入端换成虚拟混音，后半段仍使用 AudioRecord

普通公共播放回采通过 AudioPlaybackCaptureConfiguration 与 MediaProjection 组织。Builder 走专门分支：创建 AudioMix，注册包含该 mix 的动态 AudioPolicy，再由 createAudioRecordSink() 创建录音对象，并把 policy 注销责任托管给 release。

mix 同时要求 LOOP_BACK 和 RENDER：一边保留播放渲染，一边形成可被捕获的混音。录音侧 AudioAttributes 使用 REMOTE_SUBMIX 和 addr=<mix 地址> tag，让 APM 找到对应虚拟输入。

整个数据路径可以读成：目标播放器 → 可捕获的 policy mix → remote submix 输出/输入设备对 → RecordThread/RecordTrack → 共享缓冲 → AudioRecord.read。 变的是上游来源，客户端的 PCM 读取模式仍可沿用前文。

普通应用至少需要 RECORD_AUDIO、用户的 MediaProjection 授权，并与被捕获应用处于同一 user profile；被捕获播放器还受 usage、manifest 和 capture policy 限制。公共说明见 Android：Capture audio playback。这与 native 某一层因 PUBLIC_CAPTURE_PLAYBACK 而不重复同一权限检查并不冲突。

本地 AudioPlaybackCaptureConfiguration 类文档明确列出可捕获 usage 为 UNKNOWN、GAME、MEDIA，不能漏掉 UNKNOWN。manifest 必须显式允许，或未配置且 targetSdk 至少为 Q；应用级与播放器级 capture policy 的有效结果按更严格限制处理。普通 MediaProjection 回采不能因为规则匹配到了 VOICE_COMMUNICATION 就绕过通话限制；系统特权采集与 call redirection 是另外的授权路径，不能因此声称“整个 Android 只有这一条合法捕获方式”。

SUBMIX_FIXED_VOLUME 是另一个容易误读的 tag。Java 构造会识别并移除它，保存 mIsSubmixFullVolume，在 start/stop 时通知 AudioService 的相关固定音量机制。它不能消除源播放器自己的静音、音量调整或 capture policy 过滤；不要把它描述为“无论源应用怎样调音量，都保证录到原始满幅信号”。

MediaProjection 被撤销后，应处理其停止回调并结束业务。继续读到静音，不是重新申请绕过用户授权的理由。

9.4. shareAudioHistory：允许新消费者从仍保留的过去开始

热词唤醒后，识别引擎常希望拿到唤醒词之前的声音。软件历史共享通过扩大/保留 RecordThread 输入 ring，并给新 track 安排较早的 Provider 起点实现。它属于带权限的 SystemApi 流程，不是普通应用任意读取别人的麦克风历史。

协议的关键步骤是：

  1. 共享方创建录音时用 setMaxSharedAudioHistoryMillis() 声明历史上限，本快照最大 5000 ms。
  2. 开始采集，确定接收方要从该录音开始后的哪个时间点读起。
  3. 调用 shareAudioHistory(接收方包名, startFromMillis)，得到带 session 的 MediaSyncEvent。
  4. 接收方用 Builder.setSharedAudioEvent() 配置 session 并创建/启动自己的 AudioRecord；服务端还会核对包名、session 与热词采集权限。
  5. 接收方真正开始采集后，共享方才停止并释放。缓冲历史不足时按 best effort 调整。

startFromMillis 是相对共享方初始录音起点的位置，不是“往现在回看多少毫秒”。例如共享方已经录了 4000 ms，希望接收方从 2500 ms 位置开始，传的是 2500，而不是 1500。具体接收到多少历史还受 ring 可保留范围与时序影响。

9.6. 麦克风信息、方向与通话提取的边界

getActiveMicrophones() 经 RecordThread 查询 HAL 的麦克风信息与通道映射；不支持时 Java 侧还有基于路由设备信息的回退。结果适合说明“设备/通道如何描述”，不能仅凭 fallback 信息证明每个物理阵元当前实际有信号。

setPreferredMicrophoneDirection() 和 field dimension 保存请求并传给输入 HAL。native start 还会重新发送保存的偏好，但最后是否实现波束、指向或变焦，需要硬件和 HAL 支持。方法名中的 preferred 不能省略成必然生效的硬件保证。

Call Redirection 则改变授权与输入来源。PSTN 分支在 attributes 上加 call redirection 标记，VoIP 分支通过匹配相关通信播放用途的动态 policy mix 构建提取录音。不能把它们当作普通应用任意采集第三方通话的公共捷径，也不能仅凭 flag 断言 HAL 一定已经路由到上下行混合源。完整 Telecom 授权与硬件通话路径超出本文主线。

10. 录音监控：把“对象活跃”与“当前配置”合成一份可观察状态

10.1. 为什么需要两条上报通路

应用能够主动 start/stop；设备、格式与静音变化则经常由 audioserver 策略决定。如果只依赖应用自报，就不知道底层路由变了；如果只依赖音频服务端，就难以直接表达上层 recorder 的整个对象生命周期。

本地实现把两条通路汇入 system_server 的 RecordingActivityMonitor：

服务端配置变化 AudioInputDescriptor → AudioPolicyService 通知 → AudioSystem 回调 → RecordingActivityMonitor client/device 格式、portId、patch、effects、silenced 等

配置通知还会经过命令线程和 Binder/Handler 等异步边界，因此收到回调的时刻不等于硬件状态变化的精确时刻。分析先后顺序时应同时记录操作时间、回调时间和服务端日志。

10.2. RecordingActivityMonitor 的台账如何合并

有有效 riid 时，updateSnapshot() 按 riid 查找 recorder；对于由音频服务端直接管理、没有有效 riid 的条目，可按 portId 关联。START 激活，UPDATE 替换配置，STOP 失活，RELEASE 移除并解除相应监听。

只有活跃状态与配置共同满足条件，才形成对外的 active recording configuration。两条通路可能先后到达，它们是在状态机中合并，不是简单拼接两份列表。

audioserver 死亡时，monitor 删除那些没有客户端 death handler、由音频服务端跟踪的记录；上层客户端的条目则可能保留以等待重连或客户端自身释放。这个设计提供生命周期协调，但不保证音频连续，更不能说“任何一条通路失败，另一条都能完整重建全部事实”。

10.4. 麦克风隐私指示不是 riid 的简单映射

RecordingActivityMonitor 的台账参与系统观察，但状态栏麦克风隐私指示不能只沿 recorderEvent() 一条线解释。本地 SystemUI 的 AppOpsPrivacyItemMonitor 使用 AppOpsController，订阅麦克风相关操作；AppOpsController 还结合录音配置更新静音等信息。

因此排查“界面指示和录音内容不一致”，至少要区分三层：应用 recorder 的生命周期、APS/AppOps 的交付与使用状态、SystemUI 对这些状态的展示策略。一个 START 事件不等于在所有设备上立刻显示固定样式的小绿点；有指示也不证明正在采到非零、无失真的音频。

11. 如何验证：从一次 API 观测到服务端与调度证据

11.1. 先建立最小观测，不急着改系统属性

一次录音应至少记录：

  • 创建前的 source/rate/channel/encoding/请求容量，以及创建后的实际 buffer frames 与 session。
  • start 前后 state、recordingState；每次 read 的返回值、耗时、累计成功帧数。

  • getTimestamp() 的返回状态；成功时才保存 position/time，并注明 timebase。

采集线程不要逐帧打印日志，也不要同步执行网络上传、重计算或大文件写入。让日志按较低频率汇总，避免观测本身制造 overrun。

11.3. 实验一：证明“客户端格式不等于 HAL 格式”

操作：保持 A 的 16 kHz mono PCM16 参数不变，正常运行 Probe，同时保存三个 dump 和配置回调。必要时换到支持不同输入格式的外接设备，另起一轮录音。

观察：比较 getClientFormat()/轨道行与 getFormat()/输入线程配置；记录 read 返回单位，核对累计样本数与目标采样率是否在时间尺度上相符。

预期：若输入线程实际是 48 kHz，而客户端为 16 kHz，就能看到两个格式域不同，正文的 converter 路径有实际适用条件。如果两端都为 16 kHz，这一轮只能说明不需要该采样率转换，不能证明系统没有 converter。

限制：字段证明配置与框架交付约定，不直接量化重采样音质；测试音源和输出 PCM 的频谱/波形分析才可进一步评价转换结果。

11.4. 实验二：区分容量与阻塞读取批次

操作：在相同输入设备和服务端实际容量下，分别以 160、320、1600 帧请求执行阻塞 read。用工作线程和统一的停止控制，记录每次返回耗时、返回量及长尾。

观察：16 kHz 下这三种批次分别对应 10、20、100 ms 音频；同时记录 FrmCnt/FrmRdy，避免实验时容量也被改变。

预期：稳定连续采集时，大请求往往需要等待更多数据累计，但已有积压时也可能很快返回。服务端可能每小批唤醒，native read 却继续等到本次请求完成；两者不是同一周期。

限制：一次很快的 1600 帧读取不能证明低延迟，它可能只是一次性排掉 100 ms 旧积压。API 调用耗时也不等于音频从麦克风到算法的端到端延迟。

11.5. 实验三：制造慢消费者，验证局部 overrun

操作：先正常采集；随后按 Probe 的可控参数停读 500 ms，再恢复。播放可识别的连续计数音/脉冲序列或其他受控信号，必要时保存 PCM 以便离线检查。先只测一个 client，之后再在具备合法并发条件的环境里增加第二个独立消费者。

观察：停读前后 read 的数据量、样本内容、时间戳与 RecordThread: buffer overflow 等日志；连续采样 FrmRdy，检查是否出现明显积压。不要把所有 read 返回为 0 都当成 overrun。

预期：当停读超过可保留历史时，恢复后内容可能缺失，但 API 不一定返回错误，计数也不一定显式跳变。若另一个 client 正常消费，不能仅因慢 client 积压就推导整个输入必须停住。

限制：是否出现日志受日志级别、节流与路径影响；两个不同普通应用还可能先被并发策略静音，实验前要确认实际 silenced 与 UID 条件，否则测到的是策略而不是消费者隔离。

11.6. 实验四：验证“RECORDING 与 silenced 可以同时成立”

操作：准备两个不同 UID 的自有测试应用，均具备当前系统要求的录音资格。先 A 用 MIC，随后 B 用默认敏感的 CAMCORDER；分别记录前台状态、录音状态与配置回调。再停止 B，观察 A。

观察：A 是否仍为 RECORDING，read 是否返回正数，配置是否变为 silenced=true，停止 B 后是否恢复；同时观察 input 是否因资源不足发生关闭/重建。

预期：在第 7.6 节前提满足时，A 可保持启动却被静音，B 停止后重新获准。若 B 创建失败、输入被抢占或权限条件未满足，则这轮实验没有落在“只静音不拆流”的前提下，应先解释资源/权限路径。

限制：不要通过把应用随意退到后台来模拟“两个有资格但无 TOP 的客户端”；后台麦克风资格与前台服务限制可能另行改变实验。也不要把 grant/revoke 运行时权限当作仅修改一个布尔位的动作，它可能使进程被系统重启。

11.7. 实验五：切设备，追踪 portId 换代与业务缺口

操作：录音期间在可用的内置/USB 等输入之间设置偏好，记录请求返回、路由回调、配置、native restore 日志和 read 返回。设备插拔与主动 setPreferredDevice 分开测。

观察：Java 对象是否保留、实际 routed device 是否改变、portId/ioHandle 是否变化、client format 是否保持、时间戳何时恢复有效；使用可识别音源查内容是否中断。

预期：需要重建的路径会出现新服务端身份，可能仍保持同一 session/riid；某些可原地调整的路由不一定重建。即使计数接续，内容仍可有缺口。

限制：返回 true 不能证明选定设备已实际输出音频；没有暴露 ERROR_DEAD_OBJECT 也不能证明没有内部恢复。无需为了做这一实验直接重启 audioserver；服务死亡测试应另在专用调试设备进行，并明确影响所有音频会话。

12. 复习与自测：能否从机制推导场景

12.1. L0：先记住四个关系

AudioRecord 是应用获取音频数据的入口；AudioFlinger 用 RecordTrack 表示一条客户端录音，用 RecordThread 管理输入与分发；AudioPolicyService/Manager 决定输入资源和采集资格；system_server 合并录音活动与配置并向观察者分发。

控制经服务接口协作，PCM 经共享缓冲交付。客户端是消费者，服务端是生产者。初始化、active、silenced 和内容连续性彼此独立，不能用一个“正在录音”概念包办。

为什么换设备后还能用原对象 INVALID → 内部重建 → 新 portId/proxy/共享内存 → active 时再 start；generation 防止旧 buffer 误归还
为什么计数正常也会丢声音 缓冲覆盖或重建期间内容缺口，不一定等于 Java 错误或显式位置跳变

12.3. L2：按问题查，不必硬背的细节

需要查容量公式，看 RecordThread::createRecordTrack_l()；查唤醒条件，看 ServerProxy::releaseBuffer()；查慢消费者追赶，看 ResamplerBufferProvider::sync()；查特殊角色并发，看 updateUidStates_l() 的候选与特例；查权限矩阵，看 APM 构造的 PermissionReqs 和 APS 的 checkPermissionForInput；查设备切换，看 setInputDevice() 与实际路由回调；查状态台账，看 RecordingActivityMonitor 的 updateSnapshot。

FAST 接受条件、source 数值、flags、重试次数和 dump 列名属于定位工具，必须带着源码版本与运行条件使用。知道“去哪里验证”比脱离版本背一张表更重要。

12.4. 基础题

问题 1：A 构造成功后，为什么第一次非阻塞 read 可能返回 0？

展开参考答案

创建只建立通道，不等于已经激活输入并发布帧。若尚未 start，或刚 start 而共享缓冲还无可读数据，非阻塞读取可以没有数据。返回 0 表示本次没有交付样本，与“返回正数且样本全零”的静音数据不同。回看 3.9、4.1 和 5.5。

问题 2：16 kHz、双声道、PCM16 的 read(short[], ..., 320)，请求了多少帧、多少毫秒？

展开参考答案

320 是 short 数。每帧有两个声道采样点，因此是 160 帧、640 byte，对应 160/16000 秒，即 10 ms。单声道时才是 320 帧、20 ms。回看 2.1。

问题 3：Java AudioRecord 使用 SYNC，为何还能看到名为 AudioRecord 的 native 线程？

展开参考答案

transfer type 决定谁消费 PCM，而是否创建 AudioRecordThread 由 callback 是否为空决定。JNI 提供 callback storage，所以即使数据走 read，native 线程仍可处理位置事件和失效。它不会自动把 PCM 变成 Java 位置回调的参数。回看 2.7、5.6。

问题 4：mMinimum 设置为 320，是否意味着只有积累到 320 帧才会唤醒录音客户端？

展开参考答案

不能。在本快照 ServerProxy::releaseBuffer() 中，录音方向 !mIsOut 为真，会进入唤醒处理；唤醒标记还可能合并重复 syscall。320 帧通知/批次参数不等于一个强制 futex 门槛，更不等于 read 必须每次返回 320 帧。回看 3.9、5.4、5.5。

问题 5：stop 和 release 都会让 A 停止，为什么不能只保留一个操作？

展开参考答案

stop 结束当前活跃采集，保留对象与已有资源以便重启；未读残留在本快照可按非阻塞方式排出。release 进一步释放 native/服务端引用，撤销 portId/client 注册，最后一个 client 离开时才关闭对应 input。A/B 共用输入时，释放 A 不能无条件关闭 B 的输入。回看 4.6—4.7。

12.5. 场景推理题

问题 6：HAL 为 48 kHz stereo，A 要 16 kHz mono，B 要 48 kHz stereo。是否可以先全局重采样成 16 kHz，再共享给 A/B？

展开参考答案

不能用这个模型解释本实现。线程 ring 保存输入格式，每条 track 有独立 Provider/Converter：A 按需要重采样和变换声道，B 可以保持其目标格式。若先把全局输入变成 A 的 16 kHz mono，会丢掉 B 需要的输入信息，也与 RecordTrack 构造归属不符。验证应比较线程格式、两条 track 格式及 converter 参数。回看 5.2—5.3。

问题 7：A 的 read 始终返回 320，但 RMS 突然为 0，Java 仍为 RECORDING。应先判定服务端崩溃吗？

展开参考答案

不应。正数返回表示帧仍在交付，先检查录音配置的 isClientSilenced、APS client 状态、实际输入设备与源信号。普通策略静音就是在发布前将 PCM 清零，帧数可以正常推进。若 silenced=false，再查输入内容和其他静音环节；服务失效通常需额外日志/状态证据。回看 7.5、10.3、11.8。

问题 8：普通 track 的 Nmax 为 320 帧，客户端通知请求为 80 帧，采样率 16 kHz，请求容量只有 160 帧。实际下限是否为 240 帧？

展开参考答案

不是。F30=480 帧，Fmin=320×max(3,ceil(480/320))=960 帧。容量使用 Nmax 推导，而不是把客户端较小通知量乘三。实际 frameCount 至少 960 帧；80 帧通知请求若合法可以保留，但不相应缩小容量下限。回看 3.8。

问题 9：两个普通应用分别使用两条 HAL 输入，是否就可以绕过并发静音？

展开参考答案

不能。输入资源分配与并发资格是不同层。APS 对活跃录音 client 表进行 UID、敏感性、角色与 AppOp 判断，不限于同一个 input 的两条轨道。要验证应记录 UID、active/silenced、source 及 input handle，而不是只证明硬件开得起两条流。回看 3.6、7.3—7.6。

问题 10：A 被停读 500 ms 后又正常 read，累计返回帧数没有跳变，是否说明没有丢数据？

展开参考答案

不能。累计成功读取的帧数统计的是已交付内容，不自动包含被覆盖的输入历史。Provider 可能已经跳到仍保留的最近窗口，Java 也没有保证提供对应的 overrun 回调。需要结合内容中可识别的时间标记、服务端日志、缓冲水位与调度证据。回看 5.7、11.5。

问题 11：fast track 被静音且还有普通 track 活跃，为何不直接清空整个 pipe？恢复后是否必定普通化？

展开参考答案

pipe 同时供其他消费者读取，整体清零会影响获准的普通 track。本快照会使该 fast track 失效。restore 使用原始 flags 重新申请，可能再次成为 fast 并再次失效，不能承诺恢复后必然普通化。回看 6.2、6.4、8.2。

问题 12：切 USB 后 Java 对象没换，portId 变了，时间戳位置也没倒退。这三件事可以同时成立吗？

展开参考答案

可以。内部 restore 保留上层对象，重建服务端连接和客户端 proxy，产生新的策略注册/portId，并用 epoch 与 offset 接续逻辑计数。但底层设备与 PCM 内容可能已经不连续，计数不倒退不能证明无损切换。应同时观察 routed device、服务端身份与内容。回看第 8 章、9.1、11.7。

问题 13：回采只匹配了某个应用 UID，就一定能采到它的通话播放吗？

展开参考答案

不能。matching rule 是捕获范围条件之一，仍受公共 API 的可捕获 usage、manifest、capture policy、MediaProjection 与同一 user profile 等限制。普通回采的可捕获 usage 为 UNKNOWN/GAME/MEDIA。call redirection 和系统特权采集是其他授权链，不会因普通 UID 匹配自动获得。回看 9.2、9.6。

13.3. 阅读源码也要检查注释与实现是否一致

本地快照里有几处很适合作为“不要只读注释”的例子，不应将其直接推广为所有 AOSP 发布版本的缺陷：

  • android_media_AudioRecord_getRoutedDeviceIds() 的 for (...; i++) 内又写 values[i++] = ...deviceIds[i]，在 C++17 及之后的该赋值求值顺序下，会跳过奇数下标。新建 Java int 数组的未填项保持默认的 0，不能将其当作“未初始化垃圾”。该行为需在实际构建标准与版本中复核，本文不把复数路由查询作为唯一观测。
  • RecordThread::stop() 异常收尾路径中的 ALOGW_IF 把格式串放在条件位置，导致真正的格式参数变成 __func__。这影响的是已进入该分支后的日志内容，不等于所有正常 stop 都会走到警告路径；编译器是否诊断还取决于宏与告警配置。
  • Java direct ByteBuffer read 的注释与本地 JNI 基址写入方式不一致，实际使用应核对目标版本并实测；FastCapture 容量注释与构造计算也要区分。正文分别在 5.5 与 6.4 给出明确边界。

这些例子体现同一个阅读习惯：用定义解释字段，用调用点解释时机，用消费者解释结果，再用运行证据判断设备是否真的走到了该分支。
