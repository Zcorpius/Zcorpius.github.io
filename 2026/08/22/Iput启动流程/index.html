Input 启动流程

发表于 2026-08-22 | 分类于 Framework ， Input
字数统计: 4.3k | 阅读时长 ≈ 20

1. 概述

构造阶段结束时，input 系统处于“装配好但没通电”的状态：

  • 流水线的 stage（Reader → UnwantedInteractionBlocker → InputProcessor → InputDeviceMetricsCollector → InputDispatcher）都已 new 出来并串好；
  • EventHub 的 epoll / inotify fd 已经 open，但没有任何线程在 epoll_wait，所以读不到任何事件；
  • InputDispatcher 的 mInboundQueue 是空的，派发线程还不存在。

start() 要做的，就是把这条流水线通电：拉起两条工作线程（InputReader / InputDispatcher），事件才开始流动。

2. 启动入口：inputManager.start()

2.1 SystemServer 的触发点

构造结束后，SystemServer 在 startOtherServices 里紧接着做两件事：

  • setWindowManagerCallbacks：建立 IMS → WMS 的回调通道（把 WMS 的 InputManagerCallback 注入 IMS），供后续 input 处理过程中“问窗口策略 / 通知 WMS”用（按键拦截、ANR、焦点、指针 layer 等）。它必须在 start() 之前接好——线程一起来就会用到。这条通道的实现在 WMS 侧，留到学 WMS 时再看，这里当成黑盒。
  • inputManager.start()：★ 真正的“通电”，下面展开。

2.2 start() 的完整调用链

每一层都很薄，基本是转发：

所以 start() 作用的对象和 init 创建的是同一个。

2.3 拉起两条工作线程

InputManager::start() 只调了 mDispatcher->start() 和 mReader->start()中间三个 stage（Blocker / Processor / Collector）没有 start()、没有自己的线程，它们的 notify* 同步寄生在 Reader 线程上跑（详见构造篇“线程模型”）。所以整条流水线只有两个线程拥有者。

两个 start() 各 new 一个 InputThread：

InputThread 是个薄封装，内部 InputThreadImpl : public Thread，threadLoop() 反复调传入的 lambda：

所以两个线程跑起来后：

  • “InputDispatcher” 线程 → 不停调 dispatchOnce() → 处理 mInboundQueue / mLooper->pollOnce 等待唤醒。
  • “InputReader” 线程 → 不停调 loopOnce() → EventHub.getEvents() → epoll_wait 阻塞等事件 → 读 /dev/input；

“InputDispatcher” 线程 → 持续 dispatchOnce()

“InputReader” 线程 → 持续 loopOnce()

Note

"InputProcessor" HAL 线程不由 start() 启动——它要等后续 setMotionClassifierEnabled 创建 MotionClassifier 时才起（取决于设备有没有注册该 HA L）。所以 start() 只保证 Reader + Dispatcher 两条主线就位。

2.4 为什么先起 Dispatcher 再起 Reader

Reader 一启动就会立刻开始读事件并往下游推**，如果 Dispatcher 还没起来，事件没人接，会丢事件甚至崩溃。先把下游（消费者）准备好，再启动上游（生产者），这是流水线启动的标准做法。

代码里还做了回滚：如果 Reader 起不来（mReader->start() 失败），会把已经起的 Dispatcher stop() 掉，避免留下半残状态。

2.5 启动完成 = “通电”

start() 返回后，input 系统正式从“装配好”进入“运行中”：

start() 之前 start() 之后
流水线 stage 都已 new 好、串好 同左
EventHub fd epoll / inotify 已 open 同左，且有线程在 epoll_wait 了
InputReader 线程 ❌ 不存在 ✅ “InputReader” 在跑 loopOnce
InputDispatcher 线程 ❌ 不存在 ✅ “InputDispatcher” 在跑 dispatchOnce
事件流 ❌ 静止 ✅ 开始流动：/dev/input → Reader → 流水线 → Dispatcher → 窗口

也就是说，start() 是 input 系统从“静”到“动”的分水岭。从此刻起，EventHub 开始 poll 设备节点，一旦用户触摸 / 按键，事件就会顺着第 3 章的链路流向应用窗口。

这也呼应 §2.5 的”通电”：mReader->start() 之后的第一轮 loopOnce() 才真正打开设备节点。

getEvents(timeoutMillis)（EventHub.cpp）是阻塞循环：

  • epoll_wait拿到就绪 fd；
  • 若是 inotify fd → 处理设备增删（openDeviceLocked/closeDeviceLocked，并产出 DEVICE_ADDED / DEVICE_REMOVED 合成事件）；
  • 若是 wake read pipe → 退出本次循环；
  • 若是设备节点 fd → read(device->fd, readBuffer, ...) 读出 struct input_event 数组，按 RawEvent 填好返回。

新设备被打开时（EventHub.cpp 的 openDeviceLocked）：

随后通过一系列 EVIOC* ioctl 读取设备能力（按键、绝对轴、led 等），归类为 InputDeviceClass flags，再 registerDeviceForEpollLocked（EventHub.cpp）把设备 fd 加进 epoll。

3.2 InputReader 主循环

InputReader 起名为 "InputReader" 的 InputThread（InputReader.cpp），跑 loopOnce()（InputReader.cpp）：

注意 InputReader 直接持有 mNextListener 引用（构造时传入，InputReader.cpp 的 mNextListener(listener)，成员声明在 InputReader.h）——这个 listener 就是构造链里的 UnwantedInteractionBlocker（详见构造篇《input系统构造》2.4.2）。与下游 stage 不同，Reader 自己没有 QueuedInputListener 缓冲：事件先积累在 mPendingArgs 成员里，解锁后 swap 出来逐个 notify 给下一站，事件就进入流水线。

processEventsLocked（InputReader.cpp）区分两类事件：

  • type < FIRST_SYNTHETIC_EVENT：真实的 input_event，按 deviceId 路由到对应 InputDevice，由其 InputMapper 集合（KeyboardInputMapper、MultiTouchInputMapper、JoystickInputMapper 等）解析成 NotifyKeyArgs / NotifyMotionArgs 等；
  • 合成事件：DEVICE_ADDED → addDeviceLocked；DEVICE_REMOVED → removeDeviceLocked，并产出 NotifyInputDevicesChangedArgs。

loopOnce() 一轮 = 取事件 → 解析 → 推送，三步走，比 Dispatcher 简单得多（无命令队列 / ANR / 空闲判定）：

解析（processEventsLocked）和推送（mNextListener.notify）都在拿到事件的这一轮内同步完成；中间 stage（Blocker / Processor / Collector）寄生在 Reader 线程上，无自己的线程（详见 §3.3）。

3.3 InputListener 流水线上的各 stage

每个 stage 都继承自 InputListenerInterface，提供 notifyKey/notifyMotion/notifySwitch/...。InputListenerInterface::notify 用 std::visit 把变体 NotifyArgs 分发到具体函数（InputListener.cpp）。

本机代码中间有 3 个 stage（默认 ENABLE_INPUT_DEVICE_USAGE_METRICS = true，InputManager.cpp；关闭后 Collector 不创建，Processor 直接接 Dispatcher）：

Stage 文件 主要职责
UnwantedInteractionBlocker UnwantedInteractionBlocker.h / .cpp Palm rejection（PalmRejector）、PreferStylusOverTouchBlocker（手写笔按下忽略触摸），剔除手掌或抑制误触。运行在 InputReader 线程，无额外队列
InputProcessor InputProcessor.h / .cpp 调用 IInputProcessor HAL 给 motion 做分类（MotionClassifier，区分手掌/笔/手指）。notifyMotion 同步执行在 Reader 线程，但分类在独立的 "InputProcessor" HAL 线程异步进行
InputDeviceMetricsCollector InputDeviceMetricsCollector.h / .cpp 统计输入设备及其使用情况的 metrics（设备被哪些 uid 的应用使用，上报 statsd）。作为 stage 寄生在 Reader 线程；另有 notifyDeviceInteraction 由 Dispatcher 线程调用

它们的 notifyMotion 做的事（UnwantedInteractionBlocker.cpp、InputProcessor.cpp）：

其余 notify*（key / switch / sensor / vibrator 等）在这三个 stage 里基本是透传——往 mQueuedListener 里塞一份，然后 flush() 给下一站。

3.4 InputDispatcher：把事件送进窗口

3.4.1 派发线程与队列

InputDispatcher 起名为 "InputDispatcher" 的 InputThread，跑 dispatchOnce()（InputDispatcher.cpp）：

上游调用 notifyMotion（InputDispatcher.cpp）/ notifyKey（InputDispatcher.cpp）→ enqueueInboundEventLocked（InputDispatcher.cpp）把事件压入 mInboundQueue，并 mLooper->wake() 唤醒派发线程：

dispatchOnceInnerLocked（InputDispatcher.cpp）从队头取出 mPendingEvent，计算目标窗口，调用 startDispatchCycleLocked（InputDispatcher.cpp）→ publishMotionEvent（InputDispatcher 内的封装 内部调 InputPublisher::publishMotionEvent，定义在 InputTransport.cpp）/ publishKeyEvent。

3.4.2 窗口信息来源：SurfaceFlinger（不是 WMS）

InputDispatcher 构造函数（InputDispatcher.cpp）直接向 SurfaceComposer 注册窗口监听：

DispatcherWindowListener::onWindowInfosChanged（InputDispatcher.cpp）转交给 InputDispatcher::onWindowInfosChanged（InputDispatcher.cpp），把 WindowInfosUpdate 按 display 拆开，封装为 WindowInfoHandle 调 setInputWindowsLocked(handles, displayId)（定义在 InputDispatcher.cpp），最后 mLooper->wake()让派发线程重算目标窗口：

这意味着 WMS 不再是 InputDispatcher 的窗口信息来源——所有窗口的可见性、z-order、touchable region、displayId 等都由 SurfaceFlinger 的 SurfaceControl 体系直接维护并推送给 InputDispatcher。Java 层 IMS 与 WMS 的交互主要集中在 lid switch、配置变化、键位布局、touch mode、PointerController 等系统状态，而非窗口派发表。

3.4.3 InputChannel：socketpair 派发到应用

派发到目标窗口走的是 InputChannel（frameworks/native/libs/input/InputTransport.cpp）。一对 channel 由 socketpair 创建（InputTransport.cpp）：

  • server 端被 InputDispatcher 持有在对应窗口的 Connection 中；
  • client 端通过 Binder 返回给应用进程，由 WindowInputEventReceiver（基于 MessageQueue 的 epoll）监听可读事件。

InputDispatcher 派发时调 InputPublisher::publishMotionEvent（InputTransport.cpp）→ InputChannel::sendMessage（InputTransport.cpp）：

应用进程读出后（InputChannel::receiveMessage，InputTransport.cpp）由 native 层 InputConsumer 拼装成 MotionEvent / KeyEvent，回吐到 Java 层 ViewRootImpl，最终交给窗口的 DecorView / View 树消费。

3.4.4 派发-ACK 闭环（概览）

事件发出去 ≠ 派发完，Dispatcher 要等应用回执才派发下一个：

  • 应用处理完通过 InputConsumer::sendFinishedSignal（InputTransport.cpp）回执；Dispatcher 收到后把对应事件从该连接的 waitQueue 移除（doDispatchCycleFinishedCommand，InputDispatcher.cpp）。
  • 不回执 → 超时 → ANR：应用一直不回 ACK，mAnrTracker 到期就会触发 ANR。
  • 具体机制（fd 注册、命令队列、流控细节）等剖析 InputDispatcher 类时再展开。

4. 完整启动与运行时图

一次触摸 motion 事件从设备节点到应用进程的过程按时间轴展开，重点是 3 个线程之间的切换：

sequenceDiagram
    autonumber
    participant Dev as /dev/input 设备节点
    participant EH as EventHub
    participant R as InputReader
    participant B as UnwantedInteractionBlocker
    participant P as InputProcessor
    participant HAL as IInputProcessor HAL
    participant C as InputDeviceMetricsCollector
    participant D as InputDispatcher
    participant App as 应用进程

    Note over EH,R: ① InputReader 线程：epoll_wait 阻塞等待事件
    Dev->>EH: input_event 可读
    R->>EH: getEvents()
    EH-->>R: RawEvent[]
    R->>R: processEventsLocked → InputMapper → NotifyMotionArgs

    Note over R,C: ② 下面整条流水线同步跑在 InputReader 线程（notify → 加工 → flush）；
InputDeviceMetricsCollector 默认开启，关闭时 P 直接 flush 给 D
    R->>B: flush() → notifyMotion(args)
    B->>B: PalmRejector 手掌抑制（可能"一进多出"）
    B->>P: flush() → notifyMotion(改写后)
    P->>HAL: classify(args) 入队（异步，立即返回上次分类）
    HAL-->>P: （稍后）更新分类缓存
    P->>C: flush() → notifyMotion(带 classification)
    C->>D: flush() → notifyMotion(args)

    Note over D: ③ 线程切换在这里发生
    D->>D: notifyMotion 内（Reader 线程）：enqueueInboundEventLocked + mLooper->wake()
    D->>D: 被 wake 唤醒（Dispatcher 线程）：dispatchOnce → 算目标窗口（数据来自 SurfaceFlinger）
    D->>App: InputChannel.sendMessage（socketpair）
    Note over App: WindowInputEventReceiver 收 → InputConsumer → ViewRootImpl → View 树消费

读图要点：

  • 只有 2 条主线 + 1 条旁路线程：主事件流穿越 InputReader 线程 和 InputDispatcher 线程（中间 Blocker / Processor / Collector 全部同步寄生在 Reader 线程）；IInputProcessor HAL 是异步旁路（分类可慢事件流 1~2 帧）。
  • 唯一的线程切换在 ③：事件一路同步流到 InputDispatcher.notifyMotion（这时仍在 Reader 线程），它只把事件压进 mInboundQueue 并 wake()，真正派发在 Dispatcher 线程的 dispatchOnce 里完成。
  • 出口是 socketpair：Dispatcher 算好目标窗口后，经 InputChannel.sendMessage 把事件扔进 socketpair，应用进程的 WindowInputEventReceiver 读出后交给 View 树。
