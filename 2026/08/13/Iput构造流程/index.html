Input 构造流程

发表于 2026-08-13 | 分类于 Framework ， Input
字数统计: 6.5k | 阅读时长 ≈ 28

1. 概述

当用户触摸屏幕或者按键操作，首次触发的是硬件驱动，驱动收到事件后，将该相应事件写入到 /dev/input 下的输入设备节点，这便产生了最原生态的内核事件。

接着，输入系统通过 EventHub 取出原生态事件，由 InputReader 解析为 NotifyArgs，再经 InputListener 流水线（UnwantedInteractionBlocker → InputProcessor）层层封装，最终在 InputDispatcher 内组装成 KeyEvent 或 MotionEvent；

最后通过 InputChannel（socketpair）交付给相应的目标窗口（Window）来消费该输入事件。可见，输入系统在整个过程起到承上启下的衔接作用。整体链路：

Input 模块的主要组成：

  • EventHub：通过 epoll + inotify 监听 /dev/input 下的设备节点，读出 struct input_event 封装为 RawEvent；
  • InputReader：起独立线程 "InputReader" 从 EventHub 拉取 RawEvent，经 InputDevice / InputMapper 解析为 NotifyKeyArgs、NotifyMotionArgs 等 NotifyArgs，推给下游 InputListener 流水线；
  • InputListener 流水线（仅 2 个中间 stage）：
    • UnwantedInteractionBlocker：手掌抑制（PalmRejector）、PreferStylusOverTouch（手写笔按下时忽略触摸），运行在 InputReader 线程；
    • InputProcessor：调用 IInputProcessor HAL 给 motion 做分类（MotionClassifier，区分手掌/笔/手指等）。分类是异步的——它额外起一条 "InputProcessor" HAL 线程去调 HAL，主事件流不被阻塞；
  • InputDispatcher：起独立线程 "InputDispatcher" 接收流水线下游事件并入队 mInboundQueue，同时向 SurfaceFlinger 注册 WindowInfosListener 获取窗口信息，按窗口可见性/focus 计算目标窗口，再通过 InputChannel 把 KeyEvent/MotionEvent 派发出去；
  • InputManagerService：在 SystemServer 启动时被创建，内部持有 native InputManager，承担策略回调、设备热插拔、键位布局、PointerController（鼠标光标/show touches）、Accessibility 过滤（filterInputEvent）、VelocityTracker 配置等职责，并经 WindowManagerCallbacks 与 WMS 协作处理 lid switch、touch mode 等系统状态。

Important

AOSP14 与网络上多数老资料（基于 Android 6.0~11）的核心差异：

  1. Reader 与 Dispatcher 之间多了 2 个中间 stage（UnwantedInteractionBlocker、InputProcessor），不再是 Reader 直接调 Dispatcher；
  2. 窗口信息不再由 WMS 同步给 InputDispatcher，而是 InputDispatcher 直接向 SurfaceFlinger 注册监听；
  3. Motion 分类走独立的 IInputProcessor AIDL HAL，且分类在独立的 HAL 线程上异步进行。

为什么不对称是“被逼出来的”：

  • 形参1 要 sp<>，而构造 sp 必须从指针来（sp(T*)），不能用引用 *this → 只能传 this；
  • 形参2 是裸引用 &，引用必须绑定对象（左值），不能绑指针 → 必须解引用用 *this。

两边互换都传不进去（*this 喂不了 sp 构造，this 绑不了引用形参）。

一个引用计数上的微妙差异： Reader 策略被 sp 持有（强引用、计数 +1），Dispatcher 策略只是裸引用（不计数）。这之所以安全，是因为 NativeInputManager 是进程级单例（nativeInit 里 std::call_once 保证，注释明说 “should not be destroyed for the lifetime of the process”）——它永生，裸引用永不悬空。

2.5.1 InputManager 类结构

native InputManager 核心就两部分：双重继承 + 4 个私有成员。类头部的注释已经把整个架构说清楚了，是理解 inputflinger 最重要的一段话：

Important

InputManager 是输入系统的核心容器——它本身不干活,而是把 4 个组件(流水线)装进来、对外作为一个 Binder 服务(“inputflinger”)。

三条核心设计原则:

  1. 各 stage 不共享内部状态 —— 每个 stage 自己管自己的锁和数据,互相只通过 notify* 接口传事件。这让每个 stage 可以独立演进、独立测试。

  2. 单向流动,绝不回流 —— 事件只能 Reader → … → Dispatcher 往前走,永远不会从 Dispatcher 反向调Reader。这是防死锁的关键(配合”flush 必须在锁外”的规矩)。

  3. 要跟外界打交道时,统一走 Policy —— 各 stage 不直接调系统服务,而是通过 Policy 接口回调。

首先看头函数，InputManager 是双重继承：功能接口 + Binder 服务骨架的结构

  • InputManagerInterface：纯虚功能接口（start、stop、getReader、getProcessor、getDispatcher等），让测试可以 mock；
  • BnInputFlinger：Binder native 端骨架，继承自 BBinder，让 InputManager 对象本身就是一个 IBinder 。注册的 Binder 对象就是 im 本身，而非某个内部成员。

然后再看私有成员：4 个 stage，4 个字段正好对应流水线上的 4 个组件。

字段 类型 流水线位置
mReader InputReaderInterface 1. 最上游，从 EventHub 读 RawEvent
mBlocker UnwantedInteractionBlockerInterface 2. 手掌 / 误触抑制（Reader 线程同步执行）
mProcessor InputProcessorInterface 3. motion 分类 HAL（Reader 线程同步执行 + 独立 HAL 线程）

AOSP14 的每个中间 stage（Blocker、Processor）内部都包了一个 QueuedInputListener。它的作用是先把事件缓冲进 mArgsQueue，等 stage 加工完再一次性 flush 给下一站：

Important

为什么要”缓冲 + flush”而不是直接调下一站？ 因为一个进来的事件可能被加工成多个出去的事件。

最典型的就是手掌抑制：一个多点触摸的 NotifyMotionArgs 进来，Blocker 检测到其中某个 pointer 是手掌，会把它拆掉——先发一个把该 pointer 标成 CANCEL 的事件，再发一个剔除该 pointer 后的事件。这种”一进多出”用缓冲队列最自然：加工阶段往队列里塞若干个，最后统一 flush。

这跟 AOSP16 的 TracedInputListener（纯装饰器，只加 ATRACE）是完全不同的东西

AOSP14 的 QueuedInputListener 既是缓冲器，也顺带加了 ATRACE（traceEvent），一物两用。

  • InputReader 线程内的事件流是 同步接力（Blocker、Processor 都在 Reader 线程跑）；
  • InputProcessor 旁路一条 "InputProcessor" HAL 线程，只负责调 HAL、更新分类缓存，不参与主事件传递；
  • 事件进入 InputDispatcher 的 mInboundQueue 时才完成 线程切换（通过 mLooper->wake()）；
  • Dispatcher 线程独立地从队列里取事件派发给窗口。

4.5 设计动机：为什么搞这么复杂的链路

早期 Android（~6.0 之前）没有这些中间 stage，Reader 直接调 Dispatcher。后来新需求不断冒出来：

  • 手掌抑制要插在哪里？
  • motion 分类（手/笔/手掌）呢？

每个功能都”想插一腿”，如果都写在一起维护灾难。责任链让每个功能独立成 stage，想加就加、想删就删、想调整顺序就调整顺序，互不影响——这就是”流水线”设计的核心价值。

AOSP14 保留了 Blocker 和 Processor 两个中间 stage；后续版本（AOSP15/16）又往里塞了 InputFilter、PointerChoreographer、InputDeviceMetricsCollector 等更多 stage，但底层的责任链机制完全一样。

把整个 input 系统想象成一家蛋糕工厂，每个 stage 就是流水线上的一道工序：

流水线角色 类比
EventHub 进货口（从 /dev/input 进货”原料”）
InputReader 切配工（把原料 input_event 切成半成品 NotifyArgs）
UnwantedInteractionBlocker 质检员（挑出”手掌误触”这种残次品）
InputProcessor 分类师（标记这块是给”手”还是”笔”吃的，分类异步进行）
QueuedInputListener 工序间的传送带（缓冲 + 一次性放行）
InputDispatcher 发货员（打包通过 socketpair 发给客户窗口）

每个工序独立、链式接力、互不影响——这就是”组装流水线”的完整含义。后续 3.x 节就是把每个工序挨个展开讲。
