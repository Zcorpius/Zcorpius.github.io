WMS/AMS 窗口层级介绍

发表于 2026-08-31 | 分类于 Android ， WMS
字数统计: 13.2k | 阅读时长 ≈ 56

1. 概述

WMS（WindowManagerService）内部用一棵树管理系统中所有的窗口，这棵树的每一个节点都是
WindowContainer 的子类。理解这棵树是理解 WMS 的第一步，因为：

  • Z 轴顺序（谁盖在谁上面）由节点在树中的位置决定；
  • Configuration 分发（屏幕大小、密度、深色模式等）沿树从父到子传播；
  • Surface 层级（渲染合成）按树的结构分配 layer；
  • AMS 侧的 Activity/Task 组织（Task、ActivityRecord）也挂在这棵树上。

本文主要回答五个问题（每题可以先自己口头回答一遍，再展开对照摘要——也是第 7 章自测的预热）：

  1. WindowContainer 到底提供了什么公共能力？（第 2 章）

    答案展开

    它是所有树节点的基类，把“当一个节点”所需的全部能力统一收编：父子关系与 Z 序维护（mChildren 列表头底尾顶）、Configuration 沿树分发（继承 ConfigurationContainer）、Surface 动画与冻结、layer 递归分配（assignChildLayers），外加“孩子的类型由子类填 E”的泛型容器机制。
    一句话：凡能挂上树的东西都是它的子类，节点该有的它全包。

  2. 树上都有哪些节点，各自职责是什么？（第 3 章）

    答案展开

    全局唯一树根 RootWindowContainer 管所有屏；屏侧是 DisplayContent（一块屏）加 DA 家族（DisplayArea/RootDisplayArea/TaskDisplayArea/DisplayArea.Tokens/ImeContainer，即 Feature 分组的层架子）；应用侧一条链：Task（任务栈，extends TaskFragment）→ActivityRecord（一个 Activity，extends WindowToken）→WindowState（真正的窗口）。
    Task 和 ActivityRecord 这两个继承点就是 AMS 嫁接进 WM 树的桥。

  3. 0–36 共 37 个“层”是怎么来的，每种窗口落在哪一层？（第 4 章）

    答案展开

    每个窗口有 type（应用 1–99、系统 2000+），WindowManagerPolicy.getWindowLayerFromTypeLw() 把 type 映射成 0–36 的 policy layer：应用统一第 2 层，壁纸 1、输入法 13、状态栏 15、导航栏 24、圆角装饰 36 置顶。注意层是“区间”不是精确值（一个叶子可占连续多层），且同一 type 可因权限/flag 落不同层（TYPE_SYSTEM_ALERT 无权限 9、有权限 12，装饰窗带 flag 直接顶到 36）。

  4. 这棵树落到一块真实的屏幕上，具体是什么样子？（第 5 章）

    答案展开

    一个日常场景（打开 App、弹 Dialog、键盘弹起）里同屏 6 个窗口，各是树上一片 WindowState 叶子：壁纸挂 Leaf:0:1，应用链走 TaskDisplayArea → Task → ActivityRecord，键盘进 ImeContainer，状态栏/导航栏各进 15/24 层的 Leaf 格子。两条读树规律：同一个盒子里兄弟顺序定谁盖谁（Dialog 排主窗口后）；盒子挂在哪层、整盒就压在哪些层上。

  5. 怎么用 dumpsys 在真机上把这棵树读出来、逐层验证？（第 6 章）

    答案展开

    adb shell dumpsys activity containers 输出整棵树，节点格式 #下标 名字:层区间 type=… mode=… bounds=[…]，下标大的在上。读法：从 Leaf:36:36 往下扫到 Leaf:0:1，0–36 每层都有节点认领、无空洞无重叠；再把实际窗口、任务和 Binder token 对回各自的容器。配合第 7 章“先预测、再 dump”的实验法逐层验证。

2. WindowContainer：窗口树的基类

2.1 类定义与设计意图

WindowContainer 是窗口树上所有节点的公共基类 ：

  • WMS 里凡是能挂上树的东西（屏、任务、令牌、窗口本身……）都是它的子类。
  • 做一个树节点 所需的全部公共能力（父子关系、Z 序维护、配置分发、动画、layer 分配）都由这个类统一提供。

设计意图就藏在注释第一句：“Defines common functionality for classes that can hold windows directly or through their children in a hierarchy form”。 即为“能持有窗口”的类提供公共能力。注意“持有”分两种方式，正好对应树上两类节点：

  1. 直接持有：孩子就是窗口。如 WindowToken 的孩子是 WindowState ，走到它这里就到叶子了；
  2. 间接持有：自己不挂窗口，但沿子树往下走最终会到达窗口。如 RootWindowContainer 只是树根，窗口都在它子树深处的叶子上。

注释第二句是给 AOSP 贡献者的硬性约定：修改本类必须同步维护并运行 WindowContainerTests。它是整个窗口体系的基石，一处改动波及全树。

回到类声明。这一行从左到右有三个信息点：泛型 E、父类、四个接口，逐一拆开。

① 泛型 E——孩子的类型

E 只用在一个地方——mChildren：

基类不知道“孩子会是谁”，于是把决定权下放给子类：子类继承时把 E 填成具体类型，ArrayList<E> 就实例化成“只装这种孩子”的列表，装错类型编译期就被挡下。三个实际源码里的填法：

类声明（均为实际源码） mChildren 实际是 语义
RootWindowContainer extends WindowContainer<DisplayContent> ArrayList<DisplayContent> 树根下挂各块屏
WindowToken extends WindowContainer<WindowState> ArrayList<WindowState> 令牌下挂窗口
TaskFragment extends WindowContainer<WindowContainer> ArrayList<WindowContainer> 孩子既可能是 ActivityRecord 也可能是嵌套 Task，只能填公共父类

附带收益是取孩子免强转：WindowToken 遍历孩子时可以直接写 final WindowState win = mChildren.get(i);。

Important

不要把 E extends WindowContainer 认成 Java 教科书里的自限定泛型（CRTP）：Enum<E extends Enum<E>> 的 E 回答“我是谁”，这里的 E 回答“孩子是谁”。WindowState extends WindowContainer<WindowState> 填“自己”只是巧合——窗口的孩子恰好还是窗口（子窗口）；WindowToken 自己是 WindowToken，填的却是它的孩子 WindowState。E 永远回答“孩子是谁”，从不回答“我是谁”。

② 父类 ConfigurationContainer<E>——每个节点持有一份配置

树上每个节点都有自己的 Configuration（屏幕尺寸、密度、方向、深色模式……），父节点配置变化时沿树向下 onConfigurationChanged 分发，孩子可自行 override。这是“分屏里两个 Activity 配置可以不同”的实现基础（详见 2.4）。

③ 四个接口——除了当容器，这个节点还能干什么

接口 职责
Comparable<WindowContainer> 同树任意两个节点可比较 Z 序（compareTo，WindowContainer.java:2554）：兄弟按 mChildren 下标，非兄弟上溯到公共祖先再比较分叉点的下标。这让“谁上谁下”有了统一定义，是 addChild(E, Comparator) 排序插入、动画按 Z 序遍历孩子的基础
Animatable 树节点可参与窗口动画（由 SurfaceAnimator 驱动）

最后补两个初读 E 时最容易卡住的点 ：

  • E 划下的约束究竟约束谁
  • ArrayList<WindowState> 这个类型从何而来。

E extends WindowContainer 保证的是：孩子一定是树上的合法节点。这不是限制子类，而是基类自己的需要，方法体里到处是对孩子的“节点级”操作，孩子不是 WindowContainer，这些调用就编译不过。

但上界只划了最宽的范围，具体能装什么，看子类把 E 填成了什么——通常比上限严得多：

其次，源码里没有人写过 ArrayList<WindowState> mChildren。E 只是基类里的占位符：子类写下 extends WindowContainer<WindowState> 时，编译器把基类里所有的 E 都替换成 WindowState，这和把 x = 3 代入 f(x) 是一回事：

注意 ArrayList<E> 里叠着两层泛型：

  1. 外层尖括号是 ArrayList 自己的参数，回答“这个列表装什么类型”；
  2. 内里的 E 是 WindowContainer 的占位符，由子类来填。

ArrayList 说“我装 E”，E 被填成 WindowState，ArrayList<E> 就随之成了 ArrayList<WindowState>。

2.2 两个核心成员

两个要点：

  1. mParent 是 private 的：必须经 setParent() 设置，因为换父节点时还要同步执行 Configuration 级联更新（孩子要继承新父亲的配置）。
  2. mChildren 的顺序 = Z 轴顺序：列表头部在下层、尾部在上层。这是整棵树最重要的不变量，所有关于“谁盖谁”的操作最终都落到对这个列表顺序的维护上。

版本差异：Android 13 中 mChildren 的类型是 WindowList<E>；AOSP 15 已删除
WindowList 类，直接用 ArrayList<E>（wm 目录下已无 WindowList.java）。

2.3 树操作核心方法

以下方法均定义于 frameworks/base/services/core/java/com/android/server/wm/WindowContainer.java：

方法 作用
setParent(WindowContainer) 换父节点，同时级联更新 Configuration
addChild(E, Comparator<E>) 按 Comparator 找插入点加孩子（系统窗口按 layer 比较入位）
addChild(E, int) 指定下标加孩子
removeChild(E) 移除孩子
positionChildAt(int, E, boolean) 调整孩子到指定 Z 序位置（POSITION_TOP=Integer.MAX_VALUE、POSITION_BOTTOM=Integer.MIN_VALUE）

另外 forAllWindows(...) 系列按 Z 序（从顶到底或反之）遍历子树中的所有 WindowState，是 WMS 中查找窗口的主力手段（如焦点查找、输入派发目标确定）。

2.4 父类：ConfigurationContainer

WindowContainer extends ConfigurationContainer<E>——树上每个节点都持有自己的 Configuration（窗口容器配置：屏幕尺寸、方向、密度……），父节点配置变化时沿树向下 onConfigurationChanged 分发，孩子可以选择 override。这就是“分屏里两个 Activity 配置不同”、“DisplayArea 级别禁用挖孔”等的实现基础。

4.1 层从哪来

每个 WindowState 有一个窗口类型 type（WindowManager.LayoutParams.type，应用窗口 1–99，系统窗口 2000–2999），WMS 通过 WindowManagerPolicy.getWindowLayerFromTypeLw(type, canAddInternalSystemWindow, roundedCornerOverlay) 把 type 映射成 layer（0–36 的整数）。

几个容易忽略的细节：

  • 同一 type 的 layer 并非固定：TYPE_SYSTEM_ALERT 有内部权限是 12、没有是 9，防止三方冒充系统弹窗压在 APPLICATION_OVERLAY 之上。
  • 层是“区间”不是“精确值”：一个容器节点可以占据连续多层（如 Leaf:18:23），窗口进树时按自己 type 的 layer 落到对应节点。
  • 层 ≠ 最终 Surface z：assignChildLayers()（WindowContainer.java）是按树序重算 SurfaceControl layer 的常规主路径；needsZBoost、IME 相对 layer、Starting Window 和动画 leash 等专门逻辑还可能改写最终结果。树结构是理解这些规则的基础，但不能把它单独当成唯一依据。

5. 窗口层级显示

前四章把“类”和“层”分别讲完了，但它们终究是两张抽象的图：一张类谱、一张 0–36 的层号表。本章把两者叠到一块真实的屏幕上。看一个普通的使用瞬间，这棵树是怎么“显示”出来的。读完本章再回头看第 3 章的职责表，每个类都应该能在眼前浮现出对应的画面。

5.1 屏幕上看得见的日常窗口

场景取最日常的一个：你打开一个 App，它弹出一个 Dialog，你点了 Dialog 里的输入框，键盘弹起。此刻这块屏上可数出壁纸、主窗口、Dialog、输入法、状态栏和导航栏 6 个实际窗口；它们都由 WindowState 表示，也都是叶子。

图里还有两处“看不见但在”的：

  • 壁纸：处于第一层，被主界面完全盖住，dump 里仍能看到 ImageWallpaper 挂在 Leaf:0:1 。
  • 键盘压住应用、又被状态栏压：在 policy layer 的粗粒度顺序中，2 < 13、13 < 15。跨 layer 的关系由此确定；同 layer 或父子窗口之间的最终前后关系仍取决于容器树、兄弟顺序和子窗口 sublayer。IME 还具有专门的 layer 分配处理。

这棵树就是图一的收纳结构图。三条读图规律，每条都能在图上指认：

  1. 同一个父容器里，兄弟顺序影响谁盖谁。本例中主窗口与标准 Dialog 同为 ActivityRecord 的直接孩子；同 layer 时，兄弟列表中排在后面的 Dialog 盖在主窗口之上。另一类情形是 PopupWindow（TYPE_APPLICATION_PANEL）、选项菜单浮层（TYPE_APPLICATION_ATTACHED_DIALOG）等子窗口：它们才会挂成主窗口 WindowState 自己的孩子，并通过子窗口 sublayer 排序。这正是 3.1 节强调 WindowState E = WindowState 的原因。
  2. 盒子挂在哪个 layer 区间，决定跨层的粗粒度前后关系。状态栏压得住应用，与它多宽、放多高无关，关键在于它的 WindowToken 位于第 15 层对应的 DA，而应用位于第 2 层的应用区。进入同一 layer 后，仍要继续看容器树和兄弟顺序。
  3. 盒子 = 一组窗口的命运共同体。ActivityRecord 把主窗口及其子窗口归到同一 Activity 之下。这样就一起可见、一起动画、一起随 Activity 切换；再往上，Task 整体就是最近任务里飞进飞出的那张卡片。若此刻分屏，DefaultTaskDisplayArea 下会站着两个 Task，各领半屏的 Configuration（2.4 节的基础）。

最后把类一个个钉到屏幕上：

抽象的类 在这块屏上它是什么
DisplayContent 整块屏幕的“画框”，屏上所有东西都装在它里面
DisplayArea.Tokens 系统 WindowToken 的收纳格；按 layer 映射安放，一个格可覆盖连续层区间（状态栏格、导航栏格……）
ImeContainer 键盘专用的收纳格
TaskDisplayArea 划给应用的那片区域

WindowToken 系统窗口的“户口”：一组相关窗口的容器，统一承载其可见性与动画命运

于是 2.1 节类注释里那句 “can hold windows directly or through their children“ 可以翻译成屏幕语言了：

  • ActivityRecord 可直接持有主窗口和标准 Dialog；PopupWindow 等附着子窗口则通过主窗口这一层间接归属 ActivityRecord；
  • Task、TaskDisplayArea、DisplayContent 则“袋中有袋”，一层层往下才摸到窗口。

6.1 dumpsys 命令

输出即 RootWindowContainer 的树形 dump。节点格式：

  • #下标 名字:最小层:最大层 type=… mode=… bounds=[…]。
  • #N 是孩子在 mChildren 中的下标 .

由于尾部在上的规则，#0 在最底层、下标越大越靠上层。例如 Leaf:0:1 表示该叶子占据第 0–1 层，Leaf:16:16 只占第 16 层。

6.4 按层区间解读这份手机 dump

37 层骨架没有空洞

从树顶向下合并同类容器，可得到完整的层覆盖：36、32–35、26–31、24–25、18–23、17、16、15、13–14、3–12、应用层 2、0–1。它们正好覆盖 0–36；其中 3–12 是一个连续叶子、0–1 也是一个连续叶子，因此不要误以为 dump 必须每一层各有一个 Leaf:N:N。

DefaultTaskDisplayArea 没有 :2:2 后缀，却正是应用层的专用容器。应用窗口的 policy layer 都是 2，所以它和 Leaf:0:1、Leaf:3:12 一起把低层区域接满。这也是“树的节点形态”与“层区间”必须结合读的例子。

Feature 是分组壳，叶子才接住窗口

HideDisplayCutout、OneHanded、FullscreenMagnification、WindowedMagnification 是 DisplayAreaPolicy 按功能包出的区间容器：启用挖孔隐藏、单手模式或放大时，可以整体变换其子树，而不用逐个移动窗口。

同名节点在不同层区间反复出现并不重复。例如 FullscreenMagnification 分别包住 0–12、15、17、18–23、26–27、29–31、33、34–35；这是其他 Feature 的例外层把连续区间切开后的结果。窗口真正挂在 Leaf:*、DefaultTaskDisplayArea 或 ImeContainer 下。

两个特别有用的反向验证来自本机 dump：

  • Leaf:24:25 直接挂在 WindowedMagnification 下，没有 FullscreenMagnification 包裹，说明导航栏相关层被排除在全屏放大之外；
  • 17 层的 NotificationShade 没有 HideDisplayCutout 包裹，16 层却有，说明通知面板与状态栏相关层的挖孔处理路径不同。

用 type 对回落点

dump 中的 type 实际窗口 预期 policy layer dump 中的落点
2011 InputMethod 13 ImePlaceholder:13:14 下的 ImeContainer

Leaf:24:25 同时容纳第 24 与第 25 层：Taskbar（type=2019，policy layer 24，#0）在下，EdgeBackGestureHandler0（type=2024，policy layer 25，#1）在上。DisplayArea.Tokens 会按 WindowToken.getWindowLayerFromType() 的结果排序 token，所以这里 #0/#1 是 layer 24/25 排序后的结果，不是“同一 Leaf 中任意兄弟只靠下标排上下”。只有 policy layer 相同的 token，才进一步由同一父容器中的兄弟顺序细分。

ScreenDecorOverlay 也显示为 type=2024，却不在 24–25，而在 Leaf:36:36。它带有圆角装饰的私有标记，命中 4.1 的特殊分支，直接映射到 getMaxWindowLayer()。因此，type 是重要索引但不是唯一条件；权限和 flag 同样可能改变最终层。

6.5 从任务、空节点和 Binder 读运行状态

应用侧：列表顺序就是前后台关系

DefaultTaskDisplayArea 的孩子从 #0 到 #5 排列。由于尾部在上，#5 Task=233 的 MatrixAgent LauncherActivity 位于这组任务的最上方；其下依次能看到 Home 根任务、QQ Music、Bilibili 和 Operit 的任务容器。Task=1 是 Home 根任务，真正的桌面 Activity 位于其内部的 Task=70。

Task=223 下同一个 ActivityRecord 有两个 WindowState，说明它在本次快照中挂了两个窗口；而 Task=222 只显示 ActivityRecord，没有继续显示 WindowState。这只能说明该快照里的窗口容器挂载状态不同，不能仅凭这一点断言 Activity 是否存活或可见。

最下方的 Task=3 → Task=5 / Task=4 带有 MULTI-WINDOW 及相应 bounds，但没有 Activity 子树。把它理解为当前树中保留的任务容器即可，不能据此把这次画面判定为正在分屏；是否真正可见还需结合 dumpsys activity activities 或窗口可见性字段。

空叶子与 token 身份

  • 空叶子：如 Leaf:16:16、Leaf:18:23、Leaf:28:28。DisplayArea 的 37 层骨架在 Display 创建时就已建立，窗口出现时才把 token 放入对应格子；空叶子正好证明“架子”和“窗口”是两回事。
  • 有 token、没有 WindowState：ShellDropTarget 的 token 已被注册，但当前没有窗口孩子。拖放目标只在特定交互期间显示，这是合理的瞬时状态；诊断时应结合前后两次 dump，而不是把它当作坏树。
  • Binder 与 BinderProxy：输入法 token 为 android.os.Binder，通常表示由 system_server 内部服务代建；状态栏、通知面板、任务栏、屏幕装饰等为 BinderProxy，表示 token 来自外部进程的 Binder 对象。它们描述的是 token 的进程边界，不是窗口层级高低。

7.1 记忆总结

L0：本模块在 WMS 全图中的位置

本模块只回答一个问题：WMS 用一棵什么样的树管理所有窗口，Z 序、Configuration 和 Surface 层级为什么都由这棵树决定？

  1. 树由一个基类统一供能。 凡能挂上树的东西都是 WindowContainer 的子类：父子关系与 Z 序维护（mChildren 头在下、尾在上）、Configuration 沿树分发、Surface 动画与冻结、layer 递归分配，外加“孩子的类型由子类填 E”的泛型容器机制。
  2. 家族分两半。
    1. 屏侧是 RootWindowContainer → DisplayContent 与 DA 家族（RootDisplayArea/TaskDisplayArea/DisplayArea.Tokens/ImeContainer）搭出的层架子；
    2. 应用侧一条链 Task → ActivityRecord → WindowState。Task extends TaskFragment、ActivityRecord extends WindowToken 两个继承点，就是 AMS 嫁接进 WM 树的桥。
  3. 层由 type 映射而来。 窗口 type 经 WindowManagerPolicy.getWindowLayerFromTypeLw() 映射成 0–36 的 policy layer：应用统一第 2 层，壁纸 1、输入法 13、状态栏 15、导航栏 24、圆角装饰 36 置顶；同一 type 可因权限/flag 落不同层。
  4. 树落到屏幕上就是窗口叠层。 “打开 App、弹 Dialog、键盘弹起”的日常瞬间，同屏 6 个窗口各是树上一片 WindowState 叶子：壁纸挂 Leaf:0:1、应用链走 TaskDisplayArea、键盘进 ImeContainer、状态栏/导航栏各进 15/24 层的 Leaf 格子。
  5. 这棵树可以用 dumpsys 读出来。 adb shell dumpsys activity containers 按 #下标 名字:层区间 输出整棵树，下标大的在上；0–36 每层都有节点认领、无空洞无重叠，可把实际窗口、任务和 Binder token 对回各自的容器逐层验证。

Warning

容易把下面几件事混为一谈：

  • 把 mChildren 顺序当成“先加的在上”（实际头在下层、尾在上层）；
  • 把泛型 E 当成回答“我是谁”的自限定泛型（它只回答“孩子是谁”）；
  • 把 policy layer 当最终 Surface z（assignChildLayers() 是树序分层的主路径，但 Z-boost、IME 相对 layer、Starting Window、动画 leash 等还有专门处理）；
  • 把层当精确值（层是区间，一枚 Leaf:3:12 可同时装第 7 层 Toast 和第 11 层悬浮窗）；
  • 把空 Leaf 当成“这一层不存在”（37 层骨架建屏时就有，窗口出现才把 token 放进格子）；
  • 把 Task/ActivityRecord 当成 WM 树之外的额外对象（它们靠继承嫁接，所以 dumpsys activity containers 能同时看到任务和窗口）。

L1：必须能展开的模块骨架

下面五句是本章的“生成器”。无需逐字背诵；标准是每句都能展开成类关系、层号映射或 dump 实例。

  1. WindowContainer 把“当一个树节点”所需的全部能力统一收编：mChildren 顺序即 Z 序（全树最重要的不变量）、compareTo 让任意两节点可比上下、Configuration 沿树向下分发、assignChildLayers 递归分配 Surface 层级。
  2. 全树 = 屏侧架子 + 应用侧链：
    1. DisplayContent（is-a RootDisplayArea）之下，Feature 壳与 Leaf 格子收纳系统窗口
    2. TaskDisplayArea → Task → ActivityRecord → WindowState 收纳应用窗口（WindowToken 直接持窗、Task 一族间接持窗）。
  3. type 经 getWindowLayerFromTypeLw() 映射 0–36：
    1. 应用 1–99 统一 APPLICATION_LAYER=2；
    2. TYPE_SYSTEM_ALERT 无内部权限 9、有权限 12（防止三方冒充系统弹窗压过 APPLICATION_OVERLAY）；
    3. 带圆角装饰 flag 直接返回 getMaxWindowLayer()=36。
  4. 屏幕读树三条规律：
    1. 同一盒子里兄弟顺序定谁盖谁（Dialog 排主窗口后）；
    2. 盒子挂哪个 layer 区间、整盒就压在哪些层上（状态栏 15 压应用 2，与窗口位置大小无关）；
    3. 盒子是一组窗口的命运共同体（ActivityRecord 同进同出，Task 是最近任务里飞进飞出的卡片）。
  5. dump 读法：
    1. #N 是孩子在 mChildren 中的下标、下标越大越靠上；
    2. 四个锚点，沿锚点向上向下扫，其余节点不易迷失。
      1. 壁纸 Leaf:0:1 最底
      2. 应用在 DefaultTaskDisplayArea（第 2 层）
      3. 输入法 ImePlaceholder:13:14 → ImeContainer
      4. 装饰 Leaf:36:36 置顶

Important

必须同时记住的 AOSP 15 事实：

  1. WindowList 类已删除，mChildren 直接是 ArrayList<E>；
  2. 每屏共 37 层（0–36，层 0 保留未用）；层是“区间”不是精确值；
  3. assignChildLayers() 按树序完成常规 Surface 分层，层号是窗口进树与 token 排序的重要索引；Z-boost、IME 相对 layer、Starting Window 和动画 leash 等专门路径仍可能调整最终 Surface z。

L2：只需快速定位的细节

以下细节需要时应能在本文 30 秒内定位，不要求死背：

  • 0–36 每层对应的窗口 type 完整对照表（4.2 节）；
  • 同一 type 因权限/flag 落不同层的全部分支：TYPE_SYSTEM_ALERT 9/12、TYPE_SYSTEM_OVERLAY 10/23、圆角 flag 36（4.1、4.2 节）；
  • compareTo 非兄弟节点上溯公共祖先再比分叉下标的细节（2.1 节）；
  • 各 Feature 壳（WindowedMagnification/HideDisplayCutout/OneHanded/FullscreenMagnification）的分组语义与同名节点多段出现的原因（6.4 节）；
  • Dialog 与 PopupWindow 的挂点差异、子窗口 sublayer 排序（5.2 节）；
  • 常用 dumpsys 命令组合与“先预测、再 dump、再 diff”实验法（6.6 节）。

7.2 基础自测

类与泛型

  1. mChildren 列表的头尾各是哪一层？这被称为整棵树最重要的什么？

    答案展开

    头在下层、尾在上层——mChildren 的顺序即 Z 序；这是整棵树最重要的不变量，所有“谁盖谁”最终都落到对列表顺序的维护上（2.2 节）。

  2. 换父节点为什么必须走 setParent()，不能直接改 mParent？

    答案展开

    mParent 是 private 的；换父要级联更新 Configuration（孩子继承新父亲的配置），直接赋值会漏掉这步（2.2/2.3 节）。

  3. TaskFragment、TaskDisplayArea 为什么把 E 填成 WindowContainer，而 WindowToken 填 WindowState？

    答案展开

    前两者的孩子类型不唯一（Task 下既有 ActivityRecord 也有嵌套 TaskFragment，TaskDisplayArea 下既有 Task 也有子 TaskDisplayArea），只能填公共父类；WindowToken 的孩子只有 WindowState（2.1 节）。

  4. WindowState extends WindowContainer<WindowState>——填“自己”意味着什么？

    答案展开

    窗口可以有子窗口（PopupWindow、附着式对话框等），“窗口套窗口”（3.1 节）。

  5. 这里的 E 回答的是“我是谁”还是“孩子是谁”？和 Enum<E extends Enum<E>> 有何区别？

    答案展开

    “孩子是谁”。Enum<E extends Enum<E>> 的 E 是“我自己这种类型”（自限定/CRTP），这里的 E 与自身类型无关（2.1 节）。

家族与职责

  1. Task 和 ActivityRecord 分别继承哪个 WM 容器类？为什么说这两个继承点是 AMS/WMS 的桥？

    答案展开

    Task extends TaskFragment、ActivityRecord extends WindowToken。AMS 的任务/Activity 组织因此天生具备 WM 容器能力，两个世界共享同一棵树——dumpsys activity containers 能同时看到 Task 和窗口的原因（3.2 节）。

  2. ImeContainer 的 layer 分配有什么特殊处理？

    答案展开

    常规、未由 Organizer 接管的场景中，ImeContainer 先忽略普通的 layer 分配；DisplayContent 会在满足条件时把它相对 mImeLayeringTarget 置于 +1。无合格 target、分屏或 Surface 父节点变化时会走回退/专门路径，因此不能把“总是贴在目标正上方”当成无条件规则（3.2 节）。

层级体系

  1. TYPE_SYSTEM_ALERT 有/无 INTERNAL_SYSTEM_WINDOW 权限分别落第几层？为什么故意不同？

    答案展开

    无权限第 9 层、有权限第 12 层——防止三方冒充系统弹窗压到 APPLICATION_OVERLAY（第 11 层）之上（4.2 节）。

  2. ScreenDecorOverlay 的 type 是 2024（正常应落第 25 层），为什么出现在 Leaf:36:36？

    答案展开

    它设置了 PRIVATE_FLAG_IS_ROUNDED_CORNERS_OVERLAY，映射函数的特殊分支直接返回 getMaxWindowLayer() = 36（4.1 节）。

  3. “层是区间不是精确值”怎么理解？同一个 Leaf:3:12 里可能同时装着哪些层的窗口？

    答案展开

    一个叶子容器可占据连续多层（节点名 min:max 即占领声明）；Leaf:3:12 内可同时有第 7 层的 Toast、第 11 层的悬浮窗。共享同一 Leaf 不会把 layer 压平：DisplayArea.Tokens 会先按 token 的 policy layer 排序，所以 Toast 在悬浮窗下；只有 policy layer 相同，才继续由兄弟顺序细分（5.2、6.4 节）。

屏幕与树

  1. 标准 Dialog 和 PopupWindow 在树上的挂点有何不同？各自靠什么盖住主窗口？

    答案展开

    Dialog 是 ActivityRecord 的直接孩子、主窗口的兄弟，靠兄弟列表在后盖上；PopupWindow 是主窗口 WindowState 自己的孩子（子窗口），靠 sublayer 排在父窗口之上（5.1/5.2 节）。

  2. 键盘为什么压得住应用、又被状态栏压？

    答案展开

    13 > 2、13 < 15——policy layer 的粗粒度顺序是全序，与窗口的位置大小无关（5.1 节）。

读 dump

  1. dump 输出里的 #N 是什么？#0 在最底还是最顶？

    答案展开

    孩子在 mChildren 中的下标；尾部在上，#0 在最底层（6.1 节）。

  2. 输入法的 token 是 android.os.Binder，其他系统窗口多是 BinderProxy，这个差异说明了什么？

    答案展开

    Binder 说明 token 是 system_server 进程内部代建的（输入法由 IMS 代注册）；BinderProxy 说明来自外部进程经 Binder 注册（SystemUI 的系统栏/通知面板等）（6.5 节）。

  3. EdgeBackGestureHandler0 与 Taskbar 同挂 Leaf:24:25，谁在上面？由什么决定？

    答案展开

    EdgeBackGestureHandler0（type=2024，policy layer 25，#1）在 Taskbar（type=2019，policy layer 24，#0）之上。两者同在 Leaf:24:25，但先由 DisplayArea.Tokens 按 policy layer 24/25 排序；#0/#1 是这一排序的 dump 结果。若两个 token 的 policy layer 相同，才由兄弟顺序决定细粒度上下（6.4 节）。

7.3 场景追问

  1. 先弹一个已授 SYSTEM_ALERT_WINDOW 的悬浮窗，紧接着弹一个 Toast，dump 里它们会落进同一个节点吗？为什么？

    答案展开

    对 6.2 的这套默认策略会。悬浮窗是 TYPE_APPLICATION_OVERLAY（type=2038，第 11 层），Toast 是 TYPE_TOAST（第 7 层），两者都落进 Leaf:3:12——十层共用一枚叶子，是“层是区间不是精确值”的实证。但 DisplayArea.Tokens 会先按 policy layer 排序，Toast 仍在悬浮窗下；只有相同 policy layer 的 token 才再由兄弟下标分上下。设备可替换 DisplayAreaPolicy，所以不能把 Leaf:3:12 当成所有设备都固定存在的节点（4.2、6.4 节）。

  2. 下拉通知面板前后各 dump 一次，树里会新增节点吗？

    答案展开

    对 6.2 这台设备、SystemUI 未重启且该 token 已存在的前后两次 dump，通常不会：NotificationShade 的 WindowToken 与窗口已在 Leaf:17:17，下拉主要改变可见性——树管结构，可见性另有状态字段。它不是 WMS 对所有设备和生命周期的保证；SystemUI 重启、窗口/token 重建或设备定制策略都可能让树节点变化（5.2、6.6 节）。

  3. 进入分屏后再 dump，应用区会怎么变？看到带 MULTI-WINDOW 标记的 Task 就能断言正在分屏吗？

    答案展开

    DefaultTaskDisplayArea 下会出现两个 mode=multi-window 的 Task，bounds 各领半屏。但 6.2 节里 Task=3 → Task=5/Task=4 一直带着 MULTI-WINDOW 标记却没有 Activity 子树——它们只是树中保留的容器；是否真正可见还要结合 dumpsys activity activities 与窗口可见性字段（5.2、6.5 节）。

  4. 面试官说“窗口的 policy layer 就是它最终的 Surface Z 序”，这句话哪里不准确？

    答案展开

    policy layer 不是最终 Surface Z，但也不只是可忽略的“粗粒度标签”：它决定 token 的 policy 顺序；即使多个 layer 共用一个 Leaf，DisplayArea.Tokens 也会先按 getWindowLayerFromType() 排序。相同 policy layer 再看兄弟顺序，父子窗口还受 sublayer 影响。assignChildLayers() 按树序完成常规 Surface 分层，但 Z-boost、IME 相对 layer、Starting Window 和动画 leash 等专门路径仍会影响最终结果（2.3、4.2、6.4 节）。

  5. dump 里 Leaf:16:16、Leaf:18:23 是空的，ShellDropTarget 有 token 却没有窗口孩子——这棵树坏了吗？

    答案展开

    没有。37 层骨架建屏时就已建好，窗口出现时才把 token 放进对应格子，空叶子恰好证明“架子”与“窗口”是两回事；ShellDropTarget 只在拖放交互期间显示，属于合理的瞬时状态，诊断应结合前后两次 dump（6.5 节）。

  6. 同一份 dump 里，Task=223 的 ActivityRecord 下挂两个 WindowState，Task=222 下只显示到 ActivityRecord——能据此判断谁存活谁已销毁吗？

    答案展开

    不能。这只能说明本次快照的窗口挂载状态不同：两个 WindowState 对应主窗口与 Dialog 等多个窗口（5.1 节 QQ 音乐的隐私弹窗正是这种形态）；只显示 ActivityRecord 也不代表 Activity 已死。判断存活/可见要结合 dumpsys activity activities 与可见性字段（6.5 节）。

  7. 要求白纸默画默认屏的 37 层骨架时，应从哪里入手？空叶子要画吗？

    答案展开

    先钉四个锚点：Leaf:0:1 壁纸最底、DefaultTaskDisplayArea 占第 2 层、ImePlaceholder:13:14 → ImeContainer、Leaf:36:36 装饰置顶；再按 Feature 壳从最外层 WindowedMagnification:0:31 向内分段展开。空叶子也要画得出——架子建屏时就有，与窗口无关（6.3、6.4 节）。

  8. 如何用一次“先预测、再 dump、再 diff”验证 type→layer 映射，而不是只背 4.2 节的对照表？

    答案展开

    先写下预测（悬浮窗/Toast → Leaf:3:12；键盘 → ImePlaceholder:13:14 下的 ImeContainer、token 是 Binder），操作前后各执行一次 adb shell dumpsys activity containers 并 diff：新出现的 WindowToken{type=…} 落进的 Leaf 层号与预测互相印证。预测错了回对应章节；预测对了，dump 只是确认（4.2、6.6 节）。

最后对照“熟练掌握”还差三块，对应第 8 章的延伸路线：

  1. 动态主干：一个窗口从 View.addView() 到挂 Leaf:N:N 的完整流——WindowManagerService.addWindow() 的 token 校验、type→layer 映射、找容器、addChild，以及启动 Activity 时是谁在什么时机把 Task positionChildAt(POSITION_TOP) 拉起来。
  2. 树的构建算法：本文画的是算法的输出——这棵 37 层的架子如何被 DisplayAreaPolicyBuilder 按 Feature×layer 区间切分出来，正是续篇《WMS/AMS 层级树创建》的主题。
  3. 最后一公里：assignChildLayers() 如何把树序换算成 SurfaceControl 的 layer 值，即从树到屏幕像素的终点。

三块补完，再回头白纸默画一棵不带注释的骨架树，一次成型——这时候“熟练掌握”四个字才算立住。

8. 小结与延伸路线

一张图记住全文：

  • WindowContainer = 树节点公共能力（父子关系、Z 序列表、Configuration 分发、动画、layer 分配）；
  • DisplayArea 树 = 系统窗口的层架子，由 DisplayAreaPolicy 在建屏时按 Feature×layer 构建；默认可信主屏策略有 5 个 Feature，设备/厂商策略可不同；
  • Task/ActivityRecord = 应用侧组织，整体作为“第 2 层”嫁接到 DA 树上；
  • WindowState = 一个真实窗口；通常是末端节点，但也可以承载子窗口。

延伸阅读（按依赖顺序）：

  1. 窗口添加流程：WindowManagerService.addWindow() → 按 layer 找 Tokens/Task → addChild；
  2. WindowToken/ActivityRecord 的 token 校验机制（addWindowToken、ActivityRecord.Token）；
  3. DisplayAreaOrganizer（WindowOrganizer 体系）：外部如何操控 DA；
  4. assignChildLayers → SurfaceControl 合成：从树到屏幕像素的最后一公里；
  5. WindowContainerTests（frameworks/base/services/tests/wmtests/）：本文涉及行为的单测，改树相关代码前必读。
