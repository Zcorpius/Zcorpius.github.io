第 1 章 C++ 语法层：虚函数到底做了什么

1.1 没有虚函数的世界：静态绑定

1.2 virtual：把”选函数”推迟到运行期

给函数加上 virtual，语义就从”编译期定死”变成”运行期按对象的实际类型选“：

两条铁律（C++ 多态的触发条件，缺一不可）：

  1. 函数必须是 virtual（或 override 了某个 virtual）；
  2. 必须通过指针或引用调用。直接拿对象本身调用（obj.notifyMotion()）不触发动态绑定——因为对象本身就是完整类型，没有”隐藏身份”可言（详见 2.3）。

inputflinger 全链路都靠这两条铁律运转：mInnerListener 是引用（满足第 2 条），notifyMotion 是纯虚函数（满足第 1 条）。

1.5 vtable / vptr：编译器替你生成的函数指针表

虚调用在机器层面怎么实现？C++ 标准没规定，但所有主流编译器（GCC/Clang/MSVC）用的方案一致：每个多态类一张虚函数表（vtable），每个对象里一个表指针（vptr）。

对照静态绑定的 call 固定地址：虚调用多了两次内存间接寻址 + 无法内联。代价明细：

静态绑定（普通函数） 动态绑定（虚函数）

这就是为什么 NotifyArgs 一族故意不用虚函数（第 3.3 节详述）：input 事件是每秒成百上千条的热路径，AOSP 用 std::variant + std::visit 换掉了虚分派，把”每事件一个虚对象”改成”扁平数据 + 一次 switch 分发”。机制没有好坏，只有合不合场景——这是贯穿本专栏的态度。

最后一条关键事实：vptr 在构造时写入，一生不变。UnwantedInteractionBlocker 对象出生那一刻，它的 vptr 就指向 Blocker 的表，之后无论被什么样的引用接住（InputListenerInterface&、InputListenerInterface*），查表查到的都是 Blocker 的实现。”对象是什么”在构造时已定，虚调用只是运行期读取这个事实的手段。

第 1 章讲了零件。现在把 inputflinger 真实代码放上手术台，逐条指令跟踪”事件从 Reader 出门到 Dispatcher”途中的每一次函数选择。

  • notify 本身：静态绑定，永远执行基类这一份（入口统一）；
  • 它内部的 notifyMotion(args)：虚调用，且 this 还是原来的对象——查 vtable 落到实际派生类（出口随对象变）。

“入口固定 + 出口可变”，这个惯用法叫 NVI（Non-Virtual Interface，非虚接口），是 Template Method 模式的现代变体。基类掌握流程骨架（”收到 variant → 分发到对应虚函数”），派生类只填实现，不给它改流程的机会。

三次选择 × 三站转发，没有任何一站”知道”全局路线。每站只知道：我手里的引用接着谁，我就调谁。路线图分散在构造期接好的三根引用里——这就是第 0 章问题的完整答案。

第 3 章 设计模式层：机制之上搭结构

3.1 四层分工：语法机制 / 多态能力 / 设计模式 / 架构

前两章拆完了零件，现在把镜头拉远。inputflinger 里”虚函数与设计模式”的关系，可以精确地切成四层：

层 是什么 inputflinger 中的对应
语法机制 C++ 语言规定的写法 virtual、= 0、override、vtable/vptr（第 1 章）
多态能力 语法机制买到的运行期行为 通过接口引用调用 → 按对象实际类型执行（第 2 章）
设计模式 语言无关的结构约定：谁持引用、谁实现、怎么串 本章的五个模式
架构 模式组合成的系统骨架 Reader → Blocker → Processor → Dispatcher 流水线

分层的判别方法（第 0 章的 acid test）：把类图画在纸上——设计模式看得见；把 virtual 关键字删掉——模式还在，只是运行期转不动了。模式活在”持有接口引用 + 实现同一接口”这个结构关系里，虚函数只是让结构动起来的零件。

一个澄清：GoF 的 23 个模式里没有一个叫”虚函数模式”。设计模式的前提恰恰是多态——GoF 两人写书时（1994）假设的语言就是 C++ 和 Smalltalk，开篇即讲”针对接口编程，不要针对实现编程”。可以说：多态是模式的燃料，模式是烧燃料的发动机排列方式。

3.2 构造期接线：Decorator 与职责链

接线现场

注意一个精妙的结构事实：每个中间站自己就是 listener（继承接口），同时手里还握着一个 listener（组合引用）：

“is-a 接口 + has-a 接口”，一进一出——这就是它能站在流水线中间的全部资格。

这是什么模式？

从构造形态看，是 Decorator（装饰器）：同一个接口的层层包裹、从里向外建造、每层持有内层的引用。GoF 的 Decorator 意图原文是”动态地给一个对象添加一些额外的职责”——Blocker 给 Dispatcher 添加了”过滤掌纹”的职责，Processor 添加了”分类”的职责，接口（InputListenerInterface）不变，调用方（Reader）无感知。

从数据流向看，是 Pipes and Filters（管道-过滤器，POSA 卷 4）：事件像流体流过一系列过滤器，每个过滤器可以改写（加 classification 标签）、丢弃（掌纹判定为手掌 → 不往下游送）、拆分（一进多出）数据。纯 Decorator 是”透明增强”不该改数据语义，而 input 的中间站明确在改数据——所以 AOSP 文档自称 input pipeline，取的是管道语义。

从”谁能终止处理”看，带一点 Chain of Responsibility（职责链）：GoF 的 CoR 里每个 handler 可以决定”我处理完就到此为止”。InputDispatcher::notifyMotion 就是终点消费者；而 policy 截胡（interceptMotionBeforeQueueing 判定事件不该给用户）时事件也在 Dispatcher 手里终止，不再向前。

三个名字都对，各取一个侧面。真实系统里的模式几乎总是这种杂交体——教科书给你纯种，工程给你混血。贴哪个标签不重要，重要的是结构带来的性质：

  1. 增删站零成本：想旁路 Blocker？第 ④ 行改成 *mDispatcher，三行构造改一行，flush() 及所有下游代码一个字不动。
  2. 各站互不知情：Blocker 不知道后面是 Processor 还是 Dispatcher；Processor 不知道前面是谁。站与站之间只认 InputListenerInterface，不认具体类——依赖接口，不依赖实现（GoF 第一原则）。
  3. 顺序即构造顺序：想调整过滤次序，改构造顺序即可，不改任何站的代码。

为什么必须”从里向外”造

包裹式构造有个天然约束：造外层之前，内层必须已存在（引用要接一个活对象）。所以 ①②③④ 的顺序不能颠倒——这不是风格问题，是 C++ 引用语义强制的（引用不可空、不可重绑， InputListenerInterface& mInnerListener 只能在构造时接一次，接完终身不变）。

反过来这也成了文档：读 InputManager 构造函数的顺序，就是数据流的方向。构造序 = 流向序，一份代码两份信息。

3.3 Command + Visitor：NotifyArgs 的两副面孔

Command 模式：把”请求”做成数据

GoF 的 Command（命令）模式：把一个请求封装成一个对象，使你可以存储它、传递它、排队它、延迟执行它。看 NotifyMotionArgs 的素颜：

纯数据，零函数——“某设备某时刻发生了一次什么动作“这个请求的完整快照。正因为它只是数据，才能：

  • 被 std::list<NotifyArgs> 攒成一整批（processEventsLocked 的 out）；
  • 被塞进 QueuedInputListener::mArgsQueue 延迟放行（锁纪律，见 3.4）；
  • 被 splice 剪接在四层函数间零拷贝流转；
  • 全程带着 id 被延迟追踪（LatencyTracker 算端到端延迟）。

Command 的本质就一句话：把”要做的事”从”栈上的调用”变成”堆/队列里的数据”。 函数调用过去了就没了；命令对象可以等、可以看、可以数。

如果 notify* 是直接转发（没有缓冲），持锁的 Reader 会一路同步调进 Blocker → Processor → Dispatcher::notifyMotion → policy → IMS → WMS——而 WMS/IMS 的一部分接口（getScanCodeState、getInputDevices…）会反过来调用 InputReader（InputReader.cpp:233-239 的原注释写明了这个死锁场景）。此刻若还持着 mLock，就是自锁；别的线程持上游锁等 mLock，就是互等。

3.5 Active Object：mInboundQueue + eventfd + Dispatcher 线程

同步链的终点，异步世界的起点

第 2 章的调用链到 InputDispatcher::notifyMotion（dispatcher/InputDispatcher.cpp:4291）为止。仔细看它与其他站的不同——它不再往任何 mInnerListener 转发：

对照 POSA2 的 Active Object 六件套

Active Object（主动对象，《Pattern-Oriented Software Architecture Vol.2》）的意图：把方法调用与方法执行解耦到两个线程，调用方永不阻塞。标准件与 inputflinger 实物的对照：

Active Object 标准件 职责 inputflinger 实物
Proxy（代理） 暴露给调用方的接口 InputDispatcher::notifyMotion 这个入口本身
Method Request（方法请求） 把”一次调用+参数”固化成对象 MotionEntry（args 的全部字段搬进 Entry）
Activation Queue（激活队列） 存放待执行请求 mInboundQueue（std::deque）
Scheduler（调度器） 决定何时取哪个请求 dispatchOnce 的取队逻辑（+ ANR 超时排序 mAnrTracker）
Servant（仆役） 真正干活的实现 Dispatcher 线程上的 dispatchOnceInnerLocked → dispatchMotion → publishInputEvent
Future（期货） 异步取结果的凭据 没有——输入事件 fire-and-forget，无人等返回值

启动侧的对应（InputDispatcher.cpp:753）：

这个模式买到了什么

  1. 调用方永不被服务方的慢拖住。notifyMotion 的工作量严格有界（校验+入队+一次 write 系统调用）；此后”找窗口、发 socket、等 App 回 ACK、ANR 判定”这些耗时不可控的活全在另一个线程。App 卡死一万年，Reader 线程照常睡它的 epoll_wait——整个系统的输入采集不会因为一个烂应用停摆。
  2. 天然串行化。请求进队列、单线程按序消费，Dispatcher 内部大部分状态不需要加锁竞争（只在入队/取队两个瞬间碰 mLock）。
  3. 请求排队带来调度自由。Scheduler 可以按策略插队/丢弃：app switch 事件加速（enqueueInboundEventLocked 里对 isAppSwitchKeyEvent 的特殊处理）、过期事件清理——同步调用做不到这些，因为同步调用没有”排队的未来”。

eventfd 那一写，是本专栏两条线的交汇点：它同时是 Active Object 的线程交接、Reactor（Looper 的 epoll 事件循环）的触发源、也是”虚函数同步链”与”异步世界”的国境线。

第 4 章 模式独立于语法：四种语言里的同一根链条

要证明”设计模式 ≠ C++ 语法”，最硬的办法是把 3.2 节那根链条（接口引用层层相接的 pipeline）用四种语言重写。结构一模一样，语法工具完全不同：

4.1 C++（本尊，对照基准）

特点：选择性加入——你必须逐个函数声明 virtual，不加就退回静态绑定。给了程序员控制权（1.5 节的性能取舍），也给了踩坑的机会（忘写 virtual 的静默 bug）。

4.2 Java：所有方法默认虚

Java 里 virtual 这个概念消失了——除 static/final/private 外所有方法默认动态绑定，且每个类都自动”有 vtable”。语法负担更小，性能控制权更少（JVM 靠内联缓存等方法补救）。GoF 23 个模式后来几乎原样搬进 Java 书里，一张类图都没重画——模式跟着结构走，不跟着关键字走。

4.3 C：没有 class、没有继承、没有 virtual —— 手工搭 vtable

最有说服力的一站。Linux 内核满地都是这套手法（file_operations、proto_ops、驱动的 *_operations）：

语法上一无所有——没有 class、没有继承、没有 virtual——但 b->next->notify_motion(b->next, args) 与 C++ 的 mNext.notifyMotion(args) 在机器码层面是同一条指令序列（取指针、查表、间接 call）。C 程序员手工做了 C++ 编译器自动做的事：手填函数表（= 编译器生成 vtable）、头嵌接口（= 编译器埋 vptr）、显式传 self（= 编译器传 this）。

模式的最小公分母到此现形：所谓多态，就是”数据里存着函数指针，调用时查它”。 继承、interface 关键字、virtual 关键字都只是这件事的语法糖衣。

4.4 Go / Rust：连”继承”都不要了

Go 干脆取消了继承——接口自动满足；Rust 的 dyn Trait 则把”vtable”显式化为胖指针的一部分。两种语言里 3.2 节的 pipeline 类图依然成立，只是”is-a”被”实现了签名”取代。

4.5 本章结论

语言 动态绑定的语法 程序员做什么
C++ virtual + vtable 声明哪些函数参与多态
Java 默认虚 什么都不用做（想关闭反要 final）
C 手填函数指针表 自己当编译器
Go 接口隐式满足 只管实现方法
Rust dyn Trait 胖指针 选择静态分发还是动态分发

四张语法皮，一张结构骨。模式活在类图里（谁持引用、谁实现、怎么串），语言只决定”运行期怎么找到那个函数”。所以学模式的正确姿势是拿掉语法想结构——这就是为什么第 0 章的 acid test 是”删掉 virtual，模式还在”。

第 5 章 总装：从构造期接线到运行期解析的全景

把前四章的零件全部装回同一条时间线上。一次输入事件的完整一生，横跨构造期埋下的结构与运行期兑现的机制：

5.1 构造期：把结构焊死（只发生一次）

此刻还没有任何事件流动，但两样东西已定死：

  • 拓扑（Decorator/职责链）：数据将经过谁、按什么顺序——由三根引用决定；
  • 身份（vtable）：每个对象”是谁”——Blocker 对象永远查到 Blocker 的表。

5.2 运行期：机制逐级兑现（每秒无数次）

一次触摸从内核到 App 的全链路，标注每一跳用的”零件”：

5.3 模式清单结算

模式 在哪一章出场 inputflinger 现场 语法零件
Template Method / NVI 2.1 notify（非虚入口）→ 虚 notify* 非虚函数调虚函数
Decorator / 职责链 / 管道 3.2 InputManager.cpp:62-65 构造链 接口引用层层相接
Command 3.3 前半 NotifyArgs 一族纯数据 struct variant（替代虚 execute）
Visitor（双分派） 3.3 后半 std::visit + 重叠 lambda variant + 虚调用接力
缓冲式 Decorator 3.4 QueuedInputListener（锁纪律） 同接口 + 入队不转发
Active Object 3.5 mInboundQueue + eventfd + Dispatcher 线程 请求对象 + 队列 + eventfd
Reactor 3.5/5.2 EventHub 与 Looper 的 epoll 循环 epoll + eventfd + 回调

七个模式不是各自为政的装饰，而是互相咬合的传动机构：Command 让事件能进队列 → 缓冲 Decorator 决定何时出队 → 职责链决定经过谁 → Visitor/虚函数决定落到哪个实现 → Active Object 决定在哪个线程执行。抽掉任何一个，链条都转不动。

第 6 章 思想实验与自测

先自己答，再展开对照。每题都能在正文找到出处。

Q1（机制）

删掉 InputListenerInterface::notifyMotion 声明里的 virtual 关键字（只删这一个），整条流水线会发生什么？

答案

QueuedInputListener、UnwantedInteractionBlocker 等的 notifyMotion override 立刻编译失败（override 标记找不到可覆写的虚函数——1.4 节的保险丝起作用）。即使顺手把所有 override 也删掉让它编过：所有 notifyMotion 调用退化为静态绑定，mInnerListener.notifyMotion(args) 会试图调用纯虚的基类实现（没有函数体）→ 链接错误或运行期未定义行为。一句话：链条断了，但会在编译/链接期大声报错，而不是静默出错——这正是 override 存在的意义。

Q2（结构）

不修改 flush() 和任何下游代码，只改 InputManager 构造函数，让事件跳过 Blocker 和 Processor 直达 Dispatcher。怎么改？这证明了什么？

答案

证明：路线不存在 flush() 里，存在构造期接好的引用里（3.2 节性质 1）。flush() 只做多态调用，路径由引用的绑定决定——装饰器模式”增删层零成本”的来源。

Q3（运行期）

mInnerListener.notify(args) 这次调用里，一共发生了几次”选择”？各自依据什么？

答案

三次（2.2 节）：① notify 本身——静态绑定，依据编译期类型（非虚）；② std::visit——switch 分发，依据数据内容（variant 持有哪种 NotifyArgs）；③ notifyMotion——动态绑定，依据运行期对象类型（查 vptr/vtable）。入口看编译期、分支看数据、实现看对象。

Q4（设计）

NotifyArgs 用 std::variant + std::visit，而 listener 链用虚函数。同样是”多态分发”，为什么这里用两种不同的机制？

答案

两个轴的类型变化方向相反（3.3 节的取舍表）：事件种类是封闭集（9 种，系统定义，极少变）但分发极高频（每秒成百上千次）→ variant + switch 最优（无堆分配、无 vptr、跳转可优化）；listener 实现是开放集（AOSP15+ 真的加了新站）但”切换”只发生在构造期一次 → 虚函数最优。机制没有好坏，只有匹配不匹配变化的方向。

Q5（并发）

InputDispatcher::notifyMotion 里 needWake = mInboundQueue.empty()——为什么要判断”入队前队列是否为空”才写 eventfd，而不是每次都写？

答案

队列非空说明 Dispatcher 线程已被之前的唤醒、迟早会来消费（或正在消费），再写 eventfd 是重复叫门（3.5 节）。eventfd 的计数语义下多余的 write 只会被下次 read 一次性清掉，不致错但浪费一次系统调用。这是”叫醒一个已经在干活的人没有意义”的工程化表达——也顺便解释了为什么 eventfd 比条件变量更适合这里：不怕丢失的”至少一次”唤醒。

Q6（跨语言）

用 C 语言（struct + 函数指针，4.3 节）重写这条链时，哪件事 C++ 编译器替你做了而 C 程序员必须自己做？至少说出三件。

答案

① 生成 vtable（C 要手写函数指针表并逐个填）；② 在对象里埋 vptr（C 要把”接口”结构体放成员第一位并手工初始化）；③ 调用点查表（C 要手写 next->notify_motion(next, args)，连 this 都要自己传）；④ 类型检查（C 的函数指针签名对不上只有警告，C++ 的 override 直接报错）；⑤ 析构链（C 要手工定义并逐层调用 destroy）。核心是：多态 = 数据里存函数指针 + 调用时查它，OOP 语言只是把这套手工活自动化并加了静态检查。

Q7（综合）

为什么说”write(eventfd) 是本专栏两条线的交汇点”？

答案

往回看，它之前的整条链（flush → visit → 三站虚调用）全部是虚函数机制 + 同步模式的世界，跑在 Reader 线程；往前看，它是 Active Object 的线程交接（请求已入队，执行权移交 Dispatcher 线程）和 Reactor 的触发源（epoll 被唤醒）。一写之前调用栈直连、一写之后两个线程各过各的——机制与模式在此完成一次”权力交接”。

尾声

回到第 0 章的那个问题：”flush() 凭什么知道下一站是 InputDispatcher？”

现在可以给出完整的回答了：它不知道，也不需要知道。构造期，InputManager 用三根接口引用把四个对象焊成链（设计模式负责形状）；运行期，每次虚调用查 vtable 找到实际实现（C++ 机制负责绑定）；每一站重复”入队-放行”的缓冲纪律（锁纪律负责安全）；到 Dispatcher 手里，请求入队、eventfd 一写，执行权跨过线程边界（Active Object 负责解耦）。

分层是为了各司其职：语法给你零件，模式给你结构，约束给你纪律。读任何一段系统代码，把这三层分开问——“这里在用什么机制？搭的什么结构？守的什么约束？”——复杂度就会像洋葱一样一层层退掉。
