Input 启动流程

发表于 2026-08-15 | 分类于 Framework ， Input
字数统计: 6.7k | 阅读时长 ≈ 29

1. 概述

构造阶段结束时，input 系统处于“装配好但没通电”的状态：

  • 流水线的 stage（Reader → UnwantedInteractionBlocker → InputProcessor → InputDispatcher）都已 new 出来并串好；
  • EventHub 的 epoll / inotify fd 已经 open，但没有任何线程在 epoll_wait，所以读不到任何事件；
  • InputDispatcher 的 mInboundQueue 是空的，派发线程还不存在。

start() 要做的，就是把这条流水线通电：拉起两条工作线程（InputReader / InputDispatcher），事件才开始流动。

2. 启动入口：inputManager.start()

2.1 SystemServer 的触发点

构造结束后，SystemServer 在 startOtherServices 里紧接着做两件事：

  • setWindowManagerCallbacks：建立 IMS → WMS 的回调通道（把 WMS 的 InputManagerCallback 注入 IMS），供后续 input 处理过程中“问窗口策略 / 通知 WMS”用（按键拦截、ANR、焦点、指针 layer 等）。它必须在 start() 之前接好——线程一起来就会用到。这条通道的实现在 WMS 侧，留到学 WMS 时再看，这里当成黑盒。
  • inputManager.start()：★ 真正的“通电”，下面展开。

2.3 拉起两条工作线程

InputManager::start() 只调了 mDispatcher->start() 和 mReader->start()中间两个 stage（Blocker / Processor）没有 start()、没有自己的线程，它们的 notify* 同步寄生在 Reader 线程上跑（详见构造篇“线程模型”）。所以整条流水线只有两个线程拥有者。

所以两个线程跑起来后：

  • “InputDispatcher” 线程 → 不停调 dispatchOnce() → 处理 mInboundQueue / mLooper->pollOnce 等待唤醒。
  • “InputReader” 线程 → 不停调 loopOnce() → EventHub.getEvents() → epoll_wait 阻塞等事件 → 读 /dev/input；

“InputDispatcher” 线程 → 持续 dispatchOnce()

“InputReader” 线程 → 持续 loopOnce()

Note

"InputProcessor" HAL 线程不由 start() 启动——它要等后续 setMotionClassifierEnabled 创建 MotionClassifier 时才起（取决于设备有没有注册该 HA L）。所以 start() 只保证 Reader + Dispatcher 两条主线就位。

2.4 为什么先起 Dispatcher 再起 Reader

Reader 一启动就会立刻开始读事件并往下游推**，如果 Dispatcher 还没起来，事件没人接，会丢事件甚至崩溃。先把下游（消费者）准备好，再启动上游（生产者），这是流水线启动的标准做法。

代码里还做了回滚：如果 Reader 起不来（mReader->start() 失败），会把已经起的 Dispatcher stop() 掉，避免留下半残状态。

2.5 启动完成 = “通电”

start() 返回后，input 系统正式从“装配好”进入“运行中”：

start() 之前 start() 之后
流水线 stage 都已 new 好、串好 同左
EventHub fd epoll / inotify 已 open 同左，且有线程在 epoll_wait 了
InputReader 线程 ❌ 不存在 ✅ “InputReader” 在跑 loopOnce
InputDispatcher 线程 ❌ 不存在 ✅ “InputDispatcher” 在跑 dispatchOnce
事件流 ❌ 静止 ✅ 开始流动：/dev/input → Reader → 流水线 → Dispatcher → 窗口

也就是说，start() 是 input 系统从“静”到“动”的分水岭。从此刻起，EventHub 开始 poll 设备节点，一旦用户触摸 / 按键，事件就会顺着第 3 章的链路流向应用窗口。

2.3 openDeviceLocked：把一个节点变成 Device

先厘清两个概念：

  • “节点” = Linux 内核的 evdev 字符设备节点 /dev/input/eventX（devicePath 指向它）。本质是一个文件，用户态只能 open()/read()/ioctl()，本身不含”这是什么设备、怎么解析”的知识。
  • “Device” = EventHub::Device 结构体，EventHub 在用户态为这个节点建的内存对象——把 fd 包起来，再加一整套解析输入事件所需的元数据：
    • id/path/identifier（身份）
    • classes（能力分类）
    • keyBitmask/absBitmask/...（能力位图）
    • configuration/keyMap/virtualKeyMap（配置与键位映射）、
    • associatedDevice（共享电量/灯效）
    • videoDevice（关联触摸视频）。

openDeviceLocked就是主要实现，make_unique<Device>(fd, deviceId, path, identifier, ...) 是分水岭。主要有八个流程：

2.6 冷启动首批设备注册时序

要点：

  • 注册是”两段式”的：EventHub 的 openDeviceLocked 结束时设备只存在于 EventHub 的表里；必须等 DEVICE_ADDED 回到 Reader、InputDevice+mapper 建好，这个设备才算”可用”

    两段之间到达的真实事件会被 processEventsForDeviceLocked 的”查无此设备”守卫丢弃；

  • 一次冷启动、三种下游通知各司其职：

    • NotifyDeviceReset（清手势状态，走流水线）
    • NotifyConfigurationChanged（刷 meta/policy，走流水线）
    • NotifyInputDevicesChanged（通知 app，policy 直连）；

  • epoll 从 2 个 fd变成 2+N 个 fd ，其中 N 是添加的设备梳理。

3. 运行时：事件从设备节点到窗口

3.1 总览：一次触摸的三段旅程

设备注册完之后，系统进入”运行时”——用户一碰屏幕，一条事件就沿着这条路流到窗口：

贯穿全流程的是 3 条线程，主事件流只穿越其中 2 条：

线程 监听 工作 角色
“InputReader” epoll_wait（EventHub） 解析事件、跑 Blocker/Processor 生产者
“InputDispatcher” Looper.pollOnce（内部也是 epoll） 算窗口、派发 消费者
“InputProcessor” HAL 异步 Motion 分类 旁路（可慢 1~2 帧）

整个流程只有一次线程切换：事件在 Reader 线程一路同步流到 InputDispatcher.notifyMotion（入队 + wake()），之后才切到 Dispatcher 线程真正派发。下面按这条路线逐段展开。

3.2 内核 input_event 到 RawEvent

EventHub 对上游唯一的取数口是 getEvents(timeoutMillis)，一个 for(;;) 循环每轮四步：

关键点：

  • epoll_wait 是锁外阻塞（mLock.unlock() 之后才调，没事件就无限睡，持锁睡会拖死所有想拿 mLock 的线程。
  • 只有 1 个 epoll 实例（mEpollFd），注册了 2+N 个 fd：inotify + wake pipe 读端 + N 个设备节点。三类唤醒源对应三种结果：
    • 设备 fd 可读 → read() 出 struct input_event 数组 → 填成 RawEvent；
    • inotify fd 可读 → 插旗 mPendingINotify，末尾处理设备增删；
    • wake pipe 可读 → 排空管道 + awoken=true，尽快返回。
  • 超时到点（pollResult==0）→ 空手返回，让 loopOnce 的超时分支接手。

3.2.1 getEvent 读到的数据

read() 读出来的是内核结构体 struct input_event，这里逐字段翻译成 inputflinger 的 RawEvent ：

  • when = 事件发生时刻（内核打的单调钟时间戳）
  • readTime = 读到它的时刻，两者差值 = 事件在内核缓冲里积压了多久（输入延迟观测点）；
  • type/code/value 原样拷贝
  • deviceId/readTime 是 inputflinger 自己补的

3.2.2 一次触摸不是”一个事件”，是”一串事件”

触摸的原始数据是一组以 EV_SYN 收尾的 input_event（EV_ABS 坐标、EV_KEY BTN_TOUCH、EV_SYN 帧尾）。getEvents 把它们整批读出返回，processEventsLocked 再把”同一设备的这一串”整包交给 mapper，才能拼出一次 DOWN/MOVE 的完整语义。

3.3 RawEvent 到 NotifyArgs

“InputReader” 线程反复跑 loopOnce()，一轮 = 睡 → 干 → 推。这是典型的单线程事件循环（Event Loop） 即 监听（epoll_wait 睡）和 工作（解析/推送）在同一个线程里交替，没有独立的工作线程：

好处是单线程天然保证事件顺序、少加锁；代价是处理必须快、不能阻塞 。所以”可能慢/会阻塞”的活（HAL 分类、派发）都被扔到别的线程或异步做。

InputReader 持有自己的 mQueuedListener 包住下一站，这个 listener 就是构造链里的 UnwantedInteractionBlocker。与下游 stage 的差别只在缓冲来源：下游 stage 的 notify* 由上游在锁外调用、边收边入队；

而 Reader 的加工产物在锁内累加成局部 std::list<NotifyArgs>，解锁后先处理设备通知/手写笔手势，再 notifyAll() 把整批塞进 mQueuedListener，最后 flush() 一次性放行——“锁内生产、锁外推送”的规矩由这一收一放保证。

processEventsLocked 区分两类事件：

  • 真实的 input_event，按 deviceId 路由到对应 InputDevice，由其 InputMapper 集合（KeyboardInputMapper、MultiTouchInputMapper、JoystickInputMapper 等）解析成 NotifyKeyArgs / NotifyMotionArgs 等；
  • 合成事件：DEVICE_ADDED → addDeviceLocked；DEVICE_REMOVED → removeDeviceLocked，并产出 NotifyInputDevicesChangedArgs。

3.3.1 分批与路由：外层 out 怎么攒

真实事件按”同设备连续“向后合并成一整批再交设备——一次触摸是十几条 EV_ABS/EV_KEY 报文 + 1 条 EV_SYN 收尾，拆散了下游 mapper 就拼不出完整的一次 DOWN/MOVE 语义：

processEventsForDeviceLocked 只做查表路由：mDevices.find(eventHubId) → device->process(rawEvent, batchSize)；查无此设备（”搭台”未完成或已拆台）直接丢弃并告警返回空。

注意满篇的 out += ... 不是循环 push_back——它是 std::list<NotifyArgs> 的自定义运算符，实现是 splice 剪接：把右边的链表整个接到左边末尾，O(1)、零元素拷贝。产物在四层函数间流转全程只挪指针。

3.3.4 数据怎么走到 Dispatcher

mQueuedListener.flush() 没有任何 IPC、没有线程切换——mInnerListener.notify(args) 就是虚函数调用，构造期的层层包裹此刻兑现为调用链，全程跑在 InputReader 线程上：

三个要点：

  1. 每站同款结构：Blocker / Processor 各持一个自己的 QueuedInputListener，都是”锁内加工 + 入队、锁外 flush”——Reader 的”锁内生产、锁外推送”规矩（§3.3 开头）在下游逐站重演。
  2. 终点不再转发：Dispatcher::notifyMotion 只做四件事（校验 / policy 截胡 / 入 mInboundQueue / 写 eventfd）就返回。它的工作量有界——绝不等 App、不等窗口，所以 Reader 线程不会被下游拖住。
  3. eventfd 是线程边界：write(eventfd) 那一刻起，事件所有权从 Reader 线程移交给 Dispatcher 线程（它在自己的 Looper 上被唤醒）。此后找焦点窗口、socket 发送、等 ACK 都与 Reader 无关——Reader 已经回去睡下一轮 epoll_wait 了。

loopOnce() 一轮 = 取事件 → 解析 → 推送，三步走，比 Dispatcher 简单得多（无命令队列 / ANR / 空闲判定）：

解析（processEventsLocked）和推送（mQueuedListener.flush）都在拿到事件的这一轮内同步完成；中间 stage（Blocker / Processor）寄生在 Reader 线程上，无自己的线程

3.5.3 InputChannel：socketpair 派发到应用

派发到目标窗口走的是 InputChannel 。一对 channel 由 socketpair 创建：

  • server 端被 InputDispatcher 持有在对应窗口的 Connection 中；
  • client 端通过 Binder 返回给应用进程，由 WindowInputEventReceiver（基于 MessageQueue 的 epoll）监听可读事件。

InputDispatcher 派发时调 InputPublisher::publishMotionEvent → InputChannel::sendMessage ：

事件发出去 ≠ 派发完，Dispatcher 要等应用回执才派发下一个：

  • 应用处理完通过 InputConsumer::sendFinishedSignal 回执；Dispatcher 收到后把对应事件从该连接的 waitQueue 移除（doDispatchCycleFinishedCommand）。
  • 不回执 → 超时 → ANR：应用一直不回 ACK，mAnrTracker 到期就会触发 ANR。
  • 具体机制（fd 注册、命令队列、流控细节）等剖析 InputDispatcher 类时再展开。

4. 完整启动与运行

一次触摸 motion 事件从设备节点到应用进程的过程按时间轴展开，重点是 3 个线程之间的切换：

读图要点：

  • 只有 2 条主线 + 1 条旁路线程：主事件流穿越 InputReader 线程 和 InputDispatcher 线程（中间 Blocker / Processor 全部同步寄生在 Reader 线程）；IInputProcessor HAL 是异步旁路（分类可慢事件流 1~2 帧）。
  • 唯一的线程切换在 ③：事件一路同步流到 InputDispatcher.notifyMotion（这时仍在 Reader 线程），它只把事件压进 mInboundQueue 并 wake()，真正派发在 Dispatcher 线程的 dispatchOnce 里完成。
  • 出口是 socketpair：Dispatcher 算好目标窗口后，经 InputChannel.sendMessage 把事件扔进 socketpair，应用进程的 WindowInputEventReceiver 读出后交给 View 树。
