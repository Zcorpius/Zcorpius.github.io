inputflinger 学习笔记配图规范(graphviz)

以 input_classes_java_jni.dot 为基准样例。新增/修改任何图,先读本规范。

1. 通用约定

# 渲染命令(dpi=140,与现有图一致)
dot -Tpng -Gdpi=140 <name>.dot -o <name>.png

# 查布局坐标(对齐/位置核查必备)
dot -Tplain <name>.dot | awk '$1=="node"{print $2, "x="$3, "y="$4, "w="$5}'
  • 不要 graph 大标题(label/labelloc/fontsize=20 都不写),图的说明放 md 正文;
  • 图例放右上角,与首节点同排(做法见 §5.4);
  • splines=ortho 正交折线——所有边横平竖直、直角转弯(Visio/UML 工具效果)。
    代价:不能带边标签(ortho 下标签会破坏路由),成员名一律放框内成员行表达;
    箭头(onormal/diamond/vee)在 ortho 下渲染正常(已放大核查);
  • 字体三处都要设:graph / node / edge 均为 fontname="Noto Sans CJK SC";
  • 成员字号 11;
  • 一张图只讲一个层次/主题,渲染后宽高比控制在 ≤1.5(太宽说明该拆图了);
  • 内容以当前 AOSP14 源码为准:类名/成员/继承关系先 grep 源码头文件核实再落笔,
    不写”与 6.0 差异/AOSP14 新增”之类的版本对比标注;
  • 能由框内成员行表达的关系不画边(如各级的 mQueuedListener/mThread/mPolicy 持有),
    边只画:实现、接口继承、组合、必要的关联——边越少越整齐。
  • 类关系完整正确优先于布局美观:先按源码把该画的边定死(持有=◆,裸指针/引用
    =vee,实现=虚线空心三角),再做布局;布局修复只允许动 invis 排序边,绝不允许
    删语义边换对齐(reader 图教训,用户明确批评过)。

3. 节点模板

类(实线圆角边框)与接口(虚线圆角边框 + «interface»),shape=plaintext + HTML 表格:

XXX [label=<
    <TABLE BORDER="1" CELLBORDER="0" CELLSPACING="0" CELLPADDING="0" COLOR="#边框色" STYLE="ROUNDED">
      <TR><TD HEIGHT="4" BGCOLOR="#表头色"></TD></TR>                        ← 顶部垫条(表头色)
      <TR><TD BGCOLOR="#表头色"><B>类名</B></TD></TR>                        // 类
      <TR><TD BGCOLOR="#表头浅色">«interface»<BR/><B>接口名</B></TD></TR>    // 接口
      <TR><TD HEIGHT="2" BGCOLOR="#表头色"></TD></TR>                        ← 表头下间隔条
      <TR><TD ALIGN="LEFT" BGCOLOR="#行色"> - 成员 : 类型</TD></TR>          ← 文字前加一空格
      <TR><TD ALIGN="LEFT" BGCOLOR="#行色"> + 方法()</TD></TR>
      <TR><TD HEIGHT="4" BGCOLOR="#行色"></TD></TR>                          ← 底部垫条(行色)
    </TABLE>>];

框样式要点(实测踩坑,勿改回):

  • 必须 CELLPADDING="0" + 上下同色垫条 + 成员行文字前加一空格——若用 CELLPADDING="3",
    TD 底色只画到单元格边界,与边框之间会留一圈白缝(表头色带比边框窄);

  • FIXEDSIZE 等宽必须配首行 TD WIDTH="表宽-2":FIXEDSIZE 只固定外框尺寸,TD 的
    BGCOLOR 仍按内容自然宽度绘制且左对齐,右侧留”(声明宽−自然宽)”的白竖条(实测
    native 图各框 22~49pt,140dpi 下肉眼明显)。加上 WIDTH 后单列列宽撑满,全部底色
    行两侧各留 1pt 线宽,与不设 FIXEDSIZE 的框观感一致;

  • 圆角(ROUNDED)保留:顶满的色带方角会略微溢出圆弧(140dpi 下约 3px,肉眼几乎不可见),
    这是”圆角+填满”的固有取舍,已确认接受;若改直角则完全贴合但失去圆角观感;

  • TABLE BGCOLOR 的填充会跟随圆角(可用于整框单色场景),但 TD 的 BGCOLOR 永远是直角矩形。

  • 每框成员 3~5 行为宜;类型中的 </> 写成 &lt;/&gt;,& 写成 &amp;;

  • 过长的类名可用 <BR/> 断行(如 UnwantedInteraction-<BR/>Blocker);

  • 纯文字说明行(如”(实现者 NativeInputManager,见图 X)”)允许,但不做版本对比;

  • 同一列的框必须等宽对齐:给 <TABLE> 加 FIXEDSIZE="TRUE" WIDTH="N"(单位 pt),
    N 取该列最大自然宽度(dot -Tplain 的 w×72)再加少量余量,并给首行垫条 TD 加
    WIDTH="N-2"(原因见框样式要点)。不设等宽时,列内框
    宽度不一,中心/边缘都参差;设等宽后中心对齐即边缘对齐,错位产生的 L 形折线
    也会自然变回纯横/纯竖线。渲染时的 “fixed table size with unspecified height”
    警告无害,忽略即可。

4. 边语义(UML,三种 + 可选关联)

语义 写法
实现接口 [style=dashed, arrowhead=onormal, constraint=false]
接口继承接口 [arrowhead=onormal, constraint=false]
组合(持有) [arrowtail=diamond, dir=both, arrowhead=none, constraint=false](菱形在持有方)
关联/引用(少用) [arrowhead=vee, constraint=false]

一律不写边标签(ortho 不支持);哪条边对应哪个成员,靠目标框或持有框的成员行说明。

5. 布局控制(踩坑记录,最重要的一节)

5.1 UML 语义边必须 constraint=false

UML 箭头方向是”子 → 父”,与 dot 默认排序方向(边起点在上、终点在下)相反。
不给语义边关掉 constraint,接口会被排到实现类下方、再被 rank=same 拉平,
整张图被压成横向长条(实测 5993×1317 的教训)。

5.2 纵向次序用 invis 边显式串联

语义边全部失能后,排序交给一条隐形链,方向自上而下:

IMS -> NIS [style=invis];
NIS -> NI  [style=invis];
NI  -> NIM [style=invis];

多列布局必须再加同排平边固定列序:dot 的 x 排序只按交叉数,不认”列”的概念,
不加平边的话同一排的节点会被甩到任意横向位置(实测”实现类”被推到 18in 开外)。
native 图的做法——每排用 invis 平边串出”接口|实现|辅助”的顺序:

{rank=same; RIF; READER; EHI;}
RIF    -> READER [style=invis];
READER -> EHI    [style=invis];

平边只用相邻节点间的短平边,禁止跨列长平边(reader 图实测教训):跨过中间列的
平边(如 EH -> CI)在 ortho 下会被路由成”起点顶边 → 翻进行间走廊 → 横穿 → 落到
终点顶边”,挂在起点顶边上,与该框原有的竖直边共享侧边分通道,把毫不相干的
邻边贴合点挤偏 ±38pt。语义边齐全时各列本就有树边竖向锚定,平边只留锚定列首尾的
最少量(如 EHI -> ID、IDC -> CI),跨列长平边直接不写。

排布拓扑由关系集决定:一个类的多个直接持有(EHI/ID/CI 之于 InputReader)各占
一列、放同一排,列内纵向成链——列链全部居中,跨列引用边自然走列间空隙。
不要沿用历史排法硬修(reader 图教训:CI 挂 row3 时 IR 三扇出+跨列斜边全乱,
重排为”三持有同排三列”后五条列链 10 端点全部 0.0pt)。

拐点分段法(宽框向远列持有边的落点归中):直连边的落点被 ortho 路由贴到目标框
顶边最左端时,插入一个隐形 point 拐点 W(加入目标同排的 rank=same),把边拆成
持有方 ◆→ W(竖直下落到该排高度)+ W → 目标 [constraint=false](横向短平边,
入目标左侧中部)。两个 constraint 语义必须如上配置,否则 W 会被链式降秩挤进独立
半排,拆分失效(reader 图 IR◆CI 实测)。

5.4 图例固定右上角(三步)

// ① 隐形占位节点(固定宽度)
SP [style=invis, shape=box, fixedsize=true, width=5.77, label=""];
// ② 平边串联:首节点 → 占位 → 图例
IMS -> SP     [style=invis];
SP  -> LEGEND [style=invis];
// ③ 同排
{rank=same; IMS; SP; LEGEND;}
  • 同排平边决定左右顺序,占位宽度决定图例被推多远;
  • 对齐微调:渲染后 dot -Tplain 查图例与目标列最右节点的右缘坐标
    (x + w/2),差多少就把 SP 的 width 减多少,误差收到 ±0.05in 内;
  • 注意:constraint=false 的跨排隐形边不参与 x 坐标分配,拉不动图例,
    只能用占位节点法。

5.5 cluster 慎用

排序边跨 cluster 边界时,dot 会把外层 cluster 画成包住内层的嵌套大框(实测
Java 层框包住整个 JNI 层)。原则:

  • 单层流程图(排序方向与层叠方向一致,如 input_framework.dot):可用 cluster;
  • 类图(排序边纵横交错):不用 cluster,层次感全靠配色;
  • 若确需分组(如 native 图的”四级流水线”框),保证该 cluster 内部的 invis
    排序链自洽、不与外部 cluster 节点同排。

5.6 隐形链边不得与语义边同通道双份(箭头被挤离框中点)

现象:框某侧只挂一条箭头,却不在该侧中点,偏 11~39pt(native 图实测:
IM 顶 +30.5、TH 顶 +27.7、DIF 右 −39)。而 BIF→ILI、EH→EHI 这类”无孪生”边精确居中。

原因:splines=ortho 的正交路由器会给同一对节点之间的每条边分配独立通道,
style=invis 的排序链边也被照样分通道(只是不画)——隐形边占了中间通道,
可见箭头被挤到旁边的通道。

修法:排序链与语义边两端重合时合并为一条,两种情形:

情形 做法 例(native 图)
语义边方向 = 链方向 删 invis 边,语义边去掉 constraint=false 接替约束 IM -> RIF、QL -> ILI、READER -> EHI、DISPATCHER -> TH
语义边方向与链相反 改写为链方向 + dir=back + arrowtail=…(箭头几何位置与正向写法完全一致) IMI -> IM [style=dashed, dir=back, arrowtail=onormal]、RIF -> READER、ILI -> PIF 等
  • 合并后约束边集合与原隐形链逐对等价,实测所有节点中心位移 <1pt,布局不变;
  • 8 个被挤偏的贴合点归 0。残余 ±11~39pt(BLOCKER/PROCESSOR 左侧、IM 扇出绕行边)
    来自其它边绕行竖段穿插同一走廊,属 ortho 固有行为;
  • 罗盘端口(tailport/headport)在 ortho 下被路由器忽略,实测无任何效果,不要用它修对齐;
  • 核查办法:dot -Tsvg 后解析每条边 path 端点坐标,与所属框该侧中点比对(本节数据即由此测得)。

6. 落笔前核查清单

  1. 所有类/接口的存在性、继承关系 → grep 对应头文件确认(记 文件:行号 备查);
  2. 成员名/类型与源码一致(可精简,不可编造);
  3. 渲染 → PIL 查尺寸,宽高比 ≤1.5;
  4. dot -Tplain 查图例/关键节点坐标;
  5. 箭头必须裁剪放大逐一核查——整图缩略时小箭头(空心三角/菱形)不可辨识,
    不可凭 dot 源码语义推断”应该没问题”。做法:按 dot -Tplain 的英寸坐标
    (y 轴自底向上,需翻转到像素坐标)裁剪边密集区域并 2 倍放大另存,逐张目检
    箭头样式与指向(空心三角→被实现/被继承方,实心菱形→持有方,vee→被指向方);
  6. 肉眼看整图:中文无豆腐块、边标签无压字、无横穿全图的长边。
