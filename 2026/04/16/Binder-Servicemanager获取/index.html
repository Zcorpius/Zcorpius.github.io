servicemanager 获取

发表于 2026-04-16 | 分类于 Framework ， Binder
字数统计: 3.3k | 阅读时长 ≈ 15

Note

基于Android 16.0的源码剖析， 本文详细地讲解 getIServiceManager() 流程。

1. 概述

在 Java Framework 层，进程注册服务(addService)与 获取服务(getService) 的过程中，都需要调用 getIServiceManager() 先拿到 ServiceManager 远程代理对象。

所以直接先把 getIServiceManager() 的流程单独拎出来先分析，对于后续的 注册服务(addService)与 获取 服务(getService) 的分析会轻松一些。

Important

Android 15 开始，引入了 BackendUnifiedServiceManager 作为统一中间层，对上屏蔽底层差异（内核 Binder /dev/binder 与 RPC Binder Unix Domain Socket），对下提供客户端缓存能力——获取服务时先查本地缓存，命中则直接返回，未命中才发起 IPC 并更新缓存；注册服务时直接转发，成功后可选写入缓存。以此来减少 IPC 开销。

javaObjectForIBinder 的职责是：将 C++ 的 IBinder 转换为 Java 层的对应对象。它有两种返回结果，取决于 IBinder 的实际类型。从代码中可以看出有两种返回类型：JavaBBinder 与 BpBinder ：

Tip

  1. JavaBBinder 继承自 BpBinder，用于包装 Java Binder 对象，是本地实体。
  2. BpBinder 也继承自 BpBinder，持有 handle 值，是远端代理。

Note

Native 层有一个 sp<IBinder>，但不知道它具体是 JavaBBinder 还是 BpBinder。需要把它转成 Java 层能用的对象返回给 Java。本次调用中获取 handle=0 的 BpBinder，handle=0 就是 ServiceManager。这一步返回的是 ServiceManager 的代理对象 BinderProxy，不是任何具体服务。

也就是说本次调用链中的 BinderInternal.getContextObject() 就是 ServiceManager 的代理对象 BinderProxy

接下来再看 allowBlocking 方法：

核心就做一件事：对 BinderProxy 关闭主线程阻塞警告，然后原样返回。

Important

Android 默认不允许在主线程（UI 线程）做同步 Binder 调用，因为这会阻塞 UI，导致卡顿甚至 ANR。所以 BinderProxy 内部有检测机制。但 ServiceManager 是例外，因为获取 ServiceManager 代理是系统基础设施，必须在任何线程都能用，包括主线程。

唯一不同的，也是流程中最重要的就是 sp<BackendUnifiedServiceManager>::make(sm)，即把 ServiceManager 的 BpBinder 远程代理 sm，传进 BackendUnifiedServiceManager 后被保存为 mTheRealServiceManager。

BackendUnifiedServiceManager 本身继承自 BnServiceManager（BBinder 子类），所以它是一个本地 BBinder，但内部持有远端代理。

从构造函数的实现基本就能看出意图，基本就是把 通过 ServiceManager 查到的各个服务 进行缓存，后续再调 getService 获取代理服务就先从 mCacheForGetService 查，命中了就不需要通过 ServiceManager 走 IPC 了。

这其实和之前的 sCache 功能有点像，不同的是 sCache 是在 Zygote 预加载时期就填充了，而且缓存范围不如 BinderCacheWithInvalidation 。

BinderCacheWithInvalidation 类的具体实现后续再详细剖析，封装完成后回到了 IInterface::asBinder 方法:

这两个是重载方法，一个接受裸指针，一个接受 sp<> 智能指针。做的事完全一样：从 IInterface 接口对象中提取出底层的 IBinder。根据传进来的 iface 类型返回服务端或者客户端的 IBinder。而本次流程中传进来的是已经封装后的本地缓存对象，所以返回的是 BBinder。随后又回调了 javaObjectForIBinder 方法，封装成 BinderProxy 远程代理对象。

Note

  • BBinder：本进程创建的本地对象，自己就是实体
  • BpBinder：代表另一个进程的对象，通过 handle 跨进程通信

BackendUnifiedServiceManager 虽然不是 服务的实体，但它是本进程创建的本地 C++ 对象，所以它是 BBinder。它内部再持有 BpBinder 去跨进程找真正的 ServiceManager。

最后就是通过 IServiceManager.Stub.asInterface 将封装 BBinder(BackendUnifiedServiceManager) 的 BinderProxy 代理对象再次 封装成 AIDL 代理。

也就是说 getIServiceManager 方法最终拿到的是通过 ServiceManagerProxy 的创建的代理类，主要成员变量就是 **mServiceManager**AIDL 代理。真是绕了一大圈啊。。

最后再将上述流程绘制成时序图。先梳理 BinderInternal.getContextObject() 的流程，最后获取到的是 ServiceManger 的 BpBinder 的 BinderProxy 代理对象。

然后是从 BinderInternal.getContextObject() 流程结束后进入 ServiceManagerNative.asInterface 流程，也就是创建 ServiceManagerProxy 的流程：

最后获取到的是封装 BackendUnifiedServiceManager 的 BBinder 的 BindderProxy 代理对象，而BackendUnifiedServiceManager 本身是 BBinder，内部持有 ServiceManager 的 BpBinder 作为 mTheRealServiceManager，还是有点绕哈。

Important

getIServiceManager() 最终获取到的是 ServiceManagerProxy，其内部的 mServiceManager 持有一个 BinderProxy，该 BinderProxy 包装了本进程内的 BackendUnifiedServiceManager（BBinder）。而 BackendUnifiedServiceManager 本身作为本地 BBinder，内部持有 BpServiceManager（封装 BpBinder(handle=0)）作为 mTheRealServiceManager，用于实际的跨进程 IPC 通信。
