Binder 启动

发表于 2026-04-09 | 分类于 Framework ， Binder
字数统计: 3.8k | 阅读时长 ≈ 16

从启动流程上看，servicemanager 是在 Zygote 之前启动的，理论上对应进程的 Binder 创建也是 servicemanager 先执行，但大部分进程都用 Zygote 进程的启动链路，理解后直接能套用到 Android 大部分进程。ServiceManager 反而是单线程特例，能做一个很好的对比。

直接从 Zygote 进程启动开始吧，这是在系统开机时执行，只执行一次。

Zygote fork 出的子进程通过 zygote 进行 fork 后调用 AndroidRuntime 中的 ZygoteInit.nativeZygoteInit() ，最后调到 app_main.cpp 的 onZygoteInit ，来启动 binder 线程池。

还有一种情况是直接通过 app_process 启动的独立进程，不是从 Zygote fork 出来的，则走 onStarted() 实现。

对比如下：

1. 初始化 ProcessState

ProcessState 是 Android Binder IPC 框架中的 进程级单例，负责维护 Binder 的资源、线程、缓冲区和生命周期。

承担以下核心职责：

职责 说明
Binder 驱动管理 打开 /dev/binder（或 /dev/vndbinder），进行版本校验、内存映射
线程池管理 创建、配置 Binder 工作线程池
Handle 映射 维护 handle → BpBinder 的查找表
Context Manager 支持 提供成为 ServiceManager 的能力
Fork 安全 检测 fork 后的非法使用并终止进程

初始化 ProcessState:

这里主要就是做了这几件事：

  1. open binder 驱动 /dev/binder
  2. 设置 binder 最大线程数为15
  3. 调用 binder 的 mmap 方法申请对应的内存，大小为 1M-4k*2

每个进程在 ProcessState 构造时各自 mmap 自己的 binder fd，各自拥有独立的单向接收缓冲区：

  • 每个进程只有一块 mmap，不区分”来自谁”，所有发给该进程的事务数据都往这一块里写
  • 这块 ~1MB 空间是所有对端共享的，所以并发事务多时会争抢空间，这也是 Binder 事务有大小限制的根源
  • 两个进程之间并不是”协商出一块共享内存”，而是各自独立 mmap，通过内核中转

在这里就启动了一个 PoolThread 新线程，传递的 isMain 为 true，表示为主线程创建的。

调用来源 isMain 值 命令
startThreadPool() → spawnPooledThread(true) TRUE BC_ENTER_LOOPER
驱动返回 BR_SPAWN_LOOPER → spawnPooledThread(false) FALSE BC_REGISTER_LOOPER

isMain 区分的是”谁发起创建的这个线程”，而不是 是不是进程的主线程：

  • true = 用户空间主动请求创建的线程（由 startThreadPool() 发起）
  • false = binder 驱动动态请求创建的线程（内核发现线程不够用，下发 BR_SPAWN_LOOPER 命令）

注意：startThreadPool() 创建的新线程本身就是一个全新的子线程，它不是进程的主线程。但它的 isMain 就是 true。

PoolThread 的定义如下：

在 t->run(name.c_str()) 时，通过 pthread_create 创建一个新线程，然后新线程去调用 PoolThread::threadLoop()。

新线程先获取到 IPCThreadState 对象，随后通过 joinThreadPool() 向内核注册自己，然后阻塞在 ioctl 上等待事务，新线程就成为了 Binder 线程池中的一员。

其中IPCThreadState 是 Binder IPC 的线程本地状态管理对象，每个线程有独立的实例，主要负责：

  • 管理 当前线程的 Binder 上下文
  • 处理 线程与 Binder 驱动的交互
  • 管理 事务执行和阻塞等待
  • 支撑 DeathRecipient 回调和 Binder 对象引用计数

简单理解：ProcessState 管理进程级资源，IPCThreadState 管线程级 Binder 状态。

3. Binder 核心循环事件处理

从上面的流程图可以看出：joinThreadPool 是外层循环，getAndExecuteCommand 是单次迭代，talkWithDriver + executeCommand 是迭代内的两步。

getAndExecuteCommand将 talkWithDriver（与内核交换数据）和 executeCommand（处理具体命令）串联起来，并管理线程池的执行计数与饥饿检测。整个 Binder IPC 的接收端就是靠这个循环驱动的。先梳理具体流程，然后再详细分析 talkWithDriver 与executeCommand方法。

3.1. talkWithDriver —— 内核交互的底层方法

talkWithDriver 是用户空间与内核 Binder 驱动之间的唯一通信桥梁。所有 BC_* 命令的发送和 BR_* 命令的接收都通过此方法完成。

3.1.1. 前置检查

检查 binder fd 是否有效。在进程退出或驱动关闭后 mDriverFD 会被置为 -1。

3.1.2. 计算 read/write 需求

3.1.4. ioctl 核心交互

binder_write_read 结构体是用户空间与内核的协议：

ioctl 行为有如下情况：

情况 行为
write_size > 0, read_size > 0 双向交换：发送 BC_* 命令 + 接收 BR_* 命令
write_size > 0, read_size == 0 只发送
write_size == 0, read_size > 0 阻塞等待内核数据
两者都为 0 短路返回（前面已处理）

期间有个特殊情况，那就是 err == -EINTR ，此时表示 ioctl 被信号中断（返回 -EINTR），自动重试。这在 Android 中很常见（如 ART 的信号机制、debugger 信号等）。

3.1.5. 写入确认

其中内核必须一次性消费完 mOut 中的所有数据，否则视为 bug 直接 FATAL。

3.1.6. 读取确认

内核通过 read_consumed 告知写入了多少 BR_* 数据到 mIn 缓冲区。之后调用者通过 mIn.readInt32() 逐条读取命令。

3.1.7. 调用场景

基本调用场景如下：

调用者 doReceive 目的
getAndExecuteCommand true（默认） 正常循环：发送待处理命令 + 阻塞等待内核命令
waitForResponse true（默认） 发送 BC_TRANSACTION/BC_REPLY + 等待 BR_REPLY
flushCommands FALSE 只发送 mOut 中的命令，不接收

3.2. executeCommand —— 内核命令分发处理

executeCommand 是 getAndExecuteCommand 循环中的核心执行方法。它根据内核返回的 BR_* 命令类型，执行对应的处理逻辑，涵盖事务处理、引用计数管理、死亡通知、冻结通知、线程池管理等全部场景。

3.1.2. 调用场景

executeCommand 不仅在 getAndExecuteCommand 中被调用，还在 waitForResponse 的 default 分支中被调用：

调用场景 说明
getAndExecuteCommand 接收端主循环，处理所有 BR_* 命令
waitForResponse 的 default 分支 发送端等待回复时，如果收到 BR_ACQUIRE 等非回复命令，就地在当前线程处理

这意味着一个 Binder 线程在等待回复（waitForResponse）的过程中，也可能被内核”借用”来处理引用计数等轻量命令，甚至处理嵌套的 BR_TRANSACTION。
