Binder 启动

发表于 2026-04-09 | 分类于 Framework ， Binder
字数统计: 12.2k | 阅读时长 ≈ 49

本文以 AOSP 15 为基线，分析普通 Binder（/dev/binder、/dev/vndbinder）在进程中的初始化和线程池启动过程。本文不将 AOSP main 中后续引入的 Binder 冻结状态回调等变化混入 Android 15 调用链。主要涉及：

需要先区分三个概念：

  1. Zygote 父进程本身主要通过 zygote socket 接收创建进程的请求，它不会在 ZygoteInit.main() 中启动普通 Binder 线程池。
  2. 普通应用进程和 system_server 在 Zygote fork 完成后，通过 ZygoteInit.nativeZygoteInit() 启动自己的 Binder 线程池。
  3. servicemanager 不走 app_process，Android 15 中也不使用常规 joinThreadPool() 循环，而是将 Binder fd 接入主线程的 Looper。

1. 不同进程的 Binder 启动入口

Zygote 本身和独立工具进程都是同一个 app_process 程序，走哪条路在进程诞生时由启动参数决定：

三条分叉背后是三个不同的调用者：

① Zygote 本身：init 解析 init.zygote*.rc 的 service 定义，开机时 Service::Start() 以 fork + execv 拉起；secondary zygote 同理。

如 service zygote /system/bin/app_process64 -Xzygote /system/bin --zygote --start-system-server

② Zygote fork 的子进程：普通应用由 system_server 的 ProcessList.startProcess() → ZygoteProcess.startViaZygote() 发起。未使用 USAP 时，请求通过 zygote socket 送到 ZygoteServer.runSelectLoop()，再执行 forkAndSpecialize()；启用 USAP pool 时，可以由预先 fork 的 USAP 执行 specializeAppProcess()。两条路径最终都会进入 ZygoteInit.zygoteInit()。

system_server 是特例，由 Zygote 因 --start-system-server 主动 forkSystemServer()。

③ 独立工具进程：shell 执行 bmgr 等脚本，脚本里 exec app_process ... 把 shell 自己替换成目标 Java 进程。

其中②的常规子进程在 fork 之后不再 exec，它继承 Zygote 已经执行起来的 app_process 镜像，从 fork 返回点继续执行，随后由 handleChildProc() 或 USAP 的 childMain() 引导进 zygoteInit()。它不会再走一次 app_main.cpp::main()。

2.3 fork 防护

ProcessState 在首次初始化时注册三个 pthread_atfork 回调：

之后如果子进程继续访问这个继承的 ProcessState，verifyNotForked() 会触发 fatal。正常 Zygote 设计会避免在父进程中提前创建普通 Binder ProcessState，让普通子进程在 fork 后首次初始化自己的实例。

Important

fork 防护的必要性来自 Binder 驱动的对象模型：驱动以进程（binder_proc）为中心管理引用表、事务缓冲和线程表。普通 fork 不会为子进程创建一套新的 Binder 驱动状态，而且 Binder 接收区还被显式标记为不可随 fork 复制。子进程若继续使用继承的实例：

  • 继承的 fd 指向父进程的 binder_proc，子进程发出的引用计数、事务、死亡通知都会记到父进程账上。
  • Binder 驱动在 binder_mmap() 中为该 VMA 设置 VM_DONTCOPY，所以 fork 时不会把 Binder 接收区映射复制到子进程。子进程即使暂时持有继承的 fd，也没有与之匹配的用户地址接收区。
  • 子进程只剩调用 fork 的一个线程，驱动侧的线程池计数却原封不动，继续使用会导致线程管理错乱。

因此防护的做法是：fork 一发生就在子进程侧关闭继承的 fd 并标记 mForked，之后一旦调用 ProcessState::self() 立即 fatal——用快速失败取代难以排查的静默数据错乱。

3. 启动普通 Binder 线程池

完成 ProcessState 初始化后，startThreadPool() 负责创建 Binder 线程池的第一个工作线程。

3.1 startThreadPool()

它具有以下特征：

  • 同一个 ProcessState 只会执行一次实际启动。
  • 即使 mMaxThreads == 0，调用它仍会创建一个线程，只是输出警告。
  • mMaxThreads 表示驱动可以按需要求用户态补充的线程数，不包含 startThreadPool() 主动创建的这一个线程。

3.2 spawnPooledThread()

t->run() 异步创建并运行新的 PoolThread。这里的新线程不是 Linux 进程最初执行 main() 的线程。

isMain 表示它是否为 Binder 池的 primary/main looper，而不是“是否为进程 main 线程”，也不表示调度优先级：

注意：startThreadPool() 创建的新线程本身就是一个全新的子线程，它不是进程的主线程。但它的 isMain 就是 true。

4. IPCThreadState：线程级状态

IPCThreadState 是 Binder IPC 的线程本地状态管理对象，每个线程有独立的实例，主要负责：

  • 管理 当前线程的 Binder 上下文
  • 处理 线程与 Binder 驱动的交互
  • 管理 事务执行和阻塞等待
  • 支撑 DeathRecipient 回调和 Binder 对象引用计数

简单理解：ProcessState 管理进程级资源，IPCThreadState 管线程级 Binder 状态。

5. Binder 核心事件循环

整体关系如下：

如果 mIn 中还保存着未处理命令，talkWithDriver() 可以不执行 ioctl，getAndExecuteCommand() 直接继续消费现有 mIn。

joinThreadPool() 是外层长期循环，getAndExecuteCommand() 是一次循环迭代；后者再通过 talkWithDriver() 与驱动交换数据，并调用 executeCommand() 处理一条命令。

5.1 getAndExecuteCommand()

getAndExecuteCommand() 将 talkWithDriver()（与内核交换数据）和 executeCommand()（处理适用于通用命令分发器的命令）串联起来，并管理线程池的执行计数与饥饿检测。Binder 池线程和 polling 模式都会通过它处理接收到的命令；发起同步调用的线程则主要在 waitForResponse() 中等待和分发命令。

5.2 talkWithDriver()

talkWithDriver() 是普通 libbinder 的 IPCThreadState 与 Binder 驱动交换命令的集中入口。

executeCommand() 不仅在 getAndExecuteCommand() 中被调用，还在 waitForResponse() 的 default 分支中被调用：

调用场景 说明
getAndExecuteCommand Binder 池/polling 的接收循环，每次取一条命令交给 executeCommand()
waitForResponse 的 default 分支 发送端等待回复时，如果收到 BR_ACQUIRE 等非回复命令，就地在当前线程处理

这意味着一个 Binder 线程在等待回复（waitForResponse()）的过程中，也可能被内核“借用”来处理引用计数等轻量命令，甚至处理嵌套的 BR_TRANSACTION。

5.3.1 BR_TRANSACTION

收到 transaction 后，libbinder 会：

  1. 从 mIn 读取 binder_transaction_data。
  2. 通过 Parcel::ipcSetDataReference() 引用驱动提供的事务数据。
  3. 保存当前线程原有的调用者身份等嵌套调用状态。
  4. 设置 mCallingPid、mCallingUid、mCallingSid 和 transaction flags。
  5. tr.target.ptr 非空时先尝试取得目标对象的强引用，再通过 tr.cookie 找到 BBinder 并调用 transact()；目标为空时调用本进程的 context object。
  6. 同步事务通过 sendReply() 返回；TF_ONE_WAY 事务丢弃 reply，不发送 BC_REPLY。
  7. 恢复进入事务前的线程调用状态。

sendReply() 自己会调用 waitForResponse()，等待驱动确认。因此服务端处理同步调用时，也可能在发送 reply 的过程中继续处理驱动返回的其他命令。

5.3.2 executeCommand() 与 waitForResponse()

不是所有 BR_* 都由 executeCommand() 处理。waitForResponse() 自己直接处理：

  • BR_ONEWAY_SPAM_SUSPECT
  • BR_TRANSACTION_COMPLETE
  • BR_TRANSACTION_PENDING_FROZEN
  • BR_DEAD_REPLY
  • BR_FAILED_REPLY
  • BR_FROZEN_REPLY
  • BR_ACQUIRE_RESULT
  • BR_REPLY

其他命令落入 default 分支，再交给 executeCommand()。这意味着线程在等待同步 reply 时，可能处理引用计数命令、死亡通知，甚至执行嵌套的 BR_TRANSACTION，从而避免某些同步调用链发生死锁。

7.1 记忆总结

L0：本模块在 Binder 全图中的位置

本模块在 Binder 全图中的位置：Binder 在一个进程中如何被初始化，并开始接收事务？

  1. BInder出生路径：Zygote 父进程不启动普通 Binder 池；Zygote 子进程走 onZygoteInit()；独立 app_process 走 onStarted()；servicemanager 走 Looper polling。
  2. 进程级初始化：通过 ProcessState 单例打开 Binder 驱动、校验协议、设置驱动可额外请求的辅助线程数，mmap 本进程的事务接收区（1M-2页面），并注册 fork 防护。
  3. 说明首线程与扩容：之后通过 startThreadPool() 创建一个 primary pooled thread；该线程以 BC_ENTER_LOOPER 注册为 primary looper；驱动不足时返回 BR_SPAWN_LOOPER，用户态创建辅助线程并以 BC_REGISTER_LOOPER 注册。
  4. 落到事件循环：此后线程在 joinThreadPool() 循环中，looper 调用 getAndExecuteCommand()；它经 talkWithDriver() 发起 BINDER_WRITE_READ，再由 executeCommand() 分发通用 BR_* 命令；同步调用的 reply 在 waitForResponse() 处理。

Warning

错误内容：

  • 把 15 说成总线程数；
  • 把 isMain 说成进程主线程或优先级；
  • 认为 Binder 接收区是双方共用的用户态共享内存；
  • 认为 fork 会复制 Binder mmap；
  • 以及把 servicemanager 误说成“没有 Binder looper”。

Important

servicemanager 是贯穿该图的反例：它是 native 独立进程，创建 ProcessState 并成为 context manager，但不执行 startThreadPool()；

它通过 setupPolling() 发送 BC_ENTER_LOOPER，再把 Binder fd 接到主线程 Looper.pollAll()，由回调调用 handlePolledCommands()。

L1：必须能默写的模块骨架

下面五句是本模块的“生成器”。它们不是要逐字背诵；标准是每句都能展开为调用树、因果链或特例。

  1. 判断 Binder 启动路径的关键，是该进程是否执行本进程自己的 app_main.cpp::main()：Zygote 父进程和独立 app_process 会执行，Zygote fork 出来的普通子进程不会。
  2. Zygote 父进程负责预加载、fork 与 zygote socket 循环；它不走 nativeZygoteInit()，所以自身不启动普通 Binder 线程池。
  3. 普通应用和 system_server 在 fork 后进入 ZygoteInit.zygoteInit()，再经 nativeZygoteInit() → AppRuntime::onZygoteInit() → ProcessState::self()->startThreadPool() 启动池。
  4. ProcessState 是进程级单例，负责驱动 fd、协议校验、接收区 mmap、线程池配置和 fork 防护；它不能在 fork 后被子进程继续使用。

必须同时记住的特例：servicemanager 不调用 startThreadPool()。它将 Binder fd 接入主线程 Looper，由 polling 回调处理 Binder 命令；它不是“没有 Binder looper”。

7.2 基础自测

启动入口

  1. 为什么 Zygote 父进程不在 ZygoteInit.main() 中启动普通 Binder 线程池？

    答案展开

    Zygote 的核心职责是预加载并通过 zygote socket 创建子进程，而不是作为普通 Binder 服务端接收事务。它不调用 nativeZygoteInit()；普通应用和 system_server 在 fork 后才由 zygoteInit() 调用该 JNI，最终进入 AppRuntime::onZygoteInit() 启动线程池（1.1、1.2 节）。这样也避免子进程继承父 Zygote 已创建的普通 Binder ProcessState。

  2. Zygote fork 出来的应用进程与独立 app_process 工具进程，分别在哪个回调中启动普通 Binder 线程池？

    答案展开

    前者走 AppRuntime::onZygoteInit()，调用链是 ZygoteInit.nativeZygoteInit() → JNI → onZygoteInit()；后者走 RuntimeInit.nativeFinishInit() → AppRuntime::onStarted()。两者最终都调用 ProcessState::self()->startThreadPool()，区别在于进程是从 Zygote 镜像 fork 出来，还是 exec app_process 后新建运行时（1.2、1.3 节）。

  3. 为什么 Zygote 子进程不会重新执行 app_main.cpp::main()？有哪些例外？

    答案展开

    常规子进程只 fork、不 exec，因此从 fork 返回点继续执行，随后进入 handleChildProc() 或 USAP 的 childMain()，再到 zygoteInit()。--invoke-with 会走 WrapperInit.execApplication() 再次 exec；USAP 则是“预先 fork、收到请求后 specialize”的分支，但最终同样进入 zygoteInit()（1 节）。

  4. system_server 与普通应用启动 Binder 线程池的共同点和区别是什么？

    答案展开

    两者都在 Zygote 子进程中进入 ZygoteInit.zygoteInit()，并经 nativeZygoteInit() → onZygoteInit() 启动普通 Binder 池。区别主要在创建入口：system_server 由 primary Zygote 的 forkSystemServer() 在启动早期创建；普通应用通常由 AMS 通过 Zygote/USAP 请求启动（1.2、1.4 节）。

ProcessState 与 fork

  1. ProcessState 解决哪些进程级问题？为什么它必须是进程级单例？

    答案展开

    它持有 Binder 驱动 fd、接收区映射、线程池配置、handle→BpBinder 映射以及 context manager 状态。这些资源都对应同一个 Binder 驱动进程上下文；同一套 libbinder 再创建一份会使 fd、引用表和线程管理语义混乱，因此通过 std::call_once 只初始化一次（2.1 节）。

  2. ProcessState::self() 与 initWithDriver() 的关系是什么？什么时候必须先调用后者？

    答案展开

    self() 选择编译环境对应的默认驱动，通常是 /dev/binder，VNDK 场景为 /dev/vndbinder。若调用方需要非默认 driver，必须在第一次 self() 前执行 initWithDriver()；单例已按某 driver 初始化后，只允许后续请求同一个 driver，不能切换到另一个设备节点（2.1 节）。

  3. Binder 接收区为什么是 mmap(PROT_READ, MAP_PRIVATE | MAP_NORESERVE)？它是不是两个进程共用的一段用户态共享内存？

    答案展开

    这块区域是目标进程自己的 Binder 事务接收区：内核为目标进程分配事务缓冲，并映射到其用户地址空间；用户态只读解析数据，再通过 BC_FREE_BUFFER 等命令归还。它不是通信双方协商并共同 mmap 的一块用户态共享内存。默认大小为 1 MiB - 2 × page size，大事务和高并发都可能耗尽它（2.2 节）。

  4. 为什么 fork 后不能继续使用父进程已有的 ProcessState？childPostFork() 做了什么？

    答案展开

    继承的 Binder fd 仍关联父进程的 binder_proc，而 Binder 接收区 VMA 又被驱动标记为 VM_DONTCOPY，不会复制到子进程。childPostFork() 因此将 mForked 置为 true、关闭继承 fd 并设为 -1；之后访问该单例会在 verifyNotForked() 处 fatal，以快速失败替代难以诊断的跨进程状态错乱（2.3 节）。

线程池与驱动交互

  1. 默认 Binder 线程池是 15 个还是 16 个线程？

    答案展开

    常规的 kernel-managed 上限是 1 + 15 = 16：startThreadPool() 先主动创建一个 primary pooled thread；BINDER_SET_MAX_THREADS 的默认 15 表示驱动最多还可通过 BR_SPAWN_LOOPER 请求创建的辅助线程数。显式调用 joinThreadPool() 加入的线程不在这个常规计数内，因此“15 就是总线程数”是常见错误（3.1 节）。

  2. startThreadPool() 会不会让调用它的线程进入无限循环？

    答案展开

    不会。它异步创建一个 PoolThread，由这个新线程调用 IPCThreadState::joinThreadPool(true) 进入循环；发起 startThreadPool() 的线程继续执行自身逻辑。只有调用方显式执行 joinThreadPool()，当前线程才会长期停留在 Binder 循环中（3.1、3.2 节）。

  3. isMain == true 是否表示 Linux 进程的 main 线程，或表示调度优先级更高？

    答案展开

    都不是。它表示 Binder 线程池的 primary looper 角色：true 时首次向驱动发送 BC_ENTER_LOOPER，false 时响应 BR_SPAWN_LOOPER 并发送 BC_REGISTER_LOOPER。startThreadPool() 创建的 primary looper 本身仍是一个新子线程，不是进程最初的 main 线程（3.2、4.2 节）。

  4. 从驱动发现线程不足到新 Binder 线程实际可接收事务，完整链路是什么？

    答案展开

    驱动向已有 looper 返回 BR_SPAWN_LOOPER；executeCommand() 调用 ProcessState::spawnPooledThread(false)；新 PoolThread 创建自己的 IPCThreadState，进入 joinThreadPool(false)，将 BC_REGISTER_LOOPER 写入 mOut；首次 getAndExecuteCommand() 通过 BINDER_WRITE_READ 把该命令送到驱动，线程随后成为可调度的 Binder looper（3.2、4.2、6 节）。

  5. mIn、mOut 保存的是什么？业务调用的参数和 reply 又在哪里？

    答案展开

    mIn/mOut 是线程私有的命令流 Parcel，用于承载 BR_*/BC_* 及其元数据。业务事务参数由 binder_transaction_data 指向发送方的 IPC Parcel；收到 BR_TRANSACTION 或 BR_REPLY 后，libbinder 通过 Parcel::ipcSetDataReference() 引用目标进程接收区中的事务数据。二者不能混为同一个 Parcel（4.1、5.3.1 节）。

  6. talkWithDriver() 为什么在 mIn 还没消费完时通常不再 ioctl？为什么也会暂缓发送 mOut？

    答案展开

    mIn 还存在未解析的返回命令时，继续 read 会覆盖或混入现有命令流，因此本轮先在用户态消费。doReceive == true 的该路径也会令 write_size 为 0，避免在“边解析旧输入、边发送新输出”时打乱命令流处理顺序；flushCommands() 使用 doReceive == false，可单独把 mOut 刷给驱动（5.2 节）。

  7. executeCommand() 和 waitForResponse() 如何分工？为什么等待同步 reply 的线程仍可能执行嵌套事务？

    答案展开

    executeCommand() 处理入站事务、引用计数、死亡通知和 BR_SPAWN_LOOPER 等通用命令；waitForResponse() 直接处理 BR_REPLY、BR_TRANSACTION_COMPLETE、BR_DEAD_REPLY 等与本次调用相关的返回值。它遇到其他命令会落入 default 并调用 executeCommand()，包括嵌套的 BR_TRANSACTION；这让同步调用链上的线程可以回调处理工作，降低相互等待导致死锁的风险（5.3 节）。

驱动初始化与特殊模式

  1. open_driver() 在真正 mmap 前做了哪些关键初始化？各自解决什么问题？

    答案展开

    它依次打开 driver fd、通过 BINDER_VERSION 校验用户态与驱动的协议版本、通过 BINDER_SET_MAX_THREADS 设置默认最大辅助线程数 15，并尝试启用 oneway spam detection。随后 ProcessState 才用这个 fd 映射事务接收区；前两步保证“连的是可用且协议匹配的 Binder 驱动”，线程数配置则决定后续动态扩容边界（2.2 节）。

  2. BINDER_SET_MAX_THREADS = 15 能否理解为“这个进程总共只能创建 15 个线程”？

    答案展开

    不能。它只约束 Binder 驱动额外请求的 looper 数，不约束 Linux 进程的所有线程；startThreadPool() 创建的 primary pooled thread 不在这 15 个之内，显式 joinThreadPool() 的加入者也不在常规 1 + 15 估算内。应用的 UI、RenderThread、GC 等普通线程更不受此 ioctl 限制（3.1 节）。

  3. BR_FINISHED 对 primary looper 和辅助 looper 的影响为什么不同？

    答案展开

    executeCommand() 将 BR_FINISHED 转成 TIMED_OUT。joinThreadPool() 只允许 isMain == false 的辅助 looper 因该结果退出；primary looper 保持等待，以确保线程池至少保有由用户态主动创建的基础接收能力（4.2 节）。

  4. flushCommands() 与普通的 talkWithDriver() 调用有何不同？为什么它有时会连续 flush 两次？

    答案展开

    flushCommands() 以 doReceive == false 调用 talkWithDriver()，只写 mOut、不读取新 BR_* 命令，适合在线程不再自然进入驱动时主动送出 BC_FREE_BUFFER 等积压命令。第一次写入后执行的引用释放可能又产生新的 BC_RELEASE 或 BC_DECREFS，所以源码会视情况再 flush 一次（5.2 节）。

  5. IPCThreadState::stopProcess() 做了什么？为什么它不等价于“杀死进程”？

    答案展开

    它先 flush 待发送命令，再将 mDriverFD 置为 -1 并关闭旧 fd，从而停止这套普通 Binder 连接；它本身不调用 exit() 或发送杀进程信号。独立 app_process 路径中，只有目标 Java main() 返回后才会走到该收尾逻辑，之后进程是否结束由外层运行时流程决定（1.3、4.2 节）。

进程类型与上下文管理器

  1. child zygote 为什么不走 ZygoteInit.zygoteInit()，这对 Binder 线程池有什么影响？

    答案展开

    child zygote 走 childZygoteInit()，该方法直接寻找并返回目标类的 main()，跳过 commonInit()、nativeZygoteInit() 等会启动普通 Binder 池的初始化。原因是 child zygote 仍承担派生进程的角色，不应沿用普通应用进程的 Binder 线程池初始化方式（1.2 节）。

  2. /dev/binder、/dev/vndbinder 与 /dev/hwbinder 分别对应什么？本文为什么只聚焦前两者？

    答案展开

    普通 framework 侧 libbinder 默认使用 /dev/binder；VNDK 构建的普通 libbinder 使用 /dev/vndbinder；旧 HIDL/hardware Binder 使用独立的 android::hardware::ProcessState 与 /dev/hwbinder。本文分析的是 android::ProcessState / android::IPCThreadState 这套普通 libbinder，因此不展开 HIDL 的 RPC threadpool（1.6、2.1 节）。

  3. servicemanager 为什么要先 setTheContextObject(manager)，再 becomeContextManager()？

    答案展开

    前者在用户态保存 handle 0 对应的本地 ServiceManager Binder 对象；后者通过 Binder driver 注册自己为 context manager。这样驱动把发往 handle 0 的事务交给该进程时，executeCommand() 的 tr.target.ptr == 0 分支能够分发到这个本地 context object（1.5、5.3.1 节）。

  4. servicemanager 的 setupPolling() 与 joinThreadPool(true) 有哪些共同点和本质区别？

    答案展开

    两者都会发送 BC_ENTER_LOOPER，都能成为 Binder looper。区别是 joinThreadPool(true) 在 Binder 线程自己的循环里阻塞等待；setupPolling() 只完成注册并返回 fd，之后由主线程 Looper.pollAll() 统一等待 Binder fd 和 timerfd 等事件，事件到达时再调用 handlePolledCommands()（1.5、4.2 节）。

  5. 如果 getAndExecuteCommand() 从 mIn 取到的不是它认识的命令，会发生什么？这说明什么？

    答案展开

    executeCommand() 的 default 分支会记录 bad command 并返回 UNKNOWN_ERROR，同时更新 mLastError。这也说明不能把所有 BR_* 都送进该通用分发器：与发起方同步调用直接相关的 BR_REPLY、BR_DEAD_REPLY 等必须由 waitForResponse() 按其调用上下文处理（5.3、5.3.2 节）。

IPCThreadState 与线程池运行状态

  1. IPCThreadState::self() 为什么是线程本地对象，而不是像 ProcessState 一样做成进程级单例？

    答案展开

    ProcessState 管的是全进程共用的驱动 fd、接收区和线程池；而一次 Binder 调用的调用者身份、嵌套事务现场、输入/输出命令流 mIn/mOut、是否为 looper 等，都必须彼此隔离。IPCThreadState::self() 用一个全局 TLS key 保存“每个线程各自的实例”：首次访问时创建，后续同一线程复用，因而并发 Binder 调用不会互相覆盖上下文（4.1 节）。

  2. IPCThreadState 构造时为什么要先持有 ProcessState::self()，并调用 clearCaller()？

    答案展开

    前者建立线程状态与所属进程 Binder 资源的关联，后续与驱动交互、读取线程池配置都通过 mProcess 完成；后者把新线程的 calling pid、uid、sid 等调用者信息恢复为“没有正在处理入站 Binder 调用”的初始状态。只有执行 BR_TRANSACTION 期间，线程才会临时改写这些身份信息，并在处理结束后恢复原现场（4.1、5.3.1 节）。

  3. joinThreadPool() 中 mCurrentThreads、mExecutingThreadsCount 与 mWaitingForThreads 分别反映什么？

    答案展开

    mCurrentThreads 统计已加入 Binder 池的用户态线程；mExecutingThreadsCount 统计当前正在由 getAndExecuteCommand() 执行命令的线程，用于饥饿检测；mWaitingForThreads 表示正在等待可用 Binder 线程的调用者数量，执行线程减少后会通过条件变量唤醒它们。三者不能简单等同于“驱动允许创建的最大线程数”（4.2、5.1 节）。

  4. getAndExecuteCommand() 每次循环做了什么？它和 joinThreadPool() 是什么层级关系？

    答案展开 `joinThreadPool()` 是线程长期驻留的外层循环；每轮调用 `getAndExecuteCommand()`。后者先经 `talkWithDriver()` 获取命令，若 `mIn` 有完整命令则读出一个 `BR_*`，递增执行线程计数，调用 `executeCommand()`，再递减计数并完成饥饿检测/等待者唤醒。一次调用最多分发一条通用命令，余下的 `mIn` 命令会留到后续循环继续消费（4.2、5.1 节）。

  5. Binder 线程池的“饥饿（starvation）”检测在检测什么？它为什么不等于驱动立刻创建新线程？

    答案展开

    libbinder 在执行中的线程数达到 mMaxThreads 时记录饥饿起始时间，恢复到阈值以下时结束计时；持续超过约 100 ms 会输出诊断日志。它主要用于暴露池线程长期忙碌、事务可能排队的现象，不是直接的扩线程命令。实际动态补线程仍是驱动返回 BR_SPAWN_LOOPER、用户态再创建并注册辅助 looper 的协作过程（3.2、5.1 节）。

驱动协议与事务分发

  1. binder_write_read 的六个字段中，write_consumed、read_consumed 分别表示什么？libbinder 收到它们后如何处理？

    答案展开

    write_consumed 是驱动实际消费的 mOut 字节数；若它为正且小于本次待写大小，libbinder 认为驱动没有完整消费命令流并 fatal，完整消费后清空 mOut 并处理 post-write 的延迟引用释放。read_consumed 是驱动实际写入 mIn 的字节数；大于 0 时，libbinder 将 mIn 的有效大小设为该值并将读位置重置到开头，供后续逐条解析 BR_*（5.2.2、5.2.3 节）。

  2. talkWithDriver() 遇到 -EINTR 为什么重试？write_consumed == 0 是否必然是致命错误？

    答案展开

    -EINTR 表示 ioctl 被信号中断，而不是 Binder 协议本身失败；libbinder 会重试以完成这次命令交换。源码的 fatal 条件是“已消费正数字节但没有消费完整个 mOut”；write_consumed == 0 本身不会走进这个 fatal 分支，不能把它笼统说成驱动异常（5.2.2、5.2.3 节）。

  3. 为什么 BR_TRANSACTION 的业务数据不直接复制进普通 Parcel？Parcel::ipcSetDataReference() 的作用是什么？

    答案展开

    驱动已把事务数据放在目标进程的 Binder 接收区。Parcel::ipcSetDataReference() 让 Parcel 引用这段由驱动提供的缓冲，而不是再做一份不必要的用户态复制；处理完成后需要通过 Binder 命令归还相应缓冲。mIn 保存的是 BR_TRANSACTION 这类控制命令及元数据，事务载荷则在 mmap 接收区，二者职责不同（2.2、5.3.1 节）。

  4. executeCommand() 收到 BR_TRANSACTION 后，如何找到实际应执行的 Binder 对象？handle 0 的事务又如何分发？

    答案展开

    tr.target.ptr 非空时，libbinder 先尝试持有目标对象的强引用，再通过 tr.cookie 取得本地 BBinder 并调用其 transact()；若目标为空，则使用本进程保存的 context object。servicemanager 预先设置该对象并注册为 context manager，因此发往 handle 0 的事务可落到它的本地 Binder 实现（1.5、5.3.1 节）。

  5. 同步事务与 TF_ONE_WAY 事务在服务端回复路径上有什么差别？

    答案展开

    同步事务的服务端在执行本地 Binder 对象后通过 sendReply() 发送回复，sendReply() 还会进入 waitForResponse() 等待驱动确认；带 TF_ONE_WAY 的事务不需要 reply，服务端会丢弃 reply Parcel，不发送 BC_REPLY。因此不能把“收到 BR_TRANSACTION”一概理解为必然有同步返回（5.3.1 节）。

  6. 为什么线程在 waitForResponse() 中等待同步 reply 时还可能触发死亡通知或处理嵌套事务？

    答案展开

    waitForResponse() 只直接消费本次调用相关的 BR_REPLY、BR_DEAD_REPLY、BR_FAILED_REPLY、BR_TRANSACTION_COMPLETE 等命令；其它 BR_* 会落入 default 后交给 executeCommand()。所以等待线程可就地处理 BR_DEAD_BINDER 等死亡通知，也可能执行嵌套 BR_TRANSACTION，避免同步调用链彼此等待时无人处理回调造成死锁（5.3、5.3.2 节）。

  7. BR_DEAD_BINDER、BR_CLEAR_DEATH_NOTIFICATION_DONE 分别对应什么用户态动作？

    答案展开

    收到 BR_DEAD_BINDER 时，libbinder 找到对应 BpBinder 并调用 sendObituary()，从而触发已注册的 DeathRecipient 回调，再写入 BC_DEAD_BINDER_DONE 告知驱动处理完成。收到 BR_CLEAR_DEATH_NOTIFICATION_DONE 时则对相关 BpBinder 执行 decWeak()，完成取消死亡通知后的弱引用释放（4 节、5.3 节）。

7.3 场景追问

# 面试官追问 回答关键点
1 servicemanager 把最大线程数设为 0，为什么仍然能够处理 Binder 请求？ 它不调用 startThreadPool()；主线程执行 setupPolling()，发送 BC_ENTER_LOOPER 后把 Binder fd 加入 Looper。fd 可读时由回调执行 handlePolledCommands()，所以是单主线程 polling，不是零个 looper（1.5、6 节）。
2 如果 mMaxThreads == 0 却调用 startThreadPool()，会发生什么？ libbinder 会警告，但仍创建一个 primary pooled thread。0 表示不希望驱动额外请求辅助线程，并不阻止该 API 创建初始线程；这正是 servicemanager 不调用它的原因（3.1 节）。
3 一个服务已把 16 个常规 Binder 线程都占满，再来请求一定会失败吗？ 不应简单回答“必失败”。驱动和 libbinder 会受线程池上限、事务类型、嵌套调用和接收区容量共同约束；等待 reply 的调用线程还可能处理嵌套事务。正确结论是：线程池饱和会带来排队、延迟和潜在死锁风险，应缩短 Binder 回调中的阻塞工作并合理配置线程数（3、5 节）。
4 为什么应用主线程不需要自己 joinThreadPool()，应用也能接收 Binder 回调？ onZygoteInit() 已通过 startThreadPool() 创建 primary pooled thread，驱动还可按需请求辅助线程。主线程通常负责 Looper/应用生命周期；它在同步 Binder 调用等待 reply 时，也可能处理嵌套事务，但这不是常驻 Binder 池的替代品（1.2、3 节）。
5 为什么不能在 Zygote 预加载阶段先 ProcessState::self()，让所有应用继承它来省初始化？ Binder 驱动的 binder_proc、fd 和接收区必须与具体进程匹配；fork 后接收区不复制，libbinder 也会关闭继承 fd 并标记 mForked。省掉一次初始化会换来错误的内核状态归属，因此设计上必须在子进程首次使用时初始化（2.3 节）。
6 BINDER_WRITE_READ 一次 ioctl 既可写又可读，为什么还要区分 mIn 和接收区 mmap？ mIn 是很小的用户态命令缓冲，用于驱动返回 BR_* 命令及元数据；mmap 接收区存放真正的 Binder 事务数据。binder_write_read 负责“命令控制面”，事务缓冲映射承载“数据面”（2.2、5.2 节）。
