servicemanager 启动

发表于 2026-04-12 | 分类于 Framework ， Binder
字数统计: 2.1k | 阅读时长 ≈ 8

ServiceManager 是 Android 系统中所有 Binder 服务的名字注册中心，它是一个单线程、事件驱动的原生进程。

特征 说明
线程模型 单线程，无线程池 (setThreadPoolMaxThreadCount(0))
事件模型 Looper + epoll 事件驱动
Binder 限制 禁止发起同步调用 (FATAL_IF_NOT_ONEWAY)，防止死锁
内核身份 通过 BINDER_SET_CONTEXT_MGR 成为 handle=0 的目标进程
通信限制 不允许普通 App UID 注册服务

3.关键初始化详解

3.1. 打开 Binder 驱动

与上一章节打开驱动的方式不同，是调用的 ProcessState::initWithDriver 方法，明确指定驱动，除此之外创建 ProcessState 对象前面流程完全一致。

3.2. 线程池限制

值得注意的是，之前的servicemanager设置线程池为0与现在默认为15，以及设置驱动线程池为15并不冲突。

  1. ServiceManager 的 ProcessState 构造时 mMaxThreads 默认值为 15，但在 startThreadPool 之前就强制设置为 0 写入驱动，驱动从一开始就知道这个进程不需要额外线程。
  2. Binder 驱动没有自己的内核线程。驱动代码跑在用户线程的 ioctl 上下文中。老版本使用全局锁（binder_main_lock）串行化所有操作，新版本使用细化锁允许不同进程并行处理。

处理过程如下：

  1. 多个进程发起 getService/addService
  2. 各进程线程通过 ioctl(BINDER_WRITE_READ) 携带 BC_TRANSACTION 进入驱动
  3. 驱动（加锁）路由事务到 ServiceManager，放入其待处理队列，唤醒其 binder fd
  4. ServiceManager 用户态只有一个线程，Looper 检测到 fd 可读后逐个处理
  5. 其他进程的请求在驱动中排队等待，不会阻塞调用者进程（调用者在 ioctl 上等待回复）

ServiceManager 处理的是 业务逻辑，类似于管理 key-value 表 + 权限检查，单线程更安全

3.4. 双重注册

两者缺一不可：

  • setTheContextObject：对本地 binder 库 “收到 context manager 的事务时，交给这个对象处理”
  • becomeContextManager：告诉内核驱动”这个进程就是 context manager”

可以说 setTheContext 与 becomeContextManager 就是整个 Binder 系统中用户态最重要的两个方法了：

  1. becomeContextManager：告诉 Binder 驱动它是系统中的唯一上下文管理者（将 handle 注册成 0 号，决定它是系统的服务注册中心）
  2. setTheContextObject：设置本地变量 the_context_object，当 executeCommand 收到 tr.target.ptr == 0 的事务时，用它来处理。纯用户空间的事务分发。系统告诉驱动，这是 0 号的主人。（让 ServiceManager 处理 0 号事务）

具体实现等到剖析 Binder 内核的时候一起分析。
