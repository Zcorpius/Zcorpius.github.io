1. 前言

Note

无 Binder，不 Android。Binder 是 Framework 中的核心知识，但是翻阅了好些博客，要不是从底层开始讲解，要不就是从架构角度进行讲解，很是晦涩。刚好自己也想把项目的架构自己梳理一边，趁着这个机会从项目搭建开始，从 AIDL 开始从头开始整理，直到 SDK 提供，穿针引线起来。

常见Binder跨进程通信方式主要有两种：

  1. 通过 Service 组建 binderService 方式获取 IBinder 通信。
  2. 通过 ServiceManager.getService 方法，从 ServiceManager 中获取到相关服务对应的 Manager，其实也是 IBinder。

不过第一种其实也是先通过 ServiceManager 获取到对应的 AMS，然后再通过 AMS 相关接口方法传递 IBinder 对象。

在Android系统中，每个进程都运行在一块独立的内存中，在其中完成自己的各项活动，与其他进程都分隔开来。但也有进程应用间进行互动的需求，比如传递数据或者任务委托等，也就是所谓的跨进程通信。

AIDL (Android Interface Definition Language，Android 接口定义语言) 就是为了满足这种需求而诞生的。通过AIDL，可以在一个进程中获取另一个进程的数据和调用其暴露出来的方法， 从而满足进程间通信的需求。

AIDL 是用于定义服务端和客户端通信接口的一种描述语言，可以拿来生产 IPC 代码，从某种意义上说 AIDL 其实就是一个模板，因为在使用过程中，实际起作用的并不是 AIDL 文件，而是据此生产的一个 Interface 的实例代码， AIDL 其实是为了避免我们重复写代码而出现的一个模板。主要介绍一下类型特点：

  1. 文件类型：用 AIDL 书写的文件的后缀是 .aidl，而不是 .java。
  2. 默认支持的数据类型包括：
    1. Java 中的八种基本数据类型，包括 byte，short，int，long，float，double，boolean，char。
    2. String 类型。
    3. CharSequence类型。
    4. List类型：List中的所有元素必须是AIDL支持的类型之一，或者是一个其他AIDL生成的接口，或者是定义的parcelable。List可以使用泛型。
    5. Map类型：Map中的所有元素必须是AIDL支持的类型之一，或者是一个其他AIDL生成的接口，或者是定义的parcelable。Map是不支持泛型的。
  3. 但是上述类型之外的数据类型，在使用之前必须导包，就算目标文件与当前正在编写的 .aidl 文件在同一个包下——在 Java 中，这种情况是不需要导包的。

3.1. bindService 绑定流程

绑定流程如下：

3.1.1. matrixclient 创建 Intent

  • 创建显式 Intent，指定 Server 端的包名和 Service 类名

3.1.2. matrixclient 绑定服务

  • 调用 boolean result = bindService(intent, remoteConnection, Context.BIND_AUTO_CREATE);
  • BIND_AUTO_CREATE 标志表示如果服务未启动，自动创建服务

3.1.3. AMS 处理绑定请求

  • ActivityManagerService (AMS) 是 Android 系统服务，负责管理应用组件的生命周期
  • AMS 检查 MatrixService 是否已启动

3.1.4. AMS 启动 MatrixService（如果未启动）

  • 如果 MatrixServerService 未启动，AMS 创建服务进程
  • 调用 MatrixServerService.onCreate()
    • 创建 MatrixServerBinder 实例

3.1.5. AMS 调用 onBind

  • AMS 调用 MatrixService.onBind(intent)
  • onBind() 返回 mMatrixServerBinder（IBinder 对象）

3.1.6. Binder Driver 传递 IBinder

  • Binder Driver（内核层）负责跨进程传递 IBinder 对象
  • AMS 将 IBinder 对象从 Server 进程通过 Binder Driver 传递到 Client 进程
  • 这是 Binder 机制的核心：跨进程传递 Binder 对象

3.1.7. AMS 调用 onServiceConnected

  • AMS 通过 Binder Driver 跨进程调用 ServiceConnection.onServiceConnected(name, service)
  • 参数 service 就是 MatrixServerBinder 实例的 IBinder 对象

3.1.8. Matrixclient 获取代理对象

  1. AMS 调用 ServiceConnection.onServiceConnected(name, service)
  2. ServiceConnection（MatrixServerConnection）调用 IMatrixProxy.Stub.asInterface(service)
  • asInterface() 方法判断：
    • 如果是本地接口（同一进程），直接返回接口对象
    • 如果是跨进程，返回 IMatrixProxy.Stub.Proxy 代理对象
  • 由于是跨进程调用，返回 IMatrixProxy.Stub.Proxy 对象
  • 将代理对象赋值给 mIMatrixProxy

3.1.9. 绑定完成

  • 绑定流程完成，matrixclient 现在可以通过 mIMatrixProxy 调用 matrixserver 的方法

3.2. setState 流程

3.2.1. Matrixclient 调用

  • 调用 mIMatrixProxy.setState(mInitState)
  • IMatrixProxy.Stub.Proxy.setState() 方法被调用

3.2.2. Matrixclient 准备数据

  • Parcel.obtain() 创建 _data 和 _reply 对象
  • _data.writeInterfaceToken(DESCRIPTOR) 写入接口标识
  • _data.writeInt(state) 写入参数
  • 调用 mRemote.transact(TRANSACTION_setState, _data, _reply, 0) 发送请求
  • 请求通过 Binder Driver 发送到内核层

3.2.3. 跨进程通信

  • Binder Driver（内核层）接收 Client 进程的请求
  • 将请求分发到 Server 进程的 Binder 线程池

3.2.4. Matrixserver 接收数据

  • Matrixserver Binder 线程池 中的某个线程接收请求
  • 调用 IMatrixProxy.Stub.onTransact() 方法

3.2.5. Matrixserver 解析请求

  • data.enforceInterface(DESCRIPTOR) 验证接口标识
  • int _arg0 = data.readInt() 读取参数
  • 根据事务码 TRANSACTION_setState 调用相应的方法
  • IMatrixProxy.Stub.onTransact() 调用 this.setState(_arg0)

Note

关键点：this 指向的是 MatrixServerBinder 实例（因为实际运行时对象是 MatrixServerBinder）

由于多态机制，实际调用的是 MatrixServerBinder.setState(int state)，MatrixServerBinder 更新 MatrixService 的内部状态 mState = state

3.2.6. Matrixserver 返回数据

  • reply.writeNoException() 写入无异常标识
  • Binder 线程将 reply 通过 Binder Driver 返回给 Client 端

3.2.7. Matrixclient 接收返回

  • reply.readException() 读取异常信息（无异常则继续）
  • reply.recycle() 和 data.recycle() 回收 Parcel 对象
  • MainActivity 的 setState() 调用完成

3.3.getState 流程

3.3.1. Matrixclient 调用

  • 调用 mIMatrixProxy.getState()
  • IMatrixProxy.Stub.Proxy.getState() 方法被调用

3.3.2. Matrixclient 准备数据

  • Parcel.obtain() 创建 _data 和 _reply 对象
  • _data.writeInterfaceToken(DESCRIPTOR) 写入接口标识
  • （getState 无参数，无需写入参数）
  • 调用 mRemote.transact(TRANSACTION_getState, _data, _reply, 0) 发送请求
  • 请求通过 Binder Driver 发送到内核层

3.3.3. 跨进程通信

  • Binder Driver（内核层）接收 Client 进程的请求
  • 将请求分发到 Server 进程的 Binder 线程池

3.3.4. Matrixserver 接收数据

  • Matrixserver Binder 线程池 中的某个线程接收请求
  • 调用 IMatrixProxy.Stub.onTransact() 方法

3.3.5. Matrixserver 解析请求

  • data.enforceInterface(DESCRIPTOR) 验证接口标识
  • （getState 无参数，无需读取参数）
  • 根据事务码 TRANSACTION_getState 调用相应的方法
  • IMatrixProxy.Stub.onTransact() 调用 this.getState()

关键点：this 指向的是 MatrixServerBinder 实例（因为实际运行时对象是 MatrixServerBinder）

由于多态机制，实际调用的是 MatrixServerBinder.getState()，MatrixServerBinder 返回 MatrixService 的内部状态 mState

3.3.6. Matrixserver 返回数据

  • int _result = this.getState() 获取返回值
  • _reply.writeNoException() 写入无异常标识
  • _reply.writeInt(_result) 写入返回值
  • Binder 线程将 reply 通过 Binder Driver 返回给 Client 端

3.3.7. Matrixclient 接收返回

  • _reply.readException() 读取异常信息（无异常则继续）
  • int _result = _reply.readInt() 读取返回值
  • _reply.recycle() 和 _data.recycle() 回收 Parcel 对象
  • IMatrixProxy.Stub.Proxy.getState() 返回 _result
  • MainActivity 的 getState() 调用完成

3.4. IMatrixProxy.Stub.Proxy 与 IMatrixProxy.Stub 的区别

3.4.1. IMatrixProxy.Stub.Proxy（Client 端代理）

  • 位置：运行在 Client 进程中
  • 作用：封装跨进程调用的细节，提供本地接口
  • 实现：每个方法都调用 transact() 通过 Binder Driver 发送请求
  • 获取方式：通过 IMatrixProxy.Stub.asInterface(service) 获取
  • 继承关系：实现 IMatrixProxy 接口，但不继承 Binder

3.4.2. IMatrixProxy.Stub（Server 端基类）

  • 位置：运行在 Server 进程中
  • 作用：作为 Server 端的基类，处理来自 Client 的跨进程请求
  • 实现：onTransact() 方法解析事务码并调用子类实现的方法（通过多态）
  • 继承关系：继承自 android.os.Binder，实现 IMatrixProxy 接口
  • 使用方式：Server 端继承此类并实现业务逻辑

继承关系 实现 IMatrixProxy 接口 继承 android.os.Binder，实现 IMatrixProxy

4. AIDL 关键词：in、out、inout、oneway

in、out、inout 是 aidl 中的 directional tag，表示了在跨进程通信中数据的流向：

  • in 表示数据只能由 客户端流向服务端 ，服务端会获取到客户端完整的数据，但 客户端不会同步服务端对该对象的修改 ，不写的话，默认的 tag 就是 in。
  • out 表示数据只能由 服务端流向客户端 ，从服务端端接受该对象不为空，但字段内容为空， 服务端修改对象后，binder 远程调用返回后，客户端会收到修改后的对象 。
  • inout 则表示数据可在 服务端与客户端之间双向流通 。

Note

默认情况下，我们在 AIDL 中定义的接口方法是同步的，如果 AIDL 中的接口方法被 oneway 修饰了，那么这些方法就变成 异步 ，被 oneway 修饰了的方法不可以有返回值，也不可以有带 out 和 inout 的参数。

为什么需要添加 readFromParcel(Parcel in) 方法？

readFromParcel不是Parcelable接口的标准方法，但AIDL需要它来支持out和inout参数：

  • in参数：使用CREATOR.createFromParcel()创建新对象
  • out参数：创建空对象，然后用readFromParcel()更新
  • inout参数：先用CREATOR读取，再用readFromParcel()更新返回值

在AIDL生成的代码中，会调用value.readFromParcel(_reply)来更新已存在的对象，而不是创建新对象。

7.1 记忆总结

L0：本模块在 Binder 全图中的位置

本模块回答的是：应用如何用 AIDL 把一个本地接口声明，变成跨进程可调用、可回调、可感知失效的 Binder 协议？

  1. 先定义协议，不是实现。 .aidl 定义两端共同的接口、方法号和可编组类型；构建工具据此生成 Java IInterface、Stub、Proxy 等胶水代码。真正跨进程运行的是两端各自加载的生成代码和 Binder 对象，而不是 .aidl 文件本身。
  2. 绑定负责交付 Binder 引用。 客户端通过 bindService() 请求服务；服务进程的 onBind() 返回本地 Stub / Binder。系统在建立连接时把它作为 Binder 引用交给客户端；跨进程时客户端拿到的是指向服务端对象的代理，不是把服务端 Java 对象复制过来。
  3. 同步调用是一进一回。 Proxy 将接口 token、参数和事务码写入 data，transact(..., flags = 0) 令调用线程等待；服务端 Binder 线程执行 Stub.onTransact()，解包后调用业务实现，结果或异常写入 reply，客户端再 readException() 和读取返回值。
  4. 方向和 oneway 定义协议语义。 in、out、inout 说明可编组对象的入参 / 回写方向；oneway 仅让远程调用方在事务入队后立即返回，不产生 reply。服务端仍会在 Binder 线程池中稍后执行该方法，不能把它理解成“服务端立即返回”或“自动切到业务线程”。
  5. 回调与死亡都是反向持有 Binder。 客户端把自己的 IMatrixCallback.Stub Binder 引用传给服务端，服务端保存其代理后即可反向 IPC；RemoteCallbackList 会移除死亡的远程回调。若手写集合，则对保存的远程 Binder linkToDeath()，监听的是“承载该 Binder 的进程”死亡。

Warning

面试或设计时尤其不要混淆：

  • onServiceConnected() 的 IBinder 与服务端那个 Java Stub 是同一远程对象的两端表示，不是同一个跨进程 Java 实例；
  • oneway 不等于服务端异步完成，更不保证一个新线程处理；它只取消远程调用方等待 reply；
  • in / out / inout 是编组方向，不是免费性能优化；不必要的 out / inout 会增加回传和复制成本；
  • Bp / Bn 是相对某次 Binder 引用而言的角色。谁持有远程 Binder 的代理，谁才能对它 linkToDeath()；
  • ServiceConnection.onServiceDisconnected() 是绑定服务连接丢失通知，不能泛化替代任意远程 Binder 的 DeathRecipient。

L1：必须能展开的模块骨架

下面六句话是本文的“生成器”。无需逐字背诵；应能把每句展开为调用链、线程关系或失败处理。

  1. AIDL 是接口契约和代码生成器；Stub 是服务端本地 Binder 入口，Proxy 是客户端的远程调用包装。
  2. Stub.asInterface(IBinder) 先查 queryLocalInterface()；同进程返回本地实现，跨进程才创建 Proxy。因此不能假定每次调用都必经 Binder driver。
  3. 一次同步远程调用是：Proxy.write* → transact → 服务端 Binder 线程 → Stub.onTransact → 业务实现 → reply → readException / read*。
  4. oneway 方法没有返回值、没有 out / inout，远程调用方不等待；同一线程发给同一远程 Binder 的单向调用保持顺序，但服务端实现仍必须考虑 Binder 线程和耗时工作。
  5. 双向通信不是“一个 Binder 自动双向”：客户端必须把自己的 callback Binder 显式注册给服务端；服务端保存的是跨进程 callback 的代理，并在合适时机调用它。
  6. RemoteCallbackList 适合维护远程 callback 的生命周期；普通 List 则要去重、同步、linkToDeath()、unlinkToDeath()，并在服务销毁时清理。

L2：只需快速定位的细节

以下内容应能在正文或当前工程生成目录中快速定位，不需要硬背：

  • 当前 Android Gradle Plugin / aidl 版本实际生成的 Stub、Proxy、版本和兼容性代码；
  • 每个 TRANSACTION_* 的数值、Parcel 的具体读写顺序及 Parcelable 的版本兼容策略；
  • 绑定服务由 AMS / 应用进程调度的完整调用栈；
  • RemoteCallbackList 的 frozen-callee 策略、cookie、kill() 及广播 API 的约束；
  • Binder driver 的 buffer、线程池、死亡通知命令细节（可与《Binder启动》配合阅读）。

7.2 基础自测

协议、绑定与代理

  1. .aidl 文件、生成的 Stub / Proxy、服务端业务 Binder，三者各自负责什么？

    答案展开

    .aidl 是两端共同的接口契约；构建工具据此生成用于编组和分发的接口、Stub、Proxy；服务端再继承 Stub 并实现业务方法，onBind() 返回该本地 Binder。跨进程时客户端使用的是生成的 Proxy，服务端 Binder 线程经 Stub.onTransact() 进入业务实现（2、3.4 节）。

  2. Stub.asInterface(service) 为什么有时返回本地实现，有时返回 Proxy？

    答案展开

    它先通过 queryLocalInterface(DESCRIPTOR) 判断传入 Binder 是否是本进程附着了该接口的本地对象；命中时直接返回该接口实现，调用不需要编组或驱动。未命中时说明要按远程 Binder 处理，才构造 Proxy 经 transact() 发起 IPC（3.1.8、3.4.1 节）。

  3. ServiceConnection.onServiceConnected() 拿到的 IBinder 是服务端 Java MatrixServerBinder 实例本身吗？

    答案展开

    它代表服务端 onBind() 返回的同一个 Binder 对象身份，但跨进程传递后客户端持有的是可用于远程调用的 Binder 引用 / 代理，不是服务端堆中的 Java 对象实例。随后 asInterface() 在客户端把这个引用包装为 AIDL Proxy；只有同进程绑定才可能直接得到本地接口（3.1、3.4 节）。

  4. 一次 getState() 的同步远程调用，客户端与服务端分别做了什么？

    答案展开

    客户端 Proxy 把接口 token 和事务码写入 data，以 flags 为 0 的 transact() 发出并等待；服务端某个 Binder 线程进入 Stub.onTransact()，校验 token、解包、调用真实 getState()，把异常状态和返回值写入 reply。客户端收到 reply 后先 readException()，再读取返回值并回收 Parcel（3.3、3.4 节）。

参数方向与线程语义

  1. in、out、inout 的区别是什么？为什么不应把它们当成性能开关？

    答案展开

    in 把调用方对象的值编组给服务端，不回写服务端修改；out 不传初始内容，服务端创建 / 填充对象后写回调用方对象；inout 既传入又写回。它们是协议中对象数据的流向声明，序列化本身有成本；若调用方并不需要回写，使用 out 或 inout 反而增加 reply 数据和复制（4、4.2 节）。

  2. 远程 oneway void setStateAsync(int) 到底保证什么，又不保证什么？

    答案展开

    它保证远程调用方将事务交给 Binder 后不等待 reply，方法不能返回值，也不能带 out / inout 参数；同一线程对同一远程 Binder 发出的单向调用保持顺序。它不保证服务端已经执行或成功执行，也不把业务自动派发到自建线程；服务端最终仍由 Binder 线程池接收并执行，耗时实现仍会占用该线程（4、4.2 节）。

  3. oneway 在同进程调用时也会异步吗？

    答案展开

    不会。asInterface() 返回本地接口时，调用就是普通 Java 方法调用；Android 对本地 oneway 调用不提供异步语义。若业务需要“无论本地还是远程都异步”，应由接口实现明确投递到自己的 Handler / Executor，而不是依赖 oneway（3.4.1、4 节）。

  4. 为什么 out / inout 的自定义 Parcelable 需要 readFromParcel()？

    答案展开

    生成代码需要将服务端写回的内容填充到调用方已传入的对象，而不是只新建并返回另一个对象；readFromParcel() 给这个“就地回填”提供读取入口。相对地，in 只需从请求 Parcel 创建服务端要使用的对象，不需要把修改再写回调用方对象（4.1、4.2 节）。

回调与失效处理

  1. 服务端怎样获得调用客户端方法的能力？

    答案展开

    客户端实现 IMatrixCallback.Stub，在 registerMatrixCallBack() 中把该接口作为参数传入。服务端从 Parcel 读出 Binder 后经 IMatrixCallback.Stub.asInterface() 得到本地接口或远程 Proxy，保存它；日后调用 onStateChanged() 就是一次反向 Binder IPC（5.1、5.2 节）。匿名 new IMatrixCallback.Stub() { ... } 同样是合法 Binder 实现，是否匿名不会让 callback 自动变成 null。

  2. RemoteCallbackList 比普通 List<IMatrixCallback> 多解决了什么？

    答案展开

    它针对跨进程 callback 管理 Binder 身份和死亡：注册接口所在进程死亡时会自动移除，并提供受控的广播遍历 API。普通 List 只保存 Java 引用，必须自行做并发保护、按 Binder 去重、注册 / 取消死亡通知和清理，否则可能保留失效回调（5.1、6.1、6.2 节）。

  3. linkToDeath() 监听的究竟是谁死亡？为什么 Bp / Bn 不能固定等同于客户端 / 服务端？

    答案展开

    调用方必须持有一个远程 Binder；linkToDeath() 监听的是承载这个 Binder 的远程进程死亡。对服务接口而言客户端通常持有服务端的代理，客户端是 Bp、服务端是 Bn；对回调接口则反过来，服务端持有客户端 callback 的代理，服务端成为 Bp。角色随“正在讨论的 Binder 引用”变化，而非随进程名称永远固定（5、6 节）。

  4. onServiceDisconnected() 能替代对任意 IBinder 注册 DeathRecipient 吗？

    答案展开

    不能。它描述的是由 bindService() 建立的服务连接丢失，例如该服务进程被杀；它不覆盖应用持有的任意 Binder，也不提供通用的 Binder 身份级死亡监听。需要对特定远程 Binder 做资源清理或失效处理时，应使用该 Binder 的 linkToDeath()，同时正确处理注册时目标已死亡的 RemoteException（6.2 节）。

7.3 场景追问

# 场景 回答关键点
1 客户端调用 oneway setStateAsync() 后立刻读状态，却还读到旧值，是否违反 AIDL？ 没有。oneway 仅保证调用方不等服务端 reply；服务端事务可能尚未由 Binder 线程执行。需要“写后读一致”时用同步接口、明确的确认回调，或设计带版本号的状态协议。
2 服务端在 oneway 方法里 sleep(3s)，为什么仍可能拖慢后续请求？ 该方法最终仍占用服务进程的 Binder 线程；同一发送线程到同一 Binder 的单向事务还要保持顺序。耗时工作应尽快转交给业务线程，并设计排队、丢弃或合并策略。
3 为什么匿名 IMatrixCallback.Stub 没有收到回调，不应先把原因归咎于“匿名类”？ 匿名 Stub 本身可以正常提供 asBinder()。先检查是否注册成功、服务端是否保存了同一 Binder、接口是否确实为远程、回调是否被注销 / 进程已死，以及回调线程是否被业务逻辑阻塞。
4 服务端用普通 List 保存 callback 后客户端被杀，会出现什么问题？ 该 List 仍可能保留失效的远程代理；下次回调抛 RemoteException，且可能泄漏对应资源。可改用 RemoteCallbackList，或在注册时 linkToDeath()，在 binderDied() 中移除并清理。
5 客户端已绑定 Service，为什么仍需在每次 IPC 处理 RemoteException？ 绑定成功只说明当时连接可用；远程进程可在之后死亡、重启或事务失败。调用点应处理异常、清除旧代理，并按业务需要等待重新连接或重试。
6 将大对象从 in 改成 inout，为什么可能更慢而非更快？ inout 除请求方向的编组外，还要把服务端修改后的对象放进 reply，再填回调用方；若不需要回传，额外序列化和复制没有收益。
7 asInterface() 返回本地对象时，为什么不能用它验证 Binder 的线程池行为？ 同进程路径绕过 Proxy、driver 和远程 Binder 线程池，调用就在当前调用线程执行。验证 IPC 线程模型必须让客户端与服务端位于不同进程。
8 如果业务要求通知“尽量不阻塞、最新状态优先”，是否只加 oneway 就够？ 不够。还要定义服务端的队列 / 合并策略、背压、断连处理和线程切换；oneway 只解决调用方不等 reply，不能防止服务端任务积压。
