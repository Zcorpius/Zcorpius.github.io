Audio Usage 新增流程梳理

字数统计: 3.8k | 阅读时长 ≈ 16

1. 背景知识

1.1 AudioUsage 是什么

AudioUsage 描述音频的用途/场景，告诉系统”这个声音是干什么的”。系统根据 Usage 决定：

  • 音频焦点（Audio Focus）：导航语音来了是否压低媒体
  • 路由决策（Routing）：声音从哪个物理设备输出
  • 音量曲线（Volume Curve）：不同设备上的音量映射
  • 音频处理（Processing）：是否开启 AEC、NS 等

1.3 为什么要新增

车载场景中，前排和后排可能有独立的扬声器区域，需要将前排媒体（MEDIA_FRONT）和后排媒体（MEDIA_REAR）路由到不同的物理输出设备，实现分区控制。

3. 逐层详细修改

3.1. 第一层：定义

3.1.1 XSD Schema

文件：hardware/interfaces/audio/7.0/config/audio_policy_configuration.xsd

修改位置：audioUsage 简单类型（simpleType）的枚举列表

Important

修改原因：XSD 是整条链路的源头定义。它定义了 audio_policy_configuration.xml 中 preferredUsage 属性的合法值。同时，xsd_config 构建规则会根据 XSD 自动生成 Java 枚举类 AudioUsage.java。不在 XSD 中定义，后续所有引用都不成立。

Note

定位修改位置 : 那为什么是 hardware/interfaces/audio/7.0 中的文件，而不是其他的version呢？有两个方法：

  1. 在 framework/av/ 下运行 grep -rni "include <android_audio_policy_configuration_" 后面搜寻到的结果就是对应的版本。
  2. 在 /out/target/product/gen4_gvm/vendor/etc/vintf/manifest.xml 配置，也就是编译产物中的实际配置中寻找: grep -A5 "android.hardware.audio" manifest.xml ，找到的 <fqname>@7.0::IDevicesFactory/default</fqname>就是答案。

3.1.2 C/C++ 枚举定义

文件：system/media/audio/include/system/audio-hal-enums.h

修改位置：AUDIO_USAGE 枚举宏定义

Important

修改原因：这是 C/C++ 层的枚举定义，是 HAL 层、AudioFlinger、AudioPolicyManager 等所有 native 代码使用的底层枚举值。不定义这个宏，所有 C/C++ 代码都无法引用 AUDIO_USAGE_MEDIA_FRONT。

注意：枚举数值必须未被占用，且与 AIDL 定义保持一致。

3.1.3 AIDL 接口定义

文件：

# 路径 性质
1 system/hardware/interfaces/media/aidl/android/media/audio/common/AudioUsage.aidl 源文件
2 system/hardware/interfaces/media/aidl_api/android.media.audio.common.types/2/android/media/audio/common/AudioUsage.aidl 冻结版本 2（当前最新冻结版）
3 system/hardware/interfaces/media/aidl_api/android.media.audio.common.types/current/android/media/audio/common/AudioUsage.aidl 开发中版本

修改位置：AudioUsage 枚举定义

Important

修改原因：AIDL 是 Android HIDL/AIDL HAL 接口层的数据类型定义。Audio HAL 7.0+ 使用 AIDL 定义跨进程通信的数据结构。不在这里定义，HAL 服务和框架之间的 IPC 传递无法识别新值。

Tip

同步修改（需要知道hash值怎么计算）：需要更新 AIDL 的hash文件: system/hardware/interfaces/media/aidl_api/android.media.audio.common.types/2/.hash

3.1.4 Java 框架常量

文件：frameworks/base/media/java/android/media/AudioAttributes.java

需要修改的位置（共约 7 处）：

① 常量定义

② 抑制映射（SUPPRESSIBLE_USAGES）

③ Usage → AudioUsage 转换 switch

④ AudioUsage → Usage 反向映射

⑤ toString() switch

⑥ 其他 switch/case（如 usageForStreamType、toBundle 等相关方法）

Important

修改原因：AudioAttributes 是应用层设置音频属性的入口，开发者通过 setUsage(USAGE_MEDIA_FRONT) 来指定用途。所有内部映射和转换都需要覆盖新值，否则运行时会抛异常或返回错误值。

3.2. 第二层：转换

3.2.1 AIDL ↔ C++ 双向转换

文件：frameworks/av/media/audioaidlconversion/AidlConversionCppNdk.cpp

需要修改两处：

① AIDL → legacy

② legacy → AIDL

修改原因：AIDL 接口使用 AudioUsage 枚举，C++ 层使用 audio_usage_t 枚举。两个方向的转换函数用 switch 遍历所有枚举值，编译器开启 -Werror,-Wswitch，缺少任何一个 case 都会编译报错。

3.3 第三层：校验与策略

3.3.1 Usage 合法性校验

文件：frameworks/av/services/audiopolicy/managerdefault/AudioPolicyManager.cpp

修改位置：isValidAttributes() 函数

Important

修改原因：音频策略管理器在处理任何音频流之前，会先校验其属性是否合法。如果新 Usage 不在 switch 中，isValidAttributes() 返回 false，音频流直接被拒绝，无法播放。

3.3.2 策略映射（核心！决定走哪个 Route）

文件：frameworks/av/services/audiopolicy/engineconfigurable/config/<target>/audio_policy_engine_product_strategies.xml

方式 A：复用现有策略（不需要新 Route）

方式 B：创建独立策略（需要新 Route）

修改原因：策略映射是 Usage → Route 的核心桥梁。getProductStrategyForAttributes() 函数根据这个 XML 配置，将音频流的 Usage 匹配到对应的 ProductStrategy，进而决定使用哪个输出设备、哪条路由、哪个音量组。

如果使用 configurable 引擎，还需要在以下文件中配置：

  • audio_policy_engine_volume_groups.xml — 定义音量组
  • audio_policy_engine_default_volumes.xml — 定义默认音量曲线
  • audio_policy_engine_product_strategies.xml — 策略优先级排序

如果使用 default 引擎，策略在 C++ 代码中硬编码，需要修改：

  • frameworks/av/services/audiopolicy/enginedefault/src/Engine.h — 添加策略枚举
  • frameworks/av/services/audiopolicy/enginedefault/src/Engine.cpp — 实现策略映射逻辑

3.4. 第四层：物理路由

3.4.1 音频策略配置（实际设备配置）

文件：vendor/<vendor>/audio_policy_configuration.xml（具体路径因厂商而异）

需要新增三部分：

① mixPort — 软件输出流

② devicePort — 物理设备

③ route — 连接路径

修改原因：

  • mixPort 定义了 HAL 暴露的输出流，preferredUsage 指定该流专门服务 MEDIA_FRONT
  • devicePort 定义了物理输出设备（车载场景下通常是 BUS 类型），address 标识具体的硬件总线
  • route 将 mixPort 和 devicePort 连接起来，建立数据通路

三者缺一不可：没有 mixPort 无法创建音频流，没有 devicePort 无法输出到硬件，没有 route 两者无法连通。

3.4.2 attachedDevices（可选）

修改原因：如果该设备是永久挂载的（焊接在车内），需要加入 attachedDevices 列表，表示设备始终可用。

3.6. 第六层：Audio Hal

3.6.1 声明可用输出

policy XML 的 primary module 中分别追加以下配置，保留已有项。

① attachedDevices：让 AudioPolicy 启动时枚举到新 BUS

② mixPorts：新增普通 PCM 输出，不添加 PRIMARY、FAST、DIRECT 等 flags

本项目使用 CarAudio 动态路由，将 Usage/context 匹配到 BUS。此处沿用现有媒体 mixPort 的声明方式，实际实现没有新增 preferredUsage；不能把它当作这条动态路由的必要条件。

③ devicePorts：声明地址和 CarAudio 所需的 JOINT gain

gain 范围沿用当前车内媒体 BUS：-3000～0 mB，默认 -1500 mB，步进 100 mB。CarAudio 创建音量组时需要读取合法的 gain，因此不能只写一个没有 profile/gains 的空 devicePort。

④ routes：连接软件输出与设备

sink 必须与 devicePort 的 tagName 一致，sources 必须与 mixPort 的 name 一致。

3.6.4 接通新 BUS 的音量控制

当前车内媒体通常通过 bus_out_map[] 将地址转换为功放事件；表中没有前排媒体专用事件。若只新增路由，设置新 BUS 音量时会出现 needs not to set volume，随后返回 0，实际没有调整增益。

本次让前排媒体使用已有的 PAL 流音量路径：在功放分支的条件中排除新地址，再执行原有流音量换算。关键代码放在同一方法中展示：

沿用本项目现有换算：-3000 mB 及以下 → 0.0；-1500 mB → 0.5；0 mB 及以上 → 1.0。这个换算是项目已有的线性控制曲线，不是标准的 dB 到幅度指数换算。

StreamOutPrimary::SetVolume() 缓存流音量；流已打开时调用 pal_stream_set_volume()，尚未打开时在后续打开流程应用缓存。按完整地址匹配流，前排媒体不会复用后排媒体的功放事件。物理独立音量仍需确认 DSP graph 的 gain 模块和下游功放控制域。

后续若功放协议增加了真正的前排媒体专用事件，应同步修改协议和接收端，再调整 HAL 的事件表和这里的分支；不能自行编造一个事件编号。

3.6.5 PCM dump

PCM 文件有数据说明音频进入了 HAL 输出路径，不能单凭它判断 DSP 成功开图或物理扬声器位置正确。
