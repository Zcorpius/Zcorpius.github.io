#2.Binder 整体架构

1.1 为什么 Android 选择 Binder

特性 Binder 传统 IPC (Socket/Pipe)
拷贝次数 1 次 (mmap) 2 次 (内核中转)
安全性 进程 UID/PID + SELinux 依赖守护进程
面向对象 原生支持对象传递 需要额外封装
同步调用 原生支持同步 RPC 需要自行实现
性能 共享内存 + 一次拷贝 数据两次穿越内核

1.2 Binder 的 “一次拷贝” 原理

  • 发送方通过 copy_from_user() 将数据拷入内核的 binder_buffer
  • 接收方通过 mmap 已经将同一块物理内存映射到自己的用户空间
  • 接收方直接读取，无需第二次拷贝

3. 内核层关键函数实现 (binder.c)

3.1 binder_open() — 进程打开设备 (binder.c:2979)

流程：

  1. 分配 binder_proc 结构体并初始化
  2. 设置 proc->tsk = current，记录 pid
  3. 初始化 threads/nodes/refs_by_desc/refs_by_node 四棵红黑树
  4. 初始化 todo 工作队列和 wait 等待队列
  5. 加全局锁，将 proc 加入 binder_procs 全局哈希链表
  6. 创建 debugfs 条目 /proc/binder/proc/<pid>
  7. filp->private_data = proc

3.2 binder_mmap() — 内存映射 (binder.c:2883)

这是实现”一次拷贝”的关键函数：

流程：

  1. 限制最大 4MB (SZ_4M)，禁止 VM_WRITE
  2. 设置 VM 标志：VM_DONTCOPY（fork 不继承）
  3. get_vm_area(size, "binder") 分配内核连续虚拟地址
  4. 分配 pages 数组，为每一页分配物理页框
  5. 创建第一个 binder_buffer，标记为 free，加入 free_buffers 红黑树
  6. 计算 user_buffer_offset = 用户地址 - 内核地址（后续据此做地址转换）

3.4 binder_thread_write() — 处理用户写入的命令 (binder.c:1837)

循环读取用户空间 buffer 中的 BC_* 命令：

BC 命令 作用 内部处理
BC_TRANSACTION 发起一次调用 → binder_transaction(proc, thread, &tr, 0)
BC_REPLY 回复一次调用 → binder_transaction(proc, thread, &tr, 1)
BC_ACQUIRE 增加强引用 → binder_inc_ref(ref, strong=1)
BC_RELEASE 减少强引用 → binder_dec_ref(ref, strong=1)
BC_INCREFS 增加弱引用 → binder_inc_ref(ref, strong=0)
BC_DECREFS 减少弱引用 → binder_dec_ref(ref, strong=0)
BC_FREE_BUFFER 释放接收到的 buffer → binder_free_buf(proc, buffer)
BC_ENTER_LOOPER 主线程进入循环 `thread->looper
BC_REGISTER_LOOPER 子线程注册 `thread->looper
BC_EXIT_LOOPER 退出循环 `thread->looper
BC_REQUEST_DEATH_NOTIFICATION 注册死亡通知 关联 binder_ref_death 到 ref
BC_CLEAR_DEATH_NOTIFICATION 取消死亡通知 移除 death 关联

3.5 binder_transaction() — 核心事务处理 (binder.c:1402)

这是 Binder 驱动最核心、最复杂的函数。完成一次跨进程调用的数据传递。

3.6 binder_thread_read() — 向用户空间返回结果 (binder.c:2248)

流程：

  1. 若无待处理工作，阻塞在 wait_queue 上（或 non_block 时返回 EAGAIN）
  2. 从 thread->todo 或 proc->todo 取出 binder_work
  3. 根据 work->type 分发：
work 类型 写入用户空间的 BR 命令 含义
BINDER_WORK_TRANSACTION BR_TRANSACTION / BR_REPLY 有新事务到达
BINDER_WORK_TRANSACTION_COMPLETE BR_TRANSACTION_COMPLETE 发出的事务已被驱动接受
BINDER_WORK_NODE BR_INCREFS / BR_ACQUIRE / BR_RELEASE / BR_DECREFS 引用计数变化
BINDER_WORK_DEAD_BINDER BR_DEAD_BINDER 远程 Binder 对象已死亡
  1. 对于 BR_TRANSACTION/BR_REPLY：将 binder_transaction_data 写入用户 read buffer
  2. 检查是否需要更多线程：若 ready_threads == 0 && requested_threads < max_threads，写入 BR_SPAWN_LOOPER

3.7 binder_alloc_buf() / binder_free_buf() — 缓冲区管理

binder_alloc_buf() (binder.c:732)：

  • 从 proc->free_buffers 红黑树中找到 >= 所需大小的最小 buffer（最佳适配）
  • 若 buffer 大于需要，从尾部切割出新的 free buffer
  • 将分配的 buffer 从 free_buffers 移到 allocated_buffers

binder_free_buf() (binder.c:895)：

  • 释放 buffer，与相邻 free buffer 合并
  • 从 allocated_buffers 移回 free_buffers

3.8 binder_poll() (binder.c:2684)

  • ServiceManager 的事件循环使用 epoll 监听 binder fd，底层调用此函数
  • 检查 proc->todo 或 thread->todo 是否有工作
  • 有工作返回 POLLIN，否则注册等待队列
