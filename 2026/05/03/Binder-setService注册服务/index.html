Note

Native 层有一个 sp<IBinder>，但不知道它具体是 JavaBBinder 还是 BpBinder。需要把它转成 Java 层能用的对象返回给 Java。本次调用中获取 handle=0 的 BpBinder，handle=0 就是 ServiceManager。这一步返回的是 ServiceManager 的代理对象 BinderProxy，不是任何具体服务。

接下来再看 allowBlocking 方法：

核心就做一件事：对 BinderProxy 关闭主线程阻塞警告，然后原样返回。

Warning

Android 默认不允许在主线程（UI 线程）做同步 Binder 调用，因为这会阻塞 UI，导致卡顿甚至 ANR。所以 BinderProxy 内部有检测机制。但 ServiceManager 是例外，因为获取 ServiceManager 代理是系统基础设施，必须在任何线程都能用，包括主线程。

BinderCacheWithInvalidation 类的具体实现后续再详细剖析，封装完成后回到了 IInterface::asBinder 方法:

这两个是重载方法，一个接受裸指针，一个接受 sp<> 智能指针。做的事完全一样：从 IInterface 接口对象中提取出底层的 IBinder。根据传进来的 iface 类型返回服务端或者客户端的 IBinder。而本次流程中传进来的是已经封装后的本地缓存对象，所以返回的是 BBinder。随后又回调了 javaObjectForIBinder 方法，封装成 BinderProxy 远程代理对象。

Note

  • BBinder：本进程创建的本地对象，自己就是实体
  • BpBinder：代表另一个进程的对象，通过 handle 跨进程通信

BackendUnifiedServiceManager 虽然不是 服务的实体，但它是本进程创建的本地 C++ 对象，所以它是 BBinder。它内部再持有 BpBinder 去跨进程找真正的 ServiceManager。

最后就是通过 IServiceManager.Stub.asInterface 将封装 BBinder(BackendUnifiedServiceManager) 的 BinderProxy 代理对象再次 封装成 AIDL 代理。也就是说 getIServiceManager 方法最终拿到的是通过 ServiceManagerProxy 的创建的代理类，主要成员变量就是 **mServiceManager**AIDL 代理。真是绕了一大圈啊。。

上述过程就是在 BackendUnifiedServiceManager 的缓存中查找所需要 get 的服务，如果命中，那就通过 _out 进行返回。全程都在本进程内，不需要经过驱动。****_data 和 _reply 这两个 Parcel 也是在本进程内存中传递，不经过序列化/反序列化。

Note

BackendUnifiedServiceManager 的缓存只优化了getService/checkService 这一步，也就是找到服务的 BinderProxy。之后用这个 BinderProxy 调业务方法照样每次都走 IPC。

不过这个优化还是有意义的，因为系统服务启动时大量的 getService 调用集中在少数高频服务上（window、activity、package 等），省掉这些重复查询能减少启动耗时。

如果没有命中，那就需要继续通过 IPC 来进一步获取了，获取后通过 updateCache 来更新到本地缓存中。干脆也把未命中的情况梳理一下吧。

1.6.2. 代理远程查找

mTheRealServiceManager 的声明类型是 sp<os::IServiceManager>，而在 getBackendUnifiedServiceManager 方法中创建 BackendUnifiedServiceManager 对象时，传递的是通过 ProcessState 单例拿到的 contextObject 转换成的 AidlServiceManager 类型对象，即远端 ServiceManager 代理。

也就是说是 mTheRealServiceManager 是封装 BpBinder(handle=0) 的 远端 ServiceManager 的代理对象，那就调用到 AIDL 生成的客户端代理了:

这步就是真正的 IPC 跨进程调用，从客户端进程发到 ServiceManager 进程。由于封装的是 BpBinder ，所以会调用到 BpBinder::transact 方法:

终于走到内核传输流程了，IPCThreadState::self()->transact，其中 binderHandle() 中的 handle 值是 0 ，也就是要找的远程服务是 ServiceManager :

上述主要做了两件事情：

  • 打包数据到 mOut 缓冲区，Parcel 数据打包成 binder_transaction_data 结构体，写入 mOut****。
  • 阻塞等待回复，传的 flags 是 0 ，所以走 waitForResponse(reply)****。真正和内核通信就在这里面。

流程中一共调用了两次循环，经历了两次 ioctl 操作：

  • 第一次发送请求，把封装在 mOut 中的数据通过 ioctl 写入 Binder 驱动，返回 BR_TRANSACTION_COMPLETE，随后进入第二次。
  • 第二次 mOut 为空，mIn 等待填充，ioctl 系统调用在 Binder 驱动中没有数据可读时，会把当前线程挂起（sleep），直到目标进程回复后驱动再唤醒它。

等到 ServiceManager 将数据写入 Binder 驱动传回后唤醒，从 mIn 中读到 BR_REPLY，就会在 ipcSetDataReference 方法中读到共享内存数据，最后会在 readParcelable 中完成远程代理对象的封装。然后再看 ServiceManager 进程的流程。
