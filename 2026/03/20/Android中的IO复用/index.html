Android 中的 I/O 复用（poll / epoll）

知识点定位：Linux I/O 多路复用（I/O Multiplexing），属于系统编程 / 网络编程的经典内容。
《UNIX 网络编程》(UNP)、高性能服务器编程都会讲，面试高频；在 Android 里它是
EventHub、Looper/Handler、servicemanager、init 等核心组件的共同地基。

1. 解决什么问题

单线程需要同时等待多个 fd 的困境：

三种出路：

方案 思路 代价
多线程，每个 fd 一个线程 各读各的 线程开销 + 同步复杂度
非阻塞轮询 循环挨个 read 空转烧 CPU
I/O 多路复用 ★ “帮我盯着这一堆 fd，谁就绪了告诉我”，线程只阻塞在一个系统调用上 无

2. 演进史：select → poll → epoll

2.1 select（1983，老古董）

缺陷：bitmap 上限 1024；每次调用全量拷贝；内核线性扫描；返回后用户再遍历 → 两次 O(n)。

2.2 poll（1997，小修小补）

换成数组，没了 1024 上限——但每次全量拷贝、内核扫全部、返回后再遍历的老毛病一个没改。

2.3 epoll（2002, Linux 2.5.44，真正的方案）

把”每次传集合”拆成三步，内核记住你注册过什么：

2.4 对比表（面试速答版）

select poll epoll
fd 上限 1024 无硬限制 无硬限制
fd 集合传递 每次全量拷入内核 每次全量拷入内核 epoll_ctl 注册一次，内核持有
内核找就绪 fd 线性扫描全部 O(n) 线性扫描全部 O(n) 回调 + 就绪链表 O(就绪数)
返回后找就绪 用户再遍历一遍 用户再遍历一遍 直接给出就绪列表
大量连接少量活跃 慢 慢 优势最大

2.5 接口对照：poll 与 epoll 的 API

使用流程对比：

步骤 poll epoll
准备 填 pollfd 数组 create1 + 逐个 ctl ADD（只做一次）
等待 每次调用把整个数组重新传给内核 wait 只传一个输出缓冲
找就绪 自己 for 遍历数组查 revents 返回值 n + events[0..n) 即就绪列表
增删 fd 改数组（realloc / memmove） ctl ADD / ctl DEL
事件常量 POLLIN / POLLOUT EPOLLIN / EPOLLOUT（还有 ET、WAKEUP 等）

本质差别在注册是否驻留内核：poll 的监听意图每次调用即弃；epoll 的注册持久保存在
内核红黑树里——这正是 2.4 表中”全量拷贝 vs 注册一次”在接口层的体现。

3. epoll 核心机制

3.1 内核原理：红黑树 + 就绪链表

  • 注册：epoll_ctl(ADD) 把 fd 挂到该 epoll 实例的红黑树上（增删查 O(log n)，重复注册会报 EEXIST）
  • 事件到达：设备驱动 / 协议栈有数据时，通过挂在 fd 上的回调函数把该 fd 放进就绪链表
  • 等待：epoll_wait 只需检查就绪链表，非空就拷给用户、返回；空就睡眠

这就是 O(就绪数) 的来源：没事件的 fd 根本不碰。

3.2 data “回执”机制

注册时填的 epoll_event.data 会被内核原样带回：

EventHub 靠它在一个 epoll_wait 里区分三种唤醒源：设备节点 fd / inotify fd / wake pipe。

3.3 水平触发 LT vs 边缘触发 ET

水平触发 LT（默认） 边缘触发 ET（EPOLLET）
通知时机 只要还有数据没读完，每次 epoll_wait 都通知 只在状态变化瞬间通知一次
读法 随便读，漏了下次还提醒 必须一口气读到 EAGAIN
风险 无 读不干净就永久错过事件

EventHub 和 Looper 用的都是默认 LT——input 事件绝不能丢，代码也简单。

3.4 EPOLLWAKEUP（Android 特色标志）

含义：从事件入队 → epoll_wait 返回 → 拷贝到用户态的全程，持有 wakelock 阻止系统 suspend，防止输入事件处理到一半设备睡了。使用它要求进程有 CAP_BLOCK_SUSPEND capability，所以 EventHub 构造函数第一件事就是检查（ensureProcessCanBlockSuspend()，没有直接 abort）。

4. 分层知识模型（别把账记错）

一句话：fd 是用户态访问内核资源的唯一凭证，epoll 是所有 fd 的统一收发室。

5.5 getevent —— 用 poll 的输入调试工具

system/core/toolbox/getevent.c（本地 AOSP14；frameworks/native/cmds/getevent/getevent.cpp
这份更全的独立实现同样用的 poll）。它做的事和 5.1 的 EventHub 几乎一模一样——
监听 /dev/input 设备节点 + inotify 热插拔——但等待层选的是 poll：

与 EventHub 逐项对照（同一个问题、两种实现，绝佳的对比样本）：

EventHub（epoll） getevent（poll）
等待调用 epoll_wait(mEpollFd, items, ...) poll(ufds, nfds, -1)
fd 注册 openDeviceLocked 后 epoll_ctl ADD 一次，驻留内核 每次 poll 重传整个数组
找就绪 返回的即是就绪列表，按 data.fd 分发 for 扫全数组查 revents
inotify mINotifyFd 挂进 epoll ufds[0] 固定下标位
热插拔 handleNotifyEventLocked() read_notify() → 增删时 realloc / memmove 挪数组
wake 机制 wake pipe（其他线程要打断它） 无——单进程单线程，没人需要唤醒它

为什么 getevent 用 poll 就够了：

  • fd 数量：几个到十几个设备，O(n) 扫描无所谓
  • 生命周期：调试工具，用完即退，不值得建 epoll 实例
  • 代码量：poll 一次调用搞定；epoll 要 create + ctl + wait 三段式

选型结论：工具型 / fd 少 / 短生命周期 → poll（简单直接）；
常驻系统服务 / fd 多 / 多种唤醒源（EventHub、Looper、servicemanager）→ epoll。
“epoll 全面优于 poll”是误解——epoll 赢在规模，poll 赢在简单。

6. “一切皆 fd” 的延伸家族

EventHub 的 wake pipe 和 Looper 的 eventfd 引出了 fd 家族的特殊成员——
它们不是”读文件数据”的 fd，而是纯粹的事件通知 fd：

类型 创建方式 可读的时机 Android 中的用户
pipe pipe2() 对端 write EventHub wake
eventfd eventfd() 对端 write 一个计数 Looper wake
timerfd timerfd_create() 定时时间到 servicemanager 5s 定时器
inotify fd inotify_init1() 被监控目录有增删 EventHub 热插拔
signalfd signalfd() 收到指定信号 init（signal fd 的底层）
binder fd open("/dev/binder") 有 binder 事务 servicemanager

共同点：都可以 epoll_ctl 注册、被 epoll_wait 统一等待——这就是第 3 层范式的威力。

7. 通用范式总结

单线程事件循环 = 上面五步包在 for(;;) 里。nginx、Redis、libuv、Binder 线程、
EventHub、Looper，全是这个骨架。

8. 面试速答卡

  • select/poll/epoll 区别：背 2.4 那张表；重点”epoll 注册一次 + 就绪链表，O(就绪数)”
  • LT vs ET：LT 没读完下次还通知（EventHub/Looper 都用 LT，宁重不漏）；
    ET 只通知一次必须读到 EAGAIN（高性能但易丢）
  • epoll 为什么快：红黑树管理注册 + 回调填就绪链表，不扫描不活跃的 fd
  • Android Handler 底层：nativePollOnce → Looper::pollOnce → epoll_wait，
    wake 走 eventfd；没消息时主线程内核态睡眠，0% CPU
  • EPOLLWAKEUP：epoll 等待/返回全程持 wakelock 防 suspend，需 CAP_BLOCK_SUSPEND
  • 惊群：多线程等同一 fd 会惊群，可用 EPOLLEXCLUSIVE 缓解（Android 单线程模型基本不涉及）
  • getevent 为什么用 poll 不用 epoll：调试工具、fd 少、用完即退，poll 一次调用最简单；
    epoll 的优势（注册驻留内核、O(就绪数)）要在 fd 多、常驻的场景才体现——选型不是越新越好

9.1.2 管道是什么

内核里的一条单向字节流 FIFO 缓冲（默认 64KB）：

四种状态下的行为（★ 是它能当唤醒 fd 的原理）：

状态 阻塞模式 非阻塞模式（O_NONBLOCK）
缓冲空时 read ★ 卡住等数据 → 读端不可读 立即返回 -1 / errno=EAGAIN
有人 write 后 ★ 读端立即变 EPOLLIN，唤醒 epoll_wait 同左
缓冲满时 write 卡住等空间 立即返回 -1 / errno=EAGAIN
写端全部关闭后 read 返回 0（EOF） 返回 0（EOF）

9.1.3 EventHub 中的完整用法（wake pipe / self-pipe trick）

这套玩法叫 self-pipe trick：epoll_wait 只认”fd 可读”，所以把任何跨线程通知
都翻译成”往管道写一个字节”。Looper 用 eventfd 是同一招的现代版（一个 fd 顶两个）。
谁在调 wake：配置刷新（InputReader.cpp:741）、定时器提前（:599）、
Watchdog 探活（:1071）、线程退出（:99）。

9.2 fcntl() —— 事后修改 fd 属性

9.2.1 接口与定位

定位：fd 属性工具箱——open/pipe2 创建时属性就定了大半，fcntl 是事后修改的官方通道。

9.2.2 常用命令一览

命令 作用
F_DUPFD / F_DUPFD_CLOEXEC 复制 fd（类似 dup）
F_GETFD / F_SETFD fd 级标志：FD_CLOEXEC（这个 fd 本身 exec 时关不关）
F_GETFL / F_SETFL ★ 文件级状态标志：O_NONBLOCK、O_APPEND（fd 背后文件的阻塞行为）
F_SETLK / F_SETLKW 文件锁（读锁/写锁，LKW = 拿不到就等）
F_GETOWN / F_SETOWN 设置接收异步 I/O 通知的进程
F_SETPIPE_SZ 调整管道缓冲区大小（少用）

易混点：SETFD 管的是”这个 fd 本身“（复制出来的新 fd 不继承），SETFL 管的是
“fd 背后打开的文件“（同一文件的所有 fd 共享）。

9.2.3 EventHub 中的用法：给 wake pipe 两端设非阻塞

读端为什么要非阻塞：reader 醒来后必须把管道读干净（LT 模式下残留字节会让
epoll_wait 反复立即返回，变成空转）。读干净的过程必然有”最后一次 read 时已空”——
非阻塞返回 EAGAIN（知道读完了）；阻塞模式则这次 read 会永久卡死 reader 线程。

写端为什么要非阻塞：缓冲满时 write 会阻塞。调 wake() 的可能是 Binder 线程、
Watchdog 线程——绝不能让”按门铃的人”被卡住（EventHub 的 wake() 对 EAGAIN 容忍）。

更通用的安全写法是”读-改-写”：先 F_GETFL 拿旧标志，位或上 O_NONBLOCK 再
F_SETFL，避免覆盖掉其他位。EventHub 直接整体设置——对管道而言可设位就这一个，
无副作用。

9.2.4 fcntl vs ioctl：两个”命令箱”的分工

fcntl ioctl
定位 所有 fd 通用的属性操作 设备特有的操作
典型用例 设非阻塞、复制 fd、文件锁 读设备能力位图、驱动私有命令
EventHub 中 F_SETFL O_NONBLOCK（wake pipe） EVIOCGBIT 读设备支持哪些事件、EVIOCGABS 读触摸屏分辨率
Binder 中 —— ioctl(BINDER_WRITE_READ) 收发 IPC 事务
