WMS 悬浮窗剖析

发表于 2026-09-07 | 分类于 Framework ， WMS
字数统计: 9.6k | 阅读时长 ≈ 42

1. 前言

本文以示例工程 LayOutDemo 为起点，梳理一个普通 View 如何变成跨应用显示的悬浮窗，以及它如何移动、如何消失。全部主线就是三句 API：

示例运行在 Android 8.0 及以上时使用的是 TYPE_APPLICATION_OVERLAY（数值 2038）。它是非应用窗口 / 系统 alert window：不归属于当前 Activity 的 ActivityRecord，而是 WMS 为其创建一个 WindowToken，再把该 Token 放入默认 Display 已经建好的 DisplayArea.Tokens 叶子。

这正是《WMS/AMS 层级树创建》中”建树结果如何使用”的运行时案例：开机时已经准备好的mAreaForLayer[layer]，在这里负责回答”新来的 2038 号窗口应该落到树的哪片叶子”。

先把三句 API 的全程调用链一次给全，后面每章展开一段：

本文涉及的关键角色：

角色 一句话职责
WindowManagerImpl 应用侧门面：校验/补全 token 后，全部转交 WindowManagerGlobal
WindowManagerGlobal 进程级登记处：mViews/mRoots/mParams 三组平行表管理所有顶层窗口
ViewRootImpl 一个顶层窗口的客户端主体：View 树 + traversal + IWindow 端点
IWindow ViewRootImpl 暴露给 WMS 的 Binder 回调端点，mWindowMap 的 key
Session(IWindowSession) 进程级 Binder 通道，WMS 识别调用者 uid/pid 的依据
WindowManagerService system_server 侧窗口大树的总管
WindowToken 同类、同归属窗口的容器/身份节点（overlay 每次新建一个）
WindowState WMS 中一个窗口的服务端实体
DisplayArea.Tokens 开机建树产物，layer 11 的叶子，overlay Token 的挂点
SurfaceFlinger 按 WMS 提交的 transaction 合成最终画面

2. Demo 示例

2.1 项目结构与整体流程

示例工程共三个源文件 + 两个布局资源：

文件 职责
MainActivity.java 悬浮窗全部核心逻辑：权限、窗口参数、添加/移除、拖动、进入应用
DesktopLayout.java 悬浮窗根视图：LinearLayout 子类，inflate R.layout.window
window.xml + bg_floating_window.xml UI：深蓝半透明圆角卡片 + 进入应用按钮（↗）+ 关闭按钮（❌）
ic_open_app.xml 进入应用按钮的矢量图标（Material open_in_new）
AndroidManifest.xml 声明 SYSTEM_ALERT_WINDOW 权限

整体流程：

  1. 用户点击「显示悬浮窗」按钮；
  2. 若已授予”显示在其他应用上层”权限（Settings.canDrawOverlays），直接通过 WindowManager.addView 把 DesktopLayout 加为系统悬浮窗；
  3. 悬浮窗显示后 finish() 关闭本 Activity，悬浮窗挂在 WindowManager 上，不随 Activity 生命周期销毁；
  4. 按住悬浮窗可拖动；点击「进入应用」收起悬浮窗并重新拉起主界面；点击关闭（❌）移除悬浮窗、彻底退出。

2.2 悬浮窗权限

SYSTEM_ALERT_WINDOW 属于特殊权限：不能像运行时权限那样弹窗申请，必须由用户在系统设置页手动授予：

Important

Settings.canDrawOverlays() 这道检查不是安全边界，只是 app 决定是否跳转设置页的用户体验层预检。WMS 收到 Binder 调用后，仍会按调用 UID 和 AppOp 作不可绕过的最终裁决（见 3.3.2）。

2.3 窗口参数

createWindowManager() 提前备好 WindowManager 和 LayoutParams，后续 addView / updateViewLayout 复用同一份。

各字段在本流程中的含义：

参数 对 WMS / 输入 / 布局的影响
TYPE_APPLICATION_OVERLAY 走系统 alert window 权限校验；策略层为 layer 11，在普通应用（2）之上、IME（13）和状态栏（15）之下
WRAP_CONTENT 首次 measure 后由内容尺寸决定窗口请求的宽高；不是铺满屏幕的 Activity 窗口
TOP | START、x/y 确定窗口锚点和相对坐标；FLAG_LAYOUT_IN_SCREEN 使布局可参考整块屏幕
FLAG_NOT_FOCUSABLE 不能成键盘焦点，不抢返回键和音量键，不能拉起软键盘；该 flag 同时隐含非 touch-modal 语义
FLAG_NOT_TOUCH_MODAL 点在窗口边界外的触摸交给下方窗口；窗口内部仍能接收触摸
FLAG_LAYOUT_IN_SCREEN 布局以整个屏幕（含状态栏区域）为参照，x/y 坐标原点即真实屏幕左上角

三个 flags 的组合是”纯展示 + 触摸型悬浮窗”的标准搭配：不干扰宿主应用的按键与焦点，窗外的触摸原样透传给下层应用。

2.4 显示与生命周期

demo 里有两行同名的 addView，分属两个完全不同的层面，这是理解悬浮窗结构的钥匙，也最容易混淆。

2.4.1 组装 View 树

这里的 addView(view) 继承自 ViewGroup，接收者是 this（正在构造的容器自己），把 inflate 出来的 window 布局挂为本容器唯一的孩子。它是纯应用进程内的内存操作：建立 View 父子关系、请求一次 measure/layout，不跨进程、不碰窗口系统——此刻屏幕上什么都看不见，这棵树甚至还没和任何窗口产生关联。

2.4.2 把 View 树的根变成窗口

WindowManager.addView() 是另一回事：它把整棵 View 树的根（DesktopLayout）连同窗口参数交给 WindowManager——客户端由此新建 ViewRootImpl，再经 Binder 到 WMS 注册 WindowState，是一次跨进程的”开窗”。完整链路第 3 章展开。

2.4.3 两个 addView 的逐项对比

维度 ViewGroup.addView(view) WindowManager.addView(view, params)
定义处 android.view.ViewGroup android.view.WindowManager（实现在 WindowManagerImpl）
接收者 容器自己（this） 系统窗口服务（经 WindowManagerGlobal → WMS）
作用层面 应用内 View 树：把孩子挂到父容器下 系统窗口：为整棵 View 树的根开一个顶层窗口
是否跨进程 否，纯本地 是，Binder 到 system_server
配套”规格单” 子 View 的 ViewGroup.LayoutParams WindowManager.LayoutParams（type/flags/x/y，见 2.3）
可见效果 无（树还在内存里） 窗口进入 WMS Z 序，首帧完成后可见（3.4）
典型失败 子 View 已有父容器 → IllegalStateException 权限/token 问题 → BadTokenException（3.5）

2.4.4 两步各管一段：组装后的完整层级

两个易混点：

  1. WMS 里的”窗口”不是树。窗口之间是按 Z 轴叠放的有序列表——悬浮窗能盖住普通应用，是因为它的 type 映射到更高的 layer（3.3.4）；树形嵌套只存在于每个窗口内部的 View 层级里。
  2. 平时写 Activity 感受不到这两个层面的分工：Activity 的窗口（PhoneWindow + DecorView）由系统代建，setContentView 本质也是往那棵现成的 View 树里挂内容。悬浮窗 demo 跳过了 Activity，手工把一棵裸 View 树直接交给 WindowManager 开窗，两层的 addView 才都暴露在业务代码里。

showDesk() 里 addView() 成功后立即 finish() 不会移除悬浮窗：这里添加的是一个独立 ViewRootImpl 对应的独立 WMS 窗口，不是 Activity decor 的子 View。只要进程和该窗口的 Session 还活着，它就能继续存在；removeDesk() 的 removeView()（2.5）或进程死亡时才会走移除链路（第 5 章）。

拖动核心是”按住窗口的同一个位置”跟随手指：

「进入应用」（↗）与「关闭」（❌）是两个入口，最终都汇合到同一条 removeView() 移除链路（第 5 章），区别只在移除之后做什么：

openApp() 的三个实现细节：

  1. 用 getApplicationContext() 启动：悬浮窗场景下原 Activity 实例已 finish()，按钮拿到的 Context 就是它；改用应用级 Context 启动新实例，规避已销毁 Activity 的生命周期隐患。
  2. FLAG_ACTIVITY_NEW_TASK 必须加：非 Activity 的 Context 启动组件的硬性要求，否则抛 AndroidRuntimeException。
  3. Android 10+ 的后台启动 Activity 限制对本例豁免：持有 SYSTEM_ALERT_WINDOW 且用户正与其 overlay 交互的应用允许 startActivity——悬浮窗能显示即说明权限已授予，不会被系统拦截。

「进入即收起」（先 removeDesk() 再 startActivity）还规避了一个状态问题：新 MainActivity 实例的 deskShowing 从 false 起步，若旧悬浮窗不移除，主界面里再点一次「显示悬浮窗」会对新 View 执行 addView——屏幕上叠出两个悬浮窗，旧窗口从此无人管理。

2.6 示例中的遗留问题

四个值得留意的点，后文会在对应章节再次遇到：

  1. y = getRawY() - top 的状态栏扣除是老 demo 遗留：rawY 本就以整屏左上角为原点，而窗口又配置了 FLAG_LAYOUT_IN_SCREEN（窗口坐标系同样含状态栏），严格对齐不应再减 top。保留旧换算会使窗口相对手指整体偏高约一个状态栏高度；拖动仍全程跟手，但不精确（不影响第 3 章创建链路，影响第 4 章位置精度）。
  2. waitingForOverlayPermission 只置位未消费：从系统授权页返回后没有在 onResume 里重新检查并自动显示，用户得回来再点一次按钮。
  3. demo 级内存隐患：DesktopLayout 用 Activity 的 context 创建，finish() 后 WindowManager 仍全局持有该 View（连带 Activity 引用），长时间存活的悬浮窗会泄漏 Activity。正规做法是传 getApplicationContext()。
  4. 版本守卫留下的低版本 NPE：onCreate() 仅在 API >= 26 时调用 createWindowManager()，而 minSdk = 23——在 API 23~25 的设备上授权后点「显示悬浮窗」，showDesk() 里的 mWindowManager.addView(view, null) 直接空指针。旧版 TYPE_PHONE 的三元分支已随本次重构移除；当前测试机为 API 36 模拟器，不受影响。

至此示例部分完结。后面的三章分别追踪 2.4/2.5 中的三句 API 在客户端和 system_server 里各经历了什么。

3. addView：View 变成 WMS 窗口

为避免把”注册窗口”和”真正出第一帧”混在一起，本章主线分为两段：

  1. addView()：客户端创建 ViewRootImpl，通过 Binder 把 WindowState 注册进 WMS 的窗口树；
  2. 首次 traversal：relayout() 获得 Surface、绘制内容并 finishDrawing()，WMS 才把它展示出来。

3.2 App 进程：View 变成一个窗口客户端

3.2.1 WindowManagerImpl 只做上下文和 token 补全

applyTokens() 校验传入的确实是 WindowManager.LayoutParams，补入 WindowContext token（若上下文带有），并在存在默认 token 时填写它。本例是顶层 overlay 而非子窗口：没有 parentWindow，也没有提供 Activity 的窗口 token；因此它不会依附到当前 Activity 的 WindowState。

3.2.2 WindowManagerGlobal 创建独立的 ViewRootImpl

WindowManagerGlobal.addView() 是应用进程的全局登记处。它先拒绝重复添加同一个 View，再为这个根视图新建 ViewRootImpl：

3.3 system_server：权限、Token、WindowState 与层级落位

3.3.1 Session 是很薄的一层转发

客户端的 addToDisplayAsUser() 到达 system_server 后，Session 不保存窗口树，它只带着该客户端进程的 uid/pid/能力信息转发：

真正的入口是 WindowManagerService.addWindow()。

3.3.2 第一道门：窗口类型与悬浮窗授权

addWindow() 在持有全局锁前先调用策略：

PhoneWindowManager.checkAddPermission() 对 TYPE_APPLICATION_OVERLAY 的处理要点是：

  1. 它属于 system alert window，记录的 AppOp 是 OP_SYSTEM_ALERT_WINDOW；
  2. targetSdk >= O 的普通应用只能使用 TYPE_APPLICATION_OVERLAY，不能再用旧的 TYPE_PHONE 等 alert type；
  3. 系统应用、持有特权 overlay 权限的调用者可直接通过；普通应用则执行 noteOpNoThrow(OP_SYSTEM_ALERT_WINDOW, uid, packageName, ...)；
  4. AppOp 为 MODE_ALLOWED 时允许；MODE_IGNORED 虽返回成功，但后续窗口会被隐藏；拒绝则返回 ADD_PERMISSION_DENIED。

把策略里的关键分支展开，能看清为什么 Android O 后示例必须选 2038：

所以 Settings.canDrawOverlays() 与这里的 AppOp 是同一授权体系的两个观察点：前者用于 app 决定是否跳转设置页，后者才是 WMS 的不可绕过校验。

3.3.3 没有 app token 不是失败：为 overlay 新建 WindowToken

之后 WMS 检查 Display 是否存在、调用 UID 是否有该屏访问权、IWindow Binder 是否已重复添加。对于本例：

  • 类型不在 FIRST_SUB_WINDOW..LAST_SUB_WINDOW，所以 parentWindow == null；
  • attrs.token 通常为 null，因而没有可复用的 Activity token；
  • 它不是 application window，unprivilegedAppCanCreateTokenWith() 允许普通 app 为这种非应用窗口创建 token。

注意 client.asBinder() 在此刻同时是 IWindow 的唯一客户端标识和新 Token 的 binder。一个 WindowToken 不是一个 Surface，也不是一个 View；它是 WMS 中同类、同归属窗口的容器/身份节点。

3.3.5 创建 WindowState 并真正加入 Token

Token 有了以后，WMS 构建服务端窗口实体：

WindowState 保存从 LayoutParams 复制而来的 flags、尺寸与位置，保存调用者 UID、IWindow、输入句柄以及 WindowStateAnimator。构造时会计算自己的 base layer：

本例的 base layer 因而源自策略的 layer 11。随后 WindowToken.addWindow() 创建 Token 自己的 SurfaceControl（需要时），并把该 WindowState 排序插入 Token 的 children。

在 add 阶段的尾部，WMS 还会：

  • openInputChannel()：本例并未设置 INPUT_FEATURE_NO_INPUT_CHANNEL，所以即便不可获取键盘焦点，仍有输入通道以处理窗口内部触摸；
  • 初始化 AppOp 可见性、系统是否临时隐藏非系统 overlay 等状态；
  • 更新焦点、IME target、input windows 和 insets 状态；
  • 不直接做 layout。源码明确注明”window must call relayout to be displayed”。

最后 addWindow() 将输入通道、Insets 和各项 ADD_FLAG_* 返回给 ViewRootImpl。到这里窗口已经在 WMS 的树和 mWindowMap 中可见，但尚没有可以呈现的首帧内容。

token ... is not valid 子窗口或应用窗口 token 不存在/不匹配 本例应使用 TYPE_APPLICATION_OVERLAY，不要把已失效的 Activity token 传入

调用了 addView 却没显示 AppOp 可使 overlay 隐藏；或首帧尚未完成 观察 dumpsys window、dumpsys SurfaceFlinger，检查首个 traversal/绘制

按一次”显示悬浮窗”，以下断点能看到最短闭环：

  1. WindowManagerImpl.addView()：确认 type、token 和 display；
  2. WindowManagerGlobal.addView()：确认新建的是独立 ViewRootImpl；
  3. ViewRootImpl.setView() 的 addToDisplayAsUser()：确认客户端发出的属性；
  4. WindowManagerService.addWindow()：看权限、WindowToken、WindowState；
  5. DisplayContent.addWindowToken()：看 findAreaForToken() 返回的 layer 11 Tokens；
  6. ViewRootImpl.performTraversals()、relayoutWindow()、WindowManagerService.finishDrawingWindow()：确认首帧显示。

4. updateViewLayout：拖动如何改位置

第 3 章里 addView() 已为 DesktopLayout 创建了独立的 ViewRootImpl、IWindow、WindowState 与 WindowToken。本章接着示例的拖动代码，梳理每次手指移动时 updateViewLayout() 如何使已显示的 2038 悬浮窗改位置。

核心结论先说清楚：updateViewLayout() 不会创建第二个 ViewRootImpl，也不会新建 WindowState 或 Token。 它复用 addView() 已经建立的同一个 ViewRootImpl 与同一个 IWindow。客户端只把新的 LayoutParams 记为”待同步”，随后在下一帧 traversal 通过已有 Session.relayout() 向 WMS 更新同一个 WindowState；WMS 重算 frame 并用 SurfaceControl.Transaction 改变 Surface 的位置/属性。

4.2 App 进程：找到旧 root，标记属性变化

4.2.1 WindowManagerImpl：仍会补齐上下文 token

这里仍调用 3.2.1 介绍过的 applyTokens()：参数必须是 WindowManager.LayoutParams；若 WindowManager 由 WindowContext 产生，也会检查窗口 type 是否匹配，并写回 mWindowContextToken。本例使用 Activity context 与同一份 mLayoutParams，不会得到一个新 token。这不是服务端的加窗操作，它只是保证随后的 relayout 带着一致、合法的客户端属性。

4.2.2 WindowManagerGlobal：通过原 View 找回已有 ViewRootImpl

mViews、mRoots、mParams 是 addView() 时登记的三组平行列表（3.2.2）。findViewLocked(view, true) 强制要求这个 View 已经通过同一 WindowManagerGlobal 添加；否则抛出：

因此，下面两种调用都不成立：

  • 对尚未 addView() 的 DesktopLayout 调 updateViewLayout()；
  • removeView() 已完成后继续用旧引用更新。

注意源码先调用 view.setLayoutParams(wparams)，然后才替换 mParams[index] 并通知 root。这使 View 树本地看到的 LayoutParams 与 WindowManagerGlobal 的记录保持一致；它仍没有调用 WMS。

4.2.3 ViewRootImpl.setLayoutParams()：复制属性并预约下一帧

copyFrom() 是关键：它把 caller 的属性复制到 root 持有的 mWindowAttributes，同时以 bit mask 返回变化类型。本例 x/y 的变化属于 layout 相关变化。无论变化项是什么，mWindowAttributesChanged = true 加上 scheduleTraversals() 都保证下一次 Choreographer traversal 会检查并同步属性。

newView 在 addView() 的建 root 情况下才为 true；此处传 false，所以不会重复 requestLayout() 那条新窗口初始化路径，只复用已存活的 root。

4.3 traversal：updateViewLayout 实际变成 relayout

这里解释了一个常见误解：updateViewLayout() 并没有名为 updateWindow() 的 Binder 调用。它令 params != null，从而复用所有窗口第一次显示、尺寸改变、可见性改变时都会走的 relayoutWindow() 协议（3.4 已贴出该方法）。调用使用的仍是 add 阶段创建的 mWindow（IWindow.Stub）和进程级 Session。宽高来自当前 View 树测量结果；仅移动位置时通常不变，但仍随这套统一协议传给 WMS。

为什么连续拖动会合并：UI 线程在一次 traversal 执行前可处理多个 ACTION_MOVE。每次调用都覆写 mWindowAttributes、置同一个 boolean，并向 Choreographer 预约 traversal；已经预约时不会为每次 move 各创建一个独立 root 或独立生命周期。因此最终发给 WMS 的一般是某个帧边界上最新的 x/y。这是拖动不会按每一个 MotionEvent 都阻塞一次 Binder 的原因。

Note

这不表示可无限制频率更新没有成本：发生 relayout 时要跨 Binder、持有 WMS 全局锁、执行布局与 Surface placement。需要做复杂拖动/动画时，仍应避免主线程高频无意义更新，或评估 Surface/动画专用方案。

4.4 system_server：更新已有 WindowState，而非重新加窗

4.4.1 Session.relayout() 是薄转发

Session 携带所属 uid/pid；WMS 不会凭传入的任意 IWindow 直接操作窗口，而是用 Session + IWindow 在 mWindowMap 查到先前 addWindow() 登记的那个 WindowState。

4.4.2 relayoutWindow()：类型不可改，属性可更新

这段代码确定了更新的边界：

可通过 update/relayout 改 不能在已添加窗口上改
x/y、宽高、gravity、alpha、部分 flags/private flags、软输入模式等（仍会受策略与权限清洗） type；provided insets 的数量、ID、override type 等结构性定义

所以把一个已显示 overlay 的 type=2038 改为状态栏或应用窗口类型并调用 updateViewLayout() 会抛异常；若需要不同窗口类型，应移除旧窗口再按权限重新 addView()。

本例只改 x/y，WindowState、它所属的 WindowToken 以及该 Token 在 layer 11 DisplayArea.Tokens 的位置都不变。WMS 改的是这个 WindowState 的属性和最终计算出的 frame，不是层级归属。

4.4.3 布局、层级和输入一起刷新

接下来 relayoutWindow() 设置请求宽高和可见性，标记 win.mInRelayout，执行：

performSurfacePlacement(true) 驱动 DisplayContent/DisplayPolicy 的布局与 Surface 放置。布局器依据当前 gravity、x/y、窗口请求大小和 Insets 算出新的 WindowFrames；Surface placement 再把对应位置、裁剪、layer、可见性等写入待提交的 SurfaceControl.Transaction。

x/y 移动通常不需要新 Surface。若 WindowState 已有有效 SurfaceControl，服务端在返回结果中给客户端复用它；只有无 Surface 或需替换 Surface 时才由 createSurfaceControl() 设置 RELAYOUT_RES_SURFACE_CHANGED。这也是”移动窗口”通常比”创建窗口”轻的原因。

WMS 还会基于 flags/可见性判断焦点与 IME target 是否可能改变，并在需要时更新 input windows。当前示例带 FLAG_NOT_FOCUSABLE，拖动位置不会让它取得键盘焦点；但其 InputChannel 仍存在，窗口内的触摸命中区域会随新的 frame 更新。

4.5 Surface 与绘制：位置更新不等于一定重建画面

relayout 返回后，ViewRootImpl 接收新的 frame、Insets 和可能变化的 SurfaceControl。若窗口尺寸或视图内容变化，后续 performDraw() 会提交新 buffer；如果只是位置变化，已有 buffer 可以继续由同一 SurfaceControl 展示，WMS 提交的 transaction 已足以把它移动到新的屏幕位置。

不要把每次 updateViewLayout() 都理解成完整的”重新 add + 首帧 finishDrawing“。首帧协议属于 addView 后的首次 traversal；更新路径是对既有窗口与 Surface 的 relayout/placement。若此次更新确实触发新的绘制或同步 draw，客户端仍会按需要报告绘制完成，WMS 再把相应 transaction 纳入 surface placement。

4.6 常见问题与断点

现象 直接原因 检查点
调用后位置没变 传入的不是同一 root、下一帧未执行，或坐标换算错误 WindowManagerGlobal.updateViewLayout 的 index；ViewRootImpl.setLayoutParams；performTraversals 的 params != null
View ... not attached to window manager View 不在 mViews，可能尚未 add 或已移除 deskShowing 与 add/remove 生命周期；不要用重建后的新 View 更新旧窗口
Window type can not be changed after the window is added 试图以 update 修改 LayoutParams.type 移除旧窗口，换 type 后重新 add，并满足新 type 权限
拖动总是偏高 rawY 是屏幕坐标却又扣除了 top（2.6 的遗留问题） 配合 FLAG_LAYOUT_IN_SCREEN 去掉旧的 - top，或统一坐标系
拖动卡顿 高频 relayout 造成 Binder/WMS 布局压力 用 Perfetto 看 ViewRootImpl#performTraversals 和 Session.relayout；只在位置实际变化时更新

推荐断点顺序：

  1. MainActivity.updateDeskPosition()：确认 x/y 的新值；
  2. WindowManagerGlobal.updateViewLayout()：确认 find 到原 View；
  3. ViewRootImpl.setLayoutParams()：看 copyFrom() 的 change mask 与 mWindowAttributesChanged；
  4. ViewRootImpl.performTraversals()：看 params = lp 与 relayoutWindow()；
  5. WindowManagerService.relayoutWindow()：看 windowForClientLocked()、win.mAttrs.copyFrom()、performSurfacePlacement()；
  6. SurfaceFlinger / dumpsys window windows：确认窗口 frame 已随 x/y 变化。
