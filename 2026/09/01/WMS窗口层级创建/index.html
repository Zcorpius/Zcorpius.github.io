2.5 DefaultProvider 备料

五件事，件件对应后面算法的一味输入：

  1. 创建 DefaultTaskDisplayArea——应用层（第 2 层）的容器，将来所有 Task 挂它下面；
  2. 创建 HierarchyBuilder，绑定树的根；
  3. setImeContainer(imeContainer) + setTaskDisplayAreas(tdaList)——把两个”外部预制件“交给 builder（它们在 build 前就已存在，算法只是给它们找位置）；
  4. isTrusted() 才调 configureTrustedHierarchyBuilder()——只有可信屏才有系统装饰。不受信的屏（部分虚拟屏）没有这五大 Feature，树退化成”root 直接挂叶子 + TDA”；
  5. build(wmService)——进入算法本体。

2.6 Feature 声明

五个 Feature 与 dumpsys 里的分组壳一一对应：

声明顺序 Feature（dumpsys 名） 语义 Feature ID
1 WindowedMagnification 窗口放大镜要罩住的层（放大时只需缩放一个 Surface） 4
2 HideDisplayCutout（仅默认屏） 挖孔遮蔽区（状态栏/导航栏/通知面板自己处理挖孔，被排除） 6
3 OneHanded（仅默认屏） 单手模式缩放区（导航栏/安全遮罩不跟着缩，被排除） 3
4 FullscreenMagnification 全屏放大区（输入法/放大镜自身/导航栏不放大，被排除） 5
5 ImePlaceholder 输入法占位（只包输入法主窗口 + 输入法对话框两层） 7

两个要点：

  • addFeature 的顺序 = 树中层级顺序：先声明的 Feature 在树的外层（更靠根）。源码注释明说 “Traverse the features with the order they are defined, so that the early defined feature will be on the top in the hierarchy”——注意”top of the hierarchy”指外层，dump 里 WindowedMagnification:0:31 正是所有 Feature 壳的最外层；
  • HideDisplayCutout/OneHanded 只在默认屏声明（content.isDefaultDisplay）：外接屏没有挖孔、也不做单手模式，所以第一篇 dump 实战里手机/车机的主屏树都有这两层，而外接屏会少。

2.7 Feature 数据结构

核心就是那个 boolean[37]：下标即层号，true 表示”这一层归我管”。五大 Feature 声明完毕后，每人手里一张 37 格的表格——这就是构建算法的全部输入。

3. 层级树创建

3.1 逐 Feature 建骨架

3.1.1 三条不变量

算法开头的大段注释立了三条性质，整个算法就是它们的构造性证明：

  1. 每个 Feature 对应一组 DisplayArea；
  2. 任一窗口加入后，对它所属的每个 Feature，它必定位于该 Feature 对应的某个 DA 之下；
  3. Z 序保持：任意两个 DA 兄弟 a(下)、b(上)，恒有 max(z-range(a)) <= min(z-range(b))——兄弟子树各占连续层区间、互不重叠。这是第一篇里”兄弟下标可当全局 Z 序用”的根源。

3.1.3 手推五个 Feature

初始：root 一层独占 0–36。

Feature 1 WindowedMagnification（0–31）：第 0 层在 root 下建 WM:0，一路复用到 31；32–36 不覆盖。

Feature 2 HideDisplayCutout（0–14, 16, 18–23, 26–35）：0–14 连续一段挂 WM 下；16、18–23、26–31 各一段（父都是 WM）；32–35 这段的父却是 root——因为第 32 层当前归属是 root（WM 只管到 31）。

Feature 3 OneHanded（0–23, 26–32, 34–35）：每层的父 = 该层当前归属者。15 层 HDC 不管 → 父是 WM；26–31 父是 HDC:26:31；32 的父是 HDC:32:35；34–35 的父也是 HDC:32:35（33 被 except，断开成新段）。

Feature 4 FullscreenMagnification（0–12, 15–23, 26–27, 29–31, 33–35）：同样规则，但这个 Feature 最能暴露”复用看父节点”的细节，共产生 9 段：

  • 13–14 被 except → FM:0:12 止步于 12；
  • 15–23 虽然连续覆盖，但每层的当前归属者不同（15→OH:15:15、16→OH:16:16、17→OH:17:17、18–23→OH:18:23），复用条件 featureArea.mParent == areaForLayer[layer] 不成立，切成 4 段；
  • 28 被 except → 26–31 切成 26–27 和 29–31 两段（同父 OH:26:31）；
  • 33 层 OH 不覆盖 → FM:33:33 的父是 HDC:32:35；34–35 的父是 OH:34:35。

Feature 5 ImePlaceholder（13–14）：第 13 层当前的归属者是 OH:0:14（FM 只管到 12），所以 IP 挂在 OH:0:14 下、与 FM:0:12 平级——这是个容易猜错的位置，dump 可以作证。

骨架完成：

对照第一篇 dump 实战章的真机输出：HideDisplayCutout:32:35 挂 Display 直下、ImePlaceholder:13:14 与 FullscreenMagnification:0:12 同为 OneHanded:0:14 的孩子、FullscreenMagnification 同名出现 9 次（0:12 / 15:15 / 16:16 / 17:17 / 18:23 / 26:27 / 29:31 / 33:33 / 34:35）——逐节点吻合。这就是”同名 Feature 多段出现”的由来：它覆盖的层区间被其他 Feature 的 except 切开了，每连续一段一个节点。

3.2 逐层挂叶子

骨架只决定”分组”，真正装窗口的叶子要逐层补上：

3.2.1 三种叶子与复用规则

叶子的类型由 typeOfLayer 决定，只有三种：

层 叶子类型 处理
APPLICATION_LAYER(2) LEAF_TYPE_TASK_CONTAINERS 不建 Tokens，把预制件 DefaultTaskDisplayArea 挂上来（addTaskDisplayAreasToApplicationLayer），mSkipTokens = true
13、14 LEAF_TYPE_IME_CONTAINERS 复用预制件 ImeContainer（mExisting = mImeContainer），mSkipTokens = true
其余 LEAF_TYPE_TOKENS 创建 DisplayArea.Tokens 装系统窗口的 WindowToken

两个标志位的语义（PendingArea 字段）：

  • mExisting：”位置留好了，但东西是现成的”——TDA、ImeContainer、DisplayAreaGroup 根都是 build 前就创建好的容器，算法只负责把它们嵌进正确的层；
  • mSkipTokens：”这个位置不要新建 Tokens 叶子”——上表两种特殊层用。

复用条件解释了叶子区间为什么可长可短：相邻层只要”同父 + 同类型”就共用一个叶子往外延伸——Leaf:0:1（第 1 层=壁纸，第 0 层没有任何窗口类型映射）、Leaf:3:12（十层共用）、Leaf:16:16（单层）都是这条规则的产物。第 24–25 层被 HDC/OH/FM 全部 except（只有 WM 仍覆盖），归属者是 WM 本尊，所以 Leaf:24:25 直接挂在 WM:0:31 下——注意仍在 WM 壳内，并非无壳。

3.3 创建真实 DisplayArea

骨架是临时的 PendingArea，最后一步”转正”：

3.3.1 自底向上算区间右端点

每个节点的 max = 自己已知值与所有孩子 max 的最大值——递归一趟，全树名字里的 :max 就齐了。

3.3.2 排序、转正、挂树

① 保证真实树里孩子按层区间升序排列——下标顺序 = Z 序（第一篇 2.2 的不变量从这里兑现）。

3.3.3 createArea：四种情况

情况 条件 产物 名字
一 mExisting != null 预制件本身（TDA / ImeContainer / DAG 根） 原名（如 DefaultTaskDisplayArea）
二 mSkipTokens 且无 mExisting null（跳过，不生成节点） —
三 无 Feature DisplayArea.Tokens 叶子 Leaf:min:max
四 有 Feature mNewDisplayAreaSupplier 创建的 DA（WindowedMagnification 用 DisplayArea.Dimmable） Feature名:min:max

ABOVE_TASKS / BELOW_TASKS / ANY 由区间相对 APPLICATION_LAYER=2 的位置判定——这正是第一篇家族篇里 DisplayArea 三种”口味”的来源：壁纸叶子（max<2）永远 BELOW、状态栏叶子（min>2）永远 ABOVE，从类型系统上保证壁纸插不到应用上面。

3.3.4 建成之后：两张快查表

fillAreaForLayers 把每个 Tokens 叶子登记进 displayAreaForLayer[layer]；onHierarchyBuilt 把两张表缓存到 RootDisplayArea，并带”只能建一次”的断言（mHasBuiltHierarchy）。运行时新窗口注册时，DisplayContent.addWindowToken 对非 App token 走 findAreaForToken(token).asTokens().addChild(token)，与下面的 Result.addWindow 同一条链路——按 layer 查表（RootDisplayArea.mAreaForLayer[layer]）找到归属的 Tokens，不用遍历树：

查表函数 RootDisplayArea.findAreaForWindowTypeInLayer 里还有一道防线：type 算出的 layer 若等于 APPLICATION_LAYER 会直接抛 IllegalArgumentException——应用窗口不走 token 通道，Task 全部由 TDA 一族管理。

至此闭环：Feature 声明 → boolean[37] → PendingArea 骨架 → 挂叶子 → 转正 → 查表落位。最终树的形态，与第一篇 dump 实战章的精简树（骨架五个 Feature 壳 + 三类叶子）逐节点一致，可用 adb shell dumpsys activity containers 复核。

4. 厂商与多区屏定制

4.1 整套替换：自定义 Provider

实现 DisplayAreaPolicy.Provider 并配置资源 config_deviceSpecificDisplayAreaPolicyProvider（第 2.1 章的反射装载），即可替换整套层级树——常见于车机/折叠屏：声明自己的 Feature 列表（如”仪表区/导航区/副驾娱乐区”各一个壳），或重排系统窗口分层。Feature ID 厂商区间从 FEATURE_VENDOR_FIRST = FEATURE_SYSTEM_LAST + 1 = 10001 起。

4.2 屏内分区：DisplayAreaGroup

build() 有个带参重载 build(displayAreaGroupHierarchyBuilders)：多块应用区（DisplayAreaGroup，各自是一棵小 DA 树，至少含一个 TDA）时，3.2 节的 addDisplayAreaGroupsToApplicationLayer 会把各 Group 根作为”预制件”（mExisting）挂到应用层——对应车机主驾/副驾同屏两区、或大屏多窗口的形态。

Note

AOSP 15 还引入了 FEATURE_WINDOWING_LAYER（ID=9）。外层 Result build(WindowManagerService) 开头会检查首个 Feature 是否为窗口化层（WindowedMagnification 或 WindowingLayer 二者之一，见 canBeWindowingLayer）——默认策略首个就是 WindowedMagnification，无需动作；若厂商自定义策略的首个 Feature 不合规，会自动在最外层补插一个全层的 WindowingLayer 壳（屏幕级动画用），且它 setExcludeRoundedCornerOverlay(false)——唯独这个壳包含第 36 层。外层 build 与内层 HierarchyBuilder.build 的分工：外层只做”补壳 + validate + 编排主树/子树先后 + 组装 Result”，三步算法全在内层。

5. 小结

三个最值得带走的结论：

  1. 树 = 五张 boolean[37] 的确定性函数：dump 里一切”奇怪”的形态（同名多段、ImePlaceholder 挂 OH 下、Leaf:36 直挂 Display、Leaf:24:25 只剩 WM 壳）都能从 2.10 那张区间表手推出来；
  2. 声明顺序即层级：addFeature 在前的更靠外层；except 切开区间 → 同名多段；
  3. 预制件 + 查表：TDA/ImeContainer 是 build 前就造好的”现成品”，算法只负责安排位置；建成后按 layer 查表落位，树只用于结构与 Z 序，不承担查找。
