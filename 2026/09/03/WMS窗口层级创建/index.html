    2. ATMS 先于 WMS 启动，因为 WMS 构造需要它；InputManagerService 此时已创建，但其 start() 在后续 wm.onInitReady() 之后才调用。

2.2 确定策略 Provider

构造器后段那行 Provider.fromResources(...) 读取资源字符串 config_deviceSpecificDisplayAreaPolicyProvider：

策略根据TextUtils.isEmpty(name) 分成如下情况：

  • 为空，则默认 DefaultProvider
  • 非空，则反射实例化厂商自定义类（必须有无参构造并实现 Provider）。这是车机/折叠屏定制整套层级树的官方入口。

Note

注意 return new DisplayAreaPolicy.DefaultProvider(); 这行只创建、不调用：new 只会运行构造器，而 DefaultProvider 既没写构造器、也没有实例字段，走的是编译器生成的空构造器。所以除了造出一个对象，什么代码都没执行。

instantiate() 的方法体此刻一个字节都没跑，要等 DisplayContent 中 .instantiate(...) 才第一次执行。

而且这个对象无状态、可复用：每来一块屏（开机首屏、热插拔的每一块）都调它一次 instantiate，每次产出一份新 Result 成品，这正是 工厂 1 份、成品每屏 1 份 的代码基础。

Important

注意到此为止只是备好了工厂：Provider 全局一份、本身不持有任何树，它只回答”这台设备用哪套策略”。真正投产是每块屏创建时对工厂的一次调用。

这边可能对概念上的理解有偏离，可以把概念摆一起看下：

概念 归属 是什么
Display DisplayManagerService 屏幕的参数抽象：尺寸、density、rotation（物理屏 / HDMI / 虚拟屏）
DisplayContent WMS 这块屏的窗口容器（该屏层级树的根+大管家），持有一份DisplayAreaPolicy
画面内容 SurfaceFlinger 各 WindowState 的 Surface，按 DisplayContent 组织的层级顺序合成出来

Note

最容易误解的是 DisplayContent 这个名字——它不持有任何像素内容，既没有位图也没有缓冲区；它管理的是这块屏上的窗口层级结构（Z 序、旋转、动画、insets、焦点、布局都以它为单位）。

又因为 class DisplayContent extends RootDisplayArea，它不是”包含”一棵树，而是 它本身就是这棵树的根，树上挂的 WindowState 才是有画面的东西，它只负责组织它们谁上谁下。

2.4 DisplayContent 屏构建

接着看 2.3 中遍历屏幕的循环：每拿到一个 Display，就创建一个 DisplayContent。在这个构造器里，WMS 会取出唯一的 DisplayAreaPolicy.Provider，并调用它的 instantiate()，为当前这块屏构建 DisplayArea 树、返回对应的 DisplayAreaPolicy。

换句话说，Provider 是 WMS 全局共享的一份工厂；DisplayAreaPolicy 及其管理的层级树，则是每个 DisplayContent 各自拥有的一份成品：

instantiate(...) 是进入 2.5 的唯一入口。按 Java 的求值顺序，这一行可以理解成下面三步：

  1. 取回 WMS 的 mDisplayAreaPolicyProvider 字段。它在 2.2 的 fromResources() 中已经创建，这里既不会重新读资源，也不会创建新的 Provider。
  2. 真正的建树调用。变量的静态类型是 Provider，但运行时会按对象的实际类型分派：默认配置进入 DefaultProvider.instantiate()，厂商配置则进入自己的实现。这个调用在当前线程同步执行，没有 Binder、Handler 或其他中转；2.5 的代码正是从这里开始运行。
  3. 在 instantiate() 返回之后。此时它已经完成 Feature 配置和 3.x 的建树流程，并返回 DisplayAreaPolicyBuilder.Result；返回值随后才写入 mDisplayAreaPolicy。因此执行到下一行 getPendingTransaction() 时，DA 树已经建好。

Important

2.2 创建工厂，2.4 使用工厂建树：new WindowManagerService(...) 期间，Provider.fromResources() 只创建并保存一份 DefaultProvider（或厂商 Provider），此时还没有 DisplayArea 树。

后续每次 new DisplayContent(...)，才取回这份既有 Provider 并调用 instantiate()，为当前这块屏创建独立的 DisplayAreaPolicy 与 DA 层级树。

2.5 DefaultProvider 投产

这一节不是在 2.2 创建 Provider 时执行的。它的入口是 2.4 中的 provider.instantiate(...)：当 Provider 的实际类型为 AOSP 默认的 DefaultProvider 时，虚方法分派会进入下面的 instantiate()。

如果设备配置了厂商 Provider，则会在同一个调用点进入厂商实现，而不会执行本节这份默认代码。

五件事，件件对应后面算法的一味输入：

  1. 创建 DefaultTaskDisplayArea——应用层（第 2 层）的容器，将来所有 Task 挂它下面；
  2. 创建 HierarchyBuilder，绑定树的根；
  3. setImeContainer(imeContainer) + setTaskDisplayAreas(tdaList)，把两个”外部预制件“交给 builder
  4. 可信屏才有系统装饰 `configureTrustedHierarchyBuilder()。不受信的屏（部分虚拟屏）没有这五大 Feature，树退化成”root 直接挂叶子 + TDA”；
  5. build(wmService)——进入算法本体。

2.5.1 Feature 构建与添加

Feature 可以先理解为一条“层覆盖规则”，不是已经挂到树上的 DisplayArea。它记录 0～36 个窗口 layer 中哪些层需要被某项功能包裹，以及将来创建对应 DA 时使用的名称、ID 和类型。

本节通过 Feature.Builder 构建这些规则，再用 rootHierarchy.addFeature(...) 注册给 builder；第 3 章才会根据这些规则创建真实的 DA 节点。

五个 Feature 与 dumpsys 里的分组壳一一对应：

声明顺序 Feature（dumpsys 名） 语义 Feature ID
1 WindowedMagnification 窗口放大镜要罩住的层（放大时只需缩放一个 Surface） 4
2 HideDisplayCutout（仅默认屏） 挖孔遮蔽区（状态栏/导航栏/通知面板自己处理挖孔，被排除） 6
3 OneHanded（仅默认屏） 单手模式缩放区（导航栏/安全遮罩不跟着缩，被排除） 3
4 FullscreenMagnification 全屏放大区（输入法/放大镜自身/导航栏不放大，被排除） 5
5 ImePlaceholder 输入法占位（只包输入法主窗口 + 输入法对话框两层） 7

两个要点：

  • addFeature 的顺序 = 树中层级顺序：先声明的 Feature 在树的外层（更靠根）。源码注释明说 “Traverse the features with the order they are defined, so that the early defined feature will be on the top in the hierarchy”——注意”top of the hierarchy”指外层，dump 里 WindowedMagnification:0:31 正是所有 Feature 壳的最外层；
  • HideDisplayCutout/OneHanded 只在默认屏声明（content.isDefaultDisplay）：外接屏没有挖孔、也不做单手模式，所以第一篇 dump 实战里手机/车机的主屏树都有这两层，而外接屏会少。

2.5.2 Feature 数据结构

核心就是那个 boolean[37]：下标即层号，true 表示”这一层归我管”。五大 Feature 声明完毕后，每人手里一张 37 格的表格——这就是构建算法的全部输入。

2.5.3 Feature.Builder：层覆盖规则

方法 语义 例子
all() 全部 37 层先置 true HideDisplayCutout.all()
and(t...) 只把这几个 type 对应的层置 true ImePlaceholder.and(IME, IME_DIALOG)
except(t...) 把这几个 type 对应的层置 false（从已选中剔除） .except(NAVIGATION_BAR, ...)
upTo(t) 第 0 层到 t 所在层（含）全置 true WindowedMagnification.upTo(放大镜遮罩)

（应用窗口统一 APPLICATION_LAYER=2、TYPE_WALLPAPER=1、TYPE_NAVIGATION_BAR=24……上限 getMaxWindowLayer()=36）。

2.5.4 Feature.Builder.build()：排除圆角层

mExcludeRoundedCorner 默认 true：第 36 层（圆角/屏幕装饰遮罩）被强制从所有 Feature 中剔除。所以 dump 树里 Leaf:36:36 直接挂在 DisplayContent 下、不被任何 Feature 壳包裹。装饰遮罩必须永远压在一切（包括放大镜）之上，连”放大”都不能作用于它。

2.5.6 概念对照：从规则到真实树

先记住两条关系：

概念 本质 创建/产生时机 是否为真实树节点 与其他概念的关系
window type WindowManager.LayoutParams.type，表示窗口种类 创建窗口时由调用方指定 否 WMS 根据 type 计算它所属的 window layer
window layer 0～36 的逻辑层编号，用于确定窗口类别的基础 Z 序 WindowManagerPolicy.getWindowLayerFromTypeLw() 根据 type 计算 否 是 Feature 的匹配对象，也是建树后查找 Tokens 叶子的索引
Feature 一条“层覆盖规则”，内部用 boolean[37] 记录自己覆盖哪些 layer 2.5 中由 Feature.Builder 构建 否 Builder 根据它创建功能容器；一个 Feature 可能因覆盖区间被切开而对应多个 DisplayArea 节点
HierarchyBuilder 收集 Feature、TaskDisplayArea、IME 容器并执行建树算法的构建器 DefaultProvider.instantiate() 中创建 否 以 Feature 和各类预制件为输入，生成 PendingArea，最后产出真实树
PendingArea 建树期间使用的草稿节点，记录父子关系、Feature、layer 区间和预制件 第 3.1、3.2 节的 Builder 算法中产生 否 结构确定后，由 instantiateChildren() 转成或复用真实 DisplayArea
DisplayArea WMS 层级树中的真实容器节点 部分节点在 2.5 预先创建，其余在第 3.3 节创建并挂树 是 Feature 对应的功能壳、Tokens 叶子和 TaskDisplayArea 都属于 DisplayArea 体系
DisplayArea.Tokens 承载非应用 WindowToken 的叶子节点 普通 Tokens 叶子在第 3.3 节创建；IME 容器是提前准备的特殊 Tokens 是 建树后通过 layer → Tokens 索引，让非应用窗口快速找到归属位置
TaskDisplayArea 专门承载 Task/ActivityRecord 的 DisplayArea 默认 TDA 在 DefaultProvider.instantiate() 中预先创建 是 占据应用层位置；应用窗口走 Task 体系，不走普通 Tokens 叶子
RootDisplayArea DisplayArea 层级根节点的基类，提供 Feature、layer 映射及区域查找等能力 每块屏的主层级根由其子类 DisplayContent 创建；策略也可以创建其他 RootDisplayArea 是 定义“DisplayArea 树根”具备的通用能力，本身不等同于某块具体 Display
DisplayContent 表示一块具体 Display 的容器，继承 RootDisplayArea RootWindowContainer 遍历 Display 时通过 new DisplayContent(...) 创建 是 它是该屏主 DisplayArea 层级的实际根节点；Provider 以它为根建立这块屏的子树
DisplayAreaPolicy.Provider 创建策略的工厂 2.2 中由 fromResources() 创建，全局通常一份 否 每次 instantiate() 为一块 Display 生产一份 Policy
DisplayAreaPolicy 某块 Display 的建树成品及运行时操作接口 本次 instantiate() 完成并返回时产生 否 持有建树结果和查找能力；Provider 一份，Policy 每屏一份

最容易混淆的是：layer 是编号，Feature 是规则，PendingArea 是草稿，DisplayArea 才是真实节点；Provider 是工厂，Policy 是每块屏的成品。

Important

WMS 先创建 Provider；每个 DisplayContent 调用 Provider 的 instantiate()，以 Feature 和 layer 为输入，经 PendingArea 中间结构创建真实 DisplayArea 树，最终得到每屏独立的 DisplayAreaPolicy。

            DC->>DC: mDisplayAreaPolicy = 返回值
            DC->>DC: configureSurfaces() / apply()
建立 DisplayContent 的 Surface 层级
            DC-->>RWC: 构造完成（屏内 DA 树已建好）
            deactivate DC
            RWC->>RWC: addChild(displayContent)
把该屏接入设备总根
        end
    end
    RWC->>RWC: 创建默认屏 Home 根 Task，并调整默认屏位置
    RWC-->>ATMS: 首批屏初始化完成
    deactivate RWC
    ATMS-->>AMS: setWindowManager() 返回
    deactivate ATMS
    AMS-->>SS: setWindowManager() 返回
    deactivate AMS

图里每一段对应的事情是：

  1. 2.3：找到屏并接入设备总根。 RootWindowContainer 先遍历当前 Display；每个 DisplayContent 构造完成后，才通过 addChild 挂到 RootWindowContainer 下。默认屏随后会创建 Home 根 Task。
  2. 2.4：使用已存在的工厂。 Provider 早在 2.2 的 fromResources() 中创建；DisplayContent 只取回同一个对象，并把当前屏的 this、预制 IME 容器等输入传给 instantiate()。
  3. 2.5：默认 Provider 准备规则和预制件。 它创建默认 TDA，把 TDA / IME 容器交给 HierarchyBuilder，再为可信屏添加 Feature 规则；最后调用 DisplayAreaPolicyBuilder.build()。
  4. 第 3 章：完成真正的 DA 挂树。 build() 在同一次同步调用中继续执行：先生成 PendingArea 骨架，再补叶子，最后转成真实 DisplayArea 并挂到这块屏的 DisplayContent 下。只有它返回后，mDisplayAreaPolicy 才会得到值。

因此，2.2 是“造工厂”，2.3 是“逐屏启动建树”，2.4 是“调用工厂”，2.5 是“默认方案备料并交给算法”，第 3 章才展开算法如何产出整棵真实 DA 树；运行时这些步骤没有异步断点，会在一次 new DisplayContent(...) 中连续完成。

3. 层级树创建

3.1 逐 Feature 建骨架

3.1.1 三条不变量

算法开头的大段注释立了三条性质，整个算法就是它们的构造性证明：

  1. 每个 Feature 对应一组 DisplayArea；
  2. 任一窗口加入后，对它所属的每个 Feature，它必定位于该 Feature 对应的某个 DA 之下；
  3. Z 序保持：任意两个 DA 兄弟 a(下)、b(上)，恒有 max(z-range(a)) <= min(z-range(b))。兄弟子树各占连续层区间、互不重叠。这是第一篇里”兄弟下标可当全局 Z 序用”的根源。

3.1.3 手推默认五个 Feature

初始：root 一层独占 0–36。

Feature 1 WindowedMagnification（0–31）：第 0 层在 root 下建 WM:0，一路复用到 31；32–36 不覆盖。

蓝色 WM 只接管 0–31；32–36 的当前归属仍是 root，是下一次叠加 Feature 时判定父节点的起点。

Feature 2 HideDisplayCutout（0–14, 16, 18–23, 26–35）：0–14 连续一段挂 WM 下；16、18–23、26–31 各一段（父都是 WM）；32–35 这段的父却是 root——因为第 32 层当前归属是 root（WM 只管到 31）。

HDC 被拆为五段：除了 except 会断开，32–35 的当前归属者从 WM 变回 root，也必须新开一段。

Feature 3 OneHanded（0–23, 26–32, 34–35）：每层的父 = 该层当前归属者。15 层 HDC 不管 → 父是 WM；26–31 父是 HDC:26:31；32 的父是 HDC:32:35；34–35 的父也是 HDC:32:35（33 被 except，断开成新段）。

OH 不会固定挂在某一个 Feature 下：15、17 层的父是 WM，32、34–35 层的父则是 root 直下的 HDC:32:35。

Feature 4 FullscreenMagnification（0–12, 15–23, 26–27, 29–31, 33–35）：同样规则，但这个 Feature 最能暴露”复用看父节点”的细节，共产生 9 段：

  • 13–14 被 except → FM:0:12 止步于 12；
  • 15–23 虽然连续覆盖，但每层的当前归属者不同（15→OH:15:15、16→OH:16:16、17→OH:17:17、18–23→OH:18:23），复用条件 featureArea.mParent == areaForLayer[layer] 不成立，切成 4 段；
  • 28 被 except → 26–31 切成 26–27 和 29–31 两段（同父 OH:26:31）；
  • 33 层 OH 不覆盖 → FM:33:33 的父是 HDC:32:35；34–35 的父是 OH:34:35。

FM 的九段由两类边界共同决定：except 打断连续 layer，当前归属者变化则打断可复用的父节点；33 层直接挂在 HDC:32:35 下。

Feature 5 ImePlaceholder（13–14）：第 13 层当前的归属者是 OH:0:14（FM 只管到 12），所以 IP 挂在 OH:0:14 下、与 FM:0:12 平级——这是个容易猜错的位置，dump 可以作证。

骨架完成：

IP 在这里仍只是 PendingArea 骨架中的占位段；它和 FM:0:12 同为 OH:0:14 的孩子。真正的 ImeContainer 要到 3.2 挂叶子、3.3 转正时才出现。

对照第一篇 dump 实战章的真机输出：HideDisplayCutout:32:35 挂 Display 直下、ImePlaceholder:13:14 与 FullscreenMagnification:0:12 同为 OneHanded:0:14 的孩子、FullscreenMagnification 同名出现 9 次（0:12 / 15:15 / 16:16 / 17:17 / 18:23 / 26:27 / 29:31 / 33:33 / 34:35）——逐节点吻合。这就是”同名 Feature 多段出现”的由来：它覆盖的层区间被其他 Feature 的 except 切开了，每连续一段一个节点。

3.2 逐层挂叶子

骨架只决定”分组”，真正装窗口的叶子要逐层补上：

3.2.1 三种叶子与复用规则

叶子的类型由 typeOfLayer 决定，只有三种：

层 叶子类型 处理
APPLICATION_LAYER(2) LEAF_TYPE_TASK_CONTAINERS 不建 Tokens，把预制件 DefaultTaskDisplayArea 挂上来（addTaskDisplayAreasToApplicationLayer），mSkipTokens = true
13、14 LEAF_TYPE_IME_CONTAINERS 复用预制件 ImeContainer（mExisting = mImeContainer），mSkipTokens = true
其余 LEAF_TYPE_TOKENS 创建 DisplayArea.Tokens 装系统窗口的 WindowToken

两个标志位的语义（PendingArea 字段）：

  • mExisting：”位置留好了，但东西是现成的”——TDA、ImeContainer、DisplayAreaGroup 根都是 build 前就创建好的容器，算法只负责把它们嵌进正确的层；
  • mSkipTokens：”这个位置不要新建 Tokens 叶子”——上表两种特殊层用。

复用条件解释了叶子区间为什么可长可短：相邻层只要”同父 + 同类型”就共用一个叶子往外延伸——Leaf:0:1（第 1 层=壁纸，第 0 层没有任何窗口类型映射）、Leaf:3:12（十层共用）、Leaf:16:16（单层）都是这条规则的产物。第 24–25 层被 HDC/OH/FM 全部 except（只有 WM 仍覆盖），归属者是 WM 本尊，所以 Leaf:24:25 直接挂在 WM:0:31 下——注意仍在 WM 壳内，并非无壳。

3.2.2 按层手推叶子

循环从 layer 0 升到 36，每枚新叶子的父 = 该层在 Step 1 结束时的归属者（areaForLayer[layer]，对照 3.1.3 骨架图）。按扫过的区域分四段：

阶段 ① layer 0–14：OH:0:14 子树装满。 layer 0 在 FM:0:12 下新建 Tokens 叶（0 层无任何窗口类型映射，纯占位），layer 1 同父同类型延伸成 Leaf:0:1；layer 2 类型变 TASK_CONTAINERS → 建 skip 占位叶、挂预制件 TDA；layer 3 类型变回 → Leaf:3:12 一路延伸到 12；13–14 变 IME_CONTAINERS → ImePlaceholder:13:14 下挂预制件 ImeContainer：

这段同时出现三种叶子处理：普通层合并为 Leaf:0:1、Leaf:3:12，layer 2 插入预制 TDA，13–14 插入预制 ImeContainer。

阶段 ② layer 15–23：四个中带段。 15/16/17 每层的父都变（FM:15:15 / FM:16:16 / FM:17:17）→ 三枚单层叶；18–23 同父 FM:18:23 → 一枚六层叶：

连续 layer 不等于能合并：15、16、17 的当前父节点不同，各自产生单层 Leaf；18–23 才满足“同父 + 同类型”，延伸为同一枚 Leaf。

阶段 ③ layer 24–31：一处”失壳”、一处夹层。 24–25 被 HDC/OH/FM 全部 except（只剩 WM 仍覆盖）→ 归属者是 WM 本人，Leaf:24:25 直挂 WM；26–27 与 29–31 各归一段 FM；28 被 FM except、归属落回 OH:26:31 → 单层 Leaf:28:28 夹在两个 FM 段中间：

Leaf:24:25 是“少壳”而非无壳——仍直挂 WM；28 则只失去 FM 壳，因此回退到 OH:26:31，夹在两段 FM 之间。

阶段 ④ layer 32–36：高带与顶层。 32/33 各一枚单层叶，34–35 同父延伸；最后 36 被所有 Feature 排除（2.5.4 的强制规则）→ 父是 root 本人：

36 才是彻底“无壳”：它不在任何 Feature 下，Leaf:36:36 直接成为 root 的孩子。

四段拼起来——PendingArea 草图树全貌（骨架 + 16 个装窗口的叶子 = 14 枚 Leaf + TDA + ImeContainer；另有 1 枚 skip 占位叶——layer 2 那枚——转正时返回 null 丢弃，layer 13 那枚带着 mExisting = ImeContainer，转正产物就是 ImeContainer 本身）：

总览按四段展开而非硬塞一棵密集连线树：上方先确认 root 的三个直接孩子（WM、HDC:32:35、Leaf:36），下方再逐段核对每枚叶子的真实父节点。

与第一篇 dump 实战章逐节点一致，三处最值得对照：FM:0:12 的孩子下标 #0/#1/#2 = Leaf:0:1 / TDA / Leaf:3:12（出生层 0/2/3，Step 3 按 mMinLayer 排序即得）；OH:26:31 的三孩子中间夹着 Leaf:28:28；Leaf:24:25 与 Leaf:36:36 一个”少壳”一个”无壳”，成因不同（前者被 HDC/OH/FM except、只剩 WM 壳，后者被 2.5.4 的强制规则排除、真正直挂 root）。至此草图树完整，只差最后一步”转正”（3.3）。

3.3.1 自底向上算区间右端点

每个节点的 max = 自己已知值与所有孩子 max 的最大值——递归一趟，全树名字里的 :max 就齐了。

① 保证真实树里孩子按层区间升序排列——下标顺序 = Z 序（第一篇 2.2 的不变量从这里兑现）。

情况 条件 产物 名字
一 mExisting != null 预制件本身（TDA / ImeContainer / DAG 根） 原名（如 DefaultTaskDisplayArea）
二 mSkipTokens 且无 mExisting null（跳过，不生成节点） —
三 无 Feature DisplayArea.Tokens 叶子 Leaf:min:max

4. 厂商与多区屏定制

4.1 整套替换：自定义 Provider

实现 DisplayAreaPolicy.Provider 并配置资源 config_deviceSpecificDisplayAreaPolicyProvider（第 2.2 章的反射装载），即可替换整套层级树。常见于车机/折叠屏：声明自己的 Feature 列表（如”仪表区/导航区/副驾娱乐区”各一个壳），或重排系统窗口分层。Feature ID 厂商区间从 FEATURE_VENDOR_FIRST = FEATURE_SYSTEM_LAST + 1 = 10001 起。

4.2 屏内分区：DisplayAreaGroup

build() 有个带参重载 build(displayAreaGroupHierarchyBuilders)：多块应用区（DisplayAreaGroup，各自是一棵小 DA 树，至少含一个 TDA）时，3.2 节的 addDisplayAreaGroupsToApplicationLayer 会把各 Group 根作为”预制件”（mExisting）挂到应用层——对应车机主驾/副驾同屏两区、或大屏多窗口的形态。

Note

AOSP 15 还引入了 FEATURE_WINDOWING_LAYER（ID=9）。外层 Result build(WindowManagerService) 开头会检查首个 Feature 是否为窗口化层（WindowedMagnification 或 WindowingLayer 二者之一，见 canBeWindowingLayer）。

默认策略首个就是 WindowedMagnification，无需动作；若厂商自定义策略首个 Feature 不合规，会自动在最外层补插一个全层的 WindowingLayer 壳（屏幕级动画用），且它 setExcludeRoundedCornerOverlay(false)。 唯独这个壳包含第 36 层。外层 build 与内层 HierarchyBuilder.build 的分工：外层只做”补壳 + validate + 编排主树/子树先后 + 组装 Result”，三步算法全在内层。

5. 学习建议

DisplayArea 建树同时包含调用链、对象关系和构建算法，第一次阅读很难一次全部记住。不要从五个 Feature 的 layer 区间或两个 build() 开始背，应该先建立一条稳定主线，再逐层补充细节。

5.1 第一遍：先记住一个故事

WMS 先准备一个工厂；ATMS 启动建屏；每块屏调用工厂；工厂拿 Feature 和 layer 建树；最终得到每屏独立的 Policy。

可以压缩成一句口诀：一厂、多屏、两种材料、三步建树、一个成品。

口诀 对应源码概念 先记住什么
一厂 DisplayAreaPolicy.Provider WMS 构造期间创建，全局通常只有一份
多屏 DisplayContent 每块 Display 创建一个，各自拥有独立的 DisplayArea 子树
两种材料 Feature + 0～36 layer Feature 决定“怎样分组”，layer 决定“按什么 Z 序排列”
三步建树 HierarchyBuilder.build() Feature 建骨架 → layer 补叶子 → PendingArea 转正
一个成品 DisplayAreaPolicy 每次 instantiate() 为当前 Display 返回一份 Policy

严格来说，Builder 还会接收 TaskDisplayArea、IME 容器等预制件；第一遍先把它们视为要放进树里的特殊叶子，等主线稳定后再区分。

WMS 构造时只创建 Provider。ATMS 初始化窗口管理树时，会为每块屏创建 DisplayContent。DisplayContent 调用 Provider 的 instantiate()，以 Feature 和 layer 为输入，通过“建骨架、补叶子、转真实节点”三步创建 DisplayArea 树，最后得到每屏独立的 DisplayAreaPolicy。

能稳定讲出这段，已经掌握了本文骨架。源码细节按下面的顺序继续补充：

  1. Provider 与 Policy 为什么是“一份工厂、每屏一份成品”；
  2. Feature、PendingArea、DisplayArea 为什么不能混为一谈；
  3. 外层 DisplayAreaPolicyBuilder.build() 与内层 HierarchyBuilder.build() 的职责；
  4. 五个默认 Feature 各自解决什么问题；
  5. 最后才根据 Builder API 推导各 Feature 的精确 layer 区间。

不需要死记 0～36 每一层对应的窗口类型，也不需要逐字背五个 Feature 的所有 except() 参数；面试更重要的是能根据规则解释树为什么形成当前结构。

5.6 用断点和 dumpsys 巩固

  • 在 DisplayAreaPolicy.java 打断点，一次观察完整调用栈：SystemServer.startOtherServices()
    → AMS/ATMS setWindowManager → 建屏循环 → DisplayContent 构造器 → DefaultProvider.instantiate；
  • 手推完 3.2.2 的草图树，再用 adb shell dumpsys activity containers 拉取真机树逐节点对照；
  • 修改一个 Feature 的 except() 列表，例如让导航栏重新进入 HideDisplayCutout 的覆盖范围，重跑后观察树形变化。一次实际对照通常比反复阅读 build() 更容易形成记忆。

6. 面试题梳理

本文对应的核心面试题只有一条：WMS 在启动阶段，如何为每块 Display 创建窗口层级树？

面试时应先把这条主线讲完整，再根据追问展开 Provider、Feature 和 DisplayAreaPolicyBuilder。下面按真实的追问顺序梳理，不把加窗、布局、焦点等其他 WMS 主题混进来。

6.1 主问题：WMS 窗口层级树是怎样创建的？

推荐回答

SystemServer 创建 WMS 时，WMS 构造器先创建一个空的 RootWindowContainer，并通过 DisplayAreaPolicy.Provider.fromResources() 创建全局唯一的策略工厂 Provider。此时还没有为各块屏幕创建 DisplayArea 树。

随后 SystemServer 调用 AMS.setWindowManager(wm)，再转到 ATMS.setWindowManager(wm)。ATMS 取得 wm.mRoot，因此 ATMS 与 WMS 开始共享同一个 RootWindowContainer。之后调用 RootWindowContainer.setWindowManager(wm)，遍历当前所有 Display，为每块屏创建一个 DisplayContent。

在 DisplayContent 构造期间，会调用全局 Provider 的 instantiate(...)。如果使用 AOSP 默认实现，运行时进入 DefaultProvider.instantiate()：先准备 DefaultTaskDisplayArea、IME 容器和默认 Feature 规则，再交给 DisplayAreaPolicyBuilder 建树。

Builder 先按 Feature 生成 PendingArea 骨架，再按 0～36 层补齐叶子，最后把预制件和新建节点转成真实的 DisplayArea 树，同时生成 layer 到 DisplayArea.Tokens 的索引。instantiate() 返回后，这块屏才获得自己的 DisplayAreaPolicy 成品。

6.2 第一轮追问：创建时机与对象关系

1. WMS 构造完成时，整棵窗口层级树已经创建好了吗？

没有。WMS 构造器主要完成两件与本文有关的事：创建空的 RootWindowContainer，以及通过 fromResources() 创建 Provider。真正的每屏建树，要等到 new DisplayContent(...) 中调用 provider.instantiate(...)。

2. fromResources() 和 instantiate() 分别做什么？

  • fromResources()：读取资源配置，创建 AOSP 默认 Provider 或厂商 Provider；
  • instantiate()：使用这个 Provider，为当前 Display 生产一份 DisplayAreaPolicy，并在过程中完成该屏的 DisplayArea 建树。

一句话概括：前者选工厂，后者用工厂生产每块屏的成品。

3. 为什么建树入口在 DisplayContent 构造器中？

因为 DisplayArea 树是屏幕级结构。每个 DisplayContent 表示一块 Display，并且自身就是这块屏的 RootDisplayArea；只有创建具体 DisplayContent 时，Provider 才能拿到这块屏的根、IME 容器等参数，构造专属于它的策略和子树。

4. 为什么 Provider 全局一份，而 Policy 每屏一份？

Provider 只封装“如何创建策略”，本身不保存某块屏的容器树；Policy 则持有具体 Display 的树和运行时查询接口。因此同一个 Provider 可以反复调用，而每次 instantiate() 都会得到不同 Display 的 Policy。

5. ATMS 为什么要取得 wm.mRoot？

这样 ATMS 与 WMS 操作的是同一个 RootWindowContainer，而不是各自维护一棵树。ATMS 管理的 Task、ActivityRecord 与 WMS 管理的 DisplayArea、WindowToken、WindowState，最终都处在这棵共享容器树中。

6.3 第二轮追问：Feature 与建树算法

6. 0～36 层是不是 37 个 Feature？

不是。0～36 是窗口 layer，用来表达窗口的 Z 序；Feature 是一条层覆盖规则，描述哪些 layer 需要被某种功能容器包裹。一个 Feature 可以覆盖多个 layer，同一个 layer 也可能同时命中多个 Feature，最终形成嵌套的 DisplayArea。

7. Feature 本身是不是树中的 DisplayArea 节点？

不是。Feature 只保存名称、ID、覆盖层集合以及节点创建方式等规则。Builder 处理 Feature 后，才会创建对应的 DisplayArea 节点。应区分：Feature 是建树规则，DisplayArea 是建树结果。

8. DefaultProvider.instantiate() 主要做了什么？

它先创建或取得几个必须复用的预制件，包括默认 TaskDisplayArea 和 IME 容器；然后创建 HierarchyBuilder，设置这些预制件，添加默认 Feature；最后调用 Builder 的 build()。因此 2.5 的职责是“准备材料并启动算法”，不是独立于第 3 章的另一条流程。

9. DisplayAreaPolicyBuilder 怎样把规则变成树？

分三步：

  1. 遍历 Feature，为连续覆盖的 layer 区间创建 PendingArea 骨架；
  2. 遍历 0～36 层，把 TaskDisplayArea、IME 容器和普通 Tokens 叶子放入正确位置；
  3. 计算各 PendingArea 的层区间，按 Z 序递归创建或复用真实节点，并通过 addChild() 挂树。

可以记成：Feature 建骨架 → layer 补叶子 → PendingArea 转正。

10. 为什么需要 PendingArea，不能直接创建 DisplayArea 吗？

建树过程中还要确定节点的父子关系、连续 layer 区间以及预制件应放的位置。PendingArea 是中间态，先记录结构和范围，等关系全部确定后再统一实例化，可以避免一边分析规则一边反复调整真实容器树。

11. 多个 Feature 同时覆盖一个 layer 时，怎样保证原有 Z 序不乱？

Builder 按 Feature 的添加顺序生成嵌套骨架，并把相同覆盖关系的连续 layer 合并成区间；实例化时再按 mMinLayer 排列子节点。Feature 只增加容器边界，不改变 layer 本身的先后关系，因此最终仍满足从低层到高层的 Z 序。

6.4 第三轮追问：建树结果如何使用？

12. 建树完成后得到了什么？

不仅得到一棵 DisplayArea 容器树，还得到两类运行时信息：Feature 对应哪些 DisplayArea，以及每个窗口 layer 应落入哪个 DisplayArea.Tokens。所以 DisplayAreaPolicy 既是建树结果，也是后续窗口查找归属区域的接口。

13. 后续新增一个系统窗口，怎样找到它在树中的位置？

WMS 先根据窗口 type 算出 layer，再通过 RootDisplayArea.mAreaForLayer[layer] 找到对应的 DisplayArea.Tokens，将非应用 WindowToken 挂入其中。应用窗口是例外，它由 Task/TaskDisplayArea 这条链管理。

14. 多块 Display 会共用一棵 DisplayArea 子树吗？

不会。RootWindowContainer 是全局唯一根，但下面每个 DisplayContent 都拥有独立的 DisplayArea 子树和 Policy。初始化时循环创建，后续新增 Display 时也需要为新屏建立自己的层级。

15. 厂商怎样替换或扩展这套层级？

厂商可以实现自己的 DisplayAreaPolicy.Provider，并通过 config_deviceSpecificDisplayAreaPolicyProvider 让 fromResources() 反射加载。在自定义 instantiate() 中，可以调整 Feature、TaskDisplayArea 或 DisplayAreaGroup，但仍必须通过 Builder 的合法性校验，并保持 layer 顺序约束。

6.5 面试前必须分清的四句话

  1. WMS 构造器创建的是空树根和 Provider，不是完整的每屏层级树。
  2. fromResources() 创建工厂，instantiate() 才为当前 Display 建树并生成 Policy。
  3. 0～36 是窗口 layer，Feature 是 layer 覆盖规则，DisplayArea 才是真实树节点。
  4. 第 2.5 节负责备料并进入 Builder，第 3 章是在同一次调用中执行的具体建树算法。
