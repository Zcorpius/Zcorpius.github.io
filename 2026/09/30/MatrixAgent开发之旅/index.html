MatrixAgent 开发之旅

发表于 2026-09-30 | 分类于 AI-Agent
字数统计: 4.7k | 阅读时长 ≈ 16

1. 前言

一句话介绍：MatrixAgent 是一个运行在定制 Android ROM 上的 Agent 系统。它把对话、模型、工具执行、定时任务和跨应用会话放进一条可验证的链路：用户在 Matrix AI 中提出目标，系统级 Host 负责判断、执行和记录结果。

这个项目要回答的问题很直接：如果用户说“帮我找到李健的《传奇》并播放”，一个聊天框当然能回答“好的”，但它真的找到了哪一首？用户有没有确认？点击之后，播放器是否真的开始播放？应用切到 QQ 音乐之后，对话又到哪里去了？

这些问题的答案，决定了 Agent 是一个会说话的界面，还是一个可以承担任务的系统能力。MatrixAgent 的开发主线，也因此从“接入模型”延伸到“建立可信执行边界”。本文按一次任务的生命周期，拆解这个项目的关键设计、实现取舍和验证方法。

项目架构图。图中的业务域按职责分组，实际调用还包含回调和内部依赖。

2. 项目结构

2.1 模块分工

MatrixAgent 的运行环境是定制 ROM。仓库分成五个主要模块：

模块 做什么 产物
matrix-agent-launcher Matrix AI 工作区、任务中心、模型设置、悬浮角色和会话小窗 Launcher APK
matrix-agent-service-lib AIDL、Parcelable、版本协商和面向客户端的 Manager SDK AAR
matrix-agent-service 系统级 Host：对话、执行、计划、语音、存储、审计与权限判断 Host APK
ondevice MNN 推理的 Java / JNI 边界与 native 生命周期 Android Library
matrix-agent-test 可信与非可信客户端的跨 APK 契约验证 测试 APK

2.2 职责边界

这层拆分首先解决“权力放在哪里”。Launcher 负责把状态讲清楚：消息、候选、进度、失败原因、角色动作都属于呈现。Host 才拥有任务状态、数据库、能力注册表、模型配置和执行权限。客户端可以请求某项能力，却不能通过改一个 UI 状态就宣布它已经成功，也不能传入一个自称是系统用户的字符串来获得权限。

2.3 运行链路

Host 在目标 ROM 上使用 platform 签名与 android.uid.system，通过 ServiceManager 发布根 Binder，同时保留受签名权限保护的显式绑定入口。SDK 把 AIDL 封装成域 Manager，并处理 Binder 死亡与重连。入口处读取真实 Binder UID，再核对签名与权限；业务域继续基于当前请求的身份、用户和区域作约束。签名权限是入口，业务授权仍要逐次判断。

flowchart LR
    U[用户] --> L[Matrix AI Launcher]
    L --> S[版本化 SDK / AIDL]
    S --> B[Host 根 Binder
调用方身份与契约]
    B --> C[对话 / 计划 / 语音]
    C --> E[Agent Engine]
    E --> P[Policy + Capability]
    P --> R[真实 Provider / 回读]
    C --> D[(加密存储)]
    E --> D

2.4 运行前提

这里有一个必须说清的前提：它不是一只下载到任意手机就能工作的普通 APK。系统 UID、framework 编译桩、平台证书、系统权限与 SELinux 配置必须和目标 ROM 匹配。当前主要联调机是 Mi 9 SE / Android 15 / LineageOS 22.2；换 ROM 后，需要重新验证这些边界。

源码入口：Host 服务、调用方身份、SDK 连接管理。

3. 消息生命周期

3.1 统一受理

用户输入并不只有文字。按住说话的最终转写、唤醒后的最终转写，也会进入同一个 ConversationCoordinator。实时语音的 partial 只用于显示；只有最终被接受的文本才会成为用户消息并触发 Agent。这使“屏幕上闪过的识别中间结果”不会意外变成一次操作。

3.2 事务与串行

为什么要把“接受”写在执行前？因为模型请求可能排队，Binder 可能断开，应用也可能被系统杀掉。如果先执行、后补一条消息，用户看到的历史就无法可靠解释已经发生的副作用。这里先形成持久化事实，再开始执行；相同客户端操作 ID 的重试返回已有回执，不重新发起一次任务。同一会话用 keyed lane 串行处理，后一个请求能在真正出队时看到前一个请求的终态，排队时间也不会提前烧掉 Agent 的执行预算。

在代码层，这条链路有几条不能破坏的约束：

机制 要避免什么 失败时怎样收敛
幂等键与事务受理 Binder 重试生成两条消息、执行两次 重试返回已存在的消息和任务回执
会话串行 lane 后一轮抢在前一轮结束前读到旧历史 按会话出队；派发失败写确定终态
终态持久化与重启对账 进程死亡留下永远 RUNNING 的消息 恢复时核对悬挂记录，保留未知效果语义
附件与引用预校验 用户消息入库后才发现资料越权或不存在 受理前拒绝，不留下半条消息

3.3 终态与恢复

状态设计同样重要。ACCEPTED 表示已经受理，RUNNING 表示正在执行；COMPLETED、FAILED、CANCELLED、REJECTED 是确定终态。还有一个看似“不漂亮”却不能省的状态：EXECUTION_UNKNOWN。当写操作可能已经发出，而进程中断或回读失败时，系统没有证据说“成功”，也没有证据说“没做”。此时盲目重试，可能把一次动作变成两次动作；把它显示为“需要核查”，才是忠于事实的行为。

3.4 草稿与附件

草稿、引用消息、附件元数据和任务关联也遵循这个思路。引用在受理前核对是否属于同一会话；附件先核对 READY 状态与归属，再冻结这一轮可使用的上下文；已经提交的草稿不能被迟到的保存请求“复活”。这些细节看起来像 UI 功能，实际上都在维护一条消息的因果顺序。

源码入口：ConversationCoordinator、ConversationStore。

4. 执行与授权

4.1 Agent 主循环

进入 Agent 后，主循环是大家熟悉的结构：模型提出工具调用，系统校验并执行，工具观察再交回模型。真正决定可靠性的不是这个循环本身，而是每一圈都必须经过受信任的边界。

4.2 策略校验

PolicyEngine 的输入不是“模型保证安全”，而是模型给出的待审提案。例如：

  • 未注册或被标为禁止级别的能力直接拒绝；只读任务即使被模型提议了写工具，也不能执行。
  • 用户明确说了目标区域，工具参数就不能悄悄换成另一个区域；身份与目标区域还要各自通过授权检查。
  • 写入长期记忆需要用户明确要求；模型在资料里读到“记住我……”不等于用户授权。
  • 工具参数按严格 Schema 校验。参数错误可返回观察，让模型在剩余预算内修正；越权能力不会靠“换个参数”重试放行。

4.3 媒体确认

媒体播放是这个边界最直观的例子。用户说“播放李健的《传奇》”，模型可以理解标题与歌手，并要求 QQ 音乐搜索。但搜索页上可能有现场版、翻唱版或同名作品。Host 必须读取真实候选，将模型提出的目标与实际行核对，随后在下一轮请用户确认或选择。确认后再执行播放，并读取媒体会话状态。搜索和播放不能被合并成“模型觉得只有这一首，所以顺手点了”。新的搜索还会清理旧待确认上下文，避免用户一句“就这个”误确认上一次的候选。

这一设计也给错误分类留下空间：是模型理解错、策略拒绝、外部 App 搜索失败，还是点击后没有可验证的播放状态？把它们混成一个“工具失败”，排障和用户体验都会变差。

源码入口：AgentEngine、PolicyEngine、媒体 Provider。

5. 跨应用会话

5.1 会话交接

如果 Agent 打开 QQ 音乐，用户不应该被迫在音乐 App 和聊天页面之间反复切换。MatrixAgent 在交接外部应用前建立会话上下文，由 Launcher 显示一个可拖动的悬浮角色；点击角色展开的是原会话的小窗，可以看历史、补充输入、取消任务、回到全屏。

同一会话的两种呈现：全屏工作区与跨应用小窗。图片来自项目的设备采集记录。

5.2 状态投影

这里的关键不是画一个浮层，而是让浮层遵守 Host 的事实。全屏页和小窗共享消息来源；关闭窗口不会取消 Host 任务；正在编辑的草稿要能保留；Binder 断线要显示离线，而不是继续播放“正在执行”的动画。角色的 waiting、running、jumping、failed 和 review 对应任务阶段与结果，其中 review 用来提示“执行结果未确认”。动画是状态的投影，不是状态来源。

5.3 权限边界

实现上，小窗使用 TYPE_APPLICATION_OVERLAY，需要 Launcher 的悬浮窗权限。跨应用 UI 搜索另需 Host 的无障碍服务。角色看向屏幕触点的效果则是另一层平台能力：Host 用 InputMonitor 观察同用户、可信 Launcher 场景下的输入副本，不截获底层应用的原始事件；这条路径依赖 API 35+、匹配的 framework 与 MONITOR_INPUT 权限。权限不同，不能因为“有悬浮窗”就推断“能观察全屏触点”。

这也解释了为什么项目把“交接”单独做成域：何时显示、何时隐藏、窗口是否还能接收输入、交接失败后任务如何继续，都不能只靠 Activity 生命周期猜测。

源码入口：OverlayWindow、功能与交互说明。

6. 系统能力

Agent 真正进入日常使用后，问题不再都是“现在回答我”。它可能要在明天早上提醒日程，可能从麦克风接收请求，也可能需要记住用户亲自指定的偏好。MatrixAgent 没有给这些入口各造一套“简化版 Agent”，而是尽量让它们复用 Host 的身份、策略、预算、状态与存储语义。

6.1 计划调度

任务中心支持一次性、延迟、每天、每周以及日历实例绑定计划。Host 用加密持久化保存计划，并用一个物理业务闹钟指向下一次应处理的发生时间；广播到来后对账，再安排下一次。这样管理的是一组业务计划，而不是给每一条计划永久挂一个系统闹钟。

计划创建时冻结授权范围，触发时仍要核验用户、来源修订、能力范围和运行条件。自动任务使用独立会话；固定的“每日行程提醒”可并行读取今明日历，用确定性摘要发通知；“Agent 日程简报”则在授权范围内调用模型。两者都有步骤、依赖、预算、重试与取消，但并不开放任意代码执行。通知和播报分别记录交付事实：通知已经出现，不等于用户听到了播报；播报被勿扰或音频状态抑制时，也不能把整次交付写成完全成功。

任务中心：计划、运行记录与固定模板共同展示，历史保留执行时的模板版本。

6.2 语音与模型

语音的 PTT 与唤醒转写最终都提交到会话链；采音由 Host 管理，麦克风权限、前台服务、音频焦点和识别资源就绪都会返回明确状态。播报在已配置路径之间选择并回退，但“配置了 TTS”与“真实扬声器已播放”仍是不同证据。模型侧由 Host 管理云端 API、局域网服务与端侧 MNN；下载器提供断点续传、校验和原子安装，模型文件未完成校验前不会被当成已安装。

6.3 分层记忆

记忆划分为会话状态、长期偏好、长期事实和事件摘要四层。温控等会话状态只从成功且经过回读的工具结果更新；偏好和长期事实要由用户明确要求保存；事件摘要只保留有限、已核验的任务事实。召回还要受用户、区域和 Prompt 预算限制。附件文本也按归属与状态核对，切块检索后只把有界片段投影给模型，不能把附件里的指令当成用户的新授权。

这几处看似属于不同功能，设计原则却相同：模型上下文是帮助理解的材料，身份、授权和完成状态必须来自 Host 可核验的事实。

源码入口：ScheduleStore、VoiceSessionController、MemoryRouter。

7. 效果验证

7.1 评分依据

Agent 系统最容易出现的假象，是模型说“已经完成”，日志里也出现 SUCCESS，但外部世界没有改变。因此项目评测把三个东西分开记录：模型提出了什么、策略和工具观察到什么、实际副作用是什么。只有最后一项与预期一致，才能判定目标达成。

7.2 固定语料

固定语料覆盖媒体、计划和多轮对话：110 个独立场景，132 个用户轮次。离线模式每次运行两遍，使用生产 AgentEngine、PolicyEngine、能力定义与评分器，但不调用真实模型，也不访问外部服务；它适合检查“已知提案进入真实编排后是否安全、可重复”。真实模型模式另行采样，测试的是模型理解与提案质量。两者不能混成一个通过率。

一条很有代表性的反例是：模型给出正确的确认话术，任务状态也显示 SUCCEEDED，但低层端口没有播放副作用。评分器仍判失败。反过来，如果系统本应拒绝写入，实际却发生了副作用，哪怕回复在道歉，也要判为越权。计划任务同样以实际存储的触发时刻、时区与动作类型评分，不靠标题相似度蒙混过关。

7.3 真实模型

这套评测也暴露了真实问题。2026 年 9 月的模型采样里，schedule.create 曾出现绝对时间、周规则和授权范围与原话不一致的实际写入。项目随后在共享工具边界增加了字面计划约束；修复后的兼容 JSON 模式完整采样为 158/220 场景达成目标、错误参数实际写入 0。原生工具调用模式在前 160/220 个有效样本里有 125 个达成目标、错误参数实际写入 0，但后续遇到 HTTP 429 限流，报告保留为 complete=false。因此它还不是一份双模式完整质量基线。这个“没有测完就不写通过”的结论，比一个好看的百分比更有价值。

7.4 构建与真机

项目还有架构门禁和设备验证。./gradlew verifyArchitecture 会跑五个模块的非设备检查、SDK 发布依赖核对和离线评测；真机测试再检查系统签名、Binder、悬浮窗、输入链路、媒体应用与 Doze 等行为。不同日期、不同 APK 的专项结果不应相加成一个“大而全”的认证数字。阅读验证报告时，还应区分合成探针、JVM 单测和真实设备上观察到的外部效果。

评测设计：运行指南；最新这轮的范围与中断原因：智能层整改验证记录。

8. 总结

8.1 当前边界

MatrixAgent 已经形成了从输入、模型提案、策略、执行、回读到呈现的完整骨架，但它仍有明确边界：

  • 当前核心设备基线是 Mi 9 SE 的定制 Android 15 ROM；多 ROM、分屏和长时间压力还不能由这一台设备的结果外推。
  • 车辆控制默认使用 demo Provider。接入真实车辆，必须由 OEM/VHAL Provider 实现并复用策略、参数校验和回读契约。
  • QQ 音乐的搜索、独立确认与播放回读已有真机记录；B 站的候选搜索记录不等于视频打开闭环认证。
  • 语音资源、云端服务、端侧模型、麦克风和扬声器的组合，要在目标设备上分别完成认证；JVM 测试不能代替音频硬件与供应商可用性验证。
  • 定时任务首期面向已解锁、前台的 Android user 0；通知权限、精确闹钟权限与系统限制都可能让计划处于阻塞状态。

8.2 开发体会

回头看这个项目，最难的部分并不是写出一段漂亮的 Agent Loop，而是把“不确定”保存下来，把“可执行”放到系统边界内，把“已完成”绑定到回读和副作用上。对话、悬浮角色、工作流与模型市场让系统好用；事务、身份、策略、幂等、恢复和评测让它值得信任。

如果只记住一条经验，可以写成：Agent 负责提出下一步，系统负责证明这一步有没有资格执行，以及到底发生了什么。
